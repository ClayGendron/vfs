# Mounts

This page says how a [mount](../reference/glossary.md#mount) is built in the code, and why. It is for people who change VFS.

## The word

- **The class is `Mount`, and there is no "binding".** Plan 9 and Linux each keep a private live record of a mount and publish a separate description of it. Every layer is named for the mount: Plan 9's kernel record is `Mount` whether the `bind` call or the `mount` call made it, and Linux has `mount`, `vfsmount`, `statmount` and `mountinfo`. Neither uses "binding" as a noun.
- **"Bind" is kept free.** In Plan 9 and in Linux, to bind is to make something already in the file tree appear at a second path. VFS does not do that today, and the word is reserved for it.

## The class

- **`Mount` is a frozen dataclass with slots, not a `NamedTuple`.** Its `caps` field is computed once, when the mount is built, as `declared_caps - deny_ops`. Every permission check reads it. A `NamedTuple` cannot compute a field when it is built.
- **Its fields are `path`, `storage`, `permissions`, `deny_ops`, `no_overlay`, `owned`, `declared_caps` and the computed `caps`.** There is no second class for the policy and no third for the public view.
- **`Mount.to_payload()` returns the JSON-native form, a `MountPayload`.** A `Mount` holds a live storage object, so `json.dumps` cannot take it whole. `PermissionMap.to_payload()` uses the same name for the same job.
- **`remove_mount()` returns the `Mount` it removed,** so the caller can close the storage.

## Who may change a mount

- **A mount change is a write at its mount point.** Adding a mount needs what `mkdir` at the mount point needs, and removing one needs what `delete` there needs. Changing one in place with `update_mount()` asks the gate for a `delete` and a `mkdir` at the mount point, and for nothing more. That is less than a remove followed by an add. A mount beneath a `no_overlay` mount, a mount with mounts beneath it, and a mount whose `restore` is masked above can each be changed in place, and none of them can be removed and added again. A read-only parent takes no new mount, loses none, and lets none beneath it change. The root has no mount above it, so nothing above can refuse a change to the root. The two private methods `_attach_mount()` and `_detach_mount()` ask the gate themselves, so no caller goes around it.
- **A mask refuses a mount change only on the mount that holds the mount point. A read-only permission map refuses it from any mount above.** The gate reads the capabilities of the one mount that stores the mount-point directory, which are what its storage declared less its `deny_ops`. It reads the permission map of every mount above the mount point. So when `/a` is a mount, a root that masks `mkdir` does not stop a mount at `/a/b`, and a root that is read-only does.
- **A mount change needs `read_write` at the mount point.** `add_mount()`, `remove_mount()` and `update_mount()` take an `authority`, and a call that names none is treated as any verb is. The check runs before anything changes.
- **The rights are checked once, before the change.** A grant revoked after the check and before the commit does not stop that change.
- **Whoever holds `read_write` at a mount point can change that mount's policy.** `update_mount()` changes its mask, its permissions and its `no_overlay` in place, wherever the gate allows a `delete` and a `mkdir` at the mount point. An operator who wants a mount's policy kept does not give `read_write` at its mount point.
- **The storage that holds the mount point answers.** It answers through `holds()`, a question that reads the rights and changes nothing. `holds()` is not a verb, so a session cannot ask it. A storage that keeps grants and cannot answer refuses.
- **`add_mount()` makes the mount-point directory as the caller.** It is the caller's own `mkdir`, with the caller's own `parents`. A caller who may not make the directory may not mount there, and `read_write` at the mount point alone does not let a caller make a directory in a parent they cannot see. The check of the mount point, and the delete of its directory when the mount is removed, are the kernel's own work and run as the system actor.
- **If the mount that holds the mount point, or the mount at it, changes while the caller's rights are checked, the call refuses and asks for a retry.** All three mount changes keep what was judged and check it again under the mount lock, with no await between that check and the commit. The check compares the path and the storage object of the mount that holds the mount point, and the storage object of the mount at the mount point when one was there. So the same storage detached and attached again at the same path passes the check, and so does a change of a mount's policy in place. A different path or a different storage object means the rights were judged for a place that has changed.
- **Once a mount exists, no verb reaches the rights of its mount point.** `/data` then names two entries, the directory in the storage above and the root of the mounted storage, and `grant()`, `revoke()`, `grants()` and `set_posture()` reach the second. The right to change the mount is on the first, so that right is given before the mount is added or on a directory above it.
- **A session has no way to reach a `Mount`.** A `Mount` carries the storage object, and a session is what an agent holds. Reaching the storage would go around permissions. Only the file-system object has mount methods, and a test keeps it so.

## The posture of a new mount

A posture is the level everyone holds at a path and below. A new storage gives everyone `read_write`, and a posture does not cross a mount. So `add_mount()` takes `posture`, and with it a mount can be added closed. With no posture the storage is asked nothing and keeps what it holds, which is today's behaviour.

- **A posture that is given is in force before the mount is in the table.** `_attach_mount()` checks the mount point, then checks the table with no lock, reserves the storage object, reads the grants at the storage's root, checks the table again, and writes the posture unless everyone already holds it. Once the storage has been asked, whether or not it was written, the kernel checks the table and the mount point once more. Only then does it take the mount lock, check the table again and commit. The lock is not held across the write, because a posture write on a large stored storage is a relabel, and `close()` and every other mount change would wait for it. This is how the Linux mount API works too: the file system is configured while nothing points at it, and it is attached last.
- **A refusal before the write leaves the posture alone, and a refusal after it does not.** A wrong argument, a storage that keeps no posture, the rights, the gate, the `mkdir`, the first check of the mount point, and each check of the table up to the write all come before the storage is written. So does the storage's own refusal of the write. After the storage has been asked, the table and the mount point are checked again, and the table once more under the lock. A refusal there leaves any posture that was written, for the reasons the bullet on a failed posture write gives.
- **The table is checked again just before the write, and the mount point again once the storage has been asked.** The grants read is storage I/O, and the table can change while it runs. `close()` can return, the gate can tighten, or another call can take the mount point. So the table checks run again with no `await` before the write, and a table that no longer takes the mount is refused before the storage is written. The read and the write can each take a long time, the write as long as a relabel. While they run, a file can be written into the mount-point directory, the directory can be deleted, or a mount can be added above it so that another storage holds the mount point. A mount committed then would hide the file, or sit where no directory is. So whenever a posture is given, once the storage has been asked, the table is checked again and the mount point is checked again with the same check as before. This holds whether or not anything was written, since a slow read opens the same gap as a slow write. That costs two more calls on the storage that holds the mount point. The window between that check and the commit is then what it is with no posture, a few awaits wide. A call with no posture asks the storage nothing and makes no second check.
- **The posture is set as the caller, never as the system actor.** The storage judges the write as it judges `set_posture()`, so the caller must hold `read_write` at its root. On a new storage everyone does. The right to change a mount is judged in the storage above and says nothing about the mounted one. A write made as the system actor for a named caller would let that caller widen a stored posture that `set_posture()` refuses them. The caller gets no grant in the mounted storage, since a mount change that wrote a grant would be a second way to grant.
- **The storage is written unless a read shows that everyone already holds the posture at its root.** The kernel first reads `grants` at the root, as the caller, when the storage declares `grants`. It writes in three cases: the storage holds another level there, the storage does not declare `grants` so nothing can be read, or the read failed. A `set_posture()` to the level already held still rewrites every row beneath it, so a process that names its posture at every start would relabel the whole storage at every start. The read is made as the caller, because a read made as the system actor would tell a caller who holds nothing whether a guess matched a hidden posture. So a caller who can read nothing in a stored closed storage is refused even the posture it holds, and adds the mount with no posture.
- **A storage that keeps no posture refuses the argument before anything is made.** It keeps a posture when it declares `set_posture` and has the grant methods. Otherwise `add_mount()` raises `MountError` with `unsupported`. A storage that keeps no grants serves every row to every caller, so ignoring `posture="none"` there would return a mount that looks closed and is open. The declared capabilities decide, and neither the mask nor the mount's own permissions stop the posture.
- **A failed posture write adds no mount, and no failure puts a posture back.** The storage's refusal is raised as a `MountError` with the mount's path in front of its paths. The directory stays, as after any failed mount. The storage is in no table entry when the call fails, so the posture left behind opens nothing through this kernel. Putting the old posture back would be a second write and a second relabel that could fail too, and on a shared database it could overwrite a posture another process set in between. A database storage commits the posture row before it relabels. If the relabel fails, a retried `add_mount()` finds the posture in force and writes nothing, and `set_posture()` at the mount's path finishes the relabel.
- **While a posture is being set, no other call can mount that storage object.** The kernel keeps the `id` of each storage whose posture an `add_mount()` in flight is writing. The table checks refuse such a storage with a retry, whether or not the second call names a posture. Without the reservation, two calls that mount one object at two paths with two postures could both write, and the one that commits could hold the posture the other asked for. The reservation is by object, in one kernel. Two storage objects on one database are not seen, and each write there is an ordinary `set_posture()` on shared state.
- **A posture is not a field of `Mount` or `MountPayload`.** Policy lives on the mount and state lives on the storage. A posture changes through `set_posture()` while the mount stays the same object, so a field would be out of date after the first change. `update_mount()` takes no posture for the same reason, as a tmpfs remount does not take `mode=`. Rebuilding a table from `mounts()` needs no posture either, because each `Mount` carries its storage and the storage carries its posture.

## What a listing shows at a mount point

A mount point names two entries. The **covered directory** is the empty directory stored in the storage above. The **mounted root** is the root of the storage attached there. `MountListing` in `vfs/listing.py` holds the rules, and the kernel's `ls`, `stat`, `tree` and `glob` call it. `vfs/mounts.py` holds the `Mount` and the checks a mount change passes, and `vfs/listing.py` builds on it, so the mount never depends on how a listing shows it.

- **The row at a mount point is the mounted root.** It is the row `stat` of the mount point returns to the same caller, so one path shows one entry whichever verb reads it. Plan 9 does this on every directory read, where `mountfix` replaces the entry with a `stat` of what is mounted. On Linux `getdents` returns the covered entry and `stat` crosses into the mount, so `ls -l` shows the mounted root too.
- **The covered directory is never listed.** `ls`, `tree` and `glob` drop the row at a deeper mount's own path, before any rows are merged. On both systems the covered directory cannot be reached while the mount is on. Every verb drops the rows strictly beneath a deeper mount, but only the listings drop the row at the mount's own path. A deleted row at that path in a trash view, and a node at that path in a graph walk, are not the covered directory, and they stay.
- **One listing reads one mount table.** `MountListing` is built from a copy of the table each time the table changes, and a call reads that copy from start to end. A mount added or removed while a listing waits on a storage changes the next listing and never that one. `glob`, `grep` and `search` take the copy when they start, and it serves the whole call. It serves the plan of which mounts answer, the mount that holds each root, the probes of the roots, the calls on the storages and the merge. `MountListing.holder` and `MountListing.beneath` answer where a path lives for every verb, so there is one implementation. `holder` cuts the path at each `/` and looks each prefix up in the table as plain text, because a prefix of a checked path is never checked again. So finding the mount of a row costs the depth of its path, makes no call to the path check, and never costs the number of mounts. A table that holds only the root answers at once.
- **The mounted storage never hides a mount's name.** No rights question is asked of it. It decides only how much of the row a caller sees, and a caller who holds nothing gets a bare row with only `path` and `kind`. On both systems the name belongs to the directory above, and the mounted root's permissions never hide it. `stat` and `locate` already showed every mount to every named caller.
- **A mount that gives no row still shows, as a bare row.** That is a mount that refuses the caller, one that cannot answer `stat`, one whose storage fails, and one whose root is not a directory. Only a failure adds a record, a warning at the mount's path, and the records of a `stat` that succeeds are kept. A row that comes with a failure is not trusted, so a mount whose `stat` fails shows bare even when the answer held a row. A mount that cannot answer `stat` is not asked and adds no record. A dead network mount on Linux still shows its name in the directory above. A storage that raises an ordinary exception, and not a transport error, has a fault, and the exception is raised out of the listing as it is out of any verb.
- **A directory that leads to a mount point always shows.** The rule is that a bare row stands in for a `not_found`, and for nothing else. `ls`, `stat`, `tree`, `glob` and `locate` answer for such a directory from the mount table when its storage gives no row and says nothing worse than `not_found`. Each target is judged on its own errors. An error is raised for its `data["vfs.target"]`, or for its own path when the storage set no target, and when the call names one path every error is raised for that path, so one path and a batch of it give the same answer. Any other failure, such as a refusal, withholds the bare row of the target it was raised for, and that target's answer stands as the storage gave it. A failure that cannot be tied to a target, because it names no path or the storage's own root with no target as a transport failure does, withholds every bare row. `locate` reports a refusal in `note`, and otherwise says the directory exists. One function decides this for `stat` and for `locate`, on the error with the mount's path put back, so the two agree. In `tree`, each mounted storage's answer is judged by this rule before any directory it holds is added, so a storage that failed adds no directory and no mount point beneath it. A `not_found` raised for a directory above a mount, and not withheld, is dropped. That directory gets one bare row for each time the batch names it beyond the rows the storage gave for it. A `not_found` raised for any other path, or for none, stands, even when it names the same missing directory. The failures are matched once, so a batch costs its length. Plan 9 and Linux let a caller walk to a mount through a parent they cannot read, given walk or search permission. VFS has no such permission, and this rule serves in its place. It is the one rule here that the two systems do not have. One gap is left. For a caller who holds nothing on such a directory, `stat` of a missing path beneath it still names the directory as the first missing part of the path.
- **A refusal of the listed directory stands.** The anonymous caller on a closed root is refused and learns no mount name. In `ls` and `tree`, the storage above and the mounted storages are asked at the same time. When the storage above refuses, the answers of the mounted storages are dropped. `glob` asks every storage at once and merges what answers, so it decides for each mount point, and each directory above one, whether the listing of its parent failed. A failure removes only the paths in the region it describes, in the mount that holds them. A failure of a mount's `glob` is the region at the path it was raised for, and that path is in it. A failure of a root's probe is the region strictly beneath that root, so the root's own row is kept. A failure that cannot be tied to a path or a root is the whole of the mount that failed. A warning removes nothing.
- **Each mount point costs one `stat` of the mounted root.** `ls` of a directory with `k` mount points makes `1 + k` storage calls. `tree` over `m` mounts makes `1 + 2m`. `glob` makes one more for each mount point its pattern matches, and no more than `max_count` rows can use. The mounted roots are asked after the storages answer, and only for the mount points that are kept, or the first `max_count` of them, so no mounted root is asked for a path the caller does not get. That costs one round trip more than asking them at the same time. No storage is called once the kernel is closed. Every call on a storage goes through `_call_storage`, which answers the closed refusal, `backend_unavailable`, when the mount table is empty, with no `await` between that check and the storage. A mounted root refused this way shows bare with a warning, as any mounted root that cannot answer does. A directory that holds and leads to no mount point costs what it did, because the kernel works out the directories above a mount, and the mounts in each directory, once when the table changes. `ls`, `stat` and `tree` take one hop of the call's budget, so a storage that loops back on its own kernel ends in `budget_exhausted` and shows bare with a warning. Only a verb's own entry into the kernel takes a hop. The probe of a search's roots runs inside the hop the search holds and takes none.
- **`glob` judges a mount point itself.** The storage above holds a directory that is never shown, the mounted storage does not list its own root, and a directory above a mount point is returned by its storage only to a caller who may see it. The kernel tests each mount point, and each directory above one, against the pattern, the exclusions, the extension filters and `kind`, with the same matcher a storage uses on its own rows. When the call names roots and no mount point lies beneath them, nothing is judged.
- **In a batch, a directory that holds or leads to a mount point is answered once.** `stat` with `observations` is one storage call, as before. `ls` with `observations` lists such a directory on its own, however often the batch names it, and sends the other rows in one call. Its rows come after the other rows of the same mount, once for each time the batch names it, and its errors are recorded once.
- **Nothing was added to the storage protocol.** A storage does not know it is mounted.

Two things still differ from Plan 9 and Linux. `remove_mount()` deletes the mount-point directory, where `umount` leaves it. And a listing waits for every mounted storage with no time limit, as `tree` and a search of several mounts already did.

## Rebuilding a mount table

`mounts()` returns enough to build the same table again. Add every mount bare, then set each mount's policy with `update_mount()`. A mount that is read-only, that masks `mkdir` or that is sealed with `no_overlay` refuses new mounts beneath it, so the policy goes on last. Set the policy of the deepest mount first and the root's last, because a read-only mount also refuses a change to the mounts beneath it.
