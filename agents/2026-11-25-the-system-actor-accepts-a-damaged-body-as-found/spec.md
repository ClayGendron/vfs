# Only the system actor can accept a damaged body as found, and history records the new version

A draft, written on 2026-11-25. It is not reviewed, and nothing is built. Checked against `dev` at `27f3d24d`. This is unit 175-3 of story K3, gate b, converted from [spec 175](../../context/specifications/archive/175-integrity-verify-on-read-and-scrub/spec.md) under roadmap ruling D58. It rests on the checked read, the damaged pre-image history mint and the storage's version identifier.

## The outcome wanted

After an ETL job intentionally replaces a file's body through SQL, a checked read reports its old and actual hashes. Trusted host code can call `await fs.accept_body("/feed/orders", authority=Authority.system())`. If the file was at version 7, its bytes stay as found, the result names version 8 and its fresh vid, and the next checked read serves those bytes. The displaced history record keeps the failed hash, the bytes and the number 8 as evidence of the explicit acceptance. Repeating the call on the now-healthy file makes no further version. A caller with an ordinary grant, even the owner on a fully writable mount, cannot use this operation.

## The problem

The reference deployment has ten million files and a nightly million-file ingest (`AGENTS.md:74`, `AGENTS.md:85`). A single file changed intentionally outside VFS needs a point operation. Simply replacing its hash erases the old evidence. Reading the body out and writing it back risks blessing an entirely different edit between the two calls.

Executed against dev on in-memory SQLite 3.46.1: the public filesystem created `/sample` with text `old` at version 1. A raw update to `as found` left the version untouched. The public read served that text. Writing the same text back advanced the entry to 2 and left zero rows in `vfs_versions` because the mint compares the measured pre-image with the incoming digest (`src/vfs/storage/backends/database/versions.py:147`). A named caller's public `add_member` returned `vfs.permission_denied` with neither path nor data.

## Decisions

1. **Add one flat, single-file verb, `accept_body(path: str, *, authority: Authority | None = None) -> Result`.** Register it on the async and sync filesystems and their bound sessions. Sessions take only `path`. A caller supplies no bytes, replacement digest, batch or version argument. The verb accepts the first eligible body the call observes, subject to decision 4. This gives a host an explicit operation it can mask or omit from an agent surface. A flag on ordinary `write` would make a body-free privileged form part of every write interface. The name follows the verb–noun rule in [the naming guide](../../documentation/maintainers/how-we-name.md) and identifies what is being accepted.

2. **Gate the operation on resolved system authority at both dispatch and storage.** A well-shaped call resolves its explicit, session-bound or kernel-default authority by the ordinary rules (`src/vfs/authority.py:227`). Before resolving a target or dispatching to any backend, require `who.is_system`. All other actors receive the same `Result(ops=("accept_body",), ...)` with one `vfs.permission_denied`, detail `accept_body is reserved to the system actor`, no row, path, data or integrity evidence. No mount posture, owner floor, service identity or group grant passes the test. Direct storage requires positive system authority too. Its optional `authority=None` returns the same refusal before first touch, rather than passing through the older trusted default in `backend.py:1179`. An explicitly configured system default at the public filesystem is a resolved authority. Only the explicit verb can enter this path.

3. **Register an optional mutation capability with the standard point gates.** Add `accept_body` to `Op`, `MUTATING_OPS`, `DEVELOPER_OPS`, `VERB_RUNGS` with descriptive `Needs("read_write")`, and `PARAMS` with the required path. The actor gate remains decisive. Use the existing single-path router, mount-local reserved-space check, composed write permission map and normal result rebasing (`src/vfs/base.py:1826`, `:2705`, `:2852`). System calls get the existing `vfs.unsupported` on masked or incapable mounts, `vfs.read_only` on read-only paths and `vfs.invalid` for a root or reserved mutation address. Enforce the same local grammar on direct storage. Give the optional seam a runtime-checkable `SupportsAcceptBody.accept_body(*, path: Path, authority: Authority | None = None)`, returning an awaited `Result`. Register that family alone for the new op and subtract its op from the `SupportsMutation` family mapping (`src/vfs/storage/protocol.py:603`). Thus existing mutation backends keep their capabilities. Advertise it on SQLite and Postgres. Withhold this optional op on the unknown dialect floor until its body lock and byte comparison are proven. If the op group registry has landed, place it in `history` beside `restore`. Only the Python faces expose it, following `DEVELOPER_OPS` at `src/vfs/ops.py:101`.

4. **Prepare one finding and commit only for those exact bytes.** Under an ordinary read snapshot seek the live path, its entry id, version, source, recorded hash, authoritative body row key and payload. Select only the authoritative body using the source discriminator, so a bytes file's rendering cannot enter the digest. Measure it by the shared rule before taking a writer lock. On eligible damage retain the exact octets and the tuple of entry facts for the whole call. In a fresh writer transaction lock the entry by id, verify its live path, version, source and old hash, then lock the authoritative row by primary key subject to exact byte equality with the prepared octets. Use `lock_rows` from `src/vfs/storage/backends/database/dialects.py:514`. Compare a blob directly, SQLite text via `CAST(content AS BLOB)`, and Postgres text via `convert_to(content, 'UTF8')`. Select only the matching key in the locking query. SQLite's writer uses `BEGIN IMMEDIATE` and Postgres locks the two base rows independently, avoiding a lock on the nullable side of an outer join. The two matching observations confirm the fault and prevent a raw body-only change from slipping past an unaltered vid. Any changed or vanished target returns a path-local `vfs.conflict` with the instruction to inspect the file again and zero mutation. A database serialization failure redrives only with the original prepared tuple under the host's configured retry bound (`engine.py:336`), never with a newly discovered body. A rival commit after this commit is a new possible fault, detectable by the ordinary read.

5. **Accept a representable body with a recorded, unequal hash.** A valid live file with a matching digest returns one `unchanged` row from its read snapshot. Its version and vid stay fixed. A directory yields `vfs.wrong_kind`. An absent or tombstoned file at a live address yields `vfs.not_found` and is never revived. For a missing authoritative row or a present body with no recorded hash, two equal findings return the `vfs.unavailable.integrity` finding of 175-1 decisions 5, 7 and 9. A changed finding during confirmation returns a conflict and cannot turn that call into an acceptance. Present empty text and empty bytes have genuine SHA-256 digests and may be accepted. SQLite text that fails strict UTF-8 decoding cannot become a valid text file by restamping it. For a mismatched or unhashed such row, return the corresponding confirmed finding with its existing hash fields. If even its stamp matches the malformed text, return nonretryable `vfs.unavailable` with detail `the stored text is not UTF-8`. None of those refusals carries body bytes. Replacing the body from a trusted source remains available under 175-2.

6. **Keep a durable distinction between explicit acceptance and ordinary overwrite.** In the transaction of decision 4, save one whole pre-image using 175-2's damaged-history path, even though its payload bytes equal the new live body. The old hash remains the recorded one. Add nullable integer `accepted_as_version` to `vfs_versions` and `Version`. Set it on this displaced snapshot to `n + 1`, where `n` is the entry version matched at commit. Every other mint leaves it null. This distinguishes a system overwrite with independently supplied identical bytes from a deliberate acceptance, even after the live file changes again. Use the mint's existing timestamp and grant revision, the accepting system actor and system provenance, and no subject rows (`src/vfs/storage/backends/database/versions.py:86`, `:183`, `:194`). Under 180-1 decision 5, complete the prior body-start row with the old hash, bytes and acceptance link, keeping its original writer, then mint the new live-body record under the system actor at the new label. The link names the actual successor even across a metadata-only label gap. In that listing expose the marker on a marked row as an additional populated field, leaving the unmarked row's specified projection intact. Bump the format once from the then-current value and follow the normal first-touch mismatch refusal (`src/vfs/models/rows.py:135`, `src/vfs/storage/backends/database/engine.py:922`). Never infer a marker from old data.

7. **Update the live material and publish one result after commit.** Keep the entry id, path, owner, grants, source, file type and authoritative bytes. Change the file's version once and set `content_hash`, `size_bytes`, `lines` and `updated_at` by the material write's rules. For bytes, discard any prior text rendering, set lines to zero and queue rendering in the usual pending state. Apply the same invalidation as an overwrite to the chunk, encoding, indexing and render state (`src/vfs/storage/backends/database/writes.py:1308`). Never rewrite the authoritative body, update a parent membership stamp or synchronously rebuild a derived row. A success returns one body-free observation with path, kind, status `updated`, correct size, new hash, version and its storage-minted vid, plus the old finding as a warning under 175-2 decision 8. The healthy repeat has the same fields with status `unchanged` and no warning. Commit history, invalidation and live stamp together. A failed guard, failed insert, cancellation before commit or rollback exposes no partial update or warning.

## Cost

Charge the new work to explicit repairs. For `r` successful acceptances of bodies totalling `B` bytes, the implementation measures `B` bytes once outside the write transaction, compares at most `B` more in the guarded body lookups, and archives `B` bytes in displaced snapshots. The ordinary 150,000 daily calls and the nightly million-file writer incur zero extra hash passes or lookups for this verb. A hundred accepted median 4 KB files thus cost about 400 KB in each pass and about 400 KB of history payload. There is no multiplier in corpus size, directory depth within storage, or prior history length.

Per attempt, budget one point query for preparation, one point lock each for the entry and its body, one grant-revision lookup, one history insert, one live update and at most one rendering delete. The later history layout substitutes a completion and new-head insert for the single snapshot insert. Count readiness, transaction boundaries and existing SQLite statistics separately. An unchanged point lookup has no writer transaction or insert. Refused non-system calls issue zero statements. The shape uses constant bind counts, independent of payload length and below both served engines' declared parameter budgets. Memory is proportional to one file, including a bounded number of payload copies during encoding or binding. A single file can exceed `BLOB_PAGE_BYTES`, as in the existing history mint. Use the checked read's `MEASURE_OFFLOAD_BYTES` cutoff and at most one worker hop for the prepared body. No hashing, backoff, scan or index work holds a shared lock. The entry and body locks on Postgres and SQLite's writer slot cover only the final one-file comparison and commit, including storage of its snapshot. A large file makes that commit larger. Plain snapshot reads take no writer lock.

## Choices to confirm

1. **Spelling and breadth.** Take the additive, single-path `accept_body(path)` on the developer plane over a flag on `write`. It keeps body input and the existing write capability intact. A batch form or an expected digest can be added later without changing single-file behavior.
2. **Eligible damage.** Take a present body with a recorded mismatch. Leave a missing hash and invalid text for explicit replacement. Extending eligibility to an unhashed body is reversible before release and can be added later without manufacturing evidence of an earlier comparison.
3. **Recording the act.** Take the nullable successor label on the displaced snapshot. Inferring acceptance from two hashes and the system actor would conflate it with a supplied-body overwrite. A separate audit table would duplicate the entry and version keys. The additive field keeps each existing mint valid.
4. **Omitted authority on the low-level seam.** Take a refusal for this new verb. Adopting the older trusted-storage convention that `None` means system would admit more callers and can be added without revoking a capability already in use.
5. **Generic capability.** Withhold the optional repair on the unknown dialect floor. Advertising it there would require a demonstrated, byte-exact comparison and a body-row lock respected by raw writers. Adding it per proven profile later leaves today's core floor intact.

## One line

The system actor can accept one mismatched body as found, advancing its version and leaving the failed hash and an explicit link to the accepted version in history.
