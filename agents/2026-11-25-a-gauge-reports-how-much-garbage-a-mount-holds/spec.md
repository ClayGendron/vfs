# A storage reports the trash and history held by one mount in two statements

A draft, written on 2026-11-25 and checked against `origin/dev` at `27f3d24d`. It is not reviewed, and nothing of this unit is built. Unit 180-6 serves [roadmap gate 0.2](../../context/standards/roadmap.md), with no named story. It converts [specification 180 §6 and criteria 22–23](../../context/specifications/archive/180-history-pack-on-reindex-and-the-bounded-sweep/spec.md) and [task 4](../../context/specifications/archive/180-history-pack-on-reindex-and-the-bounded-sweep/tasks.md). It rests on the pack writer’s stored sizes and the retention pass’s expiry rule.

## The outcome wanted

A deployment holding a storage object can call `await storage.count_garbage()` before or after maintenance. A directory deleted with two children contributes three tombstones, one root and, once it expires, three expired rows. Packing a smaller patch reduces the stored history bytes while preserving the logical bytes. An empty mount gives a complete report in the same two reads.

## The problem

A completed rebuild tells what that pass did. It cannot say how many bytes history occupies now, and subtracting two retention samples cannot say how many rows a pass removed while other callers wrote. On dev the optional maintenance family has only `rebuild` and `refresh` (`src/vfs/storage/protocol.py:530`). The version mint writes whole replaced bodies (`src/vfs/storage/backends/database/versions.py:160`), and format 28 has neither pack counter (`src/vfs/models/rows.py:135`, `:486`). Fetching individual rows or sizes through listings would put the reference deployment’s ten million files into the measurement path.

## Decisions

1. **Expose one optional storage method.** Add runtime-checkable `SupportsGarbage` with `async def count_garbage(self) -> Result` beside `SupportsRebuild` and export it from `vfs.storage` (`src/vfs/storage/__init__.py:21`). Adding a separate protocol preserves rebuild-only backends. The holder of the storage object has the same trust as for `DatabaseStorage.rebuild()` (`backend.py:1147`). There is no path or authority parameter, router or session method, Op, family registration, program, tool or namespace row. [D53](../../context/standards/roadmap.md) at line 1264 is a lean about management access to the action log. It grants no reader access to mount-wide counts. The [naming standard](../../documentation/maintainers/how-we-name.md) uses a verb for an action. Hence `count_garbage` instead of the archive’s bare noun `garbage`. No existing caller needs an alias.

2. **Return one report from one read snapshot.** Use `DatabaseStorage._execute` with the storage’s mapped tables in a single callback. Begin after normal first touch, with the read options of `backend.py:1346–1378`. SQLite opens a deferred read transaction and Postgres pins `REPEATABLE READ` (`engine.py:981`, `dialects.py:420`). A successful, warm, uncontended call issues exactly two data statements, in the order below, including when either table is empty. Transaction control and first-touch provisioning are separately identifiable. Retries rerun the pair from the beginning and reuse the original cutoff. A failure returns the existing classified read error with no partial report, and cancellation releases the read session through the existing runner. A generic profile has no declared nonblocking read snapshot (`dialects.py:449`). At the method’s capability gate return `vfs.unsupported` on that floor before either aggregate. This optional read changes no core verb. A successful result is `Result(ops=("count_garbage",), garbage={...})` with empty observations and exactly the nine keys below. Result already accepts string operation names and extras (`src/vfs/results/envelope.py:362–364`).

3. **Count every deleted entry, including members and older generations.** The first aggregate reads only `vfs_entries WHERE deleted_at IS NOT NULL`. Use `count(*)` for `tombstoned_rows`, count the rows satisfying `trash_root_id = entry_id` for `tombstoned_roots`, and those satisfying `deleted_at < :cutoff` for `expired_rows`. Take `min(deleted_at)` for `oldest_tombstone`, rendered as a UTC ISO 8601 string with `+00:00`, or null on empty. Treat SQLite’s zone-less returned timestamp as UTC and convert an aware value to UTC. Use SQLAlchemy’s timestamp type for the bound and the minimum (`rows.py:213`). The strict boundary includes neither a live row nor a row exactly at the cutoff. Use the retention calculation from 180-4 in both callers with a single UTC instant per call and the mount’s actual `_trash_days`. A retention longer than the representable past has zero expired rows, equivalent to binding the earliest representable UTC instant. No epoch floor excludes valid earlier tombstones. A normal cascade gives root and members one timestamp (`trash.py:167`, `:200–205`), so the row count and the roots count answer different questions. Never deduplicate by path, join to roots, or assume the next pass will remove the measured number.

4. **Count physical version records once and charge only completed payloads.** The second aggregate reads `vfs_versions` once. `version_rows = count(*)`, including the live-body attribution marker. Over completed rows only (`NOT body_is_live`), `version_snapshots` counts `is_snapshot`, `version_unjudged` counts `NOT packed`, `version_logical_bytes` sums `size_bytes`, and `version_stored_bytes` sums `stored_bytes`. These metrics include retained deleted entries. A newest whole, hot version is unjudged by design. The live marker points to storage outside history, so it contributes only to the physical row count. The two sums count payload bytes, including zero-length snapshots and UTF-8 patch bytes, and exclude table, index and attribution overhead. Use conditional counts and integer sums with zero on empty. Return all counts and byte totals as Python integers without narrowing to 32 bits. No SQL selects a body or computes its length. A physical version row awaiting orphan reclamation contributes under the same rules until removed. There is no orphan classifier, owner join, or anti-join.

5. **Keep the measurement independent of the cleaners.** Run it only when a deployment asks. Use the branch draft’s `expired_rows` consumer without calculating the same metric again. Only a committed retention pass can publish its finish time and removed count, including a successful pass that removed zero. A change in a gauge, `oldest_tombstone`, and a zero backlog are each insufficient evidence of a run. Add no historical fields, run-record read or write, scan inside `refresh` or `rebuild`, or automatic polling. Source §6 and the branch draft’s outcome give this division of work.

## Cost

Per requested corpus sample, with `T` tombstoned entries and `V` physical version rows, the sparse-trash plan visits the deleted-side index’s `T` entries and fetches their root identities, then scans `V` version records. The existing partial index is `ix_vfs_entries_deleted_at` (`rows.py:441`). On a mostly deleted mount Postgres may choose an entry-table scan. Each statement returns one row, the whole result holds nine scalar values, and there is no grouping, sorting, membership list, Python row loop or transferred body. One cutoff bind suffices with fixed SQL constants in the conditional aggregates. Check compiled width against the host’s declared `parameter_budget` (`engine.py:250`), including SQLite’s tighter variable limit. The two-statement budget bounds round trips, not rows or disk pages.

At one host-requested daily sample, cost is two statements and one pass over history. Ten million live file markers alone mean at least ten million history-row visits before replaced versions. Calling it on the reference deployment’s 150,000 daily verbs would multiply that lower bound to 1.5 trillion visits (`AGENTS.md:74–98`). It adds zero work per ordinary call, file write, index visit or batch. The reader holds no writer slot, topology lock or lease. Its snapshot can retain old pages for the duration of the scan. It is cancellable, with no write to finish.

## Not checked

Executed on file SQLite 3.46.1 and disposable Postgres 16.2: real dev writes created 1,024 live controls and the files for a three-row cascade and two separate deletes. After those deletes, the probe assigned explicit UTC timestamps before 1970, at the cutoff and just after it. Through the real `_execute` read runner, the proposed entry aggregate returned five tombstones, three roots, three expired and oldest 1969-12-31 UTC on both engines. SQLite searched and Postgres scanned `ix_vfs_entries_deleted_at` on the analyzed fixture.

The version aggregate was a SQL prototype on a stand-in table, since dev lacks the pack and live-marker columns. An empty table produced five zeros. A live marker, a hot 10-byte snapshot, a judged 3-byte patch for 12 logical bytes, and a judged empty snapshot produced `(4, 2, 1, 22, 13)` in decision 4’s order. Both engines recorded two SELECTs, plus SQLite’s explicit BEGIN. A rival committed removal of one tombstone and insertion of a seven-byte version between the reads. Both returned the old pair and showed four tombstones and version totals `(5, 3, 2, 29, 20)` at the next call. Integration with pack and sliced retention, reference-scale plans, fault injection, the full test suite and unknown drivers were not run. The first two dependencies are unbuilt, the probe used a small isolated corpus, and only the served engines were provisioned.

## Choices to confirm

1. **Where the gauge is called and what it is named.** Take the optional storage method `count_garbage()`, with the source’s `garbage` report key. A routed management verb or a `/.vfs` view would require a disclosure policy. Either can consume the storage read later. The archive’s `garbage()` is a bare noun for an action. The verb spelling is reversible before the API ships.
2. **What a live attribution marker contributes.** Take the actual physical row in `version_rows` and exclude it from the other four history measures. Excluding it from all five would conceal a row per file. Counting its metadata as an unjudged stored body would charge bytes and work that neither packing nor retention finds there. A separate completed-row count can be added later.
3. **What the generic floor promises.** Withhold this optional read where the profile cannot promise both a consistent snapshot and a reader that proceeds beside a writer. Serving it at an unknown default isolation could give a pair that never existed. Enabling a further profile after the same two-connection test is additive.

## One line

One storage call returns the deleted rows and history bytes a mount holds now, with two aggregate reads from the same snapshot.
