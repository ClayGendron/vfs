## A. The typed request

- READ. A request is the four-tuple principal, action, resource, context (`cedar-policy-core/src/ast/request.rs:35-50`). Each of principal, action and resource is an `EntityUIDEntry`, either `Known { euid }` or `Unknown { ty: Option<EntityType> }` (`request.rs:72-88`); the context is `Option<Context>`, where `None` means "unknown, leave a residual" (`request.rs:47-49`), and `Context` is a concrete record or a `RestrictedResidual` that must contain an `unknown` (`request.rs:294-303`). The public wrapper is `cedar_policy::Request` (`cedar-policy/src/api.rs:5401`).
- READ. Entities are a separate store passed beside the request, not inside it: `Authorizer::is_authorized(&Request, &PolicySet, &Entities)` (`api.rs:1136`). An entity is uid, attributes, parents (ancestor uids) and tags; the JSON form is in the doc examples at `api.rs:761-829`.
- READ. Validation is at construction, not at authorization. `Request::new(principal, action, resource, context, schema: Option<&Schema>) -> Result<Request, RequestValidationError>` (`api.rs:5442-5457`): with a schema the request is checked, and an invalid request never exists. The check is the `RequestSchema` trait (`request.rs:641-666`), implemented by the schema in `cedar-policy-core/src/validator/coreschema.rs:195-260`, plus a no-op `RequestSchemaAllPass` (`request.rs:670`). The errors are a closed enum (`coreschema.rs:410-455`): undeclared action, `external` action, undeclared principal or resource type, a principal or resource type not in the action's `appliesTo`, a context that does not match the action's declared context type, an invalid enum entity id. Each variant carries the offending value and a `miette` diagnostic.
- READ. The schema types each action: `ActionType { applies_to: Option<ApplySpec>, member_of: Option<Vec<ActionEntityUID>>, external }` (`cedar-policy-core/src/validator/json_schema.rs:991-1010`), and `ApplySpec { resource_types, principal_types, context }` (`json_schema.rs:1172-1181`). So the action decides which principal types, resource types and context shape are legal. `member_of` makes actions a hierarchy (action groups); the schema computes its transitive closure and refuses a cycle (`cedar-policy-core/src/validator/schema.rs:1449-1453`), and materialises action entities with those ancestors (`schema.rs:1190-1215`), so a policy may say `action in Action::"writeOps"`.
- READ. Entities are validated against the schema when built with one (`Entities::from_json_str(json, schema)`, `api.rs:782`); since 3.0.0 the schema's action entities are added automatically and entities are checked (CHANGELOG lines 1044-1048, #360).
- READ. Policy validation modes: `Strict` (default; type-correct and of a restricted analysable form), `Permissive` (type-correct only, behind the experimental `permissive-validate` feature), `Partial` (incomplete schema, "no formal guarantees", behind `partial-validate`) (`api.rs:1488-1505`; core enum `cedar-policy-core/src/validator.rs:67-77`). `Validator::validate_with_level(pset, mode, max_deref_level)` adds RFC 76 level validation: a bound on how many entity dereferences a policy may chain, so the host knows how deep an entity slice it must load (`api.rs:1566-1576`; `cedar-policy-core/src/validator/level_validate.rs:17-31`).
- EXECUTED. A request with principal `File::"a"` against an action whose `appliesTo.principalTypes` is `["User"]` was refused before any policy ran: cedarpy returned its own `NoDecision` with the error "failed to build request: principal type `File` is not valid for `Action::"read"`". The Cedar FFI models the same split as `AuthorizationAnswer::Failure { errors, warnings }` versus `Success { response, warnings }` (`cedar-policy/src/ffi/is_authorized.rs:536-558`): a malformed call is not a `Deny`, it is a failure to ask.

## B. The decision

- READ. `Decision` has exactly two variants, `Allow` and `Deny`; the `Deny` doc says it "is also returned if sufficiently fatal errors are encountered such that no decision could be safely reached" (`cedar-policy-core/src/authorizer.rs:700-708`). `Response { decision, diagnostics }` and `Diagnostics { reason: HashSet<PolicyID>, errors: Vec<AuthorizationError> }` (`authorizer.rs:650-680`; public at `api.rs:1161-1167`, `api.rs:1300-1309`). `reason` is the set of determining policies; errors are documented as unordered "since policies may be evaluated in any order" (`api.rs:1306-1308`).
- READ. Combination: the concrete decision is `Allow` iff at least one permit is satisfied and no forbid is satisfied (`cedar-policy-core/src/authorizer/partial_response.rs:476-488`). `reason` is the satisfied permits on Allow, the satisfied forbids on a forbid-Deny, and empty on a default Deny (`must_be_determining`, `partial_response.rs:206-218`; docs.cedarpolicy.com/auth/authorization.html says the same). The paper states the properties proved in Lean: a satisfied forbid always denies; no satisfied permit denies (Section 2.4; repeated in `self-assessment.md:116`).
- READ. Errors: `ErrorHandling` has one variant, `Skip`, "the decision will be as if the erroring policy did not exist"; the comment says other modes "were debated during development" and the enum is kept so one could be added (`authorizer.rs:50-60`). In the loop, an erroring policy is recorded in `errors` and filed as not satisfied, marked `ErrorState::Error` (`authorizer.rs:126-143`; `ErrorState` at `partial_response.rs:42-50`). The docs give the reason: skipping avoids one faulty policy denying every request.
- EXECUTED. Skip-on-error applies to forbids too. With `permit(principal, action == Action::"read", resource);` and `forbid(...) when { resource.secret };`, reading a file with no `secret` attribute returned `Allow`, reason `policy0`, and the forbid's error in `errors` ("does not have the attribute `secret`"). The guard failed open. Strict validation against a schema where `secret` is optional would have refused that forbid at authoring time (it requires `resource has secret`), which is how Cedar intends the gap to be closed (INFERRED from the validator's purpose, paper Section 2.5 "validated policies evaluate without type errors").
- READ. No obligations, advice or third decision exist in the code: a repository-wide search for "obligation", "XACML", "NotApplicable" and "Indeterminate" finds nothing relevant. The paper's rationale is purity and order independence: "Policies have no side effects, and decisions are indifferent to the order that policies are considered" (Section 1), and the authorizer "is guaranteed to terminate and always produce the same authorization decision" (Section 2.4). `self-assessment.md:122` lists "Policy enforcement. Cedar returns a decision. The application must enforce it" as a non-goal. INFERRED: what XACML expresses as an obligation, Cedar leaves to the host, which may read the determining policies' annotations.

## C. Partial evaluation and residuals: the "cannot decide yet" outcome

- READ. `Authorizer::is_authorized` is `is_authorized_core(...).concretize()` (`authorizer.rs:76-78`): every authorization is a partial evaluation whose residuals are then treated as errors. Each policy lands in one of six buckets, satisfied, false or residual, for permit and forbid (`authorizer.rs:99-156`; `PartialResponse` fields `partial_response.rs:52-80`).
- READ. The third outcome is `PartialResponse::decision() -> Option<Decision>`, where `None` means "a decision could not be reached given the unknowns" (`partial_response.rs:119-139`). The table: any satisfied forbid is `Deny`; no satisfied and no residual permit is `Deny`; a residual forbid is `None`; only residual permits is `None`; a satisfied permit with no satisfied or residual forbid is `Allow`. Deny-wins is decided early; Allow waits for every forbid.
- READ. What the caller does with `None`: inspect `may_be_determining` (over-approximation) and `must_be_determining` (under-approximation) (`partial_response.rs:169-218`), list `nontrivial_residuals` (`partial_response.rs:220-248`), then call `reauthorize(mapping, authorizer, entities)` with values for the unknowns, which rebuilds a policy set from the residuals and evaluates only those (`partial_response.rs:328-345`; renamed `reauthorize_with_bindings` in 4.3.0, `api.rs:1260-1272`). Or `concretize()` to collapse to `Response`, residuals reported as errors (`partial_response.rs:113-117`, `partial_response.rs:405-420`). Conflicting bindings are refused (`ConcretizationError`, `cedar-policy-core/src/authorizer/err.rs:36-72`).
- READ. The newer type-aware partial evaluator (`tpe`, RFC 95) requires a schema and validated policies, a concrete action, and lets principal and resource be unknown by id but known by type (`cedar-policy-core/src/tpe.rs:27-50`; RFC 0095). It has the same decision table (`cedar-policy-core/src/tpe/response.rs:89-133`). `is_authorized_batched(request, ps, schema, loader, max_iters)` runs a loop: evaluate, collect the entity uids the residuals mention, ask the host's `EntityLoader` for them, re-evaluate, until `decision_from_residuals` is `Some` (`cedar-policy-core/src/batched_evaluator.rs:41-46`, `86-172`). If the iterations run out it returns `InsufficientIterationsError`, an error, not a Deny (`batched_evaluator.rs:167-171`). `PolicySet::query_resource`, `query_principal`, `query_action` answer permission queries (`cedar-policy/src/api/tpe.rs:777-937`); RFC 95 notes resource listing can be translated to SQL.
- INFERRED. Cedar's "cannot decide yet" is a pure value: the engine never pauses or calls out mid-evaluation. The host supplies the missing facts and asks again. The batched loader is the closest thing to a callback, and it is bounded by `max_iters`.

## D. Authoring and composition

- READ. A `PolicySet` holds templates and links; a static policy is a template with no slots, and `policies()` iterates the links (`cedar-policy-core/src/ast/policy_set.rs:549-552`). `link(template_id, new_id, values: HashMap<SlotId, EntityUID>)` fills `?principal` and `?resource` slots and refuses an id conflict (`policy_set.rs:485-525`). Templates fill only scope slots, never conditions (`api.rs:4273` comment; `TemplatePrincipalConstraint` at `api.rs:3993`).
- READ. Several sets combine by `PolicySet::merge(other, rename_duplicates)`, which fails or renames on an id clash (`api.rs:3085-3130`; core `policy_set.rs:255-275`). There is no per-set combining algorithm: the merged set is one flat set under the single deny-overrides rule. INFERRED: "strictest wins" across sources is obtained by putting them in one set, because forbid overrides permit regardless of origin.
- READ. Annotations are free key/value strings (`@key("value")`, `@key` meaning `""` since 4.2.0, CHANGELOG lines 590-591). The engine carries them through evaluation into `PartialResponse` (`authorizer.rs:107`), but the concrete `Diagnostics` reports only policy ids. The host looks annotations up: `PolicySet::annotation(id, key)` (`api.rs:3284-3292`). `@id` is not special to the engine: only the CLI renames policies from it (`cedar-policy-cli/src/utils/policies.rs:192-220`). EXECUTED: with `@id("allow-all-reads")` on a policy, cedarpy reported the reason as `policy0`.
- READ. Purity and termination: the language has no loops beyond linear set operations and no side effects (paper Sections 1 and 2.4); evaluation is in memory and cannot read files, network or clock (`self-assessment.md:144`); "Evaluation of bounded input terminates" (`self-assessment.md:146`). Deep nesting is guarded by `stacker` with a `RecursionLimit` error (`cedar-policy-core/src/evaluator.rs:1251`; `api.rs:1024-1032`), not on Wasm. Every behaviour is differentially tested against a Lean model (`self-assessment.md:116-118`).

## E. Cost

- READ. The open-source authorizer does no policy slicing: it evaluates every policy in the set (`authorizer.rs:106`). A policy's scope is folded into its condition, so a non-matching scope is a cheap early `false` (`evaluator.rs:397-402`; `Template::condition_ref`, `cedar-policy-core/src/ast/policy.rs:288-292`). The paper's model `authorize` slices by indexing each policy on its principal and resource scope entity (or Any) and looking up the request's principal and resource ancestors, which "performs well when the policy store is large, but P and R have relatively few ancestors" (Section 3.3). INFERRED: slicing is left to the host or service (the paper describes it for Amazon Verified Permissions).
- READ. Entity cost is the host's: Cedar requires all relevant entities in memory. Level validation bounds the dereference depth; entity manifests (entity slicing) were deprecated in 4.8.2 for `tpe` batched loading (CHANGELOG line 273, #1945). Cedar sets no input-size limits; the host must bound input (`self-assessment.md:121`). Since 4.6.0 the FFI has `stateful_is_authorized` with a cached pre-parsed policy set and schema (CHANGELOG line 350, #1831).

- READ. 3.2.0 (2024-05-17): partial-eval API reworked (#714, #817, #838; line 839). 4.2.0 (2024-10-07): level validation added experimental; valueless annotations (lines 589-591). 4.3.0 (2025-01-21): schema annotations (RFC 48); `reauthorize_with_bindings`; typed unknown principal and resource (lines 533-539). 4.4.0 (2025-04-23): RFC 76 level validation stabilised with bug fixes (lines 442-446).
- READ. 4.6.0 (2025-10-06): type-aware partial evaluation (RFC 95, #1575) and batched evaluation (#1812), both experimental (lines 355-357). The crate now says of `partial-eval`: "You should prefer `tpe`" (`cedar-policy/src/lib.rs:53`). RFC 95's motivation: the untyped evaluator produced ill-typed residuals and could not simplify `true && e` without changing error behaviour.
- READ. 4.14.0 (2026-10-17): `external` entity types and actions (RFC 116, commit `8a9b9ba`, #2615); `Request::new` refuses a request whose action is external (CHANGELOG lines 79-111; `coreschema.rs:183-188`). Commit `144048d` (2026-09-03) fixed the batched loop's exit and action seeding.
- INFERRED. Partial evaluation has been experimental since 2023 and was replaced once. The stable core is still two-valued; the third outcome lives in a separate, typed, experimental API.

## What this suggests for vfs (INFERRED)

Take:

- **Validate the `Call` once, at construction, against the operation's declared shape.** Cedar's `appliesTo` and context types per action map onto vfs operations (read, write, edit, delete, move, run): each operation declares which arguments and path shapes it carries, and a `Call` that does not fit never reaches a policy. Report it as a refusal of the request, not as a policy Deny (the FFI's `Failure`/`Success` split).
- **Type the operations as a hierarchy.** `memberOf` action groups let a policy say "any mutating operation" once. vfs's `mutates` flag is the simplest such group, and a declared group (`writes`, `deletes`, `runs`) keeps policies from enumerating verbs that will grow.
- **Make deny-overrides-allow and default deny properties, not conventions.** One combining rule over the union of every applicable policy, whatever its source, gives "strictest wins" with no per-source algorithm. vfs would extend the order to deny > interrupt > allow.
- **Return the determining policies, not one message.** `reason` as a set of policy ids, with annotations looked up by id, lets a person and an agent both read why. vfs's decision can carry each determining policy's name and its human reason directly, which Cedar leaves to the host.
- **Model "cannot decide yet" as a value plus a resume.** `Option<Decision>` with `reauthorize(bindings)` is the closest analogue of interrupt: the engine stops with a pure result naming what is missing, the host gathers it, and evaluation resumes over only the undecided remainder. vfs's interrupt can follow the same shape: the decision names what a person must answer, and the resumed call re-judges with the recorded answer bound in, rather than trusting the earlier evaluation.

Avoid:

- **Skip-on-error for a guard.** Executed above: an erroring forbid is skipped, so a guardrail fails open when another policy allows. Cedar can afford this only because strict validation proves validated policies do not error. vfs policies are arbitrary host Python with no such proof, so a policy that raises must count as the strictest outcome (deny, or interrupt), never as absent.
- **Hiding the third outcome in an experimental side API.** Cedar's stable `Decision` is two-valued, and the residual API has been experimental and rewritten since 2023. vfs wants interrupt as a first-class outcome; it belongs in the one decision type from the start.
- **Unbounded host callbacks.** Cedar's batched loader is bounded by `max_iters`, and exhaustion is an error. Any vfs policy that does I/O (a lookup, a session check) at ~20 calls a second on the gate's path needs the same bound and a defined result when it is hit.
- **Evaluating every policy on every call** is fine for a handful of host-registered functions, but at the reference deployment's 150,000 calls a day a policy set should be indexable by operation (Cedar's paper slices by scope), so a policy registered for `delete` costs nothing on a `read`.

The sharpest lesson: Cedar's purity buys termination, order independence and a provable "forbid always wins", and its one weak point, skip-on-error, is safe only because validation rules out errors. vfs gives up that proof the moment a policy is arbitrary Python, so it must decide in the type of the decision what a raising, hanging or undecided policy means, and that meaning must be the strict one.
