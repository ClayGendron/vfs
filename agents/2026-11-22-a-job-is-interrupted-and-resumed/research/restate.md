## B. What is persisted at a pause

- READ. The journal is an ordered list of **commands** (what the handler did) and **notifications** (what came back), split since protocol V4 (core:`docs/service-invocation-protocol.md:145-158`). Type ranges: commands `0x0400-0x7FFF`, notifications `0x8000-0xFBFF` (`:134-141`). Every notification has the shape of `NotificationTemplate`: an id (`completion_id`, `signal_id` or `signal_name`) and a result (`void`, `value`, `failure`, `invocation_id`, `state_keys`) (core:`service-protocol/dev/restate/service/protocol.proto:315-333`).
- READ. Completable commands carry a `result_completion_id` the SDK allocates; the runtime answers with a notification under the same id (proto `:541-560` Sleep, `:566-619` Call with two ids, `:680-700` Run). Ids are counters per invocation: completions start at 1, signals at 17, the first 16 reserved for built-in signals such as `CANCEL = 1` (core:`src/vm/context.rs:118-126`, proto `:849-853`).
- READ. **An awakeable writes nothing to the journal.** `sys_awakeable` allocates a signal id and maps a handle to it (core:`src/vm/mod.rs:1001-1023`; `CreateSignalHandle` at core:`src/vm/transitions/journal.rs:351-378` only creates a mapping). Its id string is `sign_1` + URL-safe base64 of the invocation id followed by the signal index as a big-endian u32 (core:`src/vm/mod.rs:1532-1539`). The id therefore encodes *which invocation* and *which wait*, and nothing else. The protocol document still describes the older `prom_1` form (core:`docs/service-invocation-protocol.md:267-276`), a stale page. Resolution by another party is a `CompleteAwakeableCommandMessage` in the resolver's journal (proto `:766-778`), delivered to the waiter as a `SignalNotificationMessage` (proto `:780-796`).
- READ. Durable promises are workflow-scoped and named: `GetPromiseCommand`, `PeekPromiseCommand`, `CompletePromiseCommand` (proto `:463-537`). Completing one is fallible: its completion notification may carry a failure, the test `reject_promise_fails` feeds "cannot write promise" (core:`src/tests/promise.rs:455-500`). Completing an awakeable is not completable at all; the resolver learns nothing (proto `:763-766`).
- READ. `ctx.run` writes a `RunCommandMessage` holding only a name and a completion id (proto `:680-685`) before the closure runs; the result travels as a `ProposeRunCompletionMessage`, a control frame the runtime stores and then echoes back as a `RunCompletionNotificationMessage`, or acks with `ProposeRunCompletionAckMessage` on V7+ (proto `:216-267`; core:`docs/service-invocation-protocol.md:278-296`).
- READ. A **suspension** is the SDK sending `SuspensionMessage { awaiting_on: Future }` and closing the stream (proto `:152-159`; core:`src/vm/transitions/terminal.rs:16-44`). `Future` is a tree: three leaf lists (`waiting_completions`, `waiting_signals`, `waiting_named_signals`), nested futures, and a combinator type with JavaScript semantics (proto `:112-150`). The handler's frames are discarded; nothing of the Python process is kept. The runtime "resumes the invocation as soon as it has enough new notifications to potentially unblock the await point" (core:`docs/service-invocation-protocol.md:308-313`). Before V7 the message was a flat list of entry indexes, any one of which woke it (old proto at `0b02f5b^`, `SuspensionMessage.entry_indexes`). With implicit cancellation on, the VM wraps every await as `FirstCompleted([user_future, CANCEL])`, so a cancel always wakes a suspended invocation (core:`src/vm/mod.rs:480-560`; asserted in core:`src/tests/suspensions.rs:86-141`).
- INFERRED. The pause record is the journal so far, the await tree, and per-object state: plain protobuf, no frame, no pickled closure.

## C. Resumption and matching

- READ. On resume the runtime opens a new stream: `StartMessage` (invocation id, `known_entries`, eager `state_map`, `partial_state`, `random_seed`, retry telemetry; proto `:57-110`) followed by every known command and notification. The VM buffers the commands in one queue and the notifications in another (core:`src/vm/transitions/input.rs:88-150`), then re-runs the handler from its first line.
- READ. **Matching is positional and per type.** Every `sys_*` call during replay pops the next recorded command (core:`src/vm/transitions/journal.rs:1018-1056`). First `decode_to::<M>` checks the message type (core:`src/service_protocol/encoding.rs:77-84`), failing with `CommandTypeMismatchError`, which names the recorded type, its index, and the attempted type (core:`src/vm/errors.rs:193-228`). Then `header_eq` compares fields chosen per command (core:`src/service_protocol/messages.rs:20-23`, `check_entry_header_match` at core:`journal.rs:1091-1106`), failing with `CommandMismatchError`, which prints a field-by-field diff (core:`errors.rs:232-261`). Both carry code `570 JOURNAL_MISMATCH` (core:`errors.rs:70`, `:439-447`).
- READ. What is compared varies on purpose. `Sleep` compares only the name, never the wake-up time, which is wall-clock (core:`messages.rs:255-260`). `Call` compares service, handler, key, headers, idempotency key, scope, completion ids, name, and the parameter bytes unless payload checks are off (`:263-280`). `Input` matches anything (`:157-161`). Payload equality can be switched off globally (`NonDeterministicChecksOption::PayloadChecksDisabled`, core:`src/lib.rs:308-315`) or per call (`PayloadOptions::unstable_serialization`, core:`lib.rs:36-48`); the Python SDK turns it off when a journal codec encrypts payloads with a random nonce (py:`src/lib.rs:387-394`).
- READ. Replay ends when the command queue is empty, not when the journal is (core:`src/vm/mod.rs:83-99`, `try_transition_to_processing`). An await during replay that the recorded notifications cannot satisfy, while commands remain, proves the code gained an `await`: `UncompletedDoProgressDuringReplay` lists the awaited notifications, with awakeable ids and run names (core:`src/vm/transitions/async_results.rs:29-106`, message at core:`errors.rs:315-344`). Added in `2e1c1b3` (2026-01-27).
- READ. `ctx.run` on replay: `sys_run` re-matches the `RunCommand`, then looks for its completion anywhere in the buffered notifications; if found, the closure is not executed and `RunHandle.replayed = true` (core:`journal.rs:811-883`). The Python SDK schedules the closure only when `not run.replayed` (py:`server_context.py:1064-1075`).
- READ. Awakeable completion reaches a suspended handler as a signal notification in the replayed journal; the handler re-runs, calls `ctx.awakeable()` again, gets the same signal id because the counter is deterministic, and the await resolves from the queue (test `replay_awakeable_completed_twice_then_await_directly`, core:`src/tests/signals.rs:147-169`).
- READ. Combinators are not journaled. `gather`, `select`, `wait_completed` and `as_completed` (py:`python/restate/asyncio.py:26-155`) pass an `AllCompleted` or `FirstCompleted` tree to `do_progress`. The VM resolves the tree by moving notifications one at a time, in journal order, from `to_process` into `ready` until the tree resolves (core:`src/vm/async_results_state.rs:151-230`, `pop_notification_queue` at `:317-325`). Determinism comes from the journal's notification order, which the protocol requires to be reproduced on replay (core:`docs/service-invocation-protocol.md:156-158`). The race winner is whichever answer was recorded first.

## D. Failure and change

- READ. **`ctx.run` is at-least-once.** The command is journaled before the closure; if the attempt dies before the proposal is stored, replay finds no completion and executes the closure again (core:`journal.rs:851-873`; test `replay_without_completion`, core:`src/tests/run.rs:356-403`).
- READ. Retries: the runtime owns the invocation retry policy (`InvocationRetryPolicy` with `on_max_attempts: "pause" | "kill"`, py:`retry_policy.py:24-41`). A run's own retry policy (`RetryPolicy::Infinite | None | FixedDelay | Exponential`, core:`src/retries.rs:18-48`) is applied by the VM: a retryable failure ends the attempt with `next_retry_delay`, pauses, or becomes a terminal failure journaled as the run's result (core:`journal.rs:909-965`). `ErrorBehavior` is `RETRY | PAUSE | FAIL` (proto `:191-204`).
- READ. Code change: a mismatch retries forever by default; `JournalMismatchRetryBehavior::Pause` or `FailTerminally` was added in `5ee8922` (2026-06-16) (core:`lib.rs:316-333`, applied in core:`src/vm/transitions/mod.rs:73-84`). The error text tells the user that an added `await` means a new service revision was not registered (core:`errors.rs:319`). INFERRED: invocations are pinned to the deployment that started them on the server, which is not in these repos.
- READ. Retention: `journal_retention`, `idempotency_retention` and `workflow_retention` are per service or handler settings (py:`service.py:62-66`, `workflow.py:154`). Idempotency keys are a field of every call (proto `:578`, `:639`) and of `StartMessage` (`:107-109`).
- READ. Twice resolved: per-signal deliveries are queued and handed out one per take, in journal order (`SignalDelivery::Queued`, core:`lib.rs:352-361`); `Overwrite` keeps only the latest. The fix landed in `2d25042` (2026-10-27), before which a later delivery replaced an earlier one (`ready: HashMap<NotificationId, NotificationResult>` became a `VecDeque`). An awakeable awaited once takes the first value (core:`signals.rs:147-169`). Never resolved: the invocation stays suspended; only cancellation (the built-in signal) or the server's retention ends it. INFERRED for the server part.
- READ. **Restate has added a no-replay mode.** `JournalReplay::Disabled { fail_interrupted_runs }` (`2d02a04`, 2026-10-20; core:`lib.rs:335-350`): the handler reruns from the start, every command executes anew, effects repeat, **"awakeables are unsupported"**, and `sys_awakeable` refuses because "signal ids of skipped attempts are unknown, so a new one could collide" (core:`mod.rs:1003-1010`). Runs left open by a dead attempt are failed with code 500 so tooling does not show them pending forever (`93c1572`, 2026-11-12; core:`journal.rs:39-81`). A separate `ExplicitRecoveryVM` followed (`63937cb`, 2026-11-16; core:`src/explicit_recovery/mod.rs:1-60`): no deterministic await points, every attempt "recovers explicitly from the state the earlier attempts stored", and "a call that can be issued again by a later attempt needs an idempotency key".
- READ. How the agents layer waits for a person under explicit recovery: the agent handler cannot hold an awakeable, so a tool's wait is an **idempotent call** to a journaled companion handler, `wait`, which creates the awakeable and registers `{id, name, input, since, awakeable}` in a `waiting` list (py:`agents/_signals.py:28-30`, `:356-371`). `resolve` finds the wait by id, or the oldest by name, and resolves its awakeable (`:373-398`); `pending` lists the waits (`:400-403`). The wait's id is the tool call's idempotency key, so a rerun of the tool body rejoins the same wait (py:`agents/_tools.py:709-726`).

## E. Cost

- READ. Entries per action: `set` is one command; `run` is one command plus one notification; `call` one command plus two notifications; `sleep` one plus one; an awakeable zero commands plus one notification when resolved; an ephemeral state read (V8) zero, since it is neither stored nor replayed (core:`docs/service-invocation-protocol.md:410-435`).
- READ. **Every resume ships the whole journal.** `StartMessage.known_entries` counts all commands and notifications, and the stream replays them before the SDK takes over (core:`docs/service-invocation-protocol.md:92-99`, `:211-222`). Explicit recovery still receives every earlier entry, used only to number new ids after them (core:`explicit_recovery/mod.rs:51-55`; `skip_to` at core:`context.rs:61-73`). The optimizations present are eager state (state shipped inside `StartMessage`, so reads cost no round trip, `:391-408`), `ProposeRunCompletionAck` (the result is not echoed back, `f6f6e48`, 2026-05-19) and ephemeral commands. INFERRED: replay cost is linear in journal length per resume, and a long handler with many waits pays it once per wake.
- READ. The test harness offers `always_replay`, an inactivity timeout of 0 s that forces a suspension and replay at every await, to hunt nondeterminism (py:`harness.py:147-150`, `:300-302`).

## F. History and lessons

- READ. Protocol versions (proto `:17-53`, core:`src/service_protocol/version.rs`): V1 initial; V2 entry retry telemetry; V3 yanked; **V4 immutable journal** (`0b02f5b`, 2025-01-31, "Service Protocol V4/Immutable journal", 3,695 insertions, 4,044 deletions). Before V4 a completable entry had its result filled in place by a `CompletionMessage { entry_index }`, an awakeable was an `AwakeableEntryMessage` with an in-place result, and the id was `prom_1` + invocation id + entry index (old proto at `0b02f5b^`). V4 split commands from notifications and made awakeables signals. V5 (`7d29b3d`, 2025-03-06) and V6 (`c09e270`, 2025-09-05) added the random seed and failure metadata. V7 (`d8a42ec`, 2026-04-30) replaced the flat suspension list with the `Future` tree and `AwaitingOnMessage`, and added pause/fail error behaviour. V8 (`382649d`, 2026-10-09) added ephemeral commands. The minimum supported is now V5 (core:`version.rs:42-44`).
- READ. Mismatch reporting improved in steps: `383fcff` (2025-06-26), `981c5e0` (2025-08-05, command index), `496c9f6` (2025-08-14) and `261d49c` (2026-01-14, payload checks), `2e1c1b3` (2026-01-27, the `await` check), `511152b` (2026-09-21, swapped labels fixed).
- READ. The Python SDK's agents work records its own lessons (py:`docs/agents/learnings.md:114-133`, bug table `:163-177`): "Our attempts resume from committed state; they don't replay"; "If a retry replays writes by position, it must replay reads too" (a plan store lost a write after a crash); "A wait belongs to one tool call", after a later identical tool call received an earlier call's approval because waits were matched by input; "An approval is not the call"; an operation named by a per-attempt run id was reported failed after a crash.

## What this suggests for vfs (INFERRED)

**Take.**

- *The pause record is a wait description plus data, never a frame.* Restate's suspension is a small tree of ids naming what the work waits on, beside the journal (B). An interrupt row in vfs can be the same: the interrupt id, the unit of work, the typed `Call`, and what answer is awaited. It serializes to a row on SQLite and Postgres alike.
- *An id that encodes its owner and its ordinal.* `sign_1` + invocation id + counter means the id is reproducible by a rerun and routable by any process (B). A vfs interrupt id derived from the paused unit's id plus a deterministic ordinal survives a resume in another process.
- *For the shell, positional replay with typed comparison.* The shell is already a deterministic request/reply machine. Restate's rule (pop the next record, check the kind, compare the fields that should be stable, ignore wall-clock fields, report index plus diff, code 570) maps directly onto replaying a shell line's calls (C). The per-field choice matters: compare the path and verb, decide explicitly about payload bytes.
- *Mismatch is a pause, not a retry loop.* Restate retried mismatches forever until `5ee8922` added pause or fail (D). A vfs resume that finds the code or the `Call` changed should stop with a classified result.
- *Close what an attempt left open.* `fail_interrupted_runs` exists because open runs looked pending forever (D). A vfs interrupt whose work is abandoned or cancelled needs a terminal state, not an orphan row.

**Avoid.**

- *Replaying a tool body.* Restate's own move, in its newest code, is away from replay for arbitrary handlers: `JournalReplay::Disabled`, then `ExplicitRecoveryVM`, and awakeables refused in that mode (D, F). A vfs tool body cannot be replayed safely, so it should rerun from its start and find its answers by identity, as the agents layer does.
- *Matching an answer by content.* The agents bug table shows an approval for one tool call approving a later identical one (F). A vfs answer must bind to one interrupt id, never to "a call that looks the same".
- *Positional writes with live reads.* "If a retry replays writes by position, it must replay reads too" (F). A shell line replayed against live data can take another branch; replayed reads, or a check that refuses the replay, are needed.
- *Shipping the whole history on every resume.* Restate does (E). In vfs the paused unit is a single call, a shell line or a tool body, so its record should stay bounded by that unit, not grow with a session.
- *A resolver that cannot tell whether it won.* `CompleteAwakeable` returns nothing, and twice-resolved awakeables queue values (B, D). A vfs `answer` should return whether it settled the interrupt or found it already answered, as `CompletePromise` does.

**The sharpest lesson.** Restate offers two recoveries and has learned where each one fits. Deterministic replay matched by position suits code that is a pure function of its journal, like the vfs shell. Rerunning from the start and rejoining waits by a stable id suits arbitrary code, like a vfs tool body. Using one for the other caused the bugs it records. In short: replay the shell, rerun the tool, and bind every answer to one interrupt id.
