# The engine cuts a byte slice of a body on every tuned dialect

A draft, written on 2026-11-25. It is not reviewed, and nothing is built. It was checked against `dev` at `27f3d24d`. It serves story K6 of `context/standards/roadmap.md`, gate b, as unit 178-1 of [the backlog conversion](../2026-11-25-the-backlog-converted/units.md). It is converted from `context/specifications/archive/178-the-ranged-read/spec.md` (sections 2.1, 4 and 5, and task 1 of its `tasks.md`), cut down to the two engines `dev` serves. It rests on [the two-engine spec](../2026-11-20-vfs-serves-sqlite-and-postgres-only/spec.md), which is built, and waits for nothing.

## The outcome wanted

The database adapter can put one column expression in a select that returns exactly the bytes `[offset, offset + length)` of a stored body, cut by the engine. For a bytes body (`data` in `vfs_blobs`) the bytes are the raw bytes. For a text body (`content` in `vfs_content`) they are the bytes of its UTF-8 encoding, the same bytes `size_bytes` counts. SQLite and Postgres each declare how they cut; the generic floor declares that it cannot. Nothing public changes in this unit: no verb takes a range yet. What a caller of the adapter sees is a test on SQLite and on the Postgres leg where every slice of a mixed 1- to 4-byte-character body equals Python's `body.encode()[offset:offset + length]`, in one statement, and a 64 KiB slice of a 4 MiB body returns 65,536 bytes, never the body. The ranged read of [unit 178-2](../2026-11-25-read-takes-a-byte-range-and-the-row-says-which-slice-it-carries/spec.md) calls it.

## Terms

- **Body.** The stored file content: `content` (text) in `vfs_content`, or `data` (raw bytes) in `vfs_blobs` (`rows.py:458-478`).
- **Slice.** The bytes `[offset, offset + length)` of one body, `offset` and `length` counted from 0 in bytes, cut short at the end of the body.
- **UTF-8 bytes of `content`.** The bytes of `content.encode("utf-8")`. `size_bytes` and `content_hash` are measured on them (`src/vfs/models/version.py:71`).
- **Slice form.** How a dialect turns its text column into UTF-8 bytes before cutting. A value of `BodySlice` (decision 1).
- **Blocks read.** Postgres's `Shared Hit Blocks` plus `Shared Read Blocks` for one statement under `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`: a count of pages touched, never a time.

## What the code does today

- No statement under `src/vfs` cuts a body. No `substr`, `substring` or `convert_to` is rendered anywhere (EXECUTED, `grep -rn "func.substr\|func.substring\|func.convert_to" src/vfs` finds nothing), and no `body_slice`, `BodySlice` or `slices` module exists (READ, the reassessment's section for 178-1).
- `read` fetches the whole body (`reads.py:156`). The shell review measured `head -c 10` on a 5 MiB file as one router read of 5,242,880 bytes (READ, `agents/2026-11-22-shell-review/reviews/verification.md:54`).
- SQLAlchemy has no portable "UTF-8 bytes of a text column". `cast(content, LargeBinary)` renders `CAST(content AS BYTEA)` on Postgres (EXECUTED, compiled with SQLAlchemy 2.0.52), which is an input conversion that parses backslash escapes: `CAST('a\b'::text AS bytea)` raises `invalid input syntax for type bytea` (EXECUTED on Postgres 16.15).
- On Postgres `vfs_blobs.data` is `EXTERNAL` and `vfs_content.content` keeps the default `EXTENDED` storage, which compresses with the server's `default_toast_compression` (READ, `rows.py:458-478`, `:862-871`; no other storage DDL exists).
- `dialects.py` holds 931 lines and is not in the size baseline; the ceiling is 1,000 (EXECUTED, `wc -l`; READ, `tests/lint/allowlist.py:26-33`, `tests/lint/test_code_shape.py:76`). `reads.py` and `base.py` are held at their exact counts, and this unit touches neither.

## The problem

Story K6 asks that `read(path, range=(0, 4096))` on a 4 MB body fetch at most 4,096 body bytes (READ, `context/standards/roadmap.md:189`). That is only possible if the engine cuts the slice before the body leaves the database. The cut is a per-dialect spelling SQLAlchemy takes no position on, and the text half has a trap: the obvious cast reads text as escaped bytes on Postgres. At the reference deployment the median file is 4 KB but the mean is 0.3 to 0.7 MB, so the tail carries the bytes; an agent's `head` or `sed -n 1,20p` on a 4 MB file today moves 4 MB to show 4 KB, about a thousand times what it returns, on one of about 110,000 read-shaped verb calls a day. The ranged read cannot be built until each tuned dialect can cut exactly, in the statement the read already issues.

## Decisions

1. **A profile field declares the slice form.** `DialectProfile` gains `body_slice: BodySlice | None = None`, with `BodySlice = Literal["blob_cast", "convert_to"]` declared beside `RangeSource` in `dialects.py`. `SQLITE` declares `"blob_cast"`, `POSTGRESQL` declares `"convert_to"`, and `GENERIC` keeps `None`, so an unknown dialect is never sent a slice. The field's paragraph in the `DialectProfile` docstring says what each value spells and why. Reason: turning a text column into its UTF-8 bytes is a decision SQLAlchemy takes no position on, which is what AGENTS.md admits a profile field for. Precedent: `range_source` (`dialects.py:74`, `:333`).
2. **A bytes body is cut by `substr(data, :start, :count)` on both engines.** `start` is 1-based. SQLite's `substr` counts bytes on a BLOB and Postgres's `substr(bytea, integer, integer)` counts bytes, so one spelling serves both (EXECUTED: every one of the 6,561 slices of decision 10's body matched on SQLite 3.53.1 and Postgres 16.15). `substr` is chosen over `substring` because SQLAlchemy renders `func.substr` the same on both dialects, where `func.substring` renders the `FROM … FOR` form on Postgres alone.
3. **A text body is cut from its UTF-8 bytes, by the profile's form.** `blob_cast` spells `substr(CAST(content AS BLOB), :start, :count)`: a reinterpretation, since SQLite stores TEXT as UTF-8 and TEXT and BLOB share storage. `convert_to` spells `substr(convert_to(substr(content, 1, :end), 'UTF8'), :start, :count)`, where `end` is the slice's exclusive end in bytes. The inner `substr` is a prefix in characters: a character is at least one byte, so the first `end` bytes lie inside the first `end` characters, and Postgres then fetches only a prefix of the stored value (EXECUTED on 16.15: a 4,096-byte slice of an uncompressed 4,100,000-byte text body read 7 blocks, against 523 for the whole value and 523 for the same slice without the inner prefix). `convert_to` is chosen over a cast because it transcodes from whatever the server encoding is and parses no escapes, so the bytes are UTF-8 on any Postgres database. `blob_cast` rests on the same fact as `content_bytes`, so a profile that declares it must declare `content_bytes` too, and a test pins that.
4. **Two builders in a new module, `src/vfs/storage/backends/database/slices.py`.** `data_slice(data, *, offset: int, length: int, form: BodySlice) -> ColumnElement[bytes]` and `content_slice(content, *, offset: int, length: int, form: BodySlice) -> ColumnElement[bytes]`, each typed `LargeBinary` so both drivers hand back `bytes`. `form` is required and never `None`, so a caller must narrow `profile.body_slice` before it can build a slice, and the type checker refuses a floor that forgot. `data_slice` takes `form` though both forms spell it alike, so the two builders are gated the same way. No new value type: the 0-based `offset` and `length` are the caller's numbers, and the 1-based arithmetic stays inside this module. 178-2 introduces `ByteRange` in `vfs/ops.py`, as the source's section 1 does, and passes its fields or its widened window. The module sits inside the adapter package, so outside it only the modules `ADAPTER_IMPORTERS` names may import it (`tests/lint/test_code_shape.py:39-42`).
5. **The arithmetic is total and never raises.** A negative `offset` or `length` is read as 0. Then `end = min(offset + length, SQL_INT_MAX)`, `start = min(offset, end)` and `count = end - start`. A slice with `count == 0` binds `start = 1, count = 0` and `end = 0`, which every form answers with empty bytes. A `NULL` body (a directory or ancestor row in an outer join) answers `NULL`, never empty bytes. Reasons: Postgres's `substr` takes 32-bit integers, so a bind past 2³¹ − 1 fails at the driver; SQLite's `substr` counts a negative start from the end, a silent wrong answer; and an exception is raised only at construction or by `raise_if_failed` (`context/standards/how-we-code.md:24`). The refusal of a bad range is 178-2's gate in the params table, not this builder.
6. **The ceiling is a named engine fact.** `SQL_INT_MAX: Final = 2**31 - 1` is declared in `slices.py`: the widest value Postgres's `substr` arguments hold. It equals `vfs.params.INT_CEILING` (`src/vfs/params.py:63`), which the adapter cannot import, because `vfs.storage.backends` and `vfs.params` share a rung and units on one rung stay apart (`tests/lint/test_code_shape.py:46-63`). A test pins the two equal. It is no designed cap: `size_bytes` is an `Integer` column (`rows.py:384`), so no body past it can be recorded, and both engines cap one value below it.
7. **Every number is a bind and the text never changes with the range.** `start`, `count` and `end` are anonymous `Integer` bind parameters; the literal `1` of the prefix and `'UTF8'` are rendered in the statement text. So two slices of different ranges compile to the same text, and a statement cache keeps one entry. A `data` slice adds 2 binds, a `content` slice 2 on SQLite and 3 on Postgres, all constants per statement and inside the 32-bind `_FILTER_BIND_RESERVE` that `membership_budget` already holds back (`dialects.py:535-548`). Precedent: the three-seek predicate's text never changes with the caller's grants (`src/vfs/storage/backends/database/ranges.py:12-13`).
8. **A slice is one column of the caller's one statement.** The builders add no statement, create no function and change no schema. `SCHEMA_FORMAT_VERSION` stays 28 (`rows.py:135`).
9. **The module docstring states what each engine reads inside, as measured.** SQLite loads the whole value in process and returns only the slice. Postgres reads only the TOAST chunks a `data` slice covers (EXECUTED on 16.15: a 65,536-byte slice at offset 1,000,003 of a 4,194,304-byte body read 36 blocks, against 558 for `md5(data)`). For `content`, Postgres reads a prefix of at most four times `end` bytes of an uncompressed or `pglz` value, so a slice deep in a large text body reads up to the whole value, and under `lz4` it fetches the whole compressed value (EXECUTED on 16.15: 440 blocks for a 4,096-byte prefix of an `lz4` value, the same as the whole). Each is a profile with a named direction (choice 2), never a declared limit.
10. **Nothing calls the builders in this unit.** No verb, argument, trait or public name is added. The `read_range` trait, the `range=` argument, the outward snap to whole characters and the router's fallback for the floor are 178-2's. The unit lands as its own pull request (choice 1), proved on both engines by its own tests.

## Cost

- **Per verb call, once 178-2 calls it.** About 150,000 verb calls a day, about three in four read-shaped. A ranged read is the same statement as a whole read plus 2 or 3 constant binds (decision 7), so no statement is added. The wire carries at most `count` bytes per row in place of the body: for `range=(0, 4096)` on a 4,194,304-byte body, 4,096 bytes, about 1/1,024 of today.
- **Inside the engine.** SQLite reads the whole value from its page cache in process, one row at a time, so memory holds one body while it steps; this is the least generous engine served for engine-side reads, and the bytes never leave the process. Postgres reads the covered chunks of `data` and a prefix of `content` (decision 9).
- **Per batch.** A 10,000-path ranged read issues the statements its membership chunks already issue, `ceil(keys / membership_budget(profile, parameter_budget))`; the slice's binds are per statement, not per row, so they do not grow with the batch. The bytes returned are at most `10,000 × count`.
- **Per file write, per index visit, per corpus.** Nothing: no write, index pass or rebuild touches the builders.
- **Per lock.** None. A slice is a plain read inside the caller's snapshot, so it never waits on a writer and takes no lock.

## Not checked

- That SQLite's `substr` loads the whole value before it cuts. It is carried from the source, which read it in SQLite's source; no SQLite checkout was read here, and no count of SQLite page reads was taken.

## Choices to confirm

1. **Does this unit land apart from 178-2?** The map holds it apart; the reassessment notes that with two engines the reason is weaker and the two could fold into one pull request at K6's size S. ## One line

SQLite and Postgres each declare how they cut the exact bytes of a body, raw for `data` and UTF-8 for `content`, in one column of one statement, and the generic floor declares none, ready for `read(range=)` to call.
