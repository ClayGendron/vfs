## The author's questions, answered first

- Question 1, whether `step(replies)` and the request key serve a pipeline whose stages are all in-machine builtins and functions (`f | while read l; do ...; done`): the entry point serves it, and the key does not yet (INFERRED). Such a pipeline issues no request until a body does IO, so the machine must itself run both stages as coroutines over a bounded pipe buffer inside one `step`; nothing in `step(replies)` prevents that, and decision 4's "runs until it needs something" already implies an interpreter whose execution state is explicit heap data (a frame stack), because a native call stack cannot be suspended and resumed across `step` calls. Three things are missing. First, the spec does not say in-machine stages run concurrently with a bounded buffer and a per-stage copy of the variable environment (bash runs each stage in a subshell, and an unbounded buffer is how `yes | head -1` never returns). Second, the flat key "stage and ordinal" cannot name a request inside a pipeline inside a loop inside a stage, a `$( )`, a process substitution or a `&` job without a nesting rule (H2). Third, "applies their replies in key order" read as one global order makes stage 2's replies wait behind stage 1's open pull, which serializes or deadlocks a bounded pipe the moment one stage is a host program (H2). The determinism the durable run needs is per-stage: each stage's progress depends only on its own replies and its pipe's contents, which holds for blocking pipe reads (a Kahn network) and makes arrival order irrelevant without a global order.
- Question 2, whether 2,000 cases is sized right and whether the language/program tier split is well defined: the number carries no derivation and the split is defined in the wrong place (READ, INFERRED). 2,000 sits below the Oils suite's measured 2,800 shell cases over a narrower scope, so it is not too many, but a total can be met with near-duplicates in easy areas while an area such as `getopts` or `set -e` stays thin; a per-area floor taken from the manual's section list (with a minimum per builtin, per refusal and per budget) measures coverage and a total does not (L11). The tier is defined twice and differently: the spec says "a case that uses only builtins", `tests/shell/README.md` says "only builtins, keywords and functions" and declares it in a `# tier:` header written by hand (EXECUTED). Nothing checks the header, and a command word computed at run time (`$cmd`) cannot be classified by reading. The steps-2-to-5 gate depends on this split, so the tier must be checked: a test that walks each language case's AST and fails on a program name or a non-literal command word (L11). The program tier also has a hole: the file programs of decision 10 (`ls`, `cat`, `find`, `cp`, `mv`, `rm`, `grep`) are placed in no step, so their cases have no step that must clear them before the end (M3).
- Question 3, whether the fuel slice of decision 8 is implementable when the runtime counts fuel outside the module: not as written (EXECUTED, INFERRED). In a synchronous call, wasmtime's fuel running out is a trap that unwinds the call, so a slice made by `set_fuel(slice)` ends the line rather than pausing it; a paused-and-resumed call needs the asynchronous fuel yield (`fuel_async_yield_interval` with `func_call_async` and `call_future_poll`), which `wasmtime-py` carries only as raw bindings with no wrapper and no visible `async_support` setter. The native build has no fuel at all, yet decision 15 runs the corpus on both builds. Two implementable readings exist: the machine counts its own evaluation steps for the slice (deterministic on both builds, not fuel, consistent with decision 6's "counts no steps of its own as fuel" only if the slice is not called fuel), or the module imports one host function that returns the fuel remaining and returns from `step` when a slice is spent (module build only). Either way the runtime's fuel and epoch remain the walls. The spec must choose (M1). Separately, releasing the interpreter lock does not free the event-loop thread: a slice called on the loop blocks the loop for the slice whatever the lock does (L4).
- Question 4, whether anything conflicts with AGENTS.md: yes, three things (READ). The standing push grant contradicts "Ask before every push to a remote" without naming the departure (H4). Decision 10's file programs bypass the indexed `grep` verb and the single `glob("**")`, so `grep -rn x /` costs a read per file of the corpus, against "A read must cost in proportion to what it returns, never to the corpus" (H1). Decision 17's budgets "a host may lower" are ceilings no host can raise, against "Never design toward a hard scale cap" (M6). Clean: no numpy; performance work is in an owned Rust crate; no pure-Python fallback (the native build is the same Rust); the imports rule has no Python to bind until step 6; count, never clock, holds in decisions 6, 7 and the laws; the machine holds no lock and each request is one public-verb call, so no read waits on the shell (INFERRED from decisions 4 and 11).

## Scale and the production posture

- Parser and machine structures (AST, variables, arrays, pipe buffers, here-documents, pending output) grow with the line and its data and are bounded by decision 7's counted budget with the runtime's memory limit behind it (READ); clean.
- Brace expansion and repeated substitution are checked before allocation (decision 7); clean.
- Recursion is bounded by depth budgets (decision 9), but the stack the budget is checked against is not named (L3).
- File programs over file requests grow with the corpus under the operand, not with the result: `grep -rn mfa /` is about 10,000,000 reads per call at the reference deployment, against the indexed `grep` verb at `src/vfs/base.py:1432` (H1).
- A `for` loop that calls a verb per iteration grows with the loop and is bounded by the iteration budget only; `VERB_CALL_BUDGET` of roadmap F7.4 is absent (L8).
- Decision 17's budgets cannot be raised, so `while read -r l` over a 1,200,000-line log, or a loop over the nightly million, is refused by design rather than by an external cap (M6).
- One module instance per line with its own linear memory is implied by decision 9's poisoning and not stated; at about 20 calls a second and tens of milliseconds a call, concurrency is a few instances, so this is a note, not a finding (INFERRED).
- The event loop is a shared resource like a lock: a slice run on the loop thread stalls every concurrent call for its length (L4).

## Disposition

- **H1.** Taken in part. The requests gained the verb-shaped forms: `mkdir`, `remove` (a recursive one is one `delete(cascade=True)`), `copy`, `move`, `touch` (an if-absent write), and `write` with truncate, append and create-new modes, so `>>` is one append write per flush. Not taken: `grep -r` and `find` still walk through `list` and `read`; a host-answered `grep` request that reaches the indexed verb is reported.
- **H2.** Taken inside the laws.
