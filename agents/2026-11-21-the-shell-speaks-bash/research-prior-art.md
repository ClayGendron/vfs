# A long flat chain kills the host process, and at the commit studied nothing bounds a line's total work, deadline or output

This memo is the study of prior art for the most critical parts of the shell, asked for before the pull request of [the shell spec](spec.md): how two bash interpreters built for untrusted agent input confine effects and bound resources, how expansion, pattern matching, regular expressions and the hard corners of the parser are built elsewhere, and where `crates/vfs-shell` and its host `src/vfs/shell/host.py` fall short of them. Five sibling clones were refreshed, licence-checked and read; 24 logs of probes were taken against the crate's native release build and through the vfs host; 468 cases of 13 Oils spec files were run under the host's bash and under the crate, and the 39 disagreements read. The time box was about 90 minutes of work, and it held; the brush and mvdan-sh expansion code was read only far enough to name its engines. Every probe ran against commit `10224a7`; by the end of the study the working tree held uncommitted edits that move the vfs host onto the WebAssembly module with fuel, a deadline and an output cap, which were read and not probed, and each section says what they would change. It does not repeat [the runtime memo](research-runtime.md) or [the bash suites memo](research-bash-suites.md), and cites the second where a lesson there is confirmed here. Scripts, logs and the probe crate are in [the studies folder](studies/2026-11-21-prior-art/), with `refresh.log` and `licenses.log`.

Labels: EXECUTED means a command ran here and the claim reports its output, with the log named (`experiments/logs/probes-batchN.log`, each part of a batch under its own heading); READ means read in a file cited by path and commit; INFERRED means reasoning from the two.

## The answer

The confinement of effects holds: the machine asks for every effect, normalises every path lexically before asking, and the router refuses NUL bytes, control characters and over-long segments, so a line reaches no more than its authority does (§7). What fails at `10224a7` is the bounding of work, in six reproduced defects. A long but shallow chain, `1+1+…+1` in arithmetic or `a && a && …` inside `[[ ]]`, overflows the native stack and kills the whole Python process with SIGSEGV, and a 45-byte line builds the chain at run time where no parse budget sees it; the 256-call function depth times two nested `if` does the same on an 8 MiB stack (§1). Nothing bounds a line's total work: a 70-byte doubly recursive function runs for months, and because the host never awaits when the machine asks for nothing, `asyncio.wait_for` cannot end it and the event loop does not turn; pattern matching runs past 60 s inside one step on lines bash finishes in 0.06 s (§2). Output is released at every step, so a 75-byte line printed 3.2 GB, and one line can make up to a million verb calls (§3). `printf` precision or a brace zero-pad above 65,535 panics inside the standard formatter, where no clippy denial looks (§4). The regular-expression engine answers "no match" when its budget runs out, so `^a*$` is false on 5,000 `a` (§5). bashkit and just-bash each carry a work budget, a wall-clock deadline, an output cap, a stack-sized function depth and file-system caps that would have stopped every one of these. The uncommitted edits seen at the end add fuel, a 30 s deadline, a 16 MiB output cap and the module as a wall, which would turn the process kill of §1 into a classified error and bound §2 and §3's output (INFERRED); they leave the stack depth a lawful line may reach, the panic, the silent regex answer, the request count and every native host as they were. The Oils run added five uncased conformance defects: a backslash inside a double-quoted `${v-…}` word is dropped, blanks and operators inside the parentheses of an `=~` operand are a syntax error, a variable inside an extended-pattern arm is not expanded, a here-document inside a command substitution inside a here-document is refused, and `<<${a}` takes the expanded word as its delimiter (§6).

## 1. Stack overflow from flat chains and from the product of caps (EXECUTED, READ)

A chain parsed in a loop still builds a left-deep tree, and the evaluator recurses down it (READ `syntax/arith.rs`: the depth counter at lines 201 to 209 rises only on nesting; `machine/arith.rs` `eval` recurses on `Expr::Binary`). The bash suites memo named this risk and mvdan-sh's twelve depth shapes that test it ([R5.2, "Depth limits and stack overflow"](research-bash-suites.md)); not all of them were applied.

| Line | Where it ran | Result | Log |
|---|---|---|---|
| `echo $(( 1+1+…+1 ))`, 50,001 terms | native, main thread, 8 MiB | `50001`, 0.016 s | batch 14 (7b) |
| the same, 100,001 terms | native, main thread | `thread 'main' has overflowed its stack`, exit 134 | batches 8, 14 |
| `e=$(printf '1+%.0s' {1..70000})1; echo $((e))`, 45 bytes | vfs host, Python main thread | process killed, exit 139 | batch 8c |
| the same, 40,000 terms | vfs host, Python main thread | `40001`, exit 0 | batch 8c |
| the same, 20,000 terms | vfs host, thread with a 2 MiB stack | exit 139 | batch 8d |
| the same, 5,000 terms | vfs host, thread with a 512 KiB stack | exit 139 | batch 8d |
| `[[ a && a && … ]]`, 49,000 `&&` | native and vfs host | exit 134 and 139 | batches 8, 8b |
| `let 'x=1+1+…'`, 100,001 terms | native | exit 134 | batch 8 |
| `f(){ …; if :; then if :; then f $(( $1 - 1 )); fi; fi; }; f 255` (two nested `if`) | native, main thread | exit 134 | batch 9c |
| the same with ten nested `if`, `f 100` | native, main thread | exit 134 | batch 9c |
| the same with ten nested `if`, `f 255` | vfs host, 8 MiB thread | exit 139 | batch 9 |

Shapes that held: `a && a && …` at the top level (49,000), `case` with 49,000 alternatives, `[ a -a a … ]` with 40,000, 100,000 nested `-(…)` and 500,000 `!` in arithmetic, `x=x; $((x))` and mutual references (bash's "expression recursion level exceeded"), and nesting of `(`, `$(`, `${x:-` and `[[ !` past the parse depth of 200 (EXECUTED, batches 7 and 8). Plain recursion to the function depth of 256 survives in the vfs host (batch 9d).

The binding's `catch_unwind` cannot catch a stack overflow (READ `shell_binding.rs` at `10224a7`; the spec's decision 9 says so). bashkit's answer is two caps and a stack: a hard ceiling of 16 on function, source and child-shell depth because "100 nested interpreter frames overflow a 2 MiB host stack" (READ `limits.rs` lines 40 to 90, threat TM-DOS-020), a threat entry for the product of caps (TM-DOS-142: "each nesting kind has its own cap, but their product … can exceed a 2 MiB tokio worker stack"), and on-demand stack growth on native targets ([R5.2](research-bash-suites.md)). just-bash caps call depth at 100 (READ `limits.ts`).

In the working tree (READ, not run): the binding runs the module with `WASM_STACK_BYTES = 1 << 20` and its header says a stack overflow becomes "a trap that ends this line and nothing else". In the vfs host the process would then live, and the line would end as an internal error (INFERRED, with [R1 of the runtime memo](research-runtime.md)). Two parts remain. A 1 MiB stack is smaller than the 2 MiB thread that already failed at 20,000 terms, so lines well inside every declared budget would end as faults (INFERRED). And `MemoryHost`, `cargo test` and any native host still lose the process.

What follows for the crate (INFERRED): store chains flat or evaluate them iteratively (arithmetic binary chains, `[[ ]]` `&&`/`||`), and make the fuzz targets generate long chains, not only deep nests; then replace three independent caps with one native-frame budget charged by every descent (parser, evaluator, function call, compound command, substitution), sized against the smallest stack a host may run on, with a law that a line at the budget runs on a 512 KiB thread and in the module.

## 2. No total work budget, no deadline, and a host that never yields (EXECUTED, READ)

At `10224a7` the machine counts loop iterations, function depth and memory, and nothing else ends a line (READ every `Fatal::Budget` in the crate: `loop_iterations`, `function_depth`, `memory`, and the brace and expansion counts in `expand.rs`). The spec puts total work on the runtime's fuel (decision 6), and the vfs host drove the native build ([progress, "Reported and not taken"](progress.md)), so there was no total bound.

- `f(){ (( $1 > 0 )) || return; f $(( $1 - 1 )); f $(( $1 - 1 )); }; f 40`, 70 bytes, is 2^40 calls under a depth of 40 and no loop. Natively it was still running at 20 s after 1,715 steps (batch 1). Through the vfs host under `asyncio.wait_for(…, timeout=2.0)` beside a 50 ms heartbeat task, the process was killed by `timeout 90` with the wait never firing; the same line with `f 16` took 0.59 s with 0 heartbeats where about 12 were due (batch 4). 2^24 times 0.59 s is about 115 days (INFERRED).
- At `10224a7`, `run_line` awaits only inside `host.answer`; a step that asks nothing returns to a loop that calls `step` again at once, so the coroutine never yields (READ `host.py`, the `while True` loop). One line therefore stalls every caller on the event loop for as long as it runs; at the reference deployment's 20 calls a second, a one-second stall holds about 20 calls (INFERRED from `AGENTS.md`, "Per lock").
- Inside one step, pattern matching has no checkpoint, so a host could not regain control even with a slice (EXECUTED, batch 10b, `timeout 60` exit 124 on each): `shopt -s extglob; [[ $x == *(*(a)) ]]` with 3,000 `a` (bash 0.009 s); `[[ $x == *a*a*a*a*a*a*a*a*b ]]` with 100,000 `a` (bash 0.055 s); `y=${x//a*b/}` with 20,000 `a` (bash 0.013 s), and with 3,000 `a` it took 18.8 s in one step (batch 10). Resident memory stayed at 26 MB, so this is CPU, not memory (batch 10c). The matcher's memo bounds one call to pattern size times text size (READ `pattern.rs` header), and `${x//pat/}` calls it for every start and end, which is cubic (INFERRED).

What the prior art enforces (READ): bashkit's `max_work_units` (100,000,000, shared by parser, interpreter and builtins), `max_commands` (10,000), `timeout` (30 s) and `parser_timeout` (5 s), with a work charge and a deadline check inside builtins and traversals (`limits.rs` lines 52 to 175, `docs/security.md`); its glob matcher spends one step budget of 100,000 shared across a substitution's whole scan (`interpreter/glob.rs` lines 246 to 280, TM-DOS-031, TM-DOS-127). just-bash's `maxCommandCount` (100,000, 10,000 hardened), `maxWorkUnits` (100,000,000) and `maxExecutionTimeMs` (one hour by default, 30 s hardened), checked in `execution-scope.ts` line 368. vfs has `Deadline` and `WALL_TIME_BUDGET = 10.0` (READ `src/vfs/deadline.py` line 36, used by `base.py` at lines 1343 and 2191).

In the working tree (READ, not run): `run_line` takes `fuel` and `deadline` (`DEADLINE_SECONDS = 30.0`), runs each step through `call_offloaded(offload_pool(), …)` and cancels the machine when the task is cancelled; the binding sets `FUEL = 50_000_000_000` ("about five seconds"), `FUEL_SLICE = 10_000_000` and a 10 ms epoch. That bounds `f 40` and the pattern lines by fuel and deadline and lets the loop turn (INFERRED). What remains: a native host still has no total bound; the pattern engines still cannot yield a slice, so a slice there ends only by trap; and `cli` still passes no `limits`, `fuel` or `deadline` to `run_line` (READ `base.py` line 1640), so a caller of the public surface cannot lower any budget.

What follows (INFERRED): a machine-side count of work with a declared total (one tick per checkpoint, which `io.rs` already counts as `ticks`), so the native build has a bound and the module has two; checkpoints inside the pattern and regex engines and every expansion loop; and the budgets reachable from `cli`.

## 3. Output and requests are unbounded across steps (EXECUTED, READ)

At `10224a7`, `Machine::step` releases the bytes of the output it hands back (READ `mod.rs`, `hub.release(released)`), so the memory budget bounds output only within one step, and a request ends a step.

- `for i in {1..200}; do printf %16000000d 1; cat /work/a.txt >/dev/null; done`, 75 bytes, returned `Done(0)` after 401 steps with 3,200,000,000 bytes of standard output (batch 6). Without the `cat`, the same loop ended at the 64 MiB memory budget in one step (batch 5).
- Through the vfs host, 40 iterations gave `stdout_len=640000000` and a peak resident size of 1,398 MB; the host keeps every byte in a `bytearray` and returns it as one `str` (batch 6; READ `host.py`). The loop budget allows 1,000,000 iterations.
- One line made 100,000 `touch` requests and 400,000 `cat` requests in under a second against `MemoryHost` (batch 5); in the vfs host each is a verb call. `while :; do echo "$x" >> /big; done` with a 1 MB `x` appended 11,507 times in 20 s, about 11.5 GB into the host (batch 5). `shopt -s globstar; echo /t/**/**/**/**` over a 1,110-directory tree issued 38,104 `list` requests, 34 per directory (batch 11).
- `printf %999999999d 1` printed 16,777,216 bytes and exited 0 (batch 1; READ `printf.rs` line 13, `MAX_WIDTH = 1 << 24`), where bash prints 999,999,999: a silent truncation.

What the prior art enforces (READ): bashkit's `max_stdout_bytes` and `max_stderr_bytes` (1 MiB each), `max_file_size`, `max_file_count` and total bytes on its file system (TM-DOS-005, -006, -010), and capture that reserves before each write (`docs/security.md`); just-bash's `maxOutputSize` (256 MiB, 10 MiB hardened) charged as output is produced (`execution-scope.ts` line 250, `interpreter/control-flow.ts` line 95), `maxFileSystemBytes`, `maxGlobOperations` (1,000,000) and at most five `**` segments in one pattern (`shell/glob.ts` line 40). bashkit TM-DOS-109 names silent truncation at a cap, exit 0 with no diagnostic, as a threat of its own.

In the working tree (READ, not run): `Limits.output_bytes` with `OUTPUT_BYTES = 16 << 20`, counted in `Hub::emit` across the whole line and ending it with `Budget("output", …)`. That bounds the first two items (INFERRED). The request count, the bytes written and the glob fan-out stay unbounded by the shell, and the `printf` width still truncates silently.

## 4. A panic inside the standard formatter (EXECUTED, READ)

Rust's `format!` takes a runtime width or precision only up to 65,535 and panics past it with "Formatting argument out of range". The crate passes user-chosen numbers there (READ `printf.rs` lines 474, 489, 509 and 519; `expand.rs` line 444 `pad_number`; `programs/text.rs` line 539 takes a width from counts).

- `printf %.65535f 1 | wc -c` printed `65537`; `printf %.65536f 1`, `%.65536e` and `%.65537g` panicked at `printf.rs:474`, `:489` and `:509` (batch 2).
- `echo {000…0001..2}` with 70,000 zeros panicked at `expand.rs:444`; 65,000 zeros ran (batch 2).
- Through the vfs host at `10224a7` the binding caught it: exit 1, one `vfs.internal` "the machine panicked", and the process went on; but the output of earlier commands was lost (`echo before` printed nothing) and the panic hook wrote a full backtrace to the process's standard error (batches 3, 3b). In the module, with `panic = "abort"`, it is a trap (INFERRED from [R1](research-runtime.md)).

The clippy denials (`panic`, `unwrap_used`, `indexing_slicing`) cannot see a panic inside `core::fmt`, and neither fuzz target found it (INFERRED). bashkit lists format-width threats per builtin (`od -w`, `pr`, `printf` in `docs/security.md`). What follows: clamp every runtime width and precision to 65,535 before `format!`, or pad by hand as `%70000.2f` already does (it ran, batch 2), and add a source rule that flags a `$}` in a format string.

## 5. The regular-expression engine answers "no match" when its budget runs out (EXECUTED, READ)

The engine is a backtracking walk that explores every path to find the POSIX longest match, under 2,000,000 steps and 4,000 frames; when either runs out the search returns what it has, and with nothing found that is "no match" (READ `regex.rs` lines 1 to 14 and 344 to 352). `[[ $x =~ ^a*$ ]]` with 5,000 `a` returned 1, and with 3,000 returned 0; bash returns 0 for both (batch 10). progress.md reports the 4,000-character limit; the silent wrong answer is the defect. Exponential shapes (`(a|a)*b`, `^(a|aa)*(c)$`, `^(a|ab|b)*$`) agreed with bash and finished in 0.016 s or less (batch 10).

| Project | `[[ =~ ]]` engine | Glob and extglob | Bound |
|---|---|---|---|
| vfs-shell | own backtracking walk, POSIX leftmost-longest by exhaustive search | own matcher, memo per (sequence, node, position, end) | 2,000,000 steps and 4,000 frames, then "no match"; glob 2,000 frames and list depth 64, no step budget |
| bashkit | `regex` crate (finite automaton) behind a compile cache; grep and awk add a longest-end pass with a `MatchKind::All` DFA | own matcher | glob 100,000 shared steps and depth 50, then false; regex size limits, `RE_DUP_MAX` 32,767 |
| just-bash | `re2js`, linear time, leftmost-first | glob converted to a regex | `maxGlobOperations`, five `**` segments |
| brush | `fancy-regex` (backtracking where needed) | glob converted to a `fancy-regex`; prefix removal tries every prefix | none seen in `patterns.rs` |
| mvdan-sh | Go `regexp.Compile`, RE2 syntax, leftmost-first (not `CompilePOSIX`) | `pattern.Regexp` converts to a Go regexp | `MaxPatternSize` 64 KiB |
| Oils | libc `regcomp(REG_EXTENDED)` and `regexec`, POSIX | libc `fnmatch` with `FNM_EXTMATCH` | the C library's |

All READ at the commits in Sources. None of the five has a linear POSIX-longest engine of its own; bashkit gets longest semantics in grep by a second DFA pass from the leftmost start (READ `grep_pattern.rs` header), and two of the five (just-bash, mvdan-sh) accept leftmost-first, which differs from bash on `ab|abcd` (INFERRED from the engines' documented semantics). What follows (INFERRED): a Thompson or Pike simulation finds the leftmost start and the longest end in time linear in the text for any expression without back-references, which bash's ERE does not have, and needs no step budget; if a budget stays, its exhaustion should end the line as a budget error, never answer false. The uncommitted edits do not touch `regex.rs` (READ `git diff --stat`).

## 6. The Oils cases run against the crate (EXECUTED)

468 cases from `word-split`, `word-eval`, `quote`, `glob`, `glob-bash`, `extglob-match`, `regex`, `dbracket`, `here-doc`, `command-sub`, `var-sub-quote`, `parse-errors` and `arith` ran under host bash and under the crate; 66 were skipped because their text names something outside a pure-language run; 363 agreed and 39 differed (`experiments/oils-differential.log`). The run is a measurement in the scratchpad; no case was copied into the repository, and the log keeps titles and outputs only. Eleven of the 39 are programs `MemoryHost` does not mount (`argv.py`, `od`, `tac`) or the host bash's C locale. The rest were re-probed with lines written here (batches 11b, 12 and 14).

- New and uncased. `echo "${v-a\nb}" "${v:-c\qd}"` prints `anb cqd`; bash prints `a\nb c\qd`, because inside double quotes a backslash before anything but `$`, `` ` ``, `"`, `\` or newline stays. `[[ "a  b" =~ (a  b) ]]`, `[[ "< >" =~ (< >) ]]` and `[[ "a b" =~ (a b|c) ]]` are syntax errors; bash accepts blanks and operator characters inside the parentheses of an `=~` operand (the lexer mode the bash suites memo calls `BashRegex`). With `shopt -s extglob` on its own line, `str=x; [[ $str == !($str) ]]` is true where bash is false, and `--@(help|verbose|$prefix-@(long|short)-'option')` fails to match where bash matches; the same patterns with the variable written out agree, so a parameter inside an extended-pattern arm is not expanded (INFERRED from batch 14). A here-document inside `$(…)` inside a here-document body is refused, "here-document inside a here-document body is not supported" (READ `parser.rs` line 398); bash runs it. `cat <<${a}` and `cat <<$(a)` print an extra empty line and, for the second, run `a`; the delimiter appears to be taken as the expanded word rather than its literal text (INFERRED).
- Already in `known_failures.txt`. Extended patterns inside `[[ ]]` without `shopt -s extglob` (most of the 17 extglob differences; corpus `conditionals/extended-patterns-work-inside-double-brackets`); `set -u` and an unset name in arithmetic does not end the line (corpus `options/nounset-in-arithmetic`); `globstar` leaving out the directory itself (corpus `filename-expansion/globstar-alone-lists-everything`, and batches 11 and 11b: 1,110 words against bash's 1,111).
- An uncased variant of a known failure. A literal `..` after a glob component: `echo /t/a/../*` prints the word unchanged where bash prints 20 entries, and `/t/*/..` likewise (batches 11, 11b). The listed `filename-expansion/glob-after-a-dot-slash-prefix` likely shares the cause: a literal component is matched against the listing, which holds no `.` or `..` (INFERRED).
- Not judged, because bash 5.2 and Oils' expected answer disagree and the 5.3 referee was not run: `"${var-'}'}"`, `a=( inside=() )`, and `failglob` on a `;` list.
- Agreed, of the parser hard spots the bash suites memo named: `$(case a in a) …;; esac)`, `$(( (1+2)*3 ))` beside `$( (echo sub) )`, `$((echo hi) )`, `$( (echo a); (echo b) )`, a here-document in a function body called twice, quoted and `<<-` delimiters on one line, IFS splitting with empty fields and blank-plus-colon IFS, `"${a[*]}"` under a custom IFS, and all 47 `dbracket` cases run (batch 12 and the differential log).

## 7. Confinement of effects, compared (READ, EXECUTED)

| Concern | bashkit | just-bash | vfs-shell and its host |
|---|---|---|---|
| File system | in-memory VFS by default; real mounts opt-in; `..` normalised; symlinks followed inside the VFS only | `OverlayFs` in memory over a read-only root; `isPathWithinRoot`; symlinks denied by default; NUL bytes refused; real paths stripped from errors | no file system in the machine; every path made absolute and normalised lexically before a request (READ `exec.rs` lines 1732 to 1752); no symlink in the request vocabulary; each request one router verb with the caller's authority (READ `host.py`); the router refused U+0001, NUL and a 300-byte segment, and `/d/../../../f` landed at `/f` (EXECUTED, batch 13) |
| Processes and `exec` | `bash -c`, `exec` and `&` run inside the interpreter | no `child_process` import; host-reaching globals (`Function`, `process.*`, `WebAssembly`, dynamic `import()`) blocked by a proxy | no process, clock or network in the crate (spec decision 4, a source test); `eval`, `source`, `exec`, `trap` and job control refused before the line runs (READ progress.md) |
| Network | HTTP(S) only, host allow-list, no redirect followed, no decompression | `curl` registered only with a `NetworkConfig`; each redirect checked; 10 MB response cap | none |
| Time and randomness | virtual | `performance.now` blocked; `date` defaults to UTC | asked of the host as `Value` requests (READ `mod.rs`) |
| Threat document | `knowledge/security/threat-model.md`, stable ids, about 150 entries in 11 categories, each marked mitigated or not, with tests | `THREAT_MODEL.md`: actors, trust boundaries, an attack-surface table per area naming the file of each defence, known gaps | the spec's decisions 4, 7, 8 and 9; no threat list |

A host-mediated machine whose every effect is an authority-checked verb is a stronger boundary than either in-process VFS, because there is nothing in the process to escape to (INFERRED). The gap is elsewhere: both prior-art projects keep a living list of denial-of-service threats, each with a test, and their lists name every shape §§1 to 5 reproduced: TM-DOS-142 (product of caps), TM-DOS-020 and -089 (stack), TM-DOS-016 to -019 (loops and command count), TM-DOS-002 and -058 (output), TM-DOS-031 and -127 (pattern matching), TM-DOS-025 (regex), TM-DOS-006, -010 and -095 (files, appends, glob fan-out), TM-DOS-109 (silent truncation) (READ `threat-model.md`).

## 8. Limits one of them has that vfs-shell lacks, judged here (EXECUTED where a batch is named, else INFERRED)

## One line

The shell confines what a line can touch, but at `10224a7` not how long it runs, how much it prints or how deep it goes: a 45-byte line kills the host process, a 70-byte line never ends and a 75-byte line prints 3.2 GB, where bashkit and just-bash each carry a work budget, a deadline, an output cap and a stack-sized depth; the uncommitted module host covers the first three in part, and flat chains, the formatter panic and the silent regex answer remain.
