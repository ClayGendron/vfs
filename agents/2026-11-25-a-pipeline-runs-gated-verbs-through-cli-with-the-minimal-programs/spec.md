It serves roadmap story F3 at gate b, criteria 2 and 4 ([roadmap](../../context/standards/roadmap.md), lines 683 to 699). It rests on the built listing cursor and the built shell, and it waits for nothing.

## The outcome wanted

An agent types `ls /big | wc -l` over a directory of 10,000 files and gets `10000`, and vfs answers it with ten `ls` calls of 1,000 rows each, never one call of 10,000. The agent types `ls /big | head -3` and gets three names, and vfs answers it with at most two `ls` calls, because `ls` stops asking once its reader has gone, as GNU `ls` stops at `SIGPIPE`. What the shell holds while it lists is one page, whatever the size of the directory. The agent types `sweep`, `posture` or `add_member` and gets bash's `command not found` with a hint, exit 127, and the result carries one `vfs.unrecognized` warning that says so, as `curl` already carries one `vfs.unsupported` warning.

## Terms

- **Page**: the rows one `ls` call returns under `limit=LISTING_PAGE`, and the one `entries` reply the host makes of them.
- **Key**: `Result.next_after`, the path of a page's last row, passed back as `after=` to ask for the next page.
- **Drain**: asking page after page until a page carries no key, and holding them all.
- **Never table**: `UNKNOWN_PROGRAMS` in `src/vfs/shell/host.py`, the names vfs knows and never runs, each with a hint; they answer 127.

## What the code does today

1. The host lists a directory with one unpaged call: `_list` calls `self._fs.ls(path, authority=self._authority)` with no `limit` and no `after`, and replies with every row's name and kind (`src/vfs/shell/host.py:429-437`).
2. The request carries only a path and the reply only names: `Request::List { path }` and `Reply::Entries(Vec<Entry>)` (`crates/vfs-shell/src/machine/mod.rs:186-188`, `:271`). The wire and the binding carry the same two shapes (`crates/vfs-shell-wasm/src/wire.rs:198-200`, `:318-319`, `:458-471`, `:600`; `crates/vfs-core/src/shell_binding.rs:641-652`, `:712-715`).
3. Four places ask for a listing, each once per directory: the `ls`, `find`, `rm` and `cp` programs through one helper (`crates/vfs-shell/src/programs/files.rs:8-18`), the library `grep -r` walk (`crates/vfs-shell/src/programs/grep.rs:349`) and pathname expansion (`crates/vfs-shell/src/machine/expand.rs:2042-2057`).
4. `ls` builds its whole output in one string and writes it once, after every directory is listed (`crates/vfs-shell/src/programs/files.rs:110-169`). So `ls | head -3` cannot stop it early.
5. A listing reply is charged to nothing: the machine's counted bytes grow for pipe buffers, output, read bodies and statuses (`crates/vfs-shell/src/machine/io.rs:93-100` and its callers), and no caller charges an `Entries` reply (EXECUTED, `grep -rn "charge(" crates/vfs-shell/src`).
6. A name of the never table answers 127 with its hint and keeps no fact; a name of `REFUSED_PROGRAMS` answers 126 and keeps one `vfs.unsupported` warning (`src/vfs/shell/host.py:442-446`). `sweep`, `posture`, `set_posture`, `add_member` and `remove_member` are in neither table, so each prints a bare `command not found` (`host.py:447-449`).
7. EXECUTED on 2026-11-25 over a directory of 2,000 files on the default storage: `ls /d | head -3` and `ls /d | wc -l` each issue one `ls` call with `limit=None`, and both give `statuses == [[0, 0]]`, because the whole output, 14 KB, fits in one pipe. `sweep; posture; git log` gives three 127s and `errors == []`.
8. EXECUTED: a page asked as `ls("/d", after=, limit=5)` over twelve names of mixed case, punctuation and one non-ASCII letter returns them in byte order across three pages, the last with `next_after is None`, and the key is a `Path`. In that order `-x` sorts before `.` and `..`.

## The problem

The shell's `ls` reads a whole directory in one call, holds every name in the host and in the machine, and prints only when it has them all. At the reference deployment most directories hold a few files and this costs nothing, but the tail runs into thousands of children, and an agent's `ls dir | head` over such a directory pays for the whole directory to see three names. The bytes it holds are counted nowhere, so the machine's 64 MiB budget does not bound them; only the 256 MiB wall of the module does. The listing spec built the page and left the shell to use it, and F3 criterion 2, the counted proof that a pipe moves a listing in bounded pieces and stops when its reader stops, cannot pass until it does. Separately, F3 criterion 4 asks that the developer's verbs answer as `vfs.unrecognized`, and today a caller over MCP who types `sweep` sees exit 127 and no fact saying why.

## Decisions

1. **The host asks for every listing a page at a time.** `_Host._list(path, after)` calls `self._fs.ls(path, after=after, limit=LISTING_PAGE, authority=self._authority)` and replies `("entries", (entries, next))`, where `entries` is today's list of `(name, kind)` pairs and `next` is `str(result.next_after)` or `None`. `answer` passes `args["after"]` for `op == "list"`. A refusal of the page is today's refusal, kept as a warning (`host.py:495-505`). Precedent: the listing spec's decision 5.
2. **`LISTING_PAGE: Final = 1_000` is a module constant of `src/vfs/shell/host.py`, beside `READING_BYTES`.** Its docstring says a directory of more children is listed in pages that follow `next_after`, so the host and the machine hold one page at a time. 1,000 makes F3 criterion 2's ten chunks of 10,000 exact, it is the page the listing spec measured and the `ROWS_PER_CHUNK` the source declared (archived spec 167, line 122 and line 243), and at the reference deployment's largest measured directory, 1,533 entries, it is two calls where 128 is twelve. One page of names at the 255-byte name limit is about 256 KB, under half a percent of the machine's 64 MiB `memory_bytes`. This departs from the 128 of the file-reads spec's decision 3, which gives no reason for its figure; choice 1. It is not a key of `LIMITS`: it is the host's page, not a budget of the machine.
3. **The request carries the key and the reply carries the next one.** `Request::List { path: String, after: Option<String> }` and `Reply::Entries { entries: Vec<Entry>, next: Option<String> }` in `crates/vfs-shell/src/machine/mod.rs`. The machine treats both keys as opaque text it hands back; a host chooses what they hold, and the vfs host holds the router's path. The JSON wire adds `"after"` to a `list` request and `"next"` to an `entries` reply, each a string or `null`; the binding passes `after` in the request's arguments and extracts the reply as `(list[tuple[str, str]], str | None)`. A host that answers in one page replies `next: None`, so no host is made to page.
4. **A host's pages ascend, and the machine refuses a key that does not.** The contract a host keeps is that names arrive in byte order across pages and no name repeats. The machine sorts each page, as it sorts today, and refuses a reply whose `next` is not strictly greater, bytewise, than the `after` it asked with as `HostError::Invalid`, so no host can hold a line in a loop of pages. A page may be empty and still carry a key, since a page of hidden rows is short; the strict rule is what ends such a run. The vfs host meets the contract: its rows come in path order on the binary-collated column on SQLite and Postgres (`src/vfs/models/rows.py:176-194`) and by the frontier rule across mounts (`src/vfs/results/paging.py`), and among the children of one directory path order is name order.
5. **A page is charged while the machine holds it.** `machine::entry_bytes(entry: &Entry) -> usize` is the name's length plus one byte for its kind, beside `status_bytes` (`crates/vfs-shell/src/machine/mod.rs:307`), which counts a status the same plain way. `machine::files::Listing { pub entries: Vec<Entry>, held: usize, hub: HubRef }` charges each page's `entry_bytes` as it is added and releases them when dropped, as `ReadBuffer` charges its body and releases it on drop (`crates/vfs-shell/src/machine/files.rs:20-52`). A page the charge cannot fit ends the line with the memory budget, status 137, as any other held byte does. This is the "charged while held" of the file-reads spec's decision 3.
6. **Two functions of `crates/vfs-shell/src/machine/files.rs` ask for listings, and every caller uses one of them.** `list_page(sh, path, after) -> Result<Result<(Listing, Option<String>), HostError>, Flow>` asks for one page under a fresh key from `sh.key()`, and runs `sync_path` before the first page only. `list_all(sh, path) -> Result<Result<Listing, HostError>, Flow>` drains: it asks page after page into one `Listing` until a page carries no key. The helper `list` of `programs/files.rs`, the `grep -r` walk and pathname expansion's `list_dir` call `list_all`, so `find`, `rm -r`, `cp -r`, `rm` of an empty directory, `grep -r` and `*` print what they print today. `ls` alone calls `list_page` (decision 7). Each page is one request with its own key, so the keys of a line stay a function of the line and its replies, and two runs over one world ask equal key lists, as decision 5 of the shell spec requires.
7. **`ls` prints each page of a directory as it arrives, except under `-r`.** For each directory, `ls` asks the first page, prints its names, asks the next, and so on, writing each page to its standard output before it asks the next. Under `-a`, `.` and `..` are merged into that stream at their byte position, because names such as `-x` sort before them (today, item 8). Under `-R`, the names of a directory's subdirectories are kept across its pages, charged by `entry_bytes`, and visited when the directory is done, in the order GNU prints them. Under `-r` the directory is drained first and printed in reverse, because its first line is its last name; GNU `ls` also reads a whole directory before it sorts. Headers, blank lines between directories, `-F`, `-p`, `-d` and file operands print as today. So a plain `ls` holds one page and the pipe's 64 KiB whatever the directory's size, and when its reader has gone its next write is refused and it ends with 141, as it does today when its single write is refused (`crates/vfs-shell/src/machine/io.rs:324-338`). Precedent: POSIX `ls` reading by `readdir`, which returns entries as the directory is read.
8. **A refusal after the first page ends that directory with GNU's words.** When a later page is refused, `ls` prints `ls: reading directory '<dir>': <message>`, keeps every name it printed, goes on to its next operand and exits 2, as GNU `ls` does for a failed `readdir`. A refusal of the first page keeps today's `cannot open directory` line (`crates/vfs-shell/src/programs/files.rs:128-139`). A caller who loses the right to list between two pages therefore sees only the names of the pages it was judged for: each page is a read of its own, checked against the caller's rights afresh (`src/vfs/base.py:870-873`).
9. **`ls` takes no `--after` or `--limit`.** The source's rebase note gave the programs both flags (archived spec 167, line 243). GNU `ls` has neither, the shell prints what GNU prints, and an unknown long option is GNU's own error; paging is the host's business and no caller of a line needs to see it.
10. **The five developer's verbs join the never table, and every name of the never table keeps one `vfs.unrecognized` warning.** `UNKNOWN_PROGRAMS` gains `sweep`, `posture`, `set_posture`, `add_member` and `remove_member`, each with the hint `command not found; <verb> is a developer's verb, left off the tools a line is given`, where `<verb>` is `set_posture` for `posture` and the name itself for the others. The wording follows the `sweep` docstring, "a developer's verb, meant to be left off the tools an agent is given" (`src/vfs/base.py:1138`). `_start` keeps `classified(ErrorKind.unrecognized, detail=f"{name}: {UNKNOWN_PROGRAMS[name]}")` through `keep`, as it keeps the `vfs.unsupported` of a refused program (`host.py:443`), and still replies `("refused", (127, hint))`. No verb is called. A name in no table keeps nothing (choice 3). The exit stays 127, as bash prints for a name it cannot find. The class docstring of `ErrorKind` changes "only dispatch emits ``unrecognized``" to say that dispatch emits it for a verb name and the shell's host for a command name it knows and never runs (`src/vfs/results/kinds.py:49-50`), the note unit 167-2 hands here. Precedent: F3 criterion 4 and the source's never class (archived spec 167, line 86).
11. **F3 criterion 5's `cat img.png` placeholder is not built here; it waits for the run record.** The ruling of 2026-11-22 keeps binary output a replacement-decode until the renderer's placeholder and a stored row land ([progress](../2026-11-21-the-shell-speaks-bash/progress.md), line 35), and a placeholder names a row by path, type, size and version, which a line's standard output is not. Unit 169-3 stores a line's standard output as a row ([its spec](../2026-11-25-every-shell-call-leaves-a-run-record-as-rows-in-the-root-bindings-storage/spec.md)), and it depends on this unit, so the placeholder is its to print, by its decision 10.
12. **The early close is reported by the status, not by a fact.** A producer `head` stopped ends with 141 in `statuses`, as bash's `PIPESTATUS` shows it, and no `vfs.cancelled` warning is kept. `vfs.cancelled` is the kind of a cancelled line, exit 130 (`host.py:292-293`), and a `| head` is a line working as written; F3 criterion 2's "reports `vfs.cancelled` at info severity" is not carried (choice 2).
13. **The `MemoryHost` pages on request.** `pub list_page: Option<usize>` on `MemoryHost` (`crates/vfs-shell/src/host/memory.rs`), `None` by default, answers a `List` with at most that many children strictly after `after`, and `next` set to the path of the last one while more remain, beside the read schedule `read_chunks` that unit 168-2's decision 1 puts in place of `read_chunk`, a field dev declares at `memory.rs:51` and reads nowhere. With `None` it answers one page, so the recorded corpus runs unchanged.
14. **The gates are `scripts/ci.sh`, `cargo test -p vfs-shell -p vfs-shell-wasm`, the `wasm32-unknown-unknown` build, `scripts/docs.sh check` and the Postgres leg of `tests/shell/test_engines.py`.** The Rust edit is followed by `uv sync --all-extras --group dev --reinstall-package vfs-py`, as AGENTS.md requires. The Postgres leg runs because the shell's output now depends on the engine's page order across pages, which the binary collation on Postgres decides.

## Cost

- **Per verb call, the `ls` of a line.** A directory of `n` children costs `ceil(n / LISTING_PAGE)` router calls of 5 statements each for a named caller (the listing spec's measured count), each reading at most `LISTING_PAGE + 1` rows through the live-children partial index. At the reference deployment the median directory holds 2 files, so the common `ls` is one page, the same one call as today with a `LIMIT` added. The largest measured directory, 1,533 entries, is 2 calls and 10 statements where it was 1 call and 5. A 10,000-child directory is 10 calls and 50 statements reading 10,010 rows where it was 5 statements reading 10,000. Agent verb calls are about 150,000 a day and lists about a third of them; even if every one were a 10,000-child `ls`, the added statements would be about 2.25 million a day of bounded, uncontended reads.
- **The least generous engine.** Each page statement binds a fixed number of parameters and no `IN` list, so nothing grows with the directory on SQLite or Postgres. The `GENERIC` floor and any storage without the `listing_cursor` trait get the kernel's derived page, which costs the whole listing per page; that profile is the listing spec's and is declared there.
- **Memory.** The host holds one page of at most `LISTING_PAGE` rows. The machine holds one page and at most `PIPE_CAPACITY` bytes in each pipe for a plain `ls`, charged against `memory_bytes` (64 MiB). A drain (`ls -r`, `find`, `grep -r`, `rm -r`, `cp -r`, `*`) holds the whole directory, now charged, so it ends at status 137 at the budget, about three million 20-byte names, instead of at the module's 256 MiB wall.
- **Per line.** Under `VERB_CALL_BUDGET`, 10,000 requests a line, one line can drain at most 10,000 pages, 10,000,000 names, the size of the reference deployment's whole corpus; no directory in it comes near.
- **The boundary.** Each page crosses the module's boundary as one reply of about 30 bytes a name in JSON, about 30 KB a page. At the reference page's figure of about 270 instructions a byte that is about 8 million instructions, under one `FUEL_SLICE` (10,000,000) and 0.04% of the line's 20,000,000,000 (INFERRED from `documentation/reference/shell.md`, Budgets).
- **Locks.** None is added. Each page is a read of its own that waits on no writer. A file written or deleted between two pages may or may not be listed, which POSIX also leaves open for a `readdir` of a directory that changes after `opendir`.

## Left as it is

- `find`, `grep -r`, `rm`, `cp` and pathname expansion keep their whole-directory walk (decision 6). Streaming them changes their order or their algorithm, and the served `find` and `grep` page under [a served grep hands its matches to the line a page at a time](../2026-11-22-a-served-grep-hands-its-matches-to-the-line-a-page-at-a-time/spec.md).
- `rm` of a directory without `-r` and `find -empty` drain a directory to learn that it is empty; a first non-empty page would do. It is a cost on a rare form, not a fault, and it keeps one path for every caller.
- The rest of the battery stays on memory storage. What it tests is the host's mapping of requests to verbs, which no engine changes; the effects already run on both engines (`tests/shell/test_engines.py`), and decision 14 adds the one place where the engine changes what a line prints.
- F3 criterion 7, `Session.cli` keeping `cwd`, is specified by [a session works in turns](../2026-11-22-a-session-works-in-turns-and-rewinds-or-forks-at-one/spec.md) (its decision 9 and its rule that `Session.cli` takes `cwd: str | None = None`), which also decides that no history is kept.
- F3 criterion 10, the determinism law with spec 177's fingerprint and the prefix law, is replaced by [an interrupted line replays its replies](../2026-11-22-an-interrupted-line-replays-its-replies/spec.md), and roadmap decision D60, as leaned, would remove the need for it. Decision 6 keeps the built half true. Under roadmap decision D41's record a page is a read the walk depends on and would be recorded as a reply; the interrupted-line spec already counts listings among the replies its journal holds (its line 292).

## Choices to confirm

1. **The page size: 1,000 or 128.** The file-reads spec wrote 128 with no reason; F3 criterion 2, the listing spec's measurements and the source write 1,000. Taken: 1,000 (decision 2). Both are one constant and either is cheap to reverse; 1,000 is taken because it makes the roadmap's criterion exact and costs one sixth of the calls at the largest measured directory.
2. **Does a producer a reader closed leave a fact?** The options are status 141 alone, as bash shows it, or a `vfs.cancelled` warning or info fact as F3 criterion 2 wrote. Taken: 141 alone (decision 12). Adding a fact later is additive; removing one a caller had learned to read is not.
3. **Does a name in no table keep a fact?** The options are nothing, as bash knows nothing more than `command not found`, or one `vfs.unrecognized` warning for every unresolved name. Taken: nothing (decision 10). A fact for every name can be added later without changing any line's output.
4. **Which developer's verbs are refused.** F3 criterion 4 names `sweep` and `posture`; the source adds `add_member` and `remove_member`; `set_posture` is the verb's own name. Taken: all five (decision 10). Serving one of them later as a program is additive, a 127 becoming a run; refusing one that agents had come to use would not be.
