# `install_extensions(path)` runs one mount's install from the file system, on both faces

A draft, written on 2026-11-25 and checked against `dev` at `27f3d24d`. It is not reviewed, and nothing is built. It serves roadmap story D3, acceptance item 5, at gate b ([the roadmap](../../context/standards/roadmap.md), line 525, and the gate table row at line 489), as unit 157-3 of [the unit map](../2026-11-25-the-backlog-converted/units.md). The source is [spec 157](../../context/specifications/archive/157-postgres-provisioning-for-host-apps/spec.md), read through [the study of that source](../2026-11-25-the-backlog-converted/studies/051-162/157-postgres-provisioning-for-host-apps.md) and [the reassessment against dev](../2026-11-25-the-backlog-converted/reassessment/engines.md), section 157-3; spec 157 itself holds nothing of this unit, whose content is the roadmap's item. The unit's SQL Server clause is dropped: SQL Server is not served and a storage can no longer be handed a session factory, so the title states the facade half alone, and the directory keeps the slug the unit map gave it. It rests on the storage's `install_extensions`, which is built, and on the freeze rule of roadmap decision D2.

## The outcome wanted

A developer who holds a file system, and not the storage behind it, runs the storage's extension install for one mount with one call: `await fs.install_extensions("/data")` on `AsyncVirtualFileSystem`, or `fs.install_extensions("/data")` on `VirtualFileSystem`. On Postgres it installs pgvector for a role that may create extensions and proves the distance function; on SQLite it installs nothing, proves the function and succeeds. The answer is a `Result`: success, or the storage's own refusal stamped with the mount it came from. A mount whose storage has no install succeeds with nothing done. The name is one of the router's management methods, so the sync facade's mirror and the drift tests cover it, and no agent face reaches it.

## What the code does today

- The router's management methods are `add_mount`, `remove_mount`, `update_mount`, `close`, `locate` and `locate_edge` (`src/vfs/ops.py:110-113`). `install_extensions` is named in `src/vfs` only by the database backend (EXECUTED, grep), so a developer who built the file system from a storage and let go of it cannot reach the install.
- `test_router_public_verbs_are_exactly_the_registered_ops` holds the router's public coroutines to `ALL_OPS | MANAGEMENT_METHODS | FRONT_METHODS` (`tests/test_ops.py:274-285`), and `test_every_router_coroutine_has_a_sync_twin` gives each of them a twin of the same signature (`tests/test_sync.py:231-237`). `test_the_management_allowlist_is_owned_by_ops` pins the six names (`tests/test_sync.py:685-689`).
- The sync facade forwards a management method through `_await`, which raises `RuntimeError` for a closed facade and for a call from its own loop thread (`src/vfs/sync.py:709-715`). `_result`, the verb hop, takes an `Op` (`:691`), which this name is not.
- `close()` finds a storage's optional method by a `runtime_checkable` protocol, `isinstance(mount.storage, SupportsClose)` (`src/vfs/base.py:561`; `src/vfs/storage/protocol.py:566-578`), not by `capabilities()`, which declares ops only.
- `src/vfs/base.py` holds 3,090 lines and its entry in `MODULE_LINE_BASELINE` is exactly 3,090 (`tests/lint/allowlist.py:27`); a module that grows past its entry fails `tests/lint/test_code_shape.py::test_a_listed_module_never_grows_and_an_unlisted_one_stays_under_the_ceiling`. `sync.py` (759), `ops.py` (220) and `protocol.py` (630) are under the 1,000-line ceiling (EXECUTED, `wc -l`).
- The shell's `Router` protocol names verbs only (`src/vfs/shell/programs.py:141-229`), and no MCP package exists, so no agent face reaches a management method.

## The problem

The roadmap's gate table reads "`install_extensions` | built on the storage; not reachable from the router" (`context/standards/roadmap.md:489`), and story D3's fifth item asks for `fs.install_extensions(path)` (`:525`). `context/standards/how-we-code.md:44` names the explicit verb as the way extensions are installed, so the verb is the documented path for a developer whose role may install pgvector; today that developer must keep a reference to the storage object to use it. The cost at the reference deployment is nil: the call is a developer's act at deployment, a few times in a database's life, on none of the per-call, per-write or per-index multipliers.

## Decisions

1. **`AsyncVirtualFileSystem.install_extensions(self, path: str, *, authority: Authority | None = None) -> Result`, and its twin `VirtualFileSystem.install_extensions` with the same parameters.** The router method sits after `update_mount` in the "mount administration" group of `src/vfs/base.py`; the twin sits after `update_mount` in `src/vfs/sync.py`. `path` has no default, as `update_mount`'s has none (`base.py:472-481`); a default of `"/"` can be added later without breaking a caller, and taking one away cannot. `authority` is keyword-only with `None`, as on every mount method (pinned by `tests/base/test_mount_authority.py::test_every_mount_method_takes_an_authority`).
2. **`path` names a mount point exactly, the root included.** The call normalizes it with `normalize_mount_path(path, allow_root=True)` and takes the mount with `_require_mount`, as `update_mount` does (`base.py:512-515`). A path below a mount point, a path with no mount, a path through `.vfs`, an invalid path and a closed kernel raise `ValueError`, before any storage is asked. Reason: the verb acts on one mount's storage, the roadmap says "for one mount", and a mount method that names a mount takes its mount point. Choice 1 holds the wider reading.
3. **The caller must hold `read_write` at the mount point, judged by `_require_mount_rights("install the extensions of", mount_path, authority)`, which raises `MountError` carrying the refusal.** The storage that holds the mount point judges, through `holds`; the system actor asks no storage; a storage that keeps no grants refuses nobody (`base.py:2779-2800`; `src/vfs/mounts.py:355-375`). The refusals are those of the sibling methods: `unauthenticated` for the anonymous caller under a closed posture, `not_found` for a caller who holds nothing there, so the mount point is not disclosed, and `permission_denied` for a lower level. Reason: an install changes the database under a mount, a change no lighter than `update_mount`'s policy change, and one rule for who may administer a mount keeps one test family (`tests/base/test_mount_authority.py`) for all of them. The judgment runs before the storage is asked, so a refused caller installs nothing. Choices 2 and 3 hold the other channel and the other level.
4. **The call takes no mount lock and does not judge again after the install.** It changes nothing in the mount table, so `require_judgement_stands` (`mounts.py:247`) has nothing to protect. The storage installed on is the one read from the table before the judgment, so the install runs on the storage the caller was judged for, even if the mount is replaced while it runs.
5. **A storage has the install when it is an instance of a new `runtime_checkable` protocol, `SupportsInstallExtensions`, with one member, `async def install_extensions(self) -> Result: ...`.** It sits after `SupportsClose` in `src/vfs/storage/protocol.py` and joins the imports and `__all__` of `src/vfs/storage/__init__.py`. Its docstring states the contract the database backend already keeps: optional, developer-plane, idempotent, never called by first touch, every outcome a `Result`. A mount whose storage is not an instance gets `Result(ops=("install_extensions",))`, a success with nothing done. Reason: the precedent is `close()`, which finds the optional `close` through `SupportsClose` (`base.py:561`), and on the kernel-records branches `SupportsRecordPlace`; `capabilities()` is the wrong place, because the install is not an op, no mask may hide it and no rung gates it. The name is therefore not added to `Op`, `ALL_OPS`, `DEVELOPER_OPS` or any capability set.
6. **The storage's `Result` is returned as `result.with_mount(mount_path)`, with its kinds unchanged.** Each error gains `source` naming the mount (`src/vfs/results/envelope.py:678`), as every routed result does; the storage's `permission_denied` for a role that may not install, its `unavailable` for a missing function or a failed probe, and its success all pass through. The router adds no kind and raises for none of the storage's outcomes. Reason: the outcome of the install is the storage's to classify (`engine.py:304-336`), and the constitution's one envelope (`context/standards/constitution.md`, Article 2.1) carries it; a rights refusal of decision 3 is the call's precondition, as for the siblings, and stays a raise.
7. **`MANAGEMENT_METHODS` gains `"install_extensions"`, and its docstring reads "The router's public coroutines that manage the mount tree or a mount's storage rather than route an op."** The drift test of `tests/test_ops.py` and the twin test of `tests/test_sync.py` then cover the name with no edit of theirs. `AsyncSession` and `Session` gain nothing: they carry no management method (EXECUTED, grep of `src/vfs/session.py`), and a session is a caller's verbs, not a mount's administration.
8. **The name is `install_extensions`.** It is the storage's name (`backend.py:1128`) and the roadmap's (`roadmap.md:525`), so one concept has one name on both layers, as `documentation/maintainers/how-we-name.md` requires. That page's verb table (`:26-34`) has no `install`, and `add` there means joining a collection the file system keeps, which an extension is not; the table gains a row, `install`, "Software the storage's database needs is put in place there", `install_extensions()`.
9. **The sync twin forwards through the management hop: `return self._await("install_extensions", self._fs.install_extensions, path, authority=authority)`.** A closed facade and a call from the loop thread raise `RuntimeError`, as for every management method (`sync.py:709-715`), and the router's `Result` and `ValueError` and `MountError` reach the caller unchanged, as the module docstring promises (`sync.py:16-17`).
10. **The router method's body is the five steps of decisions 2 to 6 and no more, and `src/vfs/base.py`'s entry in `MODULE_LINE_BASELINE` is set in the same change to the module's new exact count.** Raising the entry with the code that grows the module is the practice on `dev`: `86fbb9ed`, `885b6a29`, `569d2eea` and `f36595fe` each did it (EXECUTED, `git log -p tests/lint/allowlist.py`). No other module crosses the ceiling.
11. **The router method's docstring says:** what the call runs and for which mount; that `path` is a mount point and what raises `ValueError`; the rights rule and that a refusal raises `MountError` before the storage is asked; that a storage without the install succeeds with nothing done; that the storage's outcome is returned with its source; that first touch never installs, so this is the explicit install. It cites no spec.
12. **The landing notes end with the line `**Changelog:** Added: install_extensions(path) on AsyncVirtualFileSystem and VirtualFileSystem, and the SupportsInstallExtensions storage protocol.`** Reason: the release steps copy that line into the draft notes under *Added* (`context/standards/release.md:100-112`), and decision D2's freeze rule lists every added name.

## Cost

The router adds no statement. Per call it reads the mount table once, asks the storage that holds the mount point one `holds` question for a named caller and none for the system actor, as `update_mount` does, and calls the storage's install once. The storage's own cost is unchanged: on Postgres one `CREATE EXTENSION IF NOT EXISTS` and one probe, on SQLite one probe and no install statement. The multiplier is none of the reference deployment's: the call is a developer's act at deployment, not per verb call, per write, per index visit, per batch or per corpus. The router takes no lock (decision 4), so no caller waits behind the call at the router. Nothing grows with the corpus or the mount count; the mount lookup is a dictionary read.

## Choices to confirm

1. **Does `path` name a mount point exactly, or any path, resolved to the mount that holds it as `locate` does?** Taken: a mount point exactly (decision 2), as `update_mount` takes. Widening later is additive, because a path that raises today would start to succeed; narrowing after callers pass inner paths would break them.
2. **Does a caller's rights refusal raise `MountError`, or return in the `Result` beside the storage's refusals?** Taken: raise, as `add_mount`, `remove_mount` and `update_mount` do, reusing `_require_mount_rights` and its test family (decision 3). The other side gives one channel for every refusal, as Article 2.1 of the constitution asks of operations; moving to it is one method and its tests, before the freeze.
3. **Which rights gate the install: `read_write` at the mount point, or the system actor alone?** Taken: `read_write` at the mount point, the sibling methods' rule, under which a new storage's open posture lets a plain script call it. The system actor alone is the narrower gate and cheaper to loosen later, at the price of every plain call naming `Authority.system()`; it differs from every other mount method, so it is not taken without a ruling.

## One line

`install_extensions(path)` joins the router's management methods and the sync facade, runs the install of the mount at `path` for a caller who holds `read_write` there, returns the storage's outcome stamped with its mount, and succeeds with nothing done where the storage has no install.
