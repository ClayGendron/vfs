# A verified token becomes an authority at the edge and nowhere else

A draft, written on 2026-11-25 and checked against `dev` at `27f3d24d`. It is not reviewed, and nothing of this unit is built. It serves [roadmap story I1](../../context/standards/roadmap.md), gate b, criteria 1–4 and 6. It is converted from the inbound and refusal rules of [spec 149](../../context/specifications/archive/149-serve-auth-token-to-authority/spec.md). It rests on the [door-token spec](../2026-11-25-a-bare-authority-constructor-is-closed-by-a-door-token/spec.md), the [149-2 reassessment](../2026-11-25-the-backlog-converted/reassessment/mcp-guests-and-identity.md), and the [verification of D13 and D35](../2026-11-25-the-backlog-converted/decisions/c-identity-and-the-trust-edge.md).

## The outcome wanted

A host checks a bearer token addressed to its resource and gets one verified subject. A call made for that subject uses its existing grants. A delegated call records the current actor separately. An overwrite records how the subject was proved. A token with the wrong proof yields the same `vfs.unauthenticated` refusal as one intended for another resource. A correctly signed token naming a reserved principal yields `vfs.invalid`. Neither refusal reaches storage.

## The problem

Today a serving transport has no checked conversion from a token into the caller a verb accepts. The actor's name cannot stand in for the subject on a delegated call. A stale group claim can name rights removed since issuance. Discovering a signing key by making a network request for every call would add about 150,000 issuer calls a day at the reference deployment (`AGENTS.md:82`). The conversion must therefore distinguish proof from claim shape, and keep key lookup and group resolution out of the request's identity calculation.

## Decisions

1. Decided 2026-11-25: expose `authority_from_token(claims: Mapping[str, object]) -> Authority | ResultError` in `vfs.authority` and re-export it from `vfs`. It is synchronous and accepts the already verified JSON object from a trusted verifier. It does no decoding, verification, I/O or lookup. A mapping in trusted in-process code is an assertion by that code. A front may pass only the verifier's successful result, never request arguments or an unverified decode. The function adds its own name to `_DOORS` and uses one literal `provenance="edge"` and one `door=_DOOR` in the same constructor call. This is roadmap I1 criterion 1 and the sanctioned construction in 149-1 decisions 4 and 11.

2. Decided 2026-11-25: preserve the signed subject string exactly, use one issuer per principal space, and admit one subject only. No issuer prefix, case-fold, trimming or client-id substitution is applied. All verifiers serving the same grants and owners must trust the same issuer for those bare names. A switch to an unrelated issuer requires a separate principal space or an explicit identity migration. A lawful, previously unseen subject needs no registry entry. Its grants and the mount's posture determine access like those of any other named caller. The owner, actor and source identity columns on dev store the bare value (`src/vfs/models/rows.py:417`, `:496-498`). A principal id must be a nonblank Unicode string of at most `MAX_PRINCIPAL_ID_LENGTH` characters, with neither a NUL nor an unpaired surrogate, so that it can be stored on Postgres as well as SQLite. Both subject and actor refuse `SYSTEM_NAME`, `ANONYMOUS_NAME`, `EVERYONE_NAME` and any `GROUP_NAME_PREFIX`, including the prefix alone. Test length before scanning the string. Move the one length declaration from `src/vfs/models/rows.py:142` to `vfs.authority`, keeping its old import available from `rows.py` and using that declaration for the affected identity columns. The in-process principal constructors keep their existing acceptance rules.

3. Decided 2026-11-25: `sub` is the sole subject and `source_identity` is exactly that subject's `sub`. With no `act`, the same principal object is the actor. With `act`, require a JSON object with its own lawful `sub`. If that object declares `iss`, it must equal the verified top-level issuer. Only this outer actor is used. Earlier actors nested inside it describe history and are never consulted. The actor contributes zero subjects and confers none of its own grants. The authority takes `Narrowing.NONE`. This follows [RFC 8693 §4.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1) and I1 criterion 4.

4. Decided 2026-11-25: the literal issuer-controlled `kind` on a principal object accepts only `user` or `service`, defaulting to `user` only when absent. The same rule applies to `act.kind`. An issuer used with this profile must control that claim. No lookup infers kind from a client registration. The top-level OAuth `scope` string becomes the subject principal's `scopes` (`src/vfs/authority.py:87-89`). Absence gives an empty frozenset. A present string follows the case-sensitive, space-delimited grammar of [RFC 6749 §3.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3), with duplicates coalesced. A distinct principal constructed from `act` has empty scopes, including when it repeats the subject id. Nested scope, sponsor, display `name`, `groups`, member lists, caller-supplied provenance and all other unconsumed fields are ignored at both levels. In particular a signed `name` maps to no field even if display names land first. This is D13 for groups and leaves grants to their existing judge.

5. Decided 2026-11-25: separate a failed proof from an unusable verified identity. Every verifier refusal is the same `classified(ErrorKind.unauthenticated)`. A non-object or any defective field read by the door yields `classified(ErrorKind.invalid, detail="invalid token identity")`. Neither error carries a path, source, exception text, claim value, data or credential. `classified` requires detail for `invalid` (`src/vfs/results/envelope.py:235-249`, `:266-284`). Do not catch construction bugs such as a missing door token. No absent-bearer case calls the verifier or this door. That case belongs to I2.

The twelve I1 cases below start with a valid resource-bound signature and lawful `iss`, `exp`, `aud` and `sub="member-7"` unless a row changes one. Every success has exactly one subject, `source_identity="member-7"` and `provenance="edge"`.

| Case | Change to the input | Observable result |
|---|---|---|
| 1 | None | User subject is its own actor, empty scopes |
| 2 | `kind="service", scope="read run read"` | Service subject is its own actor with scopes `{"read","run"}` |
| 3 | `act={"sub":"worker","kind":"service","act":{"sub":"prior"}}` | Actor is `worker`, whose scopes are empty. Only `member-7` supplies rights |
| 4 | `groups=["group:private"], name="Display", provenance="system"` | Entire authority equals case 1, with no display name copied |
| 5 | `sub="system"` | `vfs.invalid` |
| 6 | `sub="anon"` | `vfs.invalid` |
| 7 | `sub="*"` | `vfs.invalid` |
| 8 | `sub="group:private"` | `vfs.invalid` |
| 9 | `act={"sub":"system"}` | `vfs.invalid` |
| 10 | Signature fails | `vfs.unauthenticated` before the door |
| 11 | Expiry has passed | Same refusal as case 10 |
| 12 | Audience absent | Same refusal as case 10 |

6. Decided 2026-11-25: put `TokenVerifier` and its one shipped implementation `PyJWTVerifier` in `vfs.mcp.auth`, public from `vfs.mcp` only. The structural protocol's single method is `async verify_token(token: str) -> Mapping[str, object] | ResultError`. Success yields verified claims alone. Failure is decision 5's error. The async seam admits a host implementation without making the factory asynchronous. The SDK's `AccessToken | None` convention in the D35 verification describes the transport seam and cannot carry a classified refusal. The serving adapter owns the conversion to that SDK convention and must preserve the distinction between an absent credential and a rejected one. The protocol and implementation are both optional imports. Add `pyjwt[crypto]>=2.10.1,<3` directly to the `mcp` extra and refresh `uv.lock` at build time. Whoever adds the MCP SDK to that extra uses the same dependency closure (`context/specifications/archive/170-tools-and-mcp-servers-as-views/spec.md:153`). Add no `serve` extra. This adopts the verified D35 in place of the wording still at `context/standards/roadmap.md:417` and `:1246`.

7. Decided 2026-11-25: construct `PyJWTVerifier(*, issuer: str, audience: str, public_key: bytes)` with one nonblank expected issuer, one nonblank resource audience, and one trusted RSA public verification key of at least 2048 bits in PEM format. The issuer must reserve the resource audience for access tokens accepted here, distinct from client audiences used for login. Parse the key once at construction, reject an invalid configuration with `ValueError`, and use only RS256 for this shipped profile. One configured key avoids key-discovery I/O. Rotation replaces the configured verifier. A host with a rotating key set can implement the same protocol. Request headers can select neither a key, URL nor algorithm. Pass the fixed algorithm, parsed key, issuer and audience to [PyJWT's verification API](https://pyjwt.readthedocs.io/en/stable/api.html). Require `iss`, `exp`, and `aud`, enable signature, issuer, expiry and audience validation, and use zero leeway. Accept an exact resource string or an array of strings containing it. Enforce the issuer's exact string, finite numeric dates excluding booleans, and applicable `nbf` and `iat` validation when present. Leave `sub` type and presence to the door so both calls classify a signed malformed subject identically. All malformed token data, including ill-typed dates, a malformed header or deeply nested JSON the decoder refuses, returns the one proof failure. Neither success nor failure logs the token or copies it to the authority.

8. Decided 2026-11-25: declare `MAX_TOKEN_BYTES = 16 * 1024` for admission in `vfs.authority`. The verifier rejects empty, non-ASCII or over-budget compact tokens before parsing. Check length before scanning or encoding, since every admitted compact token is ASCII. The door uses the same bound on the character length of `scope` before scanning or splitting it, and admits only the ASCII scope grammar. There is no traversal of unconsumed claims. This bounds a single proof without making token size a database or per-principal allocation.

9. Decided 2026-11-25: place the shared error definition below identity to preserve the import ladder. Today `vfs.results.envelope` imports models at line 42, models import `vfs.authority` at `src/vfs/models/version.py:42`, and even a type-only upward import fails `tests/lint/test_code_shape.py:184-206`. Move the kind vocabulary and its contract table together with `ResultError`, `classified` and their private dependencies into `src/vfs/result_errors.py`. These depend only on paths, Pydantic and the standard library. Keep all existing names importable from `vfs.results.kinds`, `vfs.results.envelope`, `vfs.results` and `vfs` at the paths that expose them today, as the very same objects. The new order in `LAYERS` is paths, result errors, authority, models, results. The optional `vfs.mcp` package sits above the public faces it consumes and below the root export. This keeps one error type and one phrase table without a local import or a lint exception.

10. Decided 2026-11-25: keep the credential out of the result envelope. I1 criterion 6 is observed in two places for the same write. Its `Result` survives `Result.from_payload(result.to_payload())` with the same evidence, and its persisted version still says `edge` before and after that round trip. The existing payload serializes the result's fields, including extra data, at `src/vfs/results/envelope.py:747-773`. Neither a token nor an authority nor a claims mapping is attached as extra data. Restoring a result can never mint an authority. The existing storage attribution suffices to prove the recorded `edge` without introducing a credential-bearing wire shape.

## Cost

At the reference deployment, serving every verb with one token costs at most 150,000 signature checks a day and about 20 a second at peak. A 10,000-entry batch presented as one call pays for one check. Verification parses at most `MAX_TOKEN_BYTES` bytes, does at most one signature check with the configured key and makes zero outbound requests. The door examines at most two principal ids, bounded by `MAX_PRINCIPAL_ID_LENGTH` each, and one bounded scope string. Its scope set has at most `(MAX_TOKEN_BYTES + 1) // 2` elements because every distinct nonempty spelling after the first needs a separator. Its subject set is always one, within `MAX_SUBJECTS`. The configured key is held once per verifier. No token, membership or identity cache grows per caller. There are zero added SQL statements, binds, rows or locks on SQLite, Postgres and the generic dialect. An overwrite fills the existing attribution columns in its ordinary commit. A read waits on no writer for authentication.

## Choices to confirm

1. **Bare id or issuer-qualified id.** Take one issuer per shared principal space with unchanged ids. It preserves existing grants and version attribution. Supporting several issuers requires an explicit mapping and collision policy before exposing them in that same space.
2. **Kind, display and sponsorship.** Take the protected literal `kind` claim and omit registration lookup, display-name import and sponsor storage. A future explicit claim adapter can add these without changing existing ids. A service token requires an issuer that controls the kind claim.
3. **Scope on delegated calls.** Take top-level scope on the subject alone. The alternative gives it to the outer actor too. Empty actor scopes are the narrower interpretation and can be extended once a consumer establishes the necessary proof.
4. **Verifier interface.** Take a verified mapping or classified refusal at the VFS seam. Using the SDK's access-token wrapper here would couple authentication to the transport and require translating its absence result. The transport can wrap the smaller interface later.
5. **Key source and algorithm profile.** Take one configured RSA public key and RS256. A trusted key set or a second algorithm can be added without broadening existing configurations. Automatic key discovery has no configuration or refresh budget on dev.
6. **Token budget.** Take a named 16 KiB initial bound. The checkout declares no bearer limit. Raising it later admits additional callers without invalidating an existing proof. The bound precedes decoding regardless of the transport's own header limit.

## One line

One verified bearer yields one edge-proven subject and its current actor, with uniform proof failures, membership resolved by VFS and only attribution surviving the call.
