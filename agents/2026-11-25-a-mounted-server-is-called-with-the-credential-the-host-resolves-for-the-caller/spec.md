# A mounted server is called with the credential the host resolves for the caller

A draft, written on 2026-11-25. It is not reviewed, and nothing is built. Checked against `dev` at `27f3d24d`, it serves [story I4](../../context/standards/roadmap.md), gate f, and is the new spec that story calls for. Its source is [spec 170 §3.1](../../context/specifications/archive/170-tools-and-mcp-servers-as-views/spec.md), which it replaces for a server registered with a resolver. It rests on [the MCP client view](../2026-11-25-a-connected-mcp-server-is-a-directory-of-tools-resources-and-prompts/spec.md), [the trust edge](../2026-11-25-a-verified-token-becomes-an-authority-at-the-edge-and-nowhere-else/spec.md), [the verification of D16](../2026-11-25-the-backlog-converted/decisions/d-mcp-serving-and-credentials.md) and [the kernel's records](../2026-11-22-the-kernel-keeps-records-of-its-own/spec.md).

## The outcome wanted

A host registers a server once and gives it a resolver. Ann and Bob then list the server and run its tools. The server sees Ann's credential on Ann's requests and Bob's on Bob's. Each sees the catalogue the server gives that credential, and neither is ever served the other's.

The credential is the host's. It goes from the resolver into one request header and nowhere else. No result, error, row, stored record, log record, shell variable or child process ever holds it. That is seen by tests that plant a unique secret and search every output for it.

A caller the host has no credential for gets `vfs.unauthenticated` at the tool's path, and no byte is sent to the server. A call for a set of subjects is `vfs.invalid`. Both are seen on a transport spy that counts bytes.

The key idea, said once more: the host holds every credential, VFS asks for one at the moment it sends a request, and VFS keeps it only in memory, on the one connection of the one caller it belongs to.

## Terms

- **Credential.** A secret the host holds that a server accepts as proof of who is calling. Here it is a bearer token.
- **Resolver.** The host's object that answers, for a server and an authority, with that caller's credential.
- **Per-user server.** A server registered with a resolver. A **static server** is one registered with one credential or none, as 170-4 specifies.
- **Caller.** For a per-user server: an authority's actor and its one subject, taken together.
- **Carrier.** The one object on a connection that writes the credential into a request's `Authorization` header.
- **Origin.** The triple of a URL's scheme, its host and its port, with the scheme's default port filled in.
- **Canary.** A unique secret string that a test plants and then searches for in everything VFS produced.

## The problem

Spec 170 gave a server one credential. Every caller who may run its tools then acts as the host, so a result can carry data the caller's own account at that server would never show. Story I4 asks for the opposite: each caller acts as itself.

That puts a second kind of secret inside VFS. The first kind, a database password, sits in one URL, which `url_of_engine` keeps out of its own error (`src/vfs/storage/backends/database/drivers.py:78-94`). This kind is per caller, arrives on every tool call, and passes next to code whose habit is to copy text outward. The probes above show two such habits on `dev`: an exception's words become an error's message, and an error's `data` and extras cross the wire unexamined. A resolver is host code that can raise, and a transport error names its request, so both habits lead straight to a leak.

It also multiplies state. At the reference deployment 1,000 people and their agents call a server. One connection each, kept for ever, is 1,000 sockets and 1,000 catalogues for one server. A read must not wait on another caller's connection being opened, and no caller may ever be served another's catalogue or body.

## Decisions

1. **The credential comes from the host, and VFS keeps none.** D16's lean (a) is taken, as its verification amends it; choice 1. A per-user server takes its credential from a resolver the host supplies. VFS has no credential store, does no token exchange, never forwards a token it was sent, and refuses a call for a set of subjects. Reason: `Authority` has no field that could hold a credential (`src/vfs/authority.py:127-131`), so identity and proof stay apart; and the host already supplies the identity seam inbound (149-2 decision 6). OAuth on demand is story T7, at 0.2 (`context/standards/roadmap.md:850`).

2. **Two public names, in a core module that needs no extra.** `src/vfs/credentials.py` holds `Credential` and `CredentialResolver`, and both are exported from `vfs`. The module imports `vfs.authority` and `vfs.results` and nothing else, and joins `LAYERS` on the rung of `vfs.pattern_matching`, above `vfs.results` and below `vfs.base`. Reason: `add_mcp` is a method of the router, a type that a public signature names is public (`documentation/maintainers/how-we-name.md`, "Public and private"), and `vfs.base` may not import the optional `vfs.mcp` package, which 149-2 decision 9 places above the public faces. The resolver is a structural protocol with one method, as 149-2's `TokenVerifier` is:

   ```python
   @runtime_checkable
   class CredentialResolver(Protocol):
       async def resolve(self, server: str, authority: Authority) -> Credential | ResultError | None: ...
   ```

   `server` is the name given to `add_mcp`, never a URL. The method is `async` only, as policies and tools are (`agents/2026-11-22-the-specs-for-jobs-and-sessions/overview.md:50`). It may be called by many calls at once.

3. **A `Credential` shows nothing of itself.** It is made only by `Credential.bearer(token)`; the bare constructor raises `TypeError`. The token is what 170-4 decision 2 says a static bearer is: a nonempty `str` of ASCII with no whitespace and no control character, of at most 149-2's `MAX_TOKEN_BYTES` characters. Any other value raises `ValueError` whose text never repeats the input. The rule keeps a carriage return or a line feed out of the header. There is no lower bound on length: a host's short secret is accepted, and decision 13 says what that costs it.
   - `repr`, `str` and every format of it give `Credential(bearer=<hidden>)`.
   - It has slots and no `__dict__`, and it is frozen. It refuses `pickle`. `copy` and `deepcopy` return the same object. Equality is identity.
   - It has three readers and no other. `write_header(headers)` sets `Authorization` on a mapping it is handed. `found_in(data)` says whether a `str` or `bytes` value holds the secret. `same_as(other)` says, in constant time, whether two credentials hold one secret. None returns the secret, so once `bearer` has returned, no frame of VFS holds the secret under a name.
   - Put by mistake in an error's `data`, it stops `to_payload` with a serialization error that does not name the secret.

   Precedent: `RecordPlace` hides its URL from its `repr` (kernel records, decision 3). A prototype of the hiding was run against the real envelope: nine renderings, `pickle`, `vars`, `copy` and `to_payload` behaved as written above.

4. **`credentials=` takes four shapes, and a per-user server is registered without connecting.** The signature is `add_mcp(name, server, *, list_floor_ms=None, credentials=None, caller_connections=None)`; decision 9 has the last argument. `None` and a static credential are 170-4's, and a static server still takes any authority, a set included. A `str` is wrapped by `Credential.bearer` as `add_mcp`'s first act and the argument's name is bound to the wrapped value, so no plain string is kept and no later frame holds one. A `Credential` is a static credential. An object with a `resolve` method makes a per-user server. Anything else raises `TypeError`. A credential of either kind with stdio parameters raises `ValueError` before any process is started, and so does one for a plain-http endpoint that is not loopback, or a URL with userinfo; that is 170-4 decision 2, extended to a resolver. `add_mcp` for a per-user server validates, reserves the name, publishes the server's three directories and returns. It opens no connection, because no caller exists yet. This departs from 170-4 decision 2, which connects at registration; a per-user server that cannot be reached is found by the first caller's operation, as `vfs.unavailable.backend`. The synchronous face takes the same four shapes, and a resolver is awaited on the router's own loop.

5. **The caller of a per-user server is one actor and one subject.** The connection key is the pair `(actor.sub, subject.sub)`, read from the authority that `caller_for` returns. A principal's kind and scopes, the provenance, the narrowing and the source identity are not in it. Reason and precedent: this is what the stored session's owner key holds (its decision 6), so a token renewed with other scopes keeps its connection, and an agent acting for Ann never shares one with Ann acting for herself. Nothing is keyed by the credential: two callers whose credentials are the same bytes still have two connections. An authority that is not one such pair is refused before the resolver is asked and before any byte is sent:

   | Authority | Result at the path | Exit | Detail, fixed |
   |---|---|---|---|
   | More than one subject | `vfs.invalid` | 2 | "a server that acts as its caller takes one subject; this authority names several" |
   | The system actor | `vfs.invalid` | 2 | "a server that acts as its caller needs a named caller; the system actor names none" |
   | The anonymous caller | `vfs.unauthenticated` | 126 | "this server acts as a named caller" |

   A set is refused because one member's credential reaches what that member holds, and a set may hold only the least of its members (`tests/support/oracles/grants.py:14`). The system actor is `vfs.invalid` because that is what `dev` and the job contract already answer where the system actor cannot act: a line (`src/vfs/shell/host.py:216-218`) and job decision 30. `unauthenticated` already reads as "Permission denied" in a line (`src/vfs/shell/programs.py:131`, `src/vfs/shell/host.py:99`).

6. **Every local refusal comes before the resolver.** A call to a per-user server passes these gates in this order. The first four ask the resolver nothing and send nothing.

   | Gate | Refusal |
   |---|---|
   | Rights at the literal path, as 170-3 and 170-4 decision 5 rule | `vfs.not_found` 127 below `list`, `vfs.permission_denied` 126 below `read` |
   | The caller's shape, decision 5 | the table above |
   | Room, checked and not yet taken: the connection's `MCP_IN_FLIGHT` budget, or for a caller with no connection a place in the server's pool, decision 9 | `vfs.busy` 1 |
   | With a live snapshot: the tool's presence and the binding of its arguments | `vfs.not_found` 127, `vfs.invalid` 2 |
   | The resolver, once, decision 7 | decision 8 |
   | The open, when the caller has no live connection, then the fourth gate for a caller who had no snapshot | `vfs.unavailable.backend` 1, `vfs.unauthenticated` 126 |
   | Rights and installation once more, as 170-4 decision 5 requires after any wait; the resolver and the open were waits | as the first gate, with no `tools/call` sent |
   | The send | 170-4 decision 9 |

   Reason: a caller who may not see a tool must learn nothing, the host's resolver included, and a refusal that VFS can give alone should cost the host nothing. A policy judges the step before the first gate and sees a path and arguments, never a credential.

7. **The resolver is asked when a request is about to be sent, and never by a list refresh.** It is asked exactly once by each `tools/call` request and by each read of a resource's body, whether the body is then fetched or served from the connection's cache, after the local gates and before the first byte. It is asked once more only by an operation that must open a caller's connection and is neither of those: a catalogue read addressed at or beneath one per-user server's own directory, by a caller with no live connection there. When one call both opens and calls, one answer serves both. A refresh of a list on a live connection, a listing rooted above the server (decision 12) and a close ask nothing. A cached body is the caller's own data at the server, so the host is asked before it is shown again and can withdraw it at once. The resolver is handed the server's name and the authority, and nothing else: no request, no header, no token. It is awaited under the call's own wall, the tighter of the line's deadline and `WALL_TIME_BUDGET`, and outside every lock. A continuation of a waiting job (170-4 decision 10) is a `tools/call` request: it asks once, for the authority the job records as its owner, and the saved part of the job holds no credential and no answer. Reason: asking at each call lets the host hand out a short-lived token with no failed call at its expiry. Departure: I4's first criterion says "never during `tools/list`"; this reads it as "a list is never a reason to ask", because story T4's third criterion has `ls` issue one `tools/list` "per server and principal" (`context/standards/roadmap.md:821`), which no caller can send before a credential exists. Choice 2.

8. **An answer is a credential, or the call ends with a fixed fact.**

   | The resolver | Result at the path | Exit | Detail, fixed |
   |---|---|---|---|
   | returns a `Credential` | the call goes on | | |
   | returns `None` or a `ResultError` | `vfs.unauthenticated` | 126 | "the host holds no credential for this caller on this server" |
   | raises, returns anything else, a bare `str` included, or returns the token the request arrived with (decision 16) | `vfs.unavailable` | 1 | "the host's credential resolver failed" |
   | is still running when the wall passes | `vfs.timeout` | 124 | none |

   In every row but the first, zero bytes are sent and no connection is opened. `None` or a returned error is the host withdrawing the caller: that caller's live connection, if it has one, is closed locally with no closing `DELETE`, and its carrier, snapshot and body cache are dropped, so no later refresh sends a credential the host has taken back. The other rows close nothing. A returned `ResultError` is not passed on: its message and data are the host's words, and they stop here. A raised exception is not read: not its text, not its arguments, not its cause. One `WARNING` names the server and the exception's class. A cancellation is passed through. A bare string is refused because a string that is not a secret, an error text say, would otherwise be sent as one. Precedent: raw errors are mapped before they cross the public boundary (`context/standards/constitution.md:84`).

9. **One connection per server and caller, in a pool whose size the host declares for each server.** Each is a supervisor of 170-4 decision 3, with its own snapshot, its own list floor, its own body cache and a response cache store of its own in the SDK's client. `add_mcp(..., caller_connections=None)` sets the most per-caller connections that one server holds. `None` takes `MCP_CALLER_CONNECTIONS: Final = 1024`, declared in `src/vfs/mcp/pool.py`. A value that is not a positive `int`, a `bool` included, or one given without a resolver, raises `ValueError` in `add_mcp` before the name is reserved. Static servers are outside every pool, under `MCP_SERVER_LIMIT`.
   - An open that finds its server's pool full closes that server's idle connection used least recently, where idle means no request pending or running. The place is free only when that close has finished, so a server never holds more than its size, closing ones counted. Room is made at the open and never earlier: a prototype that made room before it asked the resolver let a caller with no credential close another caller's connection.
   - With every connection of the server busy, the operation is `vfs.busy`, exit 1, before the resolver, as 170-4 refuses excess work.
   - Concurrent first operations of one caller share one open. Each call still asks the resolver for itself. No queue is added: a call that waits on the resolver is that call's own task, under its own wall.
   - A snapshot is charged to `TOOL_CATALOGUE_BYTES`. One that does not fit closes idle per-caller connections, least recently used first across the router, and then refuses `vfs.busy`.
   - A caller whose open failed keeps an entry holding only its next eligible instant, by 170-4's backoff. It counts toward the size and is closed like any idle one.
   - `remove_mcp` and `close` close every connection of the server, as 170-4 closes one, and drop each carrier.

   Reason: the verification of D16 costs an unbounded pool at 1,000 connections a server. Precedent for a count beside a byte budget, both arguments with declared defaults: `RightsCache(entries=RIGHTS_CACHE, budget=RIGHTS_CACHE_BYTES)` (`src/vfs/storage/backends/database/rights.py:141-144`, `:261-272`). Precedent for a host-set budget on a public face: `hop_budget` and `close_timeout` on the router (`src/vfs/base.py:296-297`), a line's `limits` (`src/vfs/shell/host.py:192`), and `list_floor_ms` on this same method. The default is the rights cache's count, and it is one place for each of the reference deployment's 1,000 callers on a server; Cost shows what a smaller size or one pool for the router would cost. The size is a declared default that the host overrides for each server, and reaching it never refuses a caller, it costs that caller an open; so it is neither a hardcoded size nor a cap on callers.

10. **The credential travels in one header, to the exact origin that was registered.** Each connection's HTTP client is built with one carrier, an `httpx2.Auth`; a static server's one connection is carried the same way. The carrier holds the credential last resolved for its caller, in memory, for the life of the connection. A list refresh and the session's closing `DELETE` send that one.
    - **The predicate.** `add_mcp` computes the endpoint's origin once: the scheme, the host as the HTTP library parses it, lower-cased and otherwise unchanged, and the port, with 80 or 443 filled in for a default. The carrier sends a request only when the request's own origin equals that triple and its URL carries no userinfo. No name is resolved, no trailing dot is removed, and no two spellings of loopback are treated as one.
    - **No upgrade.** There is no https form of a plain-http endpoint that also qualifies. Reason: the SDK's own upgrade goes from port 80 to port 443, which is another listener; a plain-http endpoint is loopback only (170-4 decision 2), where nothing needs upgrading; and "the same host" is never "the same service". This is narrower than the SDK's redirect rule on purpose.
    - **Redirects.** A redirect that stays on the exact origin is followed by the SDK, as it follows a trailing-slash 307, and carries the header. Any other request the client is asked to send is stopped inside the carrier, before a byte: the other target receives nothing at all, with or without the header. The operation is `vfs.unavailable.backend` at its path, exit 1, not retried, with the fixed detail "the server redirected the request off its registered origin", and the connection is closed as a broken generation of 170-4 decision 3. A `tools/call` so answered is not sent again.
    - **What qualifies, case by case.** For `https://maps.example/mcp`: `https://MAPS.example/mcp` and `https://maps.example:443/mcp` are the same origin; `https://maps.example:8443/mcp`, `https://maps.example./mcp` and `http://maps.example/mcp` are not. For `http://127.0.0.1:8000/mcp`: `https://127.0.0.1:8000/mcp`, `https://127.0.0.1/mcp`, `http://localhost:8000/mcp` and `http://[::1]:8000/mcp` are not. A prototype ran all of these and three redirects on `httpx` 0.28.1.
    - **Nowhere else.** The credential is never put in a URL, a JSON-RPC field, `_meta`, an argument, a word of a line, a variable, standard input or a process environment. A client for a plain-http loopback endpoint is built with `trust_env=False`, so a proxy named by the environment never receives the header; an https endpoint keeps the environment's proxy, since the header then travels inside the tunnel. Loopback means the host `localhost`, an address in `127.0.0.0/8`, or `::1`.
    - The credential's memory is released when the carrier is dropped; Python gives no way to wipe a string, and the docs say so.

11. **A request the server refuses with 401 closes that caller's connection, and nothing is sent twice.** The carrier sees each response's status in its own flow, so this needs no reading of the SDK's errors. The operation is `vfs.unauthenticated` at its path, exit 126, with the fixed detail "the server refused this caller's credential". A `tools/call` is never sent again, as 170-4 decision 8 rules. A call or a resource read carried a credential asked for at that moment, so its 401 is final. A catalogue read addressed to the server whose refresh drew the 401 opens the connection once more in the same operation, which asks the resolver once, because a list is safe to send again; a second 401 ends it. A listing from above never reopens. A 401 at an open counts as a failed attempt for 170-4's backoff, and before the next eligible instant the caller's operations answer the same fact with no resolver call and no byte. A 403 is the server's own refusal and stays in 170-4's table.

12. **Each caller reads its own catalogue, and only a read addressed to a server opens it.** `ls /.vfs/mcp` and the three directory names under a server are served from the registration, to any caller the posture lets list them, with no connection. Every entry beneath them is read from the caller's own snapshot. A read addressed at or beneath one per-user server's directory, by a caller with no live connection there, opens that caller's connection first (decision 7). A listing rooted above the server, `tree /.vfs` or a `grep -r` from `/.vfs/mcp` say, never opens one and never asks the resolver. It shows a caller with a live connection that caller's snapshot. For a caller with none it shows the three directories and one record at the server's path, `vfs.budget_exhausted.truncated` with severity `warning` and the fixed detail "a listing from above does not open a server that acts as its caller; list the server's own directory". Reason: one broad read must not call the host and open a connection for every server registered, and a result that is cut says so and says how to refine. A tool another caller's listing holds and this caller's does not is `vfs.not_found`, 127, with zero bytes sent, the same as a name no caller has. A per-user server adds no path to the open inventory of 170-3 decision 3, because the anonymous caller is refused whatever the posture.

13. **A reply that holds a credential its connection was sending is withheld.** Before 170-4's adapter makes a row, the captured reply is searched with `found_in`. This covers a `tools/call` reply, a `resources/read` reply, a list page, a JSON-RPC error, and the state and form text of an input request before a job saves them.
    - **Which credentials.** The search is for every credential the connection wrote on a request or a stream that was open at any moment between this request's admission and the capture of its reply. That set holds the call's own answer, the one the carrier held when the request was admitted, and each that replaced it meanwhile. It is not the call's own answer alone, and not the carrier's current one alone. Reason: the SDK's writer task builds the request after the call has resolved, so a later call of the same caller can replace the carrier's credential first, and a reply that arrives on a standing stream answers a request that carried an earlier one. The prototype showed it: with only the call's own answer searched, an echo of the credential the request really carried passed.
    - **The bound.** The carrier keeps these as distinct secrets, compared with `same_as`, and forgets one when no open request or stream carried it and no request admitted before it ended is still unanswered. It keeps at most `MCP_LIVE_CREDENTIALS: Final = 64`, declared in `src/vfs/mcp/pool.py`. A call whose answer would be the sixty-fifth is `vfs.busy`, exit 1, before its send. A host that returns one token until it expires holds one or two.
    - **What is searched.** Every string of the reply, keys as well as values, after JSON decoding; every decoded block of bytes; and the text blocks of a reply joined in order, so a credential cut across two blocks is found.
    - **On a hit** the whole reply is dropped. The call is `vfs.unavailable.backend`, exit 1, not retryable, with the fixed detail "the server's reply held the caller's credential and was withheld", and one `WARNING` names the server. A list page with a hit is a failed refresh and publishes nothing. Static servers are searched the same way.

    Reason: once VFS's own code is clean, an echo from the server is the one way left for the credential to reach a row, a stored reply or a model. The search finds the exact text only; a server that returns the credential encoded is not caught, and the docs say so. A short credential that is also an ordinary word makes ordinary replies match, which fails closed and names its cause; that is the price of accepting any nonempty bearer, as 170-4 decision 2 does.

14. **No detail, datum or log record is made from material that could hold a credential.** On an MCP connection, and around the resolver, every error detail is one of a fixed set of phrases chosen by what happened; the tables of decisions 5, 8, 11 and 13 are that set, beside 170-4's. No exception's text, no header, no URL and no part of a request is copied into a `message`, a `data` key or an extra field. `data` carries nothing about a credential: not its scheme, its length, its expiry or a hash of it. This departs, for this path only, from the pattern at `src/vfs/base.py:2979`. An exception VFS raises here is raised with its cause and context suppressed, so no traceback of it carries the exception it replaced. The SDK logs a reply before VFS has searched it (`streamable_http.py:191`, `:212`, `:462`), so inside the task that owns a credentialed connection the records of the SDK's client loggers are dropped at every level by one filter VFS attaches to those loggers; records from any other use of the SDK in the process pass, and VFS writes its own fixed record for what happened. The module's logger is `vfs.mcp.pool`. It writes a server's name, a count and an exception's class name, at `WARNING` for decisions 8, 10, 13 and 16 and at `DEBUG` for an open, a close and an eviction. It never writes a caller's name, following `src/vfs/authority.py:230-232`.

So the serving edge of 171-2 wraps a request's verified bearer as a `Credential` and keeps it for the life of that request alone, handed on explicitly with the work the request starts; a task VFS starts for a connection does not inherit it. Before the carrier writes any credential for that work, a resolved one, a static one or the one kept for a refresh, it is compared with `same_as`. On a match nothing is sent. A resolver's answer is then a resolver fault (decision 8); a static server's operation is `vfs.unavailable` at its path, exit 1, with the fixed detail "this server's credential is the token the caller sent, and it is not forwarded". One `WARNING` names the server. The wrapped value enters no `Authority`, cache, job, record or result. A call made in process has no inbound token and nothing to compare. Reason: forwarding the client's token is what the MCP specification forbids (`context/standards/roadmap.md:446`), and it is the mistake a host is most likely to make; one comparison a send turns a line in the docs into a rule that a test can hold.

## Cost

No statement is added on SQLite, on Postgres or on the generic floor. No table, column, index or lock is added, and neither schema format changes. The rights checks of a call are 170-1's and 170-3's, in their chunks of `membership_budget`, unchanged. Everything this spec adds is in memory or on the network, so the least generous engine sets no budget here.

- **Per verb call**, about 150,000 a day. A tool call or a resource read adds one awaited call of the host's resolver, inside the call's own wall, and zero statements. A catalogue read on a live connection adds nothing but a refresh that is due. The search of decision 13 is one pass over a reply already bounded by `MCP_FRAME_BYTES` for each live credential, at most `MCP_LIVE_CREDENTIALS` and in the ordinary case one or two.
- **In flight.** At the peak of about 20 calls a second, with a call bounded by `WALL_TIME_BUDGET` of 10 seconds, at most 200 calls are in flight even if every call were a tool call on one server that ran to its wall. A pool of 1,024 holds them, so `vfs.busy` is not reached at the reference deployment.
- **Opens and churn.** An open is one negotiation and one list walk of four methods, five requests for a server whose lists are one page each and at most `1 + 4 × MCP_LIST_PAGE_BUDGET`. The least a pool can cost is one open a day for each pair of caller and server. Above its size a returning caller pays an open again, and that is not once a session. The figures below are a model that was run, not a measurement. From the reference deployment: 1,000 people, 3.5 sessions a day each, 4 prompts a session, 10 actions a prompt, and a peak hour at four times the mean, which holds half the day's sessions. Assumed, with no measurement behind them: 5 per-user servers, of which a session uses 3; a quarter of actions are operations on a per-user server, 35,700 a day; 3 minutes between prompts and 3 seconds between actions; one caller key a person. The model then has 4,753 pairs of caller and server in the day, and at the peak 1,644 pairs used within fifteen minutes across the router, 344 on the busiest server.

  | Pool | Places | Opens a day | Opens an operation | Extra requests an operation |
  |---|---|---|---|---|
  | one for the router | 64 | 23,027 | 0.65 | 3.2 |
  | one for the router | 256 | 15,775 | 0.44 | 2.2 |
  | one for each server | 256 | 8,813 | 0.25 | 1.2 |
  | one for each server | 512 | 6,780 | 0.19 | 0.95 |
  | one for each server | 1,024 | 4,753 | 0.13 | 0.67 |

  With ten minutes between prompts the three middle rows are 19,148, 10,656 and 6,848, and the last stays at one open a pair. So one pool of 256 for the whole router costs more than three times the opens of the least and two extra requests on every operation, and a pool for each server at the default reaches the least. More agents a person, or more callers a server, raise the pairs and move a host toward the upper rows until it raises `caller_connections`.
- **Sockets.** A server holds at most its size in connections, and a router the sum of its servers' sizes beside `MCP_SERVER_LIMIT` static ones. A host short of descriptors lowers `caller_connections` and pays the table's price.
- **Refreshes.** A refresh is started only by an operation and at most once a floor on each connection, so list walks never exceed catalogue reads.
- **Memory.** Every snapshot is charged to `TOOL_CATALOGUE_BYTES`, so the catalogues of all callers together are bounded by the one budget 170-4 already declares, and that budget closes idle connections before the count does when snapshots are large. A carrier holds at most `MCP_LIVE_CREDENTIALS` credentials of at most `MAX_TOKEN_BYTES` each.
- **Waiting.** A read never waits on a writer: no statement is involved. A caller's operation waits only on that caller's own open. The pool's bookkeeping is done between awaits and holds no lock another caller needs. The resolver and the open are awaited outside the topology lock, as 170-4 decision 3 requires.

A recursive listing from above opens no per-user server and asks the resolver nothing (decision 12), so a broad read costs what it returns.

## Left as it is

- A static server: one credential, one connection, one catalogue for every caller, eager at `add_mcp`. That is 170-4, and spec 170 §3.1 stands for it.
- A stdio server takes no credential of either kind.
- `Authority` gains no field. `ResultError` and `Result` stay open records; the guards are at the producers.
- The details built from exception text at the five sites named above belong to their own owners and are not changed.
- A line's environment and `cli`'s signature.
- The kernel store's tables and format, and the action log's row.
- Story X7's search of every log record across the whole suite. This spec's canaries are written so that search can take them.

- `caller_connections`: what it bounds, its default, the table of Cost in short, and that a caller past it is served by an open and never refused.
- The exact-origin rule, with the cases of decision 10, and that a server which redirects elsewhere fails the call.
- When the resolver is asked, that it may be asked by many calls at once, that it is the place to cache, and that what it raises is not shown or logged.
- The fixed refusals of decisions 5, 8, 10, 11, 13 and 16, and what a caller should do about each.
- The limits, plainly: the credential lives in the process's memory while its connection does, and Python cannot wipe it. The reply search finds exact text only, and a short credential that is an ordinary word will match ordinary replies. A URL is printed by the SDK's logger, so no secret belongs in one. A host that passes a plain `str` holds it in its own frame, where a tracer that captures locals can read it; `Credential.bearer` at the point the secret is read avoids that. A resolver must never return the token a caller sent to VFS, and one that does is refused.
- The README does not say "as the user" in the OAuth sense (`context/standards/roadmap.md:55`).

## Earlier decisions this reverses

- Spec 170 §3.1, for a per-user server: "every vfs caller who may call its tools acts through the one credential the host configured. `tools/list` is therefore one list per server, not per caller." A static server keeps it.
- 170-4 decision 2, for a per-user server: registration no longer connects. Its other rules stand here unchanged: the bearer's characters, the stdio refusal, the origin, the clean child environment.
- 170-4 decision 10 binds a waiting job to a "credential identity". For a per-user server that identity is the caller key of decision 5, never the credential or a value derived from it, so a job survives a renewed token, an eviction and a restart, and a continuation by another caller key is the conflict that decision names.
- The SDK's redirect rule, for a credentialed connection: its http to https upgrade is not followed (decision 10).
- Story I4's heading asks for a decision record as well as a spec. Decision records were retired on 2026-10-30; this spec carries the decision.

## Not checked

- Nothing was run on Postgres, and no Postgres result is claimed. `vfs-probe-postgres` is not installed in this container, a connection to port 5432 is refused, and `VFS_TEST_POSTGRES_URL` is unset. No claim of this spec depends on an engine: it adds no statement. The Postgres leg named under Tests is a test for the build.
- The SDK and `httpx2` are not installed here. The SDK was read in four source files at the pinned revision and never run in writing this spec. One run of it is on record, [Layer 8 of the conversion's validation](../2026-11-25-the-backlog-converted/validation.md): two streamable HTTP clients of SDK 1.29.0 called one FastMCP server over a local HTTPX ASGI transport, each with its own bearer marker. The server gave two session ids; every observed request that carried a session id, teardown included, carried only its own marker; neither serialized result nor the headers' `repr` held a marker; and a credential in a custom environment variable was absent from the SDK's default stdio child environment. That shows two SDK clients keep their bearers and sessions apart and that the header rides the closing request. It does not show the design here: each client was configured through the SDK's own client with a fixed bearer, not through a carrier whose credential is replaced between requests; the server's output was constant, so no echo, no 401, no redirect and no rotation was exercised; the release was 1.29.0, where 170-4 pins `mcp>=2.3,<3` and the files read here are at `77001c96`; and no part of VFS was in it. Whether a carrier's header rides the stream and the resumption, whether a 401 and an exception raised inside the carrier surface as decisions 10 and 11 need, and whether a filter on the SDK's loggers drops what decision 14 says, belong to 170-4's first study.
- The prototypes are not `dev` code. One is the `Credential` class's hiding against the real envelope; it used a narrower character rule than decision 3 now has. One is the pool against a counting fake server, with a real `Authority` and nothing else of VFS: its thirteen counts are the ones the tests name, and it had one pool, not one a server. Three are on `httpx` 0.28.1, which stands in for `httpx2`: header carriage, the exact-origin predicate over twelve targets and three redirects, and the rotation of a carrier's credential before a request is written. The listing rule of decision 12, the withdrawal on `None` and the inbound comparison of decision 16 were not prototyped.
- The churn table is a model of least-recently-used pools over a generated day, run once with a fixed seed. Five of its inputs are assumptions, named in Cost. No deployment was measured, and `TOOL_CATALOGUE_BYTES` was not sized against one snapshot a caller.
- The loggers of the HTTP library were not read below its client module, and its frames that hold a header's value while they run were not audited. The leak tests over the root logger and over a traceback with locals are what hold them.
- The kernel store, the job contract, the run store and the action log are not on `dev`. What their records hold of a tool call was read from their specs and, for the store, from its branch.
- `MCP_CALLER_CONNECTIONS` and `MCP_LIVE_CREDENTIALS` rest on that model and on arithmetic, and on no measurement. Whether an idle connection holds a socket depends on the HTTP library's keep-alive and on a standing stream, and was not read; a process's descriptor limit is the host's setting and was not costed.

## Choices to confirm

No choice below lacks a reversible side, so the build waits for none of them. It waits for the work named under Builds on.

1. **D16.** Taken: the host's resolver, no store, no exchange inside VFS, no forwarding, a set refused. The other sides are a store VFS owns and token exchange at the edge. The side taken adds two names and one argument shape and can be withdrawn until it ships.
2. **What "never during `tools/list`" means.** Taken: the resolver is asked once by each call and each resource read, and once by a catalogue read addressed to one server that must open the caller's connection; a list refresh and a listing from above never ask. The strict reading has a cold listing refused `vfs.unauthenticated` until the caller runs a tool or makes one named warming read, a `stat` of the server; it keeps the criterion's letter, and it makes `ls` fail for a caller who holds a credential and makes a `stat` open a connection. A third reading asks once a connection and never a call; it costs one failed call at each token's expiry.
3. **The connection key.** Taken: the actor and the one subject, as a stored session's owner is. The roadmap's words are "one connection per distinct principal", which could mean the subject alone. The pair shares less, and merging it later changes only how many connections are opened.
4. **The anonymous caller and the system actor.** Taken: both are refused before the resolver. The other side lets the resolver decide. Admitting them later is an addition.
5. **A credential for a stdio server.** Taken: refused. The other side is one child a caller, handed its credential on a pipe. Nothing lawful carries it today, since the environment is ruled out.
6. **Bearer only.** Taken. `Credential` can gain a second constructor, a named header say, without changing the first.
7. **A reply that holds a credential.** Taken: withheld whole, searched for every credential live on the connection while the request was open, at most 64, with no lower bound on a credential's length. The other sides are to pass it, to cut the secret out and keep the rest, or to search for the call's own answer alone, which the prototype showed lets an echo through. A floor on length would refuse a bearer 170-4 decision 2 accepts. Relaxing later lets through replies that are refused today.
8. **A resolver that raises.** Taken: `vfs.unavailable`, a fixed detail, and a log record of the class name alone. The other sides are to raise it to the caller of the verb, or to log its traceback; either can carry the secret out.
9. **The pool's size.** Taken: a budget for each per-user server, set by the host with `caller_connections=` on `add_mcp`, default `MCP_CALLER_CONNECTIONS = 1024`. The other sides are one pool for the router, of 64 or of 256, with no argument; the model in Cost puts those at three to five times the opens. The default is the rights cache's count and comes from a model, not a measurement.
10. **No connection at registration.** Taken. The other side is an argument naming an authority to probe as, which would make the host hold a real caller's credential at startup.
11. **The inbound token.** Taken: the serving edge keeps the request's bearer, hidden, for the life of the request, and a credential equal to it is never sent. The other side is the documented rule alone. The comparison can be dropped later without changing any result a correct host sees.
12. **A credential the host withdraws.** Taken: `None` or a returned error closes that caller's connection and drops its snapshot and cached bodies, and a cached resource body is shown only after the resolver has been asked. The other side keeps them until their own freshness ends.
13. **A changed credential.** Taken: a new credential for the same caller replaces the carrier's and keeps the connection, the session and the snapshot. The other side retires the connection at every change and refuses new calls while an old one is in flight; a host that mints a token for each call would then open on every call.
14. **Exact origin.** Taken: no https upgrade and no second spelling of a host. The other side follows the SDK's upgrade from port 80 to port 443. Admitting it later is an addition.

## One line

A server registered with a resolver is called as each caller, on that caller's own bounded connection, with a credential that VFS asks the host for at every call, carries in one header, and lets reach no result, row, record, log, line or child.
