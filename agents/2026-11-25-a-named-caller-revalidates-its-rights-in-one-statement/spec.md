# A named or anonymous caller revalidates cached rights in one statement and the storage counts how the cache serves calls

A draft, written on 2026-11-25 against `dev` at `27f3d24d`. It is not reviewed, and nothing is built. Unit 179-9 has no named roadmap story and its gate is unplaced. It converts [spec 179, sections 5.2–5.4 and criteria 13–14](../../context/specifications/archive/179-the-storage-seam-as-the-kernel/spec.md) and [tasks 12–13](../../context/specifications/archive/179-the-storage-seam-as-the-kernel/tasks.md), following the [seam reassessment](../2026-11-25-the-backlog-converted/reassessment/seam.md). It rests on the rights-compile pins and the reviewed access-path tables.

## The outcome wanted

A warm `read` on SQLite or Postgres checks a named or anonymous caller's authority in one round trip when its principal IDs fit one membership query. A committed revocation or narrowing posture still takes effect on the next call, even during relabelling. The owner of a database storage handle can read its lifetime hits, misses, stale entries and evictions together, without a database call or a list of identities.

## What the code does today

A focused probe ran the real `DatabaseStorage.read` path and an in-process replacement of only the two resolver reads, on file-backed SQLite and an isolated PostgreSQL 16.2 server. For the test seed above both engines gave system 1 → 1, cold named 7 → 6, warm named 3 → 2, cold anonymous 7 → 6 and warm anonymous 4 → 3 SELECTs. A named read after revocation on a closed mount gave 11 → 9 and no observations on either engine. Removing a member's only read grant by removing membership on a second handle also gave 11 → 9 and zero observations. A held narrowing relabel, a second named read during it, and its settling continued to hide the file. Anonymous saw `vfs.unauthenticated` and zero observations under the mark (10 → 8 SELECTs). At B = 2, empty, absent and duplicated IDs gave the old keys in one statement, and three unique IDs gave the old key in three statements on both engines. SQLite running the unknown-dialect profile checked one ID and three marks in two statements. A separate in-memory SQLite counter prototype observed the write fence inspecting absent IDs before a cold resolver lookup and present IDs after it. The cold write counted exactly one miss and a replacement between lookup and comparison counted (0,1,0,0). These are prototype measurements, not landed behavior.

## The problem

A cache hit today still runs a greatest-stamp query on the caller's subjects and groups, then a separate read of all pending posture relabels. A miss does both after finding the caller's groups (`rights.py:360–387`). A stable key needs the stamp and the complete ordered tuple of marks. Dropping either check to save a trip can expose a revoked file or admit one through an old label. At the reference deployment, even the common successful check repeats across 150,000 verb calls a day. The cache gives no measure of how often those checks find reusable rights.

## Decisions

1. **Fold one stamp read and the marks read in the resolving session.** Implement `stamps_and_marks(session, tables, profile, membership_budget, ids) -> tuple[int, tuple[Mark, ...]]` for both call sites in `rights.py`. On SQLite and Postgres, deduplicate and sort the IDs. When they fit one chunk, issue one SQLAlchemy Core `UNION ALL`. Its first arm selects `CAST(NULL AS <path_prefix type>) AS path_prefix, MAX(revision) AS revision` from `tables.principal_revisions`, restricted by the shared `membership` predicate on `principal_id`. Its other arm selects `path_prefix, revision` from `tables.relabels`. Use the mount's table objects, including their schema. Only the aggregate row has a null path. Decode it wherever it occurs, mapping an empty maximum to zero, and sort the other rows by path into `Mark(path, revision)`. An empty ID set still returns the marks. This uses the existing non-null primary key, bytewise order and revision types (`src/vfs/models/rows.py:170–200`, `:809–825`). Both arms read one statement snapshot. Neither the key nor its correctness depends on the plan's arm order. Section 5.3 of the source supplies the query.

2. **Keep the existing bounded sequence when the fold cannot use one membership query or the engine is unknown.** Compare the unique ID count with the host's actual `membership_budget`. At equality the fold fits. Above budget, call `principal_revision` over all chunks, then `inflight_marks` once. Use that same sequence on an unknown dialect, identified by `profile.name not in PROFILES` (`dialects.py:457–473`). It retains the floor's previous read order and path collation without supposing an unknown engine supplies the tuned engines' snapshot. Use `membership` for the folded predicate so a later dialect-specific key-list implementation applies in one place (`membership.py:43`, `revision.py:82–96`, `labels.py:307–311`). Propagate query failures through the existing caller. A failed check never serves the cached value.

3. **Keep both uses of the key distinct.** Check the IDs remembered on a warm lookup. When the entry is stale or absent, rebuild through the existing per-subject closures, then read the key afresh with the new IDs. Include `EVERYONE_NAME` in anonymous's stamp set exactly as at `rights.py:377–380`. Preserve each mark's revision, so replacing a mark at the same path retires the old key. Preserve the opening and closing mount revisions, the rule against caching an unstable compile, the uncached admin path and the system bypass. A stale lookup followed by a compile can save two statements. A call refused before resolution saves zero. The fence's independent stamp read stays a separate query.

4. **Count outcomes of actual cache lookups.** Start four integers at zero on each `RightsCache`. Its `counts()` returns an immutable `RightsCacheCounts(hits, misses, stale, evicted)` snapshot. Keep `ids(subjects)` a passive inspection for the fence. Use a resolver-only `lookup_ids(subjects)` which counts one miss if there is no entry. If there are IDs, pass that same tuple to the cache's final lookup after the SQL await. A matching entry and key count one hit and promote it. A differing key on the entry checked counts one stale and one miss and drops it. If the entry disappeared or the tuple was replaced during the await, count one ordinary miss and rebuild, leaving a replacement intact. Use identity of the held tuple on the normal path so no second scan of its IDs is needed. A `get` with no supplied tuple retains its existing direct lookup behavior. Count once when the outcome is known, even if the ensuing compile fails or cannot be remembered. A validation that raises or is cancelled before `get` has no lookup outcome. A retry counts the lookups it actually makes. The uncached and system paths count nothing. Counting at every `ids` call as section 5.2 proposes would count the write fence's inspection as another cold miss.

5. **Count capacity removals where they happen.** Each actual removal from `put`'s least-recently-used loop increments `evicted` once, including several removals to fit a single heavy value. Replacing the entry for the same subjects or dropping a stale entry has no eviction charge. Keep `held`, weighting and promotion as built. Counters have no principal, path or operation labels, no expiry, no reset-on-read and no persistence. The loop-thread updates and snapshot have no await or lock.

6. **Expose one synchronous, storage-local snapshot.** Read `storage.counters().rights` before or after first touch, without provisioning storage. Use the same `StorageCounters` named tuple and accessor as 179-7 decision 9. The first landing declares the fields it can measure. The second adds the other field and preserves the existing named field and its semantics. Document field access by name. With both present the snapshot has the source's named fields `retries` and `rights`. Keep the concrete named tuples in `src/vfs/storage/backends/database/retries.py`. Its `__all__` lists the snapshot types that exist at landing. Re-export that module as `counters` from `src/vfs/__init__.py`, following the existing `ranking` module export. This gives `from vfs import counters` and `counters.StorageCounters` without a separate top-level type for each record. A storage-local type alone, as proposed in 179-7 decision 9, would leave the return annotation unreachable under the naming rule and the docs gate (`documentation/maintainers/how-we-name.md`, `scripts/docs_export.py:353–368`, `:538–557`). The storage's operational methods `first_touch` and `install_extensions` are precedents (`backend.py:1121–1128`). Tests, exporters and hosts can hold a backend directly. There is no change to the routed verb vocabulary, capability declarations or `Result`.

7. **Repin the actual affected calls and keep the existing cost checks exact.** In each 179-8 SQL fixture replace each eligible adjacent stamp-and-mark pair with the folded statement. Check the normalized SQL, ordering and actual rows, binds and bytes. One eligible pair saves one execution. A fallback, early refusal or bypass contributes no pair. System cases and native-call counts stay equal to their baseline. Preserve results, refusal kinds and all unrelated statements. Include both measured engine diffs and the production change in the same review. Update the existing warm `stat` pin at `tests/storage/database/test_rights.py:597–615`, the named SQLite `ls` page pin at `tests/support/cursor_contract.py:161–182` (in `tests/support/contract/cursor.py` after the split), and the three batch-write formula tests at `tests/base/test_write_at_scale.py:95–165`. Their warm named gate pays one folded query and one independent principal-revision fence query. Teach the formula's classifier and fixed-family exclusions to recognize those two families. Keep all budget-dependent terms.

## Cost

Let D be the distinct stamped IDs, B the host's `membership_budget(profile, parameter_budget)` and M the number of unfinished relabel marks. B derives from the live SQLAlchemy parameter budget, the profile's list limit and the reserved binds (`engine.py:250–257`, `dialects.py:535–548`). For D ≤ B on either supported engine the fold issues one statement, with at most D membership binds, and returns 1 + M rows. Both probe handles reported B = 32,668 from their own dialect. The stamp arm has D principal keys to look up, independent of file count. The other arm reads M pending relabels, normally zero. The ID normalization costs O(D log D) time and O(D) space as on dev. Sorting the returned marks costs O(M log M) time and O(M) space. The complete set belongs in the key, so truncating it to a new cap would change rights. Above budget or on the generic floor the count is ⌈D/B⌉ + 1 and each stamp query has at most B keys. There is no expression tree proportional to D, no new lock, no wait on a writer and no extra transaction.

For 150,000 calls a day (`AGENTS.md:82`, `:94`), with an average of F eligible pairs per call, the saving is 150,000 × F database executions. One eligible pair on every call saves 150,000. A batch pays per resolution per mount and attempt, regardless of its file count. The four integers add four integer fields per handle. A lookup costs constant extra work, an eviction one increment per entry already dropped, and a rights snapshot four integer reads. The existing `RIGHTS_CACHE` and `RIGHTS_CACHE_BYTES` remain the cache budgets (`rights.py:141–150`).

## Choices to confirm

1. **Where are the counts read?** Take the backend method over a routed administrative method. It gives a host the exact cache it owns and can later supply a cross-mount exporter without introducing a new authorization boundary now.
2. **Should an unknown engine get the optimized statement?** Take the existing ordered reads on the generic floor. Enabling the fold later is local to the profile and can follow a measured statement-snapshot and ordering contract.

## One line

One bounded query validates a cache entry on SQLite and Postgres, and four per-handle counts distinguish reuse, recompilation after a miss, stale keys and capacity evictions.
