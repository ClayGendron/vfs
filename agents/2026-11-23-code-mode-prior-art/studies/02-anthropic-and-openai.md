# 02 — The model vendors' own code mode and tool discovery: Anthropic and OpenAI

## The question

This study received the brief in `00-brief.md` with one subject: the model vendors' own versions of code mode and tool discovery. For Anthropic: the engineering post "Code execution with MCP" (files of code modules, `ls` and read, the 150,000 → 2,000 token example, intermediate results kept out of context, PII tokenization, state and skills); "Introducing advanced tool use" and the API documents for the tool search tool, programmatic tool calling and tool use examples, with every number tied to its workload; Agent Skills and the `anthropics/skills` repository; Claude Code's deferred MCP tools and its handling of large tool outputs. For OpenAI and others: tool search and deferred tools in the Responses API and the Agents SDK, hosted code calling tools, Codex's handling of MCP tools, and Google only where a direct analogue exists. Three points carry extra weight: how deferred-tool search ranks tools (what text is indexed; regex, BM25 or embeddings), how results flow (whether code sees the full tool result while the model sees only printed output), and the files-as-tools framing, since vfs proposes to store tools and their results as files that `grep` and `search` reach.

## Findings

### Anthropic: the pattern post

1. **READ (code-execution-with-mcp post).** The 2025-11-04 post is a pattern, not a shipped product. MCP servers are presented as a file tree, `servers/<server>/<tool>.ts` with an `index.ts` per server (examples: `servers/google-drive/getDocument.ts`, `servers/salesforce/updateRecord.ts`); each file is a typed TypeScript function wrapping a shared `callMCPTool` client with a namespaced name such as `google_drive__get_document`. Discovery is the agent listing `./servers/` and reading only the files it needs ("progressive disclosure"), or alternatively a `search_tools` tool whose detail-level parameter returns names only, names with descriptions, or full definitions with schemas. Intermediate results stay in the execution environment unless logged: a 10,000-row sheet is filtered in code to `Status === 'pending'` and only the count and five rows are logged; a polling loop with a 5,000 ms sleep replaces alternating tool calls. Privacy: the MCP client replaces PII with placeholders (`[EMAIL_1]`, `[PHONE_1]`, `[NAME_1]`) before the model sees it and reverses them through a lookup when the values flow into another tool call, which the post says enables "deterministic security rules" over where data may flow. State: code writes `./workspace/leads.csv` and resumes later; working code is saved as `./skills/save-sheet-as-csv.ts`, and adding a `SKILL.md` makes it a structured skill. Caveat in the post's own words: agent-generated code "requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring", an operational cost direct tool calls avoid.
2. **READ (same post).** The headline number is the vendor's estimate, not a measurement on a named benchmark: the approach "reduces the token usage from 150,000 tokens to 2,000 tokens", a 98.7% saving, for the running example "download my meeting transcript from Google Drive and attach it to the Salesforce lead"; the post separately estimates about 50,000 extra tokens for a two-hour transcript passing through the model twice. The workload behind the 150,000 figure is not specified further. INFERRED: no Anthropic API product ships the file tree of tool modules. What ships is programmatic tool calling (tools as Python functions in a container, finding 5), the tool search tool (finding 3), and Skills (folders on a filesystem, finding 8). The files-as-tools framing survives in Skills and in Claude Code's persisted outputs, not in the tool catalog.

### Anthropic: the tool search tool

3. **READ (tool search tool docs).** Two server-side variants: `tool_search_tool_regex_20251119`, where Claude writes Python `re.search()` patterns, matched case-insensitively, at most 200 characters; and `tool_search_tool_bm25_20251119`, where Claude writes natural-language queries of at most 500 characters. "Both tool search variants (`regex` and `bm25`) search tool names, descriptions, argument names, and argument descriptions." A search returns `tool_reference` blocks, 5 by default, `limit` from 1 to 10,000; the API expands each reference into the full definition inline in the conversation, and expanded tools stay usable in later turns without re-searching. At most 10,000 deferred tools per request. `defer_loading: true` controls what enters context, not what is sent: every full definition is sent on every request, because "the tool definitions in the request are searched in memory per call and nothing is stored after the response" (the ZDR note). Deferred tools are excluded from the system-prompt prefix, so the prompt cache survives a discovery; a deferred tool cannot carry `cache_control`. At least one tool must stay non-deferred. MCP connector servers defer through `default_config` on the `mcp_toolset` entry. A custom search (embeddings, anything) is a client tool that returns `tool_reference` blocks inside an ordinary `tool_result`. Search is not metered separately; loaded definitions count as input tokens. The docs' guidance: use it at 10 or more tools or over 10k tokens of definitions; keep the 3 to 5 most-used tools loaded; prefix names by service (`github_`, `slack_`) "so one search matches the whole group"; add a system-prompt line naming the tool categories.
4. **READ (advanced-tool-use post; tool search docs). Evidence, all Anthropic-measured on unpublished internal evaluations:**

   | Claim | Workload | Figure |
   |---|---|---|
   | Context cost of definitions | GitHub 35 tools (~26K), Slack 11 (~21K), Sentry 5 (~3K), Grafana 5 (~3K), Splunk 2 (~2K) | 58 tools, ~55K tokens before the conversation starts; Jira alone ~17K; "134K tokens before optimization" seen internally |
   | Upfront tokens | 50+ MCP tools | ~72K (about 77K total) without search; ~500 tokens plus 3–5 loaded tools (~3K), about 8.7K total, with search; "191,300 tokens of context compared to 122,800" preserved; "85% reduction in token usage" |
   | Selection accuracy | "MCP evaluations" | Opus 4: 49% → 74%; Opus 4.5: 79.5% → 88.1% with search on |
   | Degradation threshold | stated in the docs, no study cited | selection "degrades once you exceed 30–50 available tools" |

   The ranking inside the BM25 variant (tokenizer, field weights, k1 and b) is not documented; the docs' debugging advice for regex is to test `re.search(pattern, "tool_name", re.IGNORECASE)` and to add common keywords to descriptions.
5. **READ (cookbooks `tool_use/tool_search_with_embeddings.ipynb` and `tool_use/tool_search_alternate_approaches.ipynb` @ `8ad5de6`).** The embedding recipe renders each tool as text (`Tool: <name>`, `Description: <description>`, then `Parameters: <name> (<type>): <description>, …`, cell 7), embeds with `all-MiniLM-L6-v2` (384 dimensions), ranks by dot product of normalized vectors, and returns `tool_reference` blocks (cell 15). The alternate recipe has no search at all: the system prompt lists every tool name and a `describe_tool(tool_name)` tool returns one `tool_reference` while the application appends that definition with `defer_loading: True` to keep the cached prefix intact (cells 6, 9, 15). It names further shapes it does not build: `list_tools` by category, hierarchical browsing, and a hybrid of listing with search. INFERRED: the vendor treats discovery as pluggable over one primitive, "load this named definition now"; the ranking is a client choice.

### Anthropic: programmatic tool calling

6. **READ (programmatic tool calling and code execution docs).** The call surface is Python. A tool opts in with `allowed_callers: ["code_execution_20260120"]` (`["direct"]` is the default; both may be listed, the docs advise one); it then appears inside the code execution container as an async Python function that "takes a single dict of arguments and returns a string: the text of the `tool_result` you send back", awaited with top-level `await` and run in parallel with `asyncio.gather`. Flow: Claude writes code; when the code calls a tool, execution pauses and the API returns a `tool_use` block whose `caller` names the code execution run; the client runs the tool and returns a `tool_result` (text only; a message answering a programmatic call may contain only `tool_result` blocks); the code resumes. "Tool results from programmatic calls are not added to Claude's context: Only the final code output is", and they "do not count toward your input/output token usage". The container: Python 3.11, x86_64 Linux, 5 GiB RAM, 5 GiB disk, 1 CPU, internet "completely disabled", file access limited to the workspace; a 90-second wall-clock limit per Python cell under programmatic calling (`code_execution_20260521` tells Claude so); a pending tool call times out after about 4 minutes with a `TimeoutError` inside the code; REPL state persists across requests that reuse a container; containers are checkpointed after about 5 minutes idle and expire 30 days after creation; data retained up to 30 days, not ZDR-eligible. Billing: 5-minute minimum, 1,550 free hours per organization per month, then $0.05 per container hour; free when web search or web fetch is in the request. Restrictions: MCP connector tools and the computer and browser toolsets cannot be called programmatically; `strict: true` tools are not supported; a recursive `$ref` in an input schema is refused with `Circular $ref detected`; `tool_choice` cannot force a programmatic call.
7. **READ (same docs).** Authority and safety: tools run in the client, so credentials never enter the container; but "`allowed_callers` … is not a hard API-level block on direct calls … Do not rely on `allowed_callers` as a security boundary." The docs warn that tool results "can contain any content, including code snippets or executable commands" and to validate them against code injection. Three implementation shapes are compared: client-side direct execution ("runs untrusted code outside of a sandbox"), self-managed sandboxed execution (no egress, plus a protocol to run tool calls outside the sandbox), and the managed container.
8. **READ (advanced-tool-use post; PTC docs; dynamic-filtering blog). Evidence for programmatic calling, all vendor-measured:**

   | Workload | Before → after | Source |
   |---|---|---|
   | "Complex research tasks" | 43,588 → 27,297 tokens (37% fewer) | post |
   | Internal knowledge retrieval | 25.6% → 28.5% | post |
   | GIA benchmarks | 46.5% → 51.2% | post |
   | Budget example, 20 employees, 2,000+ line items | ~200 KB of raw expense data → ~1 KB of results; 19+ inference passes avoided | post |
   | 75-tool project-management agent benchmark | billed input tokens about 38% lower, "no change in task accuracy" | docs |
   | τ²-bench (airline, retail, telecom), one or two sequential calls a turn | scores unchanged, cost about 8% higher; "Sequential single-call workflows do not benefit" | docs |
   | Production API traffic, 10 to 49 tool definitions | typical 20–40% token savings | docs |
   | BrowseComp, web search only, code filters results | Sonnet 4.6 33.3% → 46.6%; Opus 4.6 45.3% → 61.6% | blog |
   | DeepSearchQA F1, same | Sonnet 4.6 52.6% → 59.4%; Opus 4.6 69.8% → 77.3%; across both benchmarks +11% performance with 24% fewer input tokens; price-weighted tokens rose for Opus 4.6 | blog |

   The docs' own fit test: strong for fan-out, large filterable results and agentic search; weak for "strictly sequential workflows where each call depends on Claude reasoning over the previous result", small calls on a first turn (container and script overhead exceed the saving), and tools needing user feedback between calls.
9. **READ (cookbook `tool_use/programmatic_tool_calling_ptc.ipynb` @ `8ad5de6`, recorded outputs of cells 13, 20, 22) and EXECUTED (`experiments/02-ptc-cookbook-seed/`).** The cookbook's one recorded comparison on its mock expense API: traditional 110,473 tokens, 4 API calls, 35.38 s; programmatic 15,919 tokens, 4 calls, 34.88 s; 85.6% fewer tokens, 1.4% less time. The two runs disagree on the answer: the traditional run reports ENG001's travel at $6,753.62 and the programmatic run reports $9,177.88 (both name the same three people over budget). The mock data is seeded with `random.seed(hash(employee_id + quarter))` (`tool_use/utils/team_expense_api.py:251`), and Python string hashing is randomized per process: run under `PYTHONHASHSEED` 0, 1 and 2, ENG001 gets 39, 21 and 36 line items and approved travel-plus-lodging totals of $10,585.95, $8,010.42 and $6,062.81 (`output.txt`). INFERRED: the pair is valid only if both cells ran in one kernel, and nothing records that they did; it is a single unreplicated pair, and its disagreement shows that the same question answered by in-context arithmetic and by code can differ, with nothing in the output saying which is right. The latency result, flat at the same call count, matches the docs' statement that the saving is in tokens and round trips, not in tool time.
10. **READ (advanced-tool-use post; tool search docs).** Tool use examples: `input_examples` on a definition (1 to 5 recommended; minimal, partial and full) raised "complex parameter handling" accuracy "from 72% to 90%" in internal testing, workload not further specified. When a deferred tool is discovered, its `input_examples` are expanded with its definition.

### Anthropic: Agent Skills

11. **READ (skills post; Agent Skills docs).** Skills are directories with a `SKILL.md`; disclosure has three levels: the frontmatter `name` and `description` are preloaded into the system prompt (~100 tokens per skill), the body is read on demand "using bash" (`cat pdf-processing/SKILL.md`, guidance under 5k tokens), and bundled files are read or run only when referenced; "the script code itself never enters context", only its output. There is no search step: the model matches the request against every preloaded description. Field limits: `name` at most 64 characters, lowercase letters, digits and hyphens, no `anthropic` or `claude`; `description` at most 1,024 characters and must say both what the skill does and when to use it. Runtime differs by surface: on the API no network and no package installation; in Claude Code full network, the same as any program on the machine; on claude.ai per admin setting. Security: a malicious skill "can direct Claude to call tools or run code in ways that don't match the Skill's stated purpose"; audit bundled scripts and any external fetches. The October 2025 post states the hope to "enable agents to create, edit, and evaluate Skills on their own"; the code-execution post's "save working code as a skill" is that hope applied to tool code.
12. **EXECUTED (`experiments/02-skills-metadata-size/` over `/home/user/skills` @ `e4bb5d9`).** The repository holds 19 skills; the frontmatter fields in use are `name` and `description` (19), `license` (17), and `accepts` and `surface` (1 each). Name plus description total 6,589 characters, 347 per skill (INFERRED: about 87 tokens at four characters a token, consistent with the documented ~100); the longest description is 952 characters. `SKILL.md` bodies have a median of 9,390 bytes and a maximum of 105,146 (`claude-api`), well above the under-5k-token guidance. Bundled scripts concentrate in the document skills: `docx` 59 of 61 files, `pptx` 56 of 58, `xlsx` 51 of 53, `pdf` 8 of 12. The spec itself has moved to agentskills.io (`spec/agent-skills-spec.md`).

### Anthropic: Claude Code

13. **READ (Claude Code MCP docs; changelog).** In Claude Code, "only tool names and server instructions load at session start"; MCP tool definitions are deferred and loaded through a `ToolSearch` tool, on by default. `ENABLE_TOOL_SEARCH`: unset or `true` defers all MCP tools; `auto` defers only once definitions reach 10% of the context window; `auto:N` sets the percentage; `false` loads everything. A server or a tool can opt out with `alwaysLoad` (`_meta["anthropic/alwaysLoad"]` on the tool). Descriptions are cut at 4,096 characters for server instructions and upfront tools and 16,384 for a tool loaded through search, and "when tool search matches Claude's query against a tool's description, it reads only the part within the shorter limit, so put the words Claude would search for near the start". History from the changelog: auto mode on by default for all users in 2.1.7 (2026-01-14), then named `MCPSearch`; `auto:N` in 2.1.9 (2026-01-16); the 16,384-character cap for searched descriptions in 2.1.295 (2026-10-08, previously 2,048). The changelog also records the failure modes of a deferred catalog in production: "Fixed `ToolSearch` ranking so pasted MCP tool names surface the actual tool instead of description-matching siblings" (2.1.113, 2026-04-17); "Fixed tool search sometimes loading another MCP server's tool when asked for a tool by its exact name"; "Fixed tool search returning no match when Claude selects an MCP tool by its bare name instead of its full `mcp__server__tool` name"; "Fixed empty model responses immediately after `ToolSearch` — the server renders tool schemas with system-prompt-style tags at the prompt tail, which could confuse models into stopping early" (2.1.70, 2026-03-06); several prompt-cache misses on resume and compaction; and deferred tools losing their input schemas after compaction.
14. **EXECUTED (this session runs inside Claude Code).** The session's system messages listed 66 deferred tools by name only, built-in ones among them (`WebFetch`, `WebSearch`, `NotebookEdit`) as well as MCP tools (`mcp__github__*`). The `ToolSearch` tool's own description offers three query forms: `select:A,B` for exact names, free keywords ranked against the catalog, and `+term` to require a term in the name and rank by the rest. `select:WebFetch,WebSearch` returned both full JSON schemas; the keyword query `github pull request review comment` with `max_results` 5 returned five full `mcp__github__*` schemas, best match first (`add_reply_to_pull_request_comment`, `pull_request_review_write`, `add_comment_to_pending_review`, `request_copilot_review`, `create_pull_request`). The ranking algorithm behind keyword mode is not documented in any source read here.
15. **READ (Claude Code MCP docs; changelog) and EXECUTED (this session).** Large outputs become files. For MCP tools: a warning at 10,000 tokens; a default limit of 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`); above it, or above 50,000 characters for a text result whatever its token count, "Claude Code saves it to a file and replaces it in the conversation with a message that names the file path, so Claude reads the file when it needs the content", in the session's `tool-results` directory under `~/.claude/projects/`. A server raises the threshold per tool with `_meta["anthropic/maxResultSizeChars"]`, up to 500,000 characters, for "inherently large but necessary outputs, such as database schemas or full file trees"; the Agent SDK forwards it from `ToolAnnotations(maxResultSizeChars=…)` because the CLI's schema layer strips unknown annotation fields (`src/claude_agent_sdk/__init__.py:295-305` and `:461-468` @ `3184360`). Error results longer than about 11,000 characters keep the first and last 5,000. Changelog: "Changed large tool outputs to be persisted to disk instead of truncated, providing full output access via file references" (2.1.2, 2026-01-09); the threshold fell from 100K to 50K characters (2.1.51, 2026-02-24); MCP images are also saved to a file "so Bash, Read and other tools can open them" (2.1.283, 2026-09-25); `bashOutputMaxChars` raises the inline limit for shell output up to 128K (2.1.261, 2026-09-04). In this session three `WebFetch` results of 63.1 KB, 60.1 KB and 57.3 KB came back as a `<persisted-output>` block naming a `tool-results/toolu_….txt` path with a 2 KB preview, and each was then searched with `grep -n` and read with `sed -n` by line range, which is how the code-execution numbers above were extracted.

### OpenAI

16. **READ (web-search summaries of developers.openai.com "Tool search"; Agents SDK `docs/tools.md:70-131` and `src/agents/tool.py:1641-1706` @ `6c4e4a2`).** The Responses API has a `tool_search` tool, for gpt-5.4 and later models per the search summary. `defer_loading: true` goes on individual functions, on the functions inside a namespace (not on the namespace object), or on a hosted MCP server. Two modes: hosted, where the platform returns the loaded tools in the same response, and client-executed, where the model emits a `tool_search_call` and the application answers with a `tool_search_output` (the SDK's standard runner raises rather than execute the client mode). The SDK's `tool_namespace(name, description, tools)` requires a non-empty description for each namespace; the docs advise namespaces or MCP servers over many individually deferred functions because "they usually give the model a better high-level search surface and better token savings", and "keep each namespace fairly small, ideally fewer than 10 functions"; the search summary reports OpenAI's reason as models trained mainly to search namespaces and MCP servers. What the hosted search indexes and how it ranks is not stated in any source reachable here. Developer-forum reports describe 500 errors when `tool_search` is reused after loading mixed top-level and namespaced tools (unverified).
17. **READ (Agents SDK `docs/tools.md:133-185`, `docs/release.md:63-69`, `examples/tools/programmatic_tool_calling.py`, `src/agents/tool.py:1597-1625`, `src/agents/run_internal/tool_caller.py:13-67` @ `6c4e4a2`).** OpenAI ships programmatic tool calling as a hosted Responses tool (`ProgrammaticToolCallingTool`, SDK 0.19.0): the model writes JavaScript; "the generated program runs in a fresh hosted V8 environment. It does not have Node.js APIs, filesystem or network access, or a persistent process. The program can interact only with tools that you explicitly allow." A tool opts in with `allowed_callers=["programmatic"]` (or `["direct", "programmatic"]`); function, custom, shell, apply-patch, hosted MCP and code interpreter tools can opt in, so unlike Anthropic's API a hosted MCP server's tools are callable from the program. A structured return annotation becomes a strict output JSON schema, and "the returned value is validated against that schema before it is returned to the program". The response carries a `program` item holding the generated code, child tool calls whose `caller` is `{type: "program", caller_id}`, and a `program_output`; the example instructs the program to "return exactly one JSON object" and the model explains it. Program-owned calls keep the runner's guardrails, hooks, timeouts, concurrency limits and approvals, and the SDK refuses a call whose caller the tool does not allow (`ensure_tool_caller_allowed` raises `ModelBehaviorError`) or whose `caller_id` matches no parent program. The docs advise that "approval-sensitive or high-impact tools are usually better kept as direct calls so a person can review each action before it becomes part of a larger program." Whenever the tool is present, the SDK disables provider-managed retries and retries only what the provider marks replay-safe, because a program may already have caused side effects. Per the search summary, the feature supports ZDR without a persistent container. No token, latency or accuracy figure was found in a reachable source.
18. **READ (Agents SDK `docs/tools.md:187-226`).** The hosted shell tool runs commands in an OpenAI container (`container_auto` or a reused `container_reference`), mounts skills by reference or inline bundle, and takes `network_policy` of `disabled` or `allowlist`; in allowlist mode `domain_secrets` "can inject domain-scoped secrets by name", so the secret is bound to a host rather than handed to the code.

### OpenAI Codex

19. **READ (`codex-rs/code-mode-protocol/src/description.rs:17-46`, `json_schema_types.rs:13`, `codex-rs/features/src/lib.rs:155-176` and `:1386-1396`, `:1457-1462` @ `1589e80`).** Codex carries a JavaScript code mode, feature `code_mode`, stage "under development", off by default; `code_mode_only` restricts the model-visible tools to the two entry points `exec` and `wait`. `exec` "evaluates the provided JavaScript code in a fresh V8 isolate as an async module"; every nested tool is a method on a global `tools` object, MCP tools under normalized names such as `tools.mcp__ologs__get_profile(...)`, each declared in TypeScript rendered from its JSON Schema (`declare const tools: { … }`, a 16,000-byte rendering budget per input schema, the MCP `CallToolResult` type as the return); "no Node, no file system, no network access, no console". Output to the model is only what the script appends with `text()`, `image()` or `audio()`, under `max_output_tokens`, 10,000 by default; `store(key, value)` and `load(key)` keep values across `exec` calls in a session; `yield_control()` and `wait(cell_id)` let a long script return partial output and resume; `ALL_TOOLS` lists `{name, description}` of every enabled nested tool, and deferred tools omitted from the description are found by filtering it. With `code_mode_tool_search`, `await tools.tool_search({query, limit: 8})` runs "BM25-ranked discovery of deferred tools" from inside the script and returns callable names with full TypeScript declarations.
20. **READ (`codex-rs/core/src/tools/code_mode/mod.rs:353-433` @ `1589e80`).** A nested call from the isolate is rebuilt as an ordinary `ToolCall` and sent to the same `tool_runtime.handle_tool_call_with_source(...)` that serves direct calls, tagged `ToolCallSource::CodeMode { cell_id, … }`; `exec` cannot invoke itself; arguments must be a JSON object. INFERRED: the isolate holds no credentials and no authority of its own; approvals, the sandbox policy and the execution policy that judge a direct call judge the nested one, because it re-enters the same door.
21. **READ (`codex-rs/core/src/tools/handlers/tool_search.rs:153-185` and `:333-350`, `codex-rs/tools/src/tool_search.rs:134-200`, `codex-rs/core/src/tools/handlers/mcp.rs:657-700`, `codex-rs/tools/src/tool_discovery.rs:7`, `codex-rs/core/src/tools/handlers/tool_search_spec.rs:94`, `codex-rs/features/src/lib.rs:319-321` @ `1589e80`).** Outside code mode Codex defers MCP tools behind a client-executed `tool_search` ("Searches over deferred tool metadata with BM25 and exposes matching tools for the next model call"); the `tool_search` and always-defer-MCP feature flags are removed because the behaviour is now permanent. Ranking is BM25 from the `bm25` crate (2.3.2), an English embedder fitted to the catalog corpus, default limit 8. The indexed text for a function is its name, its name with underscores turned to spaces, its description, and recursively every schema description and property name; for an MCP tool it is the flat name, the callable name, the raw tool name, the server name, the title, the description, the connector name, the namespace description, plugin display names and the sorted property names. The index is cached and rebuilt when the registry changes. Results from the same namespace are coalesced into one loadable namespace.

## What this means for a vfs code mode

All of this section is INFERRED from the findings above and from the drafted vfs specs 167, 169, 170 and 171 (`context/specifications/active/`).

- **Every vendor converged on one result rule, and vfs already has it.** Code sees the full tool result; the model sees what the code prints (Anthropic: "only the final code output"; OpenAI: `program_output`; Codex: `text()`). In the vfs shell the pipe carries full rows between stages and only the `cli` display is capped (spec 167, `RENDER_CHARACTER_BUDGET` 32,768 characters; stage stdout to 4 MiB). That is the same rule, spelled in bash. The evidence that it pays (findings 8, 9) is strongest where results are large and filterable or calls fan out, and absent where each call depends on the model reading the previous result (τ²-bench: unchanged scores, 8% more cost). An agent's read → edit → write loop is closer to the second shape, so the claim for a vfs code mode should be "cheaper fan-out and filtering", not "cheaper every call".
- **Persist the overflow and name its path, as Claude Code does, not truncate it, as Codex does.** Claude Code's answer to a large result is a file the model reads back with the same tools it uses for everything else (finding 15), and it measurably works in practice (this study was written that way). Spec 169c already records each `cli` call under `/.vfs/run/<call-id>/stdout` in a per-authority ring (64 calls, 64 MiB). Two concrete moves follow: the display's truncation marker should name that path, so the next command is `cat /.vfs/run/<id>/stdout | grep …`; and `/.vfs/run` should serve `grep` (and later `search`) and not only `stat`, `ls` and `read`, so a model can search a result it was not shown. Claude Code's per-tool override (`maxResultSizeChars` up to 500,000, for schemas and file trees) suggests a manifest field by which a tool declares that its output is meant to be read whole.
- **Ship ranked search over the tool catalog with the catalog, not later.** Spec 170 serves `grep` over `/.vfs/tools` and `/.vfs/mcp` manifests and leaves ranked search for later. Every vendor ships a ranked search, Anthropic's docs put the selection cliff at 30 to 50 tools, and two of three ship BM25. vfs's `search` already has a lexical leg; pointing it at manifests costs a rounding error at the reference deployment (thousands of manifests beside 10,000,000 files). The indexed text should be the union the vendors use: the name, the name split on `_` and `__` (Codex indexes `get_weather` and `get weather`), the server name, title and namespace description, the description, and every parameter name and parameter description. `grep -r … /.vfs/mcp` is the regex variant for free, matching Anthropic's regex tool; a default of 5 to 8 results matches the field. Results should be paths, because a path is what the next command consumes, the way a `tool_reference` is what the next API call expands.
- **vfs can do what no vendor does: filter discovery by rights.** Anthropic searches whatever definitions the request carries; Codex searches whatever is registered. Spec 170's rule, "who may call a tool is who may read its entry", makes `ls`, `grep` and `search` over `/.vfs/mcp` return only tools the caller may run. That is a governance property worth stating as the differentiator: a tool the caller cannot run is never shown, never ranked, and never costs a token.
- **Keep the catalog out of the prompt, but give the model a first move.** Claude Code preloads every deferred name, Skills preload name and description (about 87 tokens a skill, finding 12), and Anthropic advises a system-prompt line naming the tool categories. Spec 170 says vfs never places manifest text in a system prompt. The two reconcile if the host's one-line hint is "tools live under `/.vfs/tools` and `/.vfs/mcp`; `ls` them or `search` them", which costs a dozen tokens whatever the catalog size.
- **Authority must survive the hop the way Codex does it.** Codex rebuilds a nested call as an ordinary call into the same runtime (finding 20); OpenAI's SDK refuses a disallowed caller; Anthropic's `allowed_callers` is explicitly not a security boundary. Spec 167's `Fs` is the router's public verbs curried with the call's admitted authority, so every stage of a vfs pipeline re-enters the gate: that is the Codex design, and it should be pinned by a counted test that a tool reached through a pipe, a loop or `xargs` is judged exactly as when typed alone. No credential enters the shell; MCP tokens stay with the router's connection owner (spec 170), as they stay with the client in all three vendor designs.
- **Treat side effects inside loops as their own risk.** OpenAI advises keeping approval-sensitive tools direct, Anthropic lists "tools that require immediate user feedback between calls" as a weak fit and advises opting in only idempotent, parallelizable operations, and OpenAI's SDK refuses to replay a request once a program may have acted. A vfs code mode could read MCP's `destructiveHint` from the manifest and refuse such a tool as a non-first stage, inside `xargs`, or more than once per `cli` call unless the host allows it, and the `/.vfs/run/<id>/status` record already gives the per-stage attribution an approver needs.
- **Typed outputs make code reliable.** OpenAI validates each programmatic tool's output against a strict schema before the program sees it; Anthropic hands the code a string and asks the developer to document the format. vfs rows are already typed; the manifest under `/.vfs/tools/<name>` should carry the output schema (MCP `outputSchema`, `structuredContent`) beside the input schema, so a pipeline stage can rely on a field instead of parsing prose.
- **Skills: adopt the published format, so the existing corpus mounts unchanged.** Spec 169 has `/.vfs/skills`. The Agent Skills format is small (frontmatter `name` up to 64 characters, `description` up to 1,024, a body read on demand, scripts run rather than read) and the 19 published skills already follow it; the "save working code as a skill" step of the pattern post is, in vfs, writing a script into a stored program directory that `/.vfs/bin` resolves. The vendors' own caution applies unchanged: a skill is installed software, and a stored program inherits its caller's authority, never more.
- **PII placeholders belong at the render boundary, if anywhere.** The pattern post's tokenizer sits in the MCP client between tool and model. The vfs equivalent is the `cli` display: rows keep real values in the pipe, the display replaces marked columns with stable placeholders, and a later `write` or tool call resolves them in the router. It is a design question this study does not cost.
- **The language is the open bet.** Every shipped design uses Python or JavaScript; none uses a shell for orchestration, and no source here compares a shell with either. The evidence for bash is indirect: Skills and Claude Code already rely on `cat`, `grep` and files for discovery and for large results, and those are exactly the parts the vendors' code modes left to the filesystem.

## What this study does not settle

- OpenAI's own developer pages for tool search and programmatic tool calling could not be fetched; their ranking method, limits and any published numbers are missing here, and the summaries used are a search engine's paraphrase.
- The ranking behind Anthropic's BM25 variant and behind Claude Code's keyword `ToolSearch` is undocumented; only Codex's is readable in source.
- Every number in this study is the vendor's own, on internal or unpublished workloads; none has an independent replication, and the one inspectable comparison (the cookbook, finding 9) is a single unreplicated pair whose two answers disagree.
- Whether a model writes correct bash pipelines over tools as reliably as Python or JavaScript is not measured by any source read here.
- Google's position rests on search summaries only.
- How a vfs code mode would perform on τ²-bench-shaped sequential work, or on a fan-out workload, needs its own counted experiment.

## One line

Anthropic, OpenAI and Codex all settled on the same two moves, a ranked search (regex or BM25 over names, descriptions and parameter text) that loads tool definitions on demand, and code that sees full tool results while the model sees only what the code prints, and vfs's shell already has the second by construction and should ship the first over `/.vfs/tools` and `/.vfs/mcp` filtered by the caller's rights, with overflow persisted and named under `/.vfs/run` the way Claude Code persists it to a file.
