# 01 — Cloudflare Code Mode, end to end, as the primary reference design

## The question as this study received it

Study Cloudflare's Code Mode end to end as the primary reference design for a vfs code mode: the announcement and every later Cloudflare post on the topic; the implementation in `cloudflare/agents` (`packages/codemode`): how MCP tool JSON Schemas become a TypeScript API, the single tool given to the model, how the code is executed (Worker Loader, dynamic isolates), how calls from the sandbox reach MCP servers, how credentials stay outside the sandbox, what is returned to the model, limits and errors; the server-side Code Mode MCP server for the Cloudflare API and how its `search` over a large OpenAPI spec is implemented; the Worker Loader docs for isolation and limits; criticism as secondary. Answer the brief's seven "look for" points for Cloudflare, with `path:line @ commit` citations, then say what vfs should adopt, what it should do differently because its language is a bash-shaped shell over a governed namespace and its tool catalog lives as searchable files, and where Cloudflare's design is stronger.

### 1. The shape of the call surface

**F2. READ.** One package carries three call surfaces, and they differ in how much of the catalog the model sees up front.

| Surface | Tools shown to the model | What the description carries | Where |
|---|---|---|---|
| `createCodeTool` (AI SDK, TanStack) and `codeMcpServer` | one tool, `codemode` or `code`, input `{ code: string }` | **every** tool's generated TypeScript declaration, spliced into `{{types}}` | `packages/codemode/src/tool.ts:89-121`, `src/shared.ts:10-19`, `src/mcp.ts:125-235 @ 22af015` |
| The durable runtime, `createCodemodeRuntime(...).tool()` | one tool, input `{ code }` | only the connector **names**, a workflow and rules; no method or schema | `src/proxy-tool.ts:553-602 @ 22af015`; `src/content/docs/agents/tools/codemode/how-it-works.mdx:46-48 @ f425a80` |
| `openApiMcpServer` and the production Cloudflare API server | two tools, `search` and `execute`, each taking code | the OpenAPI type shapes and worked examples; no operation is listed | `src/mcp.ts:419-563 @ 22af015`; `cloudflare/mcp src/tools/search.ts:25-58`, `src/tools/execute.ts:613-635 @ b8602d6` |

In every surface the model writes a JavaScript async arrow function. The default description says "Write an async arrow function in JavaScript that returns the result. Do NOT use TypeScript syntax — no type annotations, interfaces, or generics." (`src/shared.ts:15-16 @ 22af015`). TypeScript is the documentation language and JavaScript is the execution language. Code is normalized before it runs: markdown fences are stripped and, with an acorn parse, a bare statement list is wrapped into an arrow function whose last expression becomes the return value (`src/normalize.ts:1-81 @ 22af015`).

**F3. READ.** A JSON Schema becomes a TypeScript declaration by a hand-written converter, `generateTypesFromJsonSchema` (`src/json-schema-types.ts:334-396 @ 22af015`). Per tool it emits `type <Pascal>Input` from the input schema and `type <Pascal>Output`, which is `unknown` unless the tool declares an output schema (`:345-349`). Each method gets a JSDoc block holding the tool description and one `@param input.<field> - <description>` line per top-level property (`:354-378`), and each property gets its own `/** description @format x */` comment (`:204-228`). `anyOf` and `oneOf` become unions, `allOf` an intersection, `enum` and `const` literal types, OpenAPI `nullable` a `| null`; internal `$ref`s are resolved; depth is capped at 20 and a cycle becomes `unknown` (`:76-80`, `:89-146`, `:285`). The tools are then declared as members of one global, `declare const codemode: { name: (input: NameInput) => Promise<NameOutput>; }` (`:390`). A runtime connector is the same declaration with the namespace renamed to the connector (`src/connectors/describe.ts:219-229 @ 22af015`). A snapshot of the output for two small tools is in `src/tests/__snapshots__/mcp.test.ts.snap:3-40 @ 22af015`.

**F4. READ.** Names are made into JavaScript identifiers by `sanitizeToolName`: hyphens, dots and spaces become `_`, other characters are dropped, a leading digit gets a `_` prefix, a reserved word gets a `_` suffix (`src/utils.ts:74-96 @ 22af015`; `delete` becomes `delete_`, README `:652-662`). Two tools that sanitize to the same name are refused, not silently merged (`src/executor.ts:529-540 @ 22af015`), and namespace names that would shadow the harness's own globals (`Promise`, `setTimeout`, `Error`, `console`, `__dispatchers`) are refused (`:356-398`). The Zero Trust portal applies the same rule to its `<server>_<tool>` namespacing (`src/content/docs/cloudflare-one/access-controls/ai-controls/mcp-portals.mdx:529-533 @ f425a80`).

**F5. READ.** The converter's known gaps are open issues (titles only, listed 2026-11-23): #2308 "array item unions and intersections generate incorrect TypeScript"; #2707 "array of string enum is generated as `"a" | "b"[]` (missing parentheses)"; #2181 "jsonSchemaToType drops sibling properties on root $ref and types allOf refinements as unknown"; #2597 "preserve JSON Schema validation constraints in generated JSDoc"; #2708 "codeMcpServer ignores tool outputSchema, so outputs are typed unknown"; #3017 "one tool with a non-'object' outputSchema makes every connector unavailable". INFERRED: the TypeScript surface is a lossy projection of JSON Schema. Minimums, maximums, patterns and lengths are not carried into the declaration, and in the MCP path almost every output is `unknown`, so the model writes code against results whose shape it has not been shown.

### 2. Discovery

**F6. READ.** In the durable runtime, discovery is a function call made from inside the sandbox: `codemode.search(query)` returns ranked paths, and `codemode.describe(path)` returns the TypeScript for one connector or method (`src/content/docs/agents/tools/codemode/how-it-works.mdx:50-85 @ f425a80`). The ranker is lexical and field-weighted, with no embeddings (`src/connectors/search.ts:1-206 @ 22af015`):

- Fields and weights: path 12, method 10, connector 8, description 5 (`:13-18`). Parameter schemas are **not** indexed; only names and the one description string are.
- Text is normalized by splitting camelCase, snake_case, dots and slashes into lower-case tokens (`:20-33`).
- Per field: exact match ×14, prefix ×9, phrase ×6, then per query token: exact ×4, token-prefix ×2, substring ×1 (`:57-76`).
- A coverage gate: a query of two tokens or fewer must match every token, a longer one 60% of them, unless the whole phrase appears (`:134-136`). Bonuses go to full coverage, a matching first token and an exact name (`:138-150`).
- At most 50 results come back, with `total` and `truncated` (`:11`, `:197-205`). Saved snippets are ranked in the same list (`:185-195`).

One open issue is about precision: #2296 "searchConnectors matches unrelated methods through short tokens". The design note states the intent: "Codemode moves discovery *inside the sandbox*: `codemode.search` and `codemode.describe` return results into the running code, not into the context window." (`docs/codemode/index.md:23 @ 22af015`). INFERRED: the model still sees a discovery result only when its code returns or logs it. So the first execution of a task is usually a discovery pass, and the method is called in a second execution. The rules in the tool description say so: "Never guess method names. If you have not used a connector in this conversation, run a discovery pass first" (`src/proxy-tool.ts:582 @ 22af015`).

**F7. READ.** On the server side, `search` over a large OpenAPI spec is **code the model writes over the whole dereferenced spec object**: no index, no ranking and no embeddings. In the SDK's `openApiMcpServer`, the spec is serialized into the sandbox module's source on every call, and a `$ref` resolver runs inside the sandbox when the model's code calls `codemode.spec()` (`src/mcp.ts:361-417 @ 22af015`). In the production server, a separate "forge tools" Worker holds the 27 MB pre-resolved spec as a text module. Each search starts a fresh isolate with `globalOutbound: null`, `JSON.parse`s the whole spec there, and runs the model's arrow function against it (`cloudflare/mcp src/forge-tools/search.ts:20-56 @ b8602d6`). A comment there records the cost of the earlier approach: splicing the 27 MB string into the module source "built a new string on every call, ~117 ms of CPU per search, most of it garbage collection" (`:23-28`). The `search` description lists the first 30 product tags and the spec types, and gives three examples: filter `spec.paths` by tag, read one operation's `requestBody`, read one operation's `parameters` (`src/tools/search.ts:25-58 @ b8602d6`). The one embedding-backed search in the server is the separate `docs` tool, which queries Cloudflare's documentation through AI Search (`src/tools/docs-search.ts:157 @ b8602d6`). An open issue records a scale failure of this approach in the SDK: #2596 "openApiMcpServer search deep-clones every resolved $ref, so large specs exceed Worker memory".

**F8. READ.** The Zero Trust MCP portal, which fronts many upstream servers, offers two discovery modes (`mcp-portals.mdx:563-580 @ f425a80`). Without code mode, `portal_query_tools` "Searches upstream tools by name, description, or schema using a regex pattern. Returns full tool definitions so the agent can call them." With code mode, `portal_codemode_search` runs JavaScript in a sandbox whose `codemode.tools()` "returns all upstream tool definitions with sanitized names", and `portal_codemode_execute` calls them. The portal's catalog is per user: a server "will only appear in the portal for users who match an Allow policy" (`:127`).

**F9. EXECUTED.** The Cloudflare spec as shipped at `b8602d6`, measured by `experiments/01-cloudflare-catalog/measure.mjs` at four characters per token (`output.txt`):

| Quantity | Measured here | The README's figure (`cloudflare/mcp README.md:5-12 @ b8602d6`) |
|---|---|---|
| Operations | 3,776 | 2,594 tools; "about 3,000" generated direct tools (`:52`) |
| Distinct tags (products) | 725 | — |
| Spec, `$ref`s pre-resolved | 26.8 M characters, about 6.7 M tokens | raw spec "~2,000,000" tokens |
| Every operation as an MCP tool with its full input schema | about 1.76 M tokens | 1,170,523 tokens |
| Required parameters only | about 0.20 M tokens | 244,047 tokens |
| One line per operation, `METHOD path  summary`, nothing else | about 84,000 tokens | — |
| Input schema size per operation, characters | p50 523, p90 3,995, p99 19,952, max 71,147 | — |

The README's figures were taken on an earlier, smaller spec and do not say how tokens were counted. The ratio holds either way: a fixed description of about a thousand tokens against a catalog of a million or more. The new figure is the one-line index. A list that only **names** each operation, with a few words of summary, is still about 84,000 tokens, larger than many models' working context. INFERRED: a catalog of this size cannot be shown as a flat listing even once. Discovery has to return a bounded slice, by query or by subtree.

### 3. Execution and isolation

**F10. READ.** The sandbox is a Dynamic Worker: a V8 isolate created at runtime by a Worker Loader binding. The docs describe the model: "An isolate is like a lightweight container… You can start an isolate in milliseconds, and it's fine to start one just to run a snippet of code and immediately throw away." (`src/content/docs/workers/runtime-apis/bindings/worker-loader.mdx:16-18 @ f425a80`). They add that "properly configured Dynamic Workers can run code you do not trust" (`:25`). The isolate's authority is what it is given. With `globalOutbound: null`, "Both `fetch()` and `connect()` will throw exceptions"; set to a service binding, every outbound request is routed through that binding, which receives `ctx.props` naming the sandbox; left unset, the sandbox inherits the parent's full network (`:167-177`). Custom bindings are RPC objects (`WorkerEntrypoint` classes) passed in `env` (`:208-221`). Per-invocation `limits` cap CPU milliseconds and subrequests (`src/content/docs/dynamic-workers/usage/limits.mdx:11-38`). At most 4 distinct Dynamic Workers may have requests in flight per Worker request, and 10 per Durable Object (`src/content/docs/dynamic-workers/platform/limits.mdx:11-20`). Pricing counts each `load()` as a new Dynamic Worker: 1,000 a month are included, then $0.002 each per day (`src/content/docs/dynamic-workers/pricing.mdx`). The "100x faster" start and "10x to 100x" memory saving against containers are Cloudflare's own claims (READ, search excerpt of the Dynamic Workers post).

**F11. READ.** `DynamicWorkerExecutor` runs each execution in a fresh isolate (`src/executor.ts:311-625 @ 22af015`):

- It generates one module, `executor.js`, that exports a `WorkerEntrypoint` whose `evaluate(__dispatchers, __connectors)` replaces `console.log`, `warn` and `error` with a capture buffer, builds one `Proxy` global per namespace, and races the model's function against a timer (`:484-516`).
- It loads that module with `loader.load()`, never `get(id)`, "every run produces a unique generated module, so there is nothing to cache by id" (`:569-583`). It sets `compatibilityFlags: ["nodejs_compat"]`, sets `globalOutbound` to the configured value with `null` as the default (`:322`), and passes extra `env` bindings only when they are configured.
- The timeout is a wall-clock `Promise.race` with `setTimeout` inside the sandbox, 60,000 ms by default (`:261`, `:498-507`). The v0.1.0 changelog gave the default as 30 s, so it has since doubled. No `limits` field is passed to the loader (`:573-583`), so CPU time and subrequests fall to the account plan's defaults (INFERRED from that absence and `dynamic-workers/usage/limits.mdx:11`).
- An `ExecutionGate` answers every tool call still pending when the code returns with a "late" error, so a fire-and-forget call cannot hold the isolate in flight and run the Durable Object into the concurrency limit "after a handful of executions" (`:159-226`).

The browser executor is weaker, and the README says so: its "timeout cannot preempt tight synchronous loops like `while (true) {}`" (`packages/codemode/README.md:721 @ 22af015`).

**F12. READ.** Calls leave the sandbox only as RPC, never as network traffic. Each namespace's `Proxy` turns `ns.tool(args)` into `__dispatchers.ns.call(name, json)` on a host-side `ToolDispatcher`, which is an `RpcTarget`. Arguments and results cross as JSON, with a tagged base64 codec for binary values. A host-side error comes back as `{ error }` and is re-thrown inside the sandbox (`src/executor.ts:228-257`, `:431-450`, `:68-110`). Connector globals instead call `__connectors.name.callTool(method, args)` over Workers RPC directly. A connector returns a control marker, `pause` or `error`, rather than throwing across RPC, and the proxy turns it into a local throw the model's own `try/catch` can handle (`:457-482`; README `:438-455`). The architecture note reads: "External `fetch()` and `connect()` are **blocked by default** — enforced at the Workers runtime level via `globalOutbound: null`. Sandboxed code can only interact with the host through namespaced tool calls." (README `:481-483`).

**F13. READ.** The production Cloudflare API server also starts one fresh isolate per call, with `LOADER.get(<random uuid>)` (`cloudflare/mcp src/tools/execute.ts:122-156`, `src/forge-tools/search.ts:29-30 @ b8602d6`). The reason given is that "dynamic-worker isolates disallow eval, so code cannot be passed into a warm isolate". The `execute` isolate's `globalOutbound` is a `GlobalOutbound` entrypoint that refuses any host other than the API base and injects the token (`execute.ts:69-120`). A fetch wrapper compiled into the sandbox paces the run against Cloudflare's rate limits (`:163-340`): at most 20 requests in flight, at most 3 retries, a 5 s longest hold waited out, and a run stopped once 1,000 requests have gone unsent (`src/rate-limit.ts:45`, `:74`, `:91`, `:94 @ b8602d6`). The host treats the sandbox's report as untrusted and parses it with a zod schema (`execute.ts:44-58`, `:546-548`). No explicit CPU limit or timeout is set on either isolate (INFERRED from `execute.ts:150-156` and `search.ts:30-53`).

### 4. Credentials and authority

**F14. READ.** Secrets never enter the sandbox, in every surface:

- SDK connectors hold their credentials and clients on the host. "The generated code never receives the connector credentials or client objects." (`how-it-works.mdx:127 @ f425a80`). In the README's Stripe connector, `request()` reads `this.env.STRIPE_KEY` on the host (`packages/codemode/README.md:328-334 @ 22af015`).
- `openApiMcpServer` runs the request callback "on the host (auth never enters the sandbox)" (`src/mcp.ts:415-418 @ 22af015`).
- The production server injects the token in `GlobalOutbound` from `ctx.props` and replaces any `Authorization` header the code sent: "token comes from props, never enters user code isolate" (`cloudflare/mcp src/tools/execute.ts:92-101 @ b8602d6`).

The docs name the limit of this protection plainly: "If the outbound gateway injects credentials, authorize the destination and operation first. Hiding a token does not limit what that token can do." (`src/content/docs/dynamic-workers/usage/authentication.mdx:214 @ f425a80`).

**F15. READ.** Whose authority a call carries depends on the surface:

- **The SDK has no caller identity at the call boundary.** A connector call runs with whatever credential that connector holds. The only per-call gate is the approval flag (F17). Authority is therefore the developer's choice of credential, wired per connector.
- **The production server runs each user's own Cloudflare credential.** That is an OAuth token issued for the connection, or the user's API token (`cloudflare/mcp README.md:15-45`; `src/api-permissions.ts:5-33 @ b8602d6`). Cloudflare's API judges every request. The server adds four things on top:
  1. A 401 or 403 is explained with the permission the endpoint needs. A missing OAuth scope triggers a scope step-up challenge, but only when the run was replay-safe, meaning every request it sent was a read or was refused (`execute.ts:539`, `:568-605`, `:700-725`).
  2. An empty list answered for a read the connection holds no scope for is turned into a refusal, "so it isn't mistaken for an empty account" (`README.md:89`).
  3. A policy guard refuses any write that spends money and any model run that is not a Workers AI model (`src/policy-guards.ts:1-67`).
  4. The `execute` tool is annotated `destructiveHint: true` (`execute.ts:678`).
- **Tool metadata must be identical for every user.** "MCP clients cache tool metadata and may serve one user's tool list to another, so nothing here may depend on the token" (`execute.ts:607-612 @ b8602d6`). A per-user view of the catalog cannot live in tool descriptions. It has to live in what discovery returns.
- **The Zero Trust portal judges identity before the catalog.** A user authenticates through Cloudflare Access, the portal returns only the servers whose Allow policy the user matches, and an upstream that needs per-user OAuth is authorized per user (`mcp-portals.mdx:42-43`, `:127`, `:178 @ f425a80`).

### 5. Results and state

**F16. READ.** What comes back to the model is the function's return value plus the captured console lines (`src/executor.ts:488-511`; `src/run-code.ts:16-31 @ 22af015`). A failure is a thrown `Code execution failed: <message>` with the console output appended (`run-code.ts:22-27`). An MCP tool's result is unwrapped before the sandbox sees it, in this order: `toolResult`, then `isError` as a throw, then `structuredContent`, then all-text content parsed as JSON or returned as a string, and mixed content returned whole (`src/mcp.ts:46-60`; `src/connectors/mcp.ts:42-60 @ 22af015`). Results are bounded at about 6,000 tokens by structural truncation: the output stays valid JSON of the same shape, the largest values are cut first, and every cut carries `--- TRUNCATED ---` (`src/truncate.ts:1-80`; `src/mcp.ts:25-40 @ 22af015`; `cloudflare/mcp src/truncate.ts:20-105 @ b8602d6`). The production server lets the caller lift the cap: "An agent that writes a result straight to a file or pipe, rather than reading it into the conversation, can pass `truncate: false`" (`cloudflare/mcp README.md:81`). The durable runtime keeps its own audit log of every call out of what the model sees (`src/proxy-tool.ts:754-800`). It had leaked there twice before the fix, per the issue titles #2143 "runPass returns untruncated `calls` log alongside truncated `result`, defeating the token cap" and #2182 "the full `calls[]` replay log is returned to the model, bypassing `transformResult`".

**F17. READ.** The durable runtime is a Durable Object facet with its own SQLite tables: `cm_executions`, `cm_log` with one row per connector call or step, and `cm_snippets` (`src/runtime.ts:1-50 @ 22af015`). Approval works by abort and replay. A method marked `requiresApproval` is recorded as pending and the pass aborts. Approval re-runs **the same source**: calls already applied are served from the log, the approved call executes, and the code continues (`how-it-works.mdx:200-221 @ f425a80`). This forces determinism. A sequence number must map to the same connector, method and arguments on every pass, or the execution fails with a replay-divergence error. `Date.now()` and `Math.random()` must be wrapped in `codemode.step()`. Calls inside `Promise.all()` "can arrive in different orders across passes and cause replay divergence" (`:223-245`). Rollback walks applied calls backwards and calls each tool's `revert`; it is compensation, "not database transaction isolation" (`:268-274`). Every value stored for replay is capped at 1,000,000 characters and cannot be truncated, since replay would feed the code different data. The error tells the model to "Write large data to a file or workspace instead and pass/return a small reference (such as a path)" (`src/runtime.ts:146-163 @ 22af015`). Fifty terminal executions are kept (`:144`), and a paused run expires after 24 hours (`:156`). The legacy `createCodeTool` path has no pause at all. It drops tools marked `needsApproval` from the sandbox entirely (`src/resolve.ts:16-31`; README `:720`). Approval is per method, not per argument; the issue titled #2134 "support argument-aware approval decisions before durable pause" is open.

**F18. READ.** Model-written code becomes a reusable skill only by a person's act. A snippet is the saved source of a past execution: "The model does not promote its own code. Your application reviews an execution and calls `runtime.saveSnippet()`". The model then finds it with `codemode.search()`, reads it with `codemode.describe()` and runs it with `codemode.run(name, input)`. A snippet records the connector set it was written against (`how-it-works.mdx:294-313 @ f425a80`). Intermediate results are not written anywhere the model can browse. The sandbox has no file system unless the developer adds one as a provider, such as the `workspace` namespace from `@cloudflare/computer` (`packages/codemode/README.md:607-634 @ 22af015`).

**F19. READ.** Errors are shaped for the model's next attempt:

- A sandbox `ReferenceError` such as `host is not defined` has the real globals appended, "so the retry is informed instead of another guess" (`src/proxy-tool.ts:717-727 @ 22af015`).
- A failed API request names the method, path, HTTP status and Ray ID, followed by the body as the API sent it and the server's explanation of the 401, 403 or 429 (`cloudflare/mcp src/tools/execute.ts:341-361 @ b8602d6`).
- A rate-limited run says how long to wait and tells the code to "stop instead of catching and continuing" (`:613-622`).

### 7. Failure modes and criticism

**F21. READ unless marked.** Where Cloudflare's own sources and the secondary commentary show code mode to be worse, harder, or costlier:

1. **Nested code mode.** A client that already runs its own code mode gains nothing from a code-mode server and loses the direct tools. Both Cloudflare servers grew opt-outs, `?codemode=false` on the API server (`cloudflare/mcp README.md:50-66`) and `?codemode=off` on portals. Portals refuse upstream servers that have code mode on (`mcp-portals.mdx:860-864`). The API server's direct mode returns whole results, uncapped, because "The clients that disable it usually run code mode themselves" (`README.md:83`).
2. **Approval granularity.** A person approves a whole code blob (the API server's `execute`, `destructiveHint: true`) or one method name (the runtime). The arguments a computed call will carry are known only at run time, and argument-aware approval is an open issue (#2134). The secondary excerpt about Claude Code's classifier makes the same point: a reviewer of generated code "does not see values computed at run time".
3. **Determinism tax.** Durable approval needs replayable code. Parallel calls, clocks and randomness must be avoided or wrapped (F17). This conflicts with the parallelism that code mode is praised for.
4. **A lossy, mostly untyped API.** See F5. Output types are `unknown` across the MCP path.
5. **Search quality and cost.** In-sandbox search is lexical over names and descriptions (#2296). Server-side search is a full scan of the spec by model-written code, in a fresh isolate, on every call, and it has hit memory limits on large specs (#2596).
6. **A prompt-injected run can do anything the token can.** The token is hidden, but hiding it does not narrow it (F14). Cloudflare's mitigations are host-side: a host allowlist, a spending-policy guard and scope challenges.
7. **Secondary (search excerpts):** Speakeasy calls a code-mode MCP server "for most companies, a feat of over-engineering" and places code mode at the gateway instead. A Ben-Gurion University paper on MCP-Bench is summarized as finding lower token use and latency but "a vastly expanded attack surface". A DEV post argues that a query-shaped interface needs no sandbox where code does.
8. **INFERRED.** Every execution pays for an isolate: a spawn, a fresh `JSON.parse` of the 27 MB spec per search, and a billed Dynamic Worker for each `load()` (F10). A discovery pass followed by an action pass is two model round trips and two isolates. That is still fewer round trips than one tool call per step, which is the point of the design.

## What this means for a vfs code mode

Everything in this section is INFERRED from the findings above, from the README, from AGENTS.md ("Production posture", "The reference deployment") and from the drafted specs 167, 170 and 171 under `context/specifications/active/`.

### Adopt

1. **A fixed-size tool description whatever the catalog holds.** The decisive part of Cloudflare's design is not TypeScript. It is that the model's context pays a constant cost, about a thousand tokens, while the catalog grows to thousands of operations (F2, F9). Spec 171's `cli` tool should name the grammar, the verbs and the paths where tools live, and list no tool. Cloudflare's rule that tool metadata must not vary by user (F15) applies to vfs too: MCP clients cache tool lists, so the `cli` description must be identical for every caller.
2. **Discovery in the model's own working language, over the catalog as data.** Cloudflare's production `search` is literally "write code that filters the spec" (F7), and its portal offers a regex over names, descriptions and schemas (F8). vfs gets this without a second tool. Manifests at `/.vfs/mcp/<server>/tools/<tool>` are files, so `grep -rl dns /.vfs/mcp/cloudflare/tools`, `glob`, `cat` and ranked `search "create a DNS record" /.vfs/mcp` are the discovery surface.
3. **Bounded, structurally truncated results, with a way to keep the whole result.** Cloudflare caps a result at about 6,000 tokens with valid-JSON truncation markers, and offers `truncate: false` for results bound for a file or pipe (F16). vfs's plan is better shaped: spec 170 writes call results to `/.vfs/run/<call-id>/<i>`, so the cap limits only what is printed, the rest stays addressable by path, and a pipe gets the whole value. Adopt Cloudflare's marker convention, one recognizable string the model can find, in vfs's render budget.
4. **Credentials at the door, never in the language.** Cloudflare keeps tokens host-side and injects them at the egress, which is either the connector or `GlobalOutbound` (F14). vfs's shell runs no foreign code and has no network, so the equivalent is that an MCP connection's credentials live in the `McpView` connection owner, the one task per server of spec 170 §3.3. No verb, file or `stat` should surface them.
5. **Model-actionable errors.** Two of Cloudflare's patterns carry over directly: an unknown name gets the list of real names (F19), and an API refusal names the operation, the status and the missing permission. In vfs, `command not found` should name the nearest programs and the `which` or `search` command that finds tools. A `permission` error on a tool should name the rung it needs.
6. **Replay safety computed from what ran.** Cloudflare records whether every request in a failed run was a read or refused before it offers a retry (F15). vfs knows each verb's rung from one table, so after a failed pipeline it can say exactly which steps mutated and whether re-running is safe. That is cheaper and more exact than Cloudflare's GET-or-refused heuristic.
7. **Host-side pacing of a loop.** Cloudflare's sandbox paces its own outbound requests: 20 in flight, retries, a wait budget, and a stop after 1,000 unsent (F13). A vfs pipeline that fans one tool call out over 10,000 rows is a supported batch size under "Production posture", and needs the same bounds at the `_invoke` door, per pipeline and per server.
8. **Promotion of agent-written programs by a person's act.** Cloudflare's snippets are saved only by the application, and are searchable and runnable by name thereafter (F18). vfs's programs and bin union (spec 169) can make promotion a grant rather than an API call: writing into a stored program directory needs `add` or `contribute` there, and a program is found by the same `search` as anything else.

### Do differently, because the language is a shell over a governed namespace

1. **No isolate per call, because no foreign code runs.** Cloudflare needs a fresh V8 isolate per execution because the model writes general JavaScript (F11, F13). vfs's shell is a parsed grammar dispatched to verbs (spec 167). The parser is the sandbox: a construct it does not admit is refused before anything runs. There is no spawn cost, no per-isolate bill and no 4-or-10 concurrency ceiling. At the reference deployment's 150,000 agent calls a day, this matters only as latency and simplicity, but both are real.
2. **Index the catalog; never scan it per call.** Cloudflare's server-side search is a full scan of a 27 MB spec in a fresh isolate on every call (F7). AGENTS.md rules that out for vfs: "A read must cost in proportion to what it returns, never to the corpus." The tool catalog is just more rows in the index. Ranked `search` should index each tool's name, description **and** parameter names and descriptions: Cloudflare's in-sandbox ranker indexes only the first two (F6), and its portal found schemas worth searching (F8).
3. **Never list a large catalog flat.** A names-only index of the Cloudflare API is about 84,000 tokens (F9). An MCP server projected into `/.vfs/mcp/<server>/tools/` with thousands of entries must group them (by tag, the spec's 725 products) or page them, and `ls` of the directory must respect the render budget and say how many entries were withheld.
4. **The caller's authority survives the hop.** Cloudflare's SDK has no caller identity at the call boundary (F15). vfs judges every call against the caller's `Authority` with row-level grants: "who may call a tool is who may read its entry" (spec 170, Intent). Two further steps keep that honest. The upstream credential an `McpView` uses should be per user where the upstream supports it, as the Zero Trust portal does with per-user OAuth (F15). And the catalog a caller can `ls` and `search` is already filtered by grants, which is what Cloudflare can only do in discovery results and never in tool metadata.
5. **Flags, not types, as the generated API.** Spec 170 §2 maps JSON Schema onto `--flag value`, with `--json` for whole objects and `--help` rendering one line per property. That is a weaker type surface than Cloudflare's TypeScript for nested shapes (F3), but it is lossless in a way Cloudflare's is not. `--help` can print every constraint the schema holds, the ones F5 shows TypeScript dropping, because it renders the schema rather than translating it.
6. **Results are files, so state is searchable.** Cloudflare keeps an audit log the model never sees, and caps a stored value at 1 MB with advice to write large data to a file (F17), a file system the sandbox does not have by default (F18). vfs results under `/.vfs/run/` are the file the advice asks for, and they can be grepped and searched later like anything else.
7. **Approval keyed on the rung and the arguments, at the door.** Cloudflare's abort-and-replay makes approval durable at the price of determinism (F17), and its approval is per method (F21.2). vfs's door sees each call with its computed arguments and its rung. A pending approval can be a row carrying both, and the pipeline can stop before the call rather than re-run from the top. Whether vfs needs durable resume at all is a design question this study does not settle.

### Where Cloudflare is stronger, and vfs would be weaker

1. **General computation.** JavaScript gives loops, maps, joins, JSON reshaping, error handling and `Promise.all` in one execution. A bash-shaped grammar over verbs gives pipes and the programs that exist. Work that needs real logic between calls, such as "for each zone, if the plan is free and the DNS has no CAA record, add one", is one execution in Code Mode, and in vfs is either several calls or a stored program.
2. **What models have been trained on.** The models' prior is strong for both JavaScript and bash. JSON Schema rendered as TypeScript declarations is closer to the code a model has read than a schema rendered as flags, especially for nested request bodies (F3), which vfs pushes to `--json`.
3. **A proven isolation primitive for untrusted code.** If vfs ever admits a general scripting language beside the shell, it needs something like Dynamic Workers: no network by default, bindings as the only authority, CPU and subrequest limits, outbound interception with per-sandbox props (F10). vfs has no equivalent today and should not pretend the shell's parser extends to a language.
4. **Durable approvals with rollback.** Abort and replay survives hibernation and requests. Rollback by per-tool `revert` is a worked answer to "undo what the agent did" across external systems (F17). vfs's trash and restore cover its own rows, not side effects in an upstream MCP server.
5. **Production hardening around one vendor API.** Rate-limit pacing, scope step-up, refusing empty lists that prove nothing, a guard against spending money (F13, F15). These are upstream-specific and will not come for free from a generic MCP projection. vfs would need a per-server policy hook to match them.

## What this study does not settle

- The blog posts were not read on the page, because the network policy blocked every Cloudflare web host and mirror. Their claims here are search-engine excerpts, so their wording, any workload behind the 81% figure, and any accuracy data they may contain are unverified. Re-reading them needs `blog.cloudflare.com` allowed in the session's network settings.
- No independent measurement exists in these sources of task success, latency or total tokens per task for code mode against direct tool calling, on any model size. The one in-repo LLM test is a smoke test.
- The size of the TypeScript that the codemode renderer produces for the whole Cloudflare catalog, and the ranker's precision on real queries, were not measured. Running the package's code from the clone was refused in this session. A measurement would need the package installed from npm into an isolated experiment directory.
- The bodies of the cited GitHub issues were not read; only their titles were.
- Whether a bash-shaped grammar gets models to compose multi-step tool work as reliably as JavaScript does is an empirical question for an evaluation, not for prior-art reading.
- Whether vfs needs durable, resumable approval (Cloudflare's abort-and-replay) or only a stop-before-the-call gate.

## One line

Cloudflare's Code Mode wins by keeping the catalog out of the context: one fixed-size tool, discovery as code over the catalog as data, credentials injected outside a no-network isolate. vfs can take all three with no isolate, because its language is a grammar rather than code, and do better on two of them: an indexed, grant-filtered catalog of files instead of a per-call scan, and the caller's own authority on every call. It stays weaker at general computation between calls.
