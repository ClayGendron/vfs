# 03: open-source code mode implementations, side by side

## The question as this study received it

The open-source implementations of code mode for MCP that appeared after Cloudflare's post (https://blog.cloudflare.com/code-mode/, published 2025-09-26; studied in its own right by another study in this folder), compared side by side. Required subjects: UTCP's `code-mode` library with the UTCP specification in brief, `jx-codes/lootbox`, `portofcontext/pctx`, `RhysSullivan/executor` (now `UsefulSoftwareCo/executor`), `steipete/mcporter` (now `openclaw/mcporter`), and the code mode in `block/goose`; plus at most three more well-used projects, ranked by adoption. For each: the language the model writes, how schemas become an API, discovery, execution and isolation, credentials, result handling, limits, measured evidence and maturity. One comparison table across the brief's seven points, per-project findings with `path:line @ commit` citations, a note on which designs expose tools as files or as CLI commands (because the vfs code mode calls tools through a bash-shaped CLI with tools stored as searchable files), and the field's consensus and splits.

The three additional projects chosen, by adoption recorded on 2026-11-23 (READ, GitHub repository pages): FastMCP's `CodeMode` transform (PrefectHQ/fastmcp, 28.7k stars, 2.6k forks), mcp-use's code mode (mcp-use/mcp-use, 11.0k stars, 1.6k forks), and OpenCode's `@opencode-ai/codemode` interpreter (in anomalyco/opencode, 228.8k stars for the whole repository; the package is also the engine executor runs on, which is why it is included). A web search result attributed 52,841 weekly npm downloads to `@opencode-ai/codemode` via socket.dev; socket.dev was unreachable from this session (network policy), so that figure is unverified. npm and PyPI download APIs were also unreachable, so no download counts were measured here.

### 2. UTCP code-mode: a V8 isolate with synchronous tool stubs, and a CLI recommended over its own MCP server (READ, one EXECUTED)

UTCP itself is a "manual" format telling an agent how to call a tool over its native protocol (HTTP, CLI, MCP, file) "no wrapper servers required" (READ: `docs/index.md:13,25 @ 4a9ed93`); a manual's tools carry `tags` and the client's default search strategy scores tag matches at 3.0 and description-word matches at 1.0, and "Tools with zero score are included in results (ranked last)" (READ: `docs/api/core/utcp/implementations/tag_search.md:15-39 @ 4a9ed93`).

Call surface (READ): `toolToTypeScriptInterface` turns each tool's `inputs` and `outputs` JSON Schema into a TypeScript `namespace <manual> { interface <tool>Input {...} interface <tool>Output {...} }` with each property's `description` as a JSDoc comment and an "Access as: manual.tool(args)" line (`typescript-library/src/code_mode_utcp_client.ts:106-154 @ e5fdc31`). Identifiers are sanitised by replacing every non-alphanumeric character with `_` (`:93-97`). Inside the isolate each tool is a synchronous function that blocks on `__callToolRef.applySyncPromise` until the host's async call settles (`:475-482`), so the model may write `github.get_pull_request({...})` with or without `await` (`:36`).

Execution (READ): `callToolChain(code, timeout = 30000, memoryLimit = 128)` builds a new `ivm.Isolate({ memoryLimit })` per call (`:180-189`), wraps the model's code as the body of an async function, and compiles it with `isolate.compileScript` (`:274-302`). A long comment documents a production failure: a tool call that never settles parked the isolate's OS thread "FOREVER", leaking one native thread per call "until the process hits a pid/thread limit"; the fix races every bridged call against an end-of-chain promise (`:192-236`), and landed in commits dated 2026-08-25 ("callToolChain: never let a tool call pin an isolate thread"). The MCP server's `call_tool_chain` passes `code` and `timeout` only, so its isolates always get the 128 MB default, and it truncates the JSON reply at `max_output_size` (default 200,000 characters) (`code-mode-mcp/index.ts:281-299 @ e5fdc31`). The Python edition compiles with RestrictedPython and runs the result with `exec` in a thread pool under `asyncio.wait_for` (`python-library/src/utcp_code_mode/code_mode_utcp_client.py:22,288,336 @ e5fdc31`).

TypeScript is not transpiled (READ and EXECUTED): the library has no dependencies besides `@utcp/sdk` and `isolated-vm` (`typescript-library/package.json:46-50 @ e5fdc31`) and no transpile step in its source. The experiment wraps three bodies exactly as such a library would and compiles them with Node's V8: plain JavaScript returns `1`; `const r: { n: number } = ...` fails with "SyntaxError: Missing initializer in const declaration"; an `interface` line fails with "SyntaxError: Unexpected identifier 'R'" (`experiments/03-open-source-code-mode/output.txt`). INFERRED: `isolated-vm` compiles with the same V8, so a model that follows the "Execute TypeScript code" description (`code-mode-mcp/index.ts:283`) and writes a type annotation gets a syntax error; the generated TypeScript interfaces are documentation only.

Discovery (READ): the MCP server exposes seven tools: `register_manual`, `deregister_manual`, `search_tools` (task description, limit 10), `list_tools`, `get_required_keys_for_tool`, `tools_info` and `call_tool_chain` (`code-mode-mcp/index.ts:140-292`). Inside the sandbox, `__interfaces` holds every interface and `__getToolInterface(name)` one (`code_mode_utcp_client.ts:512-530`).

The shell turn (READ): the README now says the `utcp` CLI is "the **preferred** way to use Code Mode" for any agent with shell access, and "Use the **MCP server** (below) only for MCP-only clients like Claude Desktop" (`README.md:125,146 @ e5fdc31`). The CLI prints JSON to stdout for every command (`code-mode-cli/index.ts:4-6`), offers `search`, `list`, `info`, `keys`, `run` (code on stdin or `-c`), `login` and `validate` (`:317-360`), and the agent configures it by writing `.utcp_config.json` itself (`:96-120`).

Credentials (READ): variables such as `${NOTION_TOKEN}` are substituted into call templates host-side, outside the isolate; the CLI's `login` "writes the token to `.env`" in the working directory, and "UTCP injects it on every call afterwards" (`code-mode-cli/index.ts:144,154,170`; `code-mode-cli/README.md:55`). INFERRED: the isolate never sees the token, but the agent's own shell, which runs `utcp`, can read `.env`.

Evidence (READ): the README's benchmark table is a third party's (`README.md:25-36`). That benchmark ran Claude 3 Haiku on 8 accounting scenarios in a RestrictedPython sandbox and reports 144,250 vs 45,741 tokens (68.3% fewer), 11.88 s vs 4.71 s average latency, 8 vs 1 round trips, and success 6/8 vs 7/8 (https://github.com/imran31415/codemode_python_benchmark, 44 stars). It is the benchmark author's own run on a tiny workload, not independently reproduced.

### 3. lootbox: tools and reusable scripts as TypeScript files, run by a CLI (READ, public documents only)

lootbox describes itself as "inspired by 'Code Mode'" and was first committed on 2025-09-29, three days after Cloudflare's post (README.md:21-23 at 587a5a1; first-commit date from `git log` before the clone was deleted). A tool is any exported function with zero or one object parameter in `.lootbox/tools/<ns>.ts`; types are extracted with ts-morph and prefixed by namespace (`Kv_GetArgs`) (README.md:86-99, 464-507, 636-641). External MCP servers are configured in `lootbox.config.json` and appear as `tools.mcp_<servername>`, marked "WIP may not work properly with all mcp servers" (README.md:309-353).

The model drives it from the shell: `lootbox tools` lists namespaces, `lootbox tools types kv,sqlite` prints types, `lootbox exec '<code>'`, `lootbox script.ts` or `cat script.ts | lootbox` runs a program (README.md:73-112, 281-307). A program's output is what it prints: "Do not return from scripts always log what you want to see" (LLM_QUICK_START.md:93-99). Reusable programs are files in `.lootbox/scripts/`, documented by JSDoc `@example` lines, listed by `lootbox scripts`, and fed with `stdin().json()` (README.md:159-241); the opening pitch is that a script becomes a new tool: "It's tools all the way up" (README.md:10-15).

Isolation (READ): "User scripts run in separate Deno processes", "Scripts only have `--allow-net` access", "10-Second Timeout"; tool functions "Run with `--allow-all`"; "No Authentication: Designed for localhost use" (README.md:629-650). INFERRED: the program has open network egress, so the sandbox does not stop exfiltration; the type-check claim ("the sandbox will reject any scripts that don't pass", LLM_QUICK_START.md:113) was not verifiable without the source.

### 4. pctx: a Rust server with a type-checked Deno-core runtime and a bash-explorable tool tree (READ)

Disclosure modes (READ): `ToolDisclosure` has three values: `Catalog` ("list_tools -> get_tool_details -> execute_typescript", the default), `Filesystem` ("execute_bash -> execute_typescript") and `Sidecar` ("original tool descriptions -> execute_typescript") (`crates/pctx_config/src/lib.rs:149-161 @ 499379d`; `docs/code-mode.md:73-109`).

Tools as files (READ): in filesystem mode pctx renders every tool into an in-memory map of paths: `/sdk/<Namespace>/<fnName>.d.ts` holds the input type, output type and `export async function` signature with the tool's description as a docstring, and `/sdk/README.md` is a "Token-efficient README. Shell-doc style: one .d.ts path per line under each namespace section" with the first line of each description, lowercased (`crates/pctx_code_mode/src/code_mode.rs:313-375`). `execute_bash` hands that map to just-bash (an in-process bash interpreter over a virtual filesystem) with `cwd: "/sdk"` and returns `{exit_code, stdout, stderr}` (`:517-589`). The tool description tells the model to `ls`, `cat README.md`, `grep 'keyword' README.md`, then `cat {Namespace}/{functionName}.d.ts`, says networking commands are unavailable, and calls the tree "a READ-ONLY virtual filesystem for SDK exploration" (`crates/pctx_code_mode/descriptions/tools/execute_bash/v1.txt @ 499379d`). INFERRED: this is the closest prior art to the vfs design, with one split vfs does not have: the shell only reads the catalog, and calls happen in a second language (TypeScript) through a second tool.

Schema to API (READ): tool names become camelCase function names (`crates/pctx_codegen/src/tools.rs:139`) and `ts_fn_signature` emits types, a docstring and `export async function f(input: T): Promise<U>`, with `input = {}` when every field is optional (`:226-246`); each MCP server becomes a TypeScript namespace (`docs/code-mode.md:111-119`).

Execution (READ): code is type-checked first by a TypeScript compiler held in a V8 snapshot (the bundled `typescript.min.js` reports version 5.3.3; `crates/pctx_type_check_runtime/build.rs:3`), then transpiled with `deno_ast` and run in a bare `deno_core::JsRuntime` with a `NoopModuleLoader`, because "a filesystem loader would let sandboxed code read arbitrary files from the host" (`crates/pctx_executor/src/lib.rs:354-397`). Tool calls leave the sandbox through one op, `op_invoke(id, arguments)`, which calls the host registry (`crates/pctx_code_execution_runtime/src/invoke_ops.rs:13-26`). The default timeout is 120 s, enforced by a watchdog thread that calls `terminate_execution` plus a `tokio` timeout for scripts idling on a promise (`crates/pctx_executor/src/lib.rs:38,428-480`). No heap limit is set (no `create_params` in any crate; EXECUTED: `grep -rn create_params crates` found none).

One mutex for every execution (READ): "Process-wide mutex to serialize all V8 isolate creation and usage", acquired by `execute()` "for the entire operation (type check + execution)" (`crates/pctx_executor/src/lib.rs:23-33,159-161`). INFERRED: a pctx process runs one program at a time, including while that program waits on upstream MCP calls; at the reference deployment's peak of about 20 verb calls a second, any program lasting more than about 50 ms queues every other caller.

Documentation drift (READ): `docs/code-mode.md:32,49-52` says type checking uses "typescript-go" and code runs with a "10-second timeout" and "Network restricted to configured MCP hosts only"; the code bundles the JavaScript TypeScript compiler, defaults to 120 s, and the runtime has no fetch at all (the `allowed_hosts` argument survives only in a doc comment, `crates/pctx_executor/src/lib.rs:333`). The README's "98.7% reduction in tokens (150k → 2k)" is the example from Anthropic's post, not a pctx measurement (`README.md:121-137`).

Credentials and results (READ): upstream servers are authenticated by pctx from `${env:VAR}`, `${keychain:...}` or an external command, and "LLMs can never see your auth" (`README.md:146-150`; `docs/config.md:138,461,479-485`). `execute_typescript` returns `{ success, stdout, output, diagnostics }` (`docs/code-mode.md:85`). The Python SDK adds `search_functions(query, k=10)`, ranked client-side with the `bm25s` library (`pctx-py/src/pctx_client/_client.py:219-250`).

### 5. executor (v2): six MCP tools, BM25 in Postgres over permitted rows, an interpreter that can suspend for approval (READ)

Shape (READ): the shared MCP package implements `skills`, `search`, `describe`, `call`, `execute` and `resume` (`packages/mcp/README.md:3-9 @ f8bfb8e`); the repository README still says agents get "two tools, `skills` and `execute`" (`README.md:29-31`), so the README lags the code. Each app appears once under `tools[appSlug]`; "Calls never choose accounts" and a tool input with its own `$accounts` key fails before the tool runs (`packages/mcp/README.md:86-100`).

Search (READ): "Tool search over listings kept as rows: Okapi BM25 over the words of each tool, its routers and its target's labels" (`packages/sdk/src/implementation/tool-search.ts:1-3`); words are split on camelCase and snake_case and a plural `s` is stripped (`:26-41`); input property names and descriptions are indexed too (`:43-60`). The ranking runs as SQL in Executor's own Postgres with `k1 = 1.2, b = 0.75` (`packages/sdk/src/implementation/tool-search-store.ts:2,108,404-408`), and "Statistics count the rows the scopes permit": the BM25 document frequencies and average length are computed over the caller's permitted rows, ranking and reading the page are "one statement, so they read one snapshot" (`:364-372`). A search page holds at most 25,000 UTF-8 bytes of JSON and returns a `next` cursor (`packages/mcp/src/contracts/execute.ts:514-515,547-549`). INFERRED: this is the only project studied whose tool catalog is a database table searched in SQL under per-caller authority, which is the shape vfs already has.

Execution (READ): the model's program runs in `@opencode-ai/codemode` (finding 10), imported at `packages/mcp/src/contracts/execute.ts:2`; "Every product runs authored apps and workflows in workerd, never in the host Node process", Dynamic Workers in the cloud (`DEVELOPMENT.md:175-177`). Before running, executor statically scans the program to load only the apps it names (`packages/mcp/src/implementation/execute.ts:728,1714-1719`). Limits are server-controlled: 5 minutes, 100 tool calls (`contracts/execute.ts:504-513`), 65,536 code characters, 64 live executions, discovery fan-out 8 with 10 s and 5 s waits (`:15-38`); and "Executor sets no limit on the size of a result" (`:500-502`).

Approvals and state (READ): each tool's policy decides when to ask first, "always, never, or only when the input looks risky" (`README.md:32-34`); an approval-required call suspends the program, and the model is told to "call resume with their answer; never run the program's source again", because "External effects are not rolled back on error or cancellation" (`contracts/execute.ts:518-520`). In native mode the MCP client's own prompt answers, and `call` is annotated destructive and open-world so the client confirms each one (`:580-597`). Agent-written apps are deployed as immutable versions that can be rolled back, and skills are ordinary app files read through the `skills` tool (`README.md:35-37`; `packages/mcp/README.md:43-47`).

A direct-call escape hatch (READ): `call` runs "one {path, input}" or an array of independent calls; "Use execute instead when one call's output feeds another, or to filter a large result" (`contracts/execute.ts:567-578`), and `execute`'s description says "for one or a few independent calls, use call instead" (`:520`). `git log -S` dates the `CallTool` definition to 2026-10-12 (EXECUTED). INFERRED: the most elaborate code-mode product in the set now routes simple work away from code.

### 6. mcporter: every MCP tool as a shell command, signatures as TypeScript text, no sandbox (READ)

Call surface (READ): `mcporter call` accepts flag style (`--issue-id LNR-123`, `key=value`, `key:value`) and function-call style (`'linear.create_comment(issueId: "LNR-123", body: "Hi")'`), sharing one validation pipeline (`docs/call-syntax.md:9-17 @ aa8d0c5`). Kebab-case flags become camelCase keys, `key=@path` reads a file's text, `--json -` reads a JSON object from stdin, bare strings wrap into one-item arrays when the schema says array, and numeric-looking values stay strings when the schema says string (`:71-80`). Unknown tool names get Levenshtein suggestions (`src/cli/identifier-helpers.ts:25,77`).

Signatures (READ): `mcporter list <server>` prints each tool as a TypeScript declaration with `@param` lines; more than two optional parameters are hidden behind `// optional (N): ...` unless `--all-parameters` is passed; return types come from output schemas, and unknown outputs omit the type rather than print `unknown` (`docs/call-syntax.md:21-45`). `emit-ts` writes the same data as a `.d.ts` or a typed client (`docs/emit-ts.md:8-29`).

Tools as CLI commands (READ): `generate-cli` produces a standalone CLI for one server where "Tool schemas become subcommands and schema fields become positional arguments or flags", `isError: true` exits with status 1, the default call timeout is 30 s, and `--include-tools` and `--exclude-tools` narrow it (`docs/cli-generator.md:8-24,61-64`). The project advises "one small skill per MCP server or workflow instead of a single generic `mcporter` skill", because a generic one "recreates the large-schema context problem" (`docs/agent-skills.md:10-13,52-57`).

State and credentials (READ): schemas are cached as files at `$XDG_CACHE_HOME/mcporter/<server>/schema.json`, and OAuth tokens land in `credentials.json`, "plaintext JSON by default", with opt-in JWE encryption keyed by `MCPORTER_VAULT_PASSWORD` (`docs/config.md:32,54-55,304`). INFERRED: there is no isolation layer at all; the agent's real shell runs the command with the agent's permissions, and the token file is readable from that shell unless encryption is on.

### 7. goose: Boa per call, string-named tools, and a vendor that measured and said where it does not help (READ)

Call surface (READ): three tools, `list_functions`, `get_function_details` and `execute_javascript` (`crates/goose/src/agents/platform_extensions/code_execution.rs:248-249 @ 059fee2`); the instructions say to call `await tools.call("extension__tool_name", { ... })`, "no imports or generated namespaces are needed", and the context has "no filesystem, shell, network, packages, or environment access" (`:25`). `get_function_details` returns the "original JSON input/output schemas", not generated types (`:249`); listed descriptions are cut to their first line and 240 characters (`:266`).

Design churn (READ): the February 2026 post describes an earlier interface where the model had to "import tools from modules like `import { shell } from \"developer\"`" and discover them with `search_modules` and `read_module` (`documentation/blog/2026-02-06-8-things-you-didnt-know-about-code-mode/index.md:179-184`); the current code replaced generated module namespaces with one `tools.call` taking a string name. INFERRED: the vendor moved away from per-tool generated APIs toward a single dispatcher.

Execution (READ): Boa, a pure-Rust JavaScript engine, with an idle module loader, a 2,000,000-instruction budget ("Unlike per-loop limits, it also bounds synchronous promise continuations"), a 100,000 loop-iteration limit, recursion 128, a 1,000,000-byte output limit and a semaphore of 4 worker slots (`crates/goose/src/agents/platform_extensions/javascript.rs:27-31,221-233`); the wall-clock bound is the extension timeout (`code_execution.rs:146-150`). Tool calls "retain the extension lease, permission flow, cancellation, and mutation handling", only text results reach the script, and "JavaScript state is discarded between calls" (`documentation/docs/guides/managing-tools/code-mode.md:42-43,71-79`). The `pctx` README lists Block as a user (`/home/user/pctx/README.md:20-24`), but goose at this commit has no pctx dependency; its code mode is the `code-mode` cargo feature on `boa_engine` (`crates/goose/Cargo.toml:23,249`).

Evidence (READ, vendor's own, one run each): fixing one goose bug and opening a PR with Claude Opus 4.5 took 23,339 total tokens with code mode and 33,648 without, "30% fewer" (`2026-02-06-8-things.../index.md:19,66-71,177`); a five-call task with eight extensions used 16% of the context window without code mode and 3% with it (`documentation/blog/2025-12-21-code-mode-doesnt-replace-mcp/index.md:67,71`). The same posts state the limits: "Code Mode doesn't necessarily speed up task execution; in fact, I noticed additional round-trips" (`2025-12-21.../index.md:79`), and "For simple, single-tool tasks, this overhead is not worth it" (`2026-02-06.../index.md:197`); models that skip discovery "guess, leading to hallucinated tool names" (`:183`).

### 8. FastMCP CodeMode: Python in Monty, staged discovery, auth carried through (READ)

Shape (READ): a server-side transform that replaces every tool with `search`, `get_schema` and `execute`; inside `execute`, `call_tool(name, params)` is "the only function available" (`docs/servers/transforms/code-mode.mdx:28-47,55-115 @ ca0de0d`). Search is BM25 by default and replaceable with `search_fn`; results say "2 of 10 tools:" when partial; three detail levels go from names and one-liners through compact markdown with types, literals and one level of nested field names, to the full JSON Schema (`:120-162`). The documentation names the trade-off "tokens vs. round-trips" and reports "our experience is that staged discovery leads to better results. Flooding the LLM with detailed schemas for tools it doesn't end up using can hurt more than the extra round-trip costs" (`:53,192`).

Authority (READ): "the catalog is request-scoped — different users may see different tools based on auth" (`:260`), and each `call_tool` re-reads the auth-filtered catalog and dispatches through `ctx.fastmcp.call_tool`, "with the same authorization checks as a normal tool call" (`fastmcp_slim/fastmcp/experimental/transforms/code_mode.py:748,754`; `code-mode.mdx:302`).

Execution and limits (READ): `MontySandboxProvider` (pydantic's Rust implementation of a Python subset) with a baseline of 30 s and 100 MB (`code-mode.mdx:306-316`; `code_mode.py:168-169`); 50 tool calls per `execute` by default and an optional wall-clock bound because "Sandbox duration limits exclude time spent awaiting host callbacks" (`code_mode.py:664-665,763-764`). A comment records that "Monty currently leaves Python callbacks running when a sandbox exits" (`code_mode.py:238-239`).

### 9. mcp-use code mode: the most adopted SDK, the weakest isolation (READ)

Shape (READ): the client gains `execute_code` and `search_tools`, and code calls `server.tool_name()` (`libraries/typescript/packages/client/src/code-mode/connector.ts:185-214 @ 8ff4b86`). `search_tools` lowercases the query and keeps tools whose name, description or server contains it as a substring (`code-mode/executor.ts:145-190`).

Isolation (READ): the default TypeScript executor runs `new vm.Script(...).runInNewContext(context, { timeout })` (`code-mode/executor-vm.ts:228-233`), documented as "Local Node.js VM — fast, trusted environments", with E2B's cloud sandbox for "untrusted code" (`docs/typescript/client/code-mode.mdx:51-52`). The VM executor stores `memoryLimitMb` and never uses it (`executor-vm.ts:163,168`; EXECUTED: `grep memoryLimitMb` finds only those two lines). The Python executor calls `exec(compiled_wrapped, namespace)` with a hand-built `safe_builtins` dictionary (`libraries/python/mcp_use/client/code_executor.py:124,136-178`). INFERRED: Node's own documentation states `node:vm` is not a security mechanism, and curated-builtins `exec` is escapable through object introspection; neither was exploited here.

### 10. OpenCode CodeMode: an owned interpreter, resumable runs, hooks on every host call (READ)

Design (READ): "a lightweight, pure interpreter for a JavaScript-like language built around calling tools"; "Rather than trying to sandbox arbitrary JavaScript, CodeMode only runs the language features we implement. Programs cannot directly access the network, filesystem, processes, or application APIs" (`packages/codemode/README.md:3-9 @ e1fb08a`). Unfinished async work is interrupted at the end, the last expression is the result, and unsupported syntax returns `UnsupportedSyntax` with a location (`:14-25`).

Host boundary (READ): arguments cross as copies, never shared, then become JSON next to the tool's schema (`:111-116,258-262`); `tool.before` hooks receive `{ name, input, key }` and "a failing one denies it: the host function is never called" (`:103-109`); "Descriptions and schemas are model-visible contracts. Authorization belongs in `execute`" (`:69`).

Suspend and resume (READ): a run can be suspended to a JSON snapshot and resumed "later, in this process or another one built from the same version"; plain tools block suspension while running, `Tool.idempotent` calls are rerun with the same key, and `Tool.durable({start, wait, cancel})` work continues across a suspend (`:118-219`). This is the mechanism executor's approvals stand on (finding 5).

Discovery, results, limits (READ): `runtime.catalog()` gives path, description and generated TypeScript signature; the built-in `search()` supports exact path, namespace scope, empty-query browsing and pagination, and counts toward `maxToolCalls` (`:386-396`). Every run returns `{ok, value, logs, warnings, truncated, toolCalls}`, with eleven diagnostic kinds (`:340-384`). `timeoutMs`, `maxToolCalls` and `maxOutputBytes` "have no default values", and boundary data is limited to 32 nested levels (`:398-411`).

## What this means for a vfs code mode

All of this section is INFERRED from the findings above.

The field's consensus, in plain words. First, show the model a handful of meta-tools, not the catalog: one way to run a program, and a way to find and then read a tool's contract. Second, find before you read: the cheap listing (name plus one line) comes first, the full signature only for tools the model picked. Third, the contract the model reads is a typed signature with prose: six of nine projects render JSON Schema as a TypeScript declaration with JSDoc, even where the model writes untyped JavaScript. Fourth, namespace tools by their server: `server.tool`. Fifth, keep secrets on the host and let the sandbox hold only a way to ask the host to call. Sixth, return only what the program returns or prints, bounded by a timeout. These six recur in most of the projects, so a vfs code mode that drops one should say why.

Where the field splits. The engine splits three ways: a real V8 isolate (UTCP, pctx), an owned or embedded interpreter (OpenCode, goose's Boa, FastMCP's Monty), or the agent's own shell with no sandbox (mcporter, UTCP CLI, lootbox in a subprocess). Search splits between BM25 and simple matching. Authority splits between "the host process is trusted" and "each call is judged as the caller" (executor, FastMCP, goose). Approvals exist in three projects only. The newest movement runs away from pure code: executor added a direct `call` tool in October 2026, goose and FastMCP document that single-tool tasks are slower in code mode, and UTCP now tells shell agents to use its CLI rather than its MCP server.

What that says about the vfs shape. vfs's design (the vfs shell as the language, tools and MCP servers as files under `/.vfs`, found with the same `ls`, `grep` and `search` as anything else) sits on the side of the shell-and-files designs, and several of its pieces already exist separately in the field. pctx's filesystem mode shows a model exploring tools as `.d.ts` files with `ls`, `cat` and `grep`; lootbox and mcporter show tools as CLI commands and scripts as reusable files; executor shows tool search as BM25 in a database under per-caller statistics. No project combines them: in pctx the shell reads the catalog and a second language calls the tools; in mcporter the shell calls the tools but has no catalog search; in executor the catalog is a database but the language is JavaScript. A vfs shell that both browses the catalog and runs the call, against a catalog that is the same permission-judged namespace as the data, would be the first to put discovery, execution and authority behind one surface. That is the differentiator; it is also unproven, because no project here measured anything that compares a shell-only surface with a JavaScript one.

Concrete design inputs, each from a finding. (a) The file a tool lives in should read like a signature: mcporter's TypeScript-style declaration with `@param` lines, a hidden-optional summary and an examples block (finding 6), or pctx's one-line README index plus one `.d.ts` per tool (finding 4), is the format six projects converged on, and it is what `cat` and `grep` would return. (b) Flags from JSON Schema already have a worked mapping in mcporter: kebab-case to camelCase, `key=value`, `key=@file`, `--json -` on stdin, string-preserving coercion and exit status 1 on `isError` (finding 6). (c) Search over tools should be ranked and permission-scoped in the database, as executor does with BM25 statistics computed over the rows the caller may see (finding 5); a substring match (mcp-use) or an unranked listing (goose) is the weak end of the field. (d) Credentials must never be files the agent's shell can `cat`: mcporter and the UTCP CLI put tokens in plaintext files beside the agent (findings 2, 6), which a virtual shell over governed mounts avoids by construction, but only if `/.vfs` never projects a secret as readable content. (e) Limits the field uses: a wall-clock timeout, a tool-call cap (50 to 100), an output cap (200,000 characters to 1 MB), and a code-size cap (65,536 characters); vfs's verb budget should name each. (f) Approval for side-effect tools has one serious design, OpenCode's resumable snapshot with idempotent and durable tool kinds, used by executor (findings 5, 10); a vfs `run` that pauses for a person must not hold a lock while it waits, per the reference deployment's rule that a lock is held only for a commit. (g) A single direct call must stay cheap: in a shell it already is one command, which matches where executor and goose ended up. (h) Results written to files and programs saved as reusable scripts are rare (lootbox and executor only, finding 11); vfs storing both in the namespace would go beyond every project here, and should be measured before it is claimed as a benefit.

Scale, against the reference deployment. pctx serialises every execution in a process behind one mutex and goose allows four workers (findings 4, 7); at about 20 verb calls a second at peak, a code-mode engine that holds a global lock across a program's tool calls cannot sit on the verb path. An interpreter in-process (OpenCode, Boa, Monty) or the vfs shell's own evaluator, with no global lock and with each tool call dispatched as an ordinary verb, is the shape that survives that rate.

## What this study does not settle

No project publishes a reproducible evaluation in its repository, so whether code mode raises task success, and by how much, is not settled here; the numbers available are goose's single runs with one model and a third-party eight-scenario benchmark on Claude 3 Haiku. Whether models write correct vfs shell pipelines as reliably as JavaScript for data transforms (joins, filters, aggregation) is not measured by any project. pctx's filesystem mode is the closest analogue to vfs, and nothing measures whether models use it better than its catalog mode. lootbox's source was not read (licence unclear), so its type-check gate and sandbox details rest on its README. executor's v1 design on its `main` branch was not studied. Adoption figures are GitHub stars as read on 2026-11-23; download counts could not be fetched from this session. No sandbox escape was attempted against `node:vm`, curated-builtins `exec` or RestrictedPython.

## One line

Nine open-source code modes agree on a few meta-tools, find-then-read discovery, TypeScript-style signatures, server namespaces and host-held secrets, and split on the engine, ranked search and per-caller authority; pctx (tools as `.d.ts` files browsed with bash), mcporter and lootbox (tools as CLI commands and files) and executor (BM25 tool search in Postgres under the caller's permissions) each hold one piece of the vfs design, and none combines them or measures that it works.
