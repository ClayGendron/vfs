# 05 — Tools as files, tools as CLI commands, and tool results as files

The question as this study received it: study the designs that turn tools into files or into shell commands, and that store tool results as files — the half of the vfs idea that is "tools and MCP servers called through a bash CLI and stored as files so they are searchable like anything else". Cover MCP as a CLI (philschmid/mcp-cli and its post, mcporter's CLI generation, chrishayuk/mcp-cli, apify's mcpc, and any "MCP server to shell command" project): how a JSON Schema becomes flags, `--help`, output format, piping. Cover tools as files (airshelf/mcpfs against the 2026-09-04 vfs memo, reporting only what is new; FUSE, Plan 9 and 9P style projections; Anthropic's `./servers/<server>/<tool>.ts` tree, cited only). Cover results and context as files (Cursor's dynamic context discovery, Manus's context engineering, Claude Code's persisted large results, deepagents' large-result eviction): when a result goes to a file, what the model is told, how it is found later, retention. Cover Vercel's bash-as-the-tool work (just-bash, bash-tool) and its numbers. Answer the brief's seven points where they apply, make one table of what becomes a file, and say concretely what the path layout, flag mapping, indexing, retention and permissions of a vfs code mode should be.

## Findings

### A. MCP as a CLI

**F1. The field is large, young and converging on one shape** (READ). mcpc's own comparison table, dated 2026-11-05, lists nineteen MCP CLI clients (`apify-mcpc/README.md:1599-1640 @ 673e6ea`); eleven are marked active, and the oldest (`f/mcptools`) pins MCP `2024-11-05`. Three shapes recur. *A generic runtime client* names server and tool on every call (`mcp-cli call <server> <tool> '<json>'`, `mcpc @session tools-call <tool> k:=v`, `mcporter call server.tool k=v`, `mcp2cli --mcp URL <tool> --flag v`). *A generated per-server binary* turns one server into one command (`mcporter generate-cli`, `clihub generate`, `mcp2cli-rs` aliases such as `email send --to …`, `mcp2cli bake install` wrapper scripts). *Tools as commands inside an agent shell* register each tool as a command of an in-process bash (`@just-bash/executor`: `math add a=2 b=3`). All three keep the model's surface to one tool, a shell, and move the catalog out of the prompt. mcpc states the thesis: "Just one `Bash()` tool, and `mcpc` handles the rest" (`README.md:64-72`).

**F2. philschmid/mcp-cli passes arguments as one JSON object and never maps the schema to flags** (READ, EXECUTED). Commands are `info`, `grep`, `call` (`README.md`, "Usage"); `call <server> <tool> '<json>'` or JSON on stdin, recommended for anything with quotes: "Stdin bypasses shell parsing entirely" (README "Complex Commands"). `call` prints only the joined `text` blocks of the result, and falls back to the whole result as JSON only when there are none (`src/output.ts:198-216`, `src/commands/call.ts:162-166 @ d77672a`); the README still says "JSON output is default for call command" and pipes into `jq '.content[0].text'` (`README.md:196-197`), which the 0.3.0 code no longer emits (CHANGELOG 0.3.0: "`call` outputs raw text content"). `grep` is a glob over tool *names* only, "not server name or description" (`src/commands/grep.ts:130`). No line in `src/` reads `isError` or `structuredContent` (grep, no match). EXECUTED (`output.txt`, "pmc fail"): a tool returning `isError: true` exits **0** with `boom` on stdout, indistinguishable from success; a call missing the required `query` reaches the server (`pmc echo missing required`, one wire call, server saw `{}`). Policy is a pair of glob lists per server, `allowedTools` and `disabledTools`, with deny winning (README "Tool Filtering"). A lazy per-server daemon on a Unix socket keeps connections warm for 60 s (README "Connection Pooling").

**F3. mcporter's generated CLI has the most careful flag mapping of the runtime tools, and documents its own policy hole** (READ). `generate-cli` emits one TypeScript file (optionally a Bun-compiled binary) per server, with the resolved server definition and the schemas embedded, and a hidden `__mcporter_inspect` subcommand so the binary describes itself (`docs/cli-generator.md:9-24`, "Artifact Metadata" `@ aa8d0c5`). Mapping (`src/cli/generate/tools.ts:98-140`, `template.ts:237-262, 585-605`): one long flag per top-level property, kebab-cased, collisions suffixed `-2`; `number` parsed finite; `boolean` takes an explicit `true`/`false` (never Commander negation, so `--no-cache` is a property, not a negation); `object` is `JSON.parse` of the value; `array` is either a JSON array or comma-split and coerced per item type; enum members are shown in the placeholder (`<mode:fast|slow>`); `--raw <json>` supplies the whole arguments object; required properties with a schema default may be omitted. Output is `text|markdown|json|raw`; `isError: true` exits 1 "in every output format while preserving the result on stdout" (`docs/cli-generator.md:14-15`). `mcporter list` prints each tool as a pseudo-TypeScript signature with optional parameters folded into a count (`docs/call-syntax.md`, "Reading the CLI Signatures"; the TypeScript side is another study's). The doc then says plainly that a generated CLI "does not automatically inherit that client's approval prompts, tool-call policies, or audit trail", that `--include-tools` is not "dynamic authorization", and that "Direct execution of the generated artifact bypasses that policy boundary" (`docs/cli-generator.md:75-134`).

**F4. mcpc is a full MCP client in CLI form: sessions, resources synced to files, schema snapshots** (READ). Every MCP operation is a subcommand of a named session (`mcpc @s tools-list|tools-get|tools-call|resources-read|resources-subscribe|skills-get|tasks-*`, `README.md:140-205`). Arguments are `key:=value` with JSON auto-parsing ("valid JSON keeps its type … anything else is a string"; force a string with `id:='"123"'`), an inline JSON object, or stdin (`README.md:280-306`). `--json` prints the result object exactly as the MCP specification shapes it (`README.md:350-361`); text mode is Markdown-ish and can be cut with `--max-chars`. `mcpc grep` searches tool names and server instructions (resources and prompts on request) across every live session, with `-E` regex and grep's exit convention, and is pitched as "dynamic tool discovery" after Anthropic's tool search and Cursor's post (`README.md:310-347`). `resources-subscribe <uri> <file>` keeps a local file rewritten on every `notifications/resources/updated` (`README.md:1163-1172`) — the one client here that materializes an MCP object as a file and keeps it fresh. `--schema expected.json` refuses a call when the tool's schema drifted incompatibly from a saved snapshot (`README.md:729-750`). Credentials live in the OS keychain, bridges get them over a Unix socket, and `--proxy` re-exposes a session on localhost so a sandboxed agent "can only interact with the MCP server through the `@ai-sandbox` session, without access to the original OAuth credentials" (`README.md:752-771, 1503-1530`). Exit codes split client (1), server (2), network (3) and auth (4) errors (`README.md:1545-1551`).

**F5. mcp2cli derives argparse flags from the schema, validates scalar types and enums before the wire, and ranks the list by local usage** (READ, EXECUTED). `schema_type_to_python` maps `integer`/`number` to typed parsing, `boolean` to `--x/--no-x`, `array` and `object` to strings marked "(JSON array)" or "(JSON object)", and a type-less numeric enum to a numeric type (`src/mcp2cli/__init__.py:388-417 @ bed40af`); `coerce_value` accepts a JSON array or comma-splits (`:431-470`); enums become argparse `choices`. EXECUTED: `--limit five` and `--mode medium` exit 2 with zero wire calls; `--tags 'a,b'` became `["a","b"]`, so an item containing a comma needs the JSON form; a missing required `--query` was **not** refused and reached the server as `{"limit": 5}`; `isError` exits 1 with `Error: boom` on stderr, and `--json` emits the full `CallToolResult` envelope including `structuredContent` and `isError`. `--list` is sorted by recorded call frequency from `~/.cache/mcp2cli/usage.json`, with `--top N --compact` cutting "~1,400 tokens for 96 tools" to "~20 tokens" (`README.md:315-333`); tool lists and specs are cached for an hour (`README.md`, "Caching"); `--toon` re-encodes output in TOON, claimed "40-60% fewer tokens than JSON" for uniform arrays. The same machinery serves OpenAPI and GraphQL sources, not only MCP.

**F6. `@just-bash/executor` makes every tool three things at once, and its commands ignore the schema** (READ). One `{description, execute}` registration, or one discovered from GraphQL, OpenAPI or MCP through `@executor-js/sdk`, becomes a tool path (`math.add`), a `tools.math.add({...})` call inside the QuickJS `js-exec` guest, and a bash command `math add` (`packages/just-bash-executor/README.md:42-60 @ ec5ab76`). The namespace is the first path segment; subcommands are kebab-cased with the original kept as an alias (`README.md`, "Naming rules"). Arguments come as `key=value`, `--key value`, `--json '{…}'` or stdin JSON, every value is tried as `JSON.parse` first, and precedence is flags over `--json` over stdin (`README.md:252-274`). `--help` lists input modes, not properties: `tool-command.ts` has no reference to the input schema, `properties` or `required` (grep, no match), so a misspelled argument or a missing required one goes to the tool unchecked. `onToolApproval` gates by tool path and defaults to "allow-all"; elicitation defaults to decline (`README.md:224-231`). The bridge under it is just-bash's generic hook `invokeTool(path, argsJson, abortSignal) => Promise<string>` (`packages/just-bash/src/Bash.ts:120-142`), which the 2026-10-15 agent-shell study already recorded.

**F7. The flag mapping differs on exactly the cases that matter, and only spec 170 states all of them** (READ, EXECUTED). Across the implementations read and run:

| Case | philschmid mcp-cli | mcpc | mcporter (generated) | mcp2cli | just-bash executor | mcp2cli-rs | vfs spec 170 §2 |
|---|---|---|---|---|---|---|---|
| Argument syntax | one JSON object | `k:=v` (JSON-parsed), JSON, stdin | `--k v`, `k=v`, call expression, `--raw` | `--k v`, `--stdin`, `--req-json` | `k=v`, `--k v`, `--json`, stdin | `--k v` | `--k v`, positionals for required scalars, `--json`, stdin binding |
| Array | JSON | JSON | JSON or comma-split | JSON or comma-split | JSON or string | comma-split | repeat the flag; never comma-split |
| Object / nested | JSON | JSON | JSON | JSON | JSON | `--config <JSON>` | `--x '<json>'`; dotted flags deferred to a census |
| Enum | not checked | not checked (executed: none tested) | placeholder lists members; executed `call` sent `medium` | `choices`, refused before wire (executed) | not checked | `<A\|B\|C>` | must equal a member, else `vfs.invalid` before wire |
| Missing required | sent (executed) | sent (executed) | sent by `call` (executed); generated CLI requires | sent (executed) | not checked | required flags | `vfs.invalid`, exit 2, zero wire calls |
| `isError` | exit 0, stdout (executed) | exit 2, stdout (executed) | exit 1, stdout (executed) | exit 1, stderr (executed) | thrown → stderr, exit 1 | — | exit 1, text to stderr, no rows |
| Large result | all to stdout (executed) | all, or `--max-chars` cut with a marker (executed) | all to stdout (executed) | all, or `--head N` records | stdout | — | capped at 32,768 characters with a marker (spec 167/171) |

In the experiment every one of the four runtime clients forwarded a call that omitted the schema's only required property (`output.txt`: "echo missing required" for pmc, mcp2cli, mcporter and mcpc). For mcpc the wire count reads 0 because its bridge process starts the server without the driver's environment variable; the server's echo of `{"limit": 5}` shows the call arrived.

**F8. No MCP CLI stores a tool result as a file on its own; each prints it and leaves spilling to the harness** (EXECUTED, READ). A 199,999-character result went whole to stdout from all four clients (`output.txt`, "big"). The only file-shaped results are opt-in: mcpc `resources-read -o file` and `resources-subscribe` for resources (F4), the shell's own `>` redirection, and bash-tool's experimental tee of pipeline stages (F14). None of them names, indexes, retains or permissions a result.

### B. Tools and servers as files

**F9. mcpfs has not moved since the vfs memo** (EXECUTED). A fresh clone on 2026-11-23 is at `640511e` (2026-03-06), the commit the 2026-09-04 memo read; nothing in that memo needs revising. A web search found one independent project with the same split, TakyiEric/mcpfs, which maps MCP servers to Windows drive letters with reads as files and writes through a CLI (READ, search result only, not cloned).

**F10. Anthropic's tree is the canonical "tool definition as a file" design** (READ, cited only). The post generates `./servers/<server>/<tool>.ts`, one file per tool with its typed interface, and the agent "discovers tools by exploring the filesystem: listing the `./servers/` directory … then reading the specific tool files it needs"; its worked example falls "from 150,000 tokens to 2,000 tokens — a time and cost saving of 98.7%" (an illustrative example, not a measured workload). The same post writes intermediate results to `./workspace/*.csv` and saves reusable code as `./skills/<name>.ts` with an optional `SKILL.md` (https://www.anthropic.com/engineering/code-execution-with-mcp, sections "Progressive disclosure" and "State persistence and skills").

**F11. agfs projects *services*, not tool catalogs, as files, with Plan 9's control-file pattern** (READ). "Everything is a file, in RESTful APIs. A tribute to Plan9" (`agfs/README.md:6`). A KV store is a directory of keys; a queue is a directory with `enqueue`, `dequeue`, `peek`, `size`, `clear` control files; SQL is a session: `cat …/users/ctl` mints a session id, a write to `…/<sid>/query` runs a statement, a read of `…/<sid>/result` returns rows (`README.md:110-157 @ 4e0d236`). `gptfs` is a call-as-file inbox: a file written to `inbox/` triggers an LLM request and its answer appears at `outbox/<name>_response.txt` with `outbox/<name>_status.json` (`agfs-server/pkg/plugins/gptfs/README.md`). `vectorfs` indexes every document written under `docs/` asynchronously and answers semantic search through `grep` (`plugins/vectorfs/README.md`). The server is served over HTTP with an optional FUSE mount, plus an MCP server (`agfs-mcp`) that exposes the tree back to MCP clients. Every operation is a write of a request file and a read of a response file: two calls, ordered through a session directory.

**F12. FUSE is the projection's weak point in sandboxes** (READ, search). `@desplega.ai/agent-fs` documents that gVisor-class sandboxes (GKE Sandbox, Cloud Run gen1), Codespaces, Modal and Fly Machines cannot mount FUSE (npm page via search). mcpfs and agfs both need FUSE for `cat` to reach the projection from an ordinary shell; Anthropic's tree, Cursor's folders and just-bash's `MountableFs` (`packages/just-bash/README.md:300-338`) avoid the kernel by being real files or an in-process filesystem.

### C. Results and context as files

**F13. Cursor writes four kinds of context to files and tells the model only where they are** (READ, through search summaries; cursor.com unreachable). The post (2026-01-06) calls the pattern "dynamic context discovery", against "static context which is always included". Long tool responses from shell commands and MCP calls are written to temporary files "instead of truncating", and the agent is told the location and reads the part it needs with tools such as `tail` and `grep`. MCP tool descriptions are synced into a folder, one per server; the static prompt carries little more than tool names, and the agent looks up a full description, with `rg` or `jq`, when a task needs it. Integrated terminal sessions are synced to files so the agent can grep their output. At summarization the history is condensed, but the full chat history stays available as a file for details the summary dropped. Agent Skills are files too. Cursor reports a 46.9% reduction in total agent tokens in runs that called MCP tools, from an internal A/B test (vendor figure, not independently measured, quoted here from secondary coverage).

**F14. bash-tool can tee every pipeline stage to a file; it is opt-in and unindexed** (READ). With `experimentalTeeTransform`, just-bash's `TeePlugin` rewrites each pipeline so every stage's stdout is also written to `/tmp/bash-tool/<timestamp>-<index>-<command>.stdout.txt` (`packages/just-bash/src/transform/plugins/tee-plugin.ts:72 @ ec5ab76`); the tool result carries a `teeFiles` array, and the tool description tells the model "you can read the full output of earlier pipeline stages without re-running: `cat /tmp/bash-tool/*-pnpm.stdout.txt | grep something`" (`bash-tool/src/tools/bash.ts:108-122, 159-176 @ 70ba5ad`). Inline output is cut at 30,000 characters per stream with a removed-count marker (`bash.ts:18`). The files live in the sandbox filesystem for the sandbox's life; nothing names an owner or an expiry.

**F15. Claude Code persists large results to the session's `tool-results` directory, and deletes them with the transcript after 30 days** (READ, code.claude.com). An MCP result over `MAX_MCP_OUTPUT_TOKENS` (default 25,000 tokens), or over 50,000 characters for a tool that declares no `_meta["anthropic/maxResultSizeChars"]` (ceiling 500,000), is saved to a file and "replace[d] … in the conversation with a message that names the file path, so Claude reads the file when it needs the content"; images are inlined (possibly scaled) and their original bytes also saved there; an `isError` text over about 11,000 characters is cut to its first and last 5,000 with no file (`mcp.md`, "MCP output limits and warnings"). A valid Bash result over about 30,000 characters arrives as "the path of a file saved to the session directory … plus a preview of up to the first 2,000 characters, and Claude reads or searches the file when it needs the rest"; a failing command gets only a head-and-tail excerpt "with no file path" (`tools-reference.md`, "Output limits"). The directory is `~/.claude/projects/<project>/<session>/tool-results/`, removed once older than `cleanupPeriodDays`, default 30 (`claude-directory.md`, "Cleaned up automatically"). Tool *definitions* are not files: with tool search on by default, "only tool names and server instructions load at session start" and the rest come through a `ToolSearch` tool (`mcp.md`, "Scale with MCP tool search"). Two rules worth noting: the spill is for successful results only, and a server can raise its own threshold per tool by a declared fact in `tools/list`.

**F16. deepagents evicts a large result to `/large_tool_results/<tool_call_id>` and tells the model to page it and grep the directory** (READ). Any tool result longer than `4 × tool_token_limit_before_evict` characters (default 20,000 tokens, so 80,000 characters; `NUM_CHARS_PER_TOKEN = 4`) is written to `{artifacts_root}/large_tool_results/{sanitized tool_call_id}` (`libs/deepagents/deepagents/middleware/filesystem.py:1176, 1981, 2076-2080`; `_message_eviction.py:263-279 @ 084f04f`). The message is replaced by a fixed text — "Tool result too large, the result of this tool call {tool_call_id} was saved in the filesystem at this path: {file_path} … make sure to only read part of the result at a time … offset=0 and limit=100" — followed by a five-line head and five-line tail preview with line numbers, each line capped at 1,000 characters (`_message_eviction.py:31-42, 115-150`). Discovery after the fact is built into the `grep` tool's own description: "Offloaded large tool results live under the artifacts root (`/large_tool_results/` by default); grep that directory to search them when you do not know the exact path" (`filesystem.py:1649`). `ls`, `glob`, `grep`, `read_file`, `edit_file`, `write_file` and `delete` are exempt, because they page themselves or return little (`filesystem.py:1832-1840`). Summarization appends evicted messages to `{artifacts_root}/conversation_history/{session_id}.md` and embeds that path in the summary; binary blocks go to content-addressed `{artifacts_root}/blobs/<sha256>` (`summarization.py:1940-1945`, `_blob_offload.py:3`). Where the file lives, and so its retention and sharing, is the backend's: LangGraph thread state for `StateBackend`, a store or a disk for others; no expiry code was found (grep for delete, TTL, retention near `large_tool_results`: no match). The offload calls `backend.write` directly (`_message_eviction.py:275`), while `FilesystemPermission` rules are applied in the agent-facing tool wrappers (`filesystem.py:417-522`).

**F17. Manus treats the file system as restorable memory** (READ, search summaries; manus.im unreachable). The July 2025 post argues that irreversible compression is risky because an agent cannot know which observation will matter ten steps later, so compression must be restorable: page content can be dropped from context as long as its URL stays, a document's body as long as its path stays in the sandbox; the file system is described as unlimited in size, persistent, and operable by the agent itself, which reads and writes it on demand as externalized memory. A `todo.md` rewritten step by step keeps the goal in recent attention (third-party summary). The October 2025 LangChain webinar is summarized as ordering reversible compaction before irreversible summarization and building summaries from full, not compacted, tool results; its "layered action space" was not verifiable from the summaries reached.

### D. Bash as the tool: Vercel's numbers

**F18. Vercel's d0 rewrite is the most-cited evidence for bash over a tool catalog; its sample is small** (READ, repost and X post). Vercel's internal text-to-SQL agent replaced its specialized tools (counts differ by source: "15+", 17 or 18) with bash in a Vercel Sandbox over the semantic-layer YAML files plus SQL execution. The repost's table: success rate 80% → 100%, mean run time 274.8 s → 77.4 s (3.5×), tokens about 102k → 61k (37% fewer), steps 42% fewer; Vercel's X post rounds to "40% fewer tokens, 40% fewer steps, 3.5x faster". One commentary describes the benchmark as five queries. The repost also cites Vercel's companion test of Skills against `AGENTS.md`: the skill path passed 53% because the model skipped the available skill in 56% of cases, against 100% when the documentation sat in `AGENTS.md`. Both are vendor figures on vendor workloads. bash-tool and just-bash came out of that work; their call surface is the 2026-10-15 study's subject.

### G. Failure modes and criticism

**F19. The CLI hop drops the per-call policy and the per-user identity** (READ). mcporter says it outright (F3). philschmid's and mcptools' guards are static glob lists (`mcptools/README.md:665-690`; guard mode "only works with STDIO transport"); just-bash executor's approval hook defaults to allow-all (F6). mcpc's proxy keeps tokens out of the sandbox but the session still acts with one credential (F4). In every design read, a server sees one identity per connection, not the human behind the agent; vfs spec 170 inherits that ("A server's identity is the connection's", `170 spec §3.1`).

**F20. Errors that look like success, and validation the server never does** (EXECUTED). philschmid's client prints an `isError` body on stdout with exit 0 (F2); three of four clients send a call missing a required property (F7); comma-splitting silently changes a value containing a comma (F5). Spec 170 already decides each of these the strict way, and its review recorded that a real server "accepts [unknown properties] silently" (`170 spec §2`).

**F21. Files the model can grep are an injection surface and a staleness surface** (INFERRED from F13, F4, F5). A synced description folder or a spilled result is untrusted text the agent will read; spec 170 already strips control characters, caps descriptions and prefixes provenance, and never places manifest text in a system prompt (`170 spec §6`). Freshness: Cursor resyncs, mcp2cli caches an hour, mcpc pins a schema snapshot, spec 170 refreshes on `ttlMs` with a 30-second floor.

**F22. Results as files without retention or ownership** (READ, INFERRED). Claude Code is the only design with a stated retention (30 days, with the transcript). deepagents' path is named by `tool_call_id`, has no expiry, and its location follows whatever backend the artifacts root routes to, so a store-backed deployment keeps results across threads unless the host prunes them. bash-tool's tee files and agfs's outbox persist as long as their filesystem does. None of the designs attaches an owner to a spilled result or decides who else may read it; they are single-user by construction.

## What this means for a vfs code mode

Everything in this section is INFERRED from the findings above and from specs 167, 169, 170 and 171.

**1. Keep the call surface spec 170 already drew; it is the strictest one in the field, and the experiment shows why each strict rule is needed.** One flag per top-level property, arrays by repeating the flag, objects and unions as JSON, positionals for required scalars, `--json` for the whole object, `--help` from the schema, and refusal before the wire of a missing required property, an uncoercible value, an unknown flag or a non-member enum. Every runtime client tested let at least one of those through (F7). Two additions earned by the survey. (a) `--x @<vfs path>` for any `string` property, not only base64 ones, reading the value from a namespace file; mcporter's `--body @file` is the precedent, and it is what lets a stored result feed the next call without the agent pasting it: `jira create-issue --summary "Weekly" --body @/.vfs/run/01J…/stdout`. (b) A `--schema-check` in the spirit of mcpc's snapshot (F4) is unnecessary in vfs because the manifest file's `content_hash` already shows drift (`170 spec §6`); `stat` on the tool path is the check.

**2. Path layout: definitions under `/.vfs`, results under `/.vfs/run`, both real entries the ordinary verbs reach.**

```
/.vfs/mcp/<server>/                       one directory per connected server
├── tools/<tool>                          manifest: description, inputSchema, outputSchema, annotations, trust line
├── resources/<n>                         readable; `cat` issues resources/read
└── prompts/<p>                           listed only
/.vfs/tools/<name>                        a host-registered function's manifest
/.vfs/bin/<name>                          the union: every callable by its bare command name
/.vfs/run/<call-id>/                      one record per `cli` call that ran a stage
├── command                               the line as typed
├── status                                per stage: callable, resolved path, content_hash, exit, stderr
├── stdout                                the call's output as one row (spec 167 case b)
└── <i>                                   row i of a tool's result (spec 170 §4), structured content in `status`
```

The tool *definition* is a file because that is what makes discovery the namespace's own job: `ls /.vfs/mcp`, `grep -ril invoice /.vfs/mcp/*/tools`, `cat /.vfs/mcp/jira/tools/create_issue`, and `<tool> --help` all answer from the same manifest. This is Cursor's folder per server and Anthropic's tree with one difference that matters: a vfs manifest is a row behind grants, so the folder an agent browses is already filtered to what its caller may call (`170 spec §5.1`, `rungs_at`). The *result* is a file because that is what makes a large answer recoverable, greppable and reusable (F13, F15, F16), and the record path is the call id the agent already holds.

**3. Spill rule: inline up to the cap, then a path and a preview, never a silent cut.** Spec 167/171 cap text at 32,768 characters, which sits beside Claude Code's 30,000 and bash-tool's 30,000 (F14, F15). When a `cli` call's output passes the cap, the truncation warning should name `/.vfs/run/<call-id>/stdout` and carry a head-and-tail preview with line numbers, which is deepagents' shape (F16) and Claude Code's (F15); the agent then pages it with `sed -n`/`head`/`tail` or greps it. Follow Claude Code in not spilling a failing call (its stderr gets a head-and-tail excerpt), so a failure never sends the agent to a file to learn that it failed. Let a tool raise its own spill threshold by a declared fact, as `anthropic/maxResultSizeChars` does, rather than by a global knob.

**4. Make `/.vfs/run` durable and grant-filtered, not an in-process ring, if results are to be "searchable like anything else".** Spec 169c keeps records in router memory, 64 calls per `Authority`, lost on restart, and serves only `stat`, `ls` and `read`. That serves "read the stdout I just made" and cannot serve "grep what the agent found yesterday", which is the request's half. The durable form is ordinary rows in the root binding's database under `/.vfs/run/<call-id>/`, so `grep`, `glob`, `search` and `traverse` reach them with no new verb, and the existing `Authority` rule becomes a row grant: each record is born with an owner-only grant to the calling principal (and the system actor), never with the posture of `/.vfs`. A result is often the answer to a call made with the server's one credential (F19), so it may hold data the caller's grants elsewhere would not show to others; owner-only by default keeps the store from widening it. Sharing is an explicit `cp /.vfs/run/<id>/stdout /team/reports/…`, a write that is judged by the destination's grants and leaves an audit row, which is the declassification point. Agents of one human acting as one principal see each other's records; two humans never do unless one copies.

**5. Index results lexically on write, keep them out of the vector leg by default, and give them a retention that the reference deployment can carry.** At the reference deployment's 150,000 agent verb calls a day (AGENTS.md, "The reference deployment"), persisting a record for every call is 150,000 records a day, 4.5 million at 30 days: close to half the 10,000,000-file corpus, every one of them a row the daily full rebuild would visit, which is the multiplier that "most often turns a small idea into an unaffordable one". Two choices keep it affordable. (a) Persist durably only what earns it: spilled outputs over the inline cap, tool results (`<i>` rows), and records an agent marks with an explicit save (`cp`, or a `--keep` on the line); a small result stays in the in-memory ring of 169c, which already carries it for the session. If spills are a few percent of calls (an *assumption*; no source here measures the share), that is a few thousand rows a day and on the order of 100,000 at 30 days, about 1% of the corpus. (b) Retention is a declared expiry per record (default 30 days, Claude Code's figure, F15), applied by the same sweep that empties the trash, with `cp` out of `/.vfs/run` as the way to keep something. Lexical postings for a result are written by the partial index pass like any file's; embeddings for run records are off by default because a vector per spilled log line is the derived-row cost the reference table warns about, and an agent that wants a result to be semantically findable copies it into a user path where the normal embed policy applies.

**6. Search over definitions should rank, which no CLI does.** mcp-cli globs names (F2), mcpc and mcp2cli substring-match names and descriptions (F4, F5), Claude Code and deepagents defer to a search tool. A vfs catalog is a few thousand manifest rows (a reference-scale estimate: 1,000 tools at about 1 KB each, an *assumption*), so including manifests in the lexical and vector legs of `search` is cheap and turns "which tool sends a Slack message" into one ranked `search` over `/.vfs/mcp`. Spec 170 lists `glean` over catalogues as a later item; this study's evidence argues for moving manifests into the ordinary index rather than a special one. mcp2cli's usage-ranked listing (F5) has a vfs form too: the run records already say which tools a principal calls, so `ls /.vfs/bin --sort=used` costs one grouped read over the caller's own records.

**7. Keep reads from executing and writes from hiding.** mcpfs's call-on-`stat` and agfs's write-a-request-read-a-response files are the two ways a projection blurs read and call (F9, F11). Spec 170 keeps the line: reading a manifest never runs anything, a tool runs only as a command word, and its result lands in `/.vfs/run`. The agfs pattern is still useful as a *vocabulary* for long calls: an MCP task (`tasks/*`) maps naturally onto `/.vfs/jobs/<id>/{status,result}` (already sketched in the 2026-10-15 session-state study), where `cat status` is a read of a stored row and never a poll that calls the server.

**8. Say where a CLI hop loses authority, and do not repeat it.** The field's CLIs run outside the client that holds the policy (F3, F19). In vfs the shell is inside the gate: every stage, including a tool stage, resolves through `_invoke` with the caller's `Authority`, and the result rows are owned by that caller. The one hop vfs cannot close is the MCP server's own identity; spec 170 already states it, and the result-ownership rule in point 4 is what stops it from leaking further through the store.

## What this study does not settle

- Whether a CLI-shaped tool surface beats native tool calls on accuracy for a catalog of hundreds of tools, with the same model and tasks. No source measured it; the numbers in Finding F are token and latency claims on vendor workloads, and the strongest (Vercel's) rests on a handful of queries.
- The share of agent calls whose output passes a 32,768-character cap, which decides how many run records the durable store would hold per day. Point 5's figure is an assumption; a census of real `cli` outputs (or of Claude Code `tool-results` directories) would settle it.
- Whether the schema census that spec 170 asks for changes the nested-object answer (dotted flags); study 08 in this folder carries that census.
- The exact text of the Cursor, Manus, Vercel and philschmid posts: their hosts were unreachable from this session, so their claims here are from search summaries and a repost. A later pass with those hosts allowed should check the quotations and the 46.9% and Vercel figures against the originals.
- Whether owner-only grants on run records interact cleanly with the trash, `restore` and the posture ladder (a run record is a new kind of system-written row), and what `cp` out of `/.vfs/run` must record to count as an audited declassification.
- chrishayuk/IBM `mcp-cli` was not read from source.

## One line

The field turned tools into shell commands and large results into files, but every MCP CLI forwards invalid calls, prints whole results and acts with one identity, and every results-as-files design is single-user with ad hoc retention; vfs can be the better choice by keeping spec 170's strict flag mapping, putting tool manifests and spilled results in the namespace as grant-filtered rows the ordinary verbs search, owned by the caller and expiring by a declared retention.
