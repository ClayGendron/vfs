# Code mode keeps the tool catalog out of the context; vfs can do the same with its shell over a searchable, rights-filtered catalog, and four pieces are missing

On 2026-11-23 the request was: research Cloudflare's Code Mode "and other similar" designs, as a reference design "so that our framework is a better choice", where the vfs code mode would be "calling tools and MCPs through our bash cli and storing them as files so they are searchable like anything else". No intention document was written; the request is the intent. The work ran autonomously: eight parallel studies from the same [brief](studies/00-brief.md), six over prior art, one over the vfs tree itself and one executed experiment over real tool catalogs, each running for 11 to 18 minutes, followed by this synthesis and a fidelity review of it ([09](studies/09-fidelity-review-of-the-memo.md)), whose findings are applied here. Forty-three reference repositories were cloned as siblings of the checkout, refreshed to their default branches and licence-checked ([refresh.log](studies/refresh.log), [licenses.log](studies/licenses.log)). The studies are in [studies/](studies/), and the scripts and outputs of every experiment are under [studies/experiments/](studies/experiments/). This memo commits vfs to nothing; it feeds the drafted specs 167, 169, 170 and 171.

Steps skipped, each named in its study: the first design of the catalog experiment, which would have run third-party MCP servers and release binaries, was refused by the session's permission classifier and replaced by reading checked-in tool definitions as data ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md)); running Cloudflare's codemode renderer and ranker from the clone was refused the same way, so the size of its generated TypeScript was not measured ([01](studies/01-cloudflare-code-mode.md)); GitHub issue bodies of `cloudflare/agents` were not readable, only titles; `chrishayuk/mcp-cli` could not be cloned ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)); no semantic embedder could run without a download ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) F10); and several web hosts were blocked (listed under Sources).

Labels: EXECUTED means a command ran in this session and the claim reports its output. READ means read in a cited file or page. "READ (search excerpt)" means read only in a search engine's excerpt of a page the session could not open, and is weaker evidence. INFERRED means reasoning from the evidence. Sections 1 to 7 are evidence; sections 8 and 9 are synthesis.

## The answer

Code mode is one idea with many spellings: the model is not shown the tool catalog; it is shown one or a few small, fixed tools, it writes a short program that finds and calls the tools it needs, and only what the program prints comes back into the context. The designs built for large catalogs (Cloudflare's durable runtime and API server, Anthropic's tool search, OpenAI's tool search, executor, FastMCP, pctx) add a search over tool text that returns a shortlist, from 5 to 10 tools in most and up to 50 in one, and keep credentials on the host. Smaller designs still preload every signature (Cloudflare's `createCodeTool`, smolagents), and three command-line designs leave tokens where the agent's shell can read them. The measured savings are real but mostly vendor-reported, and they come from two places: the catalog stays out of the context (a real 1,107-tool catalog is about 140,000 estimated tokens preloaded against about 100 for `ls /.vfs/mcp`, EXECUTED), and intermediate results stay out of the context when calls are chained. Code mode does not help single calls, weak models or step-by-step loops. vfs is well placed: its drafted shell is a parsed grammar dispatched to verbs, so it needs no isolate; every verb call already re-enters the rights check, which Codex, OpenAI's Agents SDK, executor, FastMCP and goose also do for nested calls and Cloudflare's SDK, Anthropic's programmatic calling and smolagents do not; and its namespace can hold tool definitions and tool results as rows that `ls`, `grep` and `search` reach and grants filter. The combination of rights-filtered discovery, owned results and one surface for discovery, execution and authority exists in no studied design. But the drafted specs do not deliver it yet. Four pieces are missing: ranked search over tool definitions (the drafts serve tools as in-memory views that `search` never reaches), a durable, owner-only home for tool results, a structured-data path between calls in the shell, and approval and per-user credentials at the point a side effect leaves vfs.

## 1. What code mode is, in Cloudflare's three spellings (READ)

Cloudflare's Code Mode turns MCP tools into a TypeScript API and gives the model one tool that takes code. In the SDK the code runs in a fresh V8 isolate created by the Worker Loader, with the network blocked (`globalOutbound: null`); tool calls leave the isolate only over Workers RPC to bindings the host holds, so no credential enters the sandbox ([01](studies/01-cloudflare-code-mode.md) F10 to F14). The production API server instead routes the isolate's outbound requests through a gateway that refuses any host but the API and injects the token (F13). The model gets back the return value and captured console output, cut structurally at about 6,000 tokens (F16).

The same idea ships in three shapes (F2): `createCodeTool`, one `code` tool with every generated TypeScript declaration preloaded; a durable runtime whose one tool lists only connector names, with methods discovered from inside the sandbox through `codemode.search` and `describe`; and the production Cloudflare API server, two tools, `search` and `execute`, both taking code. In every case the model writes JavaScript; TypeScript is only the documentation language.

Discovery is weak in a revealing way. Inside the sandbox, search is a lexical, field-weighted ranker over tool names and descriptions only, capped at 50 results. On the production server, `search` is the model's own code scanning the whole 27 MB dereferenced API spec, in a fresh isolate, on every call; there is no index (F6, F7).

Authority stops at the door. The SDK carries no caller identity at the call boundary; the production server runs each user's own token with scope step-up and a guard against writes that spend money; the Zero Trust portal shows a server only to users who match an Allow policy (F8, F15). Cloudflare's own docs say: "Hiding a token does not limit what that token can do." (F14.) Approvals work by abort and replay against a durable log, per method rather than per argument, which forces the program to be deterministic (F17).

## 2. Six moves recur across the field, with named exceptions (READ)

Across Cloudflare, Anthropic, OpenAI, Codex and nine open-source projects, six choices recur ([02](studies/02-anthropic-and-openai.md), [03](studies/03-open-source-code-mode-implementations.md)), none universal:

1. **A few fixed meta-tools, not the catalog.** Run a program; search for a tool; read one tool's contract. The model's context pays a constant cost whatever the catalog holds. Exceptions: Cloudflare's `createCodeTool` and smolagents preload every signature.
2. **Find, then read.** A cheap listing or ranked search first, the full signature only for tools the model picked. Shortlists: 5 by default at Anthropic (up to 10,000 deferred tools a request), 8 at Codex, 10 at UTCP and pctx, up to 50 in Cloudflare's runtime. Ranked search is in 5 of the 9 open-source projects (executor, FastMCP, pctx's Python SDK, UTCP, OpenCode); mcp-use matches substrings and goose, lootbox and mcporter only list.
3. **A typed signature with prose as the contract.** Six of the nine open-source projects render JSON Schema as a TypeScript declaration with doc comments, even where the model writes untyped JavaScript.
4. **Tools namespaced by server**, as `server.tool`.
5. **Secrets on the host.** The sandbox holds only a way to ask the host to call. Six of nine open-source projects keep secrets out of the program's reach; mcporter and the UTCP CLI keep token files the agent's shell can read, and lootbox runs tools with `--allow-all`.
6. **Code sees full results; the model sees only what the code prints**, under a timeout. Anthropic: "only the final code output"; OpenAI: `program_output`; Codex: `text()`, up to 10,000 tokens. An output cap is not consensus: only 3 of the 9 open-source projects set one (UTCP's MCP server 200,000 characters, goose 1 MB, OpenCode unset by default), and executor says it sets none.

What the shipped tool searches index ([02](studies/02-anthropic-and-openai.md), [06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) F3): Anthropic's regex and BM25 variants index names, descriptions, argument names and argument descriptions. Codex's readable BM25 indexes the name, the name split on underscores, the description, the schema text and the MCP server, title and namespace. executor's BM25 runs as SQL in Postgres over words split on camelCase and snake_case, including input property names and descriptions. Docker's gateway and the agentic-community registry also weight the server's name. Spring AI's index tokenizes only the description, though its tool description promises more.

Where the field splits ([03](studies/03-open-source-code-mode-implementations.md)): the engine (a real V8 isolate in UTCP and pctx; an embedded interpreter in OpenCode, goose's Boa and FastMCP's Monty; or the agent's own shell with no sandbox in mcporter and the UTCP CLI); ranked search against plain matching; whether each nested call is judged as the caller (only executor, FastMCP and goose); and whether a person can approve a call before it runs (only executor, goose and OpenCode). Codex rebuilds every call made from a script as an ordinary call into the same tool runtime that serves direct calls (READ); study 02 infers that the same approvals and sandbox policy therefore judge it (INFERRED). Anthropic documents its `allowed_callers` setting as not being a security boundary ([02](studies/02-anthropic-and-openai.md)).

The newest movement runs away from pure code. executor added a direct `call` tool on 2026-10-12 (EXECUTED: `git log -S` on the clone); goose and FastMCP document that single-tool tasks gain nothing from code mode; UTCP now tells shell agents to use its CLI rather than its MCP server ([03](studies/03-open-source-code-mode-implementations.md)).

Three readings follow (INFERRED). First, the token savings are real where the catalog is large or results are large and filterable, absent at about ten tools, and absent where each call depends on the model reading the previous result. Second, code as the action space wins on chaining calls for strong models, by about 20 points of success in the one controlled comparison, and does not help, or hurts, weak models. Third, the two comparisons of shell against code both had a full machine behind the shell, with Python, `jq` and `awk` one command away; no source measures a pipe-and-text shell with no interpreter reachable, which is what the spec 167 subset is, and none of the nine open-source projects ships a reproducible evaluation.

Security evidence, all from search excerpts ([04](studies/04-code-as-action-agents-and-the-evidence.md)): a threat-model paper names 16 attack classes for model-written code against MCP servers; Check Point reports escaping a Cloudflare Code Mode sandbox through a workerd bug starting from one prompt injection; CaMeL shows the other route, the interpreter itself enforcing policy.

## 4. What a catalog costs as context, measured (EXECUTED)

The Cloudflare API spec shipped today has 3,776 operations. Full tool definitions are about 1.76M estimated tokens, required parameters only about 0.20M, and even a one-line names-and-summaries index is about 84,000 tokens ([01](studies/01-cloudflare-code-mode.md) F9). Cloudflare's own 1.17M figure counted an earlier, smaller spec of 2,594 tools. A flat listing of a catalog that size is unusable.

Study 08 measured 1,107 real tools on 30 servers, read as data from GitHub's `__toolsnaps__` (149 tools), Alibaba Cloud DevOps' `tools.json` (203) and Docker's MCP registry (755). Tokens are chars/4, an estimate; bytes are exact ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) F2, F7, F8).

| What the model is shown | Estimated tokens |
|---|---|
| every full schema preloaded | 140,303 |
| names only | 6,015 |
| name plus first sentence | 22,328 |
| `ls /.vfs/mcp` (the server listing) | 103 |
| one server's `ls`, median | 53 |
| one manifest, median / max | 153 / 1,810 |
| a vfs `search` with limit 5, median rendered | about 515 (2,062 bytes) |

GitHub's server alone is about 39,000 tokens, 84,000 with its output schemas. The difference between preloading and browsing is three orders of magnitude, and a search plus one read costs about 600 tokens.

The same census is the "real-server schema census" spec 170 commissions before it is built ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) Part A). Of 2,241 properties, 93.1% are strictly scalar and 97.2% take a plain word under spec 170's JSON-then-string rule; 89.5% of tools need only plain words; no tool needs the `--json` fallback to be reachable; dotted flags for nested objects would rescue one tool of 495. Three amendments surfaced: GitHub types 155 integer IDs and page sizes as `number`, which the spec coerces to float; GitHub mixes camelCase and snake_case property names (94 and 165); and 28 objects are free maps with no declared properties. Annotations are sparse outside GitHub: none at Alibaba, 24 of 755 tools at Docker; and 28 of GitHub's 80 tools that are not read-only carry no `destructiveHint`, so annotations cannot carry governance (F6).

## 5. Tools as commands and results as files, in the field (READ, EXECUTED where marked)

MCP as a CLI has three shapes ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)): a generic client (philschmid mcp-cli, mcpc, `mcporter call`, mcp2cli), a generated binary per server (`mcporter generate-cli`, clihub, mcp2cli-rs), and tools as commands inside an agent shell (`@just-bash/executor`). mcpc's own table counts 19 such clients, 13 active. EXECUTED against a fake server written for the study: every client tested sent a call that left out the schema's only required argument; philschmid mcp-cli exits 0 when the tool returns `isError: true`; mcp2cli splits `a,b` into two array items; a bad integer, tried on mcp2cli only, was refused before the call went out; an out-of-enum value was refused by mcp2cli and sent by mcporter; no client spilled a 200,000-character result to a file. Spec 170 §2's flag table is stricter than every implementation surveyed, and the experiment shows each of its rules is needed. mcporter's docs say a generated CLI bypasses the calling client's approvals, policy and audit trail.

Tools as files: Anthropic's pattern post lays tools out as `servers/<server>/<tool>.ts` for the agent to explore with `ls` and read, but that is a pattern, not a product ([02](studies/02-anthropic-and-openai.md)). pctx's filesystem mode is the closest shipped analogue to vfs: each tool is a `.d.ts` file in a read-only tree the model explores with bash, and a second tool runs TypeScript to make the calls ([03](studies/03-open-source-code-mode-implementations.md)). Cursor writes MCP tool descriptions to a folder per server (search excerpt). mcpfs has not moved upstream since the 2026-09-04 memo; agfs adds Plan 9 style control and result files for services ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)).

Results as files: Claude Code moves a large output to the session's `tool-results` directory (Bash over about 30,000 characters with a 2,000-character preview; MCP over 25,000 tokens or 50,000 characters) and deletes it after 30 days. deepagents evicts results over 80,000 characters to `/large_tool_results/<tool_call_id>` with a head-and-tail preview and tells the model to grep that directory; it has no expiry, and its offload write skips its own permission rules. Cursor writes long outputs, terminals and chat history to files (search excerpt). None of these attaches an owner to a stored result ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)). Skills (Anthropic's published format) preload only a name and description, about 347 characters a skill over the 19 published skills (EXECUTED), and read the body on demand ([02](studies/02-anthropic-and-openai.md)).

## 6. Finding the right tool (READ (search excerpt), EXECUTED where marked)

The research figures in this paragraph come from search excerpts, because the papers' hosts were blocked ([06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md)). Accuracy falls as the catalog grows, in every measurement found (F1): RAG-MCP reports 13.62% selection with every tool in context against 43.13% when one is retrieved; LiveMCPBench attributes about half of all failures to retrieval. Tool retrieval is hard information retrieval: on ToolRet the best general retriever reaches NDCG@10 of 33.83 (F2). The vendor benchmarks separate retrieval from selection. As retrieval top-1, BM25 scores 14% at StackOne (270 tools) and at MCPProxy (916 tools, where a hybrid reaches 94%); one summary attributes 56% (regex) and 64% (BM25) to Arcade over 4,027 tools. As selection by a model over the retrieved shortlist, Stacklok reports 94% for its hybrid optimizer against 33.7% for Anthropic's BM25 variant and 30.0% for its regex variant over 2,792 tools. Adding example queries to a tool's text is the most reliable fix found (Tool2Vec, Re-Invoke, Toolshed; F4). Descriptions are mostly poor: 56% of 856 MCP tools have an unclear purpose, and rewording a description shifts selection up to 10× (F5). A server-then-tool hierarchy saves tokens but does not retrieve better in the one controlled comparison (F6). Poisoned descriptions win both retrieval and selection: ToolHijacker reports a 100% retrieval hit rate and about 96% attack success (F7).

vfs's own `search` over tool manifests, EXECUTED in study 08 on the 1,107-tool corpus with 65 labelled queries written and hash-frozen before retrieval ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) F11 to F17):

| Manifest content, lexical leg | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---|---|---|
| name and description | 0.477 | 0.569 | 0.677 | 0.547 |
| plus parameter lines | 0.492 | 0.677 | 0.738 | 0.591 |

Queries that use the tool's own words reach hit@5 0.848; paraphrases reach 0.474. The misses are word-form gaps ("label" against "labels", with no stemming) and synonym gaps; that these cause the gap is INFERRED in the study. `grep` on key words is worse at hit@1 (0.25 to 0.32 on the whole corpus; 0.15 to 0.39 on GitHub alone) and returns 75 to 101 candidate files. Adding servers costs precision: GitHub queries' hit@1 drops from 0.478 against GitHub alone to 0.370 against the whole corpus. Two example requests per tool, written by the researcher to stand in for host-written ones, lift GitHub hit@1 from 0.478 to 0.848; on the 13 queries that share little wording with the examples the lift is 0.385 to 0.846, an upper bound because one researcher wrote both. The offline hashing embedder, fused in as a vector leg, lowered hit@1 from 0.49 to 0.37; no semantic embedder was available offline.

The limits of these numbers (EXECUTED context, from the study): no model chose tools, so hit@k measures whether the right manifest is in what vfs returns, not whether a model picks it and fills its flags; one researcher wrote all queries, alternates and examples in one sitting; the queries lean to GitHub (46 of 65); one query moves a 46-query hit@1 by 0.022; the figures compare variants on one fixed set and are not an estimate of production accuracy.

Study 06's smaller experiment over 81 real tools found the same shape: putting the name and server into the indexed body took identifier queries from hit@1 0.20 to 1.00 and task queries' hit@5 from 0.54 to 0.73, with queries written after reading the tool list, so the shapes compare and the levels do not ([06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) F10). The reason is structural: vfs indexes a chunk's content, not the file's path (`src/vfs/models/chunk.py:93-119`, F9), so a manifest must carry its own name and server in its body.

## 7. Where vfs stands today (READ, EXECUTED where marked)

Built ([07](studies/07-where-code-mode-lands-in-vfs-today.md)): the 25 gated verbs, one `Result`, and an `Authority` judged against row-level grants on every call. Drafted and not built: the shell (spec 167), programs and the bin union (169), tools and MCP servers as views under `/.vfs` (170), the MCP adapter with one `cli` tool (171), the Python guest (172). There is no shell, no `cli`, no `/.vfs` view, no MCP serving or client, and no `mcp` or `wasm` extra.

Three findings from the probe of the live tree, EXECUTED. `run` exists as a verb (`src/vfs/base.py:1605`) but no storage serves it, and it answers `vfs.unsupported` even to a caller who cannot see the path, because the capability check runs before the permission check. A `TOOL.md` stored under `/.agents/tools/` is an ordinary row: `search` ranked it first, `grep` and `glob` found it, and a posture of `none` plus a grant hid it from one user and not another; tools are already searchable files, by accident. Writes to `/.vfs/tools/...`, `/.vfs/bin/...` and `/.vfs/run/...` succeed today as stored rows, which spec 169 will refuse.

The drafts walk away from the searchable form. Spec 169 §a7 retires `/.agents`; spec 170 generates `/.vfs/tools` and `/.vfs/mcp` in memory, so they are not indexed and unscoped searches never reach them; spec 170 §6 serves `ls`, `type`, `--help` and in-memory `grep` over manifests and leaves ranked search over catalogs as "a later item". The default record of a call (169c) is an in-memory ring of 64 calls per `Authority`, lost on restart and never indexed. There is no `jq` in 0.1.0, and an MCP tool's structured content rides beside the rows rather than in the pipe whenever text blocks exist. Spec 170 gives each MCP server one host credential; per-user credentials exist only as a roadmap story. On a fresh node the drafted default lets every caller, anonymous included, call every tool until the host sets two postures (170 §5.1). None of 167, 170 or 171 has an approval step, and a single `cli` tool hides every side effect from a host's per-tool approval. A re-sent `cli` line runs again. Study 07 also tables where the specs disagree with one another and with the code: `/.agents` against `/.vfs`, `/.agents/bin` against `/opt/bin`, `glean` and `graph` in the specs against `search` and `traverse` in the code, the roadmap overriding several specs while calling itself not a decision, and ADRs 081 to 086 cited everywhere with no file in the tree.

## 8. What a vfs code mode should be (INFERRED)

The request names two halves: tools and MCP servers called through the vfs shell, and tools stored as files searchable like anything else. The evidence supports both, and says which parts of the field to take and where vfs can go further.

**Take from the field.** One fixed-size `cli` description that names the grammar, the verbs and where tools live, lists no tool, and is identical for every caller, because MCP clients cache tool lists (Cloudflare's rule, [01](studies/01-cloudflare-code-mode.md) F15). Find before read, with a shortlist of 5 to 10 ranked results. Credentials only at the door: an MCP connection's token lives with the router's connection owner and is never a file, a `stat` field or a value in the pipe. Code sees full results and the model sees only what is printed, which the drafted vfs shell does by construction: the pipe carries whole rows and only the display is capped. Bounded output with one recognizable truncation marker. Errors that name the real alternatives: `command not found` names the nearest programs and the `search` that finds tools; a `permission` error names the rung it needs.

**Do differently, because the language is a grammar over a governed namespace.** No isolate per call: no foreign code runs, so the parser is the sandbox, and there is no spawn cost and no concurrency ceiling. Index the catalog and never scan it per call, because a read must cost in proportion to what it returns (AGENTS.md, "The reference deployment"). Never list a large catalog flat; group or page it, and say how many entries were withheld. Keep the caller's authority across the hop: every stage of a pipeline re-enters the gate, as Codex, OpenAI's Agents SDK, executor, FastMCP and goose do and as Cloudflare's SDK, Anthropic's programmatic calling and smolagents do not. Flags rather than TypeScript types as the generated surface, which keeps constraints that Cloudflare's converter drops, because `--help` renders the schema instead of translating it.

**Where vfs can be the better choice.** Each of three properties has a partial precedent; no studied design has all three. First, discovery filtered by rights: a tool the caller may not run is never listed, never ranked and never costs a token, because the catalog is rows behind grants. executor already ranks over only the rows the caller may see, FastMCP scopes its catalog by authentication, and Cloudflare's portal shows a server only to users an Allow policy matches; Anthropic and Codex search whatever is registered. Second, owned results: a stored tool result is a row born with an owner-only grant, and sharing it is an explicit, audited `cp` judged by the destination's grants; every results-as-files design studied is single-user with ad hoc retention. Third, one surface for discovery, execution and authority: pctx's shell reads the catalog but a second language calls the tools; mcporter's shell calls the tools but has no catalog search; executor's catalog is a database but its language is JavaScript. A vfs shell that browses and searches the catalog and runs the call, against the same rights-judged namespace as the data, would be the first to put all three behind one surface. That claim is unmeasured and should not be made in public until section 10's first experiment has run.

**Where vfs would be weaker.** General computation between calls: JavaScript gives loops, maps, joins and JSON reshaping in one execution; the spec 167 subset has no control flow and the 0.1.0 catalog has no JSON program. Typed nested request bodies, which TypeScript expresses and flags push to `--json`. A proven isolation primitive for untrusted code, which vfs will need if it ever admits a general language beside the shell (the spec 172 guest runs under wasm, which is its own boundary). Durable approval with rollback of side effects in upstream systems; vfs's trash covers its own rows only. Per-API hardening such as Cloudflare's guard against writes that spend money, which a generic MCP projection will not provide without a per-server policy hook.

## 9. What it means for specs 167, 169, 170 and 171 (INFERRED)

Each item names the evidence it stands on. Items marked "behaviour" would change what a drafted spec decides; under the working agreement they are reported here and were not acted on.

1. **Ranked search over tool definitions lands with the catalog, not later (behaviour, spec 170 §6).** Every vendor ships one; vfs lexical search beat key-word `grep` at hit@1 by 0.15 to 0.25 on the whole corpus and by 0.24 to 0.46 on GitHub alone ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md)); the catalog is thousands of rows against ten million files, a rounding error on the index-visit multiplier. This needs manifests that the ordinary index reaches: stored rows of a catalog storage, or a view whose manifests are scored at query time. It is also the reconciliation the request asks for: "stored as files so they are searchable like anything else" is today's accidental `/.agents` behaviour, and the drafts retire it.
2. **A manifest written to be found.** In order: a heading with the exact tool name; a provenance line with the server name and title and the trust line spec 170 already requires; the capped description; a short, host-written "Use when" block of example requests in a user's words, never taken from the server; then arguments and returns, with the output schema. The machine-readable JSON Schema sits in a separate section or sibling entry so it does not dilute the card ([06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md), [08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md)).
3. **The model starts at the listing.** The `cli` description is about 2,300 characters, roughly 575 tokens ([07](studies/07-where-code-mode-lands-in-vfs-today.md)); one hint line, "tools live under `/.vfs/mcp` and `/.vfs/tools`; `ls` them or `search` them", adds about a dozen; `ls /.vfs/mcp` about 100. Names-only or names-plus-first-sentence preambles are worth it only for a single server of a few dozen tools.
4. **No non-semantic vector leg in catalog search.** The hashing embedder lowered hit@1 from 0.49 to 0.37; a catalog ranks lexically unless a real embedding provider is configured.
5. **Durable, owner-only results (behaviour, spec 169c).** `/.vfs/run/<call-id>/` as ordinary rows rather than an in-memory ring, so `grep`, `glob` and `search` reach them; each record born with an owner-only grant to the calling principal; sharing by `cp`. Persist only what earns it, at the reference deployment's 150,000 agent calls a day: spilled outputs over the display cap, tool result rows, and records the agent saves explicitly. Persisting every call would add about 4.5 million rows over 30 days, close to half the corpus ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)). A declared retention, 30 days as Claude Code uses, applied by the sweep that empties the trash. Lexical postings by the partial index pass; embeddings off by default for run records.
6. **The spill marker names the path.** When output passes the 32,768-character display cap, the marker names `/.vfs/run/<call-id>/stdout` and carries a head-and-tail preview, so the next command is `grep` or `sed -n` over it. A failing call is not spilled; its stderr gets a head-and-tail excerpt. A tool may declare a higher threshold in its manifest. An empty result says so explicitly ("ran and produced no output"), which SWE-agent found helped and spec 167 leaves optional.
7. **Flag table amendments before spec 170 is built.** Coerce an integer literal under `number` to a JSON integer; give camelCase and snake_case names one consistent kebab alias; consider `--x key=value` for free-map objects; add `--x @<vfs path>` for any string property so a stored result feeds the next call without pasting (`--body @/.vfs/run/<id>/stdout`). Drop the planned dotted-flag pass. Keep every strict refusal; the CLI experiment shows each is needed.
8. **The shell needs a structured path to match code mode's chaining gain (behaviour, specs 167, 169, 172).** In order: control flow and functions; a JSON program on the pipe (`jaq`); output schemas shown by `cat` of a manifest; and the spec 172 Python guest reachable from the shell in one command. Every bash-only win in the evidence had Python and `jq` one keystroke away ([04](studies/04-code-as-action-agents-and-the-evidence.md)).
9. **Loops steer to batches, and the door paces fan-out.** A loop of 10,000 `stat` calls is one chunked verb call in vfs; the shell should steer to the batched form, and its budget should count verb calls. A pipeline that fans one tool call over many rows needs bounds at the `_invoke` door, per pipeline and per server, as Cloudflare's API server paces its own outbound requests.
10. **A counted test that authority survives the hop, with the claim's limits stated.** A tool reached through a pipe, `xargs` or a loop is judged exactly as when typed alone. This is the strongest claim vfs can make against the field, and it should be pinned, not asserted. Its limits: a prompt-injected program with write rights can still write anything those rights allow; that per-request authority blunts the published attack classes is reasoning, not an executed attack; and the drafted open default lets anyone call every tool until two postures are set, so the claim holds only on a locked node.
11. **Approval and replay safety at the door (behaviour, specs 170 and 171).** A single `cli` tool hides every side effect from a host's per-tool approval, so vfs must provide the stop: a pending row carrying the computed arguments and the rung, with the pipeline stopped before the call and no lock held while a person decides. Whether the stop must also survive a restart and resume (Cloudflare's abort and replay, OpenCode's snapshot) is for the approval spec to decide. After a failed pipeline, vfs knows each verb's rung from one table and can say which steps mutated and whether re-running is safe. Tools with side effects should not run inside a loop or as a non-first stage unless the host allows it.
12. **Per-user credentials across the MCP hop (behaviour, spec 170).** One host credential per server means a result can carry data the caller's own rights would not show; owner-only results contain that, but the per-principal credential story on the roadmap is what makes rights survive into the upstream.
13. **Poisoning defences on the catalog.** The description cap, the provenance line, a pinned `content_hash` that flags a changed manifest for re-vetting, admission of a server to the catalog only by grant (so unvetted text is never in any caller's readable set and never ranked), and host-written examples carrying the user vocabulary. None of these makes a malicious tool safe to call; the permission check before dispatch and approval are the real defence.
14. **Keep the plain verb tools beside `cli`.** Weak models and step-by-step loops do worse in code mode; spec 171 already exposes both, and that should stay.
15. **Revise the drafted specs against the roadmap first.** The roadmap's reversals (full bash, `/.vfs/run` as rows, per-principal credentials, `pending`, `vfs serve`) and the missing ADRs 081 to 086 are tabled in study 07; items 1, 5, 11 and 12 here land in the same places, so one revision of 167, 169, 170 and 171 should carry both.

## 10. What this memo does not settle

- **Whether a pipe-and-text vfs shell composes tool work as reliably as JavaScript or Python.** The two shell comparisons had an interpreter one command away. The experiment: the same tasks run through `cli` with and without control flow and `jaq`, against a Monty `run_code` over the same verbs, on one strong and one small model, counting success, model turns and tokens.
- **Whether a real semantic vector leg closes the paraphrase gap on manifests** (hit@5 0.474 for paraphrases). The experiment: rerun study 08's frozen query set with a downloaded model2vec or an API embedder, in an environment that allows the download.
- **Whether host-written examples generalise.** The lift in study 08 is an upper bound. The experiment: examples written by one person, queries by another, on a larger corpus such as MCP-Zero's 2,797 tools or ToolRet, with a model choosing among the shortlist.
- **The share of agent calls whose output passes the display cap**, which sets how many run records a day the durable store holds. The experiment: a census of real `cli` outputs, or of Claude Code `tool-results` directories.
- **Whether chunking a manifest by section, or indexing path segments as a field, beats one card.** The experiment: field-weighting variants on the study 08 corpus.
- **The figures read only from search excerpts.** The papers in [04](studies/04-code-as-action-agents-and-the-evidence.md) and [06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) (RAG-MCP, ToolRet, "Is Bash All You Need?", "The Bitter Lesson of Tool Calling", the code-execution threat model), the Cloudflare and OpenAI pages, the Cursor, Manus and Vercel posts, and the AIMultiple, Check Point, Stacklok, StackOne, MCPProxy and Arcade benchmarks. The experiment: a read pass in a session whose network allows `arxiv.org`, `blog.cloudflare.com`, `developers.openai.com`, `vercel.com`, `cursor.com` and those vendors' hosts, correcting any figure here that differs.
- **The size of Cloudflare's generated TypeScript over a whole catalog, and its ranker's precision on real queries.** The experiment: install the codemode package from npm into an isolated experiment directory and measure it over the same spec.

## One line

Every code mode keeps the tool catalog out of the context and lets a program, not the model, carry results between calls; vfs can do that with its shell, without an isolate, and be the better choice by making the catalog and the results ordinary rows that `search` ranks and grants filter, which needs ranked search over manifests in the same landing as the catalog, durable owner-only results, a structured path between calls, and approval and per-user credentials at the door.
