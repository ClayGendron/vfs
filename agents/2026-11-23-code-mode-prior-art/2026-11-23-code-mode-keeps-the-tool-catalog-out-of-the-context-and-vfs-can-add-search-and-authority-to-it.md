# Code mode keeps the tool catalog out of the context; vfs can do the same with its shell over a searchable, rights-filtered catalog, and four pieces are missing

On 2026-11-23 the request was: research Cloudflare's Code Mode "and other similar" designs, as a reference design "so that our framework is a better choice", where the vfs code mode would be "calling tools and MCPs through our bash cli and storing them as files so they are searchable like anything else". The work ran autonomously in one session of about an hour: eight parallel studies, each a researcher with the same [brief](studies/00-brief.md), six over prior art, one over the vfs tree itself and one executed experiment over real tool catalogs. Forty-three reference repositories were cloned as siblings of the checkout, refreshed to their default branches and licence-checked ([refresh.log](studies/refresh.log), [licenses.log](studies/licenses.log)). The studies are in [studies/](studies/), and the scripts and outputs of every experiment are under [studies/experiments/](studies/experiments/). This memo is the synthesis. It commits vfs to nothing; it feeds the drafted specs 167, 169, 170 and 171.

Labels: EXECUTED means a command ran in this session and the claim reports its output. READ means read in a cited file or page. INFERRED means reasoning from the two. Sections 1 to 7 are evidence; section 8 onward is synthesis.

## The answer

Code mode is one idea with many spellings: the model is not shown the tool catalog; it is shown one or a few small, fixed tools, it writes a short program that finds and calls the tools it needs, and only what the program prints comes back into the context. Cloudflare, Anthropic, OpenAI, Codex and nine open-source projects all converged on that, plus a ranked search over tool text that returns about five tools, plus credentials kept on the host. The measured savings are real but mostly vendor-reported, and they come from two places: the catalog stays out of the context (a real 1,107-tool catalog costs about 140,000 tokens preloaded against about 100 for `ls /.vfs/mcp`, EXECUTED), and intermediate results stay out of the context when calls are chained. Code mode does not help single calls, weak models or step-by-step loops. vfs is unusually well placed: its shell is a parsed grammar dispatched to verbs, so it needs no isolate; every call already re-enters the rights check, which almost no studied design does; and its namespace can hold tool definitions and tool results as rows that `ls`, `grep` and `search` reach and grants filter. That combination, discovery and execution and authority behind one surface, exists nowhere in the field. But the drafted specs do not deliver it yet. Four pieces are missing: ranked search over tool definitions (the drafts serve tools as in-memory views that `search` never reaches), a durable, owner-only home for tool results, a structured-data path between calls in the shell, and approval and per-user credentials at the point a side effect leaves vfs.

## 1. What code mode is, in Cloudflare's three spellings (READ)

Cloudflare's Code Mode turns MCP tools into a TypeScript API and gives the model one tool that takes code. The code runs in a fresh V8 isolate created by the Worker Loader, with the network blocked (`globalOutbound: null`); tool calls leave the isolate only over Workers RPC to bindings the host holds, so no credential enters the sandbox ([01](studies/01-cloudflare-code-mode.md) F10 to F14). The model gets back the return value and captured console output, cut structurally at about 6,000 tokens.

The same idea ships in three shapes ([01](studies/01-cloudflare-code-mode.md) F2): `createCodeTool`, one `code` tool with every generated TypeScript declaration preloaded; a durable runtime whose one tool lists only connector names, with methods discovered from inside the sandbox through `codemode.search` and `describe`; and the production Cloudflare API server, two tools, `search` and `execute`, both taking code. In every case the model writes JavaScript; TypeScript is only the documentation language.

Discovery is weak in a revealing way. Inside the sandbox, search is a lexical, field-weighted ranker over tool names and descriptions only, capped at 50 results. On the production server, `search` is the model's own code scanning the whole 27 MB dereferenced API spec, in a fresh isolate, on every call; there is no index ([01](studies/01-cloudflare-code-mode.md) F6, F7).

Authority stops at the door. The SDK carries no caller identity at the call boundary; the production server runs each user's own token with scope step-up and a guard against writes that spend money. Cloudflare's own docs say: "Hiding a token does not limit what that token can do." ([01](studies/01-cloudflare-code-mode.md) F14, F15.) Approvals work by abort and replay against a durable log, per method rather than per argument, which forces the program to be deterministic (F17).

## 2. The field converged on six moves (READ)

Across Cloudflare, Anthropic, OpenAI, Codex and nine open-source projects, six choices recur ([02](studies/02-anthropic-and-openai.md), [03](studies/03-open-source-code-mode-implementations.md)):

1. **A few fixed meta-tools, not the catalog.** Run a program; search for a tool; read one tool's contract. The model's context pays a constant cost whatever the catalog holds.
2. **Find, then read.** A cheap listing or ranked search first (name plus one line, about five results), the full signature only for tools the model picked. Anthropic's tool search returns five by default and holds up to 10,000 deferred tools; Codex and OpenAI ship the same shape.
3. **A typed signature with prose as the contract.** Six of the nine open-source projects render JSON Schema as a TypeScript declaration with doc comments, even where the model writes untyped JavaScript.
4. **Tools namespaced by server**, as `server.tool`.
5. **Secrets on the host.** The sandbox holds only a way to ask the host to call.
6. **Code sees full results; the model sees only what the code prints**, under a timeout and an output cap. Anthropic: "only the final code output"; OpenAI: `program_output`; Codex: `text()`, up to 10,000 tokens.

What the shipped tool searches index ([02](studies/02-anthropic-and-openai.md), [06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) F3): Anthropic's regex and BM25 variants index names, descriptions, argument names and argument descriptions. Codex's readable BM25 indexes the name, the name split on underscores, the description, the schema text and the MCP server, title and namespace. Docker's gateway and the agentic-community registry also weight the server's name. Spring AI's index tokenizes only the description, though its tool description promises more.

Where the field splits ([03](studies/03-open-source-code-mode-implementations.md)): the engine (a real V8 isolate in UTCP and pctx; an embedded interpreter in OpenCode, goose's Boa and FastMCP's Monty; or the agent's own shell with no sandbox in mcporter and the UTCP CLI); ranked search against plain matching; whether each nested call is judged as the caller (only executor, FastMCP and goose); and whether a person can approve a call before it runs (only executor, goose and OpenCode). Codex rebuilds every call made from a script as an ordinary call into the same tool runtime, so approvals and the sandbox still apply; Anthropic's `allowed_callers` is documented as "not a security boundary" ([02](studies/02-anthropic-and-openai.md)).

The newest movement runs away from pure code. executor added a direct `call` tool on 2026-10-12; goose and FastMCP document that single-tool tasks are slower in code mode; UTCP now tells shell agents to use its CLI rather than its MCP server ([03](studies/03-open-source-code-mode-implementations.md)).

Three readings follow. First, the token savings are real where the catalog is large or results are large and filterable, and absent where each call depends on the model reading the previous result. Second, code as the action space wins on chaining calls for strong models, by about 20 points of success in the one controlled comparison, and does not help, or hurts, weak models. Third, no source anywhere compares a shell-only surface against Python or JavaScript code mode on the same tasks, and none of the nine open-source projects ships a reproducible evaluation.

Security evidence is one-sided ([04](studies/04-code-as-action-agents-and-the-evidence.md)): a threat-model paper names 16 attack classes for model-written code against MCP servers; Check Point escaped a Cloudflare Code Mode sandbox through a workerd bug starting from one prompt injection; CaMeL shows the other route, the interpreter itself enforcing policy.

## 4. What a catalog costs as context, measured (EXECUTED)

The Cloudflare API spec shipped today has 3,776 operations. Full tool definitions are about 1.76M tokens, required parameters only about 0.20M, and even a one-line names-and-summaries index is about 84,000 tokens ([01](studies/01-cloudflare-code-mode.md) F9). A flat listing of a catalog that size is unusable.

Study 08 measured 1,107 real tools on 30 servers, read as data from GitHub's `__toolsnaps__` (149 tools), Alibaba Cloud DevOps' `tools.json` (203) and Docker's MCP registry (755). Tokens are chars/4, an estimate; bytes are exact ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) F2, F7, F8).

| What the model is shown | Estimated tokens |
|---|---|
| every full schema preloaded | 140,303 |
| names only | 6,015 |
| name plus first sentence | 22,328 |
| `ls /.vfs/mcp` (the server listing) | 103 |
| one server's `ls`, median | 53 |
| one manifest, median / max | 153 / 1,810 |
| a vfs `search` with limit 5, median rendered | about 515 (2,062 bytes) |

GitHub's server alone is about 39,000 tokens, 84,000 with its output schemas. The difference between preloading and browsing is three orders of magnitude, and a search plus one read costs about 600 tokens.

The same census is the "real-server schema census" spec 170 commissions before it is built ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) Part A). Of 2,241 properties, 93.1% are strictly scalar and 97.2% take a plain word under spec 170's JSON-then-string rule; 89.5% of tools need only plain words; no tool needs the `--json` fallback to be reachable; dotted flags for nested objects would rescue one tool of 495. Three amendments surfaced: GitHub types 155 integer IDs and page sizes as `number`, which the spec coerces to float; GitHub mixes camelCase and snake_case property names (94 and 165); and 28 objects are free maps with no declared properties. Only GitHub annotates its tools, and 28 of its 80 tools that are not read-only carry no `destructiveHint`, so annotations cannot carry governance.

## 5. Tools as commands and results as files, in the field (READ, EXECUTED where marked)

MCP as a CLI has three shapes ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)): a generic client (philschmid mcp-cli, mcpc, `mcporter call`, mcp2cli), a generated binary per server (`mcporter generate-cli`, clihub, mcp2cli-rs), and tools as commands inside an agent shell (`@just-bash/executor`). mcpc's own table counts 19 such clients, 13 active. EXECUTED against a fake server written for the study: every client sent a call that left out the schema's only required argument; philschmid mcp-cli exits 0 when the tool returns `isError: true`; mcp2cli splits `a,b` into two array items; only mcp2cli refuses a bad integer or an out-of-enum value before the call goes out; no client spills a 200,000-character result to a file. Spec 170 §2's flag table is stricter than every implementation surveyed, and the experiment shows each of its rules is needed. mcporter's docs say a generated CLI bypasses the calling client's approvals, policy and audit trail.

Tools as files: Anthropic's pattern post lays tools out as `servers/<server>/<tool>.ts` for the agent to explore with `ls` and read, but that is a pattern, not a product ([02](studies/02-anthropic-and-openai.md)). pctx's filesystem mode is the closest shipped analogue to vfs: each tool is a `.d.ts` file in a read-only tree the model explores with bash, and a second tool runs TypeScript to make the calls ([03](studies/03-open-source-code-mode-implementations.md)). Cursor writes MCP tool descriptions to a folder per server. mcpfs has not moved upstream since the 2026-09-04 memo; agfs adds Plan 9 style control and result files for services ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)).

Results as files: Claude Code moves a large output to the session's `tool-results` directory (Bash over about 30,000 characters with a 2,000-character preview; MCP over 25,000 tokens or 50,000 characters) and deletes it after 30 days. deepagents evicts results over 80,000 characters to `/large_tool_results/<tool_call_id>` with a head-and-tail preview and tells the model to grep that directory; it has no expiry, and its offload write skips its own permission rules. Cursor writes long outputs, terminals and chat history to files. None of these attaches an owner to a stored result ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)). Skills (Anthropic's published format) preload only a name and description, about 347 characters a skill measured over the 19 published skills, EXECUTED, and read the body on demand ([02](studies/02-anthropic-and-openai.md)).

## 6. Finding the right tool (READ, EXECUTED where marked)

Accuracy falls as the catalog grows, in every measurement found ([06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) F1): RAG-MCP reports 13.62% selection with every tool in context against 43.13% when one is retrieved; LiveMCPBench attributes about half of all failures to retrieval. Tool retrieval is hard information retrieval: on ToolRet the best general retriever reaches NDCG@10 of 33.83, and vendor benchmarks put BM25 top-1 at 14 to 34% over a few hundred to a few thousand tools, with lexical-plus-embedding hybrids near 94% (F2). Adding example queries to a tool's text is the most reliable fix found (Tool2Vec, Re-Invoke, Toolshed; F4). Descriptions are mostly poor: 56% of 856 MCP tools have an unclear purpose, and rewording a description shifts selection up to 10× (F5). A server-then-tool hierarchy saves tokens but does not retrieve better (F6). Poisoned descriptions win both retrieval and selection: ToolHijacker reports a 100% retrieval hit rate and about 96% attack success (F7).

vfs's own `search` over tool manifests, EXECUTED in study 08 on the 1,107-tool corpus with 65 labelled queries written and hash-frozen before retrieval ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md) F11 to F17):

| Manifest content, lexical leg | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---|---|---|
| name and description | 0.477 | 0.569 | 0.677 | 0.547 |
| plus parameter lines | 0.492 | 0.677 | 0.738 | 0.591 |

Queries that use the tool's own words reach hit@5 0.848; paraphrases reach 0.474, because the lexical leg has no stemming ("label" misses "labels"). `grep` on key words is worse at hit@1 (0.25 to 0.32) and returns 75 to 101 candidate files. Adding servers costs precision: GitHub queries' hit@1 drops from 0.478 against GitHub alone to 0.370 against the whole corpus. Two host-written example requests per tool lift GitHub hit@1 from 0.478 to 0.848; on the 13 queries that share little wording with the examples the lift is 0.385 to 0.846, an upper bound because one researcher wrote both. The offline hashing embedder, fused in as a vector leg, lowered hit@1 from 0.49 to 0.37; no semantic embedder was available offline.

Study 06's smaller experiment over 81 real tools found the same shape: putting the name and server into the indexed body took identifier queries from hit@1 0.20 to 1.00 and task queries' hit@5 from 0.54 to 0.73 ([06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) F10). The reason is structural: vfs indexes a chunk's content, not the file's path (`src/vfs/models/chunk.py:93-119`, F9), so a manifest must carry its own name and server in its body.

## 7. Where vfs stands today (READ, EXECUTED where marked)

Built ([07](studies/07-where-code-mode-lands-in-vfs-today.md)): the 25 gated verbs, one `Result`, and an `Authority` judged against row-level grants on every call. Drafted and not built: the shell (spec 167), programs and the bin union (169), tools and MCP servers as views under `/.vfs` (170), the MCP adapter with one `cli` tool (171), the Python guest (172). There is no shell, no `cli`, no `/.vfs` view, no MCP serving or client, and no `mcp` or `wasm` extra.

Three findings from the probe of the live tree, EXECUTED: `run` exists as a verb (`src/vfs/base.py:1605`) but no storage serves it, and it answers `vfs.unsupported` even to a caller who cannot see the path, because the capability check runs before the permission check. A `TOOL.md` stored under `/.agents/tools/` is an ordinary row today: `search` ranked it first, `grep` and `glob` found it, and a posture of `none` plus a grant hid it from one user and not another. Tools are already searchable files, by accident.

The drafts walk away from that. Spec 169 §a7 retires `/.agents`; spec 170 generates `/.vfs/tools` and `/.vfs/mcp` in memory, so they are not indexed and unscoped searches never reach them; spec 170 §6 serves `ls`, `type`, `--help` and in-memory `grep` over manifests and leaves ranked search over catalogs as "a later item". The default record of a call (169c) is an in-memory ring of 64 calls per `Authority`, lost on restart and never indexed. There is no `jq` in 0.1.0, and an MCP tool's structured content never enters the pipe. Spec 170 gives each MCP server one host credential; per-user credentials exist only as a roadmap story. None of 167, 170 or 171 has an approval step, and a single `cli` tool hides every side effect from a host's per-tool approval. A re-sent `cli` line runs again. Study 07 also tables where the specs disagree with one another and with the code: `/.agents` against `/.vfs`, `/.agents/bin` against `/opt/bin`, `glean` and `graph` in the specs against `search` and `traverse` in the code, and ADRs 081 to 086 cited everywhere with no file in the tree.

## 8. What a vfs code mode should be (INFERRED)

The request names two halves: tools and MCP servers called through the vfs shell, and tools stored as files searchable like anything else. The evidence supports both, and says which parts of the field to take and where vfs can go further.

**Take from the field.** One fixed-size `cli` description that names the grammar, the verbs and where tools live, lists no tool, and is identical for every caller, because MCP clients cache tool lists (Cloudflare's rule, [01](studies/01-cloudflare-code-mode.md) F15). Find before read, with about five ranked results. Credentials only at the door: an MCP connection's token lives with the router's connection owner and is never a file, a `stat` field or a value in the pipe. Code sees full results and the model sees only what is printed, which the vfs shell already does by construction: the pipe carries whole rows and only the display is capped. Bounded output with one recognizable truncation marker. Errors that name the real alternatives: `command not found` names the nearest programs and the `search` that finds tools; a `permission` error names the rung it needs.

**Do differently, because the language is a grammar over a governed namespace.** No isolate per call: no foreign code runs, so the parser is the sandbox, and there is no spawn cost and no concurrency ceiling. Index the catalog and never scan it per call, because a read must cost in proportion to what it returns (AGENTS.md, "The reference deployment"). Never list a large catalog flat; group or page it, and say how many entries were withheld. Keep the caller's authority across the hop: every stage of a pipeline re-enters the gate, as Codex does and as Cloudflare's SDK does not. Flags rather than TypeScript types as the generated surface, which is lossless where TypeScript drops constraints, because `--help` renders the schema instead of translating it.

**Where vfs can be the better choice.** Three properties no studied design combines. First, discovery is filtered by rights: a tool the caller may not run is never listed, never ranked and never costs a token, because the catalog is rows behind grants. Anthropic searches whatever the request carries, Codex whatever is registered, and the registry that does filter does so after ranking. Second, results are owned: a stored tool result is a row born with an owner-only grant, and sharing it is an explicit, audited `cp` judged by the destination's grants. Every results-as-files design studied is single-user with ad hoc retention. Third, one surface for discovery, execution and authority: pctx's shell reads the catalog but a second language calls the tools; mcporter's shell calls the tools but has no catalog search; executor's catalog is a database but its language is JavaScript. A vfs shell that browses and searches the catalog and runs the call, against the same rights-judged namespace as the data, would be the first to put all three behind one surface. That claim is unmeasured and should not be made in public until section 10's first experiment has run.

**Where vfs would be weaker.** General computation between calls: JavaScript gives loops, maps, joins and JSON reshaping in one execution; the spec 167 subset has no control flow and the 0.1.0 catalog has no JSON program. Typed nested request bodies, which TypeScript expresses and flags push to `--json`. A proven isolation primitive for untrusted code, which vfs will need if it ever admits a general language beside the shell (the spec 172 guest runs under wasm, which is its own boundary). Durable approval with rollback of side effects in upstream systems; vfs's trash covers its own rows only. Per-API hardening such as Cloudflare's guard against writes that spend money, which a generic MCP projection will not provide without a per-server policy hook.

## 9. What it means for specs 167, 169, 170 and 171 (INFERRED)

Each item names the evidence it stands on. Items marked "behaviour" would change what a drafted spec decides and come back as a report under the working agreement; none was acted on.

1. **Ranked search over tool definitions lands with the catalog, not later (behaviour, spec 170 §6).** Every vendor ships one; vfs lexical search beat key-word `grep` at hit@1 by 0.15 to 0.25 on the same files ([08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md)); the catalog is thousands of rows against ten million files, a rounding error on the index-visit multiplier. This needs manifests that the ordinary index reaches: stored rows of a catalog storage, or a view whose manifests are scored at query time. It is also the reconciliation the request asks for: "stored as files so they are searchable like anything else" is today's accidental `/.agents` behaviour, and the drafts retire it.
2. **A manifest written to be found.** In order: a heading with the exact tool name; a provenance line with the server name and title and the trust line spec 170 already requires; the capped description; a short, host-written "Use when" block of example requests in a user's words, never taken from the server; then arguments and returns, with the output schema. The machine-readable JSON Schema sits in a separate section or sibling entry so it does not dilute the card ([06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md), [08](studies/08-real-tool-catalogs-measured-as-context-and-as-searchable-files.md)).
3. **The model starts at the listing.** The `cli` description plus one hint line, "tools live under `/.vfs/mcp` and `/.vfs/tools`; `ls` them or `search` them", costs a dozen tokens; `ls /.vfs/mcp` about 100. Names-only or names-plus-first-sentence preambles are worth it only for a single server of a few dozen tools.
4. **No non-semantic vector leg in catalog search.** The hashing embedder lowered hit@1 from 0.49 to 0.37; a catalog ranks lexically unless a real embedding provider is configured.
5. **Durable, owner-only results (behaviour, spec 169c).** `/.vfs/run/<call-id>/` as ordinary rows rather than an in-memory ring, so `grep`, `glob` and `search` reach them; each record born with an owner-only grant to the calling principal; sharing by `cp`. Persist only what earns it, at the reference deployment's 150,000 agent calls a day: spilled outputs over the display cap, tool result rows, and records the agent saves explicitly. Persisting every call would add about 4.5 million rows over 30 days, close to half the corpus ([05](studies/05-tools-as-files-and-tools-as-cli-commands.md)). A declared retention, 30 days as Claude Code uses, applied by the sweep that empties the trash. Lexical postings by the partial index pass; embeddings off by default for run records.
6. **The spill marker names the path.** When output passes the 32,768-character display cap, the marker names `/.vfs/run/<call-id>/stdout` and carries a head-and-tail preview, so the next command is `grep` or `sed -n` over it. A failing call is not spilled; its stderr gets a head-and-tail excerpt. A tool may declare a higher threshold in its manifest. An empty result says so explicitly ("ran and produced no output"), which SWE-agent found helped and spec 167 leaves optional.
7. **Flag table amendments before spec 170 is built.** Coerce an integer literal under `number` to a JSON integer; give camelCase and snake_case names one consistent kebab alias; consider `--x key=value` for free-map objects; add `--x @<vfs path>` for any string property so a stored result feeds the next call without pasting (`--body @/.vfs/run/<id>/stdout`). Drop the planned dotted-flag pass. Keep every strict refusal; the CLI experiment shows each is needed.
8. **The shell needs a structured path to match code mode's chaining gain (behaviour, specs 167, 169, 172).** In order: control flow and functions; a JSON program on the pipe (`jaq`); output schemas shown by `cat` of a manifest; and the spec 172 Python guest reachable from the shell in one command. Every bash-only win in the evidence had Python and `jq` one keystroke away ([04](studies/04-code-as-action-agents-and-the-evidence.md)).
9. **Loops steer to batches, and the door paces fan-out.** A loop of 10,000 `stat` calls is one chunked verb call in vfs; the shell should steer to the batched form, and its budget should count verb calls. A pipeline that fans one tool call over many rows needs bounds at the `_invoke` door, per pipeline and per server, as Cloudflare's sandbox paces its own outbound requests.
10. **A counted test that authority survives the hop.** A tool reached through a pipe, `xargs` or a loop is judged exactly as when typed alone. This is the strongest claim vfs can make against the field, and it should be pinned, not asserted.
11. **Approval and replay safety at the door (behaviour, specs 170 and 171).** A single `cli` tool hides every side effect from a host's per-tool approval, so vfs must provide the stop: a pending row carrying the computed arguments and the rung, with the pipeline stopped before the call and no lock held while a person decides. After a failed pipeline, vfs knows each verb's rung from one table and can say which steps mutated and whether re-running is safe. Tools with side effects should not run inside a loop or as a non-first stage unless the host allows it.
12. **Per-user credentials across the MCP hop (behaviour, spec 170).** One host credential per server means a result can carry data the caller's own rights would not show; owner-only results contain that, but the per-principal credential story on the roadmap is what makes rights survive into the upstream.
13. **Poisoning defences on the catalog.** The description cap, the provenance line, a pinned `content_hash` that flags a changed manifest for re-vetting, admission of a server to the catalog only by grant (so unvetted text is never in any caller's readable set and never ranked), and host-written examples carrying the user vocabulary. None of these makes a malicious tool safe to call; the permission check before dispatch and approval are the real defence.
14. **Keep the plain verb tools beside `cli`.** Weak models and step-by-step loops do worse in code mode; spec 171 already exposes both, and that should stay.

## 10. What this memo does not settle

- **Whether a vfs shell composes tool work as reliably as JavaScript or Python.** No source measures a shell-only surface against code mode. The experiment: the same tasks run through `cli` with and without control flow and `jaq`, against a Monty `run_code` over the same verbs, on one strong and one small model, counting success, model turns and tokens.
- **Whether a real semantic vector leg closes the paraphrase gap on manifests** (hit@5 0.474 for paraphrases). The experiment: rerun study 08's frozen query set with a downloaded model2vec or an API embedder, in an environment that allows the download.
- **Whether host-written examples generalise.** The lift in study 08 is an upper bound. The experiment: examples written by one researcher, queries by another, on a larger corpus such as MCP-Zero's 2,797 tools or ToolRet.
- **The share of agent calls whose output passes the display cap**, which sets how many run records a day the durable store holds. The experiment: a census of real `cli` outputs, or of Claude Code `tool-results` directories.
- **Whether chunking a manifest by section, or indexing path segments as a field, beats one card.** The experiment: field-weighting variants on the study 08 corpus.
- **The figures read only from search excerpts.** The papers in [04](studies/04-code-as-action-agents-and-the-evidence.md) and [06](studies/06-finding-the-right-tool-retrieval-over-tool-catalogs.md) (RAG-MCP, ToolRet, the two 2026 bash and CodeAct papers, the code-execution threat model), the Cloudflare and OpenAI pages, and the Cursor, Manus and Vercel posts. The experiment: a read pass in a session whose network allows `arxiv.org`, `blog.cloudflare.com`, `developers.openai.com`, `vercel.com` and `cursor.com`, correcting any figure here that differs.
- **Whether vfs needs durable, resumable approval** (Cloudflare's abort and replay, OpenCode's snapshot) or only a stop-before-the-call gate. This waits on a spec for approval; study 07 records the roadmap's `pending` as undecided.
- **Whether the roadmap's reversals of the drafted specs are decided** (full bash, `/.vfs/run` as rows, per-principal credentials, `pending`, `vfs serve`), and where ADRs 081 to 086 live. Study 07 tables them; deciding them is a spec revision, not research.

## One line

Every code mode keeps the tool catalog out of the context and lets a program, not the model, carry results between calls; vfs can do that with its shell, without an isolate, and be the better choice by making the catalog and the results ordinary rows that `search` ranks and grants filter, which needs ranked search over manifests in the same landing as the catalog, durable owner-only results, a structured path between calls, and approval and per-user credentials at the door.
