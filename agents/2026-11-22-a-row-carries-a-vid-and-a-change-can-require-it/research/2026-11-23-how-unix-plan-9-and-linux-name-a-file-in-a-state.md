## The answer

Every system studied names "this file, in this state" by two parts: an identity that outlives a rename, and a counter that moves when the file changes. Plan 9 calls them `qid.path` and `qid.vers`, Unix an inode number with a generation and, on Linux, `i_version`. The spec's pair, the entry id and the version, is the same pair, and what moves the spec's version is what moves theirs: a directory's counter moves when a direct child is made, removed or renamed, and never when a child's body changes. Where the pair is handed to a remote caller as a validator, Unix hides it (an NFS file handle is opaque, and Linux does not let user space read its change counter), which is what the spec's digest does; Plan 9 shows the qid in clear, which the spec does not. No system studied lets a write, a remove or a rename require the pair: that is the spec's one real addition, taken from HTTP, with NFSv3's guarded `SETATTR` and git's `update-ref` as the nearest relatives. The spec's refusals line up with the errnos (`EEXIST`, `ENOENT`, `ENOTEMPTY`, `ESTALE`, `EXDEV`, `EBUSY`) with one deliberate exception it already states, a required etag met by a directory. The spec departs in eleven places (rows 11 to 21 of the table in section 7); it gives a reason for most, names the prior art for almost none, and Article 3 of the constitution requires each to be named in a numbered decision. The text that would do so closes this memo.

## 1. How each system names a file in a state

1. READ. Plan 9: a qid is a one-byte type, a four-byte version and an eight-byte path, and two files on a server are the same exactly when their qids are equal (`plan9/sys/man/5/0intro:419-431`). The path is unique among all files in the hierarchy, and a file deleted and made again under the same name "should be different" in its path (`0intro:432-435`). The version is "typically" incremented each time the file is modified (`0intro:436-437`). The qid is public: `stat` returns it, and `mv` decides whether two names are one file by comparing type, path and version (`plan9/sys/src/cmd/mv.c:206-225`).
2. READ. Plan 9 servers keep the promise unevenly. fossil's version is a per-entry counter that one helper increments with the modification time (`plan9/sys/src/cmd/fossil/file.c:1704-1717`), called on a write (`file.c:705`). lib9p adds one after every write (`9front/sys/src/lib9p/srv.c:586-592`), and 9front's ramfs adds one of its own beside it (`9front/sys/src/cmd/ramfs.c:79-87`, `233`), so a write there moves the version by two. Readers depend on the counter: the kernel's mount cache finds a cached file by path and drops its data when the version differs (`plan9/sys/src/9/port/cache.c:226-244`).
3. READ. Unix: V7's on-disk inode has no generation, only mode, link count, owner, size, addresses and three times (`unix-history-repo/usr/sys/h/ino.h:5-16`), so an inode number reused after a delete names another file with nothing to tell them apart. The generation was added for NFS. On Linux a file handle is the inode number with a 32-bit generation (`linux/include/linux/exportfs.h:33-42`), and ext4 answers `ESTALE` when the generation in a handle is not the inode's (`linux/fs/ext4/super.c:1566-1584`). FreeBSD's FFS does the same (`freebsd-src/sys/ufs/ffs/ffs_vfsops.c:1989-1998`). libfuse states the rule for a file system author: an inode number reused after a delete must take a generation never used before (`libfuse/include/fuse_lowlevel.h:74-84`).
4. READ. Linux's change counter: `i_version` must appear larger after any change that would move the change time, even when the time itself does not move (`linux/include/linux/iversion.h:10-20`). An observer learns only that something changed, never what or how much (`iversion.h:33-37`). The file system must move it on a namespace change in a directory (`iversion.h:43-47`). User space cannot read it: the `statx` bit for it is defined in a kernel-internal header "for now" (`linux/include/linux/stat.h:64-70`) and is masked out of every reply (`linux/fs/stat.c:706-710`).
5. READ. NFS reports a directory's counter around each change to it: the reply to a create, a remove or a rename carries the directory's change attribute before and after, and a flag saying the two were read atomically (`linux/fs/nfsd/xdr4.h:205-209`). This is the fact the spec's "Left as it is" calls "the parent's new etag on the result of a change" and declines to return publicly.
6. READ. Elsewhere. git names a working file's state without reading it by its stat data: two times, the device, the inode, the owner and the size (`git/statinfo.h:16-24`). It names a ref's state by its object id. Postgres names a row version by `xmin` and `ctid`, and warns that `ctid` moves on every update and is no identifier (`postgres/doc/src/sgml/ddl.sgml:1564-1573`). SQLite names the whole database's state by a data version that only other connections' changes move (`sqlite/src/sqlite.h.in:1193-1198`).
7. INFERRED, from RFC 9110 as recalled. HTTP's entity tag is an opaque string a server issues for one representation; a strong tag changes whenever the representation does; a client compares tags and never parses them.

## 2. What moves a directory's own counter

1. READ. Plan 9's manual speaks only of the time: a directory's modification time is the time of the most recent remove, create or wstat "of a file in the directory" (`plan9/sys/man/5/stat:149-154`). fossil moves the directory's version with that time on a create (`file.c:505`), a remove (`file.c:1149`) and a wstat, a rename among them (`file.c:900`). A write to a child does not reach the parent: the lines that would pass the change upward are commented out (`file.c:1719-1723`). cwfs moves the parent on a create (`plan9/sys/src/cmd/cwfs/9p2.c:948`) and on a remove, before it checks that a directory is empty (`plan9/sys/src/cmd/cwfs/9p1.c:1155`, `1187`), so a refused remove still moves it.
2. READ. The servers disagree at the edges. 9front's cwfs moves the parent on a rename (`9front/sys/src/cmd/cwfs/9p2.c:1787-1788`) and Plan 9's does not. hjfs moves the parent on a create (`9front/sys/src/cmd/hjfs/fs2.c:150-153`) and not on a remove (`fs2.c:636-655`). Plan 9's ramfs moves the parent's time and never its version (`plan9/sys/src/cmd/ramfs.c:483-486`). No server moves a directory when a child's body changes.
3. READ. Linux: ext4 sets the directory's times and increments its `i_version` when an entry is added (`linux/fs/ext4/namei.c:2148-2150`); a rename must update the times of both parents and the change time of the renamed file (`linux/fs/libfs.c:831-833`), and pjdfstest holds every file system to the last (`pjdfstest/tests/rename/22.t:22-29`). A write to a file updates the times of that file's own inode and reaches no parent (`linux/mm/filemap.c:4411-4422`).
4. EXECUTED. The spec's version moves the same way on both engines (`probes/p01_what_moves_an_id_and_a_version.py`, in `probes/output.txt`): a directory at version 1 goes to 2 when a child is made, stays at 2 when the child is rewritten or edited, stays at 3 when a grandchild is made, and moves on a child's delete, restore, rename, move in, move out and copy in. A grant, a posture and a rebuild move nothing. One difference: a rename inside one directory moves that directory's version by two, since both parents are bumped and they are the same row.

## 3. Whether a change can require the name

1. READ. 9P cannot. A write, a remove and a wstat carry a fid and no version. A wstat may leave a field alone with a "don't touch" value (`plan9/sys/man/5/stat:233-240`), and fossil refuses a wstat whose version is neither that value nor the current one (`plan9/sys/src/cmd/fossil/9p.c:168-172`). That is a comparison, written to stop a client changing the version and not as a precondition, and it exists for no other request.
2. READ. POSIX cannot either. The nearest thing in the Unix family is NFSv3's guarded attribute change: the server compares the change time the client sends with the file's and refuses when they differ (`linux/fs/nfsd/vfs.c:572-576`).
3. READ. git can, for a ref: `update-ref` stores the new value only after verifying that the current value is the old one given, and an all-zero old value means the ref must not exist (`git/Documentation/git-update-ref.adoc:21-28`, `git/refs.h:818-823`). The expected value and "must be absent" share one slot, which is the shape of the spec's mark `ABSENT`.
4. INFERRED, from RFC 9110 as recalled. HTTP can: `If-Match` with a tag makes a change conditional on the tag, and a failure is 412. `If-Match: *` requires that something exists. Create-only is the other header, `If-None-Match: *`.
5. READ and EXECUTED. Postgres is where the spec's guard is proven. At REPEATABLE READ an update of a row a concurrent transaction changed and committed is rolled back with a serialization failure (`postgres/doc/src/sgml/mvcc.sgml:536-558`), and the same failure is raised when `ON CONFLICT` meets a row the snapshot cannot see (`postgres/src/backend/executor/nodeModifyTable.c:395-404`). `probes/p04_the_quoted_statements_at_each_isolation_level.py` sent the spec's statements to Postgres 19.0 and saw exactly that: SQLSTATE 40001 at REPEATABLE READ, and no row matched at READ COMMITTED.

## 4. Exclusive creation

1. READ. Linux: `O_CREAT|O_EXCL` answers `EEXIST` whenever the open created nothing, whatever kind the occupant is, and only after that does a plain create over a directory answer `EISDIR` (`linux/fs/namei.c:4672-4676`). `O_EXCL` also stops a trailing symbolic link from being followed (`linux/fs/open.c:1272-1275`). pjdfstest expects `EEXIST` over a regular file, a directory, a fifo, both devices, a socket and a symbolic link (`pjdfstest/tests/open/22.t:13-15`). FreeBSD answers the same (`freebsd-src/sys/kern/vfs_vnops.c:395-397`).
2. READ. V7 had no exclusive create: `creat` on a name that exists opens it for writing and truncates it (`unix-history-repo/usr/sys/sys/sys2.c:98-117`).
3. READ. Plan 9: at the protocol a create of a name that exists is rejected, and the system call then falls back to an open with truncation (`plan9/sys/man/5/open:154-166`). A program that needs an atomic create sets `OEXCL`, and the kernel then gives up with "exists" (`open:223-232`, `plan9/sys/src/9/port/chan.c:1548-1552`).
4. READ. The shell: with `noclobber`, `>` refuses an existing regular file and `>|` overrides it; `>>` is not subject to it. oils opens with `O_EXCL` when the name is absent and answers `EEXIST` for an existing regular file (`oils/core/process.py:416-433`). busybox ash does the same and prints "can't create" (`busybox/shell/ash.c:5556-5590`). brush does the same through a create-new open (`brush/brush-core/src/interp.rs:1794-1826`). mvdan-sh has no `noclobber` at all (`mvdan-sh/interp/api.go:927-934`) and its interpreter does not run `>|` (`mvdan-sh/interp/runner.go:1663-1675`). Without the option every shell replaces.

## 5. Rename onto an occupied destination

1. READ. POSIX rename replaces: libfuse's contract is that an existing target "should be atomically replaced" (`libfuse/include/fuse_lowlevel.h:446-448`). The exceptions are kinds: a directory over a non-directory is `ENOTDIR`, a non-directory over a directory is `EISDIR` (`linux/fs/namei.c:3709-3715`), and a directory over a non-empty directory is `ENOTEMPTY` (`linux/fs/ext4/namei.c:3898-3902`), where pjdfstest accepts `EEXIST` or `ENOTEMPTY` (`pjdfstest/tests/rename/20.t:18-20`).
2. READ. The form that never replaces exists beside it: `RENAME_NOREPLACE` (`linux/include/uapi/linux/fs.h:59`) makes an occupied target `EEXIST` (`linux/fs/namei.c:3877-3878`), and libfuse requires a file system to honour it (`fuse_lowlevel.h:459-462`).
3. READ. Plan 9 never replaces: "it is an error to change the name to that of an existing file" (`plan9/sys/man/5/stat:190-193`), which fossil enforces (`plan9/sys/src/cmd/fossil/file.c:839-843`). Its `mv` therefore removes the target first, so a replacement there is not atomic (`plan9/sys/src/cmd/mv.c:107-112`). V7's `mv` did the same with `unlink` and `link` (`unix-history-repo/usr/src/cmd/mv.c:92-118`).
4. READ. The tools: `mv -n` skips an occupied destination silently and exits 0 in uutils (`uutils-coreutils/src/uu/mv/src/mv.rs:836-842`), busybox (`busybox/coreutils/mv.c:121-123`) and toybox (`toybox/toys/posix/cp.c:451-452`); sbase's `mv` has no such flag and always replaces (`sbase/mv.c:13-36`). None of the three uses `RENAME_NOREPLACE`: each tests for the destination and then renames, so the refusal is not atomic.

## 6. Removing a directory, and the errno of each refusal

1. READ. A directory must be empty to be removed: Plan 9's `remove(2)` says so (`plan9/sys/man/2/remove:17-19`) and fossil answers "directory not empty" (`plan9/sys/src/cmd/fossil/file.c:1206-1207`); pjdfstest expects `EEXIST` or `ENOTEMPTY` from `rmdir` (`pjdfstest/tests/rmdir/06.t:15-17`); V7's `rmdir` was a program that read the directory and printed "not empty" (`unix-history-repo/usr/src/cmd/rmdir.c:65-72`). An `unlink` of a directory is `EISDIR` on Linux (`linux/fs/namei.c:3714-3715`) and `EPERM` by POSIX (`freebsd-src/sys/kern/vfs_syscalls.c:2102-2103`, `pjdfstest/tests/unlink/08.t:14-15`).
2. READ. A stale name is `ESTALE`, "Stale file handle" (`linux/include/uapi/asm-generic/errno.h:100`), and Linux answers it for every handle it cannot decode, whoever issued it (`linux/fs/fhandle.c:278-281`). Plan 9 has no errno: an error is a string, and the servers word the same refusal differently.
3. READ. The repository already names an errno for each kind (`src/vfs/results/kinds.py:67-90`): `not_found` is `ENOENT`, `exists` is `EEXIST`, `wrong_kind` is `ENOTDIR` or `EISDIR`, `not_empty` is `ENOTEMPTY`, `conflict` is `ESTALE`, `busy` is `EBUSY`, `cross_mount` is `EXDEV`, `unsupported` is `ENOSYS` or `ENOTSUP`, `invalid` is `EINVAL`.

## What this memo does not settle

- Whether a guarded change should answer as HTTP does when the precondition fails, with a kind of its own, and not as `ESTALE` does. The repository settled `conflict` in Article 1.5, and nothing read here argues against it.
- Whether the public result of a change should carry the parent's counter before and after, as NFS's reply does. The experiment is the count of statements a `bumped` report costs, which the rewind spec's decision 2 already sizes for a private field.
- What bash itself prints for `noclobber`. No clone of bash was read; the four shells read are its followers, and three of them agree.

## One line

The spec's pair is the pair every system uses, what moves its counter is what moves theirs, its opacity is Unix's and not Plan 9's, its conditional change is HTTP's and nobody else's, and it should say all four in one numbered decision.

## Text proposed for the spec

The first block is a decision, to follow decision 19. The second is a section, to follow "Earlier decisions this reverses". Both are written to be pasted as they stand.

### 20. Where this spec leaves Plan 9 and Unix it says so, with the constraint that moved it

Article 3 of the constitution has VFS follow a convention of Plan 9 or Unix wherever one exists, and requires a deviation to be a numbered decision that names the principle, the deviation, the motivating constraint and the expected expiry. This is that decision. The section "Prior art, and where this spec departs" lists each point where a convention exists, what this spec does, and for each departure the four things the Article asks for. The points where the behaviour is older than this spec are listed too, marked as inherited, because this spec builds a guarantee on them.

Reason: a caller who knows `O_EXCL`, `rename` and `ESTALE` should be able to predict this API, and where it cannot, the place to learn why is the spec that decided it.

## Prior art, and where this spec departs

Read on 2026-11-23 in the clones and at the lines the research memo `research/2026-11-23-how-unix-plan-9-and-linux-name-a-file-in-a-state.md` records.

Where this spec agrees:

- **The name of a file in a state is an identity and a counter.** Plan 9's qid is a path that is never reused and a version that moves when the file is modified. Unix has the inode number with a generation, and Linux adds a change counter. The etag is made of the same two things, the entry id and the version.
- **What moves a directory's counter.** In fossil, cwfs, ext4, FFS and V7 a directory changes when a direct child is made, removed or renamed, and not when a child's body changes. The version of a directory here moves the same way, which is all decision 10 claims for it.
- **A stale name is `ESTALE`.** A file handle whose generation is wrong is refused `ESTALE`, and so is a handle from another file system. A stale etag and an etag from another mount are both `conflict`, the kind the code maps to `ESTALE`.
- **Create-only is `O_EXCL`.** An occupant of any kind, a directory too, is `exists`, as `O_CREAT|O_EXCL` answers `EEXIST`. A write with no precondition replaces, as `creat` and the shell's `>` do, and refusing to replace is opted into, as `noclobber` is. An append is outside the rule, as `>>` is.
- **The validator is opaque, as Unix has it.** An NFS file handle is opaque to its client, and Linux does not let user space read its change counter. The etag is a digest for the same reason: a caller that can take a validator apart will.
- **Removing a directory, a mount point, and crossing a mount** answer `not_empty`, `busy` and `cross_mount`, which are `ENOTEMPTY`, `EBUSY` and `EXDEV`.

Where this spec departs. Each row is a deviation under Article 3.

| The convention | What this spec does | The constraint that moved it | Expiry |
|---|---|---|---|
| No write, remove or rename in 9P or POSIX can require the state it was read in. | `write`, `edit`, `delete`, `move` and `restore` take `if_match`. | The callers this system is built for read a file and change it later, with other callers between, and the lost update is the commonest harm of that loop. The nearest relatives are NFSv3's guarded `SETATTR`, git's `update-ref` with an old value, and HTTP's `If-Match`. | None. |
| Plan 9 shows the qid, and Unix shows the inode number. | The entry id never leaves the storage, and the etag cannot be taken apart. | Article 3 already rejects raw inode exposure, and the models carry no database identifier by rule. | When a caller is found that must compare entries apart from their versions; "Left as it is" names the field that would serve it. |
| The words are qid, version and stale. | The words are `etag` and `if_match`. | They are the words of the one system that has the conditional change, and the ones a caller arrives knowing. | None. |
| In HTTP, create-only is another header, `If-None-Match: *`, and `If-Match: *` means that something is there. | The mark `ABSENT` is given where an etag is given. | One mapping must be able to require an etag at some paths and absence at others, so that a batch fails whole (decision 18). git's `update-ref` does the same with an all-zero old value. | None. |
| A file expected where a directory stands is `EISDIR`. | Under a required etag it is `conflict`. Without one it is `wrong_kind`, as before. | The caller named a file it had read; that a directory took its place is the file changing, and one read mends it (decision 9). | None. |
| A write always moves the file's counter, in Unix and in Plan 9. | A write of the body the file holds moves nothing and answers `unchanged`. | A call sent twice must be recognisable. Article 1.5 lets a write that changes nothing keep its revision. Inherited from the write-preconditions spec, decision 5. | None. |
| A name removed and made again is another file: a new qid path, a new inode or generation. | A write at a deleted path revives the row, which keeps its entry id and takes a later version. | The trash keeps a deleted row at its address so that it can be restored. Inherited. The version moves, so no etag from before the delete matches. | When the trash design changes. |
| A removed file occupies nothing. | A tombstone holds its address: a move onto it is `exists`, a restore requires its etag, and the mark counts it as absent. | The same. Inherited. | When the trash design changes. |
| POSIX `rename` replaces what is at its destination, atomically. | A move never replaces. This is Plan 9's rule for a rename and Linux's `RENAME_NOREPLACE`. | No verb destroys but `sweep`. Inherited. Decision 11 rests on it: a destination that is never replaced needs no precondition. | None. |
| A rename of a file onto itself succeeds and does nothing. | With a stale etag required it is `conflict`. | The precondition is judged before any other fact about the source, so that a refusal never depends on the destination. | None. |
| Two names are one file when their device and inode, or their qid paths, are equal. | No row says which entry it is apart from its version. | No caller needs it yet, and the field that would say it is the identifier the models keep out. | When a caller needs it. |

One difference is neither agreement nor a decision: a rename inside one directory moves that directory's version by two, where Unix changes the directory once. It makes no etag match that should not.
