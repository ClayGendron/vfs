## Scale and the production posture

- The `if_matches` mapping grows with the batch, as `entries` does. It is compared in Python against rows the snapshot holds and never enters a statement. EXECUTED: a write with and without an expected version sends the same 8 statements on each engine, and a stale one sends the snapshot alone (`p02`).
- The mark adds at most one insert for each depth a mixed batch creates at. The bound is the depth of the deepest path, never the batch.
- One mint for each row of a result. EXECUTED, as a size and never a pass or a fail, on one arm64 machine with Python 3.13.11 and Postgres 19.0 in Docker: selecting the id as bytes and minting adds 0.66 microseconds a row on Postgres and 0.69 on SQLite, 8 to 11% of a `glob` or `ls` row and about 7 ms for a 10,000-row listing; selecting the id as text would add 1.9 (`p07`). The spec's 1.1 is not understated.
- No lock is taken and none is held longer. EXECUTED: on Postgres the twenty writers that lose each pay one serialization failure and one second run that ends at the snapshot, with no statement after it (`p06`).
- Nothing is capped, and no dialect profile gains a field.

## Premortem

The spec was built as written and failed. The three most likely reasons:

1. A storage contract test passed on SQLite and failed on the Postgres leg, because one race has two answers and the spec wrote one. This is M1.
2. The second landing went red in `scripts/ci.sh` on the size lint, and the baseline of five modules was raised in review with nobody having decided where the code should live. This is M2.
3. A row reached a caller with a version and no etag, from a site the list of constructors missed. The spec names this risk itself under "Not checked" and guards it with a parametrized contract test; two of the verbs decision 4 names are missing from that test's list. This is L5.

## Findings, most severe first

1. **H1. The spec leaves Plan 9 and Unix in eleven places and names none of them in a decision** ([decision 15](../spec.md#15-the-etag-adds-no-primitive-and-article-15-names-it-in-place-of-if_version), and decisions 2, 6, 9, 11 and 18). Decision 15 checks Articles 1, 2, 4 and 5 and skips 3. The departures, each read against the sources in the research memo's section 7: a change can require a state, which no 9P or POSIX call can; the identity is hidden, where Plan 9 shows the qid; the words are HTTP's; "must be absent" is given under `if_match`, where HTTP uses another header; a directory met by a required etag is `conflict`, where Unix says `EISDIR`; a write of the same bytes keeps the version; a name deleted and written again is the same entry; a tombstone holds its address; a move never replaces, where POSIX `rename` does; a rename onto itself can be refused; no row says which entry it is. The spec gives a reason for seven of these, one of them in part, and names the prior art for one. Four are inherited from landed work (the unchanged write, the revived entry, the tombstone and the move that never replaces), and this spec builds guarantees on them. The design is not wrong in any of them: the study found the spec's pair, its directory rule, its create-only rule and its `ESTALE` to be the same as the systems it studies. Consequence if built: the first API of this project that a Unix reader cannot predict lands with no record of why, and the constitution's one MUST about lineage is unmet. Fix text: the decision "20. Where this spec leaves Plan 9 and Unix it says so, with the constraint that moved it" and the section "Prior art, and where this spec departs", both written out at the end of [the research memo](../research/2026-11-23-how-unix-plan-9-and-linux-name-a-file-in-a-state.md) to be pasted as they stand, and one sentence added to decision 15: "Article 3 holds by decision 20."
