# A catalogue posture decides who may see and who may call a tool

A draft, written on 2026-11-25. It is not reviewed, and nothing of the catalogue integration is built. Checked against `dev` at `27f3d24d`, it serves [roadmap story I3b](../../context/standards/roadmap.md), gate b, and converts [archived spec 170 §5.1](../../context/specifications/archive/170-tools-and-mcp-servers-as-views/spec.md). It rests on the reserved meta tree, the root binding's batch rights check, the shared program directory, the host tool's gated run and the startup check on `serve`.

## The outcome wanted

With `set_posture("/.vfs/bin", "list")` and no leaf exceptions, anonymous callers see each registered tool's name and kind. Reading a tool's manual is denied, and typing its name under the default `PATH` exits 126 without entering the function. A grant of `read` at one tool permits its recipient to read and call just that tool. At posture `none` a caller with no grant discovers no host tools and a guessed command exits 127. Shipped programs remain available at either posture. Before a transport opens, the host learns which registered tools anonymous callers could run.

## What the code does today

Executed through the dev router on in-memory SQLite and disposable Postgres. With `/` at `read`, the existing point check admitted anonymous `read` at three unstored paths under `/.vfs/bin`. After setting the head to `list`, all three passed `list` and none passed `read`. Giving one leaf posture `read` and another posture `none` plus a named `read` grant admitted only the first leaf anonymously. The system's `grants` at the second leaf returned the root, head and leaf everyone rows and its named row. The named caller lost access on revoke. System `stat` still gave `vfs.not_found` on that leaf. A system `write(..., parents=True)` under the head succeeded on both engines.

At a list-only leaf the present `holds(level="read")` returned `vfs.unauthenticated` for anonymous on both engines. That single refusal cannot distinguish a listable tool from a hidden one for the shell. The catalogue consumes the qualifying rung from 170-1. The six ranks and verb requirements are in `src/vfs/ops.py:125–175`.

## The problem

A host function can act outside the file system. Granting everyone read access to its path can therefore expose an external effect on a node where anonymous callers cannot create a single file. Checking only the catalogue head also misses a more permissive leaf. With 1,000 callers and 150,000 verb calls per day, discovery and startup must share the existing grants evaluator without loading the file estate or running a tool to check it (`AGENTS.md:74–82`).

## Decisions

1. Decided 2026-11-25: the real root binding owns policy for the global `/.vfs/bin` and its tool paths through the existing `set_posture`, `grant`, `grants` and `revoke` calls. Accept policy before registration and retain it across removal and replacement, since these rows name a path. Never create a file, a default posture or an approval when registering a tool. An absent name with a grant remains absent. Another router over the same storage sees the same policy and only its own registrations. The existing administration, capability and permission gates still apply, including `read_write` over the affected subtree for grant and revoke (`src/vfs/storage/backends/database/rights.py:956–997`). Ordinary content mutations, including either end of a transfer and a batch containing a reserved target, take 169-1's invalid-path route even as system. No catalogue exception to the grammar is needed.

2. Decided 2026-11-25: apply the ordinary caller's rung at each host tool under D64, with no registration default and no extra directory gate that would hide a deeper grant. Under `none` without a grant, discovery omits the tool and a direct `run` is `vfs.not_found`. At `list`, discovery exposes only path and kind, and both manual read and `run` are `vfs.permission_denied`. At `read` or higher the manual is readable and a valid uninterrupted run enters the function once. Use the filters and error precedence of 169-2 and 170-2, including their 127/126 shell distinction, fresh rights at use and zero invocations on discovery, help or denial. The shell's `type` reports the visible path. The trust line belongs in the readable manual. A shipped program's manual and shell dispatch remain available to every admitted caller, including under a leaf posture of `none` on that program. Every file operation the program performs still uses the caller's rights. A direct `run` of a shipped manual retains 170-2 decision 4's unsupported result. This follows domain G (`context/standards/roadmap.md:780–784`) and prevents a shared directory posture from disabling file commands.

3. Decided 2026-11-25: for D15 the host catalogue is open at startup if any currently registered host tool's effective everyone rung is **read or above**. Take anonymous as the authority for this check, independent of the transport's credentials, verb allowlist, masks and per-call policies. Read is the first rung at which the host body can be admitted. Test actual callable paths, so an inherited root `read` opens a tool under an unset head, a leaf `read` opens that tool under a `list` head, and a `read` head with every installed tool explicitly closed is closed. Named and group grants alone never open a catalogue. Shipped names, unregistered names and an empty host catalogue contribute no open leaf. Keep D15's ordinary mount test at the writing rungs beginning with `add`. When consuming that root binding's writable-prefix inventory, assign the global `/.vfs/bin` subtree to the catalogue test alone, with a component boundary. Keep the ancestor `/` and unrelated ordinary prefixes in the mount test. This avoids double-counting a catalogue posture or counting a stale grant to a removed name.

4. Decided 2026-11-25: inspect the sorted registration snapshot through one root `holds_all(paths=..., level="read", authority=Authority.anonymous(), per_path=True)` for the whole nonempty host catalogue. Use the returned keys in registration path order, never a public listing, per-tool `holds` loop, schema read or help execution. For zero host tools skip this check. Feed the open leaf paths to 171-2 as one logical binding named `/.vfs/bin`. Without the override, its paths appear in the one startup `ValueError` with all other open bindings. With `allow_open=True`, issue one `WARNING` on `vfs.mcp` for that catalogue listing its open paths, independent of warnings for ordinary mounts. A missing interface uses 171-2's unverified-binding rule. An advertised check that fails or returns no valid map aborts startup with `RuntimeError` even with the override. Verify binding and registration snapshot identity after the inspection and before accepting work. A change during inspection aborts startup without a listener or stdio read, as for 171-2's changed binding inventory. No registration lock spans a rights read. After start, new registrations and policy changes take effect on the next ordinary call. D15 is a startup check, never a grant of permission.

## Cost

For an inventory of `N` host tools under this head, the startup check uses `K=N+3` distinct posture keys when `N>0` (the leaves plus `/`, `/.vfs` and the head). The Postgres posture reads cost `ceil(K/B)` per successful check, plus 170-1's one authority resolution, where `B` is the membership owner's effective element budget. SQLite and the generic floor take that owner's chunks. For `S` shipped programs the ordered snapshot walk inspects at most `N+S` descriptors. The report contains at most `N` paths, with 170-1's bounded statements and request-local key set. Match open paths against the ordered snapshot in one pass. No entry or body reads, writes, schema changes or writer lock. Grant writes retain the root binding's existing transaction and relabel costs. The startup check adds zero work per file, index visit or ordinary verb call. Listing and execution keep the costs already budgeted in 169-2 and 170-2.

Executed a startup prototype using dev's `posture_rows` and `label_of` (`src/vfs/storage/backends/database/labels.py:135–146`, `:213–215`). On each engine 10,000 synthetic tool names under a `list` head with two readable leaf exceptions produced 10,003 distinct keys, one counted posture SELECT at the engine's declared budget and exactly the two exception paths. A separate pointwise oracle on real grant rows passed all six thresholds on both engines. These measurements exclude authority resolution, transport setup and the proposed batch seam.

## Tests

Write these nodes before integration. Use the live grant route on SQLite and the disposable Postgres leg. The existing prerequisite tests own standalone grammar, flags, paging and evaluator behavior.

- `tests/base/test_grant_routing.py::test_catalogue_policy_survives_tool_replacement` sets a head posture and named grant before registration, inspects exact global prefixes and levels through `grants`, adds and removes the tool, registers a replacement and revokes. Check names and runnable state on two routers sharing storage and the same name on a separate storage. Check an unauthorized policy change leaves every grant intact. Against installed, absent and shipped paths, try `write`, `mkdir`, `delete` and both transfer directions of `move` with valid arguments. All return `vfs.invalid` before any storage mutation. Check grant rows and the dictionary of registrations are unchanged.
- `tests/base/test_tools.py::test_changing_catalogue_posture_does_not_leak_another_callers_tools` compares two worlds differing by one secret registration while two callers use disjoint leaf grants. Change the everyone posture through `none`, `list` and `read` between calls. Compare discovery rows, matches, keys, direct errors, diagnostics and invocation counts with the missing-name world when hidden. Under `list`, pin bare anonymous names, failed manual/direct run and zero entries to the body. Under `read`, read the trust line with zero invocations and run once. Revoke the named exception under `none` and verify the very next call loses it.
- `tests/shell/test_engines.py::test_catalogue_posture_gates_the_tool_and_keeps_shipped_commands` runs with the default search path. Check `type`, `cat`, bare and slash tool commands, exit 127 when hidden, 126 when listable only and one entry after a named read grant. Under a `none` posture at the head and shipped `cat` leaf, pipe known input through shipped `cat` and verify its bytes. Reading a private file through the same command still fails without exposing its bytes.
- `tests/mcp/test_serve.py::test_startup_reports_anonymously_callable_tools_once` uses the actual database and a counting transport. Cover inherited `read`, all six leaf rungs, a `list` head with two readable exceptions, every leaf closed under a `read` head, a shipped-only snapshot, named-only access and a removed tool with a surviving writable posture. Put a writable ordinary prefix next to the catalogue. Assert the exact sorted open paths, zero binds or stdio reads on refusal, one warning per open logical binding with the override, and zero warnings for closed ones. Include an absent interface, a failed second slice, a success missing the map and a registration change during inspection. Check the override never changes the next caller's rung. On 10,000 tools count one rights batch, the budgeted posture reads on Postgres, zero file reads and zero tool entries.

## Choices to confirm

1. For catalogue D15 take effective `read` on registered callable leaves. Keeping `add` permits anonymous host effects without a startup warning. Checking only the head misses leaf exceptions in both directions. The selected rule is a startup refusal with the existing explicit override and can be relaxed without a data migration.
2. Fold the kernel acceptance into the end of 170-2 and land the startup integration with whichever of 170-2 and 171-2 lands last. An independent I3b implementation would duplicate the gates those units already need. The tests and inventory change can move to a separate landing without changing an API.

## One line

A grant names a tool's served path, `list` shows its name, `read` admits its call, and serving an anonymously callable host tool takes explicit consent at startup.
