## What a session is here

None of the three has a "session" in the vfs sense. Each has a **conversation id** (Vercel's chat `id`, AG-UI's `threadId`, assistant-ui's thread `remoteId`) and a **per-request id** (AG-UI's `runId`; Vercel has none on the default transport, only a server-minted stream id or workflow run id). In all three, the client is the one that holds the conversation. Each turn the client posts the message list it currently shows, and the backend is a stateless function of that list. Any state the backend keeps between turns, such as stored messages, a LangGraph checkpoint, or an ADK session, belongs to the application, keyed by the conversation id. None of the protocols manages it. Branches exist only in the client (assistant-ui) or in a framework's checkpoint store (LangGraph). On the wire an edit is a shorter message list, and nothing names a branch.

## 1. Identity

**Vercel.** The chat id is minted by the client when it is first read, using `generateId` (`packages/ai/src/ui/chat.ts:272-274`). It may be supplied as `ChatInit.id` (`chat.ts:204-208`). The default `generateId` makes 16 alphanumeric characters with `Math.random`, and its docstring says "Not cryptographically secure" (`packages/provider-utils/src/generate-id.ts:3-6`, `:53-57`). The persistence guide has the server mint the id instead: the page route calls `createChat()`, which calls `generateId()`, and then redirects to `/chat/{id}` (`03-chatbot-message-persistence.mdx:17-50`). The same guide checks the id against a regex before using it in a file path. Message ids come from the client by default. Assistant message ids can come from the server through `generateMessageId` or the stream's `start` chunk `messageId` (`03-chatbot-message-persistence.mdx:392-420`). The SDK has no notion of an owner. Ownership is left to the app: the resume guide says only "Ensure proper authentication and authorization for both creating and resuming streams" (`03-chatbot-resume-streams.mdx:426-431`). The memory guide says to "use collision-resistant session IDs tied to your authenticated user and serialize requests for the same session" (`content/docs/03-agents/06-memory.mdx:299`).

**AG-UI.** Both `threadId` and `runId` are REQUIRED on every `RunAgentInput` (`docs/spec/1.0/basic/run-input.mdx`, "Identity"). The reference client mints `threadId` lazily as a UUIDv4 unless the caller sets it (`sdks/typescript/packages/client/src/agent/agent.ts:213-219`). It mints a fresh UUIDv4 `runId` for every run unless the caller passes one (`agent.ts:643-644`). The LangGraph server integration falls back to its own UUID when `thread_id` is empty (`integrations/langgraph/python/ag_ui_langgraph/agent.py:1733`). The protocol defines no credential and leaves authentication to the transport binding (`docs/spec/1.0/basic/transports/index.mdx`, "Authentication and authorization are properties of the binding").

**assistant-ui.** A new thread gets a local id, `__LOCALID_` plus a random id (`packages/core/src/runtimes/remote-thread-list/remote-thread-state.ts:47`, `:198-212`). The backend then mints the canonical `remoteId` (and an optional `externalId`) in `RemoteThreadListAdapter.initialize(threadId)` (`runtimes/remote-thread-list/types.ts:18-21`, `:68-71`). That call runs lazily before the first send. The AI SDK transport awaits it and swaps the remote id into the request body's `id` (`packages/ai-sdk/src/transport/AssistantChatTransport.ts:71-77`). The docs for `onThreadIdChange` say the local id "is never surfaced" (`types.ts`, the `onThreadIdChange` docstring). Duplicate ids are avoided by retrying the local id on a clash (`remote-thread-state.ts:203-205`). A clash on the remote id is the adapter's business.

On what happens when a supplied id already exists, all three say the same thing: nothing is defined. The id is a lookup key. The app's `loadChat(id)` either finds rows or does not.

## 2. State

**Vercel.** The client `Chat` object holds the messages, the status, the active response, and a queue (`chat.ts:152-170`, `:270-310`). The server holds nothing unless the app stores it. The tool approvals guide says this outright: "the server rebuilds the conversation from the messages the client sends each turn. The server does not persist conversation state between requests. This means the message history is client-controlled input" (`03-agents/06-tool-approvals.mdx:293-297`). The default request body carries `id`, the **whole** `messages` array, `trigger` and `messageId` (`http-chat-transport.ts:188-200`). Sending only the last message is an opt-in recipe. The server then loads its stored history by `id` and appends (`03-chatbot-message-persistence.mdx:521-590`). For resumable streams the app stores one more field per chat, `activeStreamId`, and keeps the stream bytes in Redis with an expiry (`03-chatbot-resume-streams.mdx:21-44`, `:426-431`).

**AG-UI.** `messages` is "the complete history it is being shown — the protocol has no side channel through which earlier turns arrive" (`run-input.mdx`, "messages"). `state` is any JSON value, the "consumer's last agreed value". The producer streams it back as `STATE_SNAPSHOT` (replace) or `STATE_DELTA` (an RFC 6902 patch against the input state). The next run's input "carries it back as the starting value" (`docs/spec/1.0/events/state.mdx`, "Cross-run behaviour"). So shared state travels with every request, and the client is where it lives between runs. The capability `persistentState` lets an agent declare that it keeps state across runs itself (`docs/spec/1.0/schema.mdx:1326`). The resume rules say a producer "that carries nothing across the gap is conformant" (`interrupt-resume.mdx`, "Resuming").

**assistant-ui.** The client holds a message **tree**. `MessageRepository` keeps a map of messages, each with `prev`, `children` and a `next` pointer for the selected child, plus a `head` (`packages/core/src/runtime/utils/message-repository.ts:203-209`). It exports as `{headId, messages: [{message, parentId}]}` (`message-repository.ts:8-21`). Persistence goes through `ThreadHistoryAdapter.append({parentId, message})`, and storage rows carry `parent_id` (`packages/core/src/adapters/thread-history.ts:12-17`, `:51-65`). That is the app's server, not the chat protocol.

## 3. Lifecycle and concurrency

**Vercel.** Turn triggers are `submit-message`, `regenerate-message` and, client-side only, `resume-stream` (`chat.ts:147-150`, `chat-transport.ts:61-71`). `resumeStream()` issues a GET to `{api}/{chatId}/stream` (`http-chat-transport.ts:253-270`). The server looks up the chat's `activeStreamId` and replays from Redis, or answers 204 (`03-chatbot-resume-streams.mdx:185-243`). The docs state the limits plainly:
- Closing a tab or calling `stop()` is a disconnect, not a cancel. Real cancellation needs an app endpoint that compares and clears `activeStreamId` (`03-chatbot-resume-streams.mdx:10-17`, `:289-416`).
- "Multiple clients can connect to the same stream simultaneously" (`:428`).
- The only race guidance is "Clear the `activeStreamId` when starting a new stream to prevent resuming outdated streams" (`:430`).

Two tabs posting on one chat id are not covered. Within one tab, `Chat` runs its operations through a `SerialJobExecutor`, and `experimental_queue` queues sends made while a reply is in progress (`chat.ts:256-266`, `:313`). Since 5.0, two `useChat` hooks with the same `id` no longer share state; a shared `Chat` instance must be passed explicitly (`08-migration-guides/26-migration-guide-5-0.mdx:1355-1394`). The WebSocket transport adds a per-request `requestId` and a per-chunk `sequence`, and a `resume` frame carries `lastSequence` (`websocket-chat-transport.ts:23-77`). The Workflow transport takes a server-minted `x-workflow-run-id` header and reconnects to `{api}/{runId}/stream?startIndex=N` (`07-reference/04-ai-sdk-workflow/02-workflow-chat-transport.mdx:8-10`, `:198-229`). That is the one place a run id separate from the chat id appears in the Vercel stack.

**AG-UI.** A run is `RUN_STARTED` followed by `RUN_FINISHED` (outcome success, interrupt or cancelled) or `RUN_ERROR` (`docs/spec/1.0/events/lifecycle.mdx`). A stream may carry several runs in sequence, and a replayed thread is "the common case". A second `RUN_STARTED` while a run is active is a violation, but only within one stream (`lifecycle.mdx`, "Several runs on one stream"). The protocol has no reconnect. A dropped connection is a "truncated run", and "re-running is a new run with a new `runId`" (`transports/index.mdx`, "Truncation"). A `resumable` capability flag is reserved but has no mechanism and no sequence numbers on events (issue #2105, opened 2026-07-02, still open). The client offers `connectAgent()`, which "only reads the thread's history and answers nothing" (`agent.ts:60-68`, `:446-481`). Cross-request concurrency on one `threadId` is not addressed. On the client, `isRunning` is a plain flag (`agent.ts:127`, `:336`).

**assistant-ui.** Its own issues show races between two runs on one thread. In #10498 (2026-11-12, closed 2026-11-13), two runs started at once on one thread in the durable Pydantic AI backend, and the later write replaced the earlier transcript. The fix was "an atomic claim per thread before a producer starts". Assistant Cloud keeps run leases with checkpoints every 20 s and stale polling (`packages/core/src/react/runtimes/cloud/runLeases.ts:10-16`). #10751 and #10762 (2026-11-19 and 2026-11-20) show two clients rejoining one durable run, each keeping its own local message id, so two assistant rows were stored.

## 4. Fork

No protocol has a fork verb on the wire.

- **Vercel**: no fork. Its own Claude Code harness adapter cannot yet pass `forkSession` and `resumeSessionAt` (vercel/ai #24827, 2026-11-10, open). That is the only fork-shaped request, and it is about a server-side agent session, not the chat.
- **AG-UI 1.0**: no fork. Older concept pages describe `parentRunId` as "a git-like lineage" for "branching/time travel within the same thread" (`docs/concepts/serialization.mdx:25-38`, `:68-91`; `concepts/interrupts.mdx:126-128`). The 1.0 spec redefines it as "the run that spawned this one, when an agent invokes another agent as a separate run" (`schema.mdx:333`, `:973`; `run-input.mdx`, "Identity"). The two pages now contradict each other. A branch in the old reading kept the same `threadId`.
- **assistant-ui**: an edit or a regenerate creates a sibling under the same parent in the same thread (`message-repository.ts:346-378`). `getBranches(id)` returns the siblings (`:443-451`) and `switchToBranch` moves the head (`:493-506`). A branch is **never a new thread id**. The OpenCode and Pi runtimes advertise fork and revert, but those are backend-specific (`apps/docs/content/docs/runtimes/pick-a-runtime.mdx:74`, `:125`).

What happens to side effects outside the messages is not addressed anywhere. The closest evidence is assistant-ui #9758 (2026-10-15, open). There, the client truncates for an edit and sends a `checkpointId`, but "nothing on the server applies it", so "the ADK session therefore keeps the original turn after every edit or reload … and the next request runs against history the thread no longer shows."

## 5. Rewind, undo, edit-and-regenerate

**Vercel.** An edit is `sendMessage({..., messageId})`. The client cuts every message after the edited one, replaces it, and posts `trigger: 'submit-message', messageId` (`chat.ts:716-764`). A regenerate cuts back to before the assistant message and posts `trigger: 'regenerate-message', messageId` (`chat.ts:772-806`). The later history is **deleted** in the client. The server sees a shorter list plus the trigger. With the "last message only" recipe, the server must apply the cut itself, and the guide shows no such handling (`03-chatbot-message-persistence.mdx:556-590`). Tree history is the oldest open request, vercel/ai #2929 (2024-09-08, still open). #17661 (2026-07-21, closed) let an edit carry a new id so apps keeping a server-side tree get a distinct sibling id. The current code spreads the caller's message over `messageId` (`chat.ts:743-748`).

**AG-UI.** Nothing in the protocol. Issue #2154 (2026-07-10, open) says it plainly: servers "infer the intent by diffing the incoming `messages` against its own persisted history". The LangGraph integration does exactly that. It treats a same-id human message with new content as an edit, and a stored history longer than the incoming list as a rewind (`ag_ui_langgraph/agent.py:2351-2450`). It then forks a checkpoint before the message on the same `thread_id` (`agent.py:2594-2640`). The heuristic misfires: regenerating the first reply is not detected (#2109, 2026-07-03, open). Other middlewares only append unseen ids, so "an edited same-id message is silently dropped" (#2154).

**assistant-ui.** On the AI SDK runtime, an edit slices the AI SDK message list to the parent and calls plain `sendMessage`. A reload slices and calls `regenerate` (`packages/ai-sdk/src/runtime/useAISDKRuntime.ts:1232-1253`, `:1310-1324`). So the wire carries the **active branch path only**, with no parent id and no branch id. The tree lives in the client and in the history adapter. `resetHead` prunes descendants (`message-repository.ts:510-551`). The AG-UI runtime builds `RunAgentInput` from the head path, with the same `threadId` (falling back to `"main"`) and a fresh `runId` (`packages/react-ag-ui/src/runtime/AgUiThreadController.ts:3295-3343`).

## 6. Session versus run

| | conversation | per request | per question | per message |
|---|---|---|---|---|
| Vercel | chat `id` (client or server) | none by default; `activeStreamId` (server, resumable); workflow `runId` (server) | `approvalId` (server, `generateId`), `toolCallId` | message `id` |
| AG-UI | `threadId` (client) | `runId` (client, per run); `parentRunId` (spawning run) | `Interrupt.id` (producer, unique per run), `toolCallId` | message `id` |
| assistant-ui | local id, then `remoteId` / `externalId` (server) | inherits the underlying protocol's | inherits | message `id`, `parentId` |

**Human-in-the-loop, Vercel.** The server emits a `tool-approval-request` chunk with `approvalId`, `toolCallId`, an optional opaque `approvalDescriptor` and an optional `signature` (`packages/ai/src/ui-message-stream/ui-message-chunks.ts:89-98`). The id is minted server-side with `generateId()` (`packages/ai/src/generate-text/generate-text.ts:1523`). The client calls `addToolApprovalResponse({id, approved, reason})`. That turns the part's state into `approval-responded` (`chat.ts:853-890`). The answer travels **inside the message list** of the next request, which `sendAutomaticallyWhen` may send by itself (`03-chatbot-tool-usage.mdx:590-606`). The answer is a boolean plus a reason. A free-form answer uses a client-side tool and `addToolOutput` (`03-chatbot-tool-usage.mdx:560-563`). Because the history is client input, a forged approval is possible. `experimental_toolApprovalSecret` HMAC-signs the request, binding the tool name, tool call id and input, and the server checks it on replay (`06-tool-approvals.mdx:303-341`).

**Human-in-the-loop, AG-UI.** The run ends with `RUN_FINISHED` whose outcome is `interrupt`. It carries `Interrupt{id, reason, message, toolCallId?, responseSchema?, expiresAt?}` (`schema.mdx:998-1010`). The next run's `resume: [{interruptId, status, payload, metadata}]` answers it, on the same `threadId` with a new `runId` (`interrupt-resume.mdx`). The resume must cover every open interrupt. Enforcing that is the **consumer's** job, and a stateless producer is conformant. The older concept page instead says "Agents receiving a non-conforming input must emit `RunError`" and asks for idempotency on `(threadId, interruptId, status, payload)` (`concepts/interrupts.mdx:124-136`). The client checks resume coverage against `pendingInterrupts` (`agent.ts:661-670`). A frontend tool call ends the run as success, with `pendingToolCallIds`, and its result rides the next input's messages (`events/tool-calls.mdx:205-235`).

## 7. Regrets

Most regrets are cited above: Vercel #2929 and #17661 (no tree, edit ids), AG-UI #2154, #2109 and #2105 (inferred rewind, no resumable stream), and assistant-ui #9758, #10498, #10751 and #10762 (server drift, two runs on one thread, duplicate rows). Three more:

- vercel/ai #24409 (2026-11-02, open) proposes sending "only new messages plus a reference to a previous completed generation". That is a move toward state held on the server, following the Anthropic, OpenAI and Google provider APIs.
- AG-UI's own docs drift: `parentRunId` means branching in the concept pages and spawning in 1.0. Coverage of open interrupts is the agent's job in the concept page and the consumer's in 1.0.
- assistant-ui #6746 (2026-09-02, closed): switching branches re-sent an already stored message, and the server answered 409.

## What a chat application will hand vfs on each turn

**Vercel AI SDK app.** Every POST carries the chat `id`, either the whole `messages` list or only the last message, a `trigger`, and a `messageId` for edits and regenerates. The chat `id` is the natural vfs session id. It is stable across turns, devices and reloads, and it is already the app's database key. But by default it is client-minted and guessable only weakly (`Math.random`), so vfs must bind it to an authority rather than trust it. There is no branch id. A vfs fork, or a rewind of the session's memory, would be triggered by `trigger === 'regenerate-message'` or by `submit-message` with `messageId` set. Either way, history after that message is gone in the client. A vfs interrupt fits the approval path. The vfs job id can go in `approvalDescriptor`, or be the `approvalId`. The yes or no answer comes back in the next request's messages as an `approval-responded` part. That is client-controlled, so the host must still call `fs.resume(job_id, answer, authority=...)` with a server-side authority. A non-boolean answer needs the client-side-tool path (`addToolOutput`).

**AG-UI app.** Every `RunAgentInput` carries `threadId`, a fresh `runId`, the full `messages`, `state`, `tools`, `context`, `forwardedProps`, and optionally `resume`. `threadId` is the vfs session id, and `runId` maps to one call or one vfs job. A fork would be triggered only by the host's own diffing: a shorter or edited message list on the same `threadId`. Nothing on the wire says "branch from message X", and `parentRunId` no longer means that. A vfs interrupt maps almost field for field onto `RUN_FINISHED{outcome: interrupt}`:

| vfs | AG-UI |
|---|---|
| job id | `Interrupt.id` |
| `message` | `message` |
| `schema` | `responseSchema` |
| `expires_at` | `expiresAt` |
| the tool call | `toolCallId` |

The answer returns as `resume[{interruptId: job_id, payload}]` on the next run of the same thread. AG-UI's "one interrupted run, cover all its interrupts" sits comfortably with vfs's "one live interrupt per job". `state` could carry small vfs session facts back and forth, but it is client-writable.

**assistant-ui app.** On top of either protocol, the thread `remoteId` (server-minted in `initialize`) is the best session id, because the backend mints it. Branches stay inside one thread id, and the wire carries only the head path. A vfs fork per branch would therefore have to key on (thread id, branch head message id), which the server never receives unless the app adds it to `body` or `forwardedProps`.

## Lessons for vfs

1. **Accept the host's conversation id as the session id, but never as proof of ownership.** All three treat the id as an opaque lookup key. Vercel's default is a `Math.random` id minted in the browser (`generate-id.ts:53-57`). Bind the session to the authority at create time, and refuse a different authority on open. This bears on the session design.
2. **Assume every turn arrives on a fresh process with no server object.** Vercel's own trust model says "the server does not persist conversation state between requests". AG-UI calls a producer that keeps nothing conformant. Stamps held only in memory will be gone on every turn. With strict on, every edit would then be refused. The stamps must be stored, keyed by session id, or strict must not depend on them. This bears on the stamp design (PR 42).
3. **A branch is the same conversation id, not a new one.** assistant-ui siblings, LangGraph checkpoint forks, and old AG-UI `parentRunId` all stay inside one thread id. A vfs fork that requires a new session id will not match what the app hands over. Plan for a fork key below the session, such as (session id, anchor message id), or a fork the host asks for explicitly. This bears on the session fork design.
4. **No protocol tells the backend about an edit, so vfs must not infer one.** AG-UI's diff heuristics misfire (#2109, #2154). assistant-ui #9758 shows server state drifting after edits. Give the host an explicit call, such as fork or rewind at a given point. The host can map it from Vercel's `trigger` and `messageId`, or from its own diff. This bears on the session fork design.
5. **Side effects are never rewound by any of these protocols.** Files the agent wrote stay written after an edit, and so would vfs's. Say so in the fork documentation. A file system that is shared by default matches the ecosystem. Copy-on-write would be a new promise no chat client expects. This bears on the session fork design.
6. **The vfs interrupt already matches AG-UI 1.0's shape.** Its fields are id, message, schema, expiry and tool call, and the answer comes on a later request. Expose the job id so it can serve directly as `Interrupt.id` and Vercel's `approvalDescriptor`. The answer will arrive from client-controlled input. `fs.resume` must keep judging the server-side authority, which Vercel needed HMAC signing to get (`06-tool-approvals.mdx:303-341`). This bears on the interrupt design.
7. **Answers come on the next request, possibly from another device, while the old stream may still be alive.** Vercel separates disconnect from stop. AG-UI treats a dropped stream as truncated, not cancelled. A job must not be cancelled because a connection closed, and resume must be idempotent. AG-UI asks for replay safety on `(threadId, interruptId, payload)`, and vfs's "resuming a finished job returns its result" already gives it. This bears on the interrupt design.
8. **Two requests on one conversation id will happen, and the protocols do nothing about it.** assistant-ui needed an atomic per-thread claim (#10498) and run leases. Vercel's memory guide says to "serialize requests for the same session". Decide what a stored vfs session does with two concurrent writers to its stamp set: merge, or last write wins per entry. A whole-object overwrite loses one side's stamps. This bears on both designs.
9. **Keep persistence identity server-minted.** assistant-ui's duplicate rows (#10751, #10762) and Vercel's advice to use server-side message ids both come from client-local ids leaking into storage. If vfs generates ids, generate them on the server with a CSPRNG. This bears on the session design.
