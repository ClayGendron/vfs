## What a session is here

In both frameworks a session is a **stored message log keyed by an id**, and a run is a separate thing that reads it and appends to it. In the OpenAI SDK a session is only history: four methods over a list of items, and nothing about runs, owners or state (`src/agents/memory/session.py:69-110`). In ADK a session is richer. It is a record keyed by `(app_name, user_id, id)` that holds an ordered list of events and a state dict. State changes only through deltas carried on events (`src/google/adk/sessions/session.py:34-91`, `base_session_service.py:165-264`). ADK also keeps the paused state of a run inside the session's events. The OpenAI SDK keeps it outside, in a `RunState` snapshot that the caller must store.

## 1. Identity

**OpenAI.** The caller supplies `session_id` to every store's constructor (`sqlite_session.py:31-50`). It is a free string with no format. On first use the row is created implicitly: `add_items` runs `INSERT OR IGNORE` on the sessions table, then appends (`sqlite_session.py:261-285`). SQLAlchemy does the same through insert-or-lock (`sqlalchemy_session.py:420-440`). So an existing id is always **opened and appended to**. It is never refused and never overwritten. The one exception is `OpenAIConversationsSession`. There the id is a server conversation id, created lazily by `conversations.create` on first use (`openai_conversations_session.py:17-25, 79-83`). There is no owner. The docs say it plainly: "A session ID selects conversation history; the session ID does not authenticate a user or authorize access to that history" (`docs/sessions/index.md:502`). A request for a users table (#2808, 2026-03-31) was declined. The maintainer advised a join table in the host's own schema.

**ADK.** `create_session(app_name, user_id, state=None, session_id=None)` takes an optional client-supplied id and otherwise generates a UUID (`base_session_service.py:69-88`, `database_session_service.py:709-711`). If the supplied id exists, it **raises `AlreadyExistsError`**, both on a pre-check and on an `IntegrityError` race (`database_session_service.py:732-797`, `in_memory_session_service.py:141-145`). Opening is a separate call, `get_session`. The primary key is `(app_name, user_id, id)` (`schemas/v1.py:74-86`). So the same session id under two users is two sessions, and the owner is part of the key. Vertex AI is different. There the id is unique per reasoning engine and limited to `[A-Za-z0-9_-]+` (`vertex_ai_session_service.py:74`), and `get_session` raises if the stored `user_id` differs from the caller's (`vertex_ai_session_service.py:328-332`). `user_id` itself is a string the host asserts. The bundled API server takes it from the URL path (`api_server.py:1838`). Issues show what that costs: #8204 (2026-11-17, open), where a trigger takes `user_id` from the request body so a request can run as any user, and #7464 (2026-10-08, open), where colon-joined Redis keys collide across identity tuples. `Runner(auto_create_session=True)` adds an open-or-create path (`runners.py:264, 967-1000`).

## 2. State

**OpenAI.** The session holds only the list of input items, stored as JSON rows: `agent_sessions(session_id, created_at, updated_at)` and `agent_messages(id, session_id, message_data, created_at)` (`sqlite_session.py:229-259`). Nothing is bounded except by reading with `SessionSettings(limit=N)`. There is no expiry, except in two places. `RedisSession` and `DaprSession` take a `ttl` (`redis_session.py:369`, `dapr_session.py:81`), and `EncryptedSession` silently skips items older than its TTL (`encrypt_session.py:4, 123-135`). The caller deletes with `clear_session`. A sandbox agent's workspace files are a separate object with separate snapshots, outside the session (`docs/sandbox/guide.md:21-25, 341-364`).

**ADK.** The session holds events plus state. State has four scopes, set by key prefix (`state.py:96-98`). A key with no prefix is session state, stored on the session row. `user:` is shared by all of one user's sessions in the app, in `user_states`. `app:` is shared by the whole app, in `app_states`. `temp:` lives in memory for one invocation and is stripped before storage (`base_session_service.py:229-257`). Storage is SQL rows: `sessions`, `events`, `app_states` and `user_states`. Vertex accepts `ttl` and `expire_time` (`vertex_ai_session_service.py:75-82`). The database and in-memory services have no expiry. Deletion is `delete_session`.

## 3. Lifecycle and concurrency

**OpenAI.** There is no create, list or open verb. The calls are the constructor, `get_items`, `add_items`, `pop_item`, `clear_session` and `close`. A file-backed SQLite store survives a restart. The default `:memory:` store does not. Concurrency control is a **process-local** `RLock` per resolved database path (`sqlite_session.py:27-29, 96-106`). Nothing coordinates two processes beyond SQLite's own locking. `RunState` says "Independently restored snapshots must not be resumed concurrently against the same Session" and asks for "exclusive access to that history" (`run_state.py:850-855`). The tracker shows races fixed one store at a time: #2722 (SQLAlchemy first write), #3820 (two lazy creates split a Conversations history), #4205 and #4988 (concurrent `pop_item` returns one item twice), #5459 (Postgres ordering by a non-monotonic `created_at`) and #5329 (Redis compaction not atomic), all 2026.

**ADK.** The verbs are create, get (with `num_recent_events` and `after_timestamp`), list (sessions without events, ordered by update time), delete and `append_event` (`base_session_service.py:68-123`). The database and SQLite services survive a restart. Concurrency has two layers. First, an in-process `asyncio.Lock` per session key and per shared-state row (`database_session_service.py:525-582`). Second, inside the transaction, `SELECT ... FOR UPDATE` on the session row where the dialect supports it, or `BEGIN IMMEDIATE` on SQLite (`database_session_service.py:1013-1024`, `sqlite_session_service.py:476`). Then comes an **optimistic revision check**. The session object carries the storage `update_time` as a microsecond marker. If storage has moved since the session was loaded, `append_event` raises `StaleSessionError` ("Please reload the session before appending more events") (`database_session_service.py:85-88, 1056-1076`). The second writer is refused, not merged. The API server maps that error to HTTP 409 (`api_server.py:2045-2046`). The in-memory and Vertex services do no stale check. Using a timestamp as the revision was a regret. #7276 (2026-09-25) found false `StaleSessionError`s whenever two events shared a timestamp, because a database `onupdate=now()` overwrote the marker. #8216 (2026-11-18, open) found that the new buffered write service drops events behind a stale marker.

## 4. Fork

**OpenAI.** `AdvancedSQLiteSession.create_branch_from_turn(turn_number, branch_name=None)` copies **structure rows only**. Every message row before the chosen user turn gets a new `message_structure` row under the new `branch_id`. That new row points at the same `message_id`, so message bodies are shared (`advanced_sqlite_session.py:1466-1583`, the shared-row note at `1556`). The branch starts *before* that user turn, so the caller can re-ask it. The method then switches the session to the new branch. The current-branch pointer is **in-memory instance state** (`_branch_state = ("main", 0)`, `advanced_sqlite_session.py:83`). A new process is back on `main`. No parent branch or fork point is recorded. `list_branches` derives branches from rows (`advanced_sqlite_session.py:1293-1340`). Naming was a bug. The default name `branch_from_turn_{n}_{int(time.time())}` collided within one second, and an existing name, `main` included, was accepted and silently merged history into it (#4150, 2026-08-03). PR #4152 was closed in favour of #4186 (merged 2026-08-05). Today a `branch_reservations` table reserves every name forever: a reused explicit name raises `ValueError`, and a generated name gets a numeric suffix (`advanced_sqlite_session.py:1342-1373, 1432-1464`). Even a deleted branch's name stays reserved (`advanced_sqlite_session.py:1199`). Later fixes include #5178 (blank names), #6145 (force-delete fails when `main` is empty, open) and #6147 (every append scans the active branch, open). Pending approvals and the sandbox workspace are not touched by a branch. On the unreleased `feat/codex-harness` branch, `session.fork()` returns portable state. The source must be idle, with "no native descendants, unfinished work, or background processes", and "a fork does not copy workspace files" (`docs/sdk/state.md` on that branch, "Fork a conversation"; docs only).

**ADK.** There is no fork, clone or copy. Issue #4010 (2025-12-24) is still open. Its proposal (2026-10-26, unanswered) is `Runner.fork_async(fork_before_invocation_id, new_session_id)`. It would copy events before the fork point with new event ids, start session state at the fork point, share `app:` and `user:` state, and copy session artifacts version by version. `Event.branch` exists but means a path in the agent hierarchy, not a conversation branch (`events/event.py:140-147`).

## 5. Rewind, undo, edit-and-regenerate

**OpenAI.** Undo is `pop_item`. The documented edit-and-regenerate recipe pops the assistant reply and the user message, then runs again (`docs/sessions/index.md:151-172`). This is destructive and works only on the last item. Branching is the non-destructive form. The SDK also rewinds its own appends on retry, as a best effort (`session_persistence.py:1625-1660`). The codex-harness branch adds `replace_history_suffix(expected_revision, keep_prefix_count, items)`, which checks the revision before it commits (docs only).

**ADK.** `Runner.rewind_async(user_id, session_id, rewind_before_invocation_id)` is **append-only**. It appends one event that carries `rewind_before_invocation_id` and a reversing state delta and artifact delta (`runners.py:1395-1433`, `_rewind_utils.py:160-233`). `_apply_rewinds` then hides the rewound events from every prompt and from compaction (`events/_rewind_events.py:27-45`). Session state goes back to its value at the rewind point. Session artifacts are restored by writing the old version as a new one, or a tombstone if the artifact did not exist yet. `app:` and `user:` state, `user:` artifacts, memory and "anything a tool did outside ADK" are left in place (`docs/guides/runners/runner/rewind.md:129-167`). State seeded by `create_session(state=...)` is cleared, because it is on no event. The REST route first aborts the session's live runs (`api_server.py:1990-2046`). The rewind guide still says there is no HTTP route (`rewind.md:205`). The route was added the same day (commit `b01c5fff`, 2026-10-21).

## 6. Session versus run

**OpenAI.** The id is `session_id`. A run has no persisted id of its own. Its pause point is a `RunState` that the caller serializes with `to_json` and stores anywhere (`run_state.py:844-860`, `docs/human_in_the_loop.md:203-216`). The ids inside are tool `call_id`s. At an interruption the runner **writes to the session** the user input plus the turn's items, minus approval placeholders. The pending `function_call` therefore sits in history with no output (`run.py:2260-2316`). When output guardrails are present, the batch is held in `RunState._pending_session_write` and written on resume (`session_persistence.py:1277-1300`). Resume is `Runner.run(agent, state, session=session)`, given the same id and store (`docs/sessions/index.md:36-50`). Server-held state is a third option: `conversation_id` (an OpenAI Conversations resource) or `previous_response_id` (a chain of responses). Each cannot be combined with a local session, and the two exclude each other (`docs/running_agents.md:284-293, 424-426`). The regrets cluster here: #4775 (a lost append acknowledgement duplicates pending input), #4827 (deferred interrupted items never persisted), #5642 (an unclosed call breaks every later turn), #5413 (an approval reused across runs by `call_id`, open), #6091 (a cancelled run drops in-flight calls from the session, open), and #5995 (a restored codex-harness session hides a pending approval, open).

**ADK.** The nesting is session `(app, user, id)`, then invocation (`"e-" + uuid`, `invocation_context.py:833-834`), then events, then function-call ids. The pause **lives in the session**. With `ResumabilityConfig(is_resumable=True)` (`apps/_configs.py:25-42`), agents write `agent_state` and `end_of_agent` checkpoints onto events. Resume replays those events to rebuild the invocation (`invocation_context.py:592-614`, `runners.py:2000-2063`). A tool asks for confirmation with `request_confirmation`. That records a `ToolConfirmation` under its function-call id (`agents/context.py:703-733`) and emits an `adk_request_confirmation` call. The answer is a function-response message. The runner finds the paused invocation by matching that response to its call in the session (`runners.py:500-533, 632-679`). The config warns that tools run "at-least-once" and that in-memory state is lost. Regret #7569 (2026-10-16, open): a fix that would bind the confirmation to an authenticated answerer was reverted, so whoever sends the function response can approve.

## 7. Regrets

Most are cited in the sections above. Three more: OpenAI #4729 (2026-08-28), where upgrading to `AdvancedSQLiteSession` destroyed existing history. OpenAI #5176 (2026-09-25), where edited or re-owned rows were served as genuine history; the answer was a trust-boundary paragraph in the docs, not integrity checks. And OpenAI #1938, a declined request for owner and metadata storage. The pattern is clear. OpenAI's regrets are races and orphaned tool calls at the session/run seam. ADK's are timestamp revisions, the missing fork, and identities the caller asserts.

## Lessons for vfs

1. **Create must refuse an existing id, and open must check the owner.** ADK refuses on create (`AlreadyExistsError`) and puts the owner in the key `(app, user, id)`. Vertex refuses a `get` by another user. The OpenAI SDK's id only selects; it never authorizes. That pushes the whole fixation problem onto the host (`docs/sessions/index.md:502`). For vfs: key the session by its owning principal plus the id. Offer create-or-refuse and open-or-refuse, and make any open-or-create explicit. *Bears on both designs.*
2. **Concurrency is enforced in the database, as a revision check, never only in Python.** Every OpenAI race above came from a process-local lock or a check-then-insert. ADK's working answer is a row lock plus a revision marker that refuses the stale writer. A chat app with several devices needs exactly this. *Bears on stamps*: persisted stamps need a session revision so that two turns on one session cannot both refresh them.
3. **The revision is a counter, not a clock.** ADK #7276 and #8051, and OpenAI #4150 and #5459, all came from timestamps used as identity, revision or order. *Bears on both* (the session revision and job ids).
4. **Split state by lifetime, as ADK's prefixes do.** ADK separates persisted session state, shared user and app state, and `temp:` state that is dropped after the invocation. vfs needs the same split. Stamps and the shell's working directory are session state and must persist, or a stateless handler loses them each turn. Per-job scratch is temp. Files are like `app:` state: shared and never session-scoped. *Bears on stamps.*
5. **A paused job should be findable from the session, and its answer bound to an authenticated principal.** ADK keeps the pause in the session's event log and resumes from it, which suits stateless handlers. OpenAI keeps it in a caller-held, unauthenticated `RunState`, and its docs must warn that "Possession of a run ID ... is not authorization" (`human_in_the_loop.md:213-216`). ADK #7569 shows forged confirmations when the answerer is not checked. *Bears on interrupt*: store the session id on the job, and check `authority` on `resume` against the job's session owner.
6. **A pending interrupt makes a session unforkable and unrewindable.** OpenAI writes a dangling `function_call` into history at interruption and has spent months on orphan-call bugs (#4827, #5642, #6091). The codex-harness `fork()` simply requires an idle source. ADK's REST rewind aborts live runs first. *Bears on interrupt*: refuse fork and rewind while the session has a waiting job, or define exactly which side the job stays with.
7. **A fork copies the session's own memory and shares the world.** No framework forks external side effects. OpenAI branches share message bodies and leave the sandbox alone. The codex-harness fork "does not copy workspace files". ADK's proposal shares `app:` and `user:` state. For vfs the natural default is to copy stamps, working directory and variables, and share the files. Copy-on-write files would be a separate, larger feature. *Bears on stamps*: a fork's copied stamps stay valid only while the files are unchanged, which the etag check already enforces.
8. **Record lineage, and keep fork ids collision-free.** Neither framework records a parent or a fork point. OpenAI's current branch is not even durable. A chat app that shows branches needs `parent_session_id` and a fork point. Names should come from UUIDs, not time. *Bears on the session design.*
9. **Rewind does not restore what it cannot own, and it should say so.** ADK's guide lists what stays put: shared state, tool side effects, memory, billing. For vfs, rewinding a session can restore its memory but never files. Restored stamps from before the rewind are stale by definition. They should be dropped or re-checked, never trusted. *Bears on stamps.*
10. **Keep the per-append cost bounded.** OpenAI #6147 (each append scans the branch) and ADK's whole-history rewind replay grow with session length. Persisted stamps should be written as a delta per verb call, never a rewrite of the set. *Bears on stamps*, at 150,000 verb calls a day.

## Comparison

| Question | OpenAI Agents SDK | Google ADK |
|---|---|---|
| Who makes the id | The caller always. The Conversations session gets a server id | The caller, optionally; otherwise a UUID |
| Supplied id exists | Opened and appended to (`INSERT OR IGNORE`) | `AlreadyExistsError`; `get_session` is separate |
| Uniqueness scope | Per store (table or key prefix) | `(app, user, id)`; Vertex: per engine, plus a user check |
| Owner | None; the host must authorize | `user_id` in the key, asserted by the host |
| What it holds | A list of input items | Events plus state in session, `user:`, `app:` and `temp:` scopes |
| Expiry | Redis and Dapr TTL; Encrypted TTL; otherwise none | Vertex TTL; otherwise none |
| Concurrency | Process-local lock; exclusive access on resume is the caller's job | In-process lock, row lock or `BEGIN IMMEDIATE`, and a `StaleSessionError` revision check |
| Fork | `AdvancedSQLiteSession` branches: copied pointer rows, shared bodies, in-memory current branch, no lineage | None (#4010 open) |
| Rewind and undo | `pop_item` (destructive); branch from a turn | `rewind_async`: an appended reversing event, non-destructive |
| Side effects on fork or rewind | Not touched (sandbox separate) | Not touched; session artifacts restored, `user:` not |
| Paused-run state | `RunState` outside the session, held by the caller; partial history written into the session | Inside the session's events; resume by `invocation_id` |
| Id nesting | `session_id`, then `RunState` (no id), then `call_id` | Session, then invocation `e-…`, then event, then function-call id |
