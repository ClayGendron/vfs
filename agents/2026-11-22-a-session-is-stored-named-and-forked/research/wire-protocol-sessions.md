## What a session is here

In ACP a session is one conversation between an editor (the Client) and an agent. The Agent owns and stores it, and names it with a `sessionId` that every session-scoped request carries in its body. ACP keeps adding session operations: list, resume, close, delete, archive, fork, and cursors that name positions inside a session. ACP v2 separates two things. A session *exists* until the Agent discards it. It is *active* on one connection from `new`/`resume` until `close` or disconnect. In MCP up to 2025-11-25, a session was a transport artefact. The server could mint an `Mcp-Session-Id` header at `initialize`, and the session lasted as long as the client kept sending it. The 2026-07-28 revision deleted it. MCP is now stateless at the protocol layer. State that spans calls is named by an explicit identifier the server mints and the client passes back on every call.

## 1. Identity

**ACP: the Agent always mints.** "The Agent **MUST** respond with a unique Session ID" (`docs/protocol/v1/session-setup.mdx:73`). `session/new` takes `cwd` and `mcpServers` and no id. `ForkSessionResponse.session_id` is the "Unique identifier for the newly created forked session" (`agent-client-protocol-schema/src/v1/agent.rs:1881`). `SessionId` is an opaque string newtype with no format (`v1/mod.rs:38-50`). No RFD proposes a client-supplied session id; a search of the docs found none. The idempotency RFD says why one would be hard: "The Claude Agent SDK and Codex choose the ID of a forked session themselves" (`docs/rfds/v2/idempotency-keys.mdx:294`). ACP does accept one client-minted key: `idempotencyKey` on `session/prompt`. It is "scoped to the session named by `sessionId`. The same key string in another session, including a fork of this one, names an unrelated submission" (`idempotency-keys.mdx:120`). Supplied-id collision therefore never arises for sessions. For prompt keys, a repeat returns the original message's id and inserts nothing.

**ACP ownership.** The v2 draft security page says an Agent serving more than one user "**SHOULD** scope `session/list`, every request that names a session (such as `session/resume`, `session/delete`, and `session/fork`), and permission requests to the user that owns the session ... It treats another user's session as one that does not exist, so it is not listed, resuming it fails with `-32002`, and deleting it does nothing" (`docs/protocol/v2/draft/security.mdx:60`). For elicitation the rule is a MUST: "`sessionId` alone or an unverified Client-provided identity is not sufficient" (`docs/protocol/v1/elicitation.mdx:69-71`). Cursors say the same: "A `cursorId` is not a credential" (`docs/rfds/session-cursors.mdx:54`).

**MCP before removal: the server minted, and minting was optional.** "A server ... **MAY** assign a session ID at initialization time ... **SHOULD** be globally unique and cryptographically secure ... **MUST** only contain visible ASCII" (`docs/specification/2025-11-25/basic/transports.mdx:198-205`). The security page added: "MCP Servers **MUST NOT** use sessions for authentication", the ids must be "secure, non-deterministic", and servers "**SHOULD** bind session IDs to user-specific information ... `<user_id>:<session_id>` ... the user ID is derived from the user token and not provided by the client" (`docs/docs/2025-11-25/tutorials/security/security_best_practices.mdx:575-591`).

**MCP after removal: handles, still server-minted.** SEP-2567's abstract says "explicit, server-minted state handles that the model carries and threads through subsequent calls" (`seps/2567-sessionless-mcp.md:13`). The current security page renames the threat "State Handle Hijacking". It keeps the rules: "**MUST NOT** treat possession of a state handle as authentication", and "bind handles server-side to the authenticated user ... `<user_id>:<handle>` ... reject a handle presented by any other principal" (`docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx:524-559`). SEP-2567 also reports a real bug. The Python SDK "routes by `Mcp-Session-Id` alone without verifying that the authenticated identity on the request matches the one that created the session" (python-sdk#2100, cited at `seps/2567-sessionless-mcp.md:257`).

## 2. State

**ACP.** A session holds the conversation history, mode and config options, MCP server set, `cwd` and extra roots, message ids, cursors, background work (terminals, tool calls, child sessions), title, usage and archive flag. The protocol never says where or how it is stored. "Agents choose how long to keep sessions: for example, they can skip storing a session that was never prompted, expire old sessions, or remove one through `session/delete`" (`docs/protocol/v2/session-setup.mdx:48`). Delete may be soft or hard (`docs/rfds/session-delete.mdx`, Semantics). The request's `mcpServers` and roots *replace* the stored ones on every resume (`v2/session-setup.mdx:55`). So part of a session's state is re-supplied by the Client each time and never restored.

**MCP before.** Five things hung off the session: negotiated capabilities, in-flight elicitation and sampling correlation, application state (the shopping cart), mutable tool lists, and subscriptions (`seps/2567-sessionless-mcp.md:27-37`). The spec bounded none of them, and expiry was "the server **MAY** terminate the session at any time" followed by 404 (`2025-11-25/basic/transports.mdx:211-215`).

**MCP after.** Capabilities and version travel in each request's `_meta` (`seps/2575-stateless-mcp.md:268-326`). Application state lives behind handles whose "durability is documented in the tool description ... 'baskets expire after 24h idle'". An expired handle gets a useful error such as "basket `bsk_a1b2c3` has expired" (`seps/2567-sessionless-mcp.md:147-148`). Tasks carry `ttlMs` (`seps/2663-tasks-extension.md`, Task interface).

## 3. Lifecycle and concurrency

**ACP status of each operation.**

| Operation | Status | Notes |
|---|---|---|
| `session/new` | stable | Agent mints id |
| `session/load` | stable in v1, **removed in v2** | v1 "**MUST** replay the entire conversation" as `session/update`s before responding (`v1/session-setup.mdx:136`); v2 replaces it with `session/resume` plus `replayFrom: {type: "start"}` (`v2/migration.mdx:44`) |
| `session/resume` | stable since 2026-04-22 (`rfds/session-resume.mdx:86`), required in v2 | no replay (`v1/session-setup.mdx:258`) |
| `session/close` | stable, required in v2 | cancels work, frees resources, idempotent (`v1/session-setup.mdx:314`) |
| `session/list` | stable, required in v2 | filter by `cwd`, paginated |
| `session/delete` | stable since 2026-06-05 | idempotent, soft or hard |
| `session/archive` | RFD | reversible hiding; archiving closes |
| `session/fork` | **unstable** (`unstable_session_fork`, `v1/agent.rs:1680-1698`) | |
| modes | deprecated in v1, removed in v2 for config options (`v1/session-modes.mdx:6-11`) | |

The resume RFD explains why resume exists apart from load. A third-party session, loaded with "our tools ... not available", gives "a flawed user experience", so "'session/resume' is the basic primitive which 'session/load' builds on top of" (`rfds/session-resume.mdx:71-82`).

**ACP concurrency.** "Whether a session can be active on more than one connection at once is up to the Agent." An Agent may refuse the second resume, or end the first connection's activity (`v2/session-setup.mdx:56`). Prompts sent during active work are inserted or held, and held prompts go in arrival order (`v2/prompt-lifecycle.mdx:415`). When a connection ends, "The Agent **MAY** continue or cancel their foreground work" (`v2/session-setup.mdx:57`). No locking rule exists.

**MCP.** The old lifecycle was: mint at `initialize`, resend on every request, get 404 when gone and re-initialize, send `DELETE` to end (`2025-11-25/basic/transports.mdx:198-220`). Resumability replayed per-stream SSE events after `Last-Event-ID` (`transports.mdx:162-188`). 2026-07-28 removed both the session and resumability: "A broken response stream loses the in-flight request" (`2026-07-28/changelog.mdx:28`). Durable work "**MUST** use the tasks primitive instead" (`seps/2575-stateless-mcp.md:360-369`). The spec now says the connection is not the session: "an open connection, such as a STDIO process, is not a conversation or session ... State that needs to span multiple requests ... **MUST** be referenced by an explicit identifier the client passes on each request" (`2026-07-28/basic/index.mdx:182-209`).

## 4. Fork

**ACP fork** (`docs/rfds/session-fork.mdx`). Its first use case is a summary or a PR description "without polluting the user history" (lines 12-22), and subagents later (line 35). The request carries `sessionId`, `cwd` and `mcpServers`, like load (lines 49-64). The reason given is that `claude-agent-acp` "does not retain the configured MCP servers of a session" (lines 140-146). The response carries a new, Agent-minted `sessionId`. The fork is active at once (line 67). By default the fork copies the whole history.

Forking from a middle point uses a **cursor**: an opaque, Agent-owned `cursorId` that the Agent announces with `cursor_update` for positions it supports. "The new session's history is the source session's history before the cursor's position ... The source session does not change ... The new session does not inherit the source session's cursors" (lines 72-113). The cursors RFD explains why a message id was not enough. "Not every message is a valid position", some positions are not at a message, and "validity depends on the operation" (`rfds/session-cursors.mdx:26-32`). Edit-a-message, regenerate and branch-from-a-reply are each built as a fork at a cursor (`session-fork.mdx:115-119`).

On work in flight, a fork copies none of it. "A forked session starts with no background work ... Unfinished tool calls and running terminals copied into the fork's history are not live" (`rfds/v2/background-work.mdx:227`; `v2/draft/session-setup.mdx:50`). No text says what happens to a source's pending permission request on fork. Nothing implies it moves. Lineage is not recorded in `SessionInfo`; the child-session machinery (subagents) is separate.

The open questions are a cheap way to learn a fork's ids and cursors (`session-fork.mdx:157`); partial replay from a cursor; v1 anchoring; and an error code for a bad cursor (`session-cursors.mdx:355-359`). Fork is listed among the "Duplicating" retry classes: a lost response leaves an unused copy that the Client can find with list and remove with delete (`idempotency-keys.mdx:183`).

**MCP.** There is no fork. The decision document left sub-agent scoping as the open problem with sessions. Should a sub-agent get "a completely **new session**", "a **copy/fork**", or "share the exact same `session_id` (which risks the sub-agent polluting the parent's context)?" Handles answer it per piece of state: one `basket_id` passed to every subagent, a separate `browser_id` for each (`seps/2567-sessionless-mcp.md:71-86`).

**Files.** Neither protocol forks or rewinds files. ACP v1's `fs/read_text_file` and `fs/write_text_file` read and write the *Client's* files, unsaved buffers included, and carry `sessionId` only for routing (`v1/file-system.mdx:6,33,80`). v2 removed them because they were "not widely adopted" (`rfds/v2/client-filesystem-terminal-capabilities.mdx`). File state is not part of an ACP session. The cursor RFD found the runtimes split: Claude Code's "`rewindFiles` restores files, at user messages only"; Codex's "`thread/revert` removes history and does not restore files". It concludes "A rewind capability needs a field for it" (`session-cursors.mdx:267,276`).

## 5. Rewind, undo, edit-and-regenerate

ACP has no rewind method yet. Edit and regenerate are **forks at a cursor**. The source is left untouched and the new branch gets a new id (`session-fork.mdx:115-119`). A future rewind "takes a `cursorId` for the cut" and is meant to make every Client converge on the same history (`session-cursors.mdx:243`). Undo of files is runtime-specific and outside the protocol. MCP has none of these; they are client concerns over its transcript.

## 6. Session versus run

**ACP ids nest like this:** `sessionId` ⊃ prompt turn (JSON-RPC request; v2 adds `messageId` and `idempotencyKey`) ⊃ `toolCallId` ⊃ permission request. In v1 `session/request_permission` is an Agent→Client JSON-RPC request carrying `sessionId` and a `toolCall` (`v1/tool-calls.mdx:137-145`). On cancel, "The Client **MUST** respond to all pending `session/request_permission` requests with the `cancelled` outcome" (`v1/prompt-turn.mdx:648`). On close in v2, the Agent "**MUST** cancel every pending permission request and elicitation scoped to that session" (`v2/session-setup.mdx:464`). On resume after connection loss, "the Agent **SHOULD** reestablish it or safely resolve the wait" (`v2/session-setup.mdx:431`). Pending requests "are not history" and are not replayed; they wait until after `replay_complete` (`v2/session-setup.mdx:379`). The v1 load text says nothing about pending permissions. v2 added a `requires_action` foreground state that a resume snapshot reports (`v2/session-setup.mdx:413-420`). In v2 a selected reject "**MUST NOT** perform the requested operation" (`rfds/v2/permission-requests.mdx`, Honoring the decision).

**MCP's replacement for a pending question is two mechanisms, neither tied to a session.**

- *MRTR* (multi round-trip requests). The server answers `tools/call` with `resultType: "input_required"`, its `inputRequests` and an opaque `requestState`. The client gathers the answers and **re-sends the original request** with a new JSON-RPC id, `inputResponses` and the echoed `requestState` (`2026-07-28/basic/patterns/mrtr.mdx:25-53,194-257`). The server treats `requestState` as attacker-controlled. It protects its integrity with HMAC or AEAD and should embed "the authenticated principal", "a short expiry", and "an identifier for the originating request". Single use "**MUST**" be enforced server-side where needed (`mrtr.mdx:231-244`).
- *Tasks* (official extension, SEP-2663). The server may answer any request with `resultType: "task"` and a server-minted `taskId`. It "**MUST NOT** return `CreateTaskResult` until the task is durably created" (`seps/2663-tasks-extension.md`, Task Creation). The statuses are `working | input_required | completed | cancelled | failed`. `tasks/get` is "a pure, idempotent read". `tasks/update` delivers `inputResponses` and returns only an acknowledgement. Each `inputRequests` key is "unique over the lifetime of a single task". Answers to keys not currently outstanding are ignored. `tasks/list` was removed because, without sessions, "there is no other natural scope a server can define" (Motivation item 3). Task ids must be unguessable, and every task request is authorized (Security Implications). The old `tasks/result` was dropped as "a blocking trap" that forced long-lived connections (Motivation item 2).

## 7. Regrets

- **MCP removed sessions after about a year and a half** (transport 2025-03-26, removal 2026-07-28, changelog item 1). The SEP's words: "sessions have not converged on a consistent meaning across clients: some scope them per tool call, some per application launch, some per page load, and almost none resume them" (`seps/2567-sessionless-mcp.md:15`). It cites ChatGPT and Claude.ai opening a fresh session per tool call (playwright-mcp#1045, Sep 2025). It cites the TypeScript SDK's lack of any API to rebuild a session on another node (typescript-sdk#1658, Mar 2026). It names list caching costing `O(subagents × servers)` calls, "cardinality is fixed at one per session", and state that cannot be addressed from outside its session (lines 45-86). SEP-2575 adds load balancing, "sticky sessions, which bind a client to a specific server", lost state on instance failure, and server-side garbage collection as "a common source of bugs and memory leaks" (`seps/2575-stateless-mcp.md:42-70`).
- **The direction reversed mid-course.** The 2025-12-19 blog planned "moving sessions to the *data model layer*", possibly "a cookie-like mechanism" (`blog/content/posts/2025-12-19-mcp-transport-future.md:48-56`). The working group's decision document weighed data-layer sessions (transports-wg PR #20) against handles (PR #25). The Core Maintainers chose "no-session" at the 2026-04-01 meeting (discussion #2536).
- **The breaking change was measured.** A 1,000-repo survey found 90% never touched the session id and 2.5% kept app state on it. Only 0.7% (gateways doing sticky routing) needed a designed replacement (`seps/2567-sessionless-mcp.md:220-231`). There was no deprecation window (line 249).
- **ACP dropped `session/load`, modes and client file system methods in v2** (`v2/migration.mdx:14,44,51,57`). Fork went from a message id (PR #629) to cursors (2026-11-14), because message ids named positions agents could not act at.
- **ACP's HTTP transport RFD keeps what MCP dropped.** It uses an `Acp-Connection-Id` and an `Acp-Session-Id` header, cookie-based stickiness, and resumability deferred to v2 (`rfds/streamable-http-websocket-transport.mdx:49,75,123-126,427`). The `sessionId` still travels in every body (line 62). It is an RFD, not stable.

## Lessons for vfs

1. **The connection, the process and the object are not the session.** MCP failed because its session's lifetime was whatever each host made it. ACP v2 separates a session that *exists* in storage from one *active* on a connection. A vfs session that lives only in an `AsyncSession` object is MCP's failure again: stateless chat handlers end it on every turn. *Bears on the stamp design.* Stamps belong in storage keyed by session id. `close()` should end activity, not discard what the session has seen; discarding is a separate `delete` or an expiry.
2. **An explicit id on every call is what both protocols settled on.** ACP puts `sessionId` in every request body, even on its HTTP transport. MCP requires state to be "referenced by an explicit identifier the client passes on each request". A vfs session id passed per call (`fs.read(..., session=id)`, or as a tool argument over MCP) is the endorsed pattern. It does not reverse the earlier "no sessions on the wire" decision: MCP still has no protocol-level session, and the handle is ordinary tool data. *Both designs.*
3. **Both protocols mint ids on the server side.** Neither lets a client choose a session id. ACP's one client-minted value, `idempotencyKey`, is scoped inside a session that already authorizes the caller. If vfs accepts a host-supplied id, key it as (owner, id), never id alone. A host is a trusted embedder, so supplying an id is safe in-process. Over MCP, vfs should mint the handle, or accept a supplied one only inside the authenticated principal's namespace. *Both designs.*
4. **An id is a name, not a credential.** Check (id, authority) on every call. Treat another identity's session as one that does not exist: not listed, `not found` on open, no-op on delete (ACP `draft/security.mdx:60`). This also answers session fixation. A guessed or reused id either opens the caller's own session or reports nothing. Mint ids with at least 128 bits of entropy where they may act as bearer tokens. *Both designs.*
5. **Make create-with-a-supplied-id idempotent: create, or open the caller's own existing session.** ACP classes `new` and `fork` as "duplicating" and accepts that, because an unused copy is cheap. With a supplied id, vfs can do better: one id, one session per owner, and a retry opens the same one. *Bears on the stamp design.*
6. **A fork is a new id, copies history up to a server-named point, leaves the source unchanged, and copies no live work.** ACP forks do not inherit background work, cursors or pending requests. The vfs equivalent: copy the stamps (what the agent has seen), the working directory and shell variables. Never copy a waiting job; the job stays with the source session. *Bears on both designs.*
7. **Neither protocol forks or rewinds files.** Where runtimes rewind files they disagree (Claude at user messages only, Codex not at all), and ACP decided this needs an explicit capability. Default a vfs fork to *shared files, copied stamps*. Strict stamps then make a fork's writes safe against its sibling's changes. A copy-on-write view of the files would be a separate, explicitly named feature. *Bears on the stamp design.*
8. **MCP Tasks show the shape of a durable interrupted job.** The server mints the id, and the job is durably created before the id is returned. The read is pure and idempotent. The answer is a separate write, keyed by request keys unique over the job's lifetime, and stale keys are ignored. The job carries a TTL. Authorization is checked on every call. There is no list without a defined owner scope. vfs's `resume(job_id, answer, authority)` matches this. Key the answer by the step's interrupt key, enforce at-most-once on the server side (MRTR's warning), and bind the job to its authority. *Bears on the interrupt design.*
9. **Decide what close and reconnect do to a waiting question.** ACP v2: close cancels pending permission requests. A resume re-establishes them or safely resolves them, and replay never replays them as history. A vfs job outlives the session's *activity*. So state whether closing a session cancels its jobs (ACP's choice) or leaves them resumable. A resumed job's write should refresh the stamps of the session id stored on the job, not of whichever object happens to be in memory. *Bears on the interrupt design.*
10. **Document durability where the caller decides.** MCP asks for the expiry policy in the creating tool's description, and an error that says "expired" rather than "invalid". A vfs session and job need a stated TTL and a distinct expired or unknown result. Without them, a host or model retries blindly. *Both designs.*

**Together:** (a) Both histories choose an explicit handle on every call over a connection-bound session. MCP removed the connection-bound one after it failed in practice, and ACP's sessions outlive connections by design. (b) Both have the server mint the id. A caller-chosen value is accepted only inside a scope that is already authorized. (c) Both say an id is never authentication. Bind it to the verified identity on every call, and present another identity's id as nonexistent.
