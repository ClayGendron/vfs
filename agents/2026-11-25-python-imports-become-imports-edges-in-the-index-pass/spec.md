## The outcome wanted

After `rebuild` or `refresh`, a Python file in a mount has one `imports` edge to each file of the same mount it imports. The edge's weight is the number of the source's import statements that reach that file, and its `context` is the first such statement folded to one line. `traverse(method="outbound", path=..., edge_types=("imports",))` walks a module's dependencies, and the centrality prior counts the edges as it counts markdown `links` today. An import of the standard library or of a third-party package mints nothing, and the pass's Result carries one info record, `{"leg": "imports", "sources", "edges", "unresolved"}`, beside the `links` record when any import named no file. A second pass over unchanged files reads nothing again. A changed Python file has its extracted `imports` rows replaced and nothing else touched; a row a caller authored on the same triple survives.

## Terms

- *Statement row*: one row of the kernel, as 147-1 decision 3 defines it.
- *Reference*: one thing a statement asks for, the unit resolution works on: each module path of a plain `import`, and each imported name of a `from` import, a wildcard included.
- *Package marker*: a live file named `__init__.py`; its directory is a package.
- *Anchor*: the directory an absolute import of a file is resolved from first (decision 5).
- *Extraction stamp*: the pair `link_source_hash`, `link_generation` on `vfs_entries`, which after this unit records the extraction of whichever extractor reads the row's extension.
- *Leg*: one extractor's share of a pass, reported on its own info record.

## What the code does today

- The publisher is markdown-typed. `extract_link_work` keeps rows whose `ext` is in `MARKDOWN_EXTENSIONS` and whose stamp does not cover the body (`links.py:62-77`); `publish_links` deletes only `edge_type == LINK_EDGE_TYPE` and `provenance == EXTRACTED_PROVENANCE` out-edges of the re-extracted sources (`links.py:132-139`) and inserts through `insert_arbitrated` (`links.py:140`).
- Every row a slice reads is stamped with the one markdown generation whatever its extension: `"link_generation": links_generation` in the slice's flag flip (`indexing.py:324-333`), where `link_generation()` returns `"md:2"` (`src/vfs/models/links.py:36`, `:62-64`). The generation probe compares that one value with no extension term (`indexing.py:644-652`). So any bump of the value makes every chunked row stale, and the next `rebuild` re-reads every body once.
- `refresh` skips the generation probe and reads only rows a write left `NOT chunked`, so a new generation waits for a `rebuild` (`src/vfs/storage/backends/database/maintenance.py:609-617`).
- The pass's cursor carries one `LinkOutcome(sources, edges, unresolved)` and builds one record, `{"leg": "links", ...}` with the detail "markdown references across ... documents name no live entry", only when `unresolved` is non-zero (`indexing.py:192-226`); `_chunk_pass` attaches it at three exits (`maintenance.py:623`, `:638`, `:640`).
- The consumers read every type but `fs`: the centrality prior's edge scan (`src/vfs/storage/backends/database/signals.py:102-106`, reading ids only, never `weight`) and `traverse` when no type is named (`src/vfs/storage/backends/database/traverse.py:248-256`).
- `indexing.py` holds 957 lines against `MODULE_LINE_CEILING = 1000` (`tests/lint/test_code_shape.py:76`) and is not in the size baseline.
- `SCHEMA_FORMAT_VERSION` is 28 (`rows.py:135`). A move bumps the moved root's version and rewrites its `ext` (`src/vfs/storage/backends/database/topology.py:328-335`); descendants keep theirs.

## The problem

On a mount of Python source no row links a module to what it imports, so the centrality prior and `traverse` see no structure in code. At the reference deployment's ten million files, code is a large share of the estate, and that share has no graph. The stamp law makes the obvious extension expensive: with one generation value on every row, adding a Python extractor or bumping it re-reads all ten million bodies, the per-corpus multiplier, when only the Python share needs reading. The pass must also stay bounded per slice: the resolution of a slice's imports must cost probes proportional to the slice, never to the corpus, on the least generous engine served.

## Decisions

1. **An `imports` edge runs from a Python file to the file a reference of it resolves to, weighted by the count of its statements that reach that file.** `edge_type = "imports"`, `distance = NULL`, `provenance = "extracted"`, `weight` the number of the source's statements with at least one reference resolved to the target, and `context` the folded line of the first such statement in source order. Two names of one statement that land on one module add one, so `from a import b, c` with both names defined in `a.py` weighs 1. A reference that resolves to its own source mints nothing and is not unresolved. Precedent: the source's Decided semantics 1, and `publish_links`' fold of a document's references into one row whose weight is their count and whose context is the first line (`links.py:107-130`).
2. **The extractor reads files whose extension is `py`, and a target is a `.py` file.** `PYTHON_EXTENSIONS = frozenset({"py"})`, as `Path.ext` spells it. A stub (`.pyi`) is not read and is not a target, because its imports repeat its module's and the parity of 147-1 was measured on `.py` files only; adding it later is a generation bump that re-reads Python files alone (decision 10).
3. **A reference is a plain import's module path, or a `from` import's imported name; a future import holds none.** `import a.b as x, c` holds two references; `from p import n, m` holds two; `from p import *` holds one. The row of 147-1 decision 5 for `__future__` is dropped before resolution and counted nowhere, because it is a compiler directive and names no file (EXECUTED: 277 of this repository's 3,795 statements). A reference whose candidates are all absent counts one on the leg's `unresolved`, and so does a relative reference that climbs above the mount root. EXECUTED on `src/` and `tests/` of this tree: 304 files, 3,795 statements, 6,802 references, 2,469 unresolved, every one of them outside the repository's own `vfs` and `tests` packages.
4. **Each reference yields an ordered tuple of candidate paths, and the first live one wins.** For a module path `m` (dots read as `/`) under a base `B`, the *module forms* are `B/m.py` then `B/m/__init__.py`. A plain import tries the module forms of its path under each root in turn. A `from m import n` tries, under each root in turn, the module forms of `m.n` and then the module forms of `m`; a wildcard tries only those of `m`. A relative import has one base, the file's directory raised `level - 1` times, and no roots; its module `m` may be empty, in which case the module forms of `m` are `B/__init__.py` alone. The roots, in order and without repeats, are the anchor, `<anchor>/src`, the mount root `/` and `/src`. A candidate that is not a valid `Path`, is the root, or lies under `/.vfs` is dropped. Candidates per reference are at most 16. Precedent: `link_candidates`' fixed order with no configuration (`models/links.py:103-124`), its first-live-candidate rule (`links.py:111`), and CPython's search of `sys.path` in order, finding the package first and the name in it second; preferring the submodule file when both exist is the path-only reading the study verified (study, open choice 3). The roots past the study's verified list are choice 2.
5. **The anchor is the parent of the file's topmost package, or the file's own directory when that directory holds no `__init__.py`.** From the file's directory the walk climbs while the directory holds a package marker; the anchor is the parent of the last directory that did. A file outside any package anchors at its own directory, which is the directory Python puts first on `sys.path` for a script. The walk needs to know which ancestor `__init__.py` paths are live, so the publisher probes them (decision 8). A namespace package (PEP 420, no `__init__.py`) ends the walk early; its relative imports still resolve, since they need no anchor, and its absolute imports resolve when the mount root or a `src` root holds the package. EXECUTED on this tree: every import of `vfs` from `tests/` resolves through `/src`, and every import of `tests` resolves through `/`.
6. **A target, and a package marker, is a live row of a content kind.** Both probes read `deleted_at IS NULL` and `kind_membership(entry).predicate` (`src/vfs/storage/backends/database/reads.py:736-743`), so a directory named `x.py` is never a target. The `links` probe keeps no kind term, since a markdown link may name a directory (`links.py:161-163`).
7. **The resolver is `src/vfs/models/imports.py`, pure and session-free.** It holds `IMPORT_GENERATION: Final = 1`; `IMPORT_EDGE_TYPE: Final = "imports"`; `PYTHON_EXTENSIONS`; `import_generation() -> str`, which returns `f"py:{IMPORT_GENERATION}"`; the named tuple `PythonImport(modules, names, level, context)`, the noun 147-1 gives the kernel's row; `extract_imports(bodies: Sequence[str]) -> list[list[PythonImport]]`, which calls `native.python_imports` on the encoded bodies; `package_markers(source: Path) -> tuple[Path, ...]`, the `__init__.py` path of each ancestor directory below the root, nearest first; `import_anchor(source: Path, markers: AbstractSet[Path]) -> Path`; `import_candidates(source: Path, anchor: Path, statement: PythonImport) -> list[tuple[Path, ...]]`, one tuple per reference; and `fold_imports(source, anchor, statements, live: Mapping[Path, T]) -> ImportFold[T]`, the named tuple `(weights: Counter[T], contexts: dict[T, str], unresolved: int)` of decisions 1 and 3. Precedent: `models/links.py`, which holds the markdown resolver and touches no session (`models/links.py:1-12`).
8. **The storage side is `src/vfs/storage/backends/database/imports.py`.** `ImportWork(entry_id, source, statements)` is one re-extracted file. `extract_import_work(rows, generation)` keeps rows whose `ext` is in `PYTHON_EXTENSIONS`, whose `content` is not `NULL` and whose stamp does not cover the body (`content_hash == link_source_hash and link_generation == generation`), then calls `extract_imports` once for the batch; it runs in `_assess_and_split`, so the parse rides the offload hop and the body is read once. `publish_imports(session, tables, profile, membership_budget, work) -> ExtractOutcome` issues, in order: one probe of the distinct package markers of the work's sources, chunked by `membership_budget`; one probe of the distinct candidates computed from the anchors it found, chunked the same way; the fold; then the replacement of decision 9. Every list is sorted before it is chunked, as `links.py:132` and `:160` sort theirs.
9. **The shared parts move to `src/vfs/storage/backends/database/extracted.py`, and `publish_links` uses them with no change of behaviour.** The module holds `ExtractOutcome(sources, edges, unresolved)`, renamed from `LinkOutcome` because one concept takes one noun in private code too ([the naming guide](../../documentation/maintainers/how-we-name.md), "Nouns"); `live_entries(session, tables, profile, membership_budget, paths, *terms) -> dict[str, str]`, the body of `_resolve_candidates` (`links.py:149-165`) with extra terms the caller adds; `replace_extracted(session, tables, profile, membership_budget, edge_type, sources, rows) -> int`, the chunked delete of the sources' extracted out-edges of that one type and the `insert_arbitrated` of the fresh rows, returning the rows that landed; the stamp helpers of decision 10; and `extracted_records(links, imports) -> list[ResultError]` of decision 13. The move keeps `indexing.py` under its line ceiling, which the added fields and calls would otherwise approach, and gives the stamp law and the replacement one owner instead of a copy per extractor.
10. **The extraction stamp keeps its one pair, and its value is the generation of the extractor that reads the row's extension.** A markdown row is stamped `link_generation()`, a Python row `import_generation()`, and a row no extractor reads the constant `NO_EXTRACTOR_GENERATION = "none"`. The stamp is one SQL `CASE` on `vfs_entries.ext` inside the slice's existing version-guarded flip, so it costs no statement; the guard makes the `ext` it reads the one the slice read, since a move that changes `ext` bumps the version (`topology.py:328-335`) and the flip then misses. The probe term becomes `link_generation IS NULL`, or `ext` in an extractor's set and `link_generation` differing from that extractor's value; a non-null value on a row no extractor reads is current. `indexing.py` builds both from one private table, `_extracted_generations()`, returning `((MARKDOWN_EXTENSIONS, link_generation()), (PYTHON_EXTENSIONS, import_generation()))` at call time, so the seams the tests patch today (`indexing.link_generation`, at `tests/storage/database/test_links.py:254`, `tests/storage/database/test_refresh.py:834`, `tests/storage/database/test_indexing.py:2221`) keep working and a new `indexing.import_generation` seam joins them. No column is added and `SCHEMA_FORMAT_VERSION` stays 28. A bump of one extractor re-reads that extractor's files alone. This departs from spec 138 decision 4, "A generation bump re-dirties every entry once"; the alternatives are choice 1.
11. **The first `rebuild` after this lands re-reads every `.py` row once, and no other row.** Every chunked row carries `md:2` today; under decision 10 that value is current for markdown and for rows no extractor reads, and stale for Python. `refresh` mints the edges of Python files written after the landing, and leaves the existing ones to the next `rebuild`, by the law of `maintenance.py:609-617`.
12. **Both passes extract, in the same slice transaction, links first.** `chunk_dirty` calls `publish_imports` after `publish_links` (`indexing.py:351`), each on its own work list from `_ChunkWork`, which gains the field `imports: list[ImportWork]`; `_assess_and_split` takes the import generation beside the link generation. Both `rebuild` and `refresh` reach it through `_chunk_pass`, so no phase is added.
13. **Each leg reports on its own record, and the links record does not change.** `ChunkCursor` gains `imports` and `next_imports`, adopted with `links`, and `links_record()` becomes `extracted_records()`, which returns the links record then the imports record, each only when its `unresolved` is non-zero, as today. The imports record is `classified(ErrorKind.not_found, severity=Severity.info, detail=f"{unresolved} Python imports across {sources} modules name no file in the mount", data={"leg": "imports", "sources": sources, "edges": edges, "unresolved": unresolved})`. `sources` counts the re-extracted Python files and `edges` the rows that landed, summed over the committed slices. The three call sites in `maintenance.py` take the new name. Precedent: the study's verified choice 5, one record per leg.
14. **The ledger rules of spec 138 hold for `imports` rows unchanged.** Only a re-extracted source's `extracted` rows of the type `imports` are deleted, so its `links` rows, its authored rows and every row where it is the target stay. A fresh row on a triple an authored row holds is dropped by `insert_arbitrated`, and the authored row survives. A changed target rewrites nothing. A same-body overwrite or a move that keeps the extension re-extracts nothing, so a moved module's relative imports keep the targets they had. A reference to a file that does not exist yet resolves when its source next changes or the import generation bumps. A deleted target keeps its in-edges for its return (`tests/storage/database/test_links.py:239-247`).
15. **The two extractors are called by name, and no registry is declared.** The source's list of `(extension set, kernel, resolver)` would have two members; [147-1 decision 2](../2026-11-25-python-import-statements-are-read-by-an-engine-kernel/spec.md) already declines a type for languages that do not exist, and AGENTS.md, "Code smells", names it speculative generality. A third language adds an arm to `_extracted_generations()`, a work field, a publish call and an outcome. Of these four, only the table is shared, because only the stamp and the probe must agree.
16. **No right and no capability changes.** The pass runs under the index lease as it does today. `traverse` judges every row it walks under the caller's view whatever the edge type (`traverse.py:1`), and the info record carries counts and no path. `InMemoryStorage` is the database backend on SQLite (`src/vfs/storage/backends/memory.py:1-8`), so no backend gains a silent gap and no trait is declared. No leak test is owed, and none is added.
17. **The corpus check is this repository, pure and marked `slow`, and replaces the source's golden-set criterion.** The ranking harness holds no Python corpus (study, "What is stale"), so a re-score would measure nothing. The check runs `extract_imports` and `fold_imports` over every `.py` file of `src/vfs` and `tests/` outside `fixtures`, with the tree's own paths as the live set, and asserts that every reference into `vfs` or `tests` resolves. A Python ranking corpus is a follow-up of its own.

## Cost

Costed against [the reference deployment](../../AGENTS.md#the-reference-deployment-the-scale-every-idea-is-filtered-through), on SQLite and Postgres, whose `membership_budget` is the same 32,668 (`in_list_budget` 32,766 and 65,535 against SQLAlchemy's `insertmanyvalues_max_parameters` of 32,700 net of the 32-bind reserve, EXECUTED and READ at `src/vfs/storage/backends/database/dialects.py:363`, `:416`, `:535`, `:548`), and on the generic floor's 1,000 (`dialects.py:452`).

- **The multiplier is per file write, not per index visit.** A slice reads only rows a write left `NOT chunked`, or rows stale under the probe, so an unchanged body is never parsed again. That is about 1,050,000 rows a day at the centre and 1,100,000 at the ceiling, times the share of files that are Python, which is an *assumption* no public figure gives. On a generation bump the multiplier is per corpus, once, on that same share alone (decision 10).
- **Per slice, bounded by `CHUNK_SLICE_ENTRIES = 256` (`indexing.py:131`).** Per Python file of this tree, EXECUTED: 12.5 statements, 22 references, at most 16 candidates per reference, and 31 distinct candidate paths once a corpus is deduplicated; 29 distinct package markers over 304 files. A slice of 256 Python files then asks about 8,000 candidate paths and at most 256 times the depth in markers. Statements added per slice: ⌈markers / budget⌉ + ⌈candidates / budget⌉ probes, ⌈sources / budget⌉ deletes, and the insert's statements under SQLAlchemy's bind budget, `bulk_insert` (`dialects.py:702`). On SQLite and Postgres that is one of each, four statements; on the generic floor about twelve. No statement grows with the corpus or with the batch: a 10,000-file batch is 40 slices, each the same.
- **Through the day.** A partial pass of 1,250 to 2,500 files is 5 to 10 slices, about 40 statements more at most. The nightly million is about 3,900 slices and 15,600 statements more over six hours, under one a second.
- **Rows.** EXECUTED: 1,791 edges from 304 files, about 5.9 a file and at most weight 3. At ten million files with a tenth of them Python, an *assumption*, that is about 5,900,000 `imports` rows. A changed module deletes and inserts its own, about six. The centrality prior holds every non-`fs` edge in memory once a `rebuild` (`signals.py:19-21` names that whole-corpus profile), so it holds those rows too; the profile is acknowledged there and not capped here.
- **The probe of the generation law.** Today's probe is one `LIMIT 1` read a `rebuild`, lock-free (`indexing.py:229-234`); decision 10 adds two `ext IN` arms of three binds and changes nothing else, so it stays per corpus, once a day.
- **Locks.** The extraction runs inside the slice's transaction, which already holds its 256 entry rows from the flip to the commit; it adds four statements to that window and takes no new lock. A read never waits on it: Postgres reads the committed snapshot and SQLite in WAL serves readers beside the writer. A write to one of the slice's entries waits for the slice's commit, as today, which `CHUNK_SLICE_ENTRIES` bounds.
- **The collision path.** When one fresh row of a slice collides with an authored row, `insert_arbitrated` redrives the slice's inserts one statement a row (`src/vfs/storage/backends/database/edges.py:463-490`), about 1,500 statements for 256 files at this tree's density. Authored `imports` rows are rare, and the bound is the slice; it is the `links` leg's path today.

## Left as it is

- **The column names.** `link_source_hash` and `link_generation` keep their names though they record either extractor; a rename is a schema change, and belongs with a later format bump. The comment above them (`rows.py:398-399`) is reworded.
- **A file moved from `.md` to `.py` keeps its extracted `links` rows,** and gains `imports` rows. Each extractor owns its own type (decision 14); the same gap exists today for a move from `.md` to `.txt`.
- **Resolution at extraction time.** An import whose target appears later, and a target that moves, are as spec 138 decision 4 accepts. The direction that closes both is a re-resolution of unresolved references when a target is created, and no spec carries it.
- **The prior reads edge ids, not weights** (`signals.py:102-106`). A weight of 3 counts as one edge there.
- **`.pyi` stubs, dynamic imports and symbol-level references.** Out by decisions 2 and 3 and by 147-1's scope.

## Choices to confirm

1. **How the stamp records two extractors.** Options: (a) one composite value on the existing pair, `md:2+py:1`, with no schema change, where every bump re-reads all ten million bodies once and the landing re-publishes every markdown document; (b) one pair per extractor, two columns and a schema format bump, sequenced after the deletes spec's 29 and taking 30, where a bump re-reads its own files; (c) the existing pair with a value per extension (decision 10), no schema change, where a bump re-reads its own files and the landing re-reads only Python. Taken: (c). It has (b)'s cost profile without its schema change, and it is the cheaper to reverse: moving to (b) later adds columns, where reversing (b) drops them under a second format bump. Its limit is one extractor per extension, which holds while the extension sets are disjoint; an extension two extractors read would take a composite value for that extension alone.
2. **Whether `<anchor>/src` is a root.** The study verified the roots "the file's own package for relative imports, the parent of its topmost package, the mount root, and `/src`". Taken: those, with `<anchor>/src` after the anchor, because a mount holding many projects keeps each one's `src` layout under the project directory, where a test package's imports of the project's package resolve only through it; `/src` is the same rule at the mount root. Either answer is reversed by a bump of `IMPORT_GENERATION`, which re-reads Python files alone under choice 1's side.
