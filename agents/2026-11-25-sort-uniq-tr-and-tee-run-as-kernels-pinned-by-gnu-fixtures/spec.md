# `sort`, `uniq`, `tr` and `tee` print the same whatever their chunks, a 10,000-line pipeline reads its file once in counted chunks, and `awk` and `jq` answer 127 with a hint at a served form

A draft, written on 2026-11-25 against `dev` at `27f3d24d`. It is not reviewed, and nothing is built. It serves story F6 of [the roadmap](../../context/standards/roadmap.md) at gate f, criteria 2, 3 and 5 as they bear on `sort`, `uniq`, `tr`, `tee`, `awk` and `jq`, under roadmap decisions D22 and D34. It is unit 168-2 of [the conversion map](../2026-11-25-the-backlog-converted/units.md), converted from `context/specifications/archive/168-text-program-kernels/spec.md` (called the source below), and it rests on [the reassessment of 168-2](../2026-11-25-the-backlog-converted/reassessment/kernels-sessions-and-deadline.md) and on the built shell, [the shell speaks bash](../2026-11-21-the-shell-speaks-bash/spec.md).

## The outcome wanted

An agent that pipes text through `sort`, `uniq`, `tr` or `tee` gets the same bytes however vfs happens to cut the input into reads, and a law in the crate proves it at one byte, at small fixed sizes and at seeded random sizes. An agent that runs `cat f | sort | uniq -c | sort -rn | head -5` over a 10,000-line file gets GNU's five lines and GNU's `PIPESTATUS`, and the line costs exactly one `read` verb call on the vfs host and exactly the declared number of read requests on the reference host, each byte asked once. An agent that types `awk` or `jq` gets exit 127 and a hint that names a form vfs runs today (`sed -n 'A,Bp'`, `cut -d D -f N`, `cat`, `grep -o`), and nothing in the hint says that either program will arrive.

## Terms

- **A chunk** is the bytes one `Read` request's reply carries. The machine asks for `files::CHUNK` bytes a read, 64 KiB (`crates/vfs-shell/src/machine/files.rs:16`); a host may answer fewer, and the machine reads on until the reply says end of file.
- **A read schedule** is the list of lengths `MemoryHost` answers reads with, used in order and cycled, so that one line can be run with its chunk boundaries moved.
- **The split law** is the roadmap's name for the chunk law: a program's output is the same whatever the chunk boundaries of its input.
- **A served form** is a program and option that the shell runs today, by its own library or by the vfs host.

## What the code does today

1. The chunk law does not move a chunk boundary. `MemoryHost` declares `read_chunk` as "The most bytes one read answers with" (`crates/vfs-shell/src/host/memory.rs:50-51`) and sets it to `None` (`:78`), and no line of the crate reads it (EXECUTED: `grep -rn read_chunk crates/vfs-shell` finds those two lines and the law's assignment at `tests/laws.rs:70`). A `Read` is answered with the request's own `length` (READ `memory.rs:295-311`). So `output_is_the_same_whatever_the_chunk_boundaries` runs the same chunks six times and compares a run with itself.
2. The chunk law's line runs `cat`, `wc`, `while read`, `head -c` and `$(<…)`, and none of `sort`, `uniq`, `tr` or `tee` (READ `laws.rs:65-79`).
3. `sort`, `uniq` and `tr` take their whole input before they write: `sort` reads each operand whole (`text.rs:1152`), `uniq` its one input (`:1339`), and `tr` all of standard input (`:1613`). The bytes are checked against the line's memory budget with `fits` and are not charged (READ `programs/mod.rs:196-205`, `machine/exec.rs:1958-1960`). `tee` writes each chunk to standard output as it arrives and keeps a copy of all of it for its files, which it writes at the end (READ `text.rs:1703-1728`); that copy is neither checked nor charged.
4. A pipe holds at most `PIPE_CAPACITY` bytes, 64 KiB, charged while held (READ `crates/vfs-shell/src/machine/io.rs:16`, `:355-362`). A write to a pipe with no reader ends the writer with status 141 (READ `exec.rs:2389-2394`). The two constants live in modules private to the crate (READ `machine/mod.rs:12-13`), so an integration test cannot name them.
5. The pipeline of F6 criterion 3 already behaves as GNU does on the vfs host. EXECUTED (a scratch probe through `AsyncVirtualFileSystem.cli`, 2026-11-25): over 10,000 lines of 60 bytes, `cat /w/f | sort | uniq -c | sort -rn | head -5` printed five lines beginning `      2 k4999`, its `statuses` were `[[0, 0, 0, 141, 0]]`, the router's `read` was called once with `/w/f`, and the result carried no fact. No test pins any of it (READ `tests/shell/test_host.py`, `crates/vfs-shell/tests/laws.rs`), and the roadmap says the counted pin is "not written" (READ `roadmap.md:751`).
6. `awk` and `jq` answer 127 with no hint. EXECUTED (the same probe): `awk '{print $1}' /w/f; echo $?; jq . /w/f; echo $?` printed `127` twice, with `bash: line 1: awk: command not found` and the same for `jq` on standard error, and no fact. `UNKNOWN_PROGRAMS` holds `git`, `sudo`, `python3`, `python` and `perl` (READ `src/vfs/shell/host.py:113-120`), and the vfs host answers a name in it with 127 and its text, and keeps no fact (READ `host.py:445-446`). The reference page lists the same five (READ `documentation/reference/shell.md:129`).
7. The kind the roadmap names for the refusal is reserved. `ErrorKind.unrecognized` is "JSON-RPC METHOD_NOT_FOUND: the verb name is not in the vocabulary", and "only dispatch emits ``unrecognized``" (READ `src/vfs/results/kinds.py:49-50`, `:79`).

## The problem

The roadmap's F6 asks three things of these programs that `dev` does not prove. The split law has never been run on them, and the law that exists is vacuous, because the host field it sets is read nowhere. The counted pipeline is not written, and its wording comes from the retired seam: "feeds 10 chunks", "queue depth ≤ 2" and "reports the second sort cancelled" name a queue and a cancellation event the machine does not have. And `awk` and `jq`, the first a measured 2.7% of agent calls in the source's census (READ `context/specifications/archive/168-text-program-kernels/spec.md:62`, 371 of 13,746), meet a bare "command not found" that tells the agent nothing about what to type instead.

Each matters at the reference deployment. About 150,000 verb calls a day arrive through agents, most of them in pipelines; if the corpus is representative, about 4,000 lines a day name `awk` (INFERRED, the D22 verification's arithmetic), and each one that gets a bare 127 costs the agent a retry with no direction. The two drafts above will rewrite `sort`, `uniq`, `tr` and `tee` to keep raw bytes and to stream; without a split law that moves real boundaries, a rewrite that splits a UTF-8 character or a line across two chunks lands unseen. And a read must cost in proportion to what it returns: the pipeline pin is the one test that says a 600,000-byte file is asked of the host once, in ten chunks, and never again.

## Decisions

1. **`MemoryHost` answers reads by a schedule that binds.** The field `read_chunk: Option<u64>` is replaced by `read_chunks: Vec<u64>`. Empty, each `Read` is answered with the request's `length`, as today. Otherwise the n-th `Read` the host answers carries at most `read_chunks[n % len]` bytes, an entry of 0 is answered as 1 (an empty reply means end of file to `read_whole` and `FileReader::refill`, READ `exec.rs:1962-1965`, `files.rs:133`), and `eof` is true only when the reply reaches the file's end. Reason: today the law's control does nothing (fact 1), and one field with one meaning serves the fixed sizes and the random schedules alike. Precedent: the machine already accepts a short reply that is not the end (`read_whole` loops, `refill` keeps `eof` false), so no machine code changes.
2. **The existing chunk law moves to the new field and stays as it is otherwise.** `output_is_the_same_whatever_the_chunk_boundaries` sets `host.read_chunks = vec![chunk]`. Once boundaries really move, a failure it reveals in its own line (`while read`, `head -c`, `$(<…)`) is a divergence from bash and is fixed in this work, since the law is the measure the shell spec set (its Tests, under Laws: "Output unchanged whatever the chunk boundaries").
3. **A law that moves boundaries proves that it moved them.** Every chunked run in `laws.rs` asserts that it asked more `Read` requests than the whole run of the same line. Reason: the existing law passed for weeks while it changed nothing; this assertion makes a vacuous run fail. Precedent: `the_machine_ends_under_any_replies_without_panicking` asserts that its lines started and asked (`laws.rs:535-539`).
4. **The split law over the four programs is one new law with one line.** `the_text_programs_print_the_same_whatever_the_chunk_boundaries` in `crates/vfs-shell/tests/laws.rs` runs, over a file `/work/t.txt` added to its world, the line `sort t.txt; sort -n -k2 t.txt; sort -u < t.txt; cat < t.txt | sort -r; uniq -c t.txt; sort t.txt | uniq -d; cat < t.txt | uniq -u; tr a-z A-Z < t.txt; cat < t.txt | tr -s ' '; tr -d 'é本' < t.txt; tee c1.txt < t.txt | wc -c; cat c1.txt; cat < t.txt | tee -a c1.txt > /dev/null; wc -c < c1.txt`. Each program is reached by every input path it takes: an operand (read through `read_whole`), a redirection (a `FileReader` refilled a chunk at a time) and a pipe (the upstream `cat` writes each chunk as it reads it). `t.txt` holds repeated and adjacent equal lines, numbers in a second field, runs of spaces, a tab, two-byte and three-byte UTF-8 characters (`é`, `日本`) and a last line with no newline, so that a one-byte chunk splits a character and a line. Reason: these are the boundaries a streaming rewrite breaks. The input stays valid UTF-8, so the law does not depend on whether the filters draft has landed.
5. **The boundaries are whole, fixed and seeded.** The law runs the line once with `read_chunks` empty (whole), then with `[1]` (one byte at a time), `[2]`, `[3]`, `[5]` and `[64]`, then with sixteen schedules drawn from the file's existing `Rng`: seeds 1 to 16, each scrambled as `the_machine_ends_under_any_replies_without_panicking` scrambles its seed (`laws.rs:500`), each schedule 32 lengths of `1 + rng.below(97)`. Every run's standard output and status equal the whole run's. Reason: the roadmap asks "whole, one byte at a time, random boundaries" (`roadmap.md:755`), and the fixed sizes keep the existing law's precedent; seeded schedules make a failure reproducible by its seed. Precedent: the source's split law ("whole, one byte at a time, and at seeded random boundaries", source `spec.md:153`) and `tests/test_native.py:448`.
6. **Two constants become nameable.** `crates/vfs-shell/src/machine/mod.rs` adds `pub use files::CHUNK as READ_CHUNK;` and `pub use io::PIPE_CAPACITY;`. Reason: the counted pin derives its counts from the machine's declared sizes, never from a number written into the test, and both modules are private to the crate (fact 4). The names are new public names of the crate only; `vfs` gains none.
7. **F6 criterion 3 is restated in the machine's terms.** Decided 2026-11-25: over a file of 10,000 lines, `cat f | sort | uniq -c | sort -rn | head -5` prints GNU's five lines; the host is asked exactly `len(f).div_ceil(READ_CHUNK)` `Read` requests of `f`, which is 10 for the fixture, at offsets 0, `READ_CHUNK`, 2 × `READ_CHUNK` and so on, so each byte of `f` is asked once and no stage reads it again; the line asks no `Start` and no `Feed` request, because every stage is a library program the machine runs itself; and its `statuses` are `[[0, 0, 0, 141, 0]]`, the second `sort` ending on a closed pipe as SIGPIPE ends it. "Queue depth ≤ 2" is dropped: the machine has no queue, and what a stage may hold in flight is one pipe of `PIPE_CAPACITY` bytes, bounded and charged by construction (fact 4). "Cancelled" becomes status 141, which is what bash reports and what `PIPESTATUS` carries. Reason: these are the counts the machine can be asked for, and each says what the retired wording meant: input in fixed chunks, each `sort` taking its input once, bounded holdings, and the early close seen upstream.
8. **The pin's file is built so that its counts follow from the declared sizes.** Line i, for i from 0 to 9,999, is `k` and i mod 5,000 in four digits, a space, 53 zeros and a newline: 60 bytes, 600,000 bytes in all, each key twice. The test asserts two preconditions before the pin: `len.div_ceil(READ_CHUNK) == 10`, and that the `uniq -c` output, 5,000 lines of 68 bytes (340,000 bytes), exceeds `2 * PIPE_CAPACITY`, so that the second `sort` is still writing when `head` exits. Reason: the source's "640 KiB" assumed the retired seam's rows per chunk; with 64 KiB chunks a file of 589,825 to 655,360 bytes is ten chunks. The equal counts make `sort -rn` fall back to its whole-line comparison reversed, a GNU rule the recorded case pins too.
9. **The pin runs three ways, each at the layer its count lives.** GNU's answer is a recorded case, `tests/shell/cases/programs/pipelines/top-five-of-ten-thousand-lines.sh`, which builds the file with a `for ((…))` loop of `printf`, prints `wc -c < f`, runs the pipeline and prints `ps=${PIPESTATUS[*]}`; its record is made by `scripts/shell_record.py` and never by hand. The request counts are a law in `crates/vfs-shell/tests/laws.rs` over `MemoryHost`. The verb count is a test in `tests/shell/test_host.py` through `cli`, with the router's `read` spied by the existing `_counted_reads` helper (`test_host.py:309-322`). Reason: bash cannot count requests and the reference host cannot count verb calls; only the three together state the criterion. Precedent: the recorded `pipelines/pipestatus-of-each-stage` case and `test_one_open_reads_one_version_across_its_chunks` (`test_host.py:357-371`).
10. **The source's criterion 9 is restated as a memory pin on the three programs that take their whole input.** Under a memory budget of 1 MiB, `sort big`, `uniq big` and `tr a b < big`, with `big` a 2 MiB file, each end the line with status 137 and `Budget("memory", 1048576)`, as `the_memory_budget_ends_a_line_before_it_holds_more` reads it (`laws.rs:185-197`). `tee` is left out: its copy is checked by nothing today (fact 3), and the descriptors draft's decision 5 removes the copy. Reason: the source asks that a `sort` past the budget "stops with `budget_exhausted`" (source `spec.md:183`); in the machine that is the memory budget's own ending, and the `fits` checks already give it, so the pin holds the behaviour while the filters draft rewrites the three.
11. **`awk` and `jq` join `UNKNOWN_PROGRAMS` with two exact hints.** `"awk": "command not found; sed -n 'A,Bp' prints lines A to B, and cut -d D -f N prints field N"` and `"jq": "command not found; cat prints the JSON for the caller to parse, and grep -o prints each match of a pattern"`. Reason: each names forms the shell runs today (the recorded cases `programs/sed/n-with-p-prints-selected-lines`, `programs/cut/complement-fields`, `programs/grep/only-matching-with-o` exercise them), and the `awk` forms are the two the source and D22 name for the measured uses (`awk -F:` and field printing). Precedent: `perl` points at `sed -i` (`host.py:118`), a served form, and the source's hints point at the same `sed` and `cut` forms (source `spec.md:62`).
12. **Neither hint promises an arrival.** No hint says `awk` or `jq` will be installed, will arrive or is not yet served. Reason: D22's lean is that 0.1.0 ships with no generic WebAssembly host and that `awk`, `jq` and `jaq` are T6 at 0.2 (READ `roadmap.md:1185`, `:1233`), so at 0.1.0 nothing installs either, and a hint that promises one misleads every agent that reads it. This departs from the source's "awk arrives as an installed program" and from the D22 verification's "the installed `jaq` for `jq`"; both are listed below.
13. **The two names answer as the other five do: exit 127, the hint on standard error, and no fact.** Reason: the vfs host keeps no fact for a name in `UNKNOWN_PROGRAMS` (fact 6), and the landed ruling of 2026-11-22 makes a program vfs refuses a warning only when vfs knows it and will not run it (126, `vfs.unsupported`), while a program's own exit adds none (READ `agents/2026-11-21-the-shell-speaks-bash/progress.md`, "Ruled on 2026-11-22, the result of a line"). `vfs.unrecognized` is reserved for dispatch (fact 7), so F6 criterion 5's "`vfs.unrecognized` 127" is read as exit 127 with the hint. Adding a fact later is additive; see the first choice below.
14. **Only the two measured names are added.** `gawk`, `mawk`, `nawk` and `jaq` keep the bare 127. Reason: the source and D22 name `awk` and `jq`, the census measures those spellings, and a further name is one more entry whenever a measurement shows it.

## Cost

Nothing this spec adds runs per corpus, per index visit, per batch or per file write, and nothing touches storage, so the least generous engine served, SQLite or Postgres, sees no new statement. Per verb call: a line naming `awk` or `jq` costs one `Start` request and one lookup in a five-entry dictionary that becomes seven, and calls no verb; at the inferred 4,000 such lines a day that is 4,000 dictionary lookups. The pipeline pin states the per-call cost the shell already pays and keeps it: one `read` verb call for a file of any size, `len.div_ceil(READ_CHUNK)` host reads on the reference host, and at most `PIPE_CAPACITY` bytes held in each of the four pipes. `MemoryHost`'s schedule is a test host's; it adds one index per read. The new law runs its line 22 times, 21 of them chunked; at one byte a chunk over a file of a few hundred bytes that is a few hundred reads a run, counted, never timed.
