# Study: Set-based scattered delete shrinks the topology-lock hold

Spec folder: `context/specifications/active/102-set-based-scattered-delete/` (spec.md only, 34 lines; no plan.md or tasks.md). EXECUTED: `ls` of the folder. Read at HEAD 0ed462f on 2026-11-25.

## Verdict

Overtaken. The spec reshapes a delete arm that moved each target under a trash bucket with about four statements per target; that arm no longer exists, because spec 162 replaced trash-as-a-place with a tombstone on the row, and the tombstone delete is set-based with a statement count that is flat in the batch size and pinned by test.

The residual problem the spec measured, a per-target topology statement run inside the mount's serialization point, survives on `move` and `copy`, which still run pair by pair at about 13 statements per pair; that is a different verb and a different design, and it is not a conversion of this spec (see Notes for the conversion).

## Against the tree

- The spec's problem: trash-everything delete runs about 4 statements per target inside one serialized topology transaction, 52.9 s on Postgres for a scattered 10k batch (READ, `context/specifications/active/102-set-based-scattered-delete/spec.md:13`). Its direction: group targets per trash bucket, one reparent executemany plus one path-rewrite pass per bucket (READ, spec.md:15).
- Slice A was delivered as a memo (READ, spec.md:3; `context/research/2026-08-25-set-based-scattered-delete.md`): the per-target bumps were the cost, a set-based prototype held the lock 24 to 40 times shorter, and the half-open byte range was sargable where a non-constant LIKE was not (READ, memo:44-61). Slice B, the design, was never written (READ, spec.md:3, spec.md:34).
- Delete no longer moves anything. A deleted row stays at its path with `deleted_at` and `trash_root_id`; nothing in the trash family rewrites a path, a parent pointer or a posting (READ, `src/vfs/storage/backends/database/trash.py:1-12`). `TRASH_ROOT` is now a view over tombstoned rows, not a place rows move to (READ, `src/vfs/paths.py:45-47`, `src/vfs/paths.py:767-821`).
- Delete is set-based: one bounded snapshot fetch, then each kind of statement once per chunk, "so a 10,000-target call costs the same handful of round trips as a one-target call on every engine" (READ, `trash.py:14-17`). The call sequence is snapshot, chunked live-child counts, chunked root claims, one descendant stamp per chunk of roots, one chunked parent bump (READ, `trash.py:157-210`, `trash.py:470-499`). Every chunk goes through the shared `chunked()` helper at `membership_budget` (READ, `trash.py:78`, `trash.py:498`).
- Pinned by count, never by clock: a cascade delete and restore of 1,000 and 2,000 children each issue at most 10 statements and touch no posting (READ, `tests/storage/database/test_trash.py:1051-1074`); a scattered batch of 1,000 targets issues exactly the statements a batch of 10 issues (READ, `test_trash.py:1076-1100`). The roadmap's state table records "delete/restore" among the verbs with a 10k count pin (READ, `context/standards/roadmap.md:449`).
- Spec 162, the replacing design, records both slices built and committed on 2026-10-12 as `7d0bc3c` (READ, `context/specifications/active/162-trash-as-a-tombstone-on-the-row/spec.md:3`). That hash is not reachable at HEAD (EXECUTED: `git log -1 7d0bc3c` fails), consistent with history since squashed; the code it describes is present (READ, `trash.py` as above). Spec 162 is still under `active/` and is itself listed as built but not archived (READ, roadmap.md:106).
- The 2026-10-08 trash memo names the old cost directly: delete rewrote the path under `/.vfs/trash/<hour>/` at about six row writes per file (READ, `context/specifications/active/162-trash-as-a-tombstone-on-the-row/spec.md`, Intent paragraph). That is the arm spec 102 meant to reshape; it is gone.
- Every acceptance criterion of spec 102 is either met by another route or moot (INFERRED): the lock hold for a scattered 10k delete is now a constant handful of statements (criterion 1, met by design and pinned at 1k on SQLite; not measured here on the server legs); batch atomicity and guard discipline are held by the serialized-verb runner and the guarded claims (READ, `trash.py:5-9`); "trash restorability" is now a column clear (READ, `trash.py:31-38`); no statement grows with the batch (criterion 3, `chunked()` everywhere in `trash.py`).
- One residue of the memo's finding remains in delete: the descendant stamp is an executemany `UPDATE ... WHERE path LIKE :b_pattern` with one bound pattern per root (READ, `trash.py:490-499`; pattern built by `descendant_pattern`, `src/vfs/storage/backends/database/descent.py:205-207`). The memo measured a non-constant LIKE inside a VALUES join as non-sargable (READ, memo:58-59); a bound pattern per execution is a different plan shape and was not measured here (INFERRED). This is a plan-quality question for D4's count pins and the engine legs, not a lock-hold design.
- Move and copy still run pair by pair: `transfer_rows` adjudicates and applies "a batch of moves or copies, pair by pair" (READ, `src/vfs/storage/backends/database/topology.py:118-131`), and each move pair issues a guarded root claim, a fs-mirror repoint, a postings move, a descendant select, a rewrite executemany, a second postings move and two parent bumps (READ, `topology.py:299-447`).
- EXECUTED (scratch probe on SQLite, `uv run python`, scratchpad `probe_move.py`): 100 scattered single-file move pairs across 50 directories issued 1,310 statements; 200 pairs issued 2,610. About 13 statements per pair, linear in the pair count, so a 10,000-pair scattered move is about 130,000 statements inside one serialization point (INFERRED from the two counts).

## Notes for the conversion

- Action under R7 criterion 2: move the folder to `context/specifications/archive/` with a one-line landing note: overtaken by spec 162's tombstone delete; slice A's memo stays as research; slice B never built.
- Do not carry the 2026-08-25 memo's delete prototype forward as a design. Its two reusable findings are the set-based guarded reparent and the half-open byte-range descendant predicate (READ, memo:44-61, memo:90); both apply to a scattered `move`, and the byte range also bears on delete's remaining per-root LIKE stamp (READ, `trash.py:490-499`).
- The scattered-move gap is real at the reference deployment: about 13 statements per pair (EXECUTED, SQLite), so a 10,000-pair batch is about 130,000 statements while every other move, delete, restore and sweep on the mount waits behind the serialization point (READ, deletes memo:73 on what waits; INFERRED for the product). AGENTS.md's lock rule ("a lock other callers need is held for the length of a commit", Per lock) makes this a design defect for a supported 10k batch, not an edge case.
- Where it should go: D4's `move` and `copy` pins first record the linear formula (READ, roadmap.md:484), so a later set-based move is a visible delta, as D4 criterion 4 does for spec 080. The design waits on the deletes spec, because D55 changes what a replacing move writes and the deletes memo leaves the large-move shape open (READ, deletes memo:81). Needs a ruling: whether the scattered-pair move becomes its own new spec at gate b beside D4, or a slice of the deletes spec.
- A separate integrity window touches both delete's descendant stamp and move's rewrite on READ COMMITTED engines: a child committed inside the window can be left behind its parent (READ, `context/research/2026-11-14-a-child-committed-inside-a-delete-or-a-move-can-be-left-behind-its-parent-on-a-read-committed-engine.md:1-12`). It is that memo's work, not this spec's, but any later set-based move must keep its fix.
- Spec 162 itself is built but not archived (READ, roadmap.md:106); archiving 102 as overtaken by it reads best in the same R7 landing.
