# Study: MariaDB batch updates go set-based, not one round trip per row

## Verdict

live-0.2. The gap is real at HEAD 0ed462f: on MariaDB a guarded overwrite batch runs `_guarded_by_aggregate`, one `executemany` that aiomysql sends as one `UPDATE` per row, and the unguarded absorb arm does the same; the roadmap places the fix as story D5 at gate 0.2, rising to gate b only if D3 makes MariaDB first tier (READ context/standards/roadmap.md:489). Slice A (research) is done in the 2026-08-25 memo; slice B (the design and build) is not started, and the spec's "MySQL family" framing is stale because community MySQL is no longer a supported dialect.

## Against the tree

- The write path's material-update ladder is `_update_materials` (READ src/vfs/storage/backends/database/writes.py:673). It picks the VALUES-join RETURNING arm when `supports_values_update` holds, else `_guarded_by_aggregate` when the dialect declares `supports_sane_multi_rowcount`, else the per-row floor, else `unsupported` (READ writes.py:722-755).
- `supports_values_update` requires `profile.values_join` and the live dialect's `update_returning` and `update_returning_multifrom` (READ src/vfs/storage/backends/database/dialects.py:861). The MARIADB profile leaves `values_join` at its default `False` (READ dialects.py:436, dialects.py:597-625; only Postgres and SQL Server set it, dialects.py:536 and :576).
- The SQLAlchemy 2.0.52 aiomysql dialect with `is_mariadb` reports `supports_sane_multi_rowcount=True`, `update_returning=False`, `update_returning_multifrom=False`, `_found_rows_client_flag()=2` (EXECUTED: a `uv run python` probe). So MariaDB takes `_guarded_by_aggregate`.
- `_guarded_by_aggregate` runs `session.execute(_guarded_stmt(...), params)` with a list of params under `begin_nested()` (READ writes.py:902-911). The memo re-confirmed at the source that aiomysql's `executemany` packs only INSERT/REPLACE and loops `execute()` per row for an UPDATE (READ context/research/2026-08-25-mysql-family-batch-update-shapes.md:9). A 10,000-row guarded overwrite is therefore 10,000 round trips inside one REPEATABLE READ transaction (INFERRED from the two READ facts).
- The unguarded absorb arm on a non-VALUES engine is also an `executemany` of a parametrized `UPDATE`, followed by a chunked read-back select (READ writes.py:770-799). Same per-row cost on MariaDB (INFERRED).
- The problem statement is true at HEAD for MariaDB. Nothing under context/specifications/archive/ landed a MariaDB set-based guarded update; the archive hits on "080" are references, not landings (EXECUTED: grep over the archive; READ the ladder above).
- What changed under the spec since 2026-07-23:
  - MariaDB declares `guard_miss="redrive"` (READ dialects.py:601-604). An aggregate miss on MariaDB now raises `StaleSnapshot` after the savepoint rollback; it never re-drives row by row for blame (READ writes.py:908-911). The whole method redrives and, when exhausted, returns a retryable `conflict` (READ src/vfs/storage/backends/database/backend.py:1501-1506). The spec's "exact per-row blame on conflict" does not describe MariaDB today.
  - Guarded rows run in two groups, revive and non-revive, and every live-row arm adds a tombstone term that binds nothing (READ writes.py:726-729, writes.py:976-978).
  - The guard is `(entry_id, version = base, path = path-at-snapshot)` and sets `version = b_ver` (READ writes.py:963-973); the memo timed a `v_base + 1` form (READ the memo:39-42). Either is one bind per row; the tree's form carries `v_ver` as the VALUES arm does (READ writes.py:846-848).
  - A set-based MariaDB UPDATE already exists for a different table write: the index-flag stamp uses a row-constructor `IN` with CASE guards when `profile.tuple_in`, which MariaDB sets (READ src/vfs/storage/backends/database/indexing.py:906-915, dialects.py:613). That is in-tree precedent for set-based UPDATE on MariaDB, in the CASE-over-IN shape the memo measured as the runner-up (READ the memo:32, :49).
  - The torn-row regression pin for MariaDB exists and asserts the redrive converges to success (READ tests/storage/test_conformance.py:537-554).
  - The chunk math helper is `statement_budget`, pinned in tests/storage/database/test_coherence.py:1090 (READ); the file the spec names, `test_backends_database.py`, no longer exists (EXECUTED: listing of tests/storage/database/).
- A sibling per-row UPDATE outside this spec: the embedding landing `_land` is one `executemany` that the docstring records as a row at a time on the MySQL family, "a recorded suboptimality, never a cap" (READ src/vfs/storage/backends/database/embed.py:344-357). The spec does not cover it.

## Units proposed

One unit. The guarded rung and the absorb rung share one statement shape, one chunk helper and one test leg, and landing one without the other would leave half the overwrite path per-row (INFERRED).

- Slug: mariadb guarded and absorbing updates run one statement per chunk. - Content the converted spec needs: a third set-based rung in `_update_materials` between the VALUES arm and `_guarded_by_aggregate`; the UNION ALL derived-table multi-table `UPDATE t, (SELECT ... UNION ALL ...) v` joined on `(entry_id, path)` plus `version = v_base` for the guarded rows and without it for absorb; the tombstone terms kept; chunked by `statement_budget` off the compiled construction with `row_cap=membership_budget`; aggregate rowcount == chunk length under a savepoint; on a miss, rollback and the profile's `guard_miss` path (redrive on MariaDB); the absorb arm keeps its read-back select for versions and address proof, since MariaDB has no RETURNING on UPDATE (INFERRED from writes.py:780-799 and the probe).

## Open choices, each verified

1. Slice B "waits on review of the memo" (READ spec.md:3). The choice is whether the UNION ALL derived-table join is the shape. Lean: the memo's recommendation 1, the join guarded on `(entry_id, version, path)` (READ the memo:71). Verification: HOLDS. Precedent: the memo's executed measurements on both family members, 10k rows as one statement at 1.07-1.16 s against 4.05-4.72 s for the loop, identical rendered SQL from SQLAlchemy Core (READ the memo:28-45); the join carries the path guard at 3 binds a row where the CASE form needs a second CASE (READ the memo:49). Consistent with AGENTS.md's bounded-statement rule (READ AGENTS.md:58) and the per-batch multiplier: 10,000 round trips a batch at 100 batches a night is a million round trips the join removes (INFERRED from AGENTS.md's reference deployment table). The tree's CASE-over-IN flag stamp (READ indexing.py:906-915) is a working alternative, not a contradiction.
2. How the rung is selected. Lean: by capability, "the dialect renders a multi-table UPDATE and lacks `update_returning_multifrom`" (READ the memo:72). Verification: HOLDS-AMENDED. Precedent: `supports_values_update` combines a profile-declared join form (`values_join`, a decision SQLAlchemy takes no position on) with live dialect flags (READ dialects.py:189, :861), and AGENTS.md permits a profile field only for a decision SQLAlchemy does not model (READ AGENTS.md:60). Amended text: "A profile field declares that the engine accepts the derived-table multi-table UPDATE join; the rung runs where that field holds and `supports_values_update` does not, beside the live dialect's `supports_sane_multi_rowcount`; no dialect-name test."
3. How the matched-rows semantic is pinned. Spec: asserted at runtime or pinned by test (READ spec.md:22). Memo lean: a family-leg conformance row, not a runtime assert (READ the memo:73). Roadmap D5 acceptance, later: "`CLIENT_FOUND_ROWS` asserted at first touch" (READ roadmap.md:491). Verification: HOLDS-AMENDED. Precedent for a first-touch engine-fact check: the MariaDB profile reads `@@max_allowed_packet` at first touch (READ dialects.py:621-623; engine.py:212). Amended text: "First touch on a MariaDB engine asserts the connection counts matched rows (one matched-unchanged UPDATE reports 1, or the dialect's FOUND_ROWS flag is set) and refuses classified when it does not; the MariaDB conformance leg pins the same row." The roadmap's story text is the later source; it is not a Decided row in section 16 (INFERRED).
4. Attribution on mismatch. Spec acceptance: "exact per-row blame on conflict" with savepoint rollback and per-row re-drive (READ spec.md:21; memo:61). Verification: FAILS against the tree. MariaDB declares `guard_miss="redrive"` and an aggregate miss raises `StaleSnapshot` with no per-row pass (READ dialects.py:604, writes.py:908-910); the torn-row pin asserts the redrive (READ tests/storage/test_conformance.py:537-554). Alternative determined by the tree: "A chunk whose rowcount is short rolls its savepoint back and follows the profile's `guard_miss` mode exactly as `_guarded_by_aggregate` does: redrive on MariaDB, the per-row floor on a reprobe engine."
5. MariaDB's tier, which sets the gate. Lean: second tier (READ roadmap.md:1075). Verification: NEEDS-A-RULING. Needs a ruling: MariaDB first tier (D5 moves to gate b and this unit is built before 0.1.0), second tier (gate 0.2, per-row updates documented in D1's matrix), or dropped (the spec is dropped with it). Product choice; AGENTS.md lists MariaDB as a supported dialect with native cosine (READ AGENTS.md:62) but does not rank tiers.
6. The absorb arm takes the same join without the version predicate (READ the memo:71). Verification: HOLDS-AMENDED. Precedent: the VALUES arm's unguarded form drops only the version term and increments SQL-side (READ writes.py:842-848). Amended text: "The absorb arm runs the join without the version term, increments `version` SQL-side, and keeps the chunked read-back that learns versions and proves the stored path, because MariaDB has no UPDATE RETURNING."
7. Bind width for chunking: `3 + len(_CLOBBER_COLUMNS)` off the compiled construction, no new budget constant (READ the memo:51). Verification: HOLDS-AMENDED. Precedent: `_values_update` measures with `statement_budget` and `row_width=len(rows[0])` (READ writes.py:820-827). Amended text: "The width is measured from the compiled join by `statement_budget` with `row_cap=membership_budget`; the tree's tuple is id, base, new version, path and the clobber columns (READ writes.py:818), and no constant is declared."
