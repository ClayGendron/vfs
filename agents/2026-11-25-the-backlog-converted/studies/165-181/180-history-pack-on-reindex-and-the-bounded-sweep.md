# Study: History, pack on the index pass, the bounded sweep, the garbage gauge, and the history read

## Verdict

Partly live in 0.1.0 and partly 0.2, with none of it built. The history read (`versions(path)` and `read(path, version=N)`) is roadmap story K8, gate f, for 0.1.0; `pack`, the bounded `sweep` and the garbage gauge are 0.2 by the roadmap's "deliberately not in 0.1.0" table (READ, `context/standards/roadmap.md:195-202`, `:1044`). Recorded verdict: live-0.1.0, because the slice the roadmap places in 0.1.0 cannot be dropped and the 0.2 slices stay real gaps.

Nothing the spec describes is in the tree at the checkout read (EXECUTED: `git log --oneline -1` printed `09dad59`, not the `0ed462f` the task names; a grep of `src/vfs` for `packed`, `stored_bytes`, `plan_pack`, `PACK_HOT_ROWS`, `SupportsHistory`, `SupportsGarbage`, `def garbage`, `def versions` found no match outside unrelated vector and lexical code). The ground under it has moved three times: `reindex` was split into `rebuild` and `refresh`, `sweep` is to be renamed `destroy` with a narrowed caller set, and the resumption key rides `next_after`, typed as a path, which the spec's opaque keys may not ride (READ, the kernel rulings spec decisions 3, 5, 11; roadmap rows D6, D56, D57).

The phase lists are `_rebuild_phases` and `_refresh_phases` (READ, `maintenance.py:322`, `:558`); `backend.py` `_reindex_phases` is gone. `refresh` declares itself O(dirty): "a pass costs what was written since the last one, never the corpus" (READ, `maintenance.py:155-166`).

No integrity error kind exists yet (EXECUTED, grep of `src/vfs/results/kinds.py` for `integrity`: no match), so spec 175's kind, ruled as `vfs.unavailable.integrity` (READ, roadmap D8), is unbuilt. `next_after` exists only as an internal cursor field in `indexing.py:209`, not on `Result` (EXECUTED, grep), so K4 is unbuilt. `sweep` is in `DEVELOPER_OPS` at rung `read_write` (READ, `src/vfs/ops.py:97`, `:165`).

## Units proposed

1. `a file's replaced versions are listed newest first a page at a time with who wrote each` — "`versions(path)` lists a file's version rows newest first, a bounded page at a time, each row carrying its label, hash, size, source, time and attribution, under the read rung on the file's current path." Gate f. Depends on: K1 (ruled), K4 (spec 176, the paging grammar), D36 (creation attribution), the K3 conversion of spec 175 only for the shared kind vocabulary. Rewrite depth: amend (the roadmap widens the row to every attribution column, adds the batch form of K8 criterion 4, the `OpGroup` registration and the mint-on-create rule; the key's field is renamed by ruling). Source sections: Terms, §7.1, §7.3, §7.4, §9 rows for `Observation.actor`, `Op`, `SupportsHistory`; criteria 24-26, 28.

2. `any prior version of a file is read back whole and verified by its hash` — "`read(path, version=N)` returns body N, rebuilt from its chain and checked against its stored hash, and a mismatch is `vfs.unavailable.integrity`, never success." Gate f. Depends on: K3 (spec 175's conversion: the integrity kind and its repair rule), unit 1 for the shared history family and capability; not on K4. Rewrite depth: amend (kind name ruled; the constitution's `__meta__/versions/N` addressing must be reconciled, see Notes). Source sections: §7.2, §7.3, §8 first bullet; criteria 2, 27, 29, 30. It may land in the same pull request as unit 1 if K4 is late; it does not need the cursor.

3. `the full index pass packs cold history into snapshots and verified forward diffs` — "`rebuild` runs a `pack` phase that rewrites cold version rows into one snapshot and at most nine forward diffs each, lands a diff only when it is smaller and has reconstructed the body by hash, and never deletes a row or changes its attribution." Gate 0.2. Depends on: unit 2 (a read that walks a diff chain must exist before diffs are stored), the decision on which pass packs (below). Rewrite depth: amend (the phase moves from `reindex` to `rebuild` in `maintenance.py`; `PACK_HOT_ROWS = 1` is ruled; the scrub note goes to `lint`). Source sections: §1-§4, §8 second and fourth bullets, §9 schema rows, tasks 1-3; criteria 1-13.

4. `the trash retention pass reclaims in short slices, one transaction each` — "The retention arm of the irreversible verb runs in slices of at most one membership budget, each its own transaction under the serialization point, and its orphan reclaim walks `vfs_content`, `vfs_blobs` and `vfs_versions` in `entry_id` windows instead of a whole-table anti-join." Gate 0.2. Depends on: the deletes spec (not yet written; it renames `sweep` to `destroy`, sets who may call it per D57, and decides whether a live-path purge arm survives). Rewrite depth: rewrite (the verb's name, caller set and arm structure are the deletes spec's, so the shape this unit slices is not yet fixed). 5. `a retention pass resumes from where the last call stopped` — "The retention arm takes `limit=` and `after=`, processes at most `limit` units a call, and returns a resumption key that the next call continues from." Gate 0.2. Depends on: unit 4, K4 (spec 176), and a ruling on the key's field (the key is not a path). Rewrite depth: rewrite (the key cannot ride `next_after` by decision 5). Source sections: §5.1 `limit`/`after`, §5.4, task 6; criteria 14, 16, 20.

6. `a two-statement gauge reports how much garbage a mount holds` — "A storage-level maintenance read beside `rebuild()` counts tombstones, expired tombstones, version rows, unjudged rows and logical and stored version bytes in exactly two statements." Gate 0.2. Depends on: unit 3 (`packed`, `stored_bytes`), unit 4 (the retention cutoff it reports against). Rewrite depth: amend (`reindex()` becomes `rebuild()`; its overlap with `lint` must be stated). Source sections: §6, task 4; criteria 22-23.

## Open choices, each verified

1. §1, `PACK_HOT_ROWS = 1` (keep the newest version row whole) or `0`. Lean: 1. Verification: already-ruled. Decided 2026-11-15: "versions, keep newest whole"; `PACK_HOT_ROWS = 1` "is not a public name and can move after a measurement" (READ, kernel rulings spec decision 11, line 89; its table line 111).

2. §2, land pack on the Python diff law behind the 2 MiB gate with a Rust kernel as the follow-on, or build the Rust kernel first. Lean: Python first. Verification: fails. AGENTS.md's Tooling rule says performance work goes in the Rust crate and "pure Python is a test oracle, not a fallback"; the extension is required and there is one engine (READ, `AGENTS.md`, Tooling, "Performance work goes in our own Rust crate"). Pack's per-row diff is engine code under the rule's scope ("index build, ... chunking"), and it rides the rebuild's multiplier, the costliest in the reference deployment (about 11,000,000 index visits a day; READ, `AGENTS.md`, reference deployment, "Per index visit"). The precedent the rule names, spec 142 ("lexical kernels and numpy out") and spec 140 ("one engine, required extension and oracles"), both archived, moved hot paths to `crates/vfs-core` with the Python reference kept as a parity oracle in `tests/support/oracles/` (READ, `context/specifications/archive/` listing). Alternative the precedent determines: the diff and apply law as a `vfs-core` kernel, `compute_diff`/`apply_diff` moved to `tests/support/oracles/` as its parity oracle, `unidiff` removed from core dependencies; `PACK_MAX_BODY_BYTES` stays as an eligibility gate on the kernel's cost. Since pack is 0.2, this costs nothing in 0.1.0. The read path (unit 2) also applies diffs, so the same kernel serves both.

3. §5.1, keep the purge arm whole-batch, or slice it leaves first. Lean: whole-batch. Verification: needs-a-ruling, owned by the deletes spec. The deletes memo recommends that the irreversible act apply "only to what is already deleted, so destroying live data takes a delete first" (READ, `context/research/2026-11-15-deletes-tombstones-and-a-move-that-keeps-its-identity.md:71`), which would remove the purge arm at a live path altogether; D57 restricts the verb to the system actor (READ, `roadmap.md` D57). Until the deletes spec is written the arm this marker slices may not exist. Needs a ruling: in the deletes spec, whether `destroy` keeps an arm at any address other than the trash view; only if it does, whether that arm is one transaction or sliced.

4. §6, the gauge as a storage-level method beside the full pass, a routed developer-plane verb, or a `/.vfs` view row. Lean: storage-level method. Verification: holds-amended. Precedent: `rebuild()` and `refresh()` are storage-level maintenance methods of the optional `SupportsRebuild` protocol, outside the router (READ, `src/vfs/storage/protocol.py:478`, `:509-511`); roadmap D53 places the action log's read side on the developer plane for the system actor at 0.1.0 (READ, `roadmap.md` D53). Amended text: "a storage-level maintenance read beside `rebuild()` and `refresh()`, not an `Op`, with no `authority` parameter; the conversion states that `lint` (findings) and the gauge (counts) do not overlap: the gauge counts what the cleaners would reclaim, `lint` names what is broken." The `/.vfs` view arm has no landed precedent (spec 169 is unbuilt).

5. §7.1, the verb's name, `versions` or `history`. Lean: `versions`. Verification: already-ruled. Decided 2026-11-15: "The history verb is `versions`" (READ, kernel rulings spec decision 11, lines 87-89).

6. §7.3, a tombstoned file's history readable without a restore, or `not_found` with the trashed hint. Lean: `not_found` with `vfs.trashed`. Verification: holds. Precedent: `read` of a tombstoned file answers that way today, and the deletes memo records that a deleted file answers `not_found` to every read verb (READ, deletes memo line 17). The memo also records "the deleted body survives only as a version row that no verb reads" after a revive (READ, line 25), which this lean leaves as it is; an audit read of a deleted file's history is a later addition, not a reason to break the uniform answer.

7. §7.4, is `actor` visible at the read rung, and do `subjects`, `provenance`, `source_identity` and `grant_revision` join the row. Lean: `actor` only, at `read`. Verification: holds-amended. K8 criterion 1 names all six columns on the row at rung `read` (READ, `roadmap.md:198`). Precedent: `git log` shows author and committer to any reader of the history; the storage already keeps all six on every row (READ, `rows.py:546-557`). Amended text: "`versions` rows carry `actor`, `provenance`, `source_identity`, `subjects`, `grant_revision` and `created_at` at rung `read`, as K8 criterion 1 states." The roadmap criterion is not a "Decided" row, so the conversion records it as taken from the story; `Observation` gains each as a mirror field.

8. §7.4, bodies inline in a `versions` page, a `lines` field on `Observation`, a diff view between two versions. Lean: none of them in this spec. Verification: holds. Precedent: constitution Article 2 §3 bounds listings and reserves unbounded reads for a single known path (READ, `context/standards/constitution.md:88`), which a body-free listing plus one `read(version=)` per body follows; the roadmap puts the richer history queries in 0.2 (READ, `roadmap.md:1046`).

9. Kernel rulings decision 11: which index pass packs, since `reindex` was split into `rebuild` and `refresh` ("decided when spec 180 is converted"; READ, line 89). No lean in the spec. Verification of the choice "pack runs on `rebuild` only": holds. With `PACK_HOT_ROWS = 1` the work list visits one index entry per file with history every run (READ, spec §3.3 "Honest profile"); at 10,000,000 files and a refresh every 15 minutes that is up to about 960,000,000 index visits a day on `refresh` against about 10,000,000 once a day on `rebuild` (INFERRED, the reference deployment's partial-pass and rebuild rows times the spec's own profile). `refresh` declares itself O(dirty) (READ, `maintenance.py:155-166`), so pack on it breaks its contract; the reference deployment already makes the daily rebuild the compaction pass ("folding the delta posting tables into one"; READ, `AGENTS.md`, reference deployment, "Full rebuild"). Stated as: pack is the last phase of `_rebuild_phases`; `refresh` never packs.

10. The resumption keys of `versions` and the retention pass (spec §5.4, §7.1 say they ride 176's field). Verification: already-ruled against the spec. Decided 2026-11-15: the key is `next_after`, typed as a path; "Specs 175 and 180 say their scrub, sweep and versions keys ride this field as opaque strings; under this ruling they do not, and each names its own field when it is converted" (READ, kernel rulings spec decision 5, line 65). Needs a ruling at conversion: the name of each new field, or, for `versions`, whether the key is the reserved path `/.vfs/<file>/__meta__/versions/N` (constitution line 78), which is a path and could ride `next_after`.

11. D36, creation attribution: the v1 version row carries the creator, or a `created_by` column on the entry. Lean (roadmap): the version row. Verification: needs-a-ruling. A v1 row that keeps the creator alongside a copy of the live body doubles stored text at the reference deployment (about 40 GB of text at the median; READ, `AGENTS.md`, reference deployment, "File size"), while a body-less v1 row breaks the spec's invariant that every version row holds a body or a diff (spec §7.1 "the current body is not a row"; `Version.stored_payload` raises on a row with no payload, READ, `version.py:190-193`). Needs a ruling: a v1 attribution row with no body (and the read path taught that the live body is v1's), or a `created_by` column on `vfs_entries`.

## Notes for the conversion

- Split along the roadmap's line: units 1 and 2 are a 0.1.0 gate f spec (K8); units 3 to 6 are 0.2 and can be converted later or held as one 0.2 spec. The 0.2 sweep units cannot be written before the deletes spec, because the verb they slice is that spec's to reshape.

- K8 criterion 4 (`versions` on 10,000 paths in `ceil(10000 / membership_budget)` entry statements) adds a batch form the spec does not have; the spec's single-path two-statement page stays as the single-path case.

- With unit 3 on `rebuild`, its work list is a second per-file index scan on the most expensive multiplier; the spec's named direction, a pack-pending mark set by the mint's own transaction, keeps it O(new history) and is worth costing in the conversion against the about 1,050,000 file writes a day it would ride (READ, `AGENTS.md`, reference deployment, "Per file write").
