# Study: Write preconditions and the guarded append: `if_version`, `if_absent`, `append`, and `unchanged`

Labels: EXECUTED (a command ran in this checkout), READ (read at path:line), INFERRED (reasoning). The task names HEAD `0ed462f`; the checkout's HEAD is `44c3ee3`, a docs-only save point of this backlog review (EXECUTED, `git log --oneline -1`). ## Verdict

live-0.1.0. Nothing of the spec is built: `write` takes no `if_version`, `if_versions`, `if_absent` or `append`, `overwrite=` is still on every surface, an identical rewrite still reports `updated` and bumps the version, and twenty concurrent read-then-write appends still keep one line (EXECUTED, probe: rewrite `[('created', 1)] [('updated', 2)]`, `ok 20`, `lines 2`, each new keyword a `TypeError`).

The design stands in its main lines and the roadmap places it as story K2 at gate b, but three things moved under it: the ADRs it cites were retired, two rulings of 2026-11-15 contradict its `unchanged` rule's repair consequence (decision 9 and row D58), and the deletes memo of 2026-11-15 finds that a write at a deleted path reviving the old row is wrong, which every tombstone row of the spec rests on.

## Units proposed

The spec's own task list lands in five green steps (READ, `tasks.md`); the fifth (docs) folds into each unit. Four units, each gate b.

1. Slug: an identical body write reports unchanged and leaves the version alone. Title: A write or edit whose final body, kind, source and type equal the stored row's reports `unchanged`, mints nothing and writes nothing. Sources: spec §3, §7 (zero-statement row), §10 rows 1, criteria 3 to 9; tasks §1. Depends on: K1; must be reconciled with K3 (spec 175) over decision 9 and D58 before it is built (see Open choices 6). Depth: amend.
2. Slug: create exclusive write replaces overwrite and is judged at add. Title: `write(if_absent=True)` creates only where no live row stands, refuses `exists` carrying the occupant's version and hash, and `overwrite=` leaves `write`. Sources: spec §1.1 (the `overwrite` paragraph), §1.3 rows on `if_absent`, §2 step 2, §5, §6.6 (`ADDITIVE_WRITE`), §8 `exists` rows, criteria 16 to 18 and 25; tasks §2; roadmap K2 criterion 3. Depends on: K1 (decision 7, D7); the deletes spec for what a write at a deleted path does (see Open choices 8). Depth: amend.
3. Slug: a write that names the version it read is refused when the row moved on. Title: `write(if_version=N)` and `write(entries, if_versions={path: N})` refuse `vfs.conflict` with the current version and write nothing when any named row is not at its expected version. Sources: spec §1.1 to §1.4, §2 steps 4 and 6, §4, §7, §8 `conflict` and `not_found` rows, §9, criteria 2 and 10 to 15; tasks §3; roadmap K2 criteria 1 and 4. Depends on: unit 1 (the replay of one's own write answers `unchanged`); K1 (decision 8). Depth: amend.
4. Slug: append is one locked read modify write so concurrent appends keep every line. Title: `write(append=True)` reads and extends each target inside one transaction under a row lock, at rung `add`, so twenty concurrent appends keep twenty lines on every engine. Sources: spec §6 (all), §7 lock and memory rows, §10 append rows, criteria 1 and 19 to 24; tasks §4; roadmap K2 criterion 2. Depends on: units 1, 2 (`ADDITIVE_WRITE`) and 3 (`if_version` with append); the SQL Server read-never-waits fix (`context/specifications/active/2026-11-15-on-sql-server-a-read-never-waits-on-a-write.md`, not landed: no `READ_COMMITTED_SNAPSHOT` check under `src/vfs`, EXECUTED grep) for its lock costing on that engine. Depth: amend.

## Open choices, each verified

1. §9 `[NEEDS CLARIFICATION]`: accept a content-hash precondition `if_hash=` now, or wait. Lean: wait; the version is sufficient and a hash form composes as `stat` → compare → `write(if_version=)`. Verification: HOLDS. The constitution names only `if_version=` (READ, `context/standards/constitution.md:75`); the ruling names `if_version=` and `if_versions=` as the precondition's spelling (READ, `context/specifications/active/2026-11-15-the-kernels-public-names-and-argument-families-are-ruled.md:75-77`); K10's stamps carry the hash yet fill `if_version=` (READ, `roadmap.md:215`). The landscape memo recommended the peers' hash idiom on the served surface (READ, `context/research/2026-09-15-filesystem-over-database-landscape-and-vfs-differentiation.md:95`, `:194`); its "expected version or content hash" is met by the version (INFERRED). The decision text for the conversion: the kernel takes an expected version only; a hash precondition is an adapter's composition, additive later.
2. `overwrite=` leaves `write`, `if_absent=` replaces it. Verification: ALREADY-RULED, decision 7 of the 2026-11-15 rulings spec (READ, `:71-73`) and row D7 (READ, `roadmap.md:1079`).
3. The batch precondition is a mapping from path to version, `if_versions=`. Verification: ALREADY-RULED for the name (decision 8, READ, rulings spec `:75`); the path-keyed shape HOLDS, precedent: the router reorders and splits a batch per mount, so a parallel list would silently decode position (READ, `AGENTS.md`, "Code smells"); K10 and H2 already write `if_versions=` keyed by path (READ, `roadmap.md:218`, `:302`).
4. "Material" is `kind`, `source`, `content_hash`, `mime_type`. Verification: HOLDS. Precedent: the write never changes the owner (READ, `writes.py:1194-1205`), every other clobber column is a derivation or a stamp (READ, `writes.py:115-136`, `:1206-1224`), and the mint already treats an equal hash as no new version (READ, `versions.py:81`).
5. `unchanged` is judged before the version, so a replay of one's own `if_version` write succeeds at any version. Verification: HOLDS. Precedent: RFC 9110 §13.1.1 (If-Match) lets a server answer 2xx to a state-changing conditional request whose change "appears to have already been applied" (https://www.rfc-editor.org/rfc/rfc9110#section-13.1.1; INFERRED from the published standard, not fetched in this session); the OSTEP memo records the replayed-write refusal as the defect to remove (READ, `context/research/2026-10-24-what-ostep-teaches-vfs-eight-studies-and-what-changes-in-the-kernel-plan.md:66-68`).
6. The integrity consequence (§3, rebase note for 175): a same-body write of a body rotted under an intact hash reports `unchanged` and repairs nothing; spec 175's repair "cannot be write the same body again". Verification: FAILS. Decision 9 rules that "a `write` over the file succeeds and heals it" and that K3 does not land with a path on which a damaged file cannot be rewritten (READ, rulings spec `:81`); D58 says named callers fix a damaged file "by overwriting it" (READ, `roadmap.md:1130`). The correcting body has the stored hash, so the four-column rule swallows exactly that overwrite (INFERRED). The precedent fixes the outcome (a same-body overwrite of a damaged row writes the body) but not the mechanism. Needs a ruling: (a) `unchanged` trusts the stored hash and K3 marks a row damaged (by verify-on-read or scrub) so that a marked row is excluded from `unchanged`, at no cost to the write path but healing only rows already found; or (b) the `unchanged` test re-hashes the stored body before skipping, healing every rot at the cost of one body read per same-body write, which for a 10,000-file re-ingest is the whole batch's bodies read once (about 40 MB at the 4 KB median, INFERRED from the reference deployment).
7. `if_absent` over a live occupant refuses `exists` even when the occupant holds the caller's own body, and `exists` carries `version` and `content_hash`. Verification: HOLDS. Precedent: POSIX `open(O_CREAT|O_EXCL)` fails `EEXIST` whenever the name exists, whatever it holds; recognising one's own earlier create needs a request token, as NFSv3's exclusive-create verifier is (RFC 1813 §3.3.8), which here is spec 177's request key (READ, roadmap K5, `roadmap.md:170`). The data is not a leak: `exists` is answered only past the gate, and the `add` rung includes `read` (READ, `ops.py:117-121`).
8. A tombstone is absent to `if_absent`, and the write revives the old row reporting `updated`. Verification: split. That a tombstone counts as absent HOLDS: precedent the deletes memo's survey, where every system with an id and a unique path lets a deleted item give the path up (READ, `context/research/2026-11-15-deletes-tombstones-and-a-move-that-keeps-its-identity.md:35`), and POSIX, where an unlinked name does not block `O_EXCL`. That the write revives the deleted row NEEDS-A-RULING: the memo finds that revive makes the delete irreversible and leaves the first owner holding the file (READ, memo `:13`, `:25-26`), and K2's criterion 3 says the revive "reports `created`" (READ, `roadmap.md:147`) where the tree and the spec report `updated` (READ, `staging.py:326`). Needs a ruling, owned by the deletes spec: (a) a write at a deleted path revives the row and reports `updated`, as today; (b) it creates a new file beside the deleted one (the memo's generation key) and reports `created`, the delete staying undoable. Units 2 and 4 take whichever is ruled; until then each states "as a plain write at a deleted path does".
9. An `if_absent` write over an occupied target is judged at `add`, so an `add` holder hears `exists`, not `permission_denied`. Verification: HOLDS. Precedent: the ladder's `create="add"` for a fresh name (READ, `ops.py:150`) and the gate running before the plan, so a `list`-only caller is refused by the gate (READ, `rights.py:734`; `context/specifications/archive/2026-11-12-the-scan-tier-reveals-nothing-about-rows-a-caller-cannot-read.md`).
10. `append` is judged at rung `add` (`ADDITIVE_WRITE = Needs("add", create="add")`), a tombstoned target still judged as a restore. Verification: HOLDS. Precedent: Plan 9's `DMAPPEND` and NFSv4's `APPEND_DATA` beside `ADD_FILE`, recorded in the ladder study (READ, `context/research/studies/2026-10-14-permission-ladder/03-traversal-and-verbs-on-the-ladder.md:159`; `00-brief.md:9`); roadmap K2 criterion 2 places append at `add` (READ, `roadmap.md:146`).
11. The append runs in storage under a row lock at READ COMMITTED (option b), not a front loop or SQL concatenation. Verification: HOLDS-AMENDED. Precedent: the edge guard re-read locks entry rows with `locked_lookup` (READ, `edges.py:316-327`) and the topology verbs run at `topology_isolation` (READ, `dialects.py:707-718`); `edit` already keeps all twenty lines in one transaction (READ, OSTEP memo `:41`). The amendment the per-lock rule requires (READ, `AGENTS.md`, "The reference deployment", per lock): the lock read is the transaction's first statement, so the row locks are held through the batch's snapshot, composition and measurement, not for a commit only. The converted spec states that only callers mutating the same target rows wait (writes, edits, appends, deletes and moves of those paths), that reads never wait on Postgres and Oracle and on SQL Server only once the read-never-waits spec lands, and adds the counted test that on every server engine a read, a search and an edit of another file return while an append batch holds its locks, by the system actor, a named caller and anonymous.
12. An append's arbitration loss and guard miss redrive (`StaleSnapshot`) rather than refuse. Verification: HOLDS. Precedent: the whole-method redrive the write path already uses for a snapshot it cannot trust (READ, `writes.py:575`, `:657`, `:955`).
13. `conflict` is `retryable=False` where the caller stated a precondition and `True` where it did not. Verification: HOLDS. Precedent: `_conflict`'s own reason, an identical retry of a plain write adjudicates afresh (READ, `writes.py:993-996`), and the kind's retry class `refresh` (READ, `kinds.py:84`, `:231`).
14. `if_version` on no live row answers `not_found`, not `conflict`. Verification: HOLDS. Precedent: the reprobe already splits "row gone" (`not_found`) from "row moved on" (`conflict`) (READ, `writes.py:946-966`). HTTP answers 412 there (RFC 9110 §13.1.1); vfs's own split is the stronger precedent for a caller's next step (INFERRED).
15. An append joins text and bytes under the keep-the-source rule: a text row stays text when the joined bytes are UTF-8 without NUL, else becomes bytes. Verification: HOLDS. The cited ADR 085 pin 12 is retired and no spec carries it (EXECUTED, grep of spec 152); precedent: `Entry` refuses NUL in text (READ, `entry.py:144`, `:350`), so a NUL or non-UTF-8 composition cannot be stored as text.
16. Mixing `append` or `if_absent` with plain rows in one call is out of scope. Verification: HOLDS, precedent none found; rests on one call being one transaction per mount (READ, spec §1.2; constitution's atomic unit).
17. An append batch holds every pre-image and composed body in memory, with no cap and a named direction (byte-paging the body join). Verification: HOLDS. Precedent: `edit` holds the same (READ, `writes.py:300`), the mint already pages by bytes (READ, spec §7; `versions.py`), and AGENTS.md forbids converting the profile into a cap (READ, "Production posture").
18. `idempotentHint` for the `write` tool (§10). Verification: ALREADY-RULED, decision 10: the hint is withheld once `append=` lands (READ, rulings spec `:83-85`).
