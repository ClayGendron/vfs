## D20. The default local embedder is model2vec potion, and fastembed is a documented LangChain route

- Lean: amend the embedder decision to model2vec potion; keep fastembed as a documented LangChain route.
- Verification: settled-by-landed-work.
- Decision text: "The local embedder behind `vfs-py[embed-local]` is `Model2VecEmbeddingProvider` with `minishlab/potion-base-8M` (256-d); the hash embedder stays the zero-dependency conformance default; fastembed is not a vfs dependency, and a host that wants it wraps it through `LangChainEmbeddingProvider`."

At the reference deployment's 100,000,000 chunks, fastembed's 3.9 chunks/s is about 300 days of CPU for the corpus, potion's 5,212 chunks/s about 5.3 hours (INFERRED from the memo's rates).
- Landed: `src/vfs/embedding/model2vec.py:25` (`DEFAULT_MODEL = "minishlab/potion-base-8M"`), `pyproject.toml:53` (`embed-local = ["model2vec>=0.5"]`), `src/vfs/embedding/__init__.py:9-13` (hash, LangChain, model2vec, OpenAI exported) (READ); archived `context/specifications/archive/134-embedding-provider-and-reindex-embed-step/spec.md:20,66` (READ: the providers, and the measured 3,301 chunks/s of potion on the build).
- Precedent: `context/research/2026-08-26-glean-embedding-seam.md:8,115` and `context/research/studies/2026-08-26-glean/embedding-seam.md:102,115-119` (READ: fastembed 141 MB and 3.9 chunks/s, rejected; model2vec 31 MB, recommended as the optional extra).

## D21. Render at write (spec 159) is not in 0.1.0

- Lean: no, unless the first served pilot hits it.
- Verification: holds-amended.
- Decision text: "Spec 159 is out of 0.1.0. A binary written through `write` stays `render_status = 'pending'` until the next `refresh()` or `rebuild()`, which renders it; a host that needs a binary searchable at once calls `refresh()` after the upload. Spec 159 stays in the backlog for 0.2; its premise is restated over `refresh()` and its names over the ruled vocabulary (`rebuild` for `reindex`, `search` for `glean`) before it is converted."
- Reason: the gap spec 159 was cut to close has narrowed since it was written. Its intent says the host must run a whole-corpus `reindex()` after every upload (READ, `context/specifications/active/159-render-at-write/spec.md:11`; the source gap is `context/research/2026-10-08-smartowl-workspace-integration-issues.md:172-178`). Since 2026-11-13 the incremental pass `refresh()` renders the bytes rows a write changed, at O(dirty) cost (READ, `src/vfs/storage/backends/database/maintenance.py:152-166`; `src/vfs/storage/backends/database/render.py:176`). So an unrendered binary now waits only until the next partial pass, which the reference deployment runs every 15 minutes with a 1-minute floor (READ, `AGENTS.md`, the "Partial index pass" row).
- Amendment over the lean: the amended text points the 0.1.0 answer at `refresh()` and requires 159's premise to be restated. Spec 159 as written describes a world that no longer exists (INFERRED).
- Cost at the reference deployment: inline rendering sits on the per-file-write multiplier, about 1,050,000 writes a day. Each binary write under the budget would carry up to `INLINE_RENDER_SECONDS` = 5 s of render latency outside the transaction (READ, `159-render-at-write/spec.md:17`). That is affordable for locks, but it costs latency on the agent path. The binary share of writes is unmeasured (INFERRED).
- Precedent: the refresh verb (archived `context/specifications/archive/2026-10-31-refresh-the-incremental-index-verb.md:78,106`, READ); SharePoint continuous crawl and Glean connector cadences of minutes to an hour, recorded as the source of the partial-pass row (READ, `AGENTS.md`, the reference deployment table).
- A caveat that stays true: a `refresh()` called while another pass holds the index lease still refuses `conflict` (READ, `maintenance.py:163-166`). An upload endpoint retries or defers on that refusal.
- Specs affected: 159 (deferred, premise to restate), 152 (its slice C row in roadmap E8 is unchanged).

## D22. 0.1.0 ships without a generic wasm host, and `awk` refuses with a hint

- Lean: ship without; refuse with a hint; ask `wasi_python` in parallel (the same question as D49's spike).
- Verification: holds.
- Decision text: "0.1.0 builds no generic WebAssembly host. `awk` and `jq` are `vfs.unrecognized`, exit 127, each with spec 168's hint (`sed -n 'A,Bp'` or `cut -d D -f N` for `awk`; the installed `jaq` for `jq`). Spec 169b and the first-programs section of spec 169 (uutils, jaq, a WASI awk) are 0.2, unless D49's spike moves the host half forward. Adding `awk` later is an addition under the additive freeze."
- Reason: the refusal is already ruled. "Decided 2026-10-15: `awk` is a real awk, a wasm program ... There is no Rust awk subset. Until 169 lands, `awk` refuses with a hint" (READ, `context/specifications/active/168-text-program-kernels/spec.md:8-11,61-62`). The remaining question is only when the host lands. That host is XL (READ, `roadmap.md:745-747`), and it duplicates a preview1 host that wasi_python's runner already owns (READ, `context/research/2026-10-23-wasi-python-0-1-0-over-vfs-the-mount-and-the-tool-door.md:21,113`).
- Cost at the reference deployment: `awk` is 371 of the measured calls in spec 168's census (READ, `168-text-program-kernels/spec.md:61`). The roadmap's figure is 331 (READ, `roadmap.md:592`), and the census is the cited source. That is about 2.7% of 13,746 calls. At 150,000 verb calls a day, roughly 4,000 lines a day would meet the refusal, if agent traffic matches the corpus (INFERRED). Each refusal names a rewrite, and the hint covers the dominant forms (`awk -F:` 25, field printing) through `cut` and `sed` (READ, `context/research/studies/2026-10-15-agent-shell/02-program-catalog.md:65`).
- Precedent: spec 168's ruled decisions 2 and 3 (above); nushell's refused-feature error naming its replacement, adopted by the shell memo (READ, `context/research/2026-10-15-the-agent-shell-prior-art-and-experiments.md:62`).
- Specs affected: 168 (the 168a refusals stand), 169 (169b and the first programs to 0.2, or the host half forward by D49), 167 (the never table keeps `awk` and `jq` routed to their hints).

## D34. The 0.1.0 program table is 167, 168a and 168b; 168c, `awk` and `jq` are out; `grant`, `revoke` and `grants` gain shell spellings

- Lean: as stated; add the three spellings in F4.
- Verification: holds.
- Decision text: "The 0.1.0 program table is spec 167's programs and verb builtins, spec 168a's kernels (`head tail wc cut nl sed sort uniq tr tee`) and 168b's runner builtins (`xargs`, `find -exec`, `find -delete`). Spec 168c (`diff`, `cmp`) is 0.1.x; `awk` and `jq` refuse per D22. `grant`, `revoke` and `grants` are shell words spelled as their op names, with forms drawn from the verbs' parameters, and gated as the Python verbs are."
- Reason: the table follows measured demand. 168c serves 29 `diff` uses and 1 `cmp` use (READ, `168-text-program-kernels/spec.md:63-64`), about 0.2% of calls. The shell memo's growth rule admits a construct when a measured corpus shows it above about 1% (READ, `2026-10-15-the-agent-shell-prior-art-and-experiments.md:58`).
- The three grant verbs are agent-plane ops: they are in `GRANT_OPS` and absent from `DEVELOPER_OPS` (READ, `src/vfs/ops.py:88,96-100`). So they already reach the MCP surface. A shell spelling with the op's own name follows the ruling that "tool names and shell words are op names either way" (READ, `context/specifications/active/2026-11-15-the-kernels-public-names-and-argument-families-are-ruled.md:61`). Unix offers no convention to follow, because vfs rejects mode bits (READ, `context/standards/constitution.md:100`).
- Today spec 167 lists them as `unrecognized`, with a hint naming the verb tool (READ, `context/specifications/active/167-the-shell-pipeline-core/spec.md:85`). That line changes.
- Precedent: the measured corpus and growth rule (above); the names ruling (above); `ops.py`'s plane split (above).
- Consequential edits: spec 168's criterion 15 ("168a and 168c together by at least one point", READ, `168-text-program-kernels/spec.md:197`) is restated without 168c. Roadmap F6 already allows 168a to ship as Python transforms with the Rust port in 0.1.x (READ, `roadmap.md:663`).
- Specs affected: 167 (slice D never table and forms), 168 (168c deferred, criterion 15).

## D47. `cmd &` and `wait` are admitted as concurrency bounded by the call; job control past the call is refused

- Lean: admit the bounded form; refuse `jobs`, `fg`, `bg`, `disown`, `nohup`; the durable run and `/.vfs/jobs` are the background model.
- Verification: holds-amended.
- Decision text: "`cmd &` starts an asynchronous job inside the line, and `wait` (bare, `wait $!`, `wait %n`) joins jobs. The call never returns before every job has settled: the line ends with an implicit `wait`, and each job's status is in the status list. Jobs are numbered by their position in the parse, never by their completion order. Each job's stdout and stderr are emitted whole, in job order, at its join. Every job's verb calls count against the line's `VERB_CALL_BUDGET` and `WALL_TIME_BUDGET`, and at most `JOB_BUDGET` jobs run at once (a declared constant; further jobs wait to start). `jobs`, `fg`, `bg`, `disown`, `nohup` and `coproc` are `vfs.unsupported.construct` with the hint that the call returns when every job has run. The implicit final wait is a numbered deviation from POSIX, recorded under the constitution's Article 3."
- Reason: the 2026-10-15 refusal rested on one objection: the peers fake `&`, which lies to the model. just-bash parses `&` and never runs it; bashkit polls it once (READ, `context/research/studies/2026-10-15-agent-shell/01-shell-grammar.md:81,83,244`). The bounded form really runs the jobs at the same time and reports what happened, so the objection does not apply. "Decided 2026-10-28: full bash ... with everything that could be useful to vfs in it" (READ, `roadmap.md:51,592`) favours admitting it.
- Amendments over the lean:
  - Article 3 requires the deviation to be written down (READ, `constitution.md:104`). POSIX's shell "shall not wait" for an asynchronous list and leaves a job running after the script ends (READ, as quoted in `01-shell-grammar.md:42`).
  - Job numbering and output order follow the determinism law: a recorded key never carries a task id or a queue position (READ, `roadmap.md:629`). A resumed line must also reproduce an uninterrupted run byte for byte (READ, `roadmap.md:651`). Interleaved output would break both (INFERRED).
  - `JOB_BUDGET` bounds the concurrent statements one line puts on the shared database pool, which the per-lock rule of the reference deployment costs against about 20 calls a second at peak (READ, `AGENTS.md`, "Per lock"; INFERRED that an unbounded `for f in *; do cmd & done` would otherwise open one job per match).
- Precedent: the router settles every sibling before a call returns (READ, `src/vfs/base.py:3035-3050`); bounded concurrency by semaphore in the embed step (READ, `src/vfs/storage/backends/database/maintenance.py:762`); Oils YSH's `fork`/`forkwait` (READ, `01-shell-grammar.md:67`); lifo's real job table as the unbounded alternative (READ, `01-shell-grammar.md:87`). `&` is 0.2% of measured calls (READ, `01-shell-grammar.md:42`).
- Specs affected: 167 (§ scope line 186 moves `&` in; the refusal table), the new F2 and F7 slices of 167, and the durable-run spec (H4) for job numbering.

## D48. `source` and `.` of a literal path are admitted, read through the gate and parsed before the line runs; `eval` is refused

- Lean: yes to both.
- Verification: holds-amended.
- Decision text: "`source` and `.` take a literal path. The file is read through the gate as one counted `read`, under the caller's authority, and parsed before the line runs. Its programs, verbs and literal paths join the pre-execution summary. A sourced file's own literal `source` is resolved the same way, recursively, and the combined text counts against `INPUT_BYTE_BUDGET`, `TOKEN_BUDGET` and `DEPTH_BUDGET`. A computed path is `vfs.unsupported.construct` naming the expansion. So is a relative path after a `cd` or `pushd` earlier in the same line, whose address depends on a run-time value. `eval` is `vfs.unsupported.construct` in every form. Both are numbered deviations under Article 3."
- Reason: the static parse is the invariant the full-language ruling kept (READ, `roadmap.md:590,609`), and the pre-execution summary depends on it. `source` of a literal path keeps the parse static, because the file is known before anything runs. `eval` turns run-time data into code, and no static summary can name what that code does.
- Amendments over the lean:
  - Recursion and the parser budgets are made explicit. The lean is silent on a sourced file that sources another file, and the F2 budgets exist to bound exactly that (READ, `roadmap.md:612`; `167-the-shell-pipeline-core/spec.md:60`).
  - The `cd` rule is added. Without it, a relative path resolved at parse time would read a different file than bash would read (INFERRED).
  - The deviation records follow from `constitution.md:104` (READ).
- Precedent: Oils OSH parses statically so that "you get syntax errors up front" (READ, `01-shell-grammar.md:67`); codex refuses to let a string-evaluating prefix (`bash -c`, `python3 -c`, `node -e`) be blanket-approved, because its static classifier cannot see inside the string (READ, `02-program-catalog.md:89`); the first grammar already refused `eval` and re-scanning (READ, `2026-10-15-the-agent-shell-prior-art-and-experiments.md:52,54`). `source` is among the shell builtins measured in the corpus (READ, `02-program-catalog.md:57`).
- Specs affected: 167 (the never class at line 85 and the ADR 082 pin 10 note at line 219, which list `source` and `.` as `unrecognized`, both change), the F2 and F7 slices of 167, and the durable-run spec (the sourced `read` is an expansion read under D41).

## D49. The QuickJS-NG guest asks `wasi_python` to host a generic `wasm32-wasip1` module, after a spike, and T6's host is the fallback

- Lean: ask `wasi_python`; the spike first; T6's host only if the answer is no.
- Verification: holds.
- Decision text: "Before T5b is sized, a one-afternoon spike runs a QuickJS-NG `wasm32-wasip1` module under wasi_python's runner, over its mount and tool protocols, through public APIs only. If it runs, or wasi_python accepts the proposal, the JavaScript guest is a second thin adapter over that runner beside the Python one. If not, the host half of spec 169b moves into 0.1.0 for QuickJS alone, and its program-install half stays in 0.2."
- Reason: wasi_python's runner already implements the contract spec 169b would build: whole-file staging, refusals recorded, budgets, several guests at once (READ, `2026-10-23-wasi-python-0-1-0-over-vfs-the-mount-and-the-tool-door.md:21,25-26`). wasi_python's own decision 13 is "converge on our runner, but do not edit vfs" (READ, same memo:21). A second host would be the duplicate the memo warns against (READ, same memo:113).

- Cost at the reference deployment: a guest run is a per-verb-call event and its file calls go through the gate either way, so the choice moves no database cost. The difference is build size: the M adapter against the XL host on the 0.1.0 path (READ, `roadmap.md:735,745`) (INFERRED).
- Precedent: the Python guest as a thin adapter over wasi_python's runner, executed through public APIs (READ, same memo:11,113); spec 172's lean that QuickJS-NG be built "by the same yearly workflow" (READ, `context/specifications/active/172-the-wasi-python-runtime/spec.md:52`); spec 172's contract model, in which vfs states what it needs and the other project owns its code (READ, `172-the-wasi-python-runtime/spec.md:16`). The guests are ruled into 0.1.0 at gate b. "Decided 2026-10-28: Python and JavaScript both in 0.1.0" (READ, `roadmap.md:1095`).
- Specs affected: 172 (§6 QuickJS, and its dependency on 169b, which the memo already narrows), 169 (169b's host half, conditionally).
