# Every classified engine failure and every exhausted-retry conflict carries the driver's own error code in `data["vfs.engine_error"]`, read from driver attributes and never from message text

A draft, written on 2026-11-25 against `dev` at `27f3d24d`. It is not reviewed, and nothing is built. It serves roadmap story K7 at gate f, acceptance criterion 3 ([the roadmap](../../context/standards/roadmap.md), line 200). It is converted from [spec 179](../../context/specifications/archive/179-the-storage-seam-as-the-kernel/spec.md), section 3.3, with task 4 of [its task list](../../context/specifications/archive/179-the-storage-seam-as-the-kernel/tasks.md) and its criterion 9, read through [the study of that source](../2026-11-25-the-backlog-converted/studies/165-181/179-the-storage-seam-as-the-kernel.md) and [the reassessment against dev](../2026-11-25-the-backlog-converted/reassessment/seam.md), section 179-5. It rests on the classifier, the retry loop and the driver-code readers as they stand on `dev`, and it waits for no unbuilt work.

## The outcome wanted

An ETL pipeline or an agent host that gets a failed call from a database mount can route on the engine's own code without parsing a message. A `vfs.unavailable` from SQLite carries `data["vfs.engine_error"] == {"dialect": "sqlite", "code": 1, "name": "SQLITE_ERROR"}`. A `vfs.conflict` that outlived its retries on Postgres carries `{"dialect": "postgresql", "sqlstate": "40P01"}`. A failure with no code from the driver, such as a pool timeout or an `OSError`, carries no field, and a conflict that a vfs guard raised by itself carries none either. The field rides in-process on `ResultError.data` and on the wire in `Result.to_payload()`. The kinds, the retry flags and the messages stay as they are today.

## Terms

- **A classified engine failure**: a `ResultError` that vfs builds from a driver exception it caught, whatever its kind and severity.
- **An exhausted-retry conflict**: the retryable `vfs.conflict` answered when `with_retry` gave up.
- **An in-band stale snapshot**: a `StaleSnapshot` that a vfs guard raised itself, with no driver error behind it.
- **The retryable link**: the first exception on a failure's context chain, within `_UNWIND_DEPTH` links, that the profile judges retryable alone; it is the error that made the attempt retryable.

## What the code does today

- `classify_failure` has four branches, `backend_unavailable`, `unsupported`, `internal` and `unavailable`, and each puts the driver's text in `detail` and nothing in `data` (`engine.py:388-399`).
- Three sites build an exhausted-retry conflict by hand, each with `detail=f"{op} kept losing to concurrent changes: {exc.context}"` and no `data`: `_execute` (`src/vfs/storage/backends/database/backend.py:1357-1359`), `_mutate` (`backend.py:1501-1504`) and `ensure_ready` (`engine.py:296-298`).
- Three more sites classify a driver exception without the classifier: the privilege refusal of `install_extensions` (`engine.py:329-333`), the advisory of a failed planner-statistics detection (`engine.py:437-446`) and the advisory of a failed background statistics pass (`engine.py:900-911`).
- On Python 3.13 the real SQLite driver sets `sqlite_errorcode` and `sqlite_errorname` on its errors: 5 and `SQLITE_BUSY` for a lock collision, 8 and `SQLITE_READONLY`, 1 and `SQLITE_ERROR` for a missing table or a syntax error, 18 and `SQLITE_TOOBIG`; a `ProgrammingError` raised by the module itself for a bind count carries neither (EXECUTED, two probes in the session scratchpad). A `read` whose statement is rewritten to a missing table reaches `classify_failure` with that `SQLITE_ERROR` object and answers `vfs.unavailable` with `data=None` (EXECUTED).
- SQLAlchemy's asyncpg adapter translates a driver error to its own class and copies the server's code onto `sqlstate` and `pgcode` (`sqlalchemy/dialects/postgresql/asyncpg.py:781-799`, SQLAlchemy 2.0.52, READ). asyncpg's `SerializationError` and `DeadlockDetectedError` carry `40001` and `40P01` (EXECUTED).
- The `ErrorKind` docstring says "producer keys are unprefixed" (`kinds.py:58-60`), while the storage's trash keys, which a producer writes, carry the `vfs.` prefix (`kinds.py:21-23`, `src/vfs/storage/backends/database/descent.py:117`).
- The text renderer prints `data["vfs.target"]` and `data["vfs.rollup"]` and no other key (`src/vfs/results/render.py:115`, `:122`).
- `engine.py` holds 1,008 lines and `backend.py` 1,509, each exactly its entry in `MODULE_LINE_BASELINE` (`tests/lint/allowlist.py:27-34`); a module that grows fails the lint. `dialects.py` holds 931, under the ceiling of 1,000.

## The problem

The engine's own code survives only inside the message text, and the envelope forbids any consumer to parse `message` (`envelope.py:97-99`). A pipeline that wants to tell a full disk from a deadlock, or a host that wants to back off on SQLite's busy code and page someone on Postgres's I/O class, has no field to read. At the reference deployment's 150,000 verb calls and 100 nightly batches a day, the failures that do occur arrive at an ETL job or an agent host that cannot route them without a regular expression over prose. K7's criterion 3 asks for the code as a field on every backend failure.

## Decisions

1. **The field is `data["vfs.engine_error"]`, a mapping that always holds `dialect` and holds each of `sqlstate`, `code` and `name` only when the driver carries it.** `dialect` is the profile's name, the dialect's own name on the generic floor (`dialects.py`, `profile_for`); `sqlstate` is a five-character string; `code` is an integer; `name` is a string. The values are JSON-native, so `to_payload` and `from_payload` keep them as they are. Basis: the source, section 3.3; the `ErrorKind` docstring's rule that absence means "not known" (`kinds.py:51-52`). The departure from K7's member `driver` is choice 1.
2. **On the two served engines the members are read from these attributes, and from nothing else.** SQLite through aiosqlite: `code` from `sqlite_errorcode`, which is SQLite's extended code, and `name` from `sqlite_errorname`. Postgres through asyncpg, or psycopg where an application chooses it: `sqlstate` from `sqlstate`, else `pgcode`. A driver on the generic floor gets whichever of these four attributes it sets. Basis: the attributes the classifiers already read (`dialects.py:785`, `:792`, `:882`) and the probe under What the code does today; the reassessment, which finds MariaDB's, SQL Server's and Oracle's readers gone with their engines.
3. **The reader never reads `str(exc)`, `exc.args` or any message, and a member whose attribute has the wrong type is left out.** `sqlstate` is kept only as a `str` of exactly `_SQLSTATE_LENGTH` (5) characters, `code` only as an `int` that is not a `bool`, `name` only as a `str`. When none of the three is kept, the reader answers `None` and no field is written. Basis: the unit's title and K7's "never from the message"; the classifiers' `args[0]` arm is left to them, which is choice 2.
4. **The record is `EngineError(NamedTuple)` with `dialect: str`, `sqlstate: str | None`, `code: int | None` and `name: str | None`, and `as_data()` returns the present members as a `dict[str, str | int]`; it is read by `engine_error(dialect: str, exc: BaseException) -> EngineError | None`, which reads `driver_origin(exc)`.** The type and the function carry the key's own noun, because how-we-name gives one concept one noun in public and private code (`documentation/maintainers/how-we-name.md`, "Nouns"); the source's `EngineCode` and `engine_code` would be a second noun. The docstring says the record is data and is never raised. Basis: the source, section 3.3, renamed.
5. **A new module, `src/vfs/storage/backends/database/failures.py`, holds `EngineError`, `engine_error` and `classify(profile: DialectProfile, dialect: Dialect, exc: BaseException, *, context: str) -> ResultError`, the classifier's whole body; `EngineHost.classify_failure` keeps its name and signature and returns `classify(self.profile, self._dialect, exc, context=context)`.** Every caller, in the tree and on the open branches, keeps calling `classify_failure`. `engine.py` stands at its baseline and must not grow, and the field adds an argument to every answer; moving the body takes about twenty lines out. `failures.py` imports `dialects.py` and `vfs.results` and nothing above them. Basis: the size baseline, `tests/lint/allowlist.py:9-11`; precedent `attempts.py`, a module of its own for one concern of the engine host, and 177-2's decision 24, `commits.py`.
6. **`dialects.py` gains `sqlstate_attribute(origin: object) -> str | None`, the named-attribute half of `_sqlstate_of`, and `_sqlstate_of` calls it before its `args` arm.** The field and the classifiers then read the same attributes in one place, and only the classifiers read `args`. Basis: the duplication rule of AGENTS.md, "Code smells".
7. **`classify` writes the field on every branch: `backend_unavailable`, `unsupported`, `internal` and `unavailable`.** Each branch keeps its kind, its retry flag and its detail. Basis: the source, section 3.3, "The kinds do not change"; K7 criterion 3, "`classify_failure` sets `data[...]`".
8. **`classify` gains a branch for `StaleSnapshot`: `classified(ErrorKind.conflict, retryable=True, detail=f"{context} kept losing to concurrent changes: {exc.context}", data=...)`, whose field is read from the retryable link of `exc.__cause__`.** The detail is the text the three sites build today, so no message changes. An in-band stale snapshot has no `__cause__` and carries no field. The runners' arms become one each: `_execute` catches `(StaleSnapshot, SQLAlchemyError, OSError)` and `_mutate` the same, each returning `Result(ops=(op,), errors=[self._host.classify_failure(exc, context=op)])`. `ensure_ready`'s arm becomes `return self.classify_failure(exc, context="first touch")`, which composes the lower-case detail pinned at `tests/storage/database/test_coherence.py:1084`. A branch that 177-2 adds for `CommitInDoubt` reads its field from `exc.__cause__` the same way. Basis: 177-2's decision 10, quoted under Builds on, built here for the `StaleSnapshot` half.
9. **Each other classified engine failure carries the field as well: the privilege refusal of `install_extensions`, the two planner-statistics advisories, and, if the kernel store has landed when this is built, its privilege refusal and its exhausted-retry answer.** Each keeps its kind, severity, retry flag and detail and gains `data={ENGINE_ERROR_KEY: ...}` from the exception it already holds. A refusal vfs builds without a driver exception, such as the inconsistent-provisioning refusal (`engine.py:650-657`) or a missing vector function (`engine.py:620-621`), gains nothing. The build greps `src/vfs` for `classified(` beside a caught `DBAPIError`, `SQLAlchemyError` or `StaleSnapshot` and covers each hit. Basis: the unit's title, "every classified engine failure"; the source named only the classifier and the conflict, and this widens it to the rest of what the title covers.
10. **The exhausted-retry conflict carries the code of the retryable link, not of the outermost error.** A deadlock aborts the transaction and the savepoint release that follows fails with an error of its own; `is_retryable` already judges that failure by the deadlock one link down (`dialects.py:755-772`). The caller routes on the code that made the call retryable. `dialects.py` gains `retryable_link(profile: DialectProfile, exc: BaseException) -> BaseException | None`, the walk of `is_retryable`, and `is_retryable` becomes `retryable_link(profile, exc) is not None`. Basis: the unwind rule in `is_retryable`'s docstring; the source's criterion 9, "the `conflict` carries the retryable code".
11. **The key is the constant `ENGINE_ERROR_KEY: Final = "vfs.engine_error"` in `src/vfs/results/kinds.py`, under the trash keys, and it is not exported from `vfs`.** The `vfs.` prefix is the roadmap's wording and the unit's title, and the trash keys are the precedent for a key that vfs declares and a storage writes. This departs from the `ErrorKind` docstring's sentence "producer keys are unprefixed"; that sentence is amended to say that a key declared in this module is prefixed whoever writes it, and a free-form producer key, such as grep's `scanned`, is not. Basis: K7 criterion 3; `kinds.py:21-23`; the source, section 3.3, which put the constant in `storage/protocol.py` and is departed from for the precedent.
12. **The text renderer does not print the field, and `detail` keeps the driver's text.** A person reading the rendered line already sees the driver's words; the field is for code. Basis: the source, section 3.3, "The message keeps its `detail`. It stops being the only carrier."
13. **The field discloses nothing the message does not already show.** It holds at most four members, none of them a path, a row value, a bind or text, and the engine's name and code are already inside `detail`. No rights judgment reads a driver code, so no answer about what a caller may see changes. Basis: the member set of decision 1; the `detail` of every branch, `engine.py:388-399`.
14. **K7's "a forced deadlock on each leg carries the engine's code" is pinned by forcing the engine's own deadlock code through the real driver on each leg.** On Postgres a SQL function created for the test raises `40P01` with `RAISE EXCEPTION USING ERRCODE`, so the server sends the code and asyncpg and SQLAlchemy carry it as they would a real deadlock. On SQLite, which has no deadlock, the code is `SQLITE_BUSY`, made by the real driver from a lock collision between two raw `sqlite3` connections with a zero wait, and raised inside the attempt at a seam wrapped as `sqlalchemy.exc.OperationalError`, the shape the source's section 8.1 gives a driver failure. A real two-transaction deadlock is not staged: it cannot be made to outlive every retry deterministically. Basis: AGENTS.md, "Count operations, never wall-clock time"; precedent `_fail_statement`, which makes the driver raise its own error.
15. **The in-memory storage is not touched.** It has no engine and no driver code, and its failures are vfs's own. Basis: the unit's scope, "engine failure".

## Cost

- **Per verb call that fails.** The reader is attribute reads on the failure path: at most `_UNWIND_DEPTH` (4) links walked for an exhausted conflict, one origin for every other branch. It issues no statement, takes no lock and allocates one mapping of at most four members, under 100 bytes. A call that succeeds pays nothing.
- **Per batch.** A 10,000-row batch that fails at the engine is answered with one batch-level error, as today, so the field rides once per call and never per row.
- **Least generous engine.** No statement is added, so no `IN`-list or bind budget applies on SQLite or Postgres.

## Choices to confirm

1. **The member that names whose code it is.** Options: (a) `dialect`, the profile's name, as the source and the study have it; (b) `driver`, K7's word, the DBAPI module such as `asyncpg`; (c) both. Taken: (a), decision 1. A SQLSTATE or a SQLite code means what the engine says whatever driver carries it, so `dialect` names the code's space; adding `driver` later is additive, and removing a member is not.
2. **Whether the field reads the `args[0]` SQLSTATE convention.** Options: (a) named attributes only; (b) the classifiers' full reader, `args[0]` included. Taken: (a), decisions 3 and 6. On the two served engines both give the same members; `args[0]` is a convention of pyodbc, whose engine is not served, and on any other driver it can be message text of five characters. Widening the field to (b) later is additive.

## One line

Every failure vfs classifies from a database engine's error, and every conflict that outlived its retries, carries `data["vfs.engine_error"]` with the dialect and the driver's own SQLSTATE or SQLite code and name, read from attributes in one new module and never from the message.
