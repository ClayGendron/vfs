# Every classified engine failure and every exhausted-retry conflict carries the driver's own error code in `data["vfs.engine_error"]`, read from driver attributes and never from message text

The sibling specs of the conversion were written after it, and on 2026-11-25 it was checked against each as it then stood; Builds on names them.

## The outcome wanted

An ETL pipeline or an agent host that gets a failed call from a database mount can route on the engine's own code without parsing a message. A `vfs.unavailable` from SQLite carries `data["vfs.engine_error"] == {"dialect": "sqlite", "code": 1, "name": "SQLITE_ERROR"}`. A `vfs.conflict` that outlived its retries on Postgres carries `{"dialect": "postgresql", "sqlstate": "40P01"}`. A failure with no code from the driver, such as a pool timeout or an `OSError`, carries no field, and a conflict that a vfs guard raised by itself carries none either. The in-memory storage is a SQLite engine and carries the field as a SQLite file does. The field rides in-process on `ResultError.data` and on the wire in `Result.to_payload()`. Two failures with the same code carry equal fields, so a text or a payload that folds equal records folds them still. The kinds, the retry flags and the messages stay as they are today, and no call returns one record more than it returns today.

## Terms

- **A classified engine failure**: a `ResultError` that vfs builds from a driver exception it caught, whatever its kind and severity.
- **An exhausted-retry conflict**: the retryable `vfs.conflict` answered when `with_retry` gave up.
- **An in-band stale snapshot**: a `StaleSnapshot` that a vfs guard raised itself, as against the one `with_retry` raises when an engine conflict outlives its attempts. Most have no driver error behind them; five guards raise one `from` a unique violation they caught, and it is in-band all the same.
- **The retryable link**: the first exception on a failure's context chain, within `_UNWIND_DEPTH` links, that the profile judges retryable alone; it is the error that made the attempt retryable.

## The problem

The engine's own code survives only inside the message text, and the envelope forbids any consumer to parse `message` (`envelope.py:97-99`). A pipeline that wants to tell a full disk from a deadlock, or a host that wants to back off on SQLite's busy code and page someone on Postgres's I/O class, has no field to read. At the reference deployment's 150,000 verb calls and 100 nightly batches a day, the failures that do occur arrive at an ETL job or an agent host that cannot route them without a regular expression over prose. K7's criterion 3 asks for the code as a field on every backend failure.

## Decisions

1. **The field is `data["vfs.engine_error"]`, a mapping that always holds `dialect` and holds each of `sqlstate`, `code` and `name` only when the driver carries it.** `dialect` is the profile's name, the dialect's own name on the generic floor (`dialects.py`, `profile_for`); `sqlstate` is a five-character string; `code` is an integer; `name` is a string. The values are JSON-native, so `to_payload` and `from_payload` keep them as they are. Basis: the source, section 3.3; the `ErrorKind` docstring's rule that absence means "not known" (`kinds.py:51-52`). The departure from K7's member `driver` is choice 1.
2. **On the two served engines the members are read from these attributes, and from nothing else.** SQLite through aiosqlite: `code` from `sqlite_errorcode`, which is SQLite's extended code, and `name` from `sqlite_errorname`. Postgres through asyncpg, or psycopg where an application chooses it: `sqlstate` from `sqlstate`, else `pgcode`. A driver on the generic floor gets whichever of these four attributes it sets. Basis: the attributes the classifiers already read (`dialects.py:785`, `:792`, `:882`) and the probe under What the code does today; the reassessment, which finds MariaDB's, SQL Server's and Oracle's readers gone with their engines.
3. **The reader never reads `str(exc)`, `exc.args` or any message, and a member whose attribute has the wrong type is left out.** `sqlstate` is kept only as a `str` of exactly `_SQLSTATE_LENGTH` (5) characters, `code` only as an `int` that is not a `bool`, `name` only as a `str`. When none of the three is kept, the reader answers `None` and no field is written. Basis: the unit's title and K7's "never from the message"; the classifiers' `args[0]` arm is left to them, which is choice 2.
4. **The record is `EngineError(NamedTuple)` with `dialect: str`, `sqlstate: str | None`, `code: int | None` and `name: str | None`, and `as_data()` returns the present members as a `dict[str, str | int]`; it is read by `engine_error(dialect: str, exc: BaseException) -> EngineError | None`, which reads `driver_origin(exc)`.** The type and the function carry the key's own noun, because how-we-name gives one concept one noun in public and private code (`documentation/maintainers/how-we-name.md`, "Nouns"); the source's `EngineCode` and `engine_code` would be a second noun. The docstring says the record is data and is never raised. `as_data()` writes the present members in the record's declared order, which decision 16 relies on. Basis: the source, section 3.3, renamed.
5. **A new module, `src/vfs/storage/backends/database/failures.py`, holds `EngineError`, `engine_error` and `classify(profile: DialectProfile, dialect: Dialect, exc: BaseException, *, context: str) -> ResultError`, the classifier's whole body; `EngineHost.classify_failure` keeps its name and signature and returns `classify(self.profile, self._dialect, exc, context=context)`.** Every caller, in the tree and on the open branches, keeps calling `classify_failure`. `engine.py` stands at its baseline and must not grow, and the field adds an argument to every answer; moving the body takes about twenty lines out. `failures.py` imports `dialects.py` and `vfs.results` and nothing above them. Where 177-2 has landed first, the body that moves holds its `CommitInDoubt` branch and its one-line call to `is_disconnect`, and `failures.py` also imports `CommitInDoubt` from `commits.py`, which imports `dialects.py` and `seams.py` and nothing above them (177-2's decision 24). Basis: the size baseline, `tests/lint/allowlist.py:9-11`; precedent `attempts.py`, a module of its own for one concern of the engine host, and 177-2's decision 24, `commits.py`.
6. **`dialects.py` gains `sqlstate_attribute(origin: object) -> str | None`, the named-attribute half of `_sqlstate_of`, and `_sqlstate_of` calls it before its `args` arm.** The field and the classifiers then read the same attributes in one place, and only the classifiers read `args`. Basis: the duplication rule of AGENTS.md, "Code smells".
7. **`classify` writes the field on every branch: `backend_unavailable`, `unsupported`, `internal` and `unavailable`.** Each branch keeps its kind, its retry flag and its detail. Basis: the source, section 3.3, "The kinds do not change"; K7 criterion 3, "`classify_failure` sets `data[...]`".
8. **`classify` gains a branch for `StaleSnapshot`: `classified(ErrorKind.conflict, retryable=True, detail=f"{context} kept losing to concurrent changes: {exc.context}", data=...)`, whose field is read from the retryable link of `exc.__cause__`.** The detail is the text the three sites build today, so no message changes. An in-band stale snapshot carries no field: most have no `__cause__`, and the five that a guard raises `from` a unique violation (What the code does today) have a cause no profile judges retryable, so the walk finds no link (decision 18). When no field is read, the branch passes `data=None`. The runners' arms become one each: `_execute` catches `(StaleSnapshot, SQLAlchemyError, OSError)` and `_mutate` the same, each returning `Result(ops=(op,), errors=[self._host.classify_failure(exc, context=op)])`. Where 177-2 has landed first, `_mutate`'s arm also names `CommitInDoubt`, as its decision 10 has it. `ensure_ready`'s `StaleSnapshot` arm becomes `return self.classify_failure(exc, context="first touch")`, which composes the lower-case detail pinned at `tests/storage/database/test_coherence.py:1084`; its other arm keeps the context `First touch` it passes today (`engine.py:302`), so the two arms stay two and no message changes. A branch that 177-2 adds for `CommitInDoubt` reads its field by `engine_error` from the commit's own error on `exc.__cause__`, with no walk for a retryable link, as decision 18 says and 177-2's decision 9 has it. Basis: 177-2's decision 10, quoted under Builds on, built here for the `StaleSnapshot` half.
9. **Each other classified engine failure carries the field as well: the privilege refusal of `install_extensions`, the two planner-statistics advisories, and, if the kernel store has landed when this is built, its privilege refusal and its exhausted-retry answer.** Each keeps its kind, severity, retry flag and detail and gains `data={ENGINE_ERROR_KEY: ...}` from the exception it already holds. A refusal vfs builds with no driver exception in hand gains nothing: the inconsistent-provisioning refusal (`engine.py:650-659`), and the refusal of a missing vector function (`engine.py:620-621`), which reads an empty answer and a permanent probe error as one verdict and keeps neither. The build greps `src/vfs` for `classified(` beside a caught `DBAPIError`, `SQLAlchemyError` or `StaleSnapshot` and covers each hit. Basis: the unit's title, "every classified engine failure"; the source named only the classifier and the conflict, and this widens it to the rest of what the title covers.
10. **The exhausted-retry conflict carries the code of the retryable link, not of the outermost error.** A deadlock aborts the transaction and the savepoint release that follows fails with an error of its own; `is_retryable` already judges that failure by the deadlock one link down (`dialects.py:755-772`). The caller routes on the code that made the call retryable. `dialects.py` gains `retryable_link(profile: DialectProfile, exc: BaseException) -> BaseException | None`, the walk of `is_retryable`, and `is_retryable` becomes `retryable_link(profile, exc) is not None`. Basis: the unwind rule in `is_retryable`'s docstring; the source's criterion 9, "the `conflict` carries the retryable code".
11. **The key is the constant `ENGINE_ERROR_KEY: Final = "vfs.engine_error"` in `src/vfs/results/kinds.py`, under the trash keys, and it is not exported from `vfs`.** The `vfs.` prefix is the roadmap's wording and the unit's title, and the trash keys are the precedent for a key that vfs declares and a storage writes. This departs from the `ErrorKind` docstring's sentence "producer keys are unprefixed"; that sentence is amended to say that a key declared in this module is prefixed whoever writes it, and a free-form producer key, such as grep's `scanned`, is not. Basis: K7 criterion 3; `kinds.py:21-23`; the source, section 3.3, which put the constant in `storage/protocol.py` and is departed from for the precedent.
12. **The text renderer does not print the field, and `detail` keeps the driver's text.** A person reading the rendered line already sees the driver's words; the field is for code. Basis: the source, section 3.3, "The message keeps its `detail`. It stops being the only carrier."
13. **The field discloses nothing the message does not already show.** It holds at most four members, none of them a path, a row value, a bind or text, and the driver's own words for the same failure are already inside `detail`. No rights judgment reads a driver code, so no answer about what a caller may see changes. Basis: the member set of decision 1; the `detail` of every branch, `engine.py:388-399`.
14. **K7's "a forced deadlock on each leg carries the engine's code" is pinned by forcing the engine's own deadlock code through the real driver on each leg.** On Postgres a SQL function created for the test raises `40P01` with `RAISE EXCEPTION USING ERRCODE`, so the server sends the code and asyncpg and SQLAlchemy carry it as they would a real deadlock. On SQLite, which has no deadlock, the code is `SQLITE_BUSY`, made by the real driver from a lock collision between two raw `sqlite3` connections with a zero wait, and raised inside the attempt at a seam wrapped as `sqlalchemy.exc.OperationalError`, the shape the source's section 8.1 gives a driver failure. A real two-transaction deadlock is not staged: it cannot be made to outlive every retry deterministically. Basis: AGENTS.md, "Count operations, never wall-clock time"; precedent `_fail_statement`, which makes the driver raise its own error.
15. **The in-memory storage is not edited, and it carries the field as a SQLite file does.** `InMemoryStorage` is a `SQLiteStorage` over a private `:memory:` database (`src/vfs/storage/backends/memory.py:40`): it runs the SQLite driver under the profile named `sqlite` and answers a failure through the same `classify_failure`, so its field reads `{"dialect": "sqlite", ...}` with no line of `memory.py` changed (EXECUTED on a prototype, What the code does today). The earlier text of this decision said the in-memory storage had no engine and no driver code; that was the storage of an earlier generation of the code, and unit 179-7's Builds on names the mismatch. Basis: the docstring of `memory.py`, "One storage implementation, one semantics".
16. **Two failures with the same code carry equal fields, in one member order, and the field holds nothing that differs between two calls.** `as_data()` writes `dialect`, then `sqlstate`, then `code`, then `name`, each only when present, so two fields read from the same code are equal as mappings and equal in `repr`, and a JSON round trip keeps the order. The field never holds a statement, a bind, a path, an attempt count or a time. A branch that reads no field passes `data=None`, never an empty mapping. This is what the text merge of unit 167-3's decision 19 reads: it joins records "equal in `(kind, severity, retryable, path, message)` and in `data`" by a key that holds `repr` of `data`. With the field written this way, engine failures that printed as one line without the field print as one line with it, and the field splits a group only where one message stands over more than one code, which is at most one line for each code the engine has and never one for each row. Run on a prototype of that key over `dev`'s `_error_line` (`check-179-5/reader.py`): 10,000 records equal in the five fields printed one line with no field and one line with the field; the same 10,000 over seven sources printed one; with the same members written in two orders they printed two, though the mappings compared equal; with three SQLite codes behind one message, 5, 261 and 517, they printed three; and 10,000 records each at its own path printed 10,000 with the field and 10,000 without it, which the field does not change and which unit 167-3's decisions 7 and 24 own. Reason: a field that kept alike failures apart would turn the one line a fan-out prints into one line a mount. Precedent: a `NamedTuple`'s `_asdict()` keeps field order, and the trash keys are written in one order at one site (`descent.py:117`). This is choice 5.
17. **The field adds no record, and where records are folded the fold keeps the field of the record it keeps.** This unit writes `data` on records that exist today and mints none. A database mount answers an engine failure with one record a call, whatever the batch: one refused `write` of 10,000 entries returned one error and no row, and a write refused on three mounts returned three, one a mount (EXECUTED, What the code does today). So a result holds at most one such record for each mount the call reached, beside the advisories the host held, and the field costs under 100 characters of payload for each (94 on average, measured over three SQLite busy codes). A caller that makes 10,000 calls gets 10,000 results, one record each; no result of vfs grows with that loop. Three folds exist or are specified, and none is edited. The wire's rollup under `max_errors` ships each group's first record with its own field and one count entry whose `data` is `vfs.rollup` alone, so the codes of the rest of the group are not in that payload and stay on `Result.errors` in the process (EXECUTED: 10,000 records over three codes rolled to two entries, the head with code 5 and a count of 9,999 with no field). `to_str(max_errors=...)` of unit 167-3's decision 24 draws the same two entries. A shell line keeps one fact for each `(kind, path, message)`, so a loop of refused writes keeps the field of the first refusal with that key: 300 refused redirects kept one fact with its field, and with three codes behind one message they kept one fact with the first code (EXECUTED on a prototype of the field over `dev`'s shell, `check-179-5/batch.py`). Reason: each fold already drops every other field of the records it folds, the path and the message among them, and the count entry is the envelope's; a list of the distinct codes on a count entry is additive and is Out. Precedent: `to_payload`'s docstring, the rollup "caps the boundary, never the algebra". This is choice 6.
18. **Which exception the field is read from is fixed by the class of the failure `classify` was handed, and is one of three readings.** A driver failure, a `DBAPIError`, any other `SQLAlchemyError` or an `OSError`, is read by `engine_error` from its own origin (decision 7). A `StaleSnapshot` is read from the retryable link of its `__cause__`, and carries no field when it has no cause or the walk finds no link (decisions 8 and 10). A `CommitInDoubt`, where 177-2 is built, is read from its `__cause__` itself, the commit's own error, with no walk, and carries no field when it has no cause or the cause carries no code. The two readings differ, and each case was run on a prototype (`check-179-5/reader.py`). For a commit in doubt raised from the driver's real `SQLITE_READONLY`, the commit's own error read as code 8 and the retryable link as nothing; raised from an invalidated wrapper over SQLSTATE `25P02` whose `__context__` holds `40P01`, the commit's own error read as `25P02` and the link as `40P01`. For a guard's stale snapshot raised from the driver's real unique violation, the cause's own origin read as code 2067 and the link as nothing. ## Cost

- **Per verb call that fails.** The reader is attribute reads on the failure path: at most `_UNWIND_DEPTH` (4) links walked for an exhausted conflict, one origin for every other branch. It issues no statement, takes no lock and allocates one mapping of at most four members, under 100 bytes. A call that succeeds pays nothing.
- **Per batch.** A 10,000-row batch that fails at the engine is answered with one batch-level error, as today, so the field rides once per call and never per row: one refused `write` of 10,000 entries to a SQLite file returned one error and no row (EXECUTED, What the code does today).
- **Per result.** No record is added (decision 17). A result holds at most one engine-failure record for each mount the call reached, beside the host's held advisories, and each field is under 100 characters of payload. No path on `dev` puts a record for each row of a batch on one result for an engine failure; a batch that a caller sends again row by row is 10,000 calls and 10,000 results of one record each.
- **Per rendered text.** The text merge of unit 167-3 reads `data`. Equal codes are equal `data` in one member order (decision 16), so the field adds a line only where one message stands over more than one code: 10,000 alike failures printed one line with the field and one without, and three codes behind one message printed three (EXECUTED on a prototype of the key). The bound is the engine's own codes, never the batch.
- **Least generous engine.** No statement is added, so no `IN`-list or bind budget applies on SQLite or Postgres.

## Choices to confirm

1. **The member that names whose code it is.** Options: (a) `dialect`, the profile's name, as the source and the study have it; (b) `driver`, K7's word, the DBAPI module such as `asyncpg`; (c) both. Taken: (a), decision 1. A SQLSTATE or a SQLite code means what the engine says whatever driver carries it, so `dialect` names the code's space; adding `driver` later is additive, and removing a member is not.
2. **Whether the field reads the `args[0]` SQLSTATE convention.** Options: (a) named attributes only; (b) the classifiers' full reader, `args[0]` included. Taken: (a), decisions 3 and 6. On the two served engines both give the same members; `args[0]` is a convention of pyodbc, whose engine is not served, and on any other driver it can be message text of five characters. Widening the field to (b) later is additive.
3. **Which error a commit in doubt takes its field from.** The other side is unit 177-2, whose decision 9 says "read from the commit's own error on `exc.__cause__`", and the earlier text of decision 8 here, which said "the same way" as a stale snapshot. Options: (a) the commit's own error, with no walk; (b) the retryable link of the cause, as an exhausted conflict is read; (c) the link when there is one, else the commit's own error. Taken: (a), decision 18. It is the only reading that carries a code for a commit the engine refused outright, and it is the reading 177-2 already writes; (c) can be taken later by adding a member, where changing which code the one member holds cannot be done without breaking a host that routes on it.
4. **Whether a guard's stale snapshot raised from a unique violation carries the violation's code.** The other side is the five guards of `indexing.py` and `topology.py`, which no spec of the conversion edits. Options: (a) no field, the retryable-link reading; (b) the cause's own code, SQLSTATE `23505` or SQLite 2067. Taken: (a), decision 18. The outcome wanted says a conflict a guard raised by itself carries none, and adding a field to an answer later is additive where removing one is not.
5. **Whether equal codes must be equal `data`, member order included.** The other side is unit 167-3, whose merge key holds `repr` of `data` and so keeps apart two mappings that differ only in the order of their keys (its decision 19). Options: (a) this unit fixes the order and keeps the field free of anything that differs between calls; (b) unit 167-3 sorts the keys in its key and this unit promises nothing. Taken: (a), decision 16. It costs nothing here, since the record is a `NamedTuple`, it holds on `dev`'s renderer and on any host that compares `data`, and (b) stays open to that unit.
6. **What a fold keeps of the field.** The other side is the envelope's rollup, which unit 167-3's decision 24 reuses for the text, and the shell line's kept facts. ## One line

Every failure vfs classifies from a database engine's error, and every conflict that outlived its retries, carries `data["vfs.engine_error"]` with the dialect and the driver's own SQLSTATE or SQLite code and name, read from attributes in one new module and never from the message.
