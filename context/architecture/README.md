# /context/architecture

The map of the system: how the pieces of vfs fit together, what each
is called, and which decision put it there. One diagram per page, each
with the terms it introduces defined on the same page, and one
consolidated [glossary](glossary.md).

These pages are drawn **from** the decisions and the code; they decide
nothing. When a diagram and an ADR disagree, the ADR wins and the
diagram is wrong. When a diagram and the code disagree, read
`context/README.md`: fix the code unless the context is demonstrably
wrong. The diagrams exist so a spec author, a reviewer or a new
contributor can see the whole before touching a part.

## Viewing the pages

Three ways, from least to most interactive.

1. **On GitHub.** Open any page; GitHub draws the Mermaid in place.
2. **The viewer, from disk.** Open `index.html` in a browser. It is one
   self-contained file: every page, a sidebar, light and dark, and every
   diagram with pan, zoom and a full-screen mode. Drag to pan; pinch or
   hold ctrl and scroll to zoom; double-click to fit; press Escape to
   leave full screen. Opened from disk it shows the snapshot it was
   built from (the header says which commit).
3. **The viewer, live.** Serve this directory and the viewer re-reads
   the `.md` files on every load, so edits show without a rebuild:

   ```bash
   uv run python -m http.server 8765 --directory context/architecture
   ```

   then open <http://localhost:8765/>.

`index.html` is generated by `build_html.py` and committed so the file
works without a build step. After editing a page, rebuild it:

```bash
uv run python context/architecture/build_html.py
```

The renderers (marked, Mermaid) load from a CDN, so the viewer needs a
network connection the first time; the page text itself is local.

## How to read a page

Every page has the same shape, so a reader can skim one and know the
others.

1. A status line: when it was drawn, against which commit, and whether
   it draws the code as it is or a decided target.
2. The picture, in Mermaid. GitHub renders it in place; so do most
   editors with a Mermaid preview.
3. *Reading the picture*: short sentences, one idea each, the key idea
   said more than once.
4. *Terms this diagram introduces*: a table. A term is defined on the
   first page that needs it and listed again in the glossary.
5. *What is planned, and where*: the spec or ADR that decides each
   planned element.
6. *Open*: the questions the page cannot answer, pointing at
   `open-questions.md` or an ADR's *Pending Clay* list.

## The legend

- A **solid** box is built and on `main` at the commit the status line
  names.
- A **dashed** box is planned. It names the spec or ADR that decides it.
- A **dotted** box is built but retiring.
- A verb in *italics* inside a group is a planned addition to that
  group.

## Keeping the map true

- These pages are **revised in place**, unlike research memos and ADRs.
  Move the date on the status line when you do.
- When a spec lands, update the pages its *What is planned* sections
  name: the box turns solid, the spec reference moves to *Sources*.
- When an ADR is accepted or superseded, re-read the pages that cite
  it.
- Add a page when a new subsystem earns one, and a row to the table
  above. Keep one subject per page; prefer a new page over a longer
  one.
- Every term in a *Terms* table goes into `glossary.md` with a pointer
  back. The glossary is the one alphabetical index; the pages are where
  the terms are explained in context.
- Mermaid is checked by rendering. A page that does not render on
  GitHub is broken; fix the diagram, not the renderer.
- After editing any page, rebuild `index.html` with `build_html.py` so
  the committed snapshot matches the Markdown.

## Where this sits in the pipeline

`research → decide → specify → code`, all under `standards/`. The
architecture pages sit beside `standards/` as a reading aid: they are
not a stage, they commit us to nothing, and they are only as true as
the decisions and the code they draw. A spec author starts here to
find the diagram the spec will change, and ends here by changing it.
