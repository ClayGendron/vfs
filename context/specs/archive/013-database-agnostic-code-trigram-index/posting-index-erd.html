Database-Agnostic Trigram Posting Index ERD

A portable inverted index for VFS code search: write cheap gram deltas, flush them into immutable page-shaped posting segments, and compact in the background. The index is a candidate filter; exact regex/string verification still runs against stored content.

Design Summary

The portable design is an inverted trigram index stored as ordinary database tables. The write path appends cheap delta rows to gram_staging. A background flush folds those deltas into immutable compressed posting_pages. A later compaction job merges pages, applies tombstones, and retires old pages by marking is_active = false.

The core invariant is no false negatives: for every indexed chunk, each distinct folded byte trigram must be present in the read fold of active pages plus unapplied staged adds minus unapplied staged deletes.

Canonical Gram

Normalize line endings, apply NFC, apply Unicode casefold(), encode UTF-8, then emit every 3-byte window as a packed integer.

Posting Key

Posting lists use a stable integer doc_id, not UUIDs or paths. Sorted integer ids are required for compression and fast merge/intersection.

Verification

The index only returns candidate chunks. The exact literal or regex matcher must still verify candidates against stored content.

Logical Tables

Table Purpose Portability Rule
vfs_index_shards One logical index or partition. Stores backend-specific sizing knobs. Use this when a backend needs tenant, corpus, repo, or doc-id range partitioning.
vfs_entries Files and chunks. doc_id is the posting-list integer key. Keep entity identity separate from posting identity. UUID/text can remain public.
gram_staging Append-only delta log for adds and deletes. Fold by latest seq per (index_id, gram_key, entry_id).
posting_pages Immutable compressed pages of sorted doc_ids for one gram. Bound by compressed byte target, not by a fixed tiny doc count.
gram_batches Flush state machine for resumable background work. Use status transitions so crashes can resume or retry safely.
gram_stats Document frequency and active page counts. Required for rarest-first reads and compaction scheduling.

Portable Schema Skeleton

CREATE TABLE posting_pages (
  page_id       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  index_id      BIGINT NOT NULL,
  batch_id      BIGINT NOT NULL,
  gram_key      INTEGER NOT NULL,

  level         SMALLINT NOT NULL DEFAULT 0,
  generation    BIGINT NOT NULL DEFAULT 0,

  doc_count     INTEGER NOT NULL,
  min_doc_id    BIGINT NOT NULL,
  max_doc_id    BIGINT NOT NULL,

  encoding      SMALLINT NOT NULL,
  byte_count    INTEGER NOT NULL,
  postings      BINARY_BLOB_TYPE NOT NULL,
  is_active     BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE INDEX ix_posting_pages_lookup
  ON posting_pages (index_id, gram_key, is_active, min_doc_id);

CREATE TABLE gram_staging (
  seq       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  index_id  BIGINT NOT NULL,
  batch_id  BIGINT,
  gram_key  INTEGER NOT NULL,
  entry_id  ENTRY_ID_TYPE NOT NULL,
  doc_id    BIGINT,
  action    SMALLINT NOT NULL
);

CREATE INDEX ix_gram_staging_law
  ON gram_staging (index_id, gram_key, entry_id, seq);

Write, Flush, Read

Write Transaction

  1. Chunk content if needed.
  2. Extract distinct folded byte trigrams per indexed chunk.
  3. For inserts, append action = add staging rows.
  4. For edits, diff old and new gram sets.
  5. For deletes, stage delete rows before content disappears.

Background Flush

  1. Close an open batch.
  2. Apply latest-action-wins over staging rows.
  3. Resolve add rows from entry_id to doc_id.
  4. Sort doc ids per gram.
  5. Encode page-shaped sorted runs into posting_pages.

Read Fold

current_doc_set(gram) =
    union(active posting_pages for gram)
    union(unapplied staged adds for gram)
    minus(unapplied staged deletes for gram)

Posting Page Encoding

Store each page as a compressed sorted run. Keep min_doc_id and max_doc_id as normal columns for range pruning. The blob stores deltas after the first id: 

doc_ids:  [10, 20, 30, 45]
anchor:   min_doc_id = 10
blob:     varint(10), varint(10), varint(15)

decode:
  current = min_doc_id
  for gap in blob:
      current += gap
      emit current

The encoding column allows future formats such as delta-varint, bitpacking, roaring bitmaps, or Elias-Fano without a full table migration.

Postgres-Specific Notes From the Linux Experiment

A 10,000-chunk Linux-source benchmark produced 9,189,305 (gram, doc) postings across 120,437 grams. The strongest current Postgres recommendation is: 

target payload = 1 KB
benchmark 2 KB
do not default to 64 KB
consider STORAGE PLAIN only with a hard payload ceiling near 4 KB

In the retained local benchmark database, a 1 KB payload target stored 9,189,305 postings in 161,956 posting-page rows, total size 39 MB, with the TOAST table still at its empty baseline.

Errors To Avoid

  • Do not store UUIDs, paths, or strings inside posting lists. Use sorted integer doc_ids.
  • Do not use one huge mutable blob per gram. Split postings into page-shaped immutable segments.
  • Do not apply delete staging rows too early. Deletes are safe to remove only after every affected active page is rewritten or retired.
  • Do not rely on pg_trgm as the canonical code index. Its tokenizer is word-oriented and loses punctuation-sensitive grams.
  • Do not skip exact verification. The index is a conservative candidate generator.
  • Do not let staging grow only by time. Bound it by pending rows or bytes because read cost scales with pending size.
