## Scale and the production posture

- Per index visit, about 11,000,000 a day: the refresh visits each dirty entry once and adds per pass one `lex_df` fetch over its vocabulary, one `lex_docs` delete, one `lex_stats` read and the flips, each chunked by the membership budget (READ); a kept entry is read for one column and never folded. The daily rebuild's flip writes the stamp in the row it already writes; its row-constructor spelling goes from 500 to 333 rows a statement at the 1,000-element floor, about 30,000 statements a day where 20,000 (INFERRED, the spec's figure re-derived).
- Per verb call, about 150,000 a day: one live-set statement of one bind and the generation reads in place of the pointer reads; rows per call grow with the segment count since the last rebuild and never with the corpus: posting rows per gram, kernel groups per AND-group, head blocks per slot (READ). At the 15-minute default a day carries 96 segments to the fold and at the 1-minute floor 1,440; at Oracle's 1,000-element `IN` list the epoch list then takes two slices, so each epoch-pinned statement runs once per epoch slice per key chunk, every statement bounded (INFERRED from decision 9). The live-set statement reads every unreclaimed `gram_epochs` row, at the floor about 1,440 rows a call, about 216,000,000 row visits a day, small rows and no index, named as such by decision 4 (INFERRED).
- Per file write: nothing; `indexed_epoch` is not in `_CLOBBER_COLUMNS` (`writes.py:114` to `:134`) nor in what a copy carries (`_COPIED_COLUMNS`, an explicit list, `topology.py:87` to `:104`, and the copy's values at `:442` to `:456`, where a copy starts as a creation), so writes and copies never set it (READ).
- Per batch: nothing; a refresh during the nightly batch holds about 45,000 posted files in the accumulator, proportional to the dirty set, named with the partitioned build as the direction (READ).
- Per corpus: the fold's range delete grows by the day's delta rows, at most about 10,500,000 `lex_docs` rows (READ).
- Unbounded: nothing per statement; the segment count between rebuilds has no cap, which is the honest profile the spec names, with the compaction spec as its direction, not a designed limit (READ). The first refresh after a link-generation bump reads every live body (M1).
- Engines: never SQLite-shaped; the floors are Oracle's `IN` list and SQL Server's binds, and the tail fetch's triples chunk at a third of the budget (READ). The one engine assumption that fails is the single snapshot of a build's scans, which holds on SQLite, Postgres and MariaDB and not on SQL Server and Oracle (H1).

## Premortem

Built as written on a customer's SQL Server, the daily rebuild runs for hours while the nightly batch re-ingests unchanged files; every file re-ingested between the rebuild's gram scan and the lexical page that holds its chunks is published with grams, stamped, and no lexical rows; the next refresh keeps it and flips it, and search never ranks it until the next rebuild, which repeats the loss for that night's batch. That is H1, EXECUTED on SQL Server.

Built as written, a release bumps `LINK_GENERATION`, the first refresh after the deploy re-dirties every live entry and materializes every body in its chunk pass while holding the lease, where the spec promised O(dirty); at the reference deployment that is about 40 GB of text read and held several times over by a pass meant to run every 15 minutes. That is M1.

Built as written, the build's SQLite nodes for criterion 5 stage a quiet store, the closing compare is skipped because the overlay is empty, the patched `current_generation` is never called, and the node is red on a correct build or rewritten until it passes vacuously. That is L1.

## Findings, most severe first

1. **H1. On SQL Server and Oracle one build can post an entry's grams without its chunks, or its chunks without its grams, and the stamp turns either into a lasting wrong answer** ([Decisions](../specifications/active/2026-10-31-refresh-the-incremental-index-verb.md#decisions), 5, 6, 12, 14 and 26; [Design](../specifications/active/2026-10-31-refresh-the-incremental-index-verb.md#design), the build paragraph). The Design says every scan of a build "runs in the build's one transaction, as the full build's do, so they cover one snapshot of the dirty set", and decision 26 says the stamp is sound because "the rows a build read are still the entry's rows when it publishes". Neither holds where the maintenance runner pins no isolation: `_execute_maintenance` stamps `op_isolation` (`backend.py:1896`, `dialects.py:661` to `:673`), which is `REPEATABLE READ` on Postgres and MariaDB (`dialects.py:508`, `:576`) and nothing on SQL Server and Oracle, so each statement there reads the latest commit. The posting scan (one streaming statement, `indexing.py:413` to `:433`) and the lexical pages (keyset statements that re-test `chunked`, `indexable` and `deleted_at`, `lexical.py:109` to `:117`, and in the delta also `~encoded` and the stamp term) then see different commits. EXECUTED with `scan_split_probe.py` on today's tree against SQL Server 2025, a rival committed through the public verbs between `build_epoch`'s gram scan and its lexical build: (a) a same-body overwrite of `/a.txt` left it gram-covered with 0 of its chunk ids in the new epoch's `lex_docs`, because the write cleared `chunked`; (b) a restore of `/b.txt`, trashed before the run, left it not gram-covered with 1 of 1 chunk ids in the new epoch's `lex_docs`. SQLite with the rival simulated as statements in the build's session printed the same. Today both are harmless: the version-guarded flip misses `/a.txt` and the overlay serves it (EXECUTED: search for its word found it). Under this spec, (a) is stamped by the publish because the stamp is unguarded and lands on the posting scan's set; the next refresh's chunk pass keeps its rows (same body), the kept test passes, the flip makes it `encoded`, and no live segment holds its chunks. EXECUTED, the probe applied that chunk pass and that flip: search for `/a.txt`'s word answered nothing, grep still found it from its grams. (b) keeps its older stamp, so the next refresh posts it, its chunk id gets lexical rows in a second live segment, the publish deletes only the first segment's `lex_docs` row, and the scorer sums both segments' postings, the 2.0 of the drafted design (INFERRED from the EXECUTED premise and the ratio `kept_probe.py` printed). Both last until the next fold, and the rebuild's own hours-long window is the widest: every same-body overwrite or trash-and-restore landing between its gram scan and the lexical page that holds that entry's chunks does this, which at the reference deployment is the nightly re-ingest of unchanged files (INFERRED). A second path writes the stamp false on every engine, INFERRED from decision 14's lapse: a refresh whose lease lapsed after its build, a rival run's chunk pass that re-splits one of its posted entries and clears the stamp, then the first run's publish, whose generation CAS passes because a chunk pass is no publish, and whose unguarded stamp names a segment that holds the entry's old chunks and old grams; the entry is then kept with its new body in no index. Consequence if built: on the two customer engines, entries silently missing from search and chunks scored twice, each until the next rebuild, with no record. Fix text, in decision 26 and the build paragraph: "Each build feeds its lexical builder the chunk rows of exactly the entries its posting scan covered and of no other, selected by entry id from the covered set and never by re-reading the entry's flags, because on SQL Server and Oracle the two reads see different commits; and each publish stamps `indexed_epoch` on a covered entry only where its `chunk_source_hash` and `chunk_generation` still equal what the posting scan read, so the stamp lands exactly on entries whose current chunk rows the segment posted, whatever write moved the version and under a lapsed lease. The full build and the delta build both take the rule. A seam `<verb>:before-lexical` stands between the posting scan and the lexical build." Closes also with a criterion over `ENGINE_LEGS` that commits a same-body overwrite of a covered entry and a restore of a trashed one at that seam, in a rebuild and in a refresh, and asserts after the next refresh that search ranks the overwritten entry from its chunks and that the restored entry's chunk ids sit in one live segment and score as before, and with a ledger row whose mutation restores the flag filter on the lexical feed. The author chooses how the lexical feed reads the covered set (membership chunks of ids, or keyset pages over chunk ids kept in memory only when their entry is covered, which the full build's resident `covered` map allows); the spec, not the build, must say which.
