## The author's questions, answered first

1. **Decision 10 keeps planning on the loop, about 3.4 s for 10,000 roots × 64 arms. Is that consistent with closing the audit finding and with AGENTS.md, or must planning move too?** READ, INFERRED. It is consistent with AGENTS.md and not with the claim that the finding is closed. AGENTS.md allows a suboptimal profile that is named honestly with its direction, and decision 10 names one and adds no cap, so it is not a scale finding on its own. But the audit finding's intended behaviour is that "one caller's glob cannot block other agents on the same loop", and planning is glob matching too: `residuals` builds and matches one native program per pattern component per bind segment (`src/vfs/pattern_matching/glob.py:386-412`, `:528-530`), on the loop, with no wall. Its cost is not "linear in the call's own input", as the decision says; it is a product of two caller inputs, roots × arms, and for grep and glean the arms are every arm of every pattern in `globs`, a list of any length (`src/vfs/params.py:263-264`), so a grep scoped by 10,000 paths with four 64-arm globs is about four times the measured 3.4 s, by the decision's own linear cost. That is the same class of loop hold this spec removes from the row sites (7.27 s for a chained glob). So the spec's opening sentence "With both landed, the finding's fix is complete" is not evidenced, and the release-audit record would be written as if it were. Planning does not have to move in this landing, but the spec must either move it or stop claiming the finding closed and name the residual; see M1.
2. **Is decision 6 sound for every root, including `/` and roots whose text holds glob metacharacters?** READ, EXECUTED, INFERRED. Yes. The argument is structural, not only empirical. `effective_pattern` composes a path arm as `escape_glob(root)` followed by the arm anchored with a leading `/` (`glob.py:360-364`). `escape_glob` turns every metacharacter of the root into a one-member class (`glob.py:122-132`), so the root's text compiles to literal atoms that match exactly that text, and a root such as `/**` becomes `/[*][*]`, which is no `**` component and cannot collapse under `_canonical`. The anchored arm then begins with a separator atom (`_program` emits `sep` between components, `glob.py:533-556`), so every composed path arm needs at least one more `/` after the root's text, and the probe's subject is exactly the root's text. No suffix of atoms can match the empty string in place of that `sep`. The root `/` is the one root where the argument fails, because there the composed pattern is the arm alone, and the probe skips it (`base.py:2495-2496`). The author's oracle battery covers roots with `[x]`, `*`, `**`, `{a,b}`, `]`, `!`, `-` and non-ASCII text, and the engine spec's parity battery pins the engine to that oracle, so the empirical check reaches the engine too. Exclusions are not composed and still match the root's row as written today, which the decision keeps. One gap: when the call has no name arm, the spec says the probe "keeps no row and makes no hop", and the Design says `_glob_dispatches` hands `_root_probes` "nothing"; it must still run the stat probe, or a missing root loses its loud classification (L3).
3. **Decision 3 builds each distinct program on the worker of the call's first hop under a lock. Is that sound across concurrent hops and pool shutdown, and is the residency honest?** READ, INFERRED. The lock is sound. A waiting thread blocks in `threading.Lock.acquire`, which releases the GIL; the program refusals that could make a build fail are structural (`crates/vfs-core/src/glob.rs:267-283`) and `_program` never emits them; and decision 4 cuts the budget after the build, so a waiter's wait shortens its own budget instead of extending the wall. Two edges need a sentence. After `close()`, `call_offloaded` serves the hop inline (`offload.py:98-101`), so the loop thread itself can wait on the lock while a worker builds; that is the closer's cost `offload.py` already accepts, but it should be said (L7). And the build is not under the wall at all: it runs to the end however long it takes, and a row's verdict runs to the end however many programs it holds, which is H1. On residency: "as today" is true, since today's storage gates build the same programs and the router's probe today builds and drops more. But the Scale paragraph's figure, 334 MB for 10,000 patterns, describes a scoped call with no caller globs. With caller globs, the router composes every arm under every root into storage's channel, so a call scoped by 10,000 roots with a 64-arm glob reaches storage as up to 640,000 patterns and as many programs, today and after (L9).
4. **Is decision 12 in scope for one landing, and is every importer counted?** EXECUTED, READ. Yes on both. The removal is what makes the hazard structural: once decisions 5 to 7 land, the per-row helpers have no runtime caller, and leaving a per-row API on the loop invites the next caller back onto it. The project is pre-release, so `__all__` carries no compatibility promise. Every count in decision 12 matches `rg` exactly (probe 1). The uncounted mentions are internal to `glob.py` (its module docstring example at `glob.py:21-22`, which the Design rewrites, and the methods themselves) and the Markdown in the ranking corpus fixture, which criterion 14 does not read because it greps `src` only. No test pins `vfs.pattern_matching.__all__`.
5. **Are decision 9's truncation semantics right for glob, and consistent with grep and glean?** READ, INFERRED. Yes. Dropping an unjudged row is the only safe answer, because an unjudged row may match an exclusion, and storage grep already drops a body it did not verify (`grep.py:325-371`). One warning per call that names the cause, with no rows invented, is Article 2's bounded-output rule. Applying `max_count` after the law and keeping the warning whatever `max_count` is matches today's silent cut (`reads.py:381-382`, `base.py:3301-3311`) and is honest, since a missing row may sort first. Two consistency gaps remain. Glean's existing site at `glean.py:357-358` appends its wall record without checking for one already present, so with a second site the call can carry two records, against the decision's "once" (L6). And a fan-out carries one record per entry that reached its wall plus the router's own, which the spec should say rather than leave a reader to infer from "once" (L8).

## Scale and the production posture

- Rows per hop: one hop per stage carries every row of that stage, which the stage already holds (chained rows in hand, storage glob's materialized candidates, grep's candidates under `CANDIDATE_BUDGET`, glean's nominees under `OVERLAY_BUDGET`); no new copy beyond a string pair and a word a row (READ).
- Programs per set: one per distinct pattern, growing with the caller's patterns and, at storage, with roots × arms; built once per call instead of per row per arm at the probe and per root per glob per entry at the admissions; the residency is today's (question 3, L9) (READ, INFERRED).
- The wall: checked before each row and never during a build or inside a row's group loop, so a hop's overrun is one row's programs per thread plus the whole build, both of which grow without bound in the caller's pattern count (H1) (EXECUTED).
- The verdict word: 64 groups, fixed at three by the call sites, never by input; a type width, not a scale cap (READ).
- Planning on the loop: roots × arms × bind segments, no wall, named with a direction (M1) (READ, INFERRED).
- SQL: no statement changes, so the engine floor (Oracle's 1,000-element `IN` list, SQL Server's ~2,100 binds) is untouched; the engine legs still run because storage modules change (READ).
- Storage glob still materializes every candidate its prefilter returns, named with keyset paging as the direction; not a finding (READ).
