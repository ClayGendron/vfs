## Decisions, one line each

1. Decision 1, the property: the right property, and stated so a test can hold it, but the table is not complete. Write, edit, mkedge and rmedge act on rows their builders re-read by path after the gate, which the table says they do not (H1, EXECUTED), and the rows a move or copy creates beneath its destination are judged only at the destination root (M3, EXECUTED for copy). Every other mutating path I listed is in scope or out with a reason: the ten `MUTATING_OPS` (`src/vfs/ops.py:64`) are all fenced; the admin verbs and the two membership verbs, the relabel chunks, the rebuild and refresh phases, the lease commits, the render and embed landings run unfenced through `_execute_maintenance`, `_execute_leased` or the system actor, and change no row on a caller's behalf (READ, `backend.py:1414-1429`, `:1067-1084`); the retention arm of sweep is gated at `read_write` over the whole mount (`backend.py:855-857`), so its per-round judgment can refuse only a row that arrived after that gate (READ). Copy's source rows at `read`, the passing slot, is the right rung for a row the verb reads; the owner is immutable after creation (READ, `writes.py:1188-1199`), so "the row's state then" for the owner floor is decidable on every engine; the label is not (L3).
2. Decision 2, the commit point per engine: holds, with one write-in. Postgres at `REPEATABLE READ` raises 40001 for an `ON CONFLICT` or update against a row version its snapshot cannot see (READ, `../postgres/src/backend/executor/nodeModifyTable.c:378-405`, `:2936`), so the snapshot is a legitimate serialization point for writes there, and a revoke committed after it is ordered after the write: the write read nothing the revoke wrote, and the revoke, run by the system actor, reads nothing the write wrote (INFERRED). On every engine whose statements each read the latest commit the fence, as the last statement, sees every rights change committed before it, including on SQL Server under locking `READ COMMITTED`, where a stamp row an uncommitted admin write holds blocks the fence until it commits, and under snapshot `READ COMMITTED` and Oracle, which read what was committed when the statement began (INFERRED from each engine's documented consistency). A change committed between the fence and the commit is ordered after: the two overlapped, and the admin write never sees the verb's uncommitted rows. MariaDB's claim rests on error 1020, which needs `innodb_snapshot_isolation` on (L5).
3. Decision 3, the fence: sound. Every stamp is written only after `bump_revision`, under the admin lock held to commit (READ, `rights.py:983`, `:1028`, `:1099`, `:1127-1147`, `:1162-1178`; `revision.py:53-57`), so stamps take values in commit order and a stamp greater than the opening revision is exactly an admin write that committed after it. The lost-update shape the brief asked about does not arise: a long admin transaction holds the lock throughout, so no admin write can commit with a lower value after one with a higher. A stamp at or below the opening revision belongs to a write that committed before the opening read. The rejected alternatives are argued and rejected for stated reasons.
4. Decision 4, the basis: holds. A caller's ids include its closure groups (READ, `rights.py:377-387`), and a membership write stamps the member whose closure changes, which is in every affected caller's ids (READ, `rights.py:1120-1122`). A widening grant costs one redrive, and two busy callers cannot livelock each other, because a data verb stamps nothing. The "unsettled" rule redrives a cold-cache mutation whenever any admin write anywhere lands inside its compile, which is the sensitivity decision 3 rejected for the mount revision, on the miss path only; it is not costed (L4).
5. Decision 5, the exemptions: the exemption is right, but its reason is false (M1, EXECUTED). A fenced admin write would read its opening revision after its own bump, and the stamps it writes equal that value, so it would never redrive on its own stamps. Nothing reachable by a non-system caller is exempted by accident: the system actor resolves without a read, and the only uncached gate is `_grant_write`'s (READ, `backend.py:1177`, `:1329`).
6. Decision 6, the landing judgment: holds for what it covers. The update has already happened inside the transaction, so a redrive-then-refuse leaves nothing behind: the content row, the version row, the postings and the fs mirror rows are all written by the same session and roll back with it (READ, `writes.py:404-438`). A redrive that then succeeds in memory only because the staged rival vanished is a property of the staging, not of any engine (see criteria). It does not cover a create the plan itself turned into an update (H1), and it contradicts the `Needs` docstring (L1).
7. Decision 7, the topology judgments: holds. Move acts on its collected ids (`topology.py:398-403`), copy on its subtree's ids and their bodies (`:441-477`), and sweep on each round's ids (`trash.py:582-604`), so each judges exactly what it acts on (READ). Delete is the one verb that acts by a predicate, and the spec orders its judgment after the act, as it must. I EXECUTED that the gate's `subtrees` run after the stamp still reads the stamped rows, because `descendant_filter` has no tombstone term (`descent.py:193-202`), and refuses a landed row beyond the caller's rung (`beneath_probe.py`). The sentence that rows "can no longer change before commit" is not true on Postgres `READ COMMITTED`, though the property holds (L2). The rejections of `RETURNING`, a locking read and skipping are sound.

- The hot row: the opening read is a primary-key read of `vfs_meta`, one row, and the fence reads `vfs_principal_revisions` by key. The spec states this, and it is acceptable stated.
- Delete's second walk costs what its gate's walk costs, row for row. EXECUTED: for 2,502 rows owned by `eve` below `read_write`, 3 page statements at the gate and 3 again after the stamp. ## Premortem

The build landed as written and failed six months later. The three most likely stories are these.

1. A soundness hole. On SQL Server, an agent's create overwrote another owner's file. The window was not the arbitration window that criterion 19 stages, but one read earlier: between the gate's read and the write plan's own read of the same path. The plan saw the file, staged a guarded update and wrote it, and no judgment looked, because decision 6 picks only creates that arbitration turned into updates. The fence was sound throughout; what was missing was a judgment over the rows the plan updates. That is H1.
2. A redrive storm. During a membership migration that stamped a large group every few seconds, every named 10,000-file nightly batch in that group exhausted its four attempts and returned `conflict`, about 40 seconds of rolled-back work each. On the first call per caller after a deploy, cold caches combined with any admin write landing inside a compile redrove further. The spec would have needed to cost this and to name the direction, bulk ingest as the system actor or a principal outside the migration. That is L4.
3. A criterion green for the wrong reason. Someone simplified decision 5's exemption, relying on criterion 13 to catch a fenced admin write. Criterion 13 was green because `bob` happened to be uncached in that world, and in production an admin write fenced with a warm cache never redrove, so the guard the mutant row claimed was never there. Criterion 19 was green on SQL Server while H1's window stood open. That is M1 and H1.
