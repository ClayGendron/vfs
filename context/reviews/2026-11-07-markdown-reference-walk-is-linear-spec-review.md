## The author's questions, answered first

1. **Is decision 1's claim that reference nodes never nest, so decoded bytes stay at most the body's length, true of the tree-sitter-md grammar as vfs splices it?** Yes. EXECUTED: probe 4 found 0 nested reference nodes in 150,179, including `[z](`g.md`)` and `[x](<`e.md`>)`, which parse as one destination each with no `code_span` inside, and `[`a.md`](b.md)`, where the span sits in the link text beside the destination. EXECUTED: at d = 16,000 nested images the reference nodes decode 64,000 bytes of a 144,001-byte body, four bytes per destination, because each inner image's destination lies in the outer image's description, not in the outer destination. READ: `tree-sitter-md-0.5.3/bindings/rust/parser.rs`, `move_to_inline_tree`, splices an inline tree only under `inline` and `pipe_table_cell` nodes, so a reference definition's `link_destination` is a block node with no inline tree under it. One qualification for the reason under decision 1: the depth it removes is inline depth as much as block depth. Block nesting stops at 254 levels, where the block scanner aborts (probe 3), but nested images have no such stop: today the walk decodes 2,304,768,004 bytes for that 144,001-byte body (EXECUTED).
2. **Is keeping only the last folded line (decision 2) enough for linear cost, given the walk's real node order?** Yes. INFERRED: the walk is a pre-order over ordered, non-overlapping children, and the inline tree is walked in place of its block `inline` node's children, so reference start bytes never decrease, and a line's references arrive in one run. EXECUTED: probe 4 counted 0 out-of-order nodes and 0 returns to an earlier line, over tables (a row's cells arrive together), reference definitions, nested lists, quotes, lazy continuations, setext and ATX headings, and a code span across a line break (which `path_shaped` refuses anyway, since a newline is not a path character). Each line holding a reference is decoded and folded once.
3. **Does any other per-node or per-reference cost in the walk or in `extract_links` stay superlinear after this spec?** Yes, one, and it is larger than the cost the audit found. READ: `MarkdownCursor::goto_parent` (`tree-sitter-md-0.5.3/bindings/rust/parser.rs`) calls `inline_cursor.node().parent()` after every upward step inside an inline tree, and `ts_node_parent` (`tree-sitter-0.26.13/src/node.c:547-558`) walks down from the tree's root on every call, so one step costs the node's depth. EXECUTED: probe 2 shows the walk quadratic in inline depth (4.0x per doubling) and 56 seconds at 144 KB, with no decoding at all; the cost is in the cursor the Design keeps. Flat bodies do not show it (EXECUTED: 5.2 to 53.6 ms for 5,000 to 40,000 links in one paragraph), because tree-sitter balances long repetitions under hidden nodes. Nothing else stays superlinear. EXECUTED: the parse grows about linearly (38 to 170 ms over 4.5 to 36 KB of nested images; 52 to 416 ms over 5,000 to 40,000 links). READ: `strip_angles` and `path_shaped` are linear in their node; `extract_links` (`src/vfs/models/links.py:72-87`) and `clean_dest` are linear per destination; `link_candidates` is called twice per reference in `src/vfs/storage/backends/database/links.py:111,157`, each linear in one destination. A note on the fix: `TreeCursor::depth` is also not constant-time (it counts the cursor's stack), and my first alternative walk, which called it, was quadratic too (EXECUTED), so the fix keeps its own depth counter.

## Scale and the production posture

- Newline offsets: one `usize` per newline of one body, built per body inside the worker and dropped after it; linear, and bounded by the body (a `u32`, as `crates/vfs-core/src/chunk.rs:123` uses, would halve it; a note, not a finding).
- Folded line: one held at a time; one decode and one fold per line that holds a reference; one decode per reference node; output unchanged, at most 256 characters per reference.
- The walk: grows with the sum of node depths in inline trees while it keeps `MarkdownCursor`, quadratic in the body for nested images (H1). With a cursor per tree and its own depth counter it is linear.
- A 10,000-body batch: unchanged; bodies parse in parallel with one parser per worker, and nothing is held across bodies. No SQL, no statement, no engine floor is touched.

## Findings, most severe first

1. **H1. The walk keeps `MarkdownCursor`, whose upward step costs the node's depth, so the walk stays quadratic** ([Design](../specifications/active/2026-11-07-markdown-reference-walk-is-linear.md#design), [Intent](../specifications/active/2026-11-07-markdown-reference-walk-is-linear.md#intent)) — `walk` "holding today's cursor loop" keeps `tree.walk()`, a `MarkdownCursor`, whose `goto_parent` calls `Node::parent`, which descends from the root on each call (`tree-sitter-0.26.13/src/node.c:547-558`). Consequence if built: 144,001 bytes of nested images cost 56,034 ms in the walk alone, against 10.8 ms for a linear walk over the same 144,004 nodes (EXECUTED, probe 2); the reindex still holds the writer lock for that time, the Intent's "linear in the body" is false, and `WalkCost` cannot see it. Fix text, for Decisions as a new decision 2 with the rest renumbered: "The walk does not use `MarkdownCursor`: it walks the block tree with a `tree_sitter::TreeCursor` and, at each node for which `MarkdownTree::inline_tree(&node)` returns a tree, walks that tree with its own `TreeCursor` in place of the node's block children, keeping its own depth counter. It never calls `Node::parent` or `TreeCursor::depth`, because both cost the node's depth: tree-sitter's `ts_node_parent` walks down from the root, and `MarkdownCursor::goto_parent` calls it on every upward step in an inline tree, which makes a body of nested images quadratic.
