## Findings, most severe first

**M1 (Security, confirmed, low; Adversarial, executed) — posture writes made in a loop on one folder keep every batch that creates rows from landing anywhere on the mount, the system actor's included, for as long as the loop runs.** Where: `src/vfs/storage/backends/database/labels.py:243` to `:257` (the hold compares one stamp for the whole mount), `src/vfs/storage/backends/database/authorized.py:235` (it runs for the system actor), `src/vfs/ops.py:162` (`"posture": Needs("read_write")`). The defect: decision 13 declares the outcome for a batch that meets a posture write in each of its four attempts and flags it to the developer, but costs it at "an admin act at human rate", which `AGENTS.md` marks an assumption. The rate is the posture writer's own. Who can be that writer: `posture` is a developer-plane verb, on no agent-facing surface (READ, `src/vfs/ops.py:97` to `:100`), so it is the host's code, under whatever authority the host passes, and the storage layer admits any authority with `read_write` at the path. What I ran: `probe_posture_loop.py`, on the test containers with dummy principals: `bob`, granted `read_write` on `/p`, flips the posture of `/p/d/sub` between `none` and `read` in a loop; the system actor writes 2,000 new files under `/ingest`, a folder `bob` holds nothing on, three calls in a row. What I saw on Postgres: all three calls ended in the retryable `conflict` with nothing written, with 32, 28 and 26 posture writes beside them; on Oracle the same, with 21, 15 and 19, and the detail "a posture changed while it ran". The same probe on Postgres against a scratch copy with the hold removed: the batch landed on its first call. So the effect is this change's, for the system actor; a named caller's batch already met it through the fence. Nothing is exposed and nothing is torn: the damage is availability, of the bulk-ingest contract. It needs no malice: a host script that sets the posture of many folders one call at a time is such a loop, and so is a host that lets its users toggle a folder's posture. What closes it: a bound in the code with its node (a batch that lands while postures are written in a loop elsewhere on the mount), or a Disposition line carrying the developer's ruling that the unreleased tree accepts it, with decision 13 and the `labels.py` paragraph amended to say whose rate it is. Text for that amendment: "The rate is the posture writer's: the host's code may write a posture under any authority holding `read_write` on a folder, and each write redrives every mint in flight on the mount; a batch that meets one in each of its attempts lands nothing, so a host that sets many postures does it outside its ingest window. A stamp per posture path, set aside here, is the direction if that rate is ever a tenant's."
