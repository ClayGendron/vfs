## The author's questions, answered first

1. **Is chunking the pairs at half the membership budget the right bound for the tuple membership on every engine that declares `tuple_in`, Oracle's `IN`-list cap included?** Yes, and it is conservative. A statement carries `1 + 2 × pairs` binds, and `pairs ≤ membership_budget // 2`, so its binds are at most `membership_budget + 1`; `membership_budget` is `min(in_list_budget, parameter_budget - 32)` (`dialects.py:671-678`, READ), so every statement sits 31 binds inside the parameter budget on every engine. On SQLite the budget is 32,668, so a statement carries 16,334 pairs and 32,669 binds; EXECUTED on both CI SQLite versions against the statistics store, every row returned (`big.py`), and a multi-row `VALUES` is not subject to SQLite's compound-select limit. On Oracle the membership budget is 1,000, so a statement carries 500 pairs; Oracle's ORA-01795 cap counts the expressions of a single-column list, and a list of expression sets may hold any number of sets of at most 1,000 expressions each (INFERRED from Oracle's documented rule, not run here), so 500 two-element sets are well inside it. PostgreSQL and MariaDB declare 65,535 and are bounded by binds, as above. The bound is the same one `indexing.py:694-697` already ships (READ). What the bound does not settle is the plan the server engines give the form, which is M1.
2. **If the harness driver calls the leg's own builder, does the harness remain an independent referee of the leg, or does it lose something?** It remains the referee, because the referee was never the driver's copy of the arms: it is the recorded golden file. `assert_top10_pin` compares both the driver's ordering and the verb's ordering to `TOP10` on disk (`tests/ranking/pins.py:66-83`, READ). The driver's mirror shared the defect, so it refereed nothing about the fetch's spelling; the pins went red because both sides lost the same blocks against the recorded file (READ in the spec, consistent with `probe1.py`, EXECUTED). What the driver keeps independent is everything around the fetch: its own head fetch, its own scoring call without the scope ladder, the overlay or fusion, and its own MaxP (`driver.py:116-182`, READ). What the harness loses is a second spelling that a builder defect would have to fool as well; a defect in the builder's chunking (a pair dropped at a chunk boundary) now hits both sides, and the golden corpus never reaches a boundary, since q09 sends 7 pairs against a 16,334-pair chunk (INFERRED). The builder's chunking therefore needs its own pin at a small budget, which criterion 2 provides at compile level; L3's fix text makes it count pairs too.
3. **Should the focused pin gather statistics by hand, given the statistics spec that gathers them lands after this one?** Yes. At `79752e7` nothing in `src/` runs `ANALYZE` (READ in the statistics spec's problem section), and the defect needs `sqlite_stat1` rows, so without a hand `ANALYZE` the pin cannot be red on the unfixed leg. A first `ANALYZE` creates `sqlite_stat1`, which is a schema change, so a pooled connection already open reloads the statistics at its next statement (EXECUTED, `twoconn.py`); the hand step is therefore deterministic at this landing. The hand step should stay after the statistics spec lands, for a reason beyond harmlessness: that spec gathers statistics in a background pass, so without the hand step the pin's state would depend on when the pass finished. The statistics spec's decision 19 drops the hand `ANALYZE` from other plan pins; these pins should not follow, and L6's fix text says so. The hand step alone is not enough, though: the corpus the spec gives the pin does not trigger the defect, which is H1.
