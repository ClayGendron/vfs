## Scale and the production posture

- The comparison: one membership test in memory per asked chunk id, at most `limit` entries' carried chunks; no statement (EXECUTED: 8 with it and 8 without). The seam is one no-op await. Nothing grows with input.
- The redrive is bounded at `retry_attempts` (4), with sleeps of at most about 0.35 seconds in all at the default base. INFERRED, no livelock: a redrive needs a rival commit inside one call's window, ids are never reused (identity columns), and a chunk pass commits once per run as one transaction, so the same chunk cannot be chosen twice. Exhausting needs four distinct commits in four successive windows of one call, and even then it leaves as a classified retryable `conflict` (EXECUTED).
- The re-dirty `UPDATE` stays one statement over the rows it matches, with one bind more; no `IN` list and no batch growth. On a bump it already rewrites every content row once, so the extra column adds no row.
- The reference deployment, the brief's main question. A chunk-generation bump is not rare: `CHUNK_GENERATION` is "bumped deliberately when a grammar crate or walker change alters chunk shapes" (`chunking.py:174-176`, READ), so a vfs upgrade that moves a grammar crate re-splits every store whole. The chunk pass is one writer transaction (`backend.py:1198-1199`, READ). From its commit until the publish, the build runs over 10,000,000 files and about 100,000,000 chunks, which is hours. Today, on a busy store where other rows are pending, that same run already rebuilds and publishes (EXECUTED); the stranded-forever state is a quiet store's. So the honest comparison is that window. Today, search raises `KeyError` on every call whose answer has a lexical hit, and grep is whole, served by the gram index. On the build, search does not raise, but its lexical leg is empty (`_entries_for_chunks` requires `encoded`, `search.py:688`), and the vector leg is mostly empty too, because re-split chunks whose text changed carry no embedding until the embed step after publish (`indexing.py:294-298`, `backend.py:1213-1215`, READ). Search therefore answers from the overlay. So does grep, because its index side also requires `encoded` (`grep.py:577`, READ). Each verb nominates the first 25,000 `NOT encoded` rows in path order (`scope.py:72`) and reads their bodies up to the 10-second wall. That is about 0.25 percent of the corpus, chosen by path and not by match. Each call costs up to 25,000 body reads in place of a few index fetches, and Article 5's "cost is part of the contract" says that cost is part of the answer's contract. EXECUTED, with the budget lowered to 5 over 21 files: a selective search and a selective grep both answered nothing, each with a truncation record. Today grep found both files and search raised. At about 150,000 verb calls a day, with reads, lists, globs and greps about three to every write and search under a tenth, a window of hours means tens of thousands of grep and search calls in the window. Each gets a truncated answer, and that includes grep, which has no defect today. H1 names the design I would sign. It keeps grep whole and search ranked from the published epoch for the whole window, and its build cost is the same: one whole rebuild per bump. EXECUTED as a prototype on the same store, both verbs answered both files during the run, and the run published with 0 stranded ids.
