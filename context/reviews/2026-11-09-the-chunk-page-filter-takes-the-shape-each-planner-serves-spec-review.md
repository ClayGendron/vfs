## The author's questions, answered first

1. **Is a correlated scalar subquery compared to a constant a shape SQLite's planner will keep leaving alone across the versions the project supports, or does the spec rest on one version's planner?** READ in the clone at 3.54.0: the only rewrite SQLite applies to a WHERE-clause subquery is EXISTS-to-JOIN (`src/select.c:7371`), which matches a `TK_EXISTS` node only, and only when the outer statement has no OFFSET (`p->pLimit->pRight==0`); the spec's shape is a `TK_EQ` over a `TK_SELECT`, outside that pattern, and EXECUTED SQLAlchemy's SQLite compiler renders every page as `LIMIT ? OFFSET ?`, so even the EXISTS form would be exempt in the live statement. The Bloom filter itself (`where.c:6622`) is a join-loop decision that a scalar subquery never enters. So the spec rests on the absence of a rewrite for this expression class, not on one version's heuristic. EXECUTED on 3.50.4: the probe's plan is the same with and without chunk statistics and with literal or `?` binds, where the shipped join's plan changes three ways with the statistics (no statistics: entries outer with a temp B-tree sort per page; statistics at up to 4 chunks per entry: a plain nested loop; above about 5 chunks per entry: the Bloom filter). INFERRED across the supported range: below 3.38 there is no Bloom filter and both shapes are a nested loop; from 3.38 to 3.45 the filter exists but vfs's statistics step issues nothing (READ `test_below_sqlite_3_46_the_step_issues_nothing`), so a store there has the no-statistics plan, which the probe also beats; from 3.46 the measured case holds. The risk that remains is a future rewrite of this class, and the plan pin of criterion 3 is the right detector, once it runs on a store where the shipped join does plan the filter (M1).
2. **Does declaring the probe on SQLite only respect the "never assume SQLite" rule, or does it hide the same quadratic cost on an engine the research did not measure?** READ [AGENTS.md](../../AGENTS.md) "Production posture": the rule forbids designing to SQLite's limits and treating SQLite as the target; a per-dialect spelling declared on `DialectProfile` for a decision SQLAlchemy takes no position on is the pattern `rarity_hint`, `scope_facts_beside_fan` and `range_join` already follow (READ `dialects.py:424`, `:477-480`). The cost is a SQLite planner artefact, a filter constructed behind `OP_Once` on every execution, and the one other engine measured does not share it (study 03 section 5: a memoized nested loop, no filter, the probe a JIT regression). The join is the conservative default for the three unmeasured engines and the generic floor: a join is what every cost-based planner optimizes, a correlated scalar subquery is what some punish. The cost is not hidden so long as the engine legs read the plans, which criterion 4 names, but as written it counts nothing on those three engines (L2); the spec should name the operator that would flip each profile, a per-execution hash or bitmap build on the entry side, so the recorded plans are judged and not only filed.
3. **Is moving `select_unembedded`'s refusal `NOT EXISTS` onto the shared builder as a chunk-side term a behaviour change for the embed step in any case the existing tests do not pin?** EXECUTED: no. With an orphan chunk, a chunk whose `content_hash` is NULL, a refused twin, a deleted entry, a non-chunked entry, a non-indexable entry and an embedded chunk added to the text store, the join form and the probe form of the embed page select the same 10,997 ids in the same order (and the build's two forms the same 10,998). INFERRED why: an inner join on a unique key and `(SELECT 1 … WHERE key = chunk.key AND terms) = 1` are the same predicate, a missing or non-qualifying entry giving `NULL = 1`, not true; the refusal term correlates to the chunk row's own hash and is already evaluated once per chunk row in both forms (EXECUTED: the same `CORRELATED SCALAR SUBQUERY` line on `sqlite_autoindex_vfs_embed_refusals_1` appears in both plans), and a NULL hash makes it false in both. `count_unembedded` and `count_refused` keep the join (`embed.py:_count_null`) and their predicate equals the page's, so the `unembedded` count and the pages agree as today. The orphan-chunk and NULL-hash cases are the ones no existing test pins, and they behave the same.
