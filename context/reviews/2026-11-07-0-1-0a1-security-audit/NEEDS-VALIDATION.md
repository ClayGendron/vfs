## 1. PyPI trusted-publishing upload is gated in source only by writer-editable workflow logic; whether a writer without release authority can publish depends on unobserved `pypi` environment, tag and PyPI publisher settings

**Fingerprint:** `publish.yml:release-ref-not-bound-to-main-environment-pypi`

publish.yml uploads to PyPI with OIDC trusted publishing whenever a GitHub release is published (publish.yml:13-16, 86-92, 130-131). The only gate visible in source is scripts/check_release_tag.py. It compares the tag string with the [project] version in the checked-out pyproject.toml, and nothing else (check_release_tag.py:36-39). It reads no git state, so it cannot check the tagged commit's ancestry, signer or creator. Nothing in the workflow binds the tagged commit to main, although release.md:133 says the release creates the tag on main. Take a principal who has write access but no release authority: a collaborator, an installed app, or a stolen writer token. On GitHub the write role can create releases. That principal could push a side branch whose code is modified and whose version line matches, then publish a release on a tag pointing at that branch. The workflow would check out the tag's commit, pass the tag check, build it, and upload it as vfs-py. The `if: github.event_name == 'release'` guard on the publish job (publish.yml:87) and the tag-check steps are read from the workflow file at the triggering ref, so a writer also controls them on their own branch. Only hosted controls decide whether the upload can happen: protection rules on the `pypi` environment (required reviewers, deployment branch and tag policy), tag rulesets for v*, branch protection on main, the collaborator and app list, and the PyPI trusted-publisher record. None of these is in source. The repository does not record them either: the roadmap audit (07-release-ci-and-repo-hygiene.md:106) and spec 166 criterion 12 list the trusted-publisher check as a pending item, and release.md has no such note yet. Fork and PR contributors cannot reach this path. publish.yml has no pull_request, pull_request_target or workflow_run trigger, and both releasing and dispatching need write access. The prior code review (2026-11-06-the-release-lane-to-0-1-0-code-review.md:73-75) also found no lower-trust principal below a repository writer. Whether any writer who lacks release authority exists is the deciding fact.

### Claimed root cause

Inside the workflow, the release's source identity (the tagged commit and the triggering ref) is never bound to reviewed main. The only in-source gate is a string comparison between the tag and the version, and it reads only pyproject.toml. The `pypi` environment's protection rules and the PyPI trusted-publisher record are the only controls that could bind the release to a release owner and an approved ref, and neither is in source.

### Trace

1. **entrypoint** `.github/workflows/publish.yml:13` `on: release published / workflow_dispatch`: Anyone who can publish a release, or dispatch the workflow on any ref, starts the run. Both need write access. Neither event is restricted to main or to a tag pattern in source.
2. **propagation** `.github/workflows/publish.yml:32` `wheels job checkout`: actions/checkout with no ref checks out GITHUB_SHA: the release tag's commit, or the dispatched ref. That commit need not be reachable from main.
3. **propagation** `.github/workflows/publish.yml:46` `tag check step (also :74 sdist, :106 publish)`: Runs scripts/check_release_tag.py "$TAG", with the tag passed through env and quoted. This is the only source gate before the build and the upload.
4. **propagation** `scripts/check_release_tag.py:38` `main`: Returns 0 when tag == 'v' + the version in the checked-out pyproject.toml. It reads no git state: no ancestry from main, no signer, no tag creator.
5. **propagation** `.github/workflows/publish.yml:48` `maturin-action build (sdist at :76)`: Builds the wheels, and at :76 the sdist, from the checked-out commit's code.
6. **propagation** `.github/workflows/publish.yml:87` `publish job`: Runs with `if: github.event_name == 'release'`, environment pypi and permission id-token: write. The guard comes from the workflow file at the triggering ref, which a writer can edit on their own branch.
7. **sink** `.github/workflows/publish.yml:131` `Publish to PyPI`: `uv publish --trusted-publishing always` mints a PyPI upload token from the job's OIDC identity and uploads dist/ as vfs-py.

### Evidence

- `context/standards/release.md:47`: 'The workflow runs no tests. It trusts main is green.' The publish path assumes its source is main and never checks it. The tag check is named as its only gate.

## 2. A write, move or copy that read the everyone posture before a tightening posture commit can stamp the old, more open everyone_level after the relabel has cleared its mark

**Fingerprint:** `vfs/storage/database/labels:mint-reads-posture-outside-revision-lock-stale-everyone-level`

entries.everyone_level is a derived copy of the deepest everyone ('*') posture on a row's path. Once no relabel mark stands over a path, Rights.admits trusts the stored label outright. Posture writes take the admin lock with bump_revision, and every Relabeller chunk takes it with hold_revision. The mint paths take neither. write and mkdir call labels_for at writes.py:379, and move and copy call posture_beneath at topology.py:197. Both read the grants rows with plain SELECTs and never re-check the relabels table. Here is the interleaving. A write W pins its snapshot at its first statement, because op_isolation is REPEATABLE READ on Postgres and MariaDB. A posture commit P then tightens /eng/secret.md to none. The path need not hold a row, per _grant_refusal at rights.py:1318. P's Relabeller runs and clears the mark while W is still open. It cannot see W's uncommitted insert. When the posture sits at the created path, it rewrites 0 rows. W then commits with the old label. After that, any named principal with no grant can read the row, and anonymous grep and glob list it. Nothing in src corrects the label: rebuild_labels has no caller there. I re-ran the hunter's consequence emulation on SQLite in the sandbox: the mint is handed the labels that the real labels_for and posture_beneath computed before the posture commit. Results with no pending marks: write, move and copy stamp everyone_level=2 under posture none. bob (no grants) reads 'TOPSECRET payroll'. Anonymous and bob grep and glob list /eng/secret.md. Anonymous direct read stays refused (unauthenticated). bob's overwrite stays refused, because read is below the write rung. The control with fresh labels gives label 0 and not_found. rebuild_labels repairs the label. The real interleaving cannot happen on SQLite, because writers hold BEGIN IMMEDIATE. So the decisive concurrent behaviour on a real engine has not been observed. The spec that introduced the label (context/specifications/archive/150-rights-at-scale/spec.md) analyses rival admin writes, but not a concurrent mint against a relabel.

### Claimed root cause

labels_for (labels.py:124, reading posture_rows at labels.py:110-121) and posture_beneath (labels.py:139) read the everyone posture rows without the admin revision lock (no hold_revision, nothing that conflicts with bump_revision) and without consulting inflight relabel marks. The Relabeller (labels.py:244-266) rewrites only rows visible to its own statements, then deletes the mark. A mint whose posture read predates a posture commit, and which commits after that posture's relabel has passed its path, therefore stamps a stale label that no mark covers. readers then trust it (grants.py:491).

### Trace

1. **entrypoint** `src/vfs/storage/backends/database/backend.py:686` `DatabaseStorage.write`: The write verb, called by a named principal holding write rights (alice), runs its plan through _execute_write (backend.py:1666-1673) with op_execution_options(writer=True). On Postgres and MariaDB that stamps isolation_level REPEATABLE READ (dialects.py:593-594), so the snapshot is pinned at the first statement.
2. **propagation** `src/vfs/storage/backends/database/writes.py:379` `_apply`: labels_for is called for the creates after staging. Nothing in writes.py takes hold_revision or bump_revision, issues a locking read, or reads the relabels table.
3. **propagation** `src/vfs/storage/backends/database/labels.py:117` `posture_rows`: A plain SELECT of the '*' grants rows over the ancestor prefixes. Under W's pinned snapshot it returns the posture as it stood before a concurrent posture commit.
4. **propagation** `src/vfs/storage/backends/database/topology.py:197` `transfer_rows`: Move and copy compute posture_beneath with the same unlocked read, after the serialize() lock-table point (topology.py:143), which is not the revision lock. They stamp the result at topology.py:315 (moved root), 373 (descendants) and 453 (copied rows), under topology_isolation READ COMMITTED.
5. **propagation** `src/vfs/storage/backends/database/rights.py:1034` `set_posture`: The posture write upserts the '*' row and plants the relabel mark in one transaction, after bump_revision (backend.py:1594). _grant_refusal (rights.py:1318) lets the path hold no row, so a posture can be set at a path a concurrent write is creating.
6. **propagation** `src/vfs/storage/backends/database/labels.py:248` `Relabeller.step`: Each chunk takes hold_revision and rewrites the rows its statements see. It cannot see W's uncommitted rows; for a posture at a not-yet-existing path it rewrites 0 rows (observed: relabel rows=0). The last chunk deletes the mark and bumps the revision (labels.py:265-266).
7. **sink** `src/vfs/storage/grants.py:491` `Rights.admits`: With no hole standing (the mark is gone), a row whose stored everyone_level reaches the needed rung is admitted. Named callers' reads, and grep and glob for anonymous and named callers alike, then admit the stale-labelled row.

### Evidence

- `src/vfs/storage/backends/database/labels.py:1`: The module docstring says the label is derived, stamped at every mint from the posture rows, and covered by the mark only while the relabel is in flight. Nothing ties the mint's read to the lock that orders posture commits.
- `src/vfs/storage/backends/database/revision.py:60`: hold_revision is the admin lock that relabel chunks take, so they serialize behind rival admin writes. The mint paths take neither it nor bump_revision (no revision import in writes.py or topology.py).
- `src/vfs/storage/backends/database/dialects.py:436`: Postgres declares op_isolation REPEATABLE READ, and MariaDB does the same at line 500. op_execution_options (line 582) applies it to writer connections, so the write's posture read comes from its first statement's snapshot.
- `src/vfs/storage/backends/database/rights.py:389`: The strongest visible control. unauthenticated_at judges anonymous path-addressed calls from the posture rows, not the label, so an anonymous direct read stays refused (observed). Named callers and the anonymous list and search verbs still trust the label.
- `src/vfs/storage/backends/database/engine.py:654`: On SQLite, writers open BEGIN IMMEDIATE, so a posture commit cannot land inside a write's window. That is why the real interleaving cannot be observed locally.
- `context/specifications/archive/150-rights-at-scale/spec.md:74`: The in-flight rule covers stale labels only while the mark stands. The spec's race analysis (line 242) covers rival admin writes, not a mint that is concurrent with a relabel.
- `agents/v12-p3/artifacts/evidence/stale-label-rerun.json:1`: My sandboxed SQLite re-run of the hunter's consequence emulation. Fresh-label control: label 0, bob not_found. Mint given the pre-commit posture read: everyone_level=2 under posture none with no marks. bob reads TOPSECRET content, and anonymous grep and glob list the path. Anonymous direct read and bob's overwrite stay refused. rebuild_labels resets the label to 0. The relabel rewrote 0 rows for the posture at the created path.

### Blockers

- The decisive concurrent interleaving cannot happen on SQLite. Writers hold BEGIN IMMEDIATE from the plan's first read (engine.py:649-655), and a deferred SQLite reader could not upgrade a stale snapshot to a write anyway. Real engines (Postgres, MariaDB, SQL Server, Oracle) and Docker are prohibited in this sandbox. Only the consequence was observed, by handing the mint its pre-commit posture read.
- Postgres REPEATABLE READ: the source predicts that a posture at the created path, or at a directory the same batch creates, leaves W's existing parent outside the relabelled region. Then no 40001 conflict arises and W commits the stale label. Where the posture covers an existing parent, the relabel rewrites that parent, so W's guarded parent bump (_bump_parents, writes.py:1026) should fail with a serialization error and redrive. Neither outcome has been observed on a live engine.
- MariaDB: whether innodb_snapshot_isolation (ON by default from 11.6, error 1020) turns the parent bump into a restart, and whether a Relabeller range UPDATE (a current read) blocks on a concurrently moved row's uncommitted index entry and then relabels it, are both unobserved.
- SQL Server (no op_isolation): under locking READ COMMITTED, the relabel UPDATE may block on W's uncommitted key and then relabel it, which narrows the window to the gap between labels_for and the insert. Under READ_COMMITTED_SNAPSHOT it would skip the row. Which mode a deployment runs is a database setting outside source.
- Oracle: the statement-level consistent read in the relabel UPDATE is expected to skip uncommitted inserted or moved rows, leaving the window open from labels_for or posture_beneath to commit. Unobserved.

## 3. copy, sweep, delete and move check rights over a subtree once, then act on rows read later, including rows a concurrent writer just added

**Fingerprint:** `vfs/storage/database/topology-subtree-authorized-before-collection`

The topology and trash verbs check the caller's rights over the source subtree once, inside the gate (WriteGate.subtrees). That check reads the rows beneath the root as they exist at that moment. The later statements read the subtree again, live, and act on whatever they find. Copy and move fetch the subtree with _fetch_subtree and _descendant_rewrites. Delete marks every live descendant with one LIKE update. The sweep purge loops its select-then-delete until the scope reads empty. Nothing checks the rows found by these later reads. The serialization point only makes serialized verbs wait for each other. Ordinary writes never read the lock row. On the server engines the topology transaction runs at READ COMMITTED, so every statement sees rows committed after the gate. Example: alice holds rights over /team/alice only through the owner floor, and bob holds add there. If bob's file commits inside the window, alice's copy duplicates it into /mine/c, owned by alice with the destination label, and alice can then read a file the read verb hides from her. Alice's sweep in the same window permanently destroys bob's file. Run one after the other, both calls are permission_denied. Some guards narrow the window, though they do not close it. In move and delete, a direct child that commits after the snapshot bumps the root's version, so the root claim misses and the verb redrives, which re-runs the gate. That guard does not cover the window between the gate and the snapshot. It also misses a deeper descendant, whose write bumps only its own parent. Copy and the sweep purge arm have no root guard at all. In the sweep, the rival does not even need precise timing: the purge's delete of the root waits on the rival's parent-bump row lock, and the re-collect loop then finds the rival's row and deletes it. The repository's own threat model (T57 in context/research/2026-09-05-permissions-framing-threat-model-and-requirements.md) says check and act must happen in one statement or one transaction, with the write's own predicate as the check. Here the check and the act share a transaction, but under READ COMMITTED the act's predicate is not the check. I re-ran this independently. The rival write was injected at the repository's own seams (transfer:post-snapshot and purge:post-collect) on the verb's own session. With it, alice's copy succeeded and she read 'BOB SECRET' from /mine/c/s.txt, and alice's sweep succeeded and bob's file was gone. The sequential controls were permission_denied. This simulates READ COMMITTED visibility; it is not a commit from a second connection. Likely fix: inside the mutation, judge every collected row with resolution.at(rung).admits(path, owner_id, everyone_level), and refuse or redrive on a miss. That covers copy's subtree, move's descendant rewrites, delete's descendant stamp (as a RETURNING set or a pre-stamp select), and each purge collect. Another option is to make child creation take a shared lock that conflicts with the serialization row.

### Claimed root cause

The authorization decision (WriteGate.subtrees, rights.py:730-761, paging through _refused_beneath at rights.py:763-780) runs over a point-in-time read. The scope the mutation acts on is collected again afterwards by path pattern: topology.py:186 (_fetch_subtree, copy and move), topology.py:397 (_descendant_rewrites, move), trash.py:483 (_tombstone_descendants, delete) and trash.py:567 (the _purge collect loop, sweep). Rows found by these later reads are never judged. Ordinary writes do not serialize with these verbs (serialized.py:115-123). The topology connection is pinned to READ COMMITTED on PostgreSQL and MariaDB (dialects.py:437, 503). MSSQL and Oracle declare no pin, so they run at their engine default of READ COMMITTED (dialects.py:607-609). Each later statement therefore sees rows committed after the gate.

### Trace

1. **entrypoint** `src/vfs/storage/backends/database/backend.py:1692` `DatabaseStorage._execute_transfer.gate`: A named lower-trust caller's copy or move source is authorized by checks.subtrees(sources, passing) at read or read_write. delete (backend.py:763) and sweep (backend.py:862) make the same subtree call at read_write.
2. **propagation** `src/vfs/storage/backends/database/rights.py:763` `WriteGate._refused_beneath`: Pages through the rows beneath the root that exist when this statement runs, and checks each with rights.admits. A row committed afterwards is never judged.
3. **propagation** `src/vfs/storage/backends/database/serialized.py:123` `serialize`: A locking read of the single lock row. Its docstring (line 117) says nothing else reads that row, so ordinary writes commit concurrently with copy, move, delete and sweep.
4. **propagation** `src/vfs/storage/backends/database/topology.py:186` `transfer_rows`: After the gate and the per-pair checks, the source subtree is read again live through subtree_filter. Under READ COMMITTED it includes a rival's newly committed rows. Copy takes no lock or version guard on the source root.
5. **propagation** `src/vfs/storage/backends/database/trash.py:567` `_purge`: The sweep purge arm repeats collect-then-delete until the scope reads empty, which is meant to catch late children. It hard-deletes them with no rights check and no proof predicate (trash.py:381).
6. **sink** `src/vfs/storage/backends/database/topology.py:452` `_execute_copy`: Every collected row, the rival's included, is minted at the destination with owner_id = owner_for(authority) and the destination posture label (line 453). _copy_bodies (topology.py:483-517) then copies its body, so the copier owns a readable duplicate.

### Evidence

- `src/vfs/storage/backends/database/trash.py:483`: _tombstone_descendants marks every live row under the claimed directory. Its docstring says a child a rival landed after the snapshot rides with its parent. The root version guard (trash.py:200-202) catches only a direct child that commits after the snapshot; a deeper descendant, or any child in the gate-to-snapshot window, is tombstoned without being judged.
- `src/vfs/storage/backends/database/trash.py:381`: The sweep purge arm calls _purge with subtree_filter and no proof. The _purge docstring (trash.py:551-554) says writes are not serialized with this verb and the loop exists to catch a rival's new child.
- `src/vfs/storage/backends/database/topology.py:397`: Move rewrites the descendants it collects live after the root claim. A late deeper descendant is relocated to the destination and takes the destination's label without being judged.
- `src/vfs/storage/backends/database/dialects.py:437`: PostgreSQL topology_isolation is READ COMMITTED. MariaDB matches at line 503, and topology_execution_options (dialects.py:598-610) leaves MSSQL and Oracle on their READ COMMITTED default. Each statement sees rows committed after the gate.
- `src/vfs/storage/backends/database/rights.py:754`: subtrees skips the read only when the caller's rights cover the subtree whole. The gap opens exactly where rights are partial: an owner floor, or a posture that narrows a region.
- `src/vfs/storage/backends/database/writes.py:1026`: _bump_parents: a write bumps only its immediate parent's version. So a root version guard sees only direct-child arrivals, and copy and sweep check no root version at all.
- `agents/v13-p3/artifacts/evidence/seam-race.txt:1`: Verifier's independent run on InMemoryStorage. Bob's legitimate write is injected at the repository's own seams on the verb's session. Controls: alice cannot read bob's file, and her sequential copy and sweep are permission_denied. Raced: the copy succeeds and alice reads 'BOB SECRET' from /mine/c/s.txt; the sweep succeeds and bob's file is gone.

### Blockers

- The decisive interleaving needs a real commit from a second connection on a server engine (PostgreSQL, MSSQL, MariaDB or Oracle) during the verb's transaction. This sandbox allows only SQLite and InMemoryStorage. There, topology verbs open BEGIN IMMEDIATE and hold the database write lock, so a second writer cannot commit inside the window.
- The local evidence (the hunter's and mine) injects the rival write on the victim verb's own session at the repository's seams. That simulates READ COMMITTED statement visibility. It is not an observed concurrent commit, so lock interactions on a real engine are unobserved: for example, whether the copy's later body read or the sweep's delete blocks on or conflicts with the rival's parent-bump row lock in a way that forces a redrive.

## 4. A write the gate judged as a fresh create (add rung) can overwrite a rival's concurrently created file through catch_retry insert arbitration

**Fingerprint:** `vfs/storage/database/write-arbitration-absorb-without-reauthorization`

DatabaseStorage.write gates every target in upsert mode before it stages anything. A path that is absent at the gate is judged only at the create rung (add). The ops.py ladder says add 'alters only one's own rows' and that overwriting anyone else's row needs contribute. If another principal (bob) commits a create of the same path inside the gate-to-apply window (the declared write:before-apply seam), alice's insert hits the unique (parent_id, name) index. On catch_retry engines (MSSQL, Oracle and the GENERIC floor used for unknown dialects), _resolve_rows probes the occupant, finds bob's non-directory row at the same path and, because overwrite defaults to True, calls staged.absorb. That turns alice's create into an unguarded clobbering update of bob's row. The update checks only entry_id, path and liveness, and no rights check runs again. Alice's body replaces bob's. owner_id stays bob's, and bob's earlier body goes to vfs_versions. When the same overwrite runs sequentially, it is refused with permission_denied. No isolation pin covers MSSQL, Oracle or GENERIC (op_isolation is None), so their statements run at the server default READ COMMITTED. Under READ COMMITTED each statement sees rows already committed. That holds for both MSSQL modes (locking and RCSI) and for Oracle's statement-level consistency, so the probe sees bob's committed row. The engines that are probably not affected are these. SQLite: BEGIN IMMEDIATE takes the write lock at alice's first read, so no rival can commit inside the window. PostgreSQL: the REPEATABLE READ pin makes ON CONFLICT DO UPDATE against a row the snapshot cannot see raise 40001, which is retryable; the whole method then runs again, and the gate judges the occupied path at contribute. MariaDB: the REPEATABLE READ snapshot hides bob's row from the probe, so it raises StaleSnapshot and the method runs again. I reproduced this myself on SQLite. I used the real write:before-apply seam and injected bob's create on alice's own session, the way a READ COMMITTED statement would observe it. Sequentially, alice was permission_denied. In the race, alice succeeded and both a system read and bob's own read returned 'ALICE'. That happened both on the native upsert path and with the profile forced to catch_retry. With overwrite=False, the race instead ended in vfs.exists. Impact: a peer who holds only add on a shared prefix can overwrite another principal's file, but only one that is being created at the same moment, at a path the attacker also targets. It is an integrity violation of one row and discloses nothing.

### Claimed root cause

WriteGate._decide authorizes a target that is absent at gate time only at the create rung (rights.py:884). Insert arbitration in writes.py then adopts a rival's row as the write target and never re-applies the primary-rung (contribute) check and owner floor that an occupied target needs. _resolve_rows absorbs a non-directory occupant under overwrite (writes.py:628-631), and _upsert_layer's on_conflict_do_update clobbers it (writes.py:489). The absorb arm of _update_materials (writes.py:690 onward) updates the row guarded only by path and liveness. The comment there calls this 'last-writer-wins between writes by design', but that design does not account for the different rungs the two writers hold.

### Trace

1. **entrypoint** `src/vfs/storage/backends/database/backend.py:700` `DatabaseStorage.write.run`: A lower-trust named subject (alice, holding add on /drop) calls write. gate.targets(..., 'upsert') judges the committed state, where the target path is absent.
2. **propagation** `src/vfs/storage/backends/database/rights.py:884` `WriteGate._decide`: An absent target passes when minting.reaches holds at the create rung (add). The primary rung (contribute) and the owner floor run only for paths that are occupied at gate time (rights.py:873-875).
3. **propagation** `src/vfs/storage/backends/database/writes.py:331` `_finish`: The write:before-apply window. The snapshot read and staging are done and no mutation has run. A rival commit here goes unseen by the gate.
4. **propagation** `src/vfs/storage/backends/database/writes.py:444` `_insert_creates`: catch_retry profiles (MSSQL, Oracle, GENERIC) insert under a savepoint. The rival's committed row raises IntegrityError, and the chunk is redriven row by row in _resolve_rows.

Because overwrite is True and the occupant is not a directory, staged.absorb(occupant.entry_id) retargets the create onto the rival's row. No rights check runs.
6. **sink** `src/vfs/storage/backends/database/writes.py:690` `_update_materials`: The absorb arm runs an unguarded update (entry_id, path, deleted_at IS NULL) of the rival's material columns. _replace_bodies then writes alice's body into bob's row, and mint_versions (writes.py:404) archives bob's replaced body.

### Evidence

- `src/vfs/ops.py:150`: write needs contribute on an occupied target and add on a fresh name. The ladder docstring (ops.py:117-121) says add alters only one's own rows and contribute overwrites anyone's.
- `src/vfs/storage/backends/database/dialects.py:468`: MSSQL is catch_retry with no op_isolation pin, so the server default READ COMMITTED applies (RCSI also shows statements the committed rival row). ORACLE (dialects.py:529) and GENERIC (dialects.py:553) are the same.
- `src/vfs/storage/backends/database/dialects.py:436`: PostgreSQL pins REPEATABLE READ, and 40001 is a retryable SQLSTATE (dialects.py:349). A clobbering ON CONFLICT against a row the snapshot cannot see should therefore run the method again rather than overwrite. MariaDB pins REPEATABLE READ (dialects.py:500), so its probe is snapshot-blinded and raises StaleSnapshot.
- `src/vfs/storage/backends/database/writes.py:98`: _CLOBBER_COLUMNS replace the material state and clear the tombstone, but leave out owner_id, so the overwritten row still records bob as its owner.

- `agents/v14-p3/artifacts/evidence/arb-repro-output.txt:1`: My own run on SQLite InMemoryStorage, injecting bob through the write:before-apply seam on alice's session. Sequential overwrite: permission_denied. Raced create: success=True, and both the system read and bob's read return 'ALICE'. The result is the same on the native upsert path and with arbitration forced to catch_retry. With overwrite=False the race ends in vfs.exists.

### Blockers

- The decisive fact is engine concurrency: a genuine second transaction committing on MSSQL or Oracle (or a GENERIC-profile engine) inside alice's gate-to-apply window. Local execution is limited to SQLite. Production SQLite serializes writers with BEGIN IMMEDIATE, so this race cannot happen there. Both the hunter's evidence and mine inject the rival on the victim's own session to stand in for READ COMMITTED visibility. That shows the code path and the missing re-authorization, but not observed engine behavior.
- Whether PostgreSQL (REPEATABLE READ plus ON CONFLICT DO UPDATE, expected to raise 40001) and MariaDB (snapshot-blinded probe, expected to raise StaleSnapshot) really run the method again and end with permission_denied, rather than overwriting, has not been observed on a real engine.

## 5. owner_id uses the engine's default collation on MariaDB, so a principal whose sub differs from another's only by case, accents or trailing spaces sees that owner's road directories

**Fingerprint:** `vfs:models/rows.py:_string:principal-columns-unpinned-collation-mysql-family`

vfs compares principal identities exactly in Python: Principal.sub, grants.resolve and Rights.admits all use exact string equality. The SQL owner-arm predicate entry.owner_id == :owner runs on a column that gets a bytewise collation only on MSSQL. On MariaDB, owner_id compiles as a plain VARCHAR(255), so it inherits the database's default collation. path and name, by contrast, are pinned to VARBINARY there. MariaDB 11.8, the image the test leg uses, is expected to default to utf8mb4_uca1400_ai_ci, which ignores case and accents and pads trailing spaces; this was not observed in this audit. Principal.__post_init__ accepts subs such as 'ALICE', 'alice ' or 'Alicé'. Visibility.road asks SQL, through _owned_beneath, which hidden directories hold a row that each owner arm's sub owns, and Python never re-checks that answer. So a case-, accent- or space-variant principal is shown the victim's road directories in glob, ls and stat, including the trash view, and a write into such a directory fails as permission_denied instead of not_found. That reveals the names and existence of directories, which the principal could otherwise not see. File rows, content and grep results stay hidden, because the fetched rows pass Rights.admits/holds, which compare owner_id exactly. Grant and membership rows are re-keyed by exact sub in Python, so this does not escalate to inherited grants or groups. A second SQL-only consumer of the same predicate is the lexical aggregate in glean._visible_lexicon (glean.py:776, built from ranges.py:128-130). There the victim's chunks would also be counted into the BM25 corpus statistics. That is a minor statistical side channel, and it was not demonstrated. MySQL community is not a supported dialect per AGENTS.md and is served as GENERIC, but its DDL is the same VARCHAR. Postgres deterministic collations compare exactly and are not affected. Oracle is affected only under NLS_COMP=LINGUISTIC with a case-insensitive NLS_SORT. I reproduced this on SQLite, independently of the hunter, using a different tree (/hr/q3/alice-review.txt owned by 'alice', posture '/' none). With owner_id rewritten to COLLATE NOCASE, 'ALICE' sees /hr and /hr/q3 in glob and ls, stat('/hr/q3') succeeds, and its write into the directory returns permission_denied. With COLLATE RTRIM, 'alice ' sees the same. In both cases read is refused. The control 'bob' and the stock BINARY collation leak nothing (not_found).

### Claimed root cause

_string() (src/vfs/models/rows.py:179-188) adds a collation variant only for 'mssql'. On the mysql family (and Oracle under linguistic NLS settings), principal-bearing columns such as entries.owner_id (rows.py:471) and grants.principal_id are plain VARCHAR, and equality on them follows the server's collation. BytewiseString pins path and name to VARBINARY there (rows.py:224) but is not used for principal columns. The authority model treats subs as exact strings (grants.py:497, 629, 638-641). So the SQL-only owner predicates (rights.py:1250 in _owned_beneath for the road, and ranges.py:128-130 and rights.py:1220 for listing and aggregates) can admit rows that the Python authority would refuse. Where Python re-checks fetched rows (holds/admits), the gap closes. Where Python consumes the SQL result directly (the road directories, the lexicon aggregate), it leaks.

### Trace

1. **entrypoint** `src/vfs/authority.py:88` `Principal.__post_init__`: The host builds Principal(sub) from its identity provider. Only empty or blank subs, '*', 'group:'-prefixed subs and the reserved names are refused, so 'ALICE', 'alice ' and 'Alicé' are accepted as principals distinct from 'alice'.
2. **propagation** `src/vfs/storage/grants.py:641` `resolve (owner floor)`: A named subject gets OwnerArm(sub, trimmed), keyed by its exact sub ('ALICE'), covering the mount outside its shared grants.
3. **propagation** `src/vfs/storage/backends/database/reads.py:378` `glob (also ls, stat and the trash view through the same road call)`: Directories the view does not show are passed to view.road(), and every path it returns is emitted as a road observation.
4. **propagation** `src/vfs/storage/backends/database/rights.py:576` `Visibility.road`: For each owner arm, _owned_beneath asks SQL which candidate directories hold a row owned by that owner. The result is added to the visible set with no Python re-check.
5. **propagation** `src/vfs/storage/backends/database/rights.py:1250` `_owned_beneath`: The predicate is row.c.owner_id == owner. Its equality follows the column's collation, so under a case-, accent- or pad-insensitive collation 'ALICE' or 'alice ' matches rows owned by 'alice'.
6. **sink** `src/vfs/models/rows.py:471` `build_vfs_tables entries.owner_id`: Column('owner_id', _string(255)) compiles to 'owner_id VARCHAR(255)' on mariadb/mysql, with no COLLATE and no binary type (confirmed by the hunter's DDL compile). Its comparisons therefore follow the server's default collation.

### Evidence

- `src/vfs/models/rows.py:224`: BytewiseString gives the mysql family VARBINARY(n) for path and name. Keys are pinned to bytewise comparison there; principal and owner columns are not.

## 6. Posture writes and relabels rely on bytewise path comparison that Oracle and GENERIC dialects do not pin

**Fingerprint:** `vfs:storage/backends/database:posture-region-sql-relies-on-unpinned-path-collation-oracle-generic`

Row rights trust the everyone_level label stored on each row (Rights.admits, grants.py:491). A posture change does two things in SQL alone, with no Python re-check of which rows were hit. It writes the everyone posture row (_upsert_grant, matching on path_prefix = P). It also relabels the subtree (relabel_spans / _relabel_opens, matching on lo < path < hi). The gate in front of them, _grant_refusal, works out reach at P bytewise in Python. BytewiseString pins a bytewise collation only on postgresql, mssql and the mysql family. Oracle and every unknown dialect served from GENERIC get a plain String with no pin, so their comparisons follow whatever the engine defaults to. Suppose such an engine compares paths case- or accent-insensitively, for example Oracle with NLS_COMP=LINGUISTIC and a _CI or _AI NLS_SORT, a non-binary DEFAULT_COLLATION, or a GENERIC engine whose default collation is case-insensitive. Then a caller who holds read_write at /Projects through an open parent posture can call posture('/Projects', 'read'). That call rewrites the labels, and the everyone posture row, of another owner's binary-distinct private subtree /projects. Any third user can then read that owner's private rows. The caller would be refused at /projects itself. I reproduced this mechanism locally in a SQLite analogue: path columns were forced to COLLATE NOCASE by patching BytewiseString in-process. Under stock bytewise collation, the same steps leave the row hidden. That this happens on a real Oracle or GENERIC deployment is not yet observed.

### Claimed root cause

BytewiseString.load_dialect_impl pins a bytewise collation only for postgresql, mssql and the mysql family. Oracle and GENERIC fall through to plain String (rows.py:229), and the docstring at rows.py:208-212 accepts that as an ordering and byte-budget degradation that rests on Oracle's NLS_SORT=BINARY default. Two security-relevant writers decide in SQL alone which rows they change: the posture upsert key (rights.py:1375) and the relabel range and point UPDATEs (labels.py:351, 356, 503-504). Both depend on bytewise comparison. The rights.py module docstring (lines 45-49) says every engine compares bytewise, but nothing pins or checks that on Oracle or GENERIC.

### Trace

1. **entrypoint** `src/vfs/storage/backends/database/backend.py:1026` `DatabaseStorage.posture`: A named lower-trust caller asks for a posture at path P (for example /Projects). The call goes through _grant_write into set_posture.
2. **propagation** `src/vfs/storage/backends/database/rights.py:1327` `_grant_refusal`: posture_rows fetches the chain's posture rows through a SQL IN-list. label_of (line 1328) and reaches() then judge P bytewise in Python, so a case-variant posture row at /projects does not change the label at /Projects, and the gate passes on the parent's open posture.
3. **propagation** `src/vfs/storage/backends/database/rights.py:1375` `_upsert_grant`: UPDATE grants WHERE principal_id = '*' AND path_prefix = P, with path_prefix itself in the SET values. Under a non-binary comparison this can match and rewrite another owner's case-variant posture row.
4. **propagation** `src/vfs/storage/backends/database/labels.py:307` `Relabeller._advance`: The planned spans for P go to relabel_spans, which runs point UPDATEs by membership (line 351) and open-range UPDATEs through _relabel_opens (line 356).
5. **sink** `src/vfs/storage/backends/database/labels.py:504` `_relabel_opens (Oracle/GENERIC literal OR)`: UPDATE entries SET everyone_level = rank WHERE OR(path > lo AND path < hi). No Python check follows. A non-binary comparison widens the match to rows outside P's binary region, and Rights.admits (grants.py:491) then trusts the new label.

### Evidence

The ORACLE profile also declares no session_settings, so no ALTER SESSION pins NLS_COMP or NLS_SORT. By contrast, SQLite pins case_sensitive_like at line 400.
- `agents/v23-p3/artifacts/evidence/sqlite-nocase-analogue.txt:1`: Verifier-run SQLite analogue in the sandbox, with the script in agents/v23-p3/artifacts/evidence/analogue.py.
