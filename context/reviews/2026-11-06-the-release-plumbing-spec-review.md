## The author's questions, answered first

1. **Is pinning the dialect workflow's runner to `ubuntu-24.04` the right fix for the SQL Server apt failure, against a step that chooses Microsoft's apt feed by the runner's own Ubuntu release?** Yes to the pin, no to the reason the spec gives for it, and the step needs one more line. EXECUTED: both `prod.list` files Microsoft serves say `signed-by=/usr/share/keyrings/microsoft-prod.gpg`. READ, `.github/workflows/test-dialects.yml:65`: the step writes the key to `/etc/apt/trusted.gpg.d/microsoft.asc`. INFERRED, from apt's documented `signed-by` semantics (the man page is not installed in this container): a source that names `signed-by` is verified against that keyring alone and the system-wide trusted keyrings are ignored, so the key the job installs has never verified this feed; it verified on the 24.04 image because that image already ships `/usr/share/keyrings/microsoft-prod.gpg` holding `EB3E94ADBE1229CF`, and it fails on the 26.04 image because that image's keyring holds the 2025 key only, which is exactly the `NO_PUBKEY EB3E94ADBE1229CF` the spec quotes. So the pin fixes the failure (the 24.04 image's keyring and the 24.04 feed agree) and it is the deterministic choice, matching `publish.yml`'s own `ubuntu-24.04` rows; but the leg stays one image update or one Microsoft re-signing of the noble feed away from the same red, and the step keeps a dead line and a comment that misstates what it relies on. The one-line repair that makes the step true on either image is to write the key where the list looks: `curl -fsSL https://packages.microsoft.com/keys/microsoft.asc https://packages.microsoft.com/keys/microsoft-2025.asc | gpg --dearmor | sudo tee /usr/share/keyrings/microsoft-prod.gpg >/dev/null`, both keys dearmored into the named keyring; keep the pin beside it. A step that picks the feed by `/etc/os-release` is testable from a branch on whichever image the run lands on, so the spec's "cannot test from a branch" overstates it, but the pin plus the keyring line is enough now and the self-adapting feed can stay the named future direction. This is M1.
2. **Should a part flag on a pre-release be refused, as the spec decides, or should it produce something?** Refused, and the spec is right. EXECUTED: `Version("0.1.1") > Version("0.1.0a1")` is true, so ordering alone would admit `--patch` on `0.1.0a1` and the product would be a final `0.1.1` that skips the `0.1.0` the lane is building toward; PyPI would accept it silently. READ, [spec 166](../specifications/active/166-the-release-lane-to-0-1-0/spec.md) decision 3: the stages close by `--final`, and a beta that holds becomes the final, so there is no lane move a part flag could legitimately spell on a pre-release. INFERRED: making `--patch` mean "next alpha" would overload a flag whose meaning every reader already knows, and `--set` is the escape hatch for the case someone really means to abandon a lane. Two write-ins follow (L3): say that a part flag combined with `--pre` on a pre-release (`0.1.0a1 --minor --pre a`) is refused for the same reason, and say whether `--set` is bound by the ordering rule or is the one flag that is not.
3. **Is running the tag check through `astral-sh/setup-uv` plus `uv run --no-project python` in every publish job the right way to get one command on Linux, macOS and Windows, or is there a simpler cross-platform form?** It is the right form, and the two words that make it right should be in the spec. EXECUTED here: `uv run --no-project python` runs a 3.13 with `tomllib`. INFERRED: the simpler-looking `python3 scripts/check_release_tag.py` is not portable, because the Windows image's default interpreter is older than 3.11 and has no `tomllib`; `actions/setup-python` plus `python` is equally one command but a second action, and `setup-uv` is already in the publish job. The load-bearing word is `--no-project`: a plain `uv run python` in this checkout syncs the project first, which builds the Rust extension with maturin before any check runs; and `python-version: "3.13"` on `setup-uv` is what gives `--no-project` its interpreter. Neither reason is in decision 6 or the Design; L5 writes them in. A Python-free bash line could also do it, but spec 166's criterion 8 asked for a unit-tested script, which a bash line is not.
4. **Is it right to leave spec 166 unedited and active, given that its criterion 6 was overtaken when `CHANGELOG.md` was deleted, and that this spec takes four of its ten scope items?** Yes, with two corrections. READ, [the process page](../README.md): links point backward and an earlier document is never edited to point forward, and a numbered spec is converted when it is picked up to build, so 166 waits for its own pickup; its numbered folder is outside the lint, so its header and its clarification marker cost nothing today. READ, [the roadmap](../standards/roadmap.md) section 13: story R1 is "spec 166 scope 1–4", which is this spec, and R2 and R3 keep the rest, so the split is the roadmap's own. The corrections: EXECUTED, the deletion was 2026-11-04 in `1a9a768`, not 2026-11-06 (L1); and decision 1 should name which of 166's acceptance criteria this spec discharges (8, 9, 10 and the code half of 11) so that the conversion of 166 drops them rather than re-reading them as open (L9).
