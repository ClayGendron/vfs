## The author's questions, answered first

1. **Is using the loop's default executor (`asyncio.to_thread`) from the router acceptable, given `offload.py`'s statement about the tree's deliberate threads?** READ, EXECUTED, INFERRED. Acceptable in kind, but not on the reason decision 3 gives. The departure is named: `offload.py:15-17` declares the router's body-measure hop a deliberate thread on the default executor, and the spec amends that sentence to name this hop beside it. The reason "as its body-measure hop already does" does not carry over, though. That hop holds a worker for one sha256 of one body, milliseconds. This hop holds a worker for up to the full 10-second wall. The default executor is not the router's own: asyncio's `getaddrinfo` runs on it (EXECUTED), so a new asyncpg connection's DNS lookup, the body-measure hop of every large write, and any library's `run_in_executor(None, ...)` share it, and it has 14 workers on this machine. Fourteen concurrent chained greps that each reach the wall make every other default-executor user wait up to 10 seconds. The change is still a large improvement on today, where the loop itself is held. The spec should either name that residual with its reason or give the router its own pool; see M1.
2. **Is characters, not bytes, an acceptable batch measure here (decision 3)?** READ, INFERRED. Yes, with the profile stated honestly. `len(str)` is constant-time in CPython, while an exact UTF-8 size needs an encode (a second copy, the very thing batching avoids) or a pass over each text. The reindex batchers already meter characters on the same budget, and `offload.py:34-37` declares the cost: up to four times the budget in bytes on CJK or emoji text (measured 3.00x and 4.00x there). The spec's sentence that "the bytes encoded for one hop stay near 32 MiB" is therefore false for non-ASCII bodies by up to that factor; the bound still holds as a constant multiple. See L1 for the sentence to carry.
3. **Does deduplicating by `(path, text)` (decision 2) change any observable output, including row order, `columns` projection, or errors?** READ, EXECUTED, INFERRED. Order: no change, because each row in `texted` order reads its hit by its key, so the output keeps the rows' order and keeps duplicates. `columns`: no change, because `_hit_row` (`src/vfs/base.py:1946-1974`) reads only the row, its text and the hit, and rows that share a key share the text; the hit's `path` is never read there. Errors: no change for a call that finishes inside the wall, because read errors are gathered before matching; the truncation warning is new only on calls that would not finish. `max_count`: no change, because it caps matches per file (`src/vfs/base.py:1403`), so one verification per body gives each duplicate the same capped answer, in `count` and `lines` modes alike. One observable change: rows that share a body would share one `matches` list object (EXECUTED: shared after the dedupe shape, distinct today), and `Observation` is frozen but its `matches` field is a mutable `list`, so a caller who appends to one row's matches changes the other's. See L2.

## Scale and the production posture

- The `unique` dict and `bodies` list: linear in the rows, as the rows in hand already are; each key hashes its text once on the loop, a linear pass at hash speed with no copy, which is a note: it is far cheaper than the matching it saves, and the spec's Intent speaks of matching, not of every pass (INFERRED).
- The batch loop: one `byte_chunked` pass with `CONTENT_BYTE_BUDGET` from its owner, never a hardcoded size; each batch is at most the budget in characters or one body, so at most four times the budget in encoded bytes (L1) (READ).
- The thread hop: one per batch, sequential, each holding one default-executor worker for at most the remaining wall; the shared-pool exposure is M1 (EXECUTED, INFERRED).
- The wall: one absolute deadline per call, recomputed at worker start, so queue time shortens it; inside one batch the Rust matcher checks the deadline at each body's start (`verify.rs:172`, `:197`), so a single huge body runs to its end once started, bounded by its own length because the regex engine is linear (READ).
- Cancellation: a cancelled `to_thread` await abandons a worker that finishes into the void within the wall and holds only the caller's own texts, the same law `offload.py:28-41` states for the storage hop (INFERRED).
- No SQL statement is added or changed, so the engine floor (Oracle's 1,000-element `IN` list, SQL Server's ~2,100 binds) is not touched; no designed scale cap is added, and the spec's Out section rightly declines a cap on rows sent (READ).

## Premortem

1. A chained caller whose call truncates follows the warning's advice, adds `paths=`, and gets an invalid-argument refusal, because the copied guidance names a move the chained call refuses (H1).
2. A burst of fourteen or more chained greps with slow patterns on large rows fills the default executor for ten seconds, and a Postgres connection that opens in that window waits on its DNS lookup behind them (M1).
3. A caller that edits the `matches` of one returned row finds another row's matches edited too, because deduplication handed both rows one list (L2).
