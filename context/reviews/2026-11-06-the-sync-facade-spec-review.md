## The author's questions, answered first

1. **Decision 8 gives `SyncSession` its own closed flag instead of closing the wrapped `Session`. Is that sound, or does it leave two sources of truth that K10 would trip over?** READ and INFERRED. It leaves two sources of truth, and K10 trips over it. After `SyncSession.close()`, the wrapped `Session.closed` is still `False`; nothing today observes the inner object, so the split is invisible at this landing, but [K10](../standards/roadmap.md) acceptance 5 says "`Session.close()` drops the stamps" and acceptance 7 says "`SyncSession` and `Session` share one stamp implementation", and decision 8 cites exactly that sharing as its reason for wrapping `Session`. A sync session whose inner session never closes keeps its stamps until garbage collection, so K10 would have to either close the inner session anyway or duplicate the drop. The reason given for the flag, that `Session.close` is a coroutine and a session on a closed facade must stay closable, is true of the coroutine but not of the state: `Session.close` (`session.py:60`) awaits nothing and sets one attribute. The sound shape is one flag on `Session`: lift the body of `Session.close` into a synchronous private method `Session._close_now()` (or a sync `close_now()`), have `async def close` call it, have `SyncSession.close()` call it directly with no hop, and have `SyncSession.closed` read `self._session.closed`. `closed_refusal(op)` is still the right lift, because the sync verb must refuse before hopping. This is H2.
2. **Decision 3 constructs the `VirtualFileSystem` in the caller's thread before the loop thread starts. Does that satisfy X1's "constructs the `VirtualFileSystem` itself so first touch lands on its loop"?** READ and INFERRED. Yes, in substance. The roadmap's sentence is about first touch, and first touch is the engine's `ensure_ready`, which the Design runs on the facade's loop with the first verb; `engine.py:1-13` says the built path binds nothing until first touch, and `test_engine.py:301` pins construct-on-loop-A, touch-on-loop-B. Two things in the router's constructor could have bound a loop and do not: `asyncio.Lock()` at `base.py:391` binds to a loop only on a contended acquire (the 3.10+ `_LoopBoundMixin`), never at construction; `storage.capabilities()` at `base.py:396` is a plain function with no I/O. Decision 3's "construction is loop-free by the engine host's design and its pin" is right for the engine and should also name the router's own lock, because that is the one object in the router's constructor a reader would suspect; that is a write-in (L6). What decision 3 cannot claim, and does not, is that `wrap(fs)` is safe for an already-bound lock or an already-bound asyncpg pool; decision 4 says so.
3. **Decision 6 answers a call from the facade's own loop thread with `vfs.invalid`. Is that the right kind?** READ. Yes. `kinds.py:73` defines `invalid` as "the caller's input is wrong and the caller can fix it" and its contract row at `kinds.py:207` is `RetryClass.never`, "Fix the flagged parameter and retry"; a callback that reached for the sync handle from the loop can fix it by using the async filesystem, and no retry of the same call could ever succeed. The neighbours fit worse: `busy` (`kinds.py:79`) is a live bind site, `unavailable` and `timeout` promise a retry that would hang again, and `backend_unavailable` is what decision 7 already uses for the closed facade, so reusing it would blur two facts. The roadmap's X1 acceptance 4 names `vfs.invalid` for this case, so the spec is also consistent with its story.
4. **Criterion 7 compares the statement count of a 10,000-entry write through the facade with the count through an async router "over an equivalent storage". Is that countable and unambiguous as written?** READ and INFERRED. Countable: two lists of statement strings from `before_cursor_execute`, compared by length, is a count and names no clock. Ambiguous in two places. "An equivalent storage" does not say what the two storages are; `InMemoryStorage` is a `DatabaseStorage` over a `:memory:` `StaticPool` (`memory.py:32`), and two of them or two file-backed SQLite stores would each do, but the build would choose. The counting window is not said: the precedent at `test_writes.py:101` installs the listener after `first_touch()`, so first-touch statements are excluded; the facade's first touch happens inside its first verb on the loop, so a test that installs the listener before the first call on one side and after `first_touch()` on the other counts unequal lists for equal work. Both close with one sentence (L1).
5. **Decision 5 makes the blocking wait a module-level function `wait(future)` so a test can replace it. Is that an acceptable test seam in this codebase, or a smell?** READ and INFERRED. Acceptable, with one change. The tree's seam registry (`seams.py`) is for async handlers awaited on the loop, the wrong shape for a blocking wait in the caller's thread, and the tree already patches a module attribute to reach a thread hop: `tests/base/test_dispatch.py:73` replaces `base_module.asyncio.to_thread`. The faithful alternative, a real `SIGINT` raised from a timer thread while the main thread blocks in `future.result()`, is main-thread-only and racy under xdist, so a seam is the right call. The smell is the name: a public `wait` in a public module is one more name on the facade's surface that the parity test does not cover and the reference page would have to explain or hide. Make it `_wait`, under the internal helpers banner, patched as `monkeypatch.setattr(vfs.sync, "_wait", ...)` (L2).

## Premortem

Built as written, a notebook user runs `fs.close()` in a cell: the caller's thread is the kernel's main thread with its loop running, `loop.run_until_complete(loop.shutdown_asyncgens())` raises `RuntimeError: Cannot run the event loop while another loop is running`, the loop is never closed, and the ipykernel criterion did not catch it because its three cells never close. That is H1.

Built as written, an ETL pipeline shares one facade across a thread pool, the main thread calls `close()` while two workers are mid-`write`: the router's close runs, `loop.stop` returns after the current iteration, the two tasks are destroyed pending at `loop.close()`, and the two workers block forever on `future.result()` with no timeout. That is H1's second half.

Built as written, K10 lands the stamps on `Session` with "close drops the stamps", and a `SyncSession` that was closed a thousand times in a long notebook holds a thousand stamp tables, because `SyncSession.close()` set its own flag and never closed the inner `Session`. That is H2.

Consequence if built: `close()` raises `RuntimeError` from any thread whose own loop is running (EXECUTED), which is every notebook cell, the facade's first audience; and a facade shared by a thread pool, which decision 5 calls safe by construction, leaves every worker mid-call blocked forever on a future nothing will ever resolve (EXECUTED).
