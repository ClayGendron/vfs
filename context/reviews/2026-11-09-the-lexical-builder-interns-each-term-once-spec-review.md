## The author's questions, answered first

1. **Does keying the term lists by interner slot and pushing one posting per touched slot after the document's length is known preserve the exact row order and byte content the current sort-then-run-length path drains, for every input including a document with zero emitted terms?** READ and INFERRED: yes, on two conditions the spec should state. The rows depend only on each term's own sequence of `(doc_id, tf, dl)` pushes and on the term order `finish` sorts into; the term lists are independent byte streams (`lexical.rs:373-399`), so the order in which one document's distinct terms are pushed is unobservable, and `finish` sorts `(String, TermList)` pairs by the term string either way. The new path makes exactly one push per distinct term per document with the same `tf` (the in-place count) and the same `dl` (the number of terms the scanner emits, which is `tokenize(content).len()` because `emit` applies the two length rules before it pushes), in the same increasing document order, so every stream is byte-identical and the sealing at `BLOCK_SIZE` fires at the same push. A document with zero emitted terms touches no slot, pushes nothing, and still does `n_docs += 1`, `total_dl += 0` and returns `Ok(0)`, exactly as today's loop over an empty `counts`; the existing fixtures already pin that case (`tests/test_native.py:339`, `(3, "")`, and the fuzz bodies of length 0, EXECUTED: the parity nodes pass today). The two conditions: `pending_doc` needs a sentinel no accepted document id equals (0 works, because `add_doc` refuses `doc_id <= last_doc_id` from 0, but the spec does not say it; L3), and the interner's key must be the folded term the scanner hands over, which is the same bytes today's `String` key held (the study's variant does both, READ `experiments/tokbench/src/builder_variant.rs`).
2. **Is a counting global allocator in a Rust integration test under `crates/vfs-core/tests/` a count-not-clock pin the standards accept, and is "fewer than 24 allocations a chunk" a bound that holds under both the default SipHash hasher and across the batch boundaries the fuzz parity test exercises?** READ, EXECUTED and INFERRED: the kind of pin is accepted, the bound as written does not hold, and its determinism needs one more sentence. The pin: AGENTS.md's performance rule asks for how much work ran, never seconds, and an allocation count is an operation count; `crates/vfs-core/tests/` is the right place for a `#[global_allocator]` because each file there is its own binary and the crate installs none (EXECUTED). The hasher: a hasher allocates nothing, and hashbrown grows on its item count, not on hash values, so SipHash and FNV-1a give the same count, which study 02's table shows (68, 216 and 8 under both hashers, READ). The batch boundaries: `add_docs` is a Python-side slice and the accumulator sees one `add_doc` per document whichever way the batch is cut (READ `python.rs:372`), so the count per chunk does not move. The bound: the study's remaining allocations are not the posting streams, they are the vocabulary's first-sight cost, four allocations per corpus-new term (the `String` clone and the first push into each of the three empty posting `Vec`s; the stream growth after that is `realloc`, which the study's allocator counts separately), and the arithmetic fits every corpus: A 33,294 × 4 / 2,000 = 66.6 against the measured 68, B 50,347 × 4 / 943 = 213.6 against 216, C 35,764 × 4 / 20,000 = 7.2 against 8 (READ study 02 sections 2 and 5, INFERRED). So "8 a chunk" is 35,764 terms amortised over 20,000 chunks and does not transfer to 200 chunks: with the probe's real text the first pass interns 5,766 terms, about 115 allocations a chunk; a Zipf word list passes the bound only below about 1,100 words (992 words give 19.8, 1,865 give 37.3; EXECUTED). This is H1. The determinism: two tests in one binary run on parallel threads by default and the harness allocates too, so a process-wide counter reads the other test's allocations unless the spec confines it (M1). A note, not a finding: no CI job and not `scripts/ci.sh` runs `cargo test` (EXECUTED), so this pin is a hand-run gate, which criterion 9 already says by taking its evidence from the landing notes.
3. **Does the dependency on the overlay kernel spec's scanner leave anything for this spec to decide about the scanner's signature, or about what happens if that spec lands with a different closure shape?** READ and INFERRED: three things, all small. First, the scanner's Design line in the overlay spec is "a private function taking the body, two reusable buffers and a closure receiving each folded term", so the buffers are the caller's; this spec's accumulator struct lists no buffers and would either allocate them per document or invent fields (L1). Second, the closure must be able to borrow the accumulator's interner, lists, touched list and a length counter mutably at once, which works when the scanner is a free function taking `FnMut(&str)` and the closure captures disjoint fields, as the study's variant does, and fails if the scanner became a method on the accumulator; the spec's decision 3 says "one private function with a closure parameter", which is the right shape, and it should name the one requirement it has of it: each emitted term arrives borrowed, folded, with the length rules applied, once per token in order (L7). Third, the order: the spec says it lands after the overlay spec and does not say what it does if that spec is still unbuilt when this one is, so the fallback (lift the scanner itself per that spec's decision 3, and the later landing takes it) belongs in one sentence (L7); and the overlay spec does not name this spec as a co-editor of `lexical.rs` (L6). A closure receiving an owned `String` would keep the rows identical and lose the whole saving silently, because the parity tests pin rows and not allocations; the second-pass count H1 asks for is the guard, since a per-token `String` would put the second pass at about 215 allocations a chunk.
