## The author's questions, answered first

Question 1, the canary. READ and INFERRED: the canary is sound for the failure it is aimed at, a provider that refuses every request from the start of the step: a wrong `dimensions` (OpenAI answers 400), a schema-mismatched self-hosted server (422 from a FastAPI front), Google's 400 for a bad API key. Each refuses the four-word canary too, so nothing is marked, and that direction is right. It misclassifies in two places. First, a misconfigured provider read as refused content: the answer is cached for the whole step and asked before the refusals it vouches for, so a provider that turns to refusing everything mid-step with a 400 (an LLM gateway's spend budget running out, which LiteLLM's proxy answers with a 400) has every remaining batch bisected to singletons and every remaining chunk marked, durably; that is M2. Second, a refusal the canary cannot see: a self-hosted server whose real context is smaller than the provider declares (TEI answers 413 or 422 past its `max_input_length`) refuses every long chunk and accepts the short canary, so long chunks are marked as if their text were at fault, and nothing short of a model id change clears them once the operator corrects the setting; that is part of M3. The opposite direction, refused content read as misconfiguration, happens only when the canary itself fails for a transient reason (a 429 or a timeout on the canary); the spec does not say what that means, and the safe reading (any canary failure ends the step, marks nothing) costs only a run; L5 writes it in.

Question 2, the status classification. EXECUTED for OpenAI, INFERRED for the rest: for the OpenAI adapter, 400, 413 and 422 as input refusals is right. The installed client raises `BadRequestError`/`UnprocessableEntityError` as `APIStatusError` with `status_code` and `response`, its own retry never touches those codes, and OpenAI's over-cap answers ("max 300000 tokens per request", "maximum context length is 8192 tokens") are 400s. Two notes, no rank: OpenAI's `x-should-retry: true` header marks a response the server calls transient whatever its code, and the classifier could treat a 400 carrying it as transient in the same clause as `Retry-After`; and with chunks capped at 2,048 characters (`recursive_text_split`, `src/vfs/models/chunking.py:214`, per the audit's trace) a single chunk cannot exceed OpenAI's 8,192-token per-input cap, so for the shipped OpenAI adapter the realistic refusal is the batch-size one, which splitting cures without marking anything. For the LangChain adapter the classification works only as far as the wrapped SDK exposes `status_code` or `response.status_code`: `langchain_openai` re-raises the `openai` errors (covered), Cohere's `ApiError` and Ollama's `ResponseError` carry `status_code` (covered), HuggingFace's `HfHubHTTPError` carries `response.status_code` (covered), while Voyage (`http_status`), Bedrock (`ClientError.response` is a dict) and aiohttp (`status`) are not covered and stay transient, so the head-of-line block the audit found remains for them. The spec's Scope names that honestly as out, which is the right call for this landing.

Question 3, the column against the re-split, trash and restore, and the identity migration. READ: trash and restore are clean: trash only stamps `deleted_at`, the chunk rows stay, and the fingerprint-skip law in `chunk_dirty` (`indexing.py:258-264`, applied at `:560`) leaves a restored entry's rows untouched, so the flag survives restore; purge deletes the rows (`trash.py:584`). The identity migration is mostly clean: `clear_embeddings` resetting the flag is right, but the identity is stamped only when a page lands a vector (`backend.py:1463`), so a store whose only chunks were refused is never stamped and a later model change never runs `clear_embeddings`; L3 writes in the fix. The re-split is not clean: `chunk_dirty` deletes every chunk row of a re-split entry and re-inserts fresh ones (`indexing.py:331-335`), carrying vectors back by hash (`_carried_embeddings`, which reads only `embedding IS NOT NULL` rows), so a refused chunk loses its flag whenever any other line of its file changes, and every flag is lost on a chunk-generation bump. The same text is then sent again, and twins in other pages or other files are re-bisected too. That is M1.

## Findings, most severe first

M1. [Decision 4](../specifications/active/2026-11-07-a-refused-embed-batch-is-split-and-its-refused-chunks-set-aside.md#decisions) and [the Intent](../specifications/active/2026-11-07-a-refused-embed-batch-is-split-and-its-refused-chunks-set-aside.md#intent) promise that a refused chunk "is sent at most once per content and model" and "never sent again until its text or the model changes", and the live re-split breaks that promise. `chunk_dirty` deletes every chunk row of a re-split entry and inserts fresh rows (`indexing.py:331-335`); only vectors are carried back by hash (`_carried_embeddings`, `indexing.py:586-601`, reads `embedding IS NOT NULL` rows only). So an edit to any other line of the file, or a chunk-generation bump (`indexing.py:306-308` re-dirties every entry), drops the flag and the same text is sent and bisected again. Decision 1 marks twins only within the page, so a twin in a later page, a later run, or a newly written file is re-bisected too. Consequence if built: refused text costs up to `2·⌈log₂ n⌉ + 1` requests every time its file is edited, and once across the store after every generation bump; bounded, so no head-of-line block, but the declared guarantee is false and Scope's file list is short. Evidence that closes it: the spec decides one of two things and pins it with a criterion. Either the flag is carried like vectors (`_carried_embeddings` also returns the refused hashes when `carry_embeddings` holds, `_carry_embeddings` sets the flag on fresh rows by `(entry, hash)`, `indexing.py` joins the Scope), and the embed step lends a refusal by hash from the table the way `cached_vectors` lends a vector (a page row whose hash some refused row under the current identity carries is marked with no request); with a criterion such as "after criterion 2, an edit to another line of the refused chunk's file and a `reindex` send no request for the refused text". Or the guarantee is restated as "at most once per row", with the re-send cost on edit and on generation bump named honestly.

M2. [Decision 3](../specifications/active/2026-11-07-a-refused-embed-batch-is-split-and-its-refused-chunks-set-aside.md#decisions) asks the canary once per step, at the first refusal, and caches the answer for every later batch of the step, so it cannot tell a provider that starts refusing everything mid-step from refused content. On Postgres, MariaDB, SQL Server and Oracle under read committed, a delete of an absent row locks nothing, so the second insert waits on the key and then fails with a unique violation (INFERRED from those engines' documented behaviour; on SQLite `BEGIN IMMEDIATE` serializes the writers, `backend.py:1670-1677`). That run's write fails, classified, and it loses its page's vectors for that run. The next run finds the hash recorded and skips it, so it converges, unlike M4's case, which failed on every run. Fix text for decision 4: "A rival that lost its lease mid-page and records the same hash may meet the key on its insert; that write fails classified for that run, and the next run finds the hash recorded and converges, as the lease bounds the overlap to one page."
