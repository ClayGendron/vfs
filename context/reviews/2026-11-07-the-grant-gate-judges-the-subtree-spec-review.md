## The author's questions, answered first

1. **Is reading only everyone (posture) rows beneath the path enough, or can any other row shape beneath /P leave a granter short of `read_write` across the subtree?** It is enough, and decision 1 should say why in one sentence (L5). READ, `src/vfs/storage/grants.py:1-5` and `rows.py:800-803`: rows only widen and there is no deny row; the everyone rows are the one shape that narrows. READ, `grants.py:477-479`: the point test `reaches` uses the label and the spans only, never the owner arms, so nobody reaches `/P` through the owner floor; an owner-floor row beneath `/P` can only widen what someone else holds, and a granter judged by label holds that label there already. READ, `grants.py:629-638`: a caller's spans are `cover_all` of minimised prefixes, unions of whole subtrees, and the meet across members of a subject set is again a set of subtree roots; so for the spans, covering `/P` means covering its subtree, and group memberships only add subtree roots (memberships are system-only, `rights.py:1339-1346`). The one exception is a widening relabel in flight, whose spans are `cover(prefix)` less its posture children (`grants.py:384-386`); there `covers_subtree('/P')` is false and the decision 5 read finds the below-rung child, so the read still catches it. INFERRED from the above: the check "every below-rung everyone row strictly beneath `/P` has its subtree covered by the caller's spans" is exact, not merely sufficient, because a span covering the hole's own path covers its whole subtree. EXECUTED: under the emulation, criteria 1 to 7 answer as written, including the empty hole and the paged case.
2. **Is keeping posture on the point gate (decision 6) safe?** Yes. READ, `grants.py:169-179`: the deepest posture row decides each path, so a posture written at `/P` relabels only the region R from `/P` down to the next deeper posture rows. INFERRED: the label is the same on all of R (one deciding row), so a caller who reaches `/P` by label holds that label on all of R; a caller who reaches `/P` by its spans covers its subtree, or, through an in-flight widening, covers the widened region, which contains R because every posture row beneath `/P` is a posture child of that relabel or lies beneath one. The posture verb cannot remove an everyone row either: `_lawful_principal` refuses `*` for `revoke` (`rights.py:1349-1353`). EXECUTED: dave's `posture('/open', 'read')` over the `/open/closed` hole succeeds under the emulation and `/open/closed/k.md` stays `not_found` to dave (criterion 7). The in-flight sentence belongs in decision 6's reason (L5).
3. **Are the bytewise range bounds in decision 5 right for every pinned engine, and for the root path?** Yes for the root and for SQLite, Postgres, MSSQL and MariaDB; Oracle is not pinned and the spec should say so (L4). INFERRED: every strict descendant of `P` starts `P/`, and `/` (0x2F) is the byte just below `0` (0x30), so `P/ < x < P0` holds exactly the descendants, and `/P-b`, which sorts between `/P` and `/P/`, stays out; at the root, `'//'` and `'/0'` would be wrong, and `path_prefix <> '/'` is right because every lawful path starts with `/`. READ, `src/vfs/models/rows.py:191-229` and `rows.py:810`: `path_prefix` is a `BytewiseString`, collation `C` on Postgres, the UTF-8 binary collation on MSSQL, `VARBINARY` on the mysql family, SQLite's default `BINARY`; Oracle takes a plain `String` and rests on its `BINARY` defaults, which the docstring calls an accepted degradation. The bounds `P/` and `P0` hold no low byte, so MSSQL's trailing-space padding cannot move them (`grants.py:530-537` states the same rule for `Pieces`). INFERRED: the keyset page needs the `ORDER BY` and the `>` comparison to agree, which on Oracle means `NLS_SORT` and `NLS_COMP` both `BINARY`; `_refused_beneath` (`rights.py:763-780`) already rests on the same pair, so this is not new exposure. The filter is sargable on `uq_vfs_grants_key (principal_id, path_prefix)` (`rows.py:815`).
4. **Is criterion 8, a statement count through a `before_cursor_execute` listener inside the shared contract, workable on every `StorageContract` leg?** Workable, yes; countable as written, no (M1). READ, `tests/storage/test_conformance.py:59-190`: every leg, the in-memory one included, is a `DatabaseStorage`, so `storage._host.engine.sync_engine` exists on each, and the contract already reaches `_host` with a skip when it is absent (`tests/support/grants_contract.py:739-741`); `tests/storage/database/test_trash.py:463-467` is the listener precedent. EXECUTED: today a system grant issues 1 `SELECT` naming `vfs_grants` and a dave grant issues 2 (his own rows and the posture chain), cold and warm alike, and the emulated gate makes dave's 3; so "beyond today's" and "exactly one more" need those numbers written in, and the match should be case-insensitive and allow a schema prefix, because the server legs run in a schema of their own and Oracle may render names differently. INFERRED: the counting filter must be `SELECT` statements only, since `_upsert_grant` issues an `UPDATE` and maybe an `INSERT` on the same table (`rights.py:1356-1379`).
