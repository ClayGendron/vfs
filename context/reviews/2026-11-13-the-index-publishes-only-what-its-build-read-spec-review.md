## Scale and the production posture

- The lexical read issues one keyset page of 256 chunk rows per round trip, as today, but over every chunk row rather than only the covered entries' rows. EXECUTED on SQLite and Postgres over 300 files of eleven chunks, with 90 files trashed and 60 rewritten so that half the chunk rows are uncovered: today 8 page statements, built 14; the rows kept for the builder are 1,650 on both. So pages, rows and bytes on the wire scale with the whole chunk table, not with the covered set (L3).
- At the reference deployment, with 100,000,000 covered chunk rows, today's read is about 390,000 pages with about 100,000,000 entry probes or join steps at the engine. Built, it is about 390,000 × 1/(1 − u) pages with no entry probe, where u is the uncovered share of the table: trashed entries' rows, which the trash keeps until a purge, and the old rows of entries rewritten since the chunk pass, which writes never delete. A nightly batch of 1,000,000 rewrites landing during the build can make u about 10% (about 10,000,000 rows, about 43,000 more pages and about 11% more text over the wire); a large tree held in the trash can make it more (INFERRED). That trades a bounded, proportional transfer for the 100,000,000 probes removed, which is the right trade. It is no cap and needs none.
- Memory stays bounded: a page of 256 rows, and rows of uncovered entries are dropped before the byte batcher (READ in my build). The covered dict, about 10,000,000 ids, is held today for the whole build (`indexing.py:420`, READ), so no new residency. The read stays interruptible at every page.
- Against the rejected forms: membership slices would read ids out of order (about 100,000,000 to sort) and about 20,000 statements at Oracle's floor; the two-phase fetch doubles the round trips. Both cost more than the uncovered share at any plausible u (INFERRED).
- Per publish and per chunk pass: the flip term is bind-free and adds no statement (EXECUTED, criterion 3); the CAS gains one bind; the fence is one `UPDATE` of one row per chunk pass and per landing. No statement grows with batch size and no `IN` list grows outside the budgets it already chunks by (READ).
- The isolation change: on Postgres and MariaDB the chunk pass, the landings and the publish now run under `READ COMMITTED`, which every guard in them reads as SQL Server and Oracle already do (READ, `render.py:331-356`, `indexing.py:350-352`, `:494-504`). EXECUTED: criteria 6 and 8 and the fence probe hold on both engines under it; it changes no build read, so it cannot reopen defect 1.

The lock picture on the amended Design (READ, with the stagings above EXECUTED). A lease-held commit takes entry, content, chunk, edge and refusal rows, and for an embed landing's first page the meta row's identity, then the index-state row last; it never takes `vfs_lock`. The claim, the beat and the release are each one statement on the index-state row alone; the build, the reclaims and every reader only read the pointer. The admin writes (grants, memberships, posture writes, relabel steps) take the meta row first and then grant, membership, relabel or entry rows, never a chunk, refusal or index-state row. The serialized verbs take `vfs_lock` first and then entry, content and chunk rows (`trash.py:152`, `topology.py:144`, READ). Ordinary writes take entry and content rows.
