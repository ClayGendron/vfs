## Security posture

vfs's central controls are sound in shape: row rights are enforced inside storage, SQL is built with bound parameters, and the storage-tier search has real budgets. The audit confirmed **17 findings** (1 high, 13 medium, 3 low) and left **6 leads** that need a fact this run could not observe. The one **high** finding is an authorization bypass: `grant` and `revoke` are checked only at the path they name, so a caller with open access at a parent can grant itself into a private folder beneath it. Most medium findings are availability: a small file or a short pattern written by one agent makes the shared host process do quadratic or unbounded work, before any of vfs's own limits apply. Two medium findings cross principals directly: a caller-chosen `content_hash` lends one principal's rendered text to another, and a read-only permission map can be bypassed by verbs that act on a whole subtree.

Put simply: the permission checks are in the right place, but three of them check only one path where the effect spans many, and several parsers do their expensive work before the budget is consulted.

### 1. grant() and revoke() are checked only at the addressed path, so a caller that gets read_write from the everyone posture at an ancestor can grant itself (or anyone) access to a private posture hole beneath it, or revoke others' access there

- **Severity:** high (likelihood medium, impact high).
- **Source:** entry `src/vfs/base.py:1599` (`AsyncVirtualFileSystem.grant`), sink `src/vfs/storage/backends/database/rights.py:919` (`grant_rows -> _upsert_grant`).
- **Lower-trust principal:** A named principal 'eve' with no grant rows, or an anonymous caller through AsyncVirtualFileSystem, on a mount with the default read_write posture whose /team/hr posture is none.
- **Reproduction:** (1) Create InMemoryStorage(). As Authority.system(), write /team/hr/salaries.md (dummy content 'DUMMY-PRIVATE') and /team/notes.md with parents=True. Leave the root at its default posture and set posture('/team/hr', 'none'). (2) As eve, confirm the baseline: read('/team/hr/salaries.md') -> not_found; grant('/team/hr', 'eve', 'read_write') -> not_found; delete('/team') -> permission_denied. (3) As eve, call grant('/', 'eve', 'read') (or grant('/team', 'eve', 'read_write')). It answers ok. (4) As eve, read /team/hr/salaries.md (ok, 'DUMMY-PRIVATE'); with the read_write row, overwrite it and set posture('/team/hr', 'read_write'); anonymous can then read it. (5) Router variant: AsyncVirtualFileSystem(storage=...) with no authority: read -> unauthenticated, grant('/team/hr', ...) -> unauthenticated, grant('/team', 'eve', 'read') -> ok, then eve reads the file. (6) Revoke variant: system grants bob read_write at /team, then posture('/team/hr', 'none'). eve revoke('/team', 'bob') -> ok; bob's read of the hr file goes from ok to not_found. (7) Run with tools/sandbox-run.py and .venv/bin/python -I (no network, empty env, scratch-only writes).
- **Conditions:** An ancestor path P has an everyone level that reaches read_write (the default posture of a fresh DatabaseStorage/InMemoryStorage, or an explicit one), and a deeper posture row at P/Q narrows everyone to less (none, list, read, add or contribute). Spec 058 tests this 'open root with a private child' shape. Any named Authority with no rows of its own is enough. Through the router, an anonymous call (no authority and no default_authority) is also enough, because unauthenticated_at is judged only at P, where everyone holds read_write. Anonymous cannot name itself as grantee ('anon' is reserved), so it grants to a principal it names or controls. Protected rows exist beneath P/Q, or are written there later; the grant also covers future rows. For the revoke variant, another principal holds a row at P that gives it access inside P/Q.
- **Actual result:** Verifier run, direct: eve read hr -> vfs.not_found; grant at /team/hr -> vfs.not_found; delete /team -> vfs.permission_denied; grant / eve read -> ok; read hr -> ok 'DUMMY-PRIVATE'; grant /team eve read_write -> ok; overwrite -> ok; posture /team/hr read_write -> ok; anonymous read -> ok. Router, anonymous: read -> vfs.unauthenticated; grant /team/hr -> vfs.unauthenticated; grant /team eve read -> ok; eve read -> ok 'DUMMY-PRIVATE'. Revoke: bob read ok; eve read not_found; eve revoke bob at /team ok; bob read not_found. This matches the hunter's independent observation.
- **Impact:** A principal with no rights in the private subtree gains read or full read_write over it: it reads every row, overwrites or trashes them, and can re-posture the subtree open to everyone, anonymous included. The revoke variant lets it remove other principals' access inside the hole. This crosses the row-rights boundary between anonymous or named callers and protected entries.
- **Priority:** The attacker needs only an ordinary named Authority, or none at all through the router. The precondition is an operator choice: a narrower posture on a child under a permissive ancestor. That shape is documented and tested, and the default posture already supplies the permissive ancestor.
- **Smallest fix:** Make the grant and revoke gate check the subtree the row covers, not just the addressed point, as WriteGate.subtrees does for delete/move/sweep. When the caller's own spans at the required rung do not cover the subtree (neither rights.whole nor rights.covers_subtree(path)), read the posture ('*') rows strictly beneath path. Read them in bounded pages over the bytewise range (path + '/', path + '0') on grants where principal_id = '*', chunked by the membership budget. Refuse with permission_denied when any of them gives everyone less than the rung at a prefix the caller's spans do not cover whole. Add a contract test on every StorageContract leg: open root, private /P/Q. A principal with no rows, and anonymous through the router, must be refused grant and revoke at /P and at /, and still be allowed at an unrelated open sibling.

### 2. markdown_refs folds the whole enclosing line once per reference, so one agent-written single-line markdown body makes reindex hold the mount's writer transaction for quadratic time

- **Severity:** medium (likelihood medium, impact medium).
- **Source:** entry `src/vfs/base.py:958` (`AsyncVirtualFileSystem.write`), sink `crates/vfs-core/src/links.rs:72` (`line_context`).
- **Lower-trust principal:** A named agent principal (alice) writes one markdown file to a shared mount. Later the operator runs storage.reindex(). Another principal (bob) writes his own unrelated file while the reindex runs.
- **Reproduction:** (1) Run agents/v03-p3/scratch/verify.py under tools/sandbox-run.py (no network, empty env, CPU 60 s, wall 120 s, RSS 2 GiB) with ./.venv/bin/python -I. (2) Time native.markdown_refs at N=4000, 8000 and 16000 for the one-line body and for the N-line body. (3) For each N, on a fresh InMemoryStorage behind AsyncVirtualFileSystem: alice writes /doc.md, the operator awaits storage.reindex(), and 250 ms in, bob writes /bob.txt. Record the reindex time and bob's write latency. Repeat N=16000 with the N-line control, and on a file-backed SQLite DatabaseStorage.
- **Conditions:** The attacker needs write rights to any one .md path on the mount, for example its own file. The trusted operator or host runs storage.reindex() on the mount. This is routine maintenance, but it is a storage-direct verb that agents cannot call. The mount is SQLite-backed (file DatabaseStorage or InMemoryStorage), and other principals write to it while reindex runs. On server engines the chunk transaction holds only row locks, so the cross-writer effect there was not measured. The quadratic CPU, and the delay to the operator's reindex, apply on every engine.
- **Actual result:** Native one-line: 459.6 / 1705.8 / 6624.5 ms (x3.71, x3.88 per doubling). N-line control: 49.3 / 103.3 / 215.8 ms (linear). In both cases every reference got a 256-char context. InMemoryStorage one-line: reindex 592.6 / 1930.3 / 7044.2 ms, and bob's write waited 295.0 / 1645.5 / 6684.9 ms (it succeeded). N-line control at N=16000: reindex 591.8 ms, bob waited 284.1 ms. File-backed SQLite one-line at N=16000: reindex 7089.9 ms, and bob's write on another pooled connection waited 6920.4 ms, longer than one 5 s busy_timeout, before it succeeded.
- **Impact:** On SQLite-backed mounts, every other principal's write blocks for a time that grows quadratically with one file's line length: about 6.7-6.9 s at 160 KB, measured. On InMemoryStorage, all other sessions wait as well. Larger lines extrapolate past busy_timeout times the retry attempts, after which a blocked writer would fail with a conflict. That is inferred from source, not run. The event loop is not stalled, and the stall ends when the pass commits.
- **Priority:** Writing one markdown file is ordinary agent capability, and reindex is routine operator maintenance. The attacker cannot start reindex itself, but every reindex after each rewrite of the file pays the cost again.
- **Smallest fix:** Make each reference's context cost O(MAX_CONTEXT_CHARS). Compute the newline offsets once per body with memchr and find each reference's line by binary search. References arrive in document order, so cache the folded context per line start and fold each line only once. Make fold_line stop as soon as it has emitted MAX_CONTEXT_CHARS chars. As defence in depth, consider a per-body reference cap or work budget. Also consider running the offloaded CPU before the writer transaction opens, since the chunk flip is already version-guarded. For a regression test, count bytes scanned or fold invocations for one line with N and with 2N references and assert linear growth. Do not assert on wall time.

### 3. Grep lines mode copies a separate context window for every hit line, so output grows as hit lines × body size

- **Severity:** medium (likelihood medium, impact medium).
- **Source:** entry `src/vfs/params.py:270` (`grep before_context / after_context ParamSpec`), sink `src/vfs/storage/backends/database/grep.py:358` (`grep_rows Match assembly`).
- **Lower-trust principal:** An agent with ordinary read access to the shared vfs host makes one grep call on a readable multi-line file. It sets very large context values and either uses a pattern that matches every line or uses invert_match with a pattern that matches nothing.
- **Reproduction:** (1) Build VirtualFileSystem(storage=InMemoryStorage()) and write /f.txt containing L short lines, for example 'abc000000\n' repeated with increasing numbers (10 bytes per line). (2) Call fs.grep with before_context=after_context=2**31-1 and the default output_mode='lines' and max_count. (3) Add up len(m.content) over every Match in r.observations and record peak RSS. (4) Repeat for L = 250, 500, 1000, 2000, 4000, and once with context=0 as a control. (5) Run the invert_match payload at L=2000 and L=4000 to show that allow_scan is not needed.
- **Conditions:** The caller has read visibility on at least one multi-line entry, or write rights to create one. No elevated or system authority is needed. The visible body has many lines that count as hits: they match the pattern, or with invert_match they do not match it. The output is about (hit lines) × (body bytes). The host does not set max_count and does not cap before_context or after_context below the library's INT_CEILING. These are the library defaults.
- **Actual result:** Run under the sandbox launcher (no network, empty environment, CPU/RSS/wall caps). With context 0 the output was about 0.9 × body at every size. With context 2^31-1 the output was 249.9, 499.9, 999.9, 1999.9 and 3999.9 times the body for L=250 to 4000. At L=4000 a 40 KB body returned 159,996,000 characters in 4,000 Match objects, and peak RSS reached about 634 MB, up from about 126 MB. The invert_match variant without allow_scan gave the same 159,996,000 characters and about 605 MB RSS at L=4000. No truncation warning or error was returned. Output grew about 4x per doubling of L, which is quadratic. Larger bodies were not run; extrapolated, a body of a few hundred KB would exceed host memory.
- **Impact:** A quadratic memory and CPU amplification is allocated in the host process shared by every agent. It was observed reaching 634 MB from a 40 KB body, and it extrapolates to exhausting host memory with modest bodies, which can OOM-kill the process for all tenants. The pydantic Match assembly also blocks the shared event loop. The effect is temporary availability loss with no persistence or data exposure, and a restart recovers it.
- **Priority:** It needs only ordinary read access to any multi-line entry and one grep call with two integer arguments. invert_match bypasses the allow_scan refusal. The context values look like normal grep options, and no host-side cap exists in source. The caller must already be a principal the host lets call grep.
- **Smallest fix:** Bound lines-mode output by the body, not by hits × body. The preferred fix follows ripgrep: when a hit's context window overlaps or touches the previous window, extend the previous window instead of starting a new one, so each body line is emitted at most once per entry. The Match shape may need to carry several match lines per window, or keep per-hit match line numbers that point into a shared window. As defense in depth, add a declared per-call output-byte budget in hits_batch and the Python assembly that truncates with a classified 'truncated' warning, and check the deadline inside the per-body hit loop, not only between bodies.

### 4. Chained grep over observations runs regex verification on the event loop with no wall, candidate or byte budget, amplified by duplicate rows

- **Severity:** medium (likelihood medium, impact medium).
- **Source:** entry `src/vfs/base.py:1430` (`AsyncVirtualFileSystem.grep`), sink `crates/vfs-core/src/verify.rs:195` (`hits_batch / count_batch`).
- **Lower-trust principal:** An agent with read access to one roughly 1 MB file, calling grep through a host that shares one vfs event loop among agents.
- **Reproduction:** (1) Build AsyncVirtualFileSystem(storage=InMemoryStorage()) and write about 0.98 MB of plain text lines to /data/big.txt. (2) Start a coroutine that sleeps 1 ms in a loop and records the largest gap between wakeups. (3) Await fs.grep with the payload for N = 10, 20 and 40 duplicate rows, recording the largest ticker gap each time. (4) For comparison, await fs.grep with the same pattern and allow_scan=True, output_mode='files'.
- **Conditions:** The caller must hold read on at least one stored file with content. Alternatively it can attach content to the Observations itself, in which case the bytes are its own. Only an ordinary verb argument (observations=) is needed. The host serves several agents or principals from one AsyncVirtualFileSystem event loop, or from one sync VirtualFileSystem facade (one loop thread by construction), and passes agent-supplied observations and patterns through without a size limit. The stall scales with the body bytes in the listed rows and with the pattern's per-byte cost. Patterns with a literal prefilter finish quickly; alternation-under-repetition patterns such as (\w|\s){60}Q are slow.
- **Actual result:** The chained grep blocked the event loop for 0.654 s, 1.222 s and 2.703 s at N = 10, 20 and 40. That is linear in N, while the stored file was fetched once. The storage-tier scan of the same file and pattern took 0.428 s, but the loop was never blocked for more than 0.013 s, because that tier offloads the work. All calls returned success with no errors and no truncation warning.
- **Impact:** This is a temporary availability loss. Every coroutine and every sync-facade caller sharing the loop stalls for a time proportional to N x body size x pattern cost, with no deadline; about 2.7 s was observed at N=40 on 1 MB, and it grows linearly. Nothing persists and no data is exposed, and the loop recovers when the call returns. The synchronous native call cannot be cancelled.
- **Priority:** It needs only an ordinary grep argument and read access to one file, or caller-held content. The pattern and row count are uncapped and duplicates are not collapsed. Whether many principals share one loop depends on how the host deploys vfs.
- **Smallest fix:** Route chained verification through the same controls as the storage tier. First, verify each distinct (path, body) pair once and fan the result out to duplicate rows. Second, run the matcher off the loop through VerifyOffload on an executor, or through asyncio.to_thread when no backend executor is available. Third, pass a wall-time deadline derived from WALL_TIME_BUDGET and truncate with a warning when it trips. Fourth, process bodies in byte_chunked(CONTENT_BYTE_BUDGET) batches, checking the deadline between batches. A host-side cap on observations length and pattern length is additional defense in depth.

### 5. Glob patterns compile to backtracking Python regex with no cap on wildcards, so one glob call can stall the shared event loop

- **Severity:** medium (likelihood medium, impact medium).
- **Source:** entry `src/vfs/base.py:1263` (`AsyncVirtualFileSystem.glob`), sink `src/vfs/pattern_matching/glob.py:555` (`_translate_component`).
- **Lower-trust principal:** An agent with glob access to an AsyncVirtualFileSystem whose event loop is shared with other agents.
- **Reproduction:** (1) Inside the sandbox, build AsyncVirtualFileSystem(storage=InMemoryStorage()) and write one file whose leaf name is n characters long (n <= 255), plus an unrelated small file. (2) Start a 1 ms asyncio ticker and a concurrent victim task that globs '/small.txt'. (3) Await fs.glob(payload) and record the glob duration, the largest gap between ticker wakeups, and the victim's glob latency. Compare with a benign '*.txt' glob.
- **Conditions:** The caller can invoke glob, or grep/glean with glob channels, on a mount. The reproduction used the default router caller on a fresh InMemoryStorage. Visibility does not gate the cost, because the regex runs before view.shows. The mount holds rows whose names or path segments are tens of characters or longer (up to 255 bytes for each segment). Cost scales with the number of live rows in the mount, because the '[' class disables the prefilter. The host serves several agents or callers from one process and asyncio event loop, so a stall on that loop delays every other caller.
- **Actual result:** Python 3.13.11. For k=4: 0.014 s at n=64, 0.070 s at n=128 and 0.854 s at n=250. For k=6: 0.12 s at n=48 and 0.54 s at n=64. With k=4, n=128, 10 rows took 0.61 s. Each call returned zero rows and no errors. The largest event-loop gap was within a few ms of each glob's duration (for example 0.848 s at k=4, n=250). The concurrent victim glob took the same 0.85 s. The benign '*.txt' glob over the same 10 rows took 0.016 s. A 256-byte segment was refused (the segment cap), which bounds n but not k.
- **Impact:** Each call blocks the shared event loop for every co-hosted agent, for up to about a second for each long-named row at k=4 and more for larger k or more rows. The stall is temporary and recovers when the call ends. Repeated calls can sustain it. There is no persistence, and no effect on confidentiality or integrity.
- **Priority:** The payload is a short string and needs only glob access, which the default caller on a fresh storage has. A shared-loop, multi-agent host is the intended deployment, but vfs is a library, and whether the loop is shared depends on the host.
- **Smallest fix:** Compile glob regexes with the linear-time Rust regex engine already in vfs-core, or with a non-backtracking glob matcher, for compile_glob, compile_filter and _component_matches. Until then, refuse patterns above a declared wildcard count and pattern length in glob_defect/expand_pattern. Also consider applying view.shows before the regex, or running the per-row matching under the same deadline grep uses. Add a regression test that runs a fixed adversarial pattern and asserts on an operation count (matcher calls or steps), not on time.

- **Source:** entry `src/vfs/storage/backends/database/backend.py:686` (`DatabaseStorage.write`), sink `src/vfs/storage/backends/database/backend.py:1466` (`DatabaseStorage._embed_step`).
- **Lower-trust principal:** An agent or user (alice) that can write its own subtree of a shared DatabaseStorage mount using the OpenAI embedder. The default root posture gives everyone read_write; the result is the same under a closed root posture where alice's only write right is read_write on /alice. The victims (bob) write content later.
- **Reproduction:** (1) Mount DatabaseStorage(url=sqlite+aiosqlite:///<scratch>/r.db, embedder=OpenAIEmbeddingProvider(fake_client, 'text-embedding-3-small', dimensions=256)) with the default root posture (read_write for everyone); posture='none' gives the same embedding result. The fake client's embeddings.create counts 1 token per CJK ideograph and ceil(rest/4) for other text, and raises openai.BadRequestError with an httpx 400 response and no Retry-After when a request exceeds 300000 tokens. (2) As system, write /alice/README.txt and /bob/README.txt, grant each principal read_write on its own directory, and run reindex once. (3) As alice, write the 4096 CJK files. As bob, then write 40 ordinary English files. (4) Run reindex twice. After each run, count embedded and NULL chunk rows per top-level directory. Then run glean as bob and read legs['vector']. (5) Control: the same steps with zero alice files.
- **Conditions:** The mount uses an embedder whose hard caps are enforced on real tokens while vfs meters them with ceil(len/4). The shipped OpenAIEmbeddingProvider is the only shipped adapter that declares such caps. LangChain declares none, and the local providers do not refuse. The writer needs write access to some path on the same DatabaseStorage mount and no other right. The operator runs reindex as usual. The token-dense rows must have lower chunk ids than the victims' unembedded rows: written before them, or still unembedded. A full stop needs about 4096 rows, one EMBED_PAGE_ROWS page, with more than about 147 real tokens per row. Fewer rows strand only the rows that share their batch, and limit progress to one page per run. OpenAI's tokenizer must count the text at more than about 1.2 times len/4, and must refuse a request over 300000 tokens deterministically with a 400 and no Retry-After. The repository's adapter docstring declares this cap as documented. The installed openai client (_base_client.py _should_retry) retries only 408, 409, 429 and 5xx, not 400. The real cl100k token density of CJK was not measured locally; the repro used a stand-in counter of 1 token per ideograph.
- **Actual result:** Attack: in each of the 2 runs the provider got 2 requests, both refused ([2048 inputs, 319488 tokens]). Bob stayed at 1 of 41 chunks embedded and unembedded=4136. reindex returned success=True with one warning, vfs.unavailable retryable=True: 'embedding stopped after 0 requests: BadRequestError: Requested 319488 tokens, max 300000 tokens per request'. Bob's glean vector leg returned hits=2. Control: bob was 41 of 41 embedded after run 1, and the vector leg returned hits=42.
- **Impact:** The effect is persistent and store-wide, and it crosses principals: no chunk written later gets a vector on any reindex until an operator deletes or rewrites the offending rows or changes the code. glean's vector leg silently misses that content. The lexical leg and all other verbs are unaffected, and nothing is disclosed or lost. The warning names no rows and is marked retryable.
- **Priority:** The attacker needs only ordinary write access to some path and about 2 MB of CJK text. The deployment must use the OpenAI embedder, the only shipped adapter with hard caps. Benign CJK or Cyrillic corpora with default 2048-character chunks also exceed the real cap, so this can happen without any malice.
- **Smallest fix:** Meter with a bound that cannot undercount, and stop treating a deterministic refusal as a reason to end the run. (1) The OpenAI adapter's estimate_tokens should return the UTF-8 byte length, because byte-level BPE never yields more tokens than bytes. (2) embed_page should bisect a batch refused without Retry-After, and return a single row that is still refused as a per-row failure. (3) Quarantine such rows with a failed marker that select_unembedded and count_unembedded exclude, reset it when the chunk's content_hash changes, and report the count in the embedding extra. (4) _embed_step should break only on transient failures (timeout, 429 or Retry-After, network errors) and otherwise keep advancing last. Regression test: a fake provider that counts 1 token per CJK character and enforces 300000 per request; alice writes 4096 CJK files and bob writes 40; after one reindex, all of bob's chunks are embedded.

### 17. grep and glean count rows the caller cannot read toward their budgets, so the warnings and row counts reveal hidden rows and, through the gram index, what they contain

- **Severity:** low (likelihood low, impact low).
- **Source:** entry `src/vfs/storage/backends/database/backend.py:495` (`DatabaseStorage.grep`), sink `src/vfs/storage/backends/database/grep.py:369` (`grep_rows`).
- **Lower-trust principal:** Alice holds read only on /pub (root posture none). She is not allowed to learn whether rows exist under /aaa-sec, or what they contain. A direct read of /aaa-sec/h.txt answers not_found.
- **Reproduction:** (1) Create an InMemoryStorage and call first_touch. As Authority.system(), set posture('/', 'none') and grant alice 'read' on /pub. (2) As system, optionally write a hidden /aaa-sec/h.txt, in one world containing 'needle secret' and in another 'other text'. Then write 25,000 visible /pub/vNNNNNN.txt files containing 'needle visible'. For the index tier, call reindex(). (3) As alice, call grep(pattern='needle', output_mode='files', allow_scan=True). Record the row count and the truncated warnings. Confirm that read('/aaa-sec/h.txt') as alice returns not_found. (4) For glean, write 500 visible unindexed /pub files containing 'lantern', with and without one hidden /aaa-sec row. Call glean(query='lantern') as alice and compare. (5) Run everything under tools/sandbox-run.py with the repo .venv python -I. The scripts are agents/v24-p3/artifacts/evidence/repro_grep.py (args: 25000 scan, or 25000 index none|without|with) and repro_glean.py.
- **Conditions:** The attacker is a named, group, or anonymous principal with partial rights: read on some prefixes and no rights on the target prefix. A system caller is not affected. The grep variants need about 25,000 visible entries in the call's scope that match the pattern on the index tier, or are unindexed on the scan tier. The glean variant needs 500 visible unindexed entries. The attacker can create these with add or write rights on any prefix in the same mount, or an existing visible corpus can supply them. Globs let the attacker scope the call to its own prefix plus the target prefix. Ordering decides which rows are displaced. On the scan tier and the glean overlay, hidden rows must sort by path before the window's visible rows, and the attacker chooses its own path names. On the index tier, the hidden row's doc id must fall inside the first CANDIDATE_BUDGET ids. The scan and overlay variants also need the hidden rows to be unindexed, that is before reindex publishes them.
- **Actual result:** All runs used the unpatched shipped budgets. Scan tier: 25,000 rows and no warning without a hidden row; 24,999 rows and a 'candidate budget' truncated warning with one hidden row of any content. Index tier: 25,000 rows and the 'overlay not consulted' warning when no hidden row matches; 24,999 rows and the plain 'candidate budget' warning when the hidden row contains 'needle'. Glean: 500 rows and no warning, against 499 rows and an 'overlay budget' warning when one hidden row is present. In every world, alice's direct read of the hidden row answered not_found.
- **Impact:** This is a one-bit-per-query oracle across the row-rights boundary. It reveals whether hidden rows exist in a scope, and on the index tier whether a hidden row contains the searched grams, which can be repeated to probe content. It also silently drops visible matches. It does not read hidden bodies or paths directly.
- **Priority:** The attacker needs partial rights plus about 25,000 matching or unindexed visible entries in scope for grep, or 500 unindexed entries for glean. Typically that means add rights to create padding. Ordering conditions also apply. Each query yields about one bit.
- **Smallest fix:** Apply the caller's Visibility before counting anything toward a budget. In entries_for_scan, add the visibility_clauses / visible_entries pushdown to the WHERE clause, so LIMIT limit+1 and overflow count only rows the caller may see. Thread view into entries_for_scan from grep_rows and glean_rows. On the index tier, restrict the allow-list or the kernel's candidate ids to visible entries before the CANDIDATE_BUDGET cap and the nominated_count comparison. This could be done by computing allow_list_ids under the view pushdown, or by filtering doc ids through the view before capping. Replace the grep_rows docstring note that the budget counts hidden candidates with a regression test. The test should assert that grep and glean output (rows and truncation records) is identical for a partial caller whether or not hidden rows are present, both just below and at each budget.

## Hardening notes

These came out of hunting and verification. None crosses a boundary on its own today, so none is a finding. They are grouped by theme; the ledger's `x_hardening` fields hold the full list with line references.

- **Release and CI.** Pin third-party actions by commit SHA, and pin `setup-uv` and `maturin-version`. Add a top-level `permissions: contents: read` to `test.yml`, `test-dialects.yml` and `publish.yml`. Build with `--locked` (Cargo) and `uv sync --locked`. `deploy-docs.yml:29` installs `mkdocs-material` unpinned in a job holding `pages: write` and `id-token: write`; use the locked `docs` group. Raise the published extra floors (`pypdf>=5.0` and the Office parsers) to audited versions, since users resolve their own.
- **Native engine.** `postings.rs:265` reserves `Vec::with_capacity(count)` from a stored header before checking it, so a tampered posting row can abort the process. `python.rs:123,143` panic on an infinite or huge deadline, and the constructor accepts `grep_wall_seconds=inf`/`NaN`. `lexical.rs` uses `partial_cmp().unwrap()` where `total_cmp` would remove a panic class. `PanicException` is a `BaseException` and escapes verbs unclassified.
- **Search and editing budgets.** A grep pattern nested about 500 groups deep raises an uncaught `RecursionError` from `sre_parse` instead of `vfs.invalid`. `graph meet minimal=True` recomputes articulation points per removed node with no budget (this is the deferred unit). `replace()`'s multi-match error lists every match. The query-vector cache is bounded by count, not bytes. `RenderLimits.seconds` is cooperative, so library parsing (pypdf, python-docx, openpyxl) runs outside the clock.
- **Rights consistency.** `Visibility._existing_roots` reads grant roots with no `deleted_at` term. `rebuild_labels` has no caller, so a wrong `everyone_level` label lives until a later posture covers it. Oracle and the GENERIC floor do not pin a bytewise path collation or ordering (`WriteGate._refused_beneath` keyset paging, `_beneath` road probes); a startup probe that refuses non-bytewise comparison would close this class. `test_races.py` checks consistency but never races two principals with different rungs; add rival-principal variants of the `write:before-apply`, `transfer:post-snapshot` and `purge:post-collect` seams.
- **Agent-facing surfaces.** `render.py:_render_read` prints multi-observation bodies under `==> path <==` headers, so a body written by one principal can forge a header or a fake `ERROR` line in another principal's rendered read. Use unforgeable framing before the planned MCP surface puts this text in model context. `/.agents` has no reserved-write rule, and on a fresh `read_write` posture anonymous can plant skills. `run` is not write-gated by the PermissionMap. `DEVELOPER_OPS` is defined but enforced nowhere. `mkedge` accepts a caller-chosen `provenance='system'`.
- **Defaults.** A fresh storage's root posture is `read_write` for everyone, and `InMemoryStorage` takes no `posture=` argument. Several findings above lean on that default. A closed default, or a `posture=` pass-through, would shrink the blast radius of every row-rights bug.
- **Test infrastructure.** `docker/compose.test.yml` publishes the test databases on all interfaces with fixed passwords; bind them to `127.0.0.1`. Pin its images by digest. `scripts/fetch_beir.py` downloads with no checksum (dev-only).
- **Error text.** The glean vector-leg warning echoes raw provider exception text to the caller; a custom provider could put a key-bearing URL in it. A deterministic embed refusal is classified `retryable=True`.

## Positive source patterns

- Row rights live in storage (`rights.py`), not in the router, so every verb on every backend is judged by the same `Visibility` and `WriteGate`. Hidden rows read as `not_found`, the same as absent ones, and the audit confirmed this on direct reads in every scenario it tried.

- Membership verbs are system-only, cross-mount moves and edges are refused, and the reserved `/.vfs` namespace is enforced at one chokepoint (`paths.py`).
- `params.py` gates every verb argument's type, choices and integer range before dispatch.
- The release workflow has no `pull_request`, `pull_request_target` or `workflow_run` trigger. It publishes through OIDC trusted publishing behind `environment: pypi` and a tag-equals-version check.
- The sibling render stage already quarantines a row that keeps failing (`backend.py:1298-1321`); the embed fix can follow the same shape.
