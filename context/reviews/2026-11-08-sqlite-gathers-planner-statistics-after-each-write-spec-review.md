## The author's questions, answered first

1. **Does decision 25's split of the runners leave any public mutating verb's Result without the held advisories, or give one to an internal commit?** No to both, with one timing difference to write in. READ, `src/vfs/storage/backends/database/backend.py`: `write` (`:775`), `edit` (`:806`), `mkdir` (`:967`), `mkedge` (`:1013`), `rmedge` (`:1042`), `add_member` (`:1134`), `remove_member` (`:1144`) and `grant`, `revoke` and `posture` through `_grant_write` (`:1780`) return through `_execute_write`, which drains at its one return (`:1857`); `delete` (`:826`), `restore` (`:891`), `sweep` (`:925`), and `move` and `copy` through `_execute_transfer` (`:1889`) return through `_execute_topology`, which drains too (`:1913`). That is all fifteen verbs decision 13 names. Every reindex phase, the lease claim, heartbeat and release, and the relabel chunks call `_execute_maintenance` (`:1201` to `:1543`, `:1802`), which never drains, and no internal commit calls `_execute_write` or `_execute_topology`; nothing outside `backend.py` calls a runner (EXECUTED, `grep -rn` over `src/vfs`). A verb that refuses before it reaches its runner does not drain, and its advisory waits for the next one, so nothing is lost (INFERRED). The timing difference: `posture` drains at its grant write's return, before the relabel chunks run, so an advisory a chunk's own detection holds rides on the next public verb, not on `posture`'s final Result as decision 13 still says ("whose public Result takes it once at the end"). It is not lost; the spec should say where it goes (L4). `_settled` at `79752e7` did drop `written.errors` (READ, `git show 79752e7:…/backend.py`, `_settled`'s final `return`), so decision 25's fix there is real.
2. **Does decision 26's inner-task shape hold under the three ways a pass can be cancelled: `close()`, the sync facade's drain, and the loop's shutdown?** It holds for each when the owning task is cancelled once, and does not hold when it is cancelled twice, which a timed-out `close()` does. READ: the drain cancels every other task once and gathers them before it closes the router (`src/vfs/sync.py:652-658`), so by the time `close()` runs `stop_analysis` the owning task is done; the loop's shutdown in `_serve` (`sync.py:660-672`) and `asyncio.run` each cancel every task once and gather. In those two paths both tasks are cancelled, SQLAlchemy invalidates the inner connection, and the owning task's interrupt ends the statement, as decision 26 says; the built test asserts the invalidation (READ, `tests/storage/database/test_statistics.py:738`). `close()` cancels the owning task once and awaits it (READ, `engine.py`, `stop_analysis`). But the router wraps `storage.close()` in `asyncio.wait_for` (READ, `src/vfs/base.py:750`), and when that timeout fires it cancels `close()`, whose `await task` cancels the owning task a second time; that second `CancelledError` is raised out of the handler's `asyncio.sleep(0.001)`, the interrupt loop ends, and the inner task is left running. EXECUTED (`probe_double_cancel.py`, inner transaction replaced by an uninterruptible 300 ms wait, the shape of a pass still in SQLite's busy handler): "close timed out after 53 ms", "outer done: True", the inner pass task still pending, and 0 interrupts issued after close returned. In the real case the inner pass then takes the lock when the rival releases it and runs its whole `ANALYZE` and `COMMIT` with nothing interrupting it, after the engine was disposed (INFERRED). Decision 24 itself names this path (a pass in the busy handler, "can wait up to one `busy_timeout`", "the dispose in the `finally` runs either way"), so it is reachable with any `close_timeout` below 5 s or any caller that cancels `close()`. That is M1.
3. **Is decision 27's planner hint the right fix for the measured regression, given what the measurement shows about the statistics format, and is the partial index rightly out of scope?** Yes and yes, with three sentences to add. EXECUTED (`probe_plans.py` on a copy of `detail.sqlite`, SQLite 3.50.4): the scoped overlay fetch plans `SCAN vfs_entries USING INDEX ix_vfs_entries_path` under vfs's statistics (0 rows, 8.42 ms), `SEARCH … ix_vfs_entries_encoded_kind (encoded=? AND kind=?)` with `sqlite_stat1` emptied (0.16 ms), and the same seek with `unlikely(vfs_entries.encoded = 0)` (0.2 ms). The format is as decision 27 says: `ix_vfs_entries_encoded_kind` reads `56002 28001 18668` against data of 6,001 directories and 1 file with `encoded` false and 50,000 files with it true, and `PRAGMA compile_options` carries no `ENABLE_STAT4` (EXECUTED; the memo's 1.2 says the same for every CI interpreter). The hint is robust: with `sqlite_stat1` scaled to 2,800, 11,200, 1,120,040, 11,200,400 and 112,004,000 rows the plain fetch scans the path index at every size and the hinted fetch seeks at every size (EXECUTED, `probe_scale.py`, `probe_scale_small.py`), so criterion 28 can go red at 11,201 rows. It is never worse than the plain form: with 25,000 and 50,000 files awaiting the index the hinted fetch took 23.1 and 46.4 ms against 29.4 and 50.0 ms (EXECUTED, `probe_pending.py`). And it is exactly the plan the store has today with no statistics, so it cannot regress anything decision 22 measures against. The partial index is rightly its own spec: it bumps the schema format and needs the four engine legs, which a SQLite-only fix for 0.1.0a1 should not carry (INFERRED). What decision 27 should add: the honest profile of the hinted fetch when many files await the index (L8), the server-engine claim scoped to what was measured (L7), and the partial index in the Scope's Out list (L5). Separately, the measurement shows a second changed plan that criterion 25 would count against decision 22's literal sense (L6).
