## The author's questions, answered first

Question 1, is decision 1's rule correct? Yes, the rule is correct; criterion 1 is not. EXECUTED (probe 1): across every body, context, cap and invert setting tried, the rule gives disjoint regions, each holds its hit line, and their union is exactly the union of today's windows. At the body edges the Design keeps today's behaviour: the first region's `floor` is 0, and the last region's `ceiling` is the body's length, so the `context_end + 1 < ceiling` test still stops before the phantom line after a trailing `\n` (READ `verify.rs:251`; EXECUTED in the model, which covers bodies with and without a trailing terminator and with empty lines). With a cap, the rule runs over the capped hits only. The last capped region keeps its full `after` window, even across later hit lines the cap dropped, and those lines render as context with `-`, exactly as they do today (EXECUTED). In inverted mode the same rule runs over the non-matching lines (EXECUTED; for criterion 1's body with `invert` and `before = after = 1`, the regions are (1–2, hit 1), (3–4, hit 3) and (5–5, hit 5)). The defect is in criterion 1, which states a split the rule does not produce; see H1.

Question 2, is this an observable contract change, and is it named? Yes, it is observable, and the spec names it only in part. When two windows overlap, a grep `Match` now carries fewer lines in `start`, `end` and `content`, and the rendered text loses its repeated lines and marks every hit line with `:` (READ, `src/vfs/results/render.py:367-406` groups regions only by identical `(start, end)`). One more consequence follows: a caller that reads a single `Match` alone no longer sees all the `before` lines it asked for, because those lines now sit in the previous region. No caller, doc or test in the tree relies on the overlap (EXECUTED, probe 4): `tests/storage/database/test_grep.py:379` has one hit, `tests/storage/database/test_offload.py:165` and `tests/pattern_matching/test_matcher_parity.py` compare two engines that both change, rerank's `region_texts` (`src/vfs/rerank.py:143`) serves glean, and nothing under `docs/` describes `before_context` or `after_context`. The Intent says the output changes, but the first paragraph never says the verb's output changes, and three docstrings outside the Scope still describe the old window; see L3 and L5.

Question 3, is it right to keep `PROTOCOL_VERSION`? No. The seam's own rule, `crates/vfs-core/src/python.rs:26-27` (READ), bumps the protocol on a change of "shapes or semantics". Decision 4's reason covers shapes only. The case decision 4 describes, a wheel built before this change that loads and returns the old overlapping regions, is the case the gate exists to refuse. It is also the usual way a developer meets a stale extension, because [AGENTS.md](../../AGENTS.md) says uv does not rebuild the wheel after a Rust-only edit. Bumping costs two constants (`python.rs:28`, `src/vfs/native.py:35`). See M1.

## Decisions, one line each

1. The region rule: holds (EXECUTED, probe 1); its proof sketch is terse but correct, and the Design's byte loops implement it exactly; criterion 1 disagrees with it (H1).
2. Collect hits first, then clip both scans: holds; each backward scan stops at the previous region's end and each forward scan stops before the next hit's line, so the scans over all regions are disjoint and linear (INFERRED from `verify.rs:242-255` with the Design's bounds; EXECUTED in the model).
3. The oracle applies the same rule and `Match` documents it: holds; the oracle has two exits and the Design names only one (L4), and `Match`'s first line still says "a grep window" (L3).
4. Keep `PROTOCOL_VERSION`: the reason covers shapes but not semantics, and the decision departs from the rule at `python.rs:26-27` without naming it (M1).

## Scale and the production posture

The added in-memory structure is one `(ls, le, line_no)` triple per hit line, bounded by `cap` and by the body's line count. That is no more than today's `Vec<Hit>`, which it replaces (INFERRED). The added scans run once backward and once forward over the body at most. The output bytes per body are at most the body's size, and the database tier already bounds the bodies in one batch by `CONTENT_BYTE_BUDGET` (READ `src/vfs/storage/backends/database/grep.py:330-358`). No statement, bind list or loop grows with batch size. One `Match` object per hit line remains, so a body whose every line hits still yields one Python object per line. That cost is linear in the body and `max_count` is the caller's lever on it; it is a note, not a cap. The hit scan that feeds the region builder is not linear on one long line with many matches; see L6.

Found on the re-read of the amended draft. Decision 5's skip rule is correct as far as it goes. A match starts at or after the start of the last line emitted, because matches arrive in order, and that line spans its start through its end byte (the `\n`, or the body's length). So "the match starts at or before the last emitted line's end" holds exactly when today's test "the match's line start equals the last line start" holds (READ `verify.rs:139-148`, INFERRED). It skips a zero-width match at the line's terminator, as today. It does not skip a zero-width match at the start of the next line, even an empty one, and that line is emitted, as today. A zero-width match at the body's length after a trailing `\n` still reaches the phantom-line guard after a backward scan of one line. Inverted mode walks `LineRanges` and never takes this branch (READ `verify.rs:127-133`). `count_lines` shares `each_hit_line` (READ `verify.rs:98-105`), so it gains the same fix. Two new defects follow.

H2. [Decision 5](../specifications/active/2026-11-07-grep-context-regions-never-overlap.md#5-each_hit_line-skips-a-match-that-starts-at-or-before-the-end-of-the-last-line-it-emitted-before-it-scans-back-for-a-line-start) does not make the hit scan linear, although decision 5 and the Intent say it does. The skip comes after `find_iter` has found each match. The regex crate documents `find_iter` as worst case `O(m·n²)`, because each search can scan the rest of the haystack before it reports a match (READ `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/regex-1.13.1/src/lib.rs:1095-1117`; the lock pins regex 1.13.1). The per-line law bounds each search by the line, so the cost is quadratic in a long line's length. EXECUTED, in a scratch crate on regex 1.13.1: pattern `(?m)[^\n]*[^A-Z\n]|[A-Z]` with `find_iter` over one line of `A` at 5,000, 10,000, 20,000 and 40,000 bytes ran one search per byte and took 0.023, 0.093, 0.34 and 1.37 seconds. Resuming the search at the byte after each hit line found the same one hit line in one search, in 0.08 milliseconds at 40,000 bytes. EXECUTED through the live verifier: `count_lines` with `.*[^A-Z]|[A-Z]` on one line of `A` at 10,000, 20,000 and 40,000 bytes took 0.086, 0.34 and 1.37 seconds. Almost all of that time is the regex's own searching; it does not come from the backward scan decision 5 removes. If built as written, criterion 1's `one_long_line_scans_back_once` passes on pattern `x`, while one long minified line still costs the square of its length for an alternation like this one. The Design also never describes decision 5 or `HitScan`: it does not say what the struct holds or how a cargo test reads it, so the build would have to invent both. Fix text for decision 5: "### 5. After each hit line, `each_hit_line` resumes the search at the byte after that line's end with `Regex::find_at`, so each line is searched for at most once" with the body "A match never crosses `\n`, so the first match at or after a line's start decides whether that line hits, and the set of hit lines is unchanged. The searches then cover disjoint stretches of the body, and each backward scan for a line start runs only from the search's start, so the hit scan is linear in the body for `hit_lines` and `count_lines` alike. Skipping matches after `find_iter` would not be enough: `find_iter` runs one search per match, and each can scan the rest of the line. `find_at` reads the bytes before its start, so `^` and `\b` judge a line start as they do today, and a match at the body's length after a trailing `\n` still meets the phantom-line guard, which ends the scan." Fix text for the Design: "`each_hit_line` wraps a private `scan_hit_lines(hay, invert, emit) -> ScanCost`, where `ScanCost { searches: u64, back_bytes: u64 }`; the public paths drop the cost, and the cargo tests read it." Fix text for the criterion: "`one_long_line_scans_once` (one line of 100,000 `x` with pattern `x`, and one line of 40,000 `A` with pattern `.*[^A-Z]|[A-Z]`: `hit_lines` and `count_lines` each return one hit line, and `ScanCost` reports at most 2 searches and at most the body's length in `back_bytes`)". The diagram's `EACH` label then reads "hit lines in order, capped; the search resumes after each hit line".

Second re-read, decision 5's resumption. The search resumes at the byte after each hit line, so a cap still stops at the same hit line: hits arrive in the same order, and `emit` still returns false (EXECUTED, every cap above). A zero-width match at a line's start is found by the search that starts there, and that search runs only once per line, so the scan cannot loop on it (EXECUTED: `^`, `^$`, the empty pattern and `x*`). With the empty pattern every line hits once, as today. On a body with a trailing `\n`, the last search starts at the body's length, finds the empty match there, and the phantom-line guard ends the scan. On an unterminated body the next start is one past the end, where the loop stops; `find_at` with a start past the end returns no match and does not panic (EXECUTED on regex 1.13.1). Inverted mode walks `LineRanges` and calls `is_match` once per line (READ `verify.rs:127-133`), so the decision does not touch it. A note, not a finding: the spec leaves open what `ScanCost.searches` counts in inverted mode, and no criterion reads it there. `count_lines` and `hit_lines` share the scan (READ `verify.rs:98-122`).
