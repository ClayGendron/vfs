## The author's questions, answered first

1. **Is one shared count of 25,000 the right rule for glean's overlay when a glean dirty row still costs two to two and a half times a grep dirty row, or should the shared constant reach glean through a factor?** INFERRED from [study 02 section 6](../research/studies/2026-11-09-the-dirty-row-budgets-of-grep-and-glean/02-the-dirty-set-cost-curve.md) and [study 03 section 6](../research/studies/2026-11-09-the-dirty-row-budgets-of-grep-and-glean/03-the-overlay-counts-kernel-spike.md). One count, no factor. The count's job is to make the two verbs drop the same rows: study 02's sentinel table shows that once the limits agree both verbs lose the same last-sorting file and while they differ glean's loss is a superset of grep's, so a factor would reopen the gap the spec exists to close. The cost a count bounds that both verbs share, about 7 KB of body a row, the nomination sort, the surrogate and body fetches, is the same for both, and the two-and-a-half-times residue is CPU inside a kernel that now runs under the deadline, which is the wall's job and not the count's. Study 03 measured 1.5 s for a full 25,000-row overlay on SQLite and projected about 2.8 s on Postgres, both inside the 10 s wall. The one honest caveat is that the Postgres figure is a projection (the memo's section 8 names the experiment) and the worst measured query, two very common terms with 3.6 s of fixed index-tier cost, would sit near 6.8 s there; criterion 12's conformance row at 600 rows does not reach it, so the landing notes should record the Postgres leg's slope as a fact when the `db_test` cycle runs.
2. **Can fetching and counting the overlay in byte batches change any hit or score relative to one unbatched pass?** READ `glean.py:1016-1044` and INFERRED. No, provided three things hold, two of which the spec states. The per-term postings order: today `sorted(docs)` at `:987` puts bodies in surrogate order before the loop, so each term's postings arrive id-ascending; decision 8 sorts each term's accumulated postings by doc id once before `chunked(postings, BLOCK_SIZE)`, which restores the same order and the same block boundaries. Ties and the min-max scale: `score_blocks` receives the same blocks, idfs, `avg_dl` and `k`, so the engine breaks ties as it does today, and `_fuse` normalises the same hit set with the same scores. The idf for a term absent from the base: `idf(df, stats.n_docs + count)` where `df` is the term's posting count over the whole overlay and `count` is today's `len(docs)`, the number of fetched bodies; decision 8 says `_overlay_blocks` runs once over the accumulated postings, so both are totals and the value is unchanged. The third condition is the one the spec leaves open: the body count must be the number of bodies the kernel counted, which under a wall is not the number handed in, and the kernel's return shape carries no such count (H1). Study 03 saw a maximum score difference of zero with the one-call shape, which is the shape decision 8 keeps.

[The bounded-work spec](../specifications/active/2026-11-07-bounded-work-has-one-home.md) reads the same rule from the other side ("stays at 13 because no binding signature changes"), so 13 to 14 is the established rule applied.
4. **Is retaining only bodies with a nonzero term frequency safe for every path that reads an overlay body later in the call?** READ `glean.py:206-209`, `:433-435`, `:450` and `:1125-1160`. Yes for every reader today. `_Sources.bodies` has one reader, `_observe` at `:1148`, which reads a body only for a row in `rows`, and `:435` fills `rows` only with entries in `scored`; `scored` comes from `score_blocks` over the postings, and a posting exists only for a nonzero tf. The two guards the build needs: the retention must be keyed per batch (surrogate id to entry id to text) before the batch's bodies are released, and criterion 6's oracle parity would surface a missing body as a `KeyError` rather than a wrong score, which is the right failure.
