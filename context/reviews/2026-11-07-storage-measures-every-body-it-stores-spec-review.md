## The author's questions, answered first

1. **Does any legitimate caller inside vfs, or any landed test, write a bodiless content-kind entry that decision 2 would now refuse?** No. EXECUTED: the spy over the whole suite (memory and SQLite legs; the engine legs were deselected, but they run the same contract nodes) recorded zero bodiless content-kind entries at `DatabaseStorage.write`, and zero entries whose `content_hash`, `size_bytes` and `lines` differ from `measure_text` or `measure_bytes` of their body, so criterion 6's "passes unchanged" is also supported for decision 1. READ: every producer in `src/` carries a body. The router refuses a bodiless path write before dispatch (`base.py:1003-1006`: "write requires path and content or data, or entries"). It authors the rest through `_authored_entry` (`base.py:314-330`). Skills write `content` bodies (`skills.py:202-210`). `editing.py:43` builds edit's entries, not write's. `session.py:156` and `sync.py` only forward. `tests/storage/database/test_coherence.py:91` calls `write_rows` directly, below the new function, so it is not affected. No test constructs an `Entry` with `source="bytes"` (`grep`). One shape is not bodiless under the spec's definition but should be decided: a bytes-sourced entry carrying `content` and no `data` (probe three, L2).
2. **Is measuring in `DatabaseStorage.write` before the writer transaction the right owner, rather than in `write_rows` or the `WritePlan`?** Yes. READ: three facts rule out the other two places. First, `_execute_write` opens the writer transaction with the lock "held from the plan's first read" (`backend.py:1667-1673`), so hashing inside `write_rows` would hold SQLite's write lock, and a pooled connection on every engine, through CPU work. Second, `_mutate` reruns the whole closure on a retryable outcome (`backend.py:1723-1740`), so measuring inside it would hash again on every redrive. Third, `WritePlan.put_file` is synchronous (`staging.py:269`), so it cannot await a hop, and the staging layer is the pure judgment layer. Keeping `measured_entries` in `writes.py` beside `write_rows` keeps the rule in the builder module. Two consequences should be written down. `write_rows` stays callable with unmeasured entries, and a test already does so (`test_coherence.py:91`), so its docstring should state the precondition (L7). And the refusal now comes before the permission gate and first touch (L5).
3. **Is criterion 4's count of executor submissions robust, given other stages share the offload pool?** Robust today, but fragile by design. READ: `write` (`backend.py:686-713`) passes no executor, and the pool's users are grep, glean, the render step, signals and reindex (`backend.py:528`, `585`, `1288`, `1336`, `1383`, `1393`); none of them runs inside a write. Each contract test gets a fresh backend, which has its own host and its own lazily minted pool (`engine.py:227-238`), and xdist workers are separate processes, so no sibling test shares the pool. INFERRED: two things make the count fragile. First, active spec [159](../specifications/active/159-render-at-write/spec.md) puts a pre-transaction render hop on the same pool inside `write`, which would turn "exactly one" red for a reason that has nothing to do with measurement. Second, wrapping `storage._host.offload_executor.submit` reaches into `DatabaseStorage` internals from the backend-agnostic contract, which today never touches `_host` (`grep` of `tests/support/storage_contract.py`). The fix is to count calls of `writes.call_offloaded`, the measurement hop itself, in `tests/storage/database/test_offload.py`, which already reaches the host's pool (`test_offload.py:350-380`) (L3).
4. **Is the double hashing of decision 4 acceptable under the production posture in AGENTS.md?** Yes, as a profile. The real problem is a different one: decision 3's inline rule (H1). INFERRED: hashing twice is a constant factor over bytes the call already holds. It adds no statement and no structure, and the posture binds statement growth and designed caps, not constant CPU factors. READ: `hashlib` releases the GIL for inputs over 2 KB, and active spec 175 measured it at 2.46 GB/s ([175](../specifications/active/175-integrity-verify-on-read-and-scrub/spec.md), line 77), so an offloaded second pass runs beside the loop. Two corrections, though. First, every body is hashed twice, not only large ones: the validator measures each small body when its `Entry` is built (`entry.py:235`, `243`). Decision 4 should say so (L4). Second, storage's second pass over small bodies runs on the loop and adds up across the batch. EXECUTED: 0.634 s for 10,000 bytes bodies just under the threshold. That loop cost, not the double hash, is what breaks the posture (H1).

## Scale and the production posture

- The measurement pass is one loop over the batch, linear in entries; `model_copy` is shallow, so no body is copied (INFERRED); the call already holds the bodies.
- The inline measurement grows with the batch's total body bytes and has no per-call bound: 10,000 bodies just under 100,000 bytes take 0.634 s on the loop for bytes, and text costs more, because `measure_text` also counts lines (EXECUTED); this is H1.
- The offloaded hop is one per call, bounded; a cancelled await leaves the worker hashing into the void, which touches no session, and a pool shut by `close()` serves the work inline (`offload.py:79-92`) (READ).
- No statement is added or changed, and the refusal comes before the first statement, so Oracle's 1,000-element `IN` list and SQL Server's ~2,100 binds are untouched (READ).
- `MEASURE_OFFLOAD_BYTES` is a cost threshold, not a designed scale cap (READ).
- The existing version mint already hashes every replaced body inline (`versions.py:168-173`); that is a profile this spec inherits but does not make worse, and spec 175 addresses it (READ, note).
