## The author's questions, answered first

1. **Is the step sound for concurrency and for the commit's own semantics, and can a failure be mistaken for the mutation failing?** The commit's own semantics hold. The step runs after `with_retry` returns, on a separate session. A `SQLAlchemyError` or `OSError` there becomes a warning, and `Result.success` counts only fatal errors (READ, `src/vfs/results/envelope.py:380`). So a classified failure of the step never reads as a failed write. The concurrency is not sound as written. First, the listing is not a read: it takes SQLite's write lock (EXECUTED, `probe_locks.py`; READ, `../sqlite/src/pragma.c:2587-2592`, where the second checked table calls `sqlite3BeginWriteOperation` even when the list-only bit is set). Second, an unchanged store's listing still names `vfs_gram_epochs`, so under decision 4 every commit also issues an `ANALYZE` of that table, which is a write too (EXECUTED). Together, every committed mutation takes the one writer lock two more times. Each of those waits up to `busy_timeout`, 5,000 ms, behind a rival writer (H1). Third, steps running at the same moment repeat the same analysis (M1). Fourth, a step that stops partway leaves the table no longer due, so decision 8's "the next commit's listing names the same table again" is false (M2). A failure can still look like the mutation failing in one way: a cancellation or caller deadline that lands during the step. It reaches the caller after the commit, and the step widens that window from microseconds to one busy wait (L2). The warning's `retryable=True` also invites a caller to retry a write that already committed (L1).

2. **Is "the step does nothing below 3.46" acceptable, and which SQLite versions do the supported interpreters ship?** The claim is false, so it cannot be accepted as written (M3). Below 3.46 the listing names a table whose statistics the planner used on that connection, and it re-analyzes at 25×, not 10× (READ, `pragma.c` at `version-3.45.3`, the rules above `case PragTyp_OPTIMIZE` and the `TF_StatsUsed` test; `where.c:3971` sets that flag when a non-unique index is planned). The step's session is not a fresh connection. It is checked out of the pool: `AsyncAdaptedQueuePool` for a file and the one `StaticPool` connection in memory (READ, memo 2.3). That connection has usually served the verbs' own queries. So below 3.46 the step is partly active, it depends on connection history, and no test covers it. The versions: uv's interpreters link SQLite 3.50.4 (3.11.14, 3.12.12, 3.13.11, 3.14.2) and 3.53.1 (3.14.10), and Homebrew's 3.11 and 3.13 link 3.53.4 (EXECUTED, `sqlite3.sqlite_version` per interpreter on this machine). Distribution Pythons link the system library. Debian 12 ships SQLite 3.40.1, Ubuntu 24.04 ships 3.45.1, and RHEL 9 ships 3.34.1, all below 3.46 (INFERRED from those distributions' published package versions; not executed here). The python.org 3.10.4 build on this machine bundles 3.37.2 (EXECUTED; that interpreter is unsupported, and it shows only that installers bundle older SQLite). So the below-3.46 case is common, not an edge.

3. **Is `DialectProfile.statistics_listing` a justified profile field?** Yes, on AGENTS.md's bar. SQLAlchemy takes no position on maintaining planner statistics. It does model the SQLite version (`dialect.server_version_info` is `dbapi.sqlite_version_info`, READ, `sqlalchemy/dialects/sqlite/pysqlite.py:584-585`), so the 3.46 gate that M3 proposes should read that fact, not a new profile field. A note on shape, with no fix required: the field holds only the listing. The follow-ups (`PRAGMA index_list`, `ANALYZE` per index) are hardcoded SQLite in the host. So the field works as a SQLite flag carrying one statement. That is acceptable while only SQLite fills it.

4. **Is decision 15 an open question in disguise?** No. Criterion 15 has a fixed answer: 0 regressing statements. If the measurement finds a regression, the landing is blocked, and the build does not get to choose silently. Two gaps remain (L3). The fix route, "the fix appends a decision here", conflicts with the re-sign protocol: a Decision changed after "Fit to build" needs a new dated review file. The regression class is also narrow. It catches an index seek turning into a full SCAN, but not a swap to a worse index, which is the very trap this spec exists to fix.

5. **Do decision 12's filter and decision 11's moved pins keep today's pins honest?** Mostly. The filter hides only the step: nothing in `src/vfs` issues `ANALYZE`, `optimize` or `index_list` today (EXECUTED, `grep -rn`). The trash `_spy` already drops every `PRAGMA` (READ, `test_trash.py:61`). The step's own statements, though, are pinned only partly. Criterion 4 counts the listing and the `vfs_entries` index `ANALYZE`s. It does not count the `index_list` and `ANALYZE "main"."vfs_gram_epochs"` that an unchanged store issues on every commit. So once the filter is in place, nothing bounds the per-commit step (folded into H1). The moved fan pin is robust: its two-arm shape seeks the path index from 30 rows (READ, the memo's `pin.txt`). Criterion 3's store sits close to a plan flip, which EXECUTED `probe_flip.py` puts between 2,500 and 3,000 rows on both SQLite versions CI uses (L4). Dropping the two-channel spec's no-statistics leg rests on "no written store is left in that state". That is false below 3.46, and false after any wipe of `sqlite_stat1` (folded into M3).

## Scale and the production posture

- The listing: one statement per committed mutation, whatever the batch held, so it does not grow with batch size. It is a write-lock acquisition, however, not a read (H1).
- The per-table `index_list` and per-index `ANALYZE`s: bounded by the schema (23 tables, 13 indexes on the largest). They run on a crossing commit, and on every commit for an empty table with no index (H1).
- Analysis cost: linear in a table's rows, with the longest hold one index's scan. That scale profile is named honestly with its future direction, which is not a designed cap. The total-cost claim holds for one writer only (M1).
- No `IN` list or bind grows: the step binds nothing, and the own-table set is a Python set built from metadata.

## Premortem

1. On a shared SQLite file with an ETL writer and several agents, write latency doubled and every write carried a statistics warning. The step's listing and its `vfs_gram_epochs` `ANALYZE` queued behind the ETL's long write transactions for up to 5 s each. This became H1.
2. A store whose first crossing re-analysis was interrupted by `SQLITE_BUSY` kept its tombstone index at the three-row statistics of its first write, and the planner sought it for every arm. This is the trap the spec fixes, back until the next tenfold. This became M2, and its likelihood rises with H1.
3. On Ubuntu 24.04's system Python (SQLite 3.45.1), stores planned differently depending on which pooled connection ran the step, and no test covered it. This became M3.

## Findings, most severe first

1. **H1. The listing is a writer, and an unchanged store's step issues a second write on every commit** ([Decision 3](../specifications/active/2026-11-07-sqlite-gathers-planner-statistics-after-each-write.md#3-sqlite-decides-which-tables-are-due-vfs-runs-the-listing-after-every-commit-and-analyzes-only-what-it-names-with-no-write-counter-of-its-own), Decision 4, Design "Scale", Intent). `PRAGMA optimize = 0x10003` takes SQLite's write lock: EXECUTED in `probe_locks.py`, it failed "database is locked" behind a held `BEGIN IMMEDIATE` while a `SELECT` passed, and READ at `pragma.c:2587-2592` (the second checked table begins a write operation, list-only bit or not, and 0x10000 checks all 23 tables). The listing also names the empty, index-less `vfs_gram_epochs` on every call (EXECUTED), so decision 4 issues `index_list` plus `ANALYZE "main"."vfs_gram_epochs"`, another writer, on every commit of a never-reindexed store. The Intent's "pays one listing statement" and the Scale section's "under 0.09 ms" are measurements with no rival writer, and decisions 3 and 4 reason about lock holds as if only the `ANALYZE` on a crossing commit wrote. Consequence if built: every committed mutation takes the one SQLite writer lock three times instead of once. For the high-concurrency agent audience, each extra acquisition can wait up to `busy_timeout` (5,000 ms) behind a rival and then end in a warning. Under a steady writer this repeats on every write, because a failed step changes nothing. Fix text: the spec must decide how often the step may take the write lock on a commit that changes no table's size tenfold, and pin it by count. Three directions: (a) gate the listing on a read-only check vfs can make cheaply; (b) single-flight the step per host off the committing caller, coalescing commits, which is the direction decision 4 already names; (c) accept one acquisition per commit and say so in Intent, Scale and decision 3. In every case, add: "A listed table that holds no rows is skipped", and change criterion 4 to: "a one-file write to the store of criterion 2 issues exactly N statements for which `is_statistics_statement` is true", with N decided, plus a criterion that runs a one-file write while a rival holds `BEGIN IMMEDIATE` and counts the step's statements that wait.
2. **M1. Steps that run together repeat the same analysis** (Decision 4, Design "Scale"). EXECUTED in `probe_dup.py`: two connections that list before either analyzes both name `vfs_entries`, and a listing taken after 7 of 13 indexes were analyzed still names it. So K writers committing near a crossing each run the full per-index analysis, one after another, under the write lock. The claim "total analysis over a store's growth stays within a small constant of one full analysis" is evidenced for one writer only. Closes with: a decision that bounds concurrent steps within a host (for example, a step that finds one running on its host is skipped, since the running step or the next commit covers it), the cross-process profile named honestly, and a count pin: two concurrent writes on one host that cross together issue one set of `ANALYZE` statements for `vfs_entries`.
3. **M2. A re-analysis that stops partway is not picked up by the next commit** ([Decision 8](../specifications/active/2026-11-07-sqlite-gathers-planner-statistics-after-each-write.md#8-the-step-is-best-effort-a-sqlalchemyerror-or-oserror-inside-it-stops-the-step-at-that-statement-and-adds-one-warning-severity-unavailable-error-to-the-committed-ops-result-retryable-whose-detail-names-the-statistics-step-and-the-statement-the-results-success-and-observations-are-unchanged-and-the-step-does-not-retry), Decision 4). EXECUTED in `probe_partial.py`: with statistics taken at 300 rows and the table grown to 11,201, the table was due. After 2 of its 13 indexes were analyzed, the listing no longer named it, and `ix_vfs_entries_deleted_at` kept `300 300`. INFERRED from the loader: any non-partial index's fresh row resets the table's row estimate, so the tenfold check passes. Decision 8's reason, "the next commit's listing names the same table again", holds only when nothing was analyzed. Consequence if built: a step that hits `SQLITE_BUSY` mid-table, which H1 makes likely, leaves fresh and up-to-tenfold-stale statistics mixed. Statistics stale from a tiny first write give the tombstone index the trap's estimate until the next tenfold. Closes with: a decision whose reason holds when the step stops partway (for example, on a failure the step deletes that table's `sqlite_stat1` rows, so the next listing names it as unanalyzed), and a criterion with a listener that raises on the second `ANALYZE` of a crossing commit, after which the next write's step analyzes every index of `vfs_entries` (counted).
4. **M3. The below-3.46 behaviour is misstated, and that SQLite is common on supported interpreters** ([Decision 3](../specifications/active/2026-11-07-sqlite-gathers-planner-statistics-after-each-write.md#3-sqlite-decides-which-tables-are-due-vfs-runs-the-listing-after-every-commit-and-analyzes-only-what-it-names-with-no-write-counter-of-its-own), Decision 11, Scope "Out"). The spec says the step's fresh session has queried nothing, so below 3.46 the listing names nothing. But the session draws a pooled connection that has usually served the verbs' queries, and 3.45 analyzes any table whose statistics that connection's planner used, at a 25× threshold (READ, `version-3.45.3` `pragma.c` and `where.c:3971`). Debian 12, Ubuntu 24.04 and RHEL 9 system Pythons link 3.40.1, 3.45.1 and 3.34.1 (INFERRED from published package versions), while every CI interpreter links 3.50.4 or 3.53.1 (EXECUTED). Decision 11 drops the two-channel no-statistics plan leg on the premise that no written store is left without statistics, which is false there. Closes with either option. (a) The step reads `dialect.server_version_info` and does nothing below `(3, 46)`, which makes "inert" true by construction and leans on SQLAlchemy's own fact, plus a test that patches the version below 3.46 and counts 0 statistics statements. (b) Decision 3 states the real below-3.46 behaviour. In both cases, decision 11 keeps the two-channel spec's no-statistics leg (a `MULTI-INDEX OR` and no `SCAN`), run after deleting `sqlite_stat1`'s rows.
5. **L1. The step's warning should not be retryable** (Decision 8, Design `engine.py`). A `retryable` error on a committed write's Result invites an agent to retry a write that already landed. Fix text: "The warning is `retryable=False`: the write committed and is not to be retried; the next commit repeats the step on its own."
6. **L2. A cancellation during the step reaches the caller after the commit** (Decision 1). Fix text: "A cancellation or caller deadline that lands during the step propagates after the mutation committed, as one landing between commit and return does today; the step's longest wait is one `busy_timeout`, and `_mutate`'s docstring says so."
7. **L3. Decision 15's fix route and regression class** ([Decision 15](../specifications/active/2026-11-07-sqlite-gathers-planner-statistics-after-each-write.md#15-the-gram-segment-and-lexical-plans-after-reindex-are-measured-during-the-build-recorded-in-the-landing-notes-and-a-regression-blocks-the-landing)). Fix text: "A regression found here is not fixed under this review: the spec gains a decision and a new dated spec review before the build continues. A regression is a statement that, under vfs's statistics, plans a full SCAN of a table holding more than 10,000 rows, or seeks a different index than it seeks without statistics, where the table holds more than 10,000 rows."
8. **L4. Criterion 3's store sits just above a plan flip** (Design `test_statistics.py`, criteria 2 and 3). EXECUTED in `probe_flip.py`: the fan and the `kind` glob scan at 2,500 rows and seek the path index at 3,000, on 3.50.4 and on 3.53.1. The fixture's 3,221 rows leave a few hundred rows of margin. Fix text: "The store is 400 roots × 25 files, 11,201 entry rows, the memo's measured size; criterion 2's `deleted_at` row reads `11201 11201`; the tests that build it are marked `slow`."
9. **L5. Build the compared statements with SQLAlchemy's quoting** (Decision 7, Design `engine.py`). SQLite prints `%w`-escaped names, and a bare f-string diverges on a schema or name holding a double quote. Fix text: "The own-table statements and every `ANALYZE` are built with `dialect.identifier_preparer.quote_identifier`, which always quotes and doubles an embedded quote, as SQLite's listing does."
10. **L6. The diagram's first-touch edge reads backwards** (Architecture). Fix text: replace `FT --> STAT` with `FT -- "no step" --x STAT`, so the edge itself says that first touch writes no statistics.
11. **H2 (added on re-read). Other open connections never see a later analysis** ([Decision 10](../specifications/active/2026-11-07-sqlite-gathers-planner-statistics-after-each-write.md#10-writers-that-cross-together-analyze-once-each-step-runs-under-its-own-write-lock-so-a-second-writer-lists-only-after-the-first-has-committed-its-statistics), Intent). EXECUTED (`probe_xconn2.py`, SQLite 3.50.4 and 3.53.1): statistics taken at 300 rows, connection A plans the fan, then connection B grows the table to 11,201 rows and commits an `ANALYZE` (`deleted_at` reads `11201 11201` on disk, `schema_version` unchanged). A then plans a SCAN after its next query and after a new transaction, and its listing names `vfs_entries` as due. A fresh connection plans the path index and finds nothing due. Only `ANALYZE "main".sqlite_schema` on A brings it to the file. The memo's 1.7 result ("its next statement reloads the statistics") was observed when the first `ANALYZE` created `sqlite_stat1`, which is a schema change; later analyses change no schema. vfs keeps file connections in a pool with no recycle (READ, `engine.py:176`, SQLAlchemy's default `AsyncAdaptedQueuePool`), and other processes keep their own connections. Consequence if built: once a store's first write has created `sqlite_stat1`, every pooled connection, and every other process, plans from the statistics it loaded then, which may be a three-row first write's, until that connection serves a write. That write then re-analyzes the table again under the lock, once per stale connection per crossing. So the Intent's "at every size" fails on a file store under concurrency, and so does decision 10's "analyze once". Closes with: a decision that makes every connection, in this process and in others, plan from the file's statistics after a crossing commit, and says what that costs. Note that a reload outside a write transaction takes the write lock (EXECUTED: `ANALYZE "main".sqlite_schema` behind a rival's `BEGIN IMMEDIATE` failed "database is locked"; it costs 0.008 ms when free). Directions the author may weigh: a lock-free read at checkout that detects moved statistics (for example a `sqlite_stat1` row compared with the value the connection last loaded) and then reloads inside the next write transaction or recycles the connection; or a crossing commit that makes every connection re-read the schema. Each needs its own evidence. Also needed: a criterion that, after a second crossing committed on one connection, counts 0 own tables in another open connection's listing and the path index in its fan plan, and an extension of criterion 6 to a second crossing.
12. **M4 (added on re-read). Under a caller deadline shorter than one analysis, a crossing write never completes** (Decision 1, Decision 11). The step now runs before `COMMIT`, so a cancellation during a crossing's analysis rolls back the whole mutation (L2's settlement). The table stays due, so the next write runs the same analysis, and under the same deadline it is cancelled again. Every later write to that store then fails for that caller. INFERRED from decision 11's own sizes: about 0.9 µs a row, so a 10 s deadline is reached near eleven million rows on the measured machine, and sooner on slower disks. Decision 11's "the rare cost lands on one commit" assumes that commit finishes. Closes with: a decision that names this and bounds it, for example by committing the mutation first and running a crossing's analysis in its own `BEGIN IMMEDIATE` transaction straight after. That transaction re-lists under its own lock, so it stays single-flight and atomic, and its cancellation loses only the statistics. Or the decision accepts the profile in words, naming the deadline arithmetic and the direction. A criterion counts the outcome: a write cancelled during its step is retried and commits.
13. **L7 (added on re-read). Name where a rival's retries run out** (Decision 11). `with_retry` defaults to four attempts (READ, `engine.py:138`), each waiting up to the 5,000 ms `busy_timeout`. So a crossing hold past about 20 s fails a rival writer outright instead of delaying it, near twenty-two million rows at the measured rate. Fix text: "Past about twenty million rows a crossing's hold outlasts a rival's four attempts of 5 s each, and that rival's write returns `conflict`; this is part of the profile, and the direction is the same."
14. **L8 (added on re-read). Two failure-path gaps** (Decision 9, Design `engine.py`). The spec does not say what happens when the reload itself fails. It also does not say that `server_version_info` exists only after SQLAlchemy has initialized the dialect on a first connect.
