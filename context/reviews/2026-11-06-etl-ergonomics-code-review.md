## Findings, most severe first

1. **Low (contract: decay) — the kernel docstring says each storage receives "the list" the walk produced; it receives a per-mount, depth-sorted, rebased list derived from it** (`src/vfs/base.py:979-980` against `src/vfs/base.py:2621-2648`). The sentence "walked once here into the list every storage receives" is the spec's own wording (decision 2) and its point holds: one materialization, lists at the seam; but `_route_entry_batch` groups the rows by binding, rebases each with `without_mount` and hands each backend `sorted(group, key=depth)`, so no storage receives that list. Fix text: "*entries* is any iterable of :class:`Entry`, walked once here into a list; each storage then receives its own depth-sorted slice of it, never the iterable."
2. **Low (adversarial: question) — an iterable that raises while it is walked propagates out of `write` as a raw exception, and no contract says so** (`src/vfs/base.py:1711`, `src/vfs/base.py:2621`). EXECUTED, scratch script `gen_raises.py` under the scratchpad: a generator that yields one `Entry` then raises `ValueError` makes `await fs.write(gen(), parents=True)` raise `ValueError: source broke mid-walk`, and `/a.txt` does not exist afterwards (nothing was dispatched, so there is no partial state). This is the caller's own exception surfacing before the gate, the same as `list(gen())` would, and the behaviour predates this diff; what the `Iterable` annotation changes is that a pipeline's generator is now the invited shape, so the docstring should say where its failures go. Fix text, a sentence after the one above: "An exception the iterable raises while it is walked propagates to the caller unchanged; nothing has been dispatched at that point."
3. **Low (tests: low) — the subprocess helper uses `check=True`, so a broken import surfaces as a `CalledProcessError` traceback instead of an assertion that shows the interpreter's stderr** (`tests/test_package.py:47`). A regression that makes `import vfs` fail in the child would fail this test by exception, with the child's stderr hidden in the exception's attributes rather than printed by pytest. Fix text: `run = subprocess.run([...], capture_output=True, text=True)` then `assert run.returncode == 0, run.stderr` before `return run.stdout.strip()`.
