## The author's questions, answered first

1. **Is a fixed work budget on the fuzzy fallback consistent with AGENTS.md's rule against designed scale caps, and is its size and unit well chosen?** READ, EXECUTED, INFERRED. Consistent in kind: the budget bounds a heuristic's search, not a file, a corpus or a batch, and the exact path stays unbounded and linear. The tree already does this: grep's verify runs under a declared wall budget and reports a truncation (`src/vfs/storage/backends/database/grep.py:215`, `:264`; `offload.py:4`). The refusal is classified `invalid` and tells the caller what to send, so it does not make an agent guess (constitution Article 2). Two things are wrong, though. The unit misses a cost: a middle line whose Levenshtein product is zero still costs a loop step, and an edit of empty middle lines is quadratic while the budget charges almost nothing (H1). The size is argued in the wrong unit: decision 4 sizes one million as line comparisons, but the units that run out first are Levenshtein cells, where one million covers about 150 to 250 lines of real code (M1). AGENTS.md also says a suboptimality must not become a declared limit; the spec names the Rust kernel as the future direction in Scope, which is what that rule asks, so with H1 and M1 fixed the budget is acceptable.
2. **Does any existing caller or test depend on the full multi-match error listing, or on the current argument shapes of the replacers, `get_line_number` or `get_context_lines`?** EXECUTED. No caller in `src/` does: the only importer of the engine's functions is `src/vfs/storage/editing.py:18` (`apply_edits`); every other import takes `EditOperation`. The multi-match listing is asserted by one test, `test_replace_reports_ambiguous_matches_with_line_context`, with two matches, under decision 5's three, so it holds; no row of `tests/support/storage_contract.py` reads "Found", "Match at line" or a method name. The argument shapes are a different story: `tests/storage/test_replace.py` calls `line_trimmed_replacer(content, find)`, `block_anchor_replacer(content, find)`, `get_line_number(content, pos)` and `get_context_lines(content, start, end)` at 22 call sites across 18 test functions, and the Design changes every one of those shapes while saying all 39 functions pass unchanged (H2).
3. **Is keeping the match inline acceptable under the production posture, given the edit runs inside the writer transaction?** EXECUTED, READ, INFERRED. Not with the reason decision 6 gives. The budget makes one call's stall bounded: my probe ran one million two-row cells in 0.11 s and one million matrix cells in 0.17 s on this machine (a reviewer's measurement, not a criterion). But the budget is per `replace()` call, and `edit_rows` makes one call per target and edit (`writes.py:299-308`), so a 10,000-target edit whose edits miss holds the loop for that per-call stall 10,000 times, serially, while the writer transaction is open. Active spec 175 already gives `edit_rows` an executor. Inline can be the right choice for small edits; the decision must say what the stall is and why it is accepted, or hop past a threshold (H3).

## Scale and the production posture

- `_Lines`: one split per `replace()` call, three lists linear in the content's lines; bounded by the content (INFERRED from the Design).
- The block-anchor candidate search: one pass for first anchors, one sorted index list of last anchors, one bisection per first anchor; linear plus a log factor (INFERRED).
- The block-anchor similarity loop: grows with candidates times middle lines, and the spec's units charge only candidates and cells, so an edit of empty middle lines grows with the square of the input outside the budget (EXECUTED: 499,500, 1,999,000 and 7,998,000 calls at 1,000, 2,000 and 4,000 lines, four times per doubling, 0 cells charged; H1).
- The line-trimmed scan: one unit per line comparison, every inner step charged, so it is bounded by the budget; each unit is a C-level string compare whose cost grows with line length, a note rather than a finding, since the total stays within the budget times the old text's longest line.
- The multi-match error: three blocks whatever the match count; `ReplaceResult.matches` stays linear in the matches (L3).
- The request: the budget is per call, so the request's fuzzy work is the budget times targets times edits, all on the event loop inside the writer transaction (H3). No SQL statement changes; the engine floor (Oracle's 1,000-element `IN`, SQL Server's binds) is not touched.
- Designed scale cap: none in the sense AGENTS.md forbids (question 1); the Rust kernel is named as the direction.
