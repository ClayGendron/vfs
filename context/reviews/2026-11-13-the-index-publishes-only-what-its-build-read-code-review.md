**M1 — the slice's size read re-reads every candidate the byte cut left behind, so over-budget entries cost up to 256 size-read rows and 256 rendering reads each.** Where: `indexing.py:378` to 382 (`sizes … .limit(limit)`, `_slice_ids`, `cursor.next_after = kept[-1]`). What I ran: `count_probe.py` (scratch), which counts the rows `_slice_ids` is handed during the chunk pass, and `length_probe.py`, which overrides SQLite's `length` on each connection with a counting function. What I saw: 300 text files over a budget patched to 1,000 bytes gave 300 slices and 44,160 size-read rows; 1,000 gave 223,360; 40 files of 1 MiB + 100 bytes at the real budget gave 820 rows (40·41/2); 60 rendered PDFs each a slice of one (budget patched to 1) gave 1,830 `length()` evaluations in the chunk pass, against 60 when they fit one slice. The law: each slice reads the next `min(256, remaining)` candidates and keeps `k` of them, and the next slice starts after the `k`-th, so size-read rows are `256 × slices` and each candidate is read `256 / k` times; for a run of entries each past `CHUNK_SLICE_BYTES` that is 256 reads per entry, growing faster than the entries visited. Why it matters: decision 14 bounds the meter "by 256 times `RENDER_CHARS` a slice" and that is true, but the same rendering is measured again by every slice whose window it sits in: a nightly batch of 10,000 binaries whose renderings pass 1 MiB is 10,000 slices, each computing `length` over up to 256 renderings of up to 2,097,152 characters, about 2.6 million rendering reads where one each would do; on Postgres in a UTF-8 database `length(text)` detoasts the value it counts (INFERRED from the engine's documented `textlen`), and on SQLite it reads the overflow pages. This rides the per-batch multiplier and the rebuild after a generation change, which re-splits the corpus. Fix text: "`ChunkCursor` gains `pending: list[tuple[int, int]]` and `next_pending`, the size read's candidates past the cut with their meters. `chunk_dirty` cuts from `cursor.pending` first, and reads only `limit - len(cursor.pending)` more rows past the last pending id; `next_pending` is adopted with `next_after` once the slice commits, so a redrive re-reads from the same place. The body read keeps its terms, so a stale meter only mis-sizes one slice." Pin: `length_probe.py`'s world as a node, 60 rendered PDFs each a slice of one, counting the size-read rows handed to `_slice_ids`: 60, not 1,830.
