# Mature runtimes and engines bound work with one absolute deadline value passed explicitly, check it between chunks in one helper that also mints the stop, and run it on one lazily made pool per process or loop; vfs carries a bare float through twenty signatures, checks it forty-three ways, and owns two pools over one rayon engine

On 2026-11-07 Clay asked, after a structural review of the day's eleven landings: "Please research prior art before writing these specs, ensure we are following good patterns and then write up the specs." The review had found that the wall-time deadline is carried as a bare `float`, that the clock is read at 43 sites under four differently named "every 64th item" cadences, that each site that reaches the wall mints its own truncation record, and that the router and the engine host each own a `ThreadPoolExecutor` of `os.cpu_count()` threads with the same lifecycle rules written twice. This memo answers one question: how do mature runtimes and engines represent a deadline, how often and where do they check it, and who owns the pool the work runs on. Three researchers, each a fresh agent with no knowledge of the author's reasoning, worked 45-minute boxes and finished inside them; the author ran one further experiment. The studies, the briefs, the experiments and the clone logs are under [the studies folder](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/). There is no intention: the work is a refactor of a concern the tree already has. Two earlier memos settled that the work leaves the loop and that a shut pool serves its remaining hops inline, [matcher offload](2026-08-18-matcher-offload.md) and [the close lifecycle](2026-08-25-close-lifecycle-and-shutdown-race-prior-art.md); this memo stands on them and repeats neither.

Labels: EXECUTED means a command ran here and the claim reports its output. READ means read in a file or page cited by path or URL. INFERRED means this memo's reasoning from the two. Every clock below is EXECUTED on one Apple M1 Pro (10 cores, macOS, Darwin 25.5.0) under CPython 3.13.11; a clock here is a fact about that machine, never a test budget.

## The answer

READ across the five runtimes: every one keeps the deadline absolute on one monotonic clock inside one explicit value (`CancelScope`, `Instant`, `context.Context`), converts a relative timeout to it exactly once at the entry point, re-derives the remaining time from it at every hop, passes it explicitly and never stores it, and classifies a stop at the deadline distinctly from a plain cancel. READ across the four engines: the check sits at the bottom of a loop over a unit of work or between chunks, never per innermost step; one helper or macro owns it, hand-placed where loops are; the stop is one record minted in that place; and the rows or hits produced before the stop are kept. READ across the five pool owners: one lazily made pool per process or per loop, sized by the machine or a flat token count and never by the caller, left to let running work finish at close, and, where a rayon engine sits beneath, kept narrow because the Python pool is a concurrency gate and not a source of throughput. EXECUTED on this machine: one native matcher call saturates all ten cores, and twenty Python threads over it buy no throughput and thirteen times the latency. INFERRED: vfs follows the first rule in spirit, since every stage takes an absolute deadline and cuts the budget at worker start, and breaks it in form, since the value is a bare float and the law lives in a ninety-line docstring; it breaks the second rule, since each loop owns its own cadence constant and its own truncation text; and it breaks the third, since two pools of the full core count sit over one rayon pool of the same width.

## 1. The deadline value

1.1 READ ([study 01](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/01-runtime-deadline-primitives.md), sections 1 to 5). trio's `CancelScope` converts a relative deadline on `__enter__` and refuses to read `.deadline` on an unentered relative scope; anyio's `move_on_after` and `fail_after` compute `current_time() + delay` at creation; tokio's `timeout(Duration)` does `Instant::now().checked_add` once and `timeout_at` takes an `Instant`; Go's `WithTimeout` is literally `WithDeadline(parent, time.Now().Add(timeout))`; the gRPC guide says a timeout becomes a deadline when the application starts the call.

1.2 READ (the same study). Across a process hop the relative form is re-derived from the absolute one and never carried: grpc-go sends `time.Until(deadline)` rounded up as `grpc-timeout` and rebuilds a `WithTimeout` context on arrival. In process the one value is passed explicitly; Go's package documentation makes it the first parameter, never a struct field. At a thread hop every system gives up on interruption: trio and anyio do not carry the deadline into `to_thread.run_sync`, and the thread may only poll `from_thread.check_cancelled()`; tokio's `spawn_blocking` task cannot be aborted once started.

1.3 READ (the same study). The stop is a distinct classification the caller can branch on: trio's `CancelReason(source="deadline")` and `TooSlowError`, anyio's `TimeoutError` with reason "deadline exceeded", tokio's `Result<T, Elapsed>`, Go's `DeadlineExceeded` against `Canceled`. No primitive returns partial results; the caller keeps what it accumulated and reads a flag.

1.4 READ in vfs (`offload.py:28-30`, `base.py:2095-2105`, `glob.py:350-435`, `rights.py:434-470`). vfs already holds the absolute deadline from call start and cuts the budget at worker start, which is the gRPC rule. EXECUTED: `grep -rn 'deadline: float' src/vfs` counts 20 signatures; `grep -rn 'monotonic()' src/vfs` counts 43 call sites in 16 files; the budget is recomputed from the deadline as `max(0.0, deadline - monotonic())` at six Python sites and converted to an `Instant` two different ways in the crate (`python.rs:124,144` inline, `python.rs:240` through `deadline_after`).

## 2. The cadence and the check's owner

2.1 READ ([study 02](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/02-engine-interrupt-cadence.md), sections 1 to 4). SQLite's check is one label in the virtual machine (`src/vdbe.c:1147`) reached by `goto` from eleven loop-bottom opcodes, deliberately not on every opcode, with the source comment recording the measurement: about 1.5% faster under cachegrind. Postgres's check is one macro, `CHECK_FOR_INTERRUPTS()`, hand-placed at 327 sites in 148 backend files, once per tuple in the executor and once per page in the heap scan, with the comment that a higher-level check cannot stop a scan over many pages of dead tuples. zoekt turns `MaxWallTime` into a context deadline once at request entry and polls `ctx.Done()` at exactly two sites, once per shard before work and once per document, never per match. Lucene's `TimeLimitingBulkScorer` checks once per chunk, a chunk starting at 100 documents and growing by half each time, with the comment that this avoids checking the timeout for every document scored.

2.2 READ (the same study). Every engine keeps what it produced before the stop and reports the stop in one place: SQLite's `SQLITE_INTERRUPT` with the rows already returned standing, Postgres's one `ereport`, zoekt's counters on `Stats` with a nil error, Lucene's exception caught one frame up and turned into a `partialResult` flag with the collected hits kept.

2.3 EXECUTED ([study 02's experiment](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/experiments/02-engine-interrupt-cadence/)). `time.monotonic()` costs about 16 ns a call on this machine, with a resolution of 41.7 ns. Over a bare loop of a million trivial items, a check every item costs about 3.0 times the bare loop, a masked check every 64th about 1.7 times, and every 1,024th the same 1.7 to 2.1 times: the per-item mask test is the cost, not the clock. Lucene's shape, an outer loop over chunks that reads the clock once per chunk and an inner loop with no test, costs 1.07 times the bare loop at 64 and 0.98 at 1,024, which is nothing.

2.4 EXECUTED ([the author's experiment](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/experiments/04-deadline-type-cost/output.txt)). The same bare loop costs 28 ns an item; the inline `i % 64 == 0 and monotonic() > deadline` vfs writes today costs 60 ns an item; a `Deadline` object with `__slots__` whose `tick()` counts internally and reads the clock every 64th call costs 91 ns an item; its `expired()` read on every item costs 91 ns an item. INFERRED: a value type's method costs about 30 ns an item over the inline test in CPython, which is noise against a row's real work (a glob judgement or a posture lookup runs microseconds) but is paid per item, where the chunked shape of 2.3 is paid per chunk; a helper should therefore offer a chunking iterator for a Python hot loop and reserve a per-item method for loops whose items are slow.

2.5 EXECUTED ([study 01's experiment](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/experiments/01-runtime-deadline-primitives/)). Under a fake clock whose deadline falls at tick 1,000, a count cadence of 64 overruns the deadline by 23, 49 and 43 items at item costs of 1, 7 and 50 ticks, and a cadence of 128 by 23, 113 and 107; a per-item clock read and a timer-set flag overrun by none. INFERRED: a count cadence bounds the overrun in items, never in time, so the right N is a per-stage question about how long one item can take, the Postgres dead-page argument applied to a glob program or a grep body.

2.6 READ in vfs. Four cadence constants hold the value 64 under four names: `_RESIDUATIONS_PER_CHECK` (`base.py:158`), `PAIR_ROWS_PER_CHECK` (`glob.py:266`), `POSTURE_PATHS_PER_CHECK` (`rights.py:168`) and `PROGRAMS_PER_CHECK` (`glob.rs:223`), with a fifth helper `_past(deadline, position)` (`rights.py:1196`). The truncation record is minted by `_wall_record` in the router (`base.py:3478`), by six `WALL_TIME_CAUSE not in truncations` guards in storage grep (`grep.py:281-392`), once in glean (`glean.py:1120`) and once in reads (`reads.py:444`). The crate carries the batch skeleton twice, `verify.rs:196-240` and `glob.rs:291-310`, and `glob.rs:35` imports `BatchOutcome` from the sibling grep kernel rather than from a shared place.

## 3. Who owns the pool

3.1 READ ([study 03](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/03-who-owns-the-worker-pool.md), sections 1 to 6). asyncio's loop owns one lazily made default executor of `min(32, cpu_count + 4)` threads, shuts it without waiting at `loop.close()`, and refuses a submission after `shutdown_default_executor` with `RuntimeError`. anyio keeps one process-global thread pool whose idle threads retire after ten seconds and bounds it with one `CapacityLimiter(40)` per event loop, overridable per call. trio keeps a process-global LIFO cache of daemon threads and one limiter of 40 per run, a number its source says was "pulled out of the air", and warns against CPU-bound work in threads at all. SQLAlchemy's asyncio extension has no worker pool: greenlets on the loop thread. polars builds one process-global rayon pool, `POLARS_MAX_THREADS` or `available_parallelism`, fixed before first use, and its guide says adding your own parallelism over it is very unlikely to help and may compete for resources. The pyo3 parallelism page says to detach the GIL around rayon work and shows two Python threads over a sequential kernel roughly matching one parallel Rust call rather than adding to it.

3.2 READ in vfs. rayon-core 1.13.0's global pool is `available_parallelism` wide unless `RAYON_NUM_THREADS` is set, and vfs-core builds no pool of its own, so every `par_iter` in the crate runs on one process-global pool of ten threads on this machine. The router's verify pool and the engine host's offload pool are each `OFFLOAD_WORKERS = os.cpu_count()` wide (`base.py:2050`, `engine.py:238`), so a host running both can have twenty Python threads each inside a native call that itself fans out over ten rayon threads.

3.3 EXECUTED ([study 03's experiment](studies/2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools/experiments/03-who-owns-the-worker-pool/)). With N Python threads each submitting the same batch of 256 bodies of 1 MiB to `ContentMatcher.count_lines` at once, aggregate throughput for a literal pattern was 86.2, 88.6, 96.9, 100.7 and 84.7 GiB/s at N = 1, 2, 4, 10 and 20, and for an automaton pattern 2.64, 2.56, 2.74, 2.05 and 2.66 GiB/s. One call alone took 0.095 s; with ten co-submitters 1.22 s; with twenty 1.88 s. INFERRED: one call already saturates the machine, width past one buys latency and not work, and the Python pool is therefore a concurrency gate whose only job is to bound how many callers wait inside a native call at once.

3.4 INFERRED. The two vfs pools exist for one stated reason, in the chained-grep spec's decision 4: a batch may hold a worker for the whole ten-second wall, so it must not share asyncio's default executor with `getaddrinfo`. That reason argues against the default executor, not for two pools: one package-level pool of the core count, shared by the router and every storage host in the process, keeps DNS off it and halves the thread count over the rayon engine. The pool's lifecycle rules, lazy creation, shutdown without waiting, inline service of a hop captured before the shutdown, and re-minting on the next capture, are then written once as a type instead of twice as prose.

## 4. What the three studies agree on, for the spec

4.1 INFERRED, the synthesis. One value type holds the absolute monotonic deadline and is passed explicitly, never stored on a long-lived object; a relative budget is converted to it once at the verb's entry; the remaining time is derived from it at every hop, so time spent queued shortens the budget; the stop is classified distinctly and the work produced before it is kept. The check lives in one helper that the loop calls between chunks, not in a mask the loop writes per item; the chunk size is the helper's default and a stage overrides it only with a reason about its item's cost. The truncation record is minted beside the deadline, once, with the stage's guidance text as its one parameter. In Rust the same helper holds an `Instant`, the batch skeleton and the outcome type, and both kernels use it. One lazily made pool per process serves every hop; its width is the machine's core count and never a caller's knob; it shuts without waiting and lets a captured hop finish inline, as [the close lifecycle memo](2026-08-25-close-lifecycle-and-shutdown-race-prior-art.md) already settled.

4.2 INFERRED, where the systems disagree and the spec must choose. The cadence shape splits three ways, a clock read per scheduler tick (trio), a count of operations owned by one budget (tokio's 128, SQLite's `nProgressOps`, Lucene's growing chunk), and a timer that sets a flag the loop reads (anyio, Go, Postgres). The timer shape is exact and costs one more thread and one flag crossing pyo3; the count shape is what vfs has today and what the Rust kernels can take without a new crossing. The width of the one pool is the core count in vfs's own measurement and "a few slots" in study 03's reading; the experiment shows the difference is latency under contention, not throughput.

## What this memo does not settle

The chunk size per stage: an experiment that times the slowest single item of each stage (one glob program step over a 255-character segment, one grep body of the byte budget, one posture lookup, one residuation) and sets each stage's N so that N items overrun the wall by less than a declared fraction of it. The cost of `Instant::now()` in the Rust kernels relative to one glob step: an experiment in `cargo bench` or a criterion harness, never a test. Whether vfs should build a named rayon pool of its own as polars does, so the Rust width is a declared fact rather than rayon's default read from the environment: a placeholder memo when the first host reports oversubscription. Whether the pool's width should be measured again on a CI runner and under free-threaded CPython: the same oversubscription script, run there. Whether the stop should be reported as an exception caught one frame up, Lucene's shape, or as the `(results, completed)` pair vfs returns today: the pair matches the runtimes' flag-and-keep rule and no study found a reason to change it, so the spec keeps it unless a kernel needs the other.

## One line

Keep the deadline absolute in one explicit value, check it between chunks in one helper that also mints the stop, and run every hop on one lazily made pool of the core count, because that is what trio, anyio, tokio, Go, gRPC, SQLite, Postgres, zoekt, Lucene and polars agree on, and vfs today has the rule right and the form wrong in forty-three places.
