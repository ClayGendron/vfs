# Single-product documentation sites put the content types across the top, the product's domains down the side inside each type, and keep tutorials one short ordered path that later branches by domain and never by level

On 2026-11-12 Clay asked, after the new docs site was first built from `documentation/` with a left sidebar only: "Can you have some opus agents study prior art of how other docs sites that use diataxis layout the page? I probably want to have some horizontal nav buttons along with the vertial ones on the left, but so we grow more and more docs, will we want to organize tutorials by just starting out and advanced topics, or group files by domain?" The question this memo answers is what a documentation site that follows Diátaxis puts in a horizontal bar and in a sidebar, and how it groups tutorials as the set grows from five to thirty. Four researchers, fresh Opus agents with no knowledge of the author's reasoning, each worked a 30-minute box over public pages and the public source of each site's navigation, and all four finished inside or at their box (researcher 03 in about 7 minutes, 02 in 9, 04 in 11, 01 in 12, by the harness's clock). No reference clone was studied, so nothing was refreshed or licence-checked. Three deviations are recorded: researcher 03 saved no navigation outlines; researcher 04 could not reach one Gatsby post, which returned 404; and the one page of the Diátaxis site that addresses structure at scale had been removed from the live site, so researcher 04 read it from the framework's repository history. The brief, the four studies and the saved outlines are under [the studies folder](studies/2026-11-12-how-diataxis-docs-sites-lay-out-navigation-and-group-tutorials/). There is no intention: the memo informs the navigation of the docs site and the spec that will replace the published site with it; none exists yet. This memo commits to nothing; the spec that stands on it decides.

Labels: EXECUTED means a command or fetch ran in this study, by a researcher or the coordinator, and the claim reports its output. READ means read in a page or file cited by URL, or in one of the four studies, each of which cites its own sources by URL and read date. INFERRED means this memo's reasoning from the two.

## 1. The answer in one paragraph

INFERRED from the four studies, which reached the same shape independently. The horizontal bar should hold the content types, not the product's domains: a front door (Introduction and Overview), then Tutorials, How-to guides, Reference and Explanation, each added only when it has pages, so four to seven entries at most. The sidebar should show only the pages of the chosen entry, grouped by the product's domains in one fixed order that is the same under every type. The home page should carry the other axis: a short overview and a map by domain whose rows link across the types. Tutorials should be neither sorted by level nor grouped by domain while there are five: they stay one ordered path, each page naming the one before it. When the set grows, the path stays as a short starting group and the rest is grouped by domain, with no "advanced" group, because most pages that would go in one are how-to guides and belong there under their domain.

## 2. When a single-product site has a top bar, the bar holds content types, and four to seven of them (READ, INFERRED)

READ in study 02: of the sites with a documentation-level bar, the ones documenting one product split it by content type (Docker's Get started, Guides, Manuals, Reference; React's Learn and Reference; Textual; Mintlify; FastAPI; Material's own docs), and the ones owned by a company with several products split it by product and put content types in the sidebar (Pydantic today, Polars, Svelte, Stripe, HashiCorp). Pydantic made that move when it had five products: its former nine content tabs are now sidebar groups under a product switcher. READ in study 02: the common count is four to seven entries, and the outliers show a cost. Textual has eleven tabs, five of them single pages that leave the sidebar empty. Stripe has ten and needs a "More" overflow that hides some. INFERRED: vfs is one install and one API, so its bar is a content-type bar, and it should stay short.

## 3. The sites that name Diátaxis mostly have no top bar at all, and put the four types at the top of a sidebar (READ)

READ in study 01: among sites that state they follow Diátaxis, the four types are the top level of a vertical sidebar on the Canonical sites (Ubuntu Server, Juju, LXD, MAAS) and their starter pack, and on pytest, Hypothesis and Briefcase. Only minterpy puts the four types in a horizontal bar. READ in study 01: "How-to guides" and "Reference" are kept almost everywhere; "Tutorial" is the name most often replaced (Get Started, First steps), and explanation is renamed most (Topic guides, Conceptual guide, Fundamentals). INFERRED: a top bar is therefore a choice the owner is making, not something the Diátaxis adopters do by default. The two findings fit together: the types are the first level of the tree on every single-product site, and a bar is a wide-screen way to show that first level. READ in study 02: Material hides its tabs below 1220 pixels and shows the tab names as the top level of the slide-out menu, so the bar is a shortcut to the first level, not a second navigation, and each tab name must also read well in that menu.

## 4. The product's domains live one level down, as the same groups inside every type, and again on the home page (READ, INFERRED)

READ in study 01: Ubuntu Server's How-to guides section has thirteen domain groups and its Explanation section repeats most of the same names; LXD, MAAS and Django's how-to index group by domain too. READ in study 02: no single-product site puts its domains on the bar; Mintlify, Material, Supabase and Tailwind all carry them as sidebar groups. READ in studies 01 and 04: the home page is where the two axes meet. Ubuntu Server, LXD, Juju and Django open with a domain index whose rows link into several types, and Canonical's own tooling text says the home page is "organized by subject, not by Diataxis type" and that the two views "are intentionally different". READ in study 04: Cloudflare and GitLab invert this, product or workflow first and type inside, and both are estates of many products. INFERRED: no site repeats the whole grid of types by domains at the top level. Each gives the second axis its own surface. For vfs that is the sidebar groups and the home page.

## 5. Every entry opens on a landing page that reads as an overview (READ)

READ in study 02: every bar entry on every site read opens on a landing page, which in Material needs the `navigation.indexes` feature. READ in study 04: the framework's author wrote that a landing page "should read like an overview", not a bare list, and Canonical's standard is a heading, one to three sentences, then links, with groups in the order of product concepts and lifecycle, never alphabetical. INFERRED: adding a bar means writing a short index page for each tab, which the site does not have today.

## 6. Tutorials stay one ordered list while the set is small, and the size at which sites add groups is about fifteen (READ, INFERRED)

READ in study 03: every set of up to about fifteen tutorials is one ordered list with no groups (Juju 1, LXD 1, SQLAlchemy 1 in 7 sections, PyTorch's basics 8, Django 8 plus 2, pandas 10, Vue 15), and groups first appear between fourteen and twenty-one (LangChain 14, Stripe 17, Kubernetes 21). READ in study 01: no type-first Diátaxis site read has more than ten tutorials. READ in study 04: the author's removed page set a lower line, about seven items to a list before another layer is added, and Canonical forms a sub-group when a subject has two or more articles. INFERRED: the studies disagree on the exact number, between seven and fifteen, and agree that five is well under it. The five vfs tutorials already form one path, so they need an order and a stated prerequisite on each page, and no groups.

## 7. Past that size, sites keep one short marked first path and group the rest by domain (READ)

READ in study 03: PyTorch has an eight-step Learn the Basics path and then 97 tutorials in 13 domain sections; TensorFlow has a Beginner tier and then 11 domain groups; Kubernetes puts a Basics group first; Terraform has Get Started and then Fundamentals and Use Cases. READ in study 01: Ubuntu Server, at only five tutorials, already splits into a Getting started path and Next steps by subject. INFERRED: the first path is ordered by what to learn first, and everything after it is grouped by what it is about. Using the same domain names as the how-to guides lets a reader step from a lesson to the guides on the same subject.

## 8. A split by level never holds: it is at most two tiers, and the advanced tier turns into domain groups or how-to guides (READ)

READ in study 03: where sites split by level it is two tiers only, and the second does not stay a level. TensorFlow's Advanced is eleven domain groups. FastAPI's Advanced User Guide says on its own landing page that its sections are "not necessarily 'advanced'". Django renamed its "Advanced tutorials" to "Follow-on tutorials". READ in study 01: Wagtail's "Advanced" section grew to 67 files of mixed types, and in Cloudflare's 52-row tutorials table 34 rows are labelled Beginner and one Advanced. READ in studies 03 and 04: the framework's page on tutorials against how-to guides calls the belief that tutorials are basic and how-to guides advanced a common mistake; a how-to guide can cover a basic procedure and a tutorial can teach something advanced, and the difference is whether the reader is at study or at work. INFERRED: "advanced topics" is not a group to plan for. A demanding lesson says so on the page, with its prerequisites, and a page that serves a reader with a task is a how-to guide whatever its difficulty.

## 9. The four types grow at different rates, so most growth lands in how-to guides and reference (READ, INFERRED)

READ in studies 01 and 04: tutorials stay few (Canonical writes "Ideally, there must be just one tutorial"; Gatsby has one; type-first sites hold one to ten), how-to guides grow into the hundreds (Ubuntu Server 153 files, LXD 87), reference grows with the product (Django 120) and mirrors its structure, and explanation is often the smallest set (Python and Sequin report little or none). READ in study 03: many pages called tutorials on large sites are how-to guides under another name (Stripe's and Supabase's quickstarts, Kubernetes's examples). INFERRED: a count near thirty tutorials is a signal to check each page against the study-or-work test before adding structure. The site reaching a hundred pages will mostly be how-to guides and reference, and the domain groups matter most there.

## 10. What the framework's author says, and what he no longer publishes (READ, EXECUTED)

READ in study 04: the author's pages say that getting started with Diátaxis "does not require you to think about dividing up your documentation into four sections", and of creating empty sections for the four types first, "Don't do that. It's horrible." A four-way top level is described as the usual outcome of the practice, not its aim. EXECUTED by researchers 01, 03 and 04: the page that held his guidance on structure at scale, "Diátaxis in complex hierarchies", returns 404 on the live site. EXECUTED by researcher 04: the framework's repository shows the file removed in commit c9534824 of 2026-08-03 with no reason given. INFERRED: the seven-item rule and the landing-page rule cited above are from that removed page, so they stand as what he wrote in 2023, carried forward by Canonical's practice, and not as current guidance from the framework's site. The rule against empty sections is live, and it supports adding each tab only when its pages exist.

## 11. What this means for the vfs site as built (INFERRED, READ)

INFERRED: today the site has pages for a front door and for tutorials only, so a bar added now would hold two or three entries (the front door, Tutorials, and History or a project entry) and grow as How-to guides, Reference and Explanation are written. READ in study 02: the Material features that make this shape are `navigation.tabs` for the bar, `navigation.sections` for domain groups in the sidebar, `navigation.indexes` for a landing page per entry, and `navigation.path` for breadcrumbs, with `navigation.tabs.sticky` optional. READ in study 02: Material's documentation carries a banner naming Zensical as its successor, and Polars has already moved to it. INFERRED: the navigation shape recommended here is ordinary and does not depend on the tool, so that fact bears on a later choice of tool and not on this one. INFERRED: the eight domain names in the brief (the file system and its calls, the command line, storage and databases, search, permissions and governance, AI agents and tool calling, mounts, operations) are the coordinator's reading of the product, not a studied finding, and the owner should set them before they become sidebar groups.

## What this memo does not settle

Whether a bar of two or three entries looks deliberate or thin on the vfs site before the other types exist is not known; the experiment is to build the current eight pages with tabs, sections and indexes turned on and view them at desktop width and below 1220 pixels. The size at which the tutorial list should become groups lies somewhere between seven and fifteen and rests on other sites' shapes, not on vfs's readers; the experiment is to revisit it when the tenth tutorial is written, with the site's own analytics if it has traffic by then. Why the complex-hierarchies page was removed is not stated in any source read; the experiment is to read the framework's issue tracker and news page for 2026-08-03. The phone behaviour of the sites that do not use Material was not measured beyond Docker's; the experiment is to load each at phone width in a browser. Counts for HashiCorp's tutorial library, Juju's tutorials and LangChain's older site were not taken; the experiment is the git-trees listing of each repository, named in studies 01 and 03.

## One line

Put the content types across the top, the product's domains down the side inside each type and again on the home page, and keep tutorials one ordered path that later becomes a short starting group followed by domain groups, with no advanced bucket.
