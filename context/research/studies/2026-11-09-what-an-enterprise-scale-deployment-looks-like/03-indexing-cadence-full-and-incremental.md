# Real search systems rebuild their whole index about once a week and refresh it every one to fifteen minutes; six full rebuilds a day has no precedent, and vfs's own `reindex` today rebuilds the whole posting set whenever anything is dirty

This is Researcher 03's study for the brief in [00-brief.md](00-brief.md): how often real search systems reindex, fully and incrementally, and what the vfs tree already assumes. The 45-minute box opened at 2026-11-09 09:11:45 EST and the study was finished inside it (the closing time is in the last paragraph). Every claim is labelled EXECUTED (a command run here, output recorded), READ (a page or file cited by URL or path and line) or INFERRED (reasoning from the two). All web pages were read on 2026-11-09. The arithmetic in sections 7 and 8 is the output of [experiments/03-indexing-cadence-full-and-incremental/cadence_arithmetic.py](experiments/03-indexing-cadence-full-and-incremental/cadence_arithmetic.py), recorded in [output.txt](experiments/03-indexing-cadence-full-and-incremental/output.txt) beside it.

The short version, said three ways. Full rebuilds are rare and reason-driven: the systems that schedule one at all do it weekly or monthly, and the systems that do not schedule one run it only when the schema, the analyzer, the index format or the embedding model changes. Incremental passes are frequent: one second inside a Lucene index, 45 seconds to a minute for a code-host poll, 15 minutes for SharePoint's continuous crawl and Microsoft's connector floor, ten minutes to an hour for most Glean connectors. The ratio between the two is the finding: a full pass runs 100 to 1,000 times less often than an incremental one, never six times a day.

## 1. Microsoft: SharePoint Server, SharePoint in Microsoft 365, and the Copilot connectors

READ. SharePoint Server's freshest mode is the continuous crawl: "a continuous crawl automatically starts at predefined time intervals. The default interval for continuous crawls is every 15 minutes", and the floor is one minute: "The shortest interval that you can set is 1 minute", changeable only through PowerShell, with the warning "If you reduce the interval, you increase the load on SharePoint Server and the crawler" ([Manage continuous crawls](https://learn.microsoft.com/en-us/sharepoint/search/manage-continuous-crawls)). This is a documented default, measured on nothing; it applies to on-premises farms of any size.

READ. The continuous crawl is paired with an automatic hourly-scale incremental sweep: "Such errors are retried during a 'clean-up' incremental crawl, which automatically runs every four hours for content sources that have continuous crawl enabled" (same page). So Microsoft's own layering is a 15-minute change pass plus a 4-hour error-retry pass, and neither touches the whole corpus.

READ. A full crawl in SharePoint Server has no schedule at all; it is reason-driven. The "Reasons to do a full crawl" list is ten items, every one an event: a new Search service application, a new or changed content source, a software update or service pack, an added or changed managed property ("A full crawl of all affected content sources is required for the new or changed managed property to take effect"), detecting "security changes that were made to local groups on a file share", resolving "consecutive incremental crawl failures", changed crawl rules, "replace a corrupted search index", a changed content access account ([Plan crawling and federation](https://learn.microsoft.com/en-us/sharepoint/search/plan-crawling-and-federation)). Four more are forced by the system, also events: a stopped crawl, a restored content database, a never-crawled source, a missing crawl-database entry. No periodic full crawl appears anywhere on the page.

READ. SharePoint in Microsoft 365 removes the schedule from the administrator entirely: "content is automatically crawled based on a defined crawl schedule. The crawler picks up content that has changed since the last crawl and updates the index", and a whole-site reindex is a last resort: "Reindexing a site can cause a massive load on the search system. Don't reindex your site unless you've made changes that require all items to be reindexed" ([Manually request crawling and reindexing](https://learn.microsoft.com/en-us/sharepoint/crawl-site-content)). Microsoft publishes no number for the hosted cadence; community estimates (15 minutes to an hour for a new document to appear) are not Microsoft's and are not used here.

READ. The Copilot (formerly Graph) connectors are the one Microsoft surface with a documented default for both passes. The Azure Data Lake Storage Gen2 connector's default row reads "Incremental crawl every 15 minutes; full crawl every week" ([ADLS Gen2 deployment](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/azure-data-lake-storage-gen2-deployment)). The platform's scheduling grid is "Recurrence: Daily, weekly, biweekly, or every four weeks" for the day and "Frequency: Repeat crawls within a day. Intervals range from 15 minutes to 12 hours" within it, so 15 minutes is the floor for either crawl type ([Deploy connectors, Guidelines for crawl settings](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/deployment-overview)). The File Share connector "only supports full crawl" ([File Share connector](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/fileshare-connector)), which on a Windows share means a weekly-grid full walk is the only pass.

READ. Microsoft states the purpose of the full pass in words that matter for vfs: "Use a full refresh in scenarios such as: Detecting deleted items. Recovering from incremental crawl failures. Updating ACLs. Modifying crawl rules. Updating the connection schema", "Incremental crawls don't currently process updates to permissions", and "Even when you use incremental refreshes, run full refreshes periodically to ensure data consistency between the source system and the search index" ([Guidelines for crawl settings](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/deployment-overview)). Two operational rules follow the same page and [Manage connectors](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/manage-connector): "System load can delay crawl start times by up to an hour", overlapping crawls are serialized ("If a crawl overlaps with the next scheduled crawl, the next crawl runs only if it's a different type"), and "items that aren't rediscovered during crawls for 28 days are automatically removed from the Microsoft 365 index", a 28-day horizon that is itself a cadence fact.

INFERRED. Across Microsoft's three surfaces the pattern is one shape: a change pass at 15 minutes (default and floor), an error-retry pass at hours, and a whole-corpus pass that is either weekly by default (connectors) or event-driven only (SharePoint Server, SharePoint Online). The whole-corpus pass exists to catch what a change feed cannot show, deletions and permission changes in a source the indexer does not own.

## 2. Elastic: connectors, Workplace Search, Elasticsearch, Lucene and OpenSearch

READ. Elastic's connector framework has two sync types with no default schedule published: "Full syncs" bring every document and delete the vanished ones, "Incremental syncs are only available after an initial full sync has successfully completed", and the recommended trigger for a full sync is a configuration event, "whenever Sync rules are modified" ([Content syncs](https://www.elastic.co/docs/reference/search-connectors/content-syncs)). The page is candid that incremental is a write saving, not a read saving: the connector still fetches all data from the source and skips a document when "a document already exists in Elasticsearch with the same timestamp"; "For small volumes of data, the performance improvement using incremental syncs will be negligible", and for large volumes "the performance impact can be huge".

READ. The retired Workplace Search product did publish defaults, four passes with four periods: full sync every 72 hours ("synchronizes all of the data from the content source ensuring full data parity"), incremental sync every 2 hours ("synchronizes updates to the data at the content source ensuring high data freshness"), deletion sync every 6 hours ("ensuring regular removal of stale data"), permissions sync every 5 minutes when document-level permissions are on, and "Modifying a content source's indexing configuration will trigger a full synchronization of the source's data" ([Customize indexing for a content source](https://www.elastic.co/guide/en/workplace-search/current/workplace-search-customizing-indexing-rules.html)). These are documented defaults from 2020 to 2023 for hosted SaaS sources (Google Drive, SharePoint Online, Confluence), not measurements; the product is no longer updated, which is why they are read as a historical data point.

READ. Inside the engine the incremental unit is one second: "`index.refresh_interval` ... How often to perform a refresh operation, which makes recent changes to the index visible to search. The value defaults to `1s` in Elastic Stack and `5s` in Serverless", and an idle shard (no search for `index.search.idle.after`, default `30s`) stops refreshing until the next search ([Index modules](https://www.elastic.co/docs/reference/elasticsearch/index-settings/index-modules)). OpenSearch, the fork, documents the same `1s` default and the same idle behaviour ([Index settings](https://docs.opensearch.org/latest/install-and-configure/configuring-opensearch/index-settings/)). Lucene's maintenance is continuous merging, never a rebuild: `TieredMergePolicy` defaults are `maxMergeAtOnce` 10, `segmentsPerTier` 10.0, `maxMergedSegmentMB` 5 GB, `floorSegmentMB` 2 MB, `deletesPctAllowed` 20 ([TieredMergePolicy](https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/TieredMergePolicy.html)), so an index carries up to a fifth of its documents as deletions before the policy reclaims them.

READ. A whole-index rebuild in Elasticsearch exists for exactly one family of reasons, a schema change: "Except for supported mapping parameters, you can't change the mapping or field type of an existing field. Changing an existing field could invalidate data that's already indexed. If you need to change the mapping of a field in other indices, create a new index with the correct mapping and reindex your data into that index" ([Update field mappings](https://www.elastic.co/docs/api/doc/elasticsearch/v8/operation/operation-indices-put-mapping)). The one operation that rewrites every segment, force merge, is explicitly for data that has stopped changing: "We recommend force merging only a read-only index (meaning the index is no longer receiving writes)" because it "can cause very large (greater than 5 GB) segments to be produced, which are not eligible for regular merges" ([Force merge](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-indices-forcemerge)).

INFERRED. Elastic's stack is the clearest statement of the principle: inside the index there is no such thing as a scheduled full rebuild. Freshness is a one-second refresh, compaction is a continuous tiered merge, and the only full rewrite is a migration forced by a schema or analyzer change. The scheduled full passes live one layer up, in the connectors, and exist because a foreign source hides its deletions and permission changes.

## 3. Glean and Coveo

READ. Glean publishes a default cadence per connector, and the table is the richest single source in this study ([Connector refresh rates](https://docs.glean.com/connectors/crawling-refresh-rates)). Incremental crawls cluster at 10 minutes to 1 hour: Box 10m, Egnyte 10m, Quip 10m, Asana 10m, Guru 10m, Linear 10m, SmartSheet 10m, Gong 5m, Salesloft 5m, Amazon S3 1h, Bitbucket 1h, GitLab 1h, Confluence 1h, Zoom 1h, Outlook 30m, Google Drive 3h, Slack 3h, Jira 6h, GitHub 1d. Full crawls cluster at one day to 28 or 30 days: Amazon S3 1d, Notion 6h, Linear 1d, Guru 1d, Confluence Cloud 30d, Confluence Server 7d, SharePoint 28d, OneDrive 28d, Dropbox 28d, GitHub 28d, Bitbucket 28d, Jira 28d, Slack 28d, Zendesk 28d, Gmail 28d, Google Calendar 28d, Microsoft Teams channels 30d; Box, Google Drive and Azure Files have no full crawl at all but a "discovery" pass every 14 days (Box, Drive) or 2 days (Azure Files). Identity and permission passes run at 10m to 1h for most connectors. The page labels these as default refresh patterns, not guarantees; they are documented defaults for a hosted multi-tenant service, measured on nothing public.

READ. Glean names what the full pass is for: deletion handling covers "webhook-based and full-crawl cleanup" ([Crawling strategy](https://docs.glean.com/connectors/crawling-frequency)); the strategy page states the goal as "minimizing the time between a change in the source and its appearance in Glean" within source API limits. So, as at Microsoft, the whole-corpus pass is the deletion and permission reconciler, and the systems with webhooks (Box, Drive) drop the full crawl in favour of a 14-day discovery walk.

READ at one remove (search-engine extract of the Coveo pages; the direct fetches returned 503). Coveo's three operations are a cost ladder. Refresh is the incremental pass: "A refresh consumes less computing resources than a rescan. However, while all connectors support rescans, several don't support refreshes at all". Rescan: "A Rescan is a source update operation during which Coveo crawls a content repository, but only re-indexes new or updated content", "typically used as a safeguard", and "Typically, a weekly rescan is sufficient", because "The rescan will clean up the index after several refreshes have occurred". Rebuild is the event-only operation: "Any time you change a setting that must apply to all items in a source", and "If a source configuration change isn't reflected, run a rebuild" ([Refresh, rescan, and rebuild](https://docs.coveo.com/en/2039/), [Keep an index up to date](https://docs.coveo.com/en/2705/)). Coveo adds a serialization rule: a manually launched rebuild waits for an in-flight scheduled refresh.

INFERRED. Glean and Coveo, the two enterprise-search vendors whose whole business is cadence, agree with Microsoft and Elastic: the incremental pass is minutes to an hour, the whole-corpus walk that re-indexes only what changed is weekly (Coveo rescan) to monthly (Glean full crawl), and the pass that re-indexes everything is never scheduled, only triggered by a configuration change. Coveo's vocabulary is the useful one for vfs: a "rescan" visits every item but writes only the changed ones; a "rebuild" rewrites every item.

## 4. Code search: zoekt, Sourcegraph, GitHub and GitLab

READ. zoekt's standalone `zoekt-indexserver` is pull-based with hour-scale polling: `flag.DurationVar(&o.fetchInterval, "fetch_interval", time.Hour, "run fetches this often")` and `flag.DurationVar(&o.mirrorInterval, "mirror_duration", 24*time.Hour, "find and clone new repos at this frequency.")` (`cmd/zoekt-indexserver/main.go:80,84`); its index call passes `-incremental` (`main.go:160-166`), which `zoekt-git-index` defines as `flag.Bool("incremental", true, "only index changed repositories")` (`cmd/zoekt-git-index/main.go:43`). The design document states the service's three jobs as "Poll Git hosting sites ... to fetch new updates", "Reindex any changed repositories", "Run the webserver" (`doc/design.md:299-302`).

READ. The incremental decision is a whole-repository fingerprint, not a per-file one: `IncrementalSkipIndexing` returns true only when `IndexState()` is `IndexStateEqual` (`index/builder.go:389-394`), and `IndexState()` returns `IndexStateVersion` on a feature-version mismatch, `IndexStateOption` when `repo.IndexOptions != o.GetHash()`, `IndexStateContent` when the branch set or any branch commit differs, `IndexStateMeta` when only mutable metadata moved (`index/builder.go:398-448`). Anything but `Equal` or `Meta` rebuilds the repository's shards from scratch: "Non-delta shard builds delete all existing shards before they write out new ones. By contrast, delta shard builds work by stacking changes on top of existing shards" (`index/builder.go:761-764`). So in zoekt the unit of a full rebuild is the repository, and a repository whose HEAD moved is rebuilt whole on every fetch that sees a change; this is the one system in the study whose "full rebuild" is routine, and it is routine because the unit is small enough that a rebuild is the cheap path.

READ. Sourcegraph's `zoekt-sourcegraph-indexserver` tightens the poll to a minute and names the forced-rebuild cadence of its delta builds: `fs.DurationVar(&rc.interval, "interval", time.Minute, "sync with sourcegraph this often")` (`cmd/zoekt-sourcegraph-indexserver/main.go:1499`); delta builds are allowlisted per repository ("This should only be true for repositories we explicitly enable", `index.go:88-90`, `main.go:224-226`); and `getEnvWithDefaultUint64("DELTA_SHARD_NUMBER_FALLBACK_THRESHOLD", 150)` (`main.go:1647`) feeds `DeltaShardNumberFallbackThreshold`, "an upper limit (inclusive) on the number of preexisting shards that can exist before attempting another delta build. If the number of preexisting shards exceeds this threshold, then a normal build will be performed instead" (`gitindex/index.go:441-447`), with the comment "HACK: For our interim compaction strategy, we force a full normal index once the number of shards on disk for this repository exceeds the provided threshold" (`gitindex/index.go:934-946`). Compaction of the index directory is on its own clock: `"vacuum_interval"` default 24 h and `"merge_interval"` default 8 h (`main.go:1510-1511`); a failed repository backs off 10 minutes, growing linearly to 120 minutes (`main.go:1505-1506`).

READ. GitLab, which runs zoekt behind its own indexer, adopted the same shape as a stopgap: "This MR forces a full reindex on average once every 200 indexing operations", noting "Sourcegraph sets this limit to 150 to achieve the same result", and calling it "a band-aid solution" while a proper compaction is built ([GitLab MR 140136](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/140136)). This is the only precedent found for a scheduled full rebuild measured in operations rather than days, and it is a compaction device over an append-only delta index, not a freshness device.

READ. Sourcegraph's hosted cadence: "The frequency at which Sourcegraph polls the code host for updates is determined by a smart heuristic ... based on past commit frequency in the repository", "Repositories will never be updated more frequently than 45 seconds, and no less frequently than every 8 hours", and after a fetch "the global search index will automatically update a short while after", "usually a few minutes" ([Repository update frequency](https://sourcegraph.com/docs/admin/repo/update-frequency)). Webhooks are optional: "this is usually not necessary". The data-freshness page adds that repository-scoped searches "are always up-to-date" while unscoped searches "may trail latest default branch revisions by some interval of time" that depends on repository count and indexing compute ([Search details](https://sourcegraph.com/docs/code_search/explanations/search_details)).

READ. GitHub's Blackbird is the one measured whole-corpus figure in the study: a corpus of "almost 45 million repositories", "115 TB of code and 15.5 billion documents", deduplicated to "around 28 TB" unique content; the indexer "responds to events like `git push` to crawl changed content" through Kafka; it can "publish around 120,000 documents per second" and "re-index the entire corpus in about 18 hours", versus "about 36 hours" without delta indexing; results are "consistent on a commit-level basis" ([The technology behind GitHub's new code search](https://github.blog/engineering/the-technology-behind-githubs-new-code-search/)). The 18 hours is a capacity statement (what a rebuild would cost), not a schedule; the steady state is push-driven. EXECUTED: 15.5 billion documents over 18 hours is 239,000 documents a second, twice the stated publish rate, which is consistent with delta indexing halving the documents crawled ("reduces the number of documents we have to crawl by over 50%"); ten million files at GitHub's 120,000 documents a second would be 1.4 minutes of publish time, which says a ten-million-file full rebuild is small by Blackbird's standards and the cost question for vfs is the relational engine's, not the indexer's.

INFERRED. Code search at every scale studied is event-driven at the incremental tier (push or a 45-second-to-hourly poll) and treats the whole-corpus rebuild as either a per-repository unit (zoekt), a compaction trigger counted in operations (Sourcegraph 150, GitLab 200), or a capacity figure never scheduled (GitHub). None schedules a full rebuild by the clock.

## 5. Vector stores and RAG pipelines

READ. LangChain's indexing API makes the full-versus-incremental distinction a cleanup mode, not a rebuild: `cleanup=None` deletes nothing; `incremental` "Cleans up all documents that haven't been updated AND that are associated with source IDs that were seen during indexing"; `full` "Delete all documents that have not been returned by the loader during this run of indexing", with the warning "In full mode, the loader should be returning the entire dataset, and not just a subset of the dataset"; `scoped_full` is full within the seen source IDs. The record manager is a "Timestamped set to keep track of which documents were updated", and `force_update` exists for one case, "Useful if you are re-indexing with updated embeddings" ([index reference](https://reference.langchain.com/python/langchain-core/indexing/api/index)). INFERRED from the how-to text returned by the search engine, "Indexing again should result in both documents getting skipped -- also skipping the embedding operation!": unchanged content is never re-embedded, so a "full" run is a full enumeration of the source, not a full re-embed.

READ. LlamaIndex's ingestion pipeline does the same by hash: "Attaching a `docstore` to the ingestion pipeline will enable document management"; "If a duplicate `doc_id` is detected, and the hash has changed, the document will be re-processed and upserted"; "If a duplicate `doc_id` is detected and the hash is unchanged, the node is skipped" ([Ingestion pipeline](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/)).

READ. Qdrant's operations tutorial gives the cadence practitioners use and the trigger for a full re-embed: detect change by "Content fingerprint, like SHA-256 of the text. It changes if a single character changes, and never otherwise"; run it as a CI job on merge or "a nightly cron job"; store the embedding model and pipeline version in collection metadata and "if one of the two changed, trigger full collection re-embedding" ([Incremental embedding updates](https://qdrant.tech/documentation/tutorials-operations/incremental-embedding-updates/)). It also states the cost law of the naive design: "This design re-reads the whole collection on every run", "Per-run cost scales with corpus size, not with what actually changed", "At around 100,000 points, this stays cheap", "By around 1 million points, each run moves hundreds of MB". This is a vendor tutorial, measured on the author's own pipeline; the 100,000 and 1,000,000 figures are the author's experience, not a benchmark.

READ at one remove (search-engine extracts). Weaviate: a collection's vectorizer is immutable, so a model change means "export your data, create a new collection, and import your data into it", with a collection alias swapped to the new one in production ([Switching vectorizers](https://docs.weaviate.io/weaviate/tutorials/vectorizer-migration)). Qdrant: a new collection or a new named vector, dual writes during the backfill, an alias swap at the end ([Migrate to a new embedding model](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/)).

INFERRED. In the vector world there is no scheduled full re-embed anywhere in the documentation read; every vendor and framework re-embeds a chunk when its content hash changes and re-embeds the whole corpus only when the model or the chunking pipeline changes. The "full" run that does exist is a full enumeration to find deletions, the same purpose as Microsoft's and Glean's full crawl.

## 6. What the vfs tree already assumes

READ. `src/vfs/sync.py` is the synchronous facade and carries no index cadence: it forwards every verb through one loop thread (`sync.py:1-23`, `82-95`) and exposes no `reindex` twin; EXECUTED `grep -n -i reindex src/vfs/sync.py` returned nothing. `reindex` is reached through the storage protocol, `class SupportsReindex(Protocol)` with `async def reindex(self) -> Result` (`src/vfs/storage/protocol.py:474-483`), and the roadmap plans a `vfs reindex` command-line subcommand (`context/standards/roadmap.md:771`) and a how-to that says "`reindex()` after binary writes and its `conflict` retry" (`roadmap.md:826`). EXECUTED `grep` over `docs/` and `README.md` for a reindex schedule found no stated cadence anywhere in the live tree.

READ. The reindex verb's phases are stated in `indexing.py`'s module docstring: "assess the dirty, build postings, publish" (`indexing.py:1`); Phase A "re-derive per-entry state for entries whose rows no longer reflect their content" (`indexing.py:3-6`), which is incremental, "linear in the dirty set" (`indexing.py:282-285`); Phase B "build the full posting set under a fresh epoch (invisible until published)" (`indexing.py:7`); then publish by flipping `encoded` flags and the epoch pointer together, then reclaim (`indexing.py:8-13`). `build_epoch`'s own docstring is explicit about the grain: "Build the full posting set under a fresh epoch, or no-op. The no-op check: no live entry awaits encoding and the current epoch's two-part fingerprint matches. Anything else rebuilds whole — posting rows are a regenerable cache, and format or options drift is a drop-and-rebuild, never a migration" (`indexing.py:366-372`), and about the cost: "Peak build memory is the accumulated posting set ... held for the whole build and paid whenever any entry is dirty. A known suboptimality, deliberately not converted into a designed corpus cap; gram-range partitioned passes are the future direction" (`indexing.py:393-399`). The lexical index "is one step of the gram epoch's build phase: one stream over the chunk rows of every `chunked ∧ indexable ∧ live` entry" (`lexical.py:3-5`).

READ. The embedding step is the opposite grain, incremental by construction: "a short read selects one page of `embedding IS NULL` rows past the last id seen (keyset, so the loop always advances)", "The chunk row is the cache", and a model change is the one full re-embed: "when the configured provider differs, every embedding is cleared and the pair re-stamped by the first batch written under the new identity ... model swap is a re-embed by the verb that owns regeneration, never a read-time migration" (`embed.py:8-27`). The docstring sizes the step: "A 10,000-file store is ~10⁵ chunks and, against a hosted provider at a low rate-limit tier, tens of minutes of network wait" (`embed.py:5-7`).

READ. Freshness between reindexes is served by the overlay, not by the index: grep unions "the flag-partitioned scan side (`NOT encoded`) so index staleness can never lose a match" (`grep.py:17-18`), the traits vocabulary declares `grep_staleness` and `glean_staleness` as `none` or `overlay` (`protocol.py:84-86`), and the roadmap's E5 story corrects the second: "`traits()` says `glean_staleness` is `overlay` for the lexical leg and `reindex` for the vector leg" (`roadmap.md:563`). The lease that serializes reindexers has `REINDEX_LEASE_TTL_MS = 5 * 60 * 1000` and `REINDEX_HEARTBEAT_SECONDS = 60.0` (`indexing.py:124-125`), and `INDEX_FORMAT_VERSION = 4` with the rule "every fold, extraction-grain, gram-extraction, or lexical-table change must hand-bump this to force the rebuild" (`indexing.py:97-99`).

INFERRED. Put together, vfs today has three grains in one verb. The dirty assessment and the embed step are incremental and already match the industry's "only what changed" practice. The gram and lexical build is a whole-corpus rebuild on every run that finds anything dirty, which matches zoekt's per-repository habit and nothing else in the study at corpus grain. The overlay scan means vfs does not need the reindex for freshness of grep or the lexical leg at all; it needs it for the vector leg and for the bound on the scan tier's size. AGENTS.md's own rule names this shape: "Where the current implementation is suboptimal at scale (e.g. a whole-corpus in-memory build), acknowledge the profile honestly in the docstring and name the future direction".

## 7. Comparing the families

INFERRED, with the figures READ above. The incremental tier agrees to within an order of magnitude across every family: 1 s inside Lucene, Elasticsearch and OpenSearch; 45 s to 1 min for a code-host poll (Sourcegraph floor, `zoekt-sourcegraph-indexserver` sync); 5 min for permission syncs (Workplace Search) and the fastest Glean connectors; 15 min for SharePoint Server's continuous crawl default, Microsoft's connector floor and the ADLS Gen2 default; 10 min to 1 h for most Glean connectors and zoekt's standalone `fetch_interval`; 2 h for Workplace Search's incremental sync; 8 h as Sourcegraph's ceiling for a quiet repository. Clay's "partial reindex every fifteen minutes" sits exactly on SharePoint's default and Microsoft's floor.

INFERRED. The whole-corpus tier agrees too, and it is far slower: 72 h (Workplace Search full sync), 7 days (Microsoft connector default, Coveo rescan, Glean's Confluence Server and Zoom), 14 days (Glean discovery for Box and Drive), 28 to 30 days (most Glean full crawls, Microsoft's rediscovery horizon), and never-by-the-clock for SharePoint Server, SharePoint Online, Elasticsearch, Lucene, GitHub, LangChain, LlamaIndex, Qdrant and Weaviate, which rebuild only on a schema, format, analyzer or model change. The sole exceptions are the code indexers whose unit is one repository (zoekt rebuilds a changed repository whole on every fetch; Sourcegraph and GitLab force a per-repository full build every 150 or 200 delta builds), and that exception is about compaction of an append-only shard set, not about freshness. Six whole-corpus rebuilds a day has no precedent in any system found.

INFERRED. The figures disagree only on what the full pass is for, and the disagreement is instructive. Microsoft, Glean, Coveo and Workplace Search run it to see deletions and permission changes that a foreign source's change feed hides; Elasticsearch, Lucene and the vector stores never run it because the index owns its documents and sees every delete. vfs is in the second group: deletes stamp `deleted_at` and demote `encoded` on the same row (`indexing.py:33-37`), grants are rows in the same database, and the gram index is a derived cache behind a `NOT encoded` overlay. The reconciliation reason for a periodic full pass therefore does not apply to vfs; the remaining reasons are the ones Elasticsearch has (format or options drift, already fingerprinted by `INDEX_FORMAT_VERSION` and the options hash) and the ones the vector stores have (a model change, already handled by `clear_embeddings`).

EXECUTED (`cadence_arithmetic.py`, output in `output.txt`). On Clay's proposed corpus and workload (10,000,000 files, 1% edited over a 10-hour working day, 10% in a nightly batch) the organic write volume is 100,000 daytime writes plus 1,000,000 nightly, 1,100,000 writes a day. Six full rebuilds visit 60,000,000 files, 54.5 times the day's organic writes; one full rebuild is 9.1 times; a weekly rebuild amortizes to 1.30 times the daily organic writes per day; a 28-day full crawl amortizes to 0.32 times. Ninety-six 15-minute passes a day; the forty in working hours each see about 2,500 changed files, 0.025% of the corpus, and the nightly batch is one pass of 1,000,000, ten days of daytime edits in one call.

## 8. Proposed figures for the reference table

Incremental (partial) index pass: every 15 minutes, with a floor of 1 minute. Justification: SharePoint Server's continuous-crawl default and floor, Microsoft's connector grid floor and ADLS Gen2 default, Glean's 10-minute-to-1-hour cluster; Sourcegraph's 45-second poll floor says a minute is the practical bottom for a pull design.

Fraction of the corpus one incremental pass touches: 0.025% in working hours (about 2,500 of 10,000,000 files), and one nightly pass of 10% (1,000,000 files). Justification: EXECUTED arithmetic on the brief's own change rates; every incremental design in the study (SharePoint change log, Elastic timestamp compare, LangChain and LlamaIndex hashes, Qdrant hashes) writes only the changed set, so the touched fraction is the change rate divided by passes, not a property of the indexer. Researcher 02's change-rate figure should replace the 1% and 10% here if it differs.

Full (whole-corpus) rebuild: once a week at most, scheduled off-hours, and otherwise only on a format, options or embedding-model change. Justification: the Microsoft connector default (weekly), Workplace Search (72 h), Coveo's weekly rescan, Glean's 7-to-30-day full crawls; the systems that own their documents (Elasticsearch, Lucene, the vector stores) never schedule one, and vfs owns its documents.

Full rebuild cost in file visits: 10,000,000 per rebuild, 9.1 times a day's organic writes; amortized weekly, 1.3 times the daily organic writes per day. Justification: EXECUTED arithmetic; the figure that costs a design is the per-run visit count, because vfs's `build_epoch` holds the whole posting set in memory for the run.

Full re-embed: never on a schedule; only on a model or chunking-pipeline change, as a backfill behind the serving index. Justification: Qdrant, Weaviate, LangChain's `force_update`, LlamaIndex's hash skip, and vfs's own `clear_embeddings` all agree.

Scheduled full rebuilds a day: 0 as the steady state, with 1 a week as the ceiling. Justification: no system in the study schedules more than one whole-corpus pass per 72 hours; the only sub-daily full builds (zoekt) are per repository and exist for shard compaction.

The one figure in Clay's proposal that this evidence most changes is "six full reindexes a day": every precedent puts a whole-corpus rebuild at weekly to monthly or never, so six a day is roughly 40 times above the densest default found (72 hours) and 54 times the day's organic write volume in file visits. The "partial reindex every fifteen minutes" survives on precedent, but with one vfs-specific caveat the author should see: in the tree as it stands, a reindex that finds anything dirty rebuilds the whole gram and lexical posting set (`indexing.py:366-372`), so a 15-minute cadence today would be 96 whole-corpus posting builds a day, 960,000,000 entry visits against 1,100,000 organic writes, until the "gram-range partitioned passes" the docstring names as the future direction exist. The reference table should carry the industry's two grains as two rows, so that a design is costed against a 15-minute pass over 2,500 files and a weekly pass over 10,000,000, never against a 15-minute pass over 10,000,000.

## One line

Real systems refresh in minutes and rebuild in weeks or never; six full rebuilds a day is unprecedented, a 15-minute partial pass is standard, and vfs's reindex must learn to rebuild only the dirty slice before a 15-minute cadence is affordable.
