# Every file system that runs at ten million files and beyond keeps directory aggregates as counters maintained with the write, never computed on demand on the hot path; every one of them labels the counter approximate or in doubt, bounds its lag in seconds, keeps recursive totals only for marked directories, and keeps a full scan as the repair path

This study is Researcher 04's answer in the study [what an enterprise-scale deployment looks like](00-brief.md), on how the file systems that run at ten million files and beyond keep per-directory counts and byte totals, and what it costs them. The 45-minute box opened at 2026-11-09 09:11:45 EST (EXECUTED: `date` at the first command) and the study was finished inside it, the file complete at 09:24:30 EST, thirteen minutes in (EXECUTED: `date` after the write). Every claim below is labelled EXECUTED (a command run here), READ (a page or file cited by URL or path) or INFERRED (reasoning from those). The question behind it is whether vfs should maintain per-directory counts and byte totals on every write or compute them on demand. vfs today stores none: the one place that needs a child count, the trash occupancy check in `src/vfs/storage/backends/database/trash.py`, computes a live grouped `count()` per parent on demand in chunks of the membership budget (`_live_child_counts`, lines 408 to 426) (READ). ## 1. CephFS: recursive statistics on every directory, propagated lazily by the metadata server, honestly labelled imprecise

What is kept. Every directory fragment carries two statistics structures (READ, `mdstypes.h` `struct fnode_t`: `frag_info_t fragstat, accounted_fragstat; nest_info_t rstat, accounted_rstat;`). `frag_info_t` is commented "this frag" and holds `mtime`, `change_attr`, `nfiles` ("files") and `nsubdirs` ("subdirs"); `nest_info_t` is commented "this frag + children" and holds `rctime`, `rbytes`, `rfiles`, `rsubdirs` and `rsnaps`; both inherit a `version` from `scatter_info_t` (READ, `include/cephfs/types.h`). The inode carries the same pair with their lock owners named in the source: `frag_info_t dirstat; // protected by my filelock`, `nest_info_t rstat; // protected by my nestlock`, `nest_info_t accounted_rstat; // protected by parent's nestlock` (READ, `types.h`, under the comment "dirfrag, recursive accountin"). So CephFS keeps both a direct-children count (dirstat) and a recursive total (rstat) for every directory, and the "accounted" copy records what has already been pushed into the parent, so that propagation is a delta, not a recount (INFERRED from the field names and the lock comments).

When it is updated. The statistics are protected by scatter locks, whose purpose the developer documentation states directly: "statistics of a directory may need to be updated by multiple clients at the same time", "wrlock allows multiple writers at the same time", "When new files are created under these directories, the recursive stats are independently updated on the active MDSs", and "Later, to fetch the updated stats, the 'scattered' data is aggregated ('gathered') on the auth MDS (of the inode); which typically happens when a rdlock is requested on this lock type" (READ, MDS Locker doc; the nest lock `CEPH_LOCK_INEST` is listed as covering "rstats"). Propagation up the tree is rate-limited by two MDS options: `mds_dirstat_min_interval`, "The minimum interval (in seconds) to try to avoid propagating recursive stats up the tree", default 1.0, and `mds_scatter_nudge_interval`, "How quickly dirstat changes propagate up", default 5.0 (READ, MDS configuration reference; both are documented defaults). The 2008 design note by Sage Weil says the same in plain words: "stats are pushed up as long as there are no conflicting locks", "There may be some delay before the recursive stats propagate up the hierarchy", with a plan to push times up "at least once every minute or something" (READ, ceph.io 2008-05-23).

How staleness reaches the caller. The totals are read as virtual extended attributes (`ceph.dir.rbytes`, `ceph.dir.rfiles`, `ceph.dir.rentries`), and the client option `client_dirsize_rbytes`, default true, puts the recursive byte total in a directory's `st_size`, with the documented warning that it "May confuse programs such as rsync" (READ, client configuration reference). Quotas are enforced by the client from these same counters: the kernel client reads `i_rbytes` against `i_max_bytes` and `i_rfiles + i_rsubdirs` against `i_max_files`, walking up the realm hierarchy on each check (READ, `fs/ceph/quota.c`). Because the counters lag, the quota documentation says so: "Quotas are imprecise", "Processes that are writing to the file system will be stopped a short time after the quota limit is reached", "How far over the quota they are able to go depends primarily on the amount of time, not the amount of data", "Generally speaking writers will be stopped within tens of seconds of crossing the configured limit" (READ, Quotas page). The mailing lists record how far "lazy" can stretch: in 2015 John Spray wrote "I'm not sure we've really defined what is supposed to trigger recursive statistics (rstat) updates yet" after a user saw `rbytes` unchanged for seconds until a remount (READ, ceph-users 2015-08-03); in 2021 a user reported recursive stats not updated 24 hours after copying 16 TB, and the reply was that "the recursive stats do get updated although it might take a while", that "MDS load can also have an impact" and that `mds_dirstat_min_interval` "would delay the recursive stat propagation" (READ, dev@ceph.io 2021-03-05). These are user reports and a maintainer's reply, not measurements.

Cost and scale. No Ceph document I reached gives a numeric cost for rstat maintenance; the cost is structural: a scatter-lock protocol with per-fragment versions and a gather on read (INFERRED from the Locker doc). The directory itself is split into fragments at `mds_bal_split_size` 10,000 entries, each fragment capped at `mds_bal_fragment_size_max` 100,000 entries beyond which "clients will receive ENOSPC errors if they try to create files in the fragment" (READ, Directory fragmentation; documented defaults and a limit). The design claim is an unlimited file count; the production figures I could reach were only in search summaries (a single MDS rank saturating near 8,000 metadata ops/s in Inditex's 2026 Ceph Days slides, which I could not open), so I record no CephFS scale figure as measured.

## 2. HDFS: recursive counters on quota-bearing directories, incremented synchronously inside the write under the global lock, with a throttled whole-subtree scan for everything else

What is kept and where. A directory carries a `DirectoryWithQuotaFeature` only when a quota is set on it; the feature holds two `QuotaCounts` (`quota` and `usage`), each a namespace count (names in the tree), a storage-space total in bytes at replication, and per-storage-type totals (READ, `DirectoryWithQuotaFeature.java`). The quota guide confirms the semantics are recursive: "The name quota is a hard limit on the number of file and directory names in the tree rooted at that directory", "The space quota is a hard limit on the number of bytes used by files in the tree rooted at that directory", "Quotas stick with renamed directories; the rename operation fails if operation would result in a quota violation", and quotas "are stored in the fsimage" (READ, HDFS Quotas Guide). Directories without a quota keep no counter.

When it is updated. Synchronously, in the same operation, by walking the path. `FSDirectory.updateCount` is documented "update count of each inode with quota"; it first returns if `!namesystem.isImageLoaded()` ("still initializing. do not check or update quotas"), then calls `verifyQuota`, which walks from the target position back to the root checking each quota-bearing ancestor ("Verify quota for adding or moving a new INode with required namespace and storagespace to a given position"), then `unprotectedUpdateCount`, whose loop is `for(int i=0; i < numOfINodes; i++) { if (inodesInPath.getINode(i).isQuotaSet()) { ... .addSpaceConsumed2Cache(counts);` (READ, `FSDirectory.java`). `addSpaceConsumed2Cache` is documented "Update the space/namespace/type usage of the tree" (READ, `DirectoryWithQuotaFeature.java`). The cost per mutation is therefore one in-memory increment per quota-bearing ancestor, bounded by path depth, performed while the NameNode already holds its single global namespace write lock (READ for the loop; the lock is described in the LinkedIn post: "The NameNode uses a single global read-write lock that protects the entire namespace").

The two scans. Quota usage is recomputed from scratch at startup and failover: HDFS-8865 states "the whole file system tree is recursively scanned in order to initialize the quota", measured 55 seconds single-threaded on the fsimage of one of the reporter's large NameNodes (inode count not stated), falling to about 12 seconds with 8 fork-join threads; the resulting setting `dfs.namenode.quota.init-threads` defaults to 12 (READ, HDFS-8865 and hdfs-default.xml; a measurement on an unstated population, 2015). For a directory without a quota, `du` and `count` call `getContentSummary`, which walks the subtree under the lock; HDFS-4995 (fixed in 2.3.0) records "it could hold the namesystem lock for a long time. We've seen it taking over 20 seconds" (READ). The fix is a yield: `dfs.content-summary.limit`, default 5000, "The maximum content summary counts allowed in one locking period", and `dfs.content-summary.sleep-microsec`, default 500, "The length of time in microseconds to put the thread to sleep, between reaquiring the locks" (READ, hdfs-default.xml; documented defaults); the context's `yield()` "Relinquish locks held during computation for a short while and reacquire them. This will give other threads a chance to acquire the contended locks and run" (READ, `ContentSummaryComputationContext.java`). When the scan reaches a quota-bearing directory it compares the cached usage with the recomputed one and logs "BUG: Inconsistent storagespace for directory" on a mismatch (READ, `DirectoryWithQuotaFeature.java`, `checkStoragespace`), which is HDFS's consistency check between the maintained counter and the truth.

Scale. Shvachko's 2010 analysis assumed about 600 bytes of NameNode heap per file (one file object, two block objects) and a target of 100 million files in 60 GB, with 60 million deployed at Yahoo in 2009 (READ through the search summary of the ;login: article; an analysis, not a benchmark). LinkedIn's 2021 account is the largest primary figure I reached: one NameNode "maintains 1 billion objects (directories, files, and blocks)", a "380 GB heap to maintain 1.1B of namespace objects", a 10,000-node cluster storing 500 PB, NameNodes averaging 150K ops/sec and peaking at 250K ops/sec with 1 to 2 ms average latency after observer reads, with "Reads make up 95% of namespace operations" (READ, LinkedIn 2021; an operator's measurement of its own production cluster). The post does not mention quotas or `getContentSummary`, so the synchronous ancestor-increment design is documented to coexist with that scale but is not separately measured there (INFERRED).

## 3. btrfs qgroups: a precise shared-versus-exclusive total per subvolume, maintained on every extent change, so expensive that the project recommends against it and shipped a cheaper approximate mode

What is kept. A qgroup tracks two byte totals per subvolume or snapshot, not per directory: "Referenced" (data reachable from any subvolume in the qgroup) and "Exclusive" (data whose references all lie within the qgroup) (READ, btrfs-quota(8)). Qgroups can be arranged in a hierarchy, but the leaf unit is the subvolume.

Cost. The man page's performance section is the bluntest statement of maintenance cost in this study: "The qgroup mode is considered not recommended for daily usage, unless there is no planned new snapshot/subvolume creation and deletion", "When qgroup mode is activated, it affects all extent processing, which takes a performance hit", "Operations that modify a whole subvolume/snapshot in one go, which include snapshot creation and subvolume deletion, are heavily affected and can cause a system hang due to the heavy load", and the kernel's workarounds have "extra costs, e.g. marking qgroup inconsistent, breaking limits and requiring extra rescan" (READ, btrfs-quota(8)). The measured figures come from the simple-quotas cover letter: on the fsperf unshare test, qgroups raised average transaction commit time from 162.13 ms to 285.75 ms (+76%), raised mean `wait_current_trans` by 1347%, cut write bandwidth by 25.5% and lengthened the run by 34%; simple quotas, which charge each extent permanently to the subvolume that created it and give up shared-versus-exclusive, cost +1.25% commit time and −3.3% bandwidth, "similar performance characteristics to normal, quotas disabled, btrfs" (READ, Burkov 2023-07-20 via LWN; a benchmark on the author's machine, 1000 files and 100 snapshots).

Staleness and repair. `btrfs quota status` reports an "Inconsistent" field; the repair is `btrfs quota rescan`, which "discards all qgroup numbers and rescans metadata" (READ, btrfs-quota(8)). The lesson for this question is the shape of the trade: the precise aggregate is maintained synchronously at commit and the project itself calls its cost unacceptable for a snapshotting workload, and the fix was an approximate aggregate with the same API (INFERRED from the two sources).

## 4. ZFS: no per-directory aggregates at all; the dataset is the unit, and even its totals are documented as a few seconds behind

What is kept. `used` "counts all space consumed by the dataset and its descendants", `quota` and `refquota` cap it, and `userused@`, `groupused@` and `projectused@` keep per-identity totals charged by owner or by an inheritable project ID attribute on each object (READ, zfsprops(7)). A directory has no count or total; `du` walks.

Lag, stated. "The amount of space used, available, or referenced does not take into account pending changes. Pending changes are generally accounted for within a few seconds", "Committing a change to a disk using fsync(2) or O_SYNC does not necessarily guarantee that the space usage information is updated immediately", and for quotas "Enforcement of user quotas may be delayed by several seconds" (READ, zfsprops(7); documented behaviour). ZFS is the clearest case of a system that chose a coarse unit (dataset, identity) for its maintained aggregates and left the directory tree to on-demand walks (INFERRED).

## 5. Lustre: quotas by user, group and project, enforced approximately by granting space in units to the storage targets; a directory subtree becomes an aggregate only by tagging it with a project ID

What is kept. Lustre accounts by "user, group, or project"; the Quota Master Target "runs on the MDT, holds the global quota limits" and is "the single authority for quota limits", and a Quota Slave Device "runs on each OST and MDT, enforces limits locally" by requesting qunit allocations, where the master "dynamically adjusts qunit size based on remaining quota and the number of slaves" (READ, Lustre wiki, last edited 2026-08-31). "Space accounting is enabled by default on ldiskfs" (READ, same page). A project is attached to a directory tree by tagging it: `lfs project -p 100 -r -s /mnt/fsxfs/dir1` "associates all the files and sub-directories of the directory with the project" and sets the inherit flag so new files join it (READ, AWS FSx for Lustre page; vendor documentation of Lustre 2.15 behaviour).

Accuracy. "Quota enforcement is approximate until the user is near the limit", and after a limit changes "QSDs may take a short time to receive the new allocation" (READ, Lustre wiki). Lustre therefore has no per-directory counter; its aggregate is a per-identity counter distributed across storage targets with a declared approximation, and a directory total is available only where an administrator marked the tree with a project (INFERRED).

## 6. GPFS / IBM Storage Scale: fileset quotas as the subtree aggregate, an explicit "in doubt" column for unaccounted space, and an I/O-intensive recount to repair it

What is kept. Quotas are kept by user, group and fileset; "The GPFS quota commands support the -j option for fileset block and inode allocation" and "The quota limit on blocks and inodes in a fileset are independent of the limits for specific users or groups of users" (READ, Filesets and quotas 5.2.0). A fileset is a subtree, and the aggregate unit is the fileset, not an arbitrary directory (INFERRED from the page and the fileset model described in the search summaries of the 5.0 documentation, which I could not open directly).

Staleness, named in the interface. `mmlsquota` prints an `in_doubt` column: space the quota server has handed to nodes that have not yet reported it as used. "The mmlsquota command might report negative in-doubt values" when it mixes stale and current data, and "This condition is transient and can be ignored"; in-doubt space is lost when "a node to which in-doubt space is allocated fails before it can update quota management"; `-e` makes the command collect "updated information from all the cluster nodes before it displays the output" and still "this space might not be included" (READ, Listing quotas 5.2.0). The repair rule: "If the amount of in-doubt space approaches a significant percentage of the quota", "issue the mmcheckquota command to account for the lost space" (READ, same page). `mmcheckquota` will "Count inode and space usage in a file system by user, group and fileset", "is I/O-intensive and should be run when the system load is light", runs by default in the maintenance QoS class, and "A node failure could leave users unable to open files or deny them disk space that their quotas should allow" until it runs (READ, mmcheckquota 5.2.0).

The scan at scale. The policy engine is GPFS's whole-tree pass. Marc Kaplan (IBM) recalled on the user-group list "a Billion files scanned with mmapplypolicy in under 20 minutes" on "ordinary at the time, spinning disks (not SSD!)" with "about 1000 files per directory", describing the phases as a directory scan, then an inode scan (READ, gpfsug-discuss 2018-02-08; a vendor engineer's recollection of a demonstration, not a documented benchmark). The same list has a user reporting a full backup of a 2-billion-inode file system taking 60 days, cut to 40 with 20 parallel directory scans (READ through the search summary; a different workload with per-file stat calls). Roughly, one billion files in twenty minutes is 830,000 files per second across a parallel cluster on 2010s disks (INFERRED).

## 7. NTFS, FSRM and ReFS: per-volume per-user quotas in the file system; per-folder recursive usage only through a filter driver that tracks it in real time after an initial scan; none on ReFS

NTFS itself. "The NTFS file system supports disk quotas, which allow administrators to control the amount of data that each user can store on an NTFS file system volume" (READ, Managing Disk Quotas). The unit is volume by user; NTFS keeps no per-directory count or total, and Explorer's folder size is a walk (INFERRED from the page's scope).

FSRM directory quotas. File Server Resource Manager adds quotas on folders: "Limit the space that is allowed for a volume or folder" with auto-apply quotas for new subfolders (READ, FSRM overview and Quota Management). The protocol specification is the primary statement of how: a directory quota's state consists of "the properties that are tracked in real time to maintain, enforce, and report on quota usage"; "Quota usage: This property tracks the total disk space usage in the file system tree below the folder path including files, directories, streams, metadata"; the quota survives rename ("If the folder is renamed, the quota configuration continues to be associated with the renamed folder"); and it has three states, "Incomplete: ... the procedure to calculate the current quota usage (the quota scan) has not yet started", "Rebuilding: ... though started, has not yet completed", "Complete" (READ, MS-FSRM 3.2.1.2.1). So FSRM is a maintained recursive byte counter per marked folder, seeded by a scan and then kept by a minifilter that intercepts I/O (the filter mechanism is from the search summary of the Server 2008 documentation, which I did not open). "FSRM supports volumes formatted with the NTFS file system only. The Resilient File System isn't supported" (READ, FSRM overview), and the ReFS feature table lists "Disk quotas" as unavailable on ReFS (READ, ReFS overview). FSRM counts bytes only; it keeps no file count.

## 8. JuiceFS: a direct-children counter row per directory, accumulated in the client and flushed every second in batches of a thousand, a fast mode labelled possibly inaccurate, a strict mode that walks, and recursive totals only for quota-bearing directories

What is kept. One row per directory in a `dirStats` table: `Inode`, `DataLength`, `UsedSpace`, `UsedInodes` (READ, `pkg/meta/sql.go` lines 241 to 246). The documentation states the scope: "Directory statistics only track usage for individual directories. To get a recursive sum, use `juicefs info -r`. This could be a costly operation for large directories. If you need to frequently get the total statistics for particular directories, consider setting an empty quota for such directories to achieve recursive statistics" (READ, `docs/en/guide/dir-stats.md` line 97). The Enterprise Edition "provides a recursive sum in directory statistics" visible in `ls -lh` (READ, same file line 99). The feature is on by default for volumes formatted since v1.1.0 and "comes with a minor performance cost" (READ, line 7).

When it is updated. A write calls `updateParentStat`, which adds the length and space delta to an in-memory map for the parent (`updateDirStat`) and to the nearest quota (`updateDirQuota`); when the parent is unknown the lookup of parents runs in a goroutine (READ, `pkg/meta/quota.go` lines 198 to 217). `flushDirStat` ticks every `DirStatFlushPeriod`, default `1 * time.Second` (lines 219 to 236); `doFlushDirStat` swaps the map out under the lock and hands it to the engine (lines 238 to 254). The SQL engine writes it as `update dirStats set data_length = data_length + ?, used_space = used_space + ?, used_inodes = used_inodes + ? where inode = ?`, grouped by `groupBatch(batch, 1000)` into transactions of at most 1,000 directory rows, and any row the update did not find is rebuilt by `parallelSyncDirStat` (READ, `pkg/meta/sql.go` lines 3793 to 3835). Quota usage flushes on its own three-second ticker (`flushQuotas`, `time.NewTicker(3 * time.Second)`, `quota.go` line 511). A read, `GetDirStat`, returns the stored row plus the still-pending in-memory delta, or recomputes when no row exists (lines 163 to 179); the recompute, `calcDirStat`, is one `readdir` of the directory summing lengths and 4 KiB-aligned sizes (lines 141 to 160), and `doGetDirStat` triggers it when a stored counter has gone negative, logging "dir usage of inode %d is invalid ... try to fix" (`sql.go` lines 3884 to 3910).

How inaccuracy is exposed. "Directory statistics are calculated asynchronously and can potentially produce inaccurate results when clients run into problems. `juicefs info`, `juicefs summary`, and `juicefs quota` all provide a `--strict` option to run in strict mode. This bypasses directory statistics, unlike the default fast mode", and `juicefs fsck --path /d --sync-dir-stat --repair` recomputes and rewrites a wrong counter, with the worked example showing a fast-mode 448 MiB against a strict 1 GiB (READ, `dir-stats.md` lines 102 to 157). Setting a quota on a directory "may take a long time for a large directory, because the current usage of the directory needs to be calculated" (READ, `docs/en/guide/quota.md` line 150), and nested quotas are each checked by a recursive lookup up the path (line 205). JuiceFS is thus the closest analogue to vfs, a metadata engine over SQL (its `dbMeta` runs on SQLite, MySQL and PostgreSQL), and its answer is: direct-children counters as rows, deltas coalesced in memory and flushed in bounded batches, recursive totals only where a quota marks the directory, a fast mode labelled possibly inaccurate, a strict walk, and an fsck repair (INFERRED summary of the readings above).

## 9. Comparison: what the systems that run largest agree on

Maintained, never computed, on the hot path. All eight keep whatever aggregate they offer as a counter updated as a consequence of the write; none recomputes a subtree to answer a quota check or a size read. HDFS increments synchronously inside the mutation under its global lock; CephFS, ZFS, GPFS, Lustre and JuiceFS accumulate deltas and let them land with a declared lag; FSRM updates in a filter at I/O time; btrfs updates at transaction commit (READ, sections 1 to 8; INFERRED as a synthesis). The on-demand recursive walk exists everywhere, but every system treats it as the slow path and either throttles it (HDFS yields every 5,000 inodes for 500 µs), warns about it (JuiceFS "could be a costly operation", GPFS "I/O-intensive ... when the system load is light") or runs it only to seed or repair (FSRM "Rebuilding", btrfs rescan, HDFS quota initialization, JuiceFS fsck).

Recursive totals are kept only for marked directories, with one exception that proves the rule. HDFS keeps recursive counts only on quota-bearing directories; JuiceFS keeps direct-children counts on every directory and recursive totals only where a quota is set; FSRM keeps recursive bytes only on quota folders; GPFS, Lustre and ZFS keep them at fileset, project or dataset granularity, each a marked subtree or identity. CephFS alone keeps a recursive `rstat` on every directory, and CephFS alone needed a scatter-lock protocol to do it, rate-limits its propagation at 1 and 5 seconds by default, documents its quotas as imprecise by "tens of seconds", and has mailing-list reports of hours and a maintainer saying the trigger for updates was never fully defined (READ, section 1). The two designs that keep a recursive counter for every directory (CephFS) or a precise shared-or-exclusive total maintained at every commit (btrfs qgroups) are the two whose own documentation records the heaviest costs (INFERRED).

Every counter is labelled, and every system keeps a scan to repair it. Ceph: "Quotas are imprecise". ZFS: "generally accounted for within a few seconds", "may be delayed by several seconds". GPFS: an `in_doubt` column, "transient and can be ignored" negatives, `mmcheckquota` when in-doubt grows. Lustre: "approximate until the user is near the limit". JuiceFS: fast mode "can potentially produce inaccurate results", `--strict`, `fsck --sync-dir-stat`. btrfs: an "Inconsistent" status and `quota rescan`. HDFS: "BUG: Inconsistent storagespace" logged when the scan disagrees, counters rebuilt from the tree at every startup. FSRM: a "Rebuilding" state (READ, sections 1 to 8). No system I read presents a maintained aggregate as exact to the caller without a strict or repair path beside it.

The lag the asynchronous ones accept is seconds. JuiceFS flushes directory statistics every 1 second and quota usage every 3 seconds; CephFS propagates no faster than 1 second and nudges at 5; ZFS says "a few seconds"; Ceph quota enforcement lands "within tens of seconds"; GPFS's in-doubt is bounded only by the next `mmcheckquota` (READ). HDFS accepts zero lag by paying an ancestor walk inside the lock, and that lock still serves 150,000 to 250,000 operations a second over 1.1 billion objects at LinkedIn (READ, section 2), because the increment is an in-memory add bounded by depth (INFERRED).

The scan's cost, where it is measured. HDFS: 55 seconds single-threaded to re-derive all quota counters from a large production fsimage, 12 seconds on 8 threads; `getContentSummary` over 20 seconds under the lock before the yield was added (READ, section 2; inode counts not stated). GPFS: a billion files in under twenty minutes across a cluster on spinning disks (READ, section 6; recollection). Neither figure is on a 10-million-file corpus, and both are in-memory or parallel-cluster scans, so they are lower bounds for a relational store (INFERRED).

What the batching looks like. JuiceFS coalesces per-directory deltas in memory and lands them 1,000 rows per transaction as `x = x + ?` increments; HDFS folds the whole delta of one operation into one path walk; GPFS grants space in qunits so that nodes do not round-trip per write (READ). Where many writes hit one directory, every system adds once per flush or per operation, never once per file per ancestor in separate statements (INFERRED).

## 10. Proposed figures for the reference table

Per-directory aggregate kept: direct-children file count, subdirectory count and byte total as columns on the directory row, maintained with the write. Justification: this is JuiceFS's `dirStats` row and CephFS's `fragstat`, the shape the two file-system-over-metadata-store designs chose, and the cheapest to keep because a write touches one parent (READ, sections 1 and 8).

Recursive totals: kept only for marked directories (mount roots and any directory an operator or a quota marks), not for every directory. Justification: HDFS, JuiceFS, FSRM, GPFS, Lustre and ZFS all scope recursive counters to marked subtrees; the one system that keeps them everywhere, CephFS, carries the heaviest protocol and the worst recorded staleness (READ, section 9).

Update path: inside the write transaction when the store is a single transactional database (HDFS's model, lag zero), with per-directory deltas coalesced within a batch so a 10,000-file write issues one increment per touched directory per ancestor level, not 10,000 ancestor chains. Justification: HDFS increments synchronously under one lock at a billion objects; JuiceFS batches 1,000 directory rows per transaction (READ, sections 2 and 8; INFERRED for the batch shape).

Declared staleness budget where asynchronous: 1 to 5 seconds. Justification: JuiceFS 1 s and 3 s, Ceph 1 s minimum and 5 s nudge, ZFS "a few seconds" (READ; documented defaults).

Exposure contract: the fast read is labelled approximate, a strict read walks, and a repair verb recomputes and rewrites. Justification: every one of the eight systems ships this triad in some form (READ, section 9).

On-demand recursive scan budget: a yield every 5,000 entries (HDFS's default) or an equivalent chunk, treated as a maintenance operation rather than a hot-path verb. Justification: HDFS-4995 and the `dfs.content-summary.*` defaults; GPFS "run when the system load is light" (READ).

Full-recount reference cost: one visit per entry, so ten million visits for the reference corpus; the only measured anchors are HDFS's 55 seconds single-threaded on a large unstated fsimage and GPFS's billion files in twenty minutes on a parallel cluster, both in-memory or near it, so a relational recount is slower by a factor this study cannot give (READ for the anchors; INFERRED for the bound).

Ancestor increments per write: one per ancestor that carries a counter, bounded by depth, which is HDFS's loop. Researcher 01's depth figure fixes the constant (READ, section 2; INFERRED).

The one figure in Clay's proposal this evidence most changes: the proposal carries no directory-aggregate line, and so leaves the question open between "maintain on every write" and "compute on demand"; the evidence closes it. The systems at a billion files maintain direct-children counters with the write and compute nothing recursive on demand for the hot path, so the reference table should carry an aggregate line, and the cost it books for the 1% daytime edits and the 10% nightly batch is one coalesced increment per touched directory per flush, not a subtree count per `ls` or `stat`. The nightly 10% batch, a million files under the proposal, is the case that forces coalescing: a million separate ancestor-chain updates is the pattern none of the eight systems does (INFERRED from sections 2, 8 and 9).

## What this study does not settle

The Lustre Operations Manual's quota chapter, Oracle's btrfs comparison and IBM's 5.0.x fileset documentation were unreadable through the fetch tool inside the box, so Lustre's project-quota inheritance rests on the wiki and AWS's operator documentation, and GPFS's fileset model rests on the 5.2.0 pages plus search summaries. No Ceph document I reached states a numeric cost for rstat maintenance or a measured production file count, and the Ceph Days 2026 slides that carry per-rank throughput were a binary PDF I did not decode. HDFS-8865's 55-second figure has no inode count attached, so it cannot be scaled to ten million files. No source measured a relational database keeping these counters, so the translation from in-memory NameNode increments to row updates with their lock and index costs is left to the spec and to a benchmark of vfs's own.

## One line

At a billion files, directory aggregates are counters kept with the write, direct-children everywhere and recursive only where marked, labelled approximate with a strict walk and a repair scan beside them.
