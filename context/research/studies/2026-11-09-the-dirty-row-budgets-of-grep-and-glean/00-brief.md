## The question (from Clay, 2026-11-09)

Glean's lexical leg scores at most 500 unindexed entries per call (`OVERLAY_BUDGET` in `glean.py`), in path order, and drops the rest with a record. Grep's scan tier reads up to its remaining candidate budget of 25,000 unindexed entries, in the same path order, under a 10 second wall. Clay asked whether glean could brute-force the dirty rows the way grep does, or whether both verbs should carry one limit N past which dirty files are left out, and whether the rule should differ by store size. The refresh spec ([2026-10-31](../../../specifications/active/2026-10-31-refresh-the-incremental-index-verb.md), decision 23) leaves both budgets as they are; this study decides whether that is right before the spec is built. What Clay wants confirmed is that the defaults are set up properly, make sense at the reference scale, and agree with each other. Prior art is out of scope by Clay's decision: the question is about our own numbers.

## What is known today (verified in the code at b85e3df)

- Both verbs partition on `vfs_entries.encoded`: the index tier serves `encoded` rows from the epoch's postings, the scan tier serves `NOT encoded` rows from their live bodies. The scan tier nomination is one shared helper, `scope.entries_for_scan`, which returns rows in path order capped at a `limit`, and both verbs pass it the same gates and scope channels.
- grep (`grep.py`): `CANDIDATE_BUDGET = 25_000` counts index candidates plus scan nominees; the scan tier gets `CANDIDATE_BUDGET - len(index candidates)`; when the index side alone fills the budget the scan tier is never consulted and the record says so by name. Bodies are fetched in `CONTENT_BYTE_BUDGET = 32 MiB` batches, matched through the shared matcher on the offload pool, under `WALL_TIME_BUDGET = 10.0` s measured from the verb's entry (`offload.py`). `POSTING_BYTE_BUDGET = 4 MiB` bounds the index side. Every trip appends a named truncation and the Result carries a warning record.
- glean (`glean.py`): the overlay fetches up to `OVERLAY_BUDGET = 500` nominees, judges the gates, fetches bodies, tokenizes and scores them (`_overlay`, `_overlay_blocks` on the offload pool, `score_blocks`) under the base epoch's statistics with the overlay's own df for terms the base never saw; when the nominee fetch overflows it appends `("overlay budget", {"scanned", "budget"})`. `SCOPE_ID_BUDGET = 5_000` is the allow-list size past which a scope counts as wide. The vector leg reads chunk vectors directly; a dirty entry has no vector until the embed step runs, so the overlay is a lexical-leg device only.
- `OVERLAY_BUDGET` arrived with the lexical leg landing (`54c8915`, spec 132). No research memo measured it.
- The baseline study of 2026-10-31 ([02-baseline-measurements](../2026-10-31-incremental-index-refresh/02-baseline-measurements.md)) measured grep's scan tax (10 patterns: 1.0 s clean and 4.0 s at 5% dirty on 10k; 13.4 s clean and 24 to 27 s at 1 to 5% dirty on 50k) and saw glean's overlay record appear exactly when the dirty set passed 500. Its scripts under `../2026-10-31-incremental-index-refresh/experiments/baseline/` (`corpus.py`, `harness.py`, `study.py`) build synthetic prose corpora and drive the verbs; reuse their approach, not their files.

## The reference scale (AGENTS.md, "The reference deployment")

10,000,000 files; median body 4 KB; about 150,000 verb calls a day, of which ranked searches are about 200 by people and under a tenth of agent calls; about 50,000 organic single-file writes a working day, 100,000 at the ceiling; a nightly batch of 1,000,000. The dirty set is write rate times time since the last index pass, so with a 15 minute refresh it is about 1,250 to 2,500 in working hours, with hourly refresh 5,000 to 10,000, and with three rebuilds a day and no refresh it reaches tens of thousands by afternoon. These figures are the same on a 100,000-file store with the same write rate: corpus size does not set the dirty set.

## The two studies

01, inventory and alignment (reads code and git history, runs nothing heavy). Every runtime limit the two verbs apply on or around the scan tier, in one table: name, value, module, what it counts, what it protects, the record it emits when tripped, and where it came from (the landing commit and whether a memo or spec measured it). Then the alignment check in plain terms: do both verbs bound the scan tier in the same shape (count, bytes, wall), do their records tell a caller the same kind of thing, does `entries_for_scan`'s path order mean the same file is dropped by both, and which numbers are measured against which are inherited. Name every divergence and say whether it is justified by a real difference between the verbs or is drift.

02, the measured cost curve (SQLite, this machine, plus one Postgres leg). Corpora of 10,000 and 100,000 files, bodies log-normal around a 4 KB median with a tail to 200 KB, chunked and fully indexed by `reindex()`, then dirtied by rewriting N files chosen uniformly at random for N in 500, 2,000, 5,000, 10,000, 25,000 (skip N above the corpus). For each N: five grep patterns and five glean queries of 2 to 4 words at `limit=10`, each run three times, reporting wall, statements issued, rows fetched, bytes of body read, and the truncation records. For glean, run with `OVERLAY_BUDGET` lifted to 25,000 for the measurement (monkeypatch the module constant in the harness; the repo is read-only) so the curve past 500 is visible, and split the overlay's cost into nominee fetch, body fetch, and tokenize-and-score (time the `_overlay` phases with the harness; use statement counts and byte totals as the primary measure and report the clocks as facts with the machine named). Postgres leg: the same at N = 10,000 and 25,000 on the 100,000 store, URL `postgresql+asyncpg://vfs:vfs@localhost:54320/vfs` (the container is up). Report the N at which each verb crosses the 10 second wall and what a dirty entry costs each verb per call.
