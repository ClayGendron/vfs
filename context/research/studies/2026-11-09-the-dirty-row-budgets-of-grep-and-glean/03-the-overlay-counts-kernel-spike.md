# With tokenize-and-count in a Rust kernel the overlay costs glean about 60 µs per dirty row on SQLite, 40 of them the engine's own tokenizer, against 165 µs today and grep's 10 to 25 µs

Study 02 ([02-the-dirty-set-cost-curve](02-the-dirty-set-cost-curve.md)) measured glean's overlay at about 175 µs per dirty row, of which about 150 µs is `_overlay_blocks` in `src/vfs/storage/backends/database/glean.py`: the Rust tokenizer returning every token as a Python string, then a Python `Counter` over them. It left one question as an estimate: what the overlay costs when the tokenize-and-count stays in Rust. This is study 03, the spike that measures it ([the brief](00-brief.md); [the memo](../../2026-11-09-the-dirty-row-budgets-of-grep-and-glean.md), section 7, first item). The box was two hours of wall time; the work took about 50 minutes of it, and every step of the brief ran, the pyo3 prototype and the rerun on the 100,000-file store included. Nothing under `src/`, `tests/` or `crates/` was edited, and no existing file under `context/` was changed; the brief's file table row for this study is still to be filled in by whoever lands the folder.

Labels: EXECUTED means a command ran here and the claim reports its output; READ means read in a cited file; INFERRED means reasoning from the two.

## 1. The answer in one paragraph

EXECUTED and INFERRED. In pure Rust on this machine the engine's `tokenize` runs at 112 MB/s, 64 µs per 7,167-byte body, 59 ns per token; the fused kernel that tokenizes and counts in one pass with no per-token allocation and no dictionary runs at 170 MB/s, 41 to 43 µs per body for two to four query terms; building a Rust dictionary of every token instead costs 102 to 114 µs per body, so the dictionary is the expensive part in Rust too. Called from Python the batched kernel costs 41 to 42 µs per body, the same as pure Rust to within the noise, and a call per document costs at most 2 µs more, so the boundary crossing is not a factor at either granularity. Inside the verb on the 100,000-file SQLite store, with `OVERLAY_BUDGET` lifted to 25,000 and `_overlay_blocks` routed through the prototype, the overlay's tokenize-and-count phase measured 38 to 41 µs per dirty row (against 139 to 144 in the same session through the Python path), the overlay as a whole 59 to 65 µs (against 159 to 185), and the whole call 67 to 77 µs per row at N of 10,000 and 25,000 (against 167 to 182); the slopes between levels are 39 to 41 µs per row for tokenize-and-count, 57 to 60 for the overlay and 65 to 70 for the call. Every hit list and every score was identical to the Python path's on all five queries at all three levels, and the sentinel file was found at 10,001 dirty rows and lost at 25,001 exactly as before. On Postgres the projection is about 110 µs per dirty row (70 of SQL legs measured by study 02 plus 40 of kernel), so an ordinary 25,000-row call falls from the measured 5.3 to 5.6 s to about 2.8 s and the 9.4 s worst call, which carries 3.6 s of fixed index-tier cost, to about 6.8 s. The remaining gap to grep is the tokenizer itself: 40 µs per body against grep's matcher at about 0.5 µs, and a byte-level probe of the same rules on all-ASCII bodies shows it can reach 24 µs without changing a rule.

## 2. Method

EXECUTED. Step 1, the intrinsic throughput: a scratch binary crate depending on `vfs-core` by path (no `python` feature) read the 2,000 bodies and timed `vfs_core::tokenize` over all of them, seven timed passes after one warm-up, median reported; `std::hint::black_box` holds the results. Corpus facts, counted in Rust: 2,000 bodies, 14,334,854 bytes, 14,334,854 chars (every body is ASCII), 2,184,212 tokens by the engine's tokenizer, 7,167 bytes and 1,092 tokens per body; study 02's micro-measurement used the same generator, the same count of bodies and reported the same 14.3 MB and 2.18 million tokens, so the figures are comparable.

EXECUTED. Step 2, the counting step: `kernel.rs` reproduces the tokenizer's loop (same scanning, folding, identifier splitting and length rules; the generated tables are included from `crates/vfs-core/src/lexical_tables.rs` by `#[path]` so they cannot drift) with one change, the folded term is handed to a closure as a borrowed `&str` instead of being cloned into a `Vec<String>`. Over that loop sit `count_terms` (total count plus a compare of each term against the two to four query terms), `count_terms_dictionary` (a `HashMap<String, u32>` of every token, then the query terms looked up) and `overlay_postings` (the batch shape: per query term the `(doc_id, tf, dl)` postings in doc order plus the summed length). The bench also times, on the engine's own `tokenize` output, a `HashMap<&str, u32>` count with lookups (the shape of Python's `Counter`) and a linear compare of each token against the term list. Before timing, the bench asserts on every body and every query that the kernel's token count equals `tokenize(body).len()` and its term frequencies equal those of the `HashMap` over `tokenize`'s output.

EXECUTED. Step 3, the crossing: the pyo3 prototype exposes `overlay_postings(docs: list[tuple[int, str]], terms: list[str])`, which borrows the bodies as `PyBackedStr` (no copy for these ASCII strings), runs the kernel under `py.detach` as the grep matcher does, and returns the per-term postings as tuples; and `count_terms(body, terms)` for a call per document. `crossing.py` timed, on the same 2,000 bodies as Python `str` objects, the status quo loop (`tokenize` plus `Counter` plus `get`), `vfs.models.lexical.tokenize` alone, the batched kernel and the per-document kernel, seven passes, medians, then asserted the kernel's postings equal the status quo's on every body and query.

EXECUTED. Step 4, the rerun: `study_kernel.py` installs a switch in place of `glean._overlay_blocks` before study 02's harness wrappers are installed, so the `glean.tokenize` phase timer wraps whichever implementation the switch selects; the kernel implementation calls `overlay_counts.overlay_postings` and then assembles the blocks exactly as the Python original does (`idf`, `term_weight`, `encode_block`, `BLOCK_SIZE`, read off the glean module). Per level on the 100,000-file SQLite store: a fresh copy of study 02's clean indexed base (`PRAGMA wal_checkpoint(TRUNCATE)` then a file copy), the same N files study 02 drew (`random.Random(1000 + n).sample`) rewritten with `salt=1` plus the sentinel last, one pass of the five lifted-budget queries through the Python path, three passes through the kernel path, then each query once through each path with the hit lists compared path for path and score for score, then the sentinel recall probe through the kernel; the wall was lifted to 600 s as in study 02. Levels 5,000, 10,000 and 25,000 ran, 5,000 added for a third point on the slope. The smoke run on the 10,000-file store at N of 500 is on file too.

## 3. The tokenizer's intrinsic throughput, and the kernel variants

EXECUTED, pure Rust, 2,000 bodies, median of seven passes, from [bench_output.txt](experiments/kernel/bench_output.txt). The parity assertions passed for the fused, dictionary and byte-path kernels on every body and query.

| variant | query terms | µs per body | MB/s | ns per token |
|---|---|---|---|---|
| A: `vfs_core::tokenize` → `Vec<String>` (what Python calls) | none | 64.2 | 112 | 58.8 |
| B: A, then `HashMap<&str, u32>` over every token, then look up the terms (`Counter`'s shape) | 2 to 4 | 110.8 to 114.2 | 63 to 65 | 101.5 to 104.6 |
| C: A, then compare every token to the term list, no dictionary | 2 to 4 | 67.2 to 70.9 | 101 to 107 | 61.5 to 64.9 |
| D: fused kernel, no per-token allocation, no dictionary (`count_terms`) | 2 to 4 | 41.3 to 43.1 | 166 to 174 | 37.8 to 39.4 |
| E: fused tokenizer feeding a `HashMap<String, u32>` of every token (`count_terms_dictionary`) | 2 to 4 | 101.7 to 103.5 | 69 to 70 | 93.1 to 94.7 |
| F: the batch entry point the prototype wraps (`overlay_postings`) | 2 to 4 | 41.8 to 43.8 | 164 to 171 | 38.3 to 40.1 |
| G: the same rules over bytes for all-ASCII bodies, a headroom probe (`count_terms_ascii`) | 2 to 4 | 23.9 to 25.5 | 281 to 300 | 21.9 to 23.3 |

INFERRED from the table. The engine's tokenizer alone, in Rust, is 64 µs per body, not the 87 µs study 02 measured through Python; the 23 µs difference is the cost of materializing 1,092 Python `str` objects per body, about 21 ns each, and it vanishes when the tokens never cross. Of the 64 µs, about 22 µs (A against D) is the per-term `String` clone in `emit`, so a third of the tokenizer's own time is allocation. A dictionary of every token costs about 60 µs per body in Rust whichever way it is built (B against C, E against D): about 1,092 hash-and-probe operations at 55 ns each, the same order as Python's `Counter` at 65 µs, so moving `Counter` to Rust without removing it would buy little. The compare against two to four terms is in the noise: D moves from 41.3 to 43.1 µs between two and four terms, under 1 µs per extra term per body. The byte-level probe G is not the proposal, since it handles only the ASCII case and falls back to D otherwise; it shows that the rules themselves are not the floor and that `Vec<char>` collection plus the fold buffer cost another 17 µs per body.

EXECUTED and INFERRED. The batched call from Python, 40.6 to 42.0 µs per body, is within a microsecond of the pure-Rust F figure of 41.8 to 43.8 µs, so the crossing per batch, the `PyBackedStr` borrows and the result tuples together cost under 1 µs per body; and a call per document costs 0.6 to 2.4 µs more than the batch, which is the per-call crossing. Either granularity is affordable next to the 40 µs of tokenizing. The status quo reproduces study 02's 152 µs per body within a few µs (143 to 148 here), and the kernel's postings equalled the status quo's on every body and query, so the two measurements are of the same work.

## 6. The projection beside grep

EXECUTED on SQLite (sections 3 to 5 here, and study 02's sections 4 and 9); INFERRED for Postgres from study 02's section 8 SQL-leg figure of about 70 µs per row plus the kernel's 40 and a crossing under 2.

| cost per dirty row per call | grep, scan-only pattern | grep, five-pattern slope | glean overlay today (Python) | glean overlay with the kernel | glean whole-call slope with the kernel |
|---|---|---|---|---|---|
| SQLite 100,000 files | 24 to 37 µs | 10 to 23 µs | 159 to 167 µs | 59 to 65 µs measured | 65 to 70 µs measured |
| Postgres 100,000 files | 65 to 66 µs | not measured | 210 to 225 µs | about 110 µs projected | about 115 µs projected |
| of which SQL legs | the whole figure less about 0.5 µs of matcher | the same | 22 to 26 µs SQLite, about 70 Postgres | the same | the same |
| of which CPU | about 0.5 µs (the Rust matcher) | the same | 135 to 146 µs Python around `tokenize` | 38 to 41 µs Rust kernel | the same |
| body bytes read | about 7 KB | 3.4 to 7 KB | about 7 KB | about 7 KB | about 7 KB |

INFERRED. At the lifted budget of 25,000 rows a glean call's overlay drops from 4.1 s to 1.5 s on SQLite, and on Postgres from the 5.3 to 5.6 s study 02 measured to about 2.8 s; the one Postgres call that touched 9.4 s against the 10 s wall, the two-very-common-terms query, keeps its 3.6 s of fixed index-tier cost and loses about 2.6 s of overlay, so it would sit near 6.8 s, and the ordinary queries near 2.9 s. Both verbs then clear the wall inside a shared 25,000 count: grep's scan-only call at that count was 0.63 s on SQLite and 1.63 s on Postgres, and its slowest call with the index side in play 1.02 s and 2.7 s. Per dirty row glean now costs 2 to 2.5 times grep's scan-only pattern on SQLite (60 against 24 to 37) and under 2 times on Postgres (110 against 65), down from 7 and 3.3; against grep's whole-suite slope of 10 to 23 the ratio is 3 to 6, down from 7 to 17. The two verbs read the same 7 KB per dirty row and issue the same statement count, so what is left of the difference is the engine tokenizer at 40 µs a body against a trigram-verified regex at under 1 µs, and the byte-path probe says about 17 of those 40 are collection and fold buffers rather than rules. At the reference deployment the multiplier is the ranked-search count: with a 15 minute refresh and a dirty set of about 2,500 rows, each glean's overlay costs 0.15 s of offload CPU with the kernel against 0.4 s today, and the body traffic of about 17 MB a call is unchanged by the kernel, which removes the CPU asymmetry between the verbs and leaves the byte traffic as the shared cost one count limit bounds.

## What this study does not settle

The Postgres figure is a projection from study 02's SQL legs plus this study's kernel, not a measurement; the experiment is the `study_kernel.py` driver pointed at `postgresql+asyncpg://vfs:vfs@localhost:54320/vfs` with study 02's schema clone at N of 10,000 and 25,000.

Whether the engine's `tokenize` itself should drop the per-term `String` (about 22 µs of 64 per body) for the indexer's sake as well as the overlay's, and whether a byte path for ASCII runs (another 17 µs) is worth its second code path; the experiment is the bench's variants D and G run inside `reindex()` on the 100,000-file store, counting rows visited and reporting the build wall as a fact, against the index-visit multiplier of about 11,000,000 a day.

The kernel's return shape, tuples per posting against three packed arrays per term, was not costed at 25,000 rows beyond being in the noise here; the experiment is the prototype with a `bytes`-returning encoder (the engine's block codec on the Rust side) against the tuple form, counting Python objects created per call.

The prototype runs detached from the GIL on borrowed `PyBackedStr` bodies, which is correct because `_overlay` holds the `docs` list alive across the call; whether the production kernel should instead own its bodies (one copy of about 7 KB a row) so the offload pool can drop the list early is a design choice for the spec, not for this study.

The sentinel behaviour and hit parity were checked at `limit=10` on five queries; the experiment that pins the kernel for landing is a parity test in `tests/` comparing `_overlay_blocks` against a pure-Python oracle in `tests/support/oracles/` over generated bodies with non-ASCII, mixed-case and underscored identifiers, which these prose bodies barely exercise.

## One line

In Rust the engine's tokenizer costs 64 µs per 7 KB body and a fused tokenize-and-count 41 µs, the pyo3 crossing costs under 2 µs a document, and inside glean on the 100,000-file SQLite store the kernel takes the overlay from about 165 to about 60 µs per dirty row with identical hits and scores, so glean brute-forcing the dirty set costs 2 to 2.5 times grep's scan tier instead of 7, and one shared count limit is now affordable for both verbs.
