## Zensical: what it is and how far along it is

- READ (`README.md`, `pyproject.toml`): Zensical is a static site generator "built by the creators of Material for MkDocs". It is a Rust engine with a Python package around it, built with maturin, and it needs Python 3.11 or later. Its Python dependencies include `markdown`, `pymdown-extensions`, `jinja2` and `pyyaml`, so pages are still rendered by Python Markdown today.
- READ (the announcement page): it replaces both MkDocs and Material for MkDocs with "one coherent stack". The author of mkdocstrings has joined the project to work on API reference generation.
- EXECUTED (package index): the latest release is 0.1.1, dated 2026-11-10. Release 0.1.0 is dated 2026-11-05. There are 76 releases since a first placeholder on 2024-11-25, and 25 of them fall between 2026-07-30 and 2026-11-10, which is about one release every four days.
- READ (`pyproject.toml`): the package classifies itself "Development Status :: 4 - Beta".
- READ (https://zensical.org/docs/upgrade/): the project "follows semantic versioning and is currently on the 0.x release line, starting with version 0.1.0". Public interfaces may still change, and "once we reach version 1.0, the standard semantic versioning rules will apply more strictly". The announcement's October 2026 notice calls 0.1 "a dependable release line".
- READ (https://zensical.org/roadmap/): the roadmap "does not promise delivery dates or a fixed implementation order". It lists 17 items as available, all of them replacements for MkDocs plugins or settings (among them `privacy`, `llmstxt`, `blog`, `social`, `api-autonav`, `autoapi`). It lists one item as in development: Zensical Markdown, a Rust reimplementation of Python Markdown. It lists three items as up next: command-line access to the project model, a migration readiness check, and the Module API for Python. The Module API is marked "Spark first", which means members of the paid Zensical Spark programme get it before the public does. Versioning, a native API documentation system and CommonMark support are listed with no status.
- INFERRED: "stable" in Zensical's own words today means the build of an existing Material for MkDocs project from its own configuration. "Planned" means every way of extending the build with one's own code.

## Zensical: how a site is configured, and what it says about each thing the vfs site uses

- READ (`python/zensical/main.py`, `config.py`): the build looks for `zensical.toml`, then `mkdocs.yml`, then `mkdocs.yaml`, or takes a file named with `-f`. A `.toml` file is read as a `[project]` table; anything else is read as MkDocs YAML, including `!ENV` tags, `!!python/name:` tags and `INHERIT`.
- READ (migration page): "Both builders read the same `mkdocs.yml`", moving to `zensical.toml` "is not required", and the recommended path is to keep MkDocs in production, build the same project with Zensical beside it, and compare.

## The experiment: the vfs site built with Zensical 0.1.1

The pages above say what should work. This experiment checks it. The site's inputs (`documentation/`, `overrides/`, `mkdocs-documentation.yml` and `src/vfs`) were copied to a scratch folder outside the checkout, and `uvx --from zensical==0.1.1 --with "mkdocstrings[python]>=1.0" zensical build -f mkdocs-documentation.yml` was run there. Nothing in the vfs checkout was built or changed. Each run's output is saved in the experiment folder.

- EXECUTED (run A, configuration unchanged): the build fails. The error is `unknown method: undefined has no method named strftime (in partials/copyright.html:18)`. The footer override calls a Python method on the build date, and MiniJinja has no Python methods. This is the caveat the migration page states.
- EXECUTED (run B, that one template line replaced by fixed text in the scratch copy): the build succeeds and writes 14 HTML files, 13 pages and a 404 page. Three things are missing and nothing fails. First, no page under `reference/api/` exists: the hook `api_pages.py` never ran, and the only signal is three "page does not exist" warnings for the glossary's links to those pages. Second, both diagrams on the Overview page are still `<img>` tags: the hook `inline_svg.py` never ran. Third, no line of the log names hooks at all (`grep -ci hook` returns 0 for every run).
- EXECUTED (run B): the rest carried. The tabs, the three partial overrides and `main.html` rendered. The privacy replacement ran and applied `links_attr_map` (four links carry `aria-describedby="vfs-new-tab"`). The 15 Markdown extensions, the Mermaid custom fence and the `!ENV` tag raised no warning.
- EXECUTED (runs A and B; `find site/assets/external -type f` after run D): the privacy replacement downloaded 49 files. 33 are the fonts. The other 16 are scripts and styles named in the theme's bundle: a Python-in-browser runtime, a code editor, a lightbox, a diagram library, a video player, and files from two advertising hosts. Apart from the diagram library, which the site's Mermaid fence can call on, the vfs site uses none of them. No built HTML page refers to the other 15 (`grep -rl` over the HTML finds 0 files); the theme's own JavaScript bundle does. INFERRED: the replacement follows every address it finds in the theme's bundle, so the build contacts those hosts and the site ships copies of files no page loads.
- EXECUTED (run C, the five stub pages written by hand as `::: vfs.Name` and listed in the nav of the scratch copy): the build succeeds with "No issues found". mkdocstrings rendered all five pages. The headings match the brief's counts: 40 on `AsyncVirtualFileSystem` (the class and 39 members), 23 on `Entry`, 34 on `Result`, each with its symbol-type badge. The Griffe extension ran: no raw `:term:` marker remains in the output, and the `Entry` page links to `../../glossary/#entry`.
- EXECUTED (run D, one docstring in the scratch copy changed to mark a term the glossary lacks, built with `--strict`): the extension's message is printed, the build reports "No issues found" and exits 0. The guard that stops a build on an unknown term does not hold under Zensical. INFERRED: the extension reports through a logger that MkDocs counts as a warning in strict mode; Zensical does not count that logger.
- EXECUTED (run E, a page added to the scratch copy outside the nav, holding a link to a missing page, a link to a missing anchor and an absolute link, built with `--strict`): the missing page and the missing anchor are reported, "2 issues found", and the build aborts with exit code 1. The absolute link and the page left out of the nav are not reported. Two of the four checks the vfs configuration asks for carry.
- EXECUTED (run F, the `api-autonav` replacement enabled on `src/vfs` in the scratch copy): the build succeeds and writes 103 API pages, one per Python module, for the 103 Python files under `src/vfs`. It documents every module, private ones included. It does not make one page per exported name, and it has no notion of `vfs.__all__`.
- INFERRED: the key result is that the content pipeline carries and the build-time code does not. mkdocstrings, the Griffe extension, the privacy plugin, the overrides and the extensions all work. The two hooks do nothing, silently, and one guard goes quiet.

## The pattern

- INFERRED: the projects that moved or can move keep their own code out of the build. Polars had one hook and turned it into a script that runs first. uv has none: its generators write Markdown files, and the site tool only ever sees files. Zensical's own advice for generated pages is the same: run the script as a separate step.
- INFERRED: a script that writes files before the build works under every site tool. A hook that edits the build from inside works under one. The second kind is what a move costs.
- INFERRED: generated reference is trusted when it is never stored. uv ignores its generated pages in git and remakes them in every job, so a stale page cannot exist. The check mode is only needed where a generated file is committed.
- INFERRED: reference that is not a Python API is grouped by the kind of thing the reader has in hand: a command they typed, a setting key, an environment variable. Each kind gets one page with one heading per item, and the heading's anchor is the item's name, so other pages can link to an item for years.
- INFERRED: a separate API site, as Polars has, follows from a separate tool, not from a choice about readers. Its cost is visible: a link map of 282 URLs kept by hand.

## One thing in each project that looks like a mistake

- Zensical. EXECUTED (run B): a configuration that names hooks builds with exit code 0 and no message about them, while the pages those hooks make are missing. READ: the plugins page says unlisted plugins are "silently ignored". INFERRED: a tool that reads another tool's configuration should say which parts it skipped; silence turns a missing feature into a wrong site.
- Polars. READ and EXECUTED: the guide links to the API through 282 absolute URLs typed by hand into one YAML file, all pointing at the `stable` build. Nothing in the clone checks them against the Sphinx output. A second one: the build's success depends on searching the log for a failure sentence.
- uv. READ (`docs/reference/index.md` against `mkdocs.yml`): the hand-written index of Reference lists six entries and omits Environment variables, Installer options, Troubleshooting and Benchmarks, so the one hand-kept list on the section has drifted. EXECUTED: the command-line reference is a single page of 1.18 MB. EXECUTED (`grep -c 'Self::'` on the live environment page gives 4): links written for the code's own documentation tool leak into the page as dead link targets. READ: Reference also holds Contributing, Benchmarks, Troubleshooting and Policies, which are not reference in the Diátaxis sense.

## What the vfs site should do

### The tool: move later, on a named trigger, and keep the cost of the move small until then

- Do not move now. Reason: the site depends on two hooks and Zensical has no replacement for them. Evidence: the migration page lists `hooks` as "not yet supported"; the Module API for Python is "up next" with no date and reaches paid members first; run B built the site without its API pages and without inlined diagrams and reported success.
- Do not plan to stay for good. Reason: fixes for Material for MkDocs end on 2027-05-05, under six months away, and its authors call MkDocs itself unmaintained. Evidence: the announcement page. The site would still build from pinned versions after that date, so the date is a deadline for a decision, not for the move.
- Move when one of two things is true: Zensical ships a public way to run build-time code, or the site no longer needs any. Evidence: everything else carried in runs B and C, so the hooks are the whole of the gap.
- What carries, as measured: the configuration file as it is, the nav and tabs, all 15 Markdown extensions, mkdocstrings with every handler option the site sets, the Griffe extension, the privacy plugin with its link attributes, the override folder, and the checks for a missing page and a missing anchor.
- What does not carry, as measured, and the fix for each. One: `overrides/api_pages.py` does not run. The fix is the one Polars and uv use: a script that writes the stub pages as files before the build, with the API section written in the nav. The check that a name is in `vfs.__all__` moves into that script. Zensical's own `api-autonav` is not a substitute: run F shows it makes a page per module, 103 of them. Two: `overrides/inline_svg.py` does not run. It rewrites rendered HTML, which no script before the build can do; it needs either the Module API or a pass over the built site after the build. Three: `overrides/partials/copyright.html` line 18 calls a Python method on the build date; the date must be passed in as text, for example through `extra`. Four: the glossary guard in `overrides/docstring_markup.py` reports an unknown term as a logged warning, and run D shows Zensical builds through it; the guard must raise an error instead, which stops either tool. Five: the checks for a page left out of the nav and for an absolute link did not fire in run E; a small script over the docs folder and the nav would restore the first.
- Until the move, treat each new hook as debt. Reason: the hook count is the migration cost. A hook that only creates files can be a script today at no loss. A hook that edits rendered pages is the expensive kind.
- Rehearse instead of guessing. Reason: runs A to F took a few minutes and found five concrete gaps, three of which no page of Zensical's documentation lists. Repeating them at each Zensical minor release shows when the gap closes. The commands are in this file and the logs are in the experiment folder.
- When the move comes, set `variant: classic` first and compare. Reason: the default variant is `modern`, and the site's own stylesheet was written against Material's markup and styles. Evidence: `config.py:809` and the migration page.

### The Reference entry: one tab, a sibling group per kind of thing, interfaces first, glossary last

- Keep the Python API inside Reference. Reason: it is built by the same tool in the same build, so glossary links, cross-references and link checks all resolve in one pass. Evidence: Polars keeps its API apart only because a different tool builds it, and pays with a hand-kept map of 282 URLs; uv, with one tool, keeps everything in one sidebar.
- Group by the kind of thing the reader has in hand, in this order: Python API, Command line, Settings, Error kinds, Access levels, Glossary. Reason: a reader arrives with a name, a command, a setting key or an error, and each should have one obvious place. Interfaces come first because they are looked up most; the glossary comes last because every other page links into it. Evidence: uv orders Commands, Settings, Environment variables first, then hand-written facts.
- Name the group "Python API", not "API". Reason: once a command line sits beside it, "API" no longer says which interface. Evidence: uv names each group for what the reader types ("Commands", "Settings", "Environment variables").
- Give each non-API kind one page with one heading per item, and make the heading's anchor the item's own name. Reason: other pages then link to a single command, setting or error kind, and the link survives regeneration. Evidence: uv's hand-written pages hold 61 anchored links into its three generated pages.
- Split a page only when it grows past comfortable reading. Reason: one page is easiest to search and link while small. Evidence: uv's settings page works as one page at 155 headings and 432 KB; its command-line page, at 62 commands and 1.18 MB, is the example of one page kept too long. The vfs command line, with a handful of commands, fits one page.
- Generate the command-line, settings and error-kind pages from the code, and never store or hand-edit the output. Reason: a page remade on every build cannot go stale, and a strict build then checks every link into it. Evidence: uv ignores its generated pages in git and remakes them in every check and publish job. The vfs hook already has this property for the API pages, because its pages exist only during the build.
- Let generated and hand-written pages sit as plain siblings. Reason: a reader does not care how a page was made. Evidence: uv's sidebar draws no line between them.
- Keep the section's index page short, or generate it. Reason: a hand-kept list of the section's pages drifts. Evidence: uv's index omits four of its own entries.
- Keep pages that are not reference out of Reference. Reason: troubleshooting is how-to material, and contributing and policies describe the project, not the product's interfaces. Evidence: uv's Reference holds eleven such pages out of twenty, and its index page no longer describes the section.

## What this study could not settle, and what would settle it

- Whether the site looks the same under Zensical. The runs checked that pages build and what they contain, not how they render. Opening the run C output in a browser beside the MkDocs build, once with `variant: classic` and once without, would settle it.
- Whether Zensical's own validation settings can restore the two checks that did not fire in run E. Polars rewrote its validation block to eight Zensical settings, none of which names the nav. Reading Zensical's validation page and repeating run E with those settings would settle it.
- Whether the 15 unused files the privacy replacement downloads can be switched off. Reading the data-privacy page of Zensical's documentation for an exclusion setting, and repeating run B with it, would settle it.
- When the Module API for Python becomes public and whether it can rewrite rendered HTML. The roadmap gives no date. Reading the roadmap and the plugins page again at each Zensical minor release would settle it.
- When Polars moved and which commit did it. The clone is shallow. Reading the history of `zensical.toml` in a full clone would settle it.
- How the same experiment fares on the current Material for MkDocs release. The vfs site names 9.7.1 and the latest is 9.8.1. Building the site with 9.8.1 and comparing the output would show whether the last maintained releases change anything the site relies on.
