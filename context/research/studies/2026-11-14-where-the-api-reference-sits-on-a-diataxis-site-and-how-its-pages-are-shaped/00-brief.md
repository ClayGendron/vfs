## The brief every researcher received

You are researching for the repository at `/Users/claygendron/Git/Repos/vfs`. vfs is a Python library, a virtual file system that gives AI agents governed access to an organization's data and tools. A developer installs it with pip, creates a file system in a few lines of Python, and hands an AI agent one command-line tool (`ls`, `cat`, `grep` and a few others) to work in it. Its readers are developers: people building AI agents, and enterprise teams deciding whether to adopt it.

The documentation is being rewritten under the Diátaxis framework (tutorials, how-to guides, reference, explanation). It is a static site built with Material for MkDocs 9.7.1 from the folder `documentation/` by `mkdocs-documentation.yml`. Its top bar holds the content types: Home, Tutorials, How-to Guides, Reference, Explanation. The sidebar shows the pages of the chosen entry. That shape was chosen from an earlier study and is not in question here.

What is new is the Reference tab. It holds two hand-written pages, Access Levels and Glossary, and since today an API section of five pages generated from the code's docstrings by mkdocstrings 1.0.8 with mkdocstrings-python 2.0.11. A build hook, `overrides/api_pages.py`, holds a list of public names, creates one page per name that holds the single line `::: vfs.Name`, and adds the pages to the navigation. Only names the package exports in `vfs.__all__` may have a page; there are 22 such names and five have a page so far: `AsyncVirtualFileSystem` (39 members on one page), `Entry` (22), `Result` (33), `MountInfo` (9) and `MountError` (1). The page for a class lists its public methods and its fields, a field with no docstring included; source code is not shown. The library has two faces with the same verbs, `AsyncVirtualFileSystem` and a synchronous `VirtualFileSystem`, so their pages will repeat each other. The docstrings are prose with reStructuredText roles and no parameter sections. A Griffe extension, `overrides/docstring_markup.py`, turns a `:term:` marker in a docstring into a link to the Glossary page and stops the build on a term the glossary does not define. The glossary is one page with one heading per term, and each term links to the API page of the class that defines it. The library also has a command line, error kinds, settings and a storage protocol that will need reference pages. The site will plausibly grow to a hundred pages or more.

The owner's questions are these. First, placement: should the API reference stay inside the Reference tab or become its own entry, and what else belongs in Reference beside it. Second, the pages themselves: how do mature projects shape an API page (one page per object, per class or per module; what a page shows; how it is ordered and indexed), and how do they maintain that look over years without hand-editing generated pages. Third, the long term: what structure will still hold at a hundred pages, and what the tool the site is built on will carry.

## The four questions

Researcher 01, where the API reference sits on sites that follow Diátaxis. Clones: `diataxis-documentation-framework` (the framework's own text, with its full history), `django`, `pytest`, `hypothesis`, `numpy`, `toga` (BeeWare), `sphinx-docs-starter-pack` (Canonical's template) and `lxd` (a Canonical product, documentation under `doc/`). First read what the framework's text says about reference: what reference is for, how it should be structured, and anything on generated reference and API documentation. Then for each project: is the API reference inside the section the project calls reference, or a separate top-level entry, and what is it called; what else the reference section holds beside the API (command line, settings, errors, file formats, a glossary, release notes) and how those pages are grouped (by domain, by module, by kind of thing, alphabetically); whether the API pages are written by hand or generated from the code, and by what; how many reference pages there are and what share is API; how tutorials, how-to guides and explanation link into the API reference; and whether the project has a glossary, where it sits, how an entry is written, and how many times the rest of the documentation links a term to it (count the markers). Say which projects keep the API apart from the rest of reference and what reason each gives, in its own words where it gives one. Write to `01-where-the-api-reference-sits-on-sites-that-follow-diataxis.md`, saved outlines under `experiments/01-where-the-api-reference-sits-on-sites-that-follow-diataxis/`.

Researcher 02, how sites built with Material for MkDocs and mkdocstrings build and shape their API pages. Clones: `fastapi`, `pydantic`, `textual`, `griffe` and `mkdocstrings-python` (the handler whose templates draw the pages; its own documentation lists every option). For each of the first four: where the API pages sit in the navigation (their own top entry, or inside a reference entry) and under what name; how many API pages there are and what one page covers (one object, one class, one module, one topic); how a page comes to exist (a hand-written file holding `:::` lines, a script run at build time, a plugin that walks the package) and where the list of documented names is kept; which mkdocstrings options are set for the whole site and which per page; whether any template or stylesheet of the handler is overridden, and how much; the docstring style, and whether docstrings were written with the rendered page in mind; how members are ordered and filtered, what the page's table of contents looks like for the largest class, and how large that page is; how cross-references between pages and to other projects are made; whether source code is shown; what hand-written prose surrounds the generated content; and what the entry page of the API section holds. Note that Pydantic's live site was reported on 2026-11-12 to have moved to another tool: report what the repository holds today and how its API pages are produced now. Then, from `mkdocstrings-python`: list the levers a site has over the look of an API page (the options by group, the template override mechanism, the stylesheet hooks, summary tables, backlinks, inherited members, signatures, symbol-type badges) and say which a small project should set once and leave. Write to `02-how-material-sites-with-mkdocstrings-build-and-shape-api-pages.md`, saved outlines under `experiments/02-how-material-sites-with-mkdocstrings-build-and-shape-api-pages/`.

Researcher 03, one page per object at scale, and an API reference kept apart from the guide. Clones: `numpy` (documentation under `doc/`, pages generated one per object), `polars` (a user guide under `docs/` and a separate API reference under `py-polars/docs/`) and `cpython` (the library reference under `Doc/library/`, written by hand, and `Doc/glossary.rst`). For each: how the API reference is divided into pages and why (per object, per class, per module, per topic), and how many pages result; how the index of the API is organised (by topic, by module, alphabetically) and who maintains that index; how a per-object page is generated and from what template, and what such a page holds; whether the API reference is a separate site, a separate build or a section, and how the guide and the reference link to each other in both directions; what the reader sees for a class with dozens of methods; and what the project says the approach costs (build time, scripts to maintain, pages to keep in step). Then the glossary practice in `cpython` and `numpy`: where the glossary sits, how an entry is written, how many times the documentation pages and how many times the docstrings link a term to it (count the `:term:` markers in each), and whether any check fails a build on an unknown term. Conclude what granularity suits a library with 22 public names today that may have 60 in two years, and what each choice costs at each size. Researcher 04, the tool's future and the reference that is not the Python API. Clones: `zensical` (the successor its authors name for Material for MkDocs), `polars` (which has moved its user guide to it) and `uv` (a Material for MkDocs site whose reference is generated from a command line and from settings). First the tool. Fetch what Material for MkDocs says today about its own maintenance and for how long. Then the reference that is not the Python API. From `uv`: what the Reference entry holds, which pages are generated and by what script, how a generated page is kept in step with the code, how the command-line reference is divided into pages, and how hand-written and generated reference pages sit side by side. Conclude two things: which parts of the vfs site would carry over to the successor tool, which would not, and whether the evidence says to move now, later or not at all; and how a Reference entry should group a Python API, a command line, settings, error kinds, access levels and a glossary.
