# Four mkdocstrings sites write their API pages by hand as short stub files grouped by topic or module, set the look once in site-wide options, and override no handler template; three of the four no longer publish with Material for MkDocs

I was asked on 2026-11-14 how sites built with Material for MkDocs and mkdocstrings build and shape their API pages, from the clones of FastAPI, Pydantic, Textual, Griffe and the Python handler `mkdocstrings-python`. The time box was 30 minutes and I used about 11 of them. Every item of the question was read for all four sites and the handler. The short version comes first. An API page on these sites is a small hand-written Markdown file that holds a few sentences and one or more `:::` lines. A `:::` line is the mkdocstrings directive that is replaced at build time by the rendered documentation of one Python object. No site generates those files with a script. No site overrides a template of the handler. The look is set once, in the site-wide options, and a page changes it only to pick or order members. One fact was not in the brief: only Textual still publishes with Material for MkDocs. FastAPI and Griffe now build the same `:::` pages with Zensical, and Pydantic's public site is built by another tool in another repository.

## The pattern

- Every page is a file a person wrote. INFERRED from the four READ results: no site creates API pages with a script or a plugin that walks the package. The stub is short, and it is the one place a person decides what is on the page and in what order.
- The page is a topic or a module, never a single small name. INFERRED: FastAPI puts 61 objects on 24 pages and Griffe puts 225 on 22. A class with many members gets its own page. Small related names share one. No site has a page for an object with one member.
- The look is set once and site-wide. INFERRED: between 7 and 22 options sit in the configuration. A page overrides almost nothing, and what it does override is which members appear and in what order.
- A handful of options are common ground. READ: `separate_signature` and `signature_crossrefs` are set by all four. `merge_init_into_class` is set by all four. Three of four set `show_symbol_type_heading` and `show_symbol_type_toc`. All four filter to public names, three with `'!^_'` and Griffe with `public`.
- Nobody overrides a template. EXECUTED and READ: zero handler templates are overridden across five repositories, the handler's own documentation included. The most any site does is eight CSS rules. This is how the look is maintained over years: there is nothing local to maintain.
- Prose sits around the generated content, and it is brief. INFERRED: a title, one to three sentences, sometimes an import line, sometimes group headings. The explanation lives in the guide. The API page links to it.
- Docstrings are written for the page. INFERRED: all four put Markdown links and cross-references in docstrings, hundreds of them. Pydantic has the clearest convention, a fixed admonition in the docstring that links to the guide and a fixed admonition in the guide that links to the API.
- Showing source is what makes a page heavy. INFERRED from the page sizes: the two sites that show source have the 1.2 MB pages. Textual shows none and its 196-heading page is 0.5 MB.
- Three of four give the API its own top entry, but for a reason the fourth does not share. INFERRED: FastAPI, Pydantic and Textual do not organise their top bar by Diátaxis type, and FastAPI and Pydantic have no other reference to put beside the API. Griffe has a command line and a parser reference, and it nests the API inside Reference beside them.

## The levers the handler gives a site

The handler documents 67 options (EXECUTED: counted from `src/mkdocstrings_handlers/python/_internal/config.py`, saved with each default in the experiments folder). Its documentation groups them in five pages under `docs/usage/configuration/`.

| Group | Count | What it controls | Options that change the look most |
|---|---|---|---|
| General | 12 | how code is loaded and what surrounds an object | `show_source`, `backlinks`, `show_bases`, `show_inheritance_diagram`, `extensions`, `preload_modules`, `extra` |
| Headings | 13 | the heading of each object and the table of contents | `heading_level`, `show_root_heading`, `show_root_full_path`, `show_symbol_type_heading`, `show_symbol_type_toc`, `parameter_headings`, `show_category_heading`, `toc_label` |
| Members | 8 | which members appear and in what order | `members`, `filters`, `members_order`, `group_by_category`, `inherited_members`, `summary`, `show_labels` |
| Docstrings | 22 | how a docstring is parsed and which sections show | `docstring_style`, `docstring_section_style`, `merge_init_into_class`, `show_if_no_docstring`, `relative_crossrefs`, `scoped_crossrefs` |
| Signatures | 12 | how a signature is drawn | `separate_signature`, `show_signature_annotations`, `signature_crossrefs`, `line_length`, `unwrap_annotated`, `show_attribute_values` |

- Options. READ: any option can be set site-wide, or under a `:::` line for one object. A page-level `docstring_style` applies to that object only, not to its members.
- Member order and filter. READ `docs/usage/configuration/members.md`: `members_order` takes `alphabetical` (the default), `source` or `__all__`. `filters` takes a list of regular expressions or the word `public`, which keeps names in `__all__` or without a leading underscore. `members` takes an explicit list, and the list's order wins over `members_order`. `group_by_category`, on by default, puts attributes, classes and functions in separate runs.
- Summary tables. READ: `summary` is off by default. It takes `true` or a mapping by kind (`attributes`, `functions`, `classes`, `modules`, `type_aliases`). It puts a table of names with their first line at the top of a module or class, before the full entries.
- Backlinks. READ `docs/usage/configuration/general.md`: `backlinks` takes `flat` or `tree`. It lists under an object every section of the site that links to it. The documentation warns that it works only when set site-wide.
- Inherited members. READ: `inherited_members` takes `true` or a list of names. Members come only from base classes in the same package, unless `preload_modules` names another package.
- Signatures. READ: `separate_signature` moves the signature out of the heading into a code block. `show_signature_annotations` adds types. `signature_crossrefs` turns each type into a link. `line_length` sets where the block wraps, 60 by default.
- Symbol-type badges. READ `docs/usage/customization.md`: `show_symbol_type_heading` and `show_symbol_type_toc` put a short coloured tag (class, method, attribute) before a name. The colours are CSS variables named `--doc-symbol-KIND-fg-color` and `--doc-symbol-KIND-bg-color`. The tag text is set by a CSS `content` rule, so a site can change both without a template.
- Stylesheet hooks. READ: every element has a class. `doc-object` and `doc-class`, `doc-function`, `doc-attribute` wrap an object. `doc-heading` marks its heading. `doc-contents` wraps its body, with `first` on the outermost. `doc-labels` and `doc-label-LABEL` mark labels such as `property`. `doc-section-title` marks a docstring section title. The handler ships its own 236-line stylesheet. The documentation recommends three additions for Material: a left indent on nested contents, a mark on external links, and the backlink tree.
- Template overrides. EXECUTED: the handler has 74 Jinja template files for the Material theme, base versions included. Each top-level template only extends a twin under `_base/`. EXECUTED: the base templates declare 108 blocks. The names that matter are `heading`, `labels`, `signature`, `docstring`, `contents`, `summary`, `source`, `children`, `bases` and `inheritance_diagram`. A site overrides by placing a file with the same name in a folder named by the `custom_templates` option of mkdocstrings, extending the base, and replacing one block. The documentation says only the Material templates have blocks. The `extra` option passes a site's own values into a template.
- What a small project should set once and leave. INFERRED from the four sites: `filters: public`, `members_order: source`, `separate_signature`, `show_signature_annotations`, `signature_crossrefs`, `merge_init_into_class`, `show_root_heading`, `show_symbol_type_heading`, `show_symbol_type_toc`, `show_source: false`, and `summary` once a class passes a dozen members. Leave `backlinks`, `inherited_members`, `parameter_headings`, `show_inheritance_diagram` and `show_category_heading` off until a reader asks: each one multiplies the size of a page or the length of its table of contents. Override no template.

## What the vfs site should do

- Keep the API inside Reference, as a nested section named "Python API". Reason: the vfs top bar is the four Diátaxis types, and vfs has a command line, error kinds, settings and a storage protocol that also need reference pages. Evidence: Griffe is the one site of the four with other reference material, and it nests the API beside its command line. The three that give the API a top entry have a top bar that is not organised by type. The placement question as a whole belongs to Researcher 01; this is what my four sites add to it.
- Group names into pages by topic; do not give every exported name a page. Reason: `MountError` has one member and `MountInfo` nine, and a page that short is a click that returns one paragraph. Evidence: no site of the four has one page per name; FastAPI averages 2.5 objects a page and Griffe 10. A workable cut for 22 names is one page each for `AsyncVirtualFileSystem`, `VirtualFileSystem`, `Entry` and `Result`, and one page per topic for the rest (mounts, errors, settings), which gives eight to ten pages today and room for 60 names without a longer sidebar.
- Make each API page a file in the repository, and turn the hook into a check. Reason: a page the hook writes can hold only the `:::` line, so it has no place for the sentence that says what the object is for, the import line, or a group heading. Evidence: all four sites hand-write the stub, and all four put prose in it. The hook's rule, that only names in `vfs.__all__` may have a page, should stay, and should gain its mirror: every name in `vfs.__all__` appears on exactly one page. Evidence: Griffe's two tests check the list in both directions. A second reason: checked-in stubs are what FastAPI and Griffe carried to another builder unchanged, and Pydantic's own hook comment records that a hook-registered piece did not travel.
- Let the code order the members; avoid page-level `members:` lists. Reason: with `members_order: source` and `filters: public`, the page follows the class, and a new verb appears without an edit to the docs. Evidence: FastAPI and Pydantic keep explicit lists of 19 and 18 names, and each list is a second place to forget. If the 39 members of the file system class need grouping, order them in the source file.
- Add `signature_crossrefs: true` and `summary` to the site-wide options, and leave the rest as they are. Reason: the current vfs block already matches the common ground (`filters: public`, `members_order: source`, `merge_init_into_class`, `separate_signature`, `show_signature_annotations`, both symbol-type options, `show_source: false`). `signature_crossrefs` is set by all four sites and makes `Result` in a signature a link to its page. `summary` gives the 39-member page a table of verbs at the top, which is what a reader scanning for one verb needs; Griffe sets it.
- Keep `show_source: false`. Reason and evidence: the two sites that show source have pages of 1.2 MB; Textual hides it and its largest page is 0.5 MB with ten times the headings of FastAPI's.
- Override no handler template, and keep the handler CSS to a few rules. Reason: a template override is local code that must track every handler release. Evidence: none of five repositories has one. Textual's eight rules (a rule above each object heading, an indent on nested contents) are the upper bound of what was needed.
- Render both faces in full, each on its own page, and say so in one sentence at the top of each. Reason: a reader arrives from search or a link on the face they use and should find the whole verb there. Evidence: FastAPI renders the shared verbs of `FastAPI` and `APIRouter` in full on both pages. This is the weakest recommendation here, because one precedent is thin; the closing section names the experiment.
- Write the entry page as an index grouped by topic. Reason: at 60 names a reader needs to find the name before the page. Evidence: Griffe's index is a topic-grouped list with one line per name, kept in the package docstring and rendered; FastAPI's and Textual's two-sentence entry pages leave the sidebar to do that work. A hand-written `index.md` with the same shape is enough at 22 names.
- Link the guide to the API and the API to the guide by a fixed convention. Reason: reference that nothing links to is found only by search. Evidence: Pydantic uses one admonition in 34 docstrings to point at the guide and one in 26 guide sections to point back; Textual, Pydantic and Griffe carry 376, 331 and 151 cross-references from prose into the API. FastAPI's tutorials carry none, and its reference pages link out with absolute URLs instead. The vfs `:term:` role already does this for the glossary; the same Griffe extension is the place for a role that links a docstring to a guide page.
- Treat the stub pages and the option block as the durable part, and the hooks as the replaceable part. Reason and evidence: FastAPI moved builder on 2026-05-19 and Griffe has moved, both keeping mkdocstrings, the `:::` pages and the options; Textual stays on a locked handler, 1.3.0 against today's 2.0.11, and its live page lacks what three of its options ask for. Pin and upgrade the handler deliberately, and look at a built page after each upgrade.

The one-line version: write eight to ten short stub pages by hand, grouped by topic, inside Reference; set the look once in the options; override nothing; and check the list of names against `vfs.__all__` in both directions.

## What this study could not settle, and what would settle it

- How Pydantic's public site turns a `:::` line into a page. The repository names `pydantic/unified-docs` and says it uses the options in `mkdocs.yml`, but that repository is not among the clones. Reading its build script would say whether it runs Griffe directly, and why the live `BaseModel` page lists members the stub excludes.
- Whether Zensical runs every piece the vfs site depends on. FastAPI and Griffe show that the mkdocstrings plugin, a Griffe extension named in the options and inventories work under it. Neither uses a MkDocs hook written in Python to add pages or navigation. Researcher 04's study of the `zensical` clone covers that point.
- Whether two full pages for the two faces read better than one page and a pointer. An experiment would settle it: build `VirtualFileSystem` both ways, with `summary` on, and compare the page size, the table of contents and the search results for one verb.
- How large the `AsyncVirtualFileSystem` page becomes with `summary` on. Building the site once with the option and reading the byte count and heading count of that page, as done here for the four live pages, would give the figure.
- Whether Textual's missing badges come from the locked handler version, as inferred. Reading the changelog of `mkdocstrings-python` for the release that introduced `show_symbol_type_heading` and `parameter_headings`, and comparing it with 1.3.0, would confirm it.
