# Mature tokenizers scan the text in place and reuse one term buffer, so a term costs a copy, never an allocation, and ours pays both per term

It reads how five catalogued projects of the same job produce terms (tantivy, Lucene, bm25s, zoekt, pg_textsearch) and, because pg_textsearch delegates the whole job to Postgres core, the Postgres clone as a sixth. Every clone was refreshed to its upstream default branch, its licence read and logged (`refresh.log`, `licenses.log` in this folder). Nothing was copied; every citation is a path and a line in the clone. The box was ninety minutes; nothing heavy was run, so no benchmark in any clone was executed here and this study reports only the figures the clones publish in their files. ## The answer in one paragraph

INFERRED from everything below. The two compiled search engines in the set, tantivy and Lucene, agree on every point the brief asks about: the text is scanned where it lies (tantivy over `char_indices` of the `&str`, Lucene over a bounded streaming `char[]` window), a token is one reused buffer plus two offsets into the source, lowercasing happens in place over that buffer with a whole-token ASCII test first, the length gate is one integer compare on a length already known, and the indexer hashes the term's bytes into an arena that copies the key only the first time it sees it. zoekt goes further and never builds a string at all, since a trigram is a `uint64`, and it scans bytes with an explicit ASCII branch. The allocation-per-term designs in the set are the two that are not engines of their own: bm25s, a Python library that lets `re.findall` produce `str` objects, and Postgres's text-search parser, which decodes the whole input into a 4-byte-per-character array up front and allocates three times per word, with pg_textsearch adding a fourth copy. Our tokenizer sits with the second group on representation (a `Vec<char>` of the whole body, a `String` clone per emitted term, a `Vec<String>` returned) and with the first on rules and class checks (an ASCII fast path per character, generated tables otherwise). The brief's measured split of our 64 µs, about 22 µs of clone and about 17 µs of collection and fold buffer, is exactly the cost the consensus design does not pay.

## 1. Our tokenizer, as the thing being compared

READ `crates/vfs-core/src/lexical.rs`. `tokenize` (lines 166 to 190) collects the whole body into a `Vec<char>` (line 167), walks it by index, finds maximal runs of `is_word` characters, calls `identifier_parts` on the run and `emit` on the run and then, when there is more than one part, on each part (lines 185 to 186). `emit` (lines 126 to 131) folds the `&[char]` slice into a reused `String` scratch through `fold_into`, gates on `scratch.chars().count() >= 2` and `scratch.len() <= 64` (line 128), and pushes `scratch.clone()` (line 129). `fold_into` (lines 111 to 124) clears the scratch and, per character, pushes the ASCII lowercase for ASCII (lines 114 to 115), else applies the Turkic-i pre-fold and a binary search over `CASEFOLD` (line 119; 1,530 entries, `lexical_tables.rs` line 2884), pushing the mapped `&str` or the character. The class checks (lines 74 to 106) test `ch.is_ascii()` and use the std ASCII predicates, else `in_ranges` (line 74), a binary search over range tables of 749 (`WORD`), 651 (`UPPER`), 671 (`LOWER`) and 83 (`DIGIT`) entries. `identifier_parts` (lines 143 to 164) splits the `&[char]` run on `_`, keeps a digit-led piece whole, and otherwise calls `is_upper` on every character and `case_boundary` (lines 133 to 139, up to three more class checks) at each upper. The result is `Vec<String>`, duplicates kept.

READ `crates/vfs-core/src/python.rs` lines 324 to 325: the binding is `fn tokenize(content: &str) -> Vec<String>`, which pyo3 turns into a Python list of `str`.

READ `crates/vfs-core/src/lexical.rs` lines 435 to 467, `LexicalAccumulator::add_doc`: it calls `tokenize`, takes `dl` as the vector's length, `sort_unstable()`s the `Vec<String>`, run-length counts it into a reused `counts: Vec<(String, u32)>` (moving each first-seen `String` in and dropping the duplicates), then for each `(term, tf)` does `self.terms.get_mut(&term)` on a `HashMap<String, TermList>` and either pushes the posting or inserts the `String` as a new key. So every emitted occurrence costs one `String` allocation in `emit`; the ones that turn out to be duplicates within the document are freed by the run-length step, and the ones already in the map are freed after the lookup. Only a term new to the corpus keeps its allocation.

## 2. tantivy: one `Token` owned by the tokenizer, borrowed by the stream, filled by `push_str`

READ `tantivy/tokenizer-api/src/lib.rs` lines 15 to 29. `Token` is `offset_from` and `offset_to` (byte offsets into the source, the doc comment says the text is `&text[offset_from..offset_to]`), `position`, `text: String`, `position_length`. Lines 119 to 148: `TokenStream` is a pull interface, `advance()` then `token()` returning `&Token`, with `process(&mut self, sink: &mut dyn FnMut(&Token))` as the push helper that drives the whole stream into a closure. Nothing in the API returns a collection of tokens.

READ `tantivy/src/tokenizer/simple_tokenizer.rs`. The tokenizer struct owns one `Token` (lines 7 to 9); `token_stream` resets it and hands the stream `&'a mut Token` plus `text.char_indices()` (lines 20 to 27). `advance` (lines 42 to 55) clears `token.text`, pulls `(offset, c)` pairs until `c.is_alphanumeric()`, finds the run end with `search_token_end` (lines 32 to 38, a filter over the same `CharIndices` for the first non-alphanumeric), sets the two byte offsets and `push_str`s the `&str` slice between them into the reused `String`. So the token text is a copy of the source bytes into a buffer that is allocated once and grows to the longest token, then never reallocates; there is no `Vec<char>`, no per-character push, and the class check is Rust's `char::is_alphanumeric` on decoded characters coming out of `char_indices`.

READ `tantivy/src/tokenizer/lower_caser.rs` lines 44 to 66. The filter tests `token.text.is_ascii()` for the whole token and, when true, calls `make_ascii_lowercase()` in place on the token's own `String`; otherwise it writes `c.to_lowercase()` per character into a second reused buffer (`output.clear(); output.reserve(50)`) and `mem::swap`s the two `String`s, so even the non-ASCII path allocates nothing after warm-up. The comment at lines 48 to 49 says the final-sigma rule is deliberately ignored.

READ `tantivy/src/tokenizer/remove_long.rs` lines 17 to 37 and `tantivy/src/tokenizer/tokenizer_manager.rs` lines 64 to 66: the default analyzer's length gate is `token.text.len() < 40`, a byte count of the UTF-8, one integer compare. READ `tantivy/src/tokenizer/mod.rs` line 174 and `tantivy/src/postings/postings_writer.rs` line 145: the indexer's own cap is `MAX_TOKEN_LEN = u16::MAX - 5` bytes, also checked on `token.text.len()`.

READ `tantivy/src/tokenizer/split_compound_words.rs`. The only splitter in tantivy is dictionary-driven: an Aho-Corasick automaton (lines 56 to 70), a token is split only when consecutive dictionary matches cover all of it (lines 131 to 157), and each part becomes an owned `Token` with `text: tail.to_owned()` pushed onto a reused `parts` vector (lines 152 to 155). There is no case-change or underscore splitter; the identifier split we do has no counterpart in tantivy.

READ `tantivy/src/postings/postings_writer.rs` lines 132 to 165 and `tantivy/stacker/src/arena_hashmap.rs` line 81. The indexer consumes the stream through `token_stream.process(&mut |token| ...)`: it truncates a reused `IndexingTerm` byte buffer back to the field prefix, `append_bytes(token.text.as_bytes())`, and calls `subscribe`, which calls `term_index.mutate_or_create(term.serialized_term(), ...)` on an arena hash map keyed by `&[u8]`. INFERRED: the key bytes are copied into the arena only when the term is new; a repeated occurrence costs a hash and a probe and no copy. Across tokenizer, filters and indexer, steady-state allocation per token is zero.

READ `tantivy/benches/analyzer.rs` and `tantivy/Cargo.toml` lines 193 to 195. The shipped benchmark is criterion over `alice.txt`: `default-tokenize-alice` drives the default analyzer with `advance()` in a loop and asserts exactly 30,731 tokens; `dynamic-tokenize-alice` does the same through the boxed filter chain; `sample_size(200)`. It counts tokens and asserts the count, and reports time only when run; the file carries no figure, and none was run here.

## 3. Lucene: a JFlex DFA over a streaming `char[]`, a reused `CharTermAttribute`, bytes interned once

READ `lucene/lucene/core/src/java/org/apache/lucene/analysis/standard/StandardTokenizerImpl.jflex`. The scanner is generated from a grammar declaring `%unicode 12.1`, `%function getNextToken`, `%char` and `%buffer 255` (lines 42 to 49). Character classes are Unicode Word_Break properties, `\p{WB:ALetter}`, `\p{WB:MidLetter}`, `\p{WB:ExtendNumLet}` and so on (lines 87 to 93), and the rules at lines 216 to 252 implement UAX#29 word boundaries, returning `WORD_TYPE` or `NUMERIC_TYPE`. `getText` (lines 144 to 145) copies `zzBuffer[zzStartRead..zzMarkedPos]` into the term attribute with `copyBuffer`.

READ `lucene/lucene/core/src/java/org/apache/lucene/analysis/standard/StandardTokenizerImpl.java` (the generated file, 1,110 lines). Classification is a two-level table: `zzCMap(input)` returns `ZZ_CMAP_BLOCKS[ZZ_CMAP_TOP[input >> 8] | offset]` (lines 740 to 744), a constant-time lookup for any code point; the DFA is `ZZ_TRANS`, `ZZ_ROWMAP` and `ZZ_ACTION` (lines 377 to 439). The scan loop reads code points with `Character.codePointAt(zzBufferL, zzCurrentPosL, zzEndReadL)` over a `char[]` (lines 995 and 1014) that starts at 255 chars (line 51), is refilled from the `Reader` by `zzRefill` (lines 753 to 773) and grows only when a single token outruns it (lines 714 to 717). The whole text is never materialized as code points.

READ `lucene/lucene/core/src/java/org/apache/lucene/analysis/standard/StandardTokenizer.java` lines 152 to 176. `incrementToken` loops on `scanner.getNextToken()`, and the length gate is `scanner.yylength() <= maxTokenLength`, one compare on a length the scanner already holds; a too-long token is skipped and counted as a position hole. `maxTokenLength` has a hard ceiling of 1,048,576 (line 80). INFERRED: `yylength` is in UTF-16 code units, so Lucene's gate is a character count where tantivy's is a byte count, and neither recounts the token to get it.

READ `lucene/lucene/core/src/java/org/apache/lucene/analysis/tokenattributes/CharTermAttributeImpl.java`. The term is a reused `char[] termBuffer` (line 32, oversized by `ArrayUtil.oversize`) and a `BytesRefBuilder builder` (line 39) reused for the UTF-8 form. `copyBuffer` grows the array if needed and `System.arraycopy`s (lines 45 to 47); `getBytesRef` copies the chars into the reused builder as UTF-8 (lines 92 to 93); a `String` is built only by `toString`/`subSequence` (line 112) when someone asks for it.

READ `lucene/lucene/core/src/java/org/apache/lucene/analysis/LowerCaseFilter.java` lines 36 to 43 and `lucene/lucene/core/src/java/org/apache/lucene/analysis/CharacterUtils.java` lines 54 to 70. Lowercasing is in place over the term buffer: a loop over `char`s that lowercases `'A'..'Z'` with `c | 32` and, at the first `c > 127`, switches to the `codePointAt`/`Character.toLowerCase`/`toChars` path for the rest of the token. `simpleCaseFold` (lines 79 to 95) has the same shape with `UnicodeUtil.foldCase`, and `CaseFoldingFilter` (`lucene/lucene/core/src/java/org/apache/lucene/analysis/CaseFoldingFilter.java`, "since 10.6.0") applies it. INFERRED: both are one-to-one mappings, which is what makes in-place folding possible; our full casefold maps one code point to up to three (ß to ss) and cannot be done strictly in place for non-ASCII.

READ `lucene/lucene/analysis/common/src/java/org/apache/lucene/analysis/miscellaneous/WordDelimiterGraphFilter.java` and `WordDelimiterIterator.java` in the same directory. This is the identifier split. The iterator walks `char[] text` (line 43 of the iterator) with a 256-entry `byte[]` class table for Latin-1 built from `Character.isLowerCase`/`isUpperCase`/`isDigit` (lines 84 to 104) and `Character.getType` beyond it (lines 302 to 330); a break is decided by `isBreak(lastType, type)` (lines 227 to 245): same class never breaks, upper followed by any letter never breaks, lower-to-upper breaks when `SPLIT_ON_CASE_CHANGE` is set, letter-digit breaks when `SPLIT_ON_NUMERICS` is set. The filter copies the incoming term once into a reused `savedTermBuffer` (lines 190, 524 to 528), records every part as four `int`s in a reused `bufferedParts` array (lines 158, 392 to 395), sorts the parts by position with an in-place merge sorter (line 337), emits the original first when `PRESERVE_ORIGINAL` is set (lines 269 to 273), and emits each part by `termAttribute.copyBuffer(savedTermBuffer, startPart, endPart - startPart)` (line 417). Only concatenations allocate a fresh `char[]` (line 619). INFERRED: the parts are offsets into one saved copy, the same shape as our `parts: Vec<&[char]>`, and the difference is that Lucene then copies each part into the reused attribute where we fold it into the scratch and clone the scratch.

READ `lucene/lucene/core/src/java/org/apache/lucene/index/IndexingChain.java` line 2075 and `lucene/lucene/core/src/java/org/apache/lucene/index/TermsHashPerField.java` lines 190 to 200. The indexer calls `termsHashPerField.add(termAttribute.getBytesRef(), docID)`, and `add` does `bytesHash.add(termBytes)` on a `BytesRefHash` backed by a byte block pool, taking the `termID >= 0` branch (a new term, bytes interned) or the negative branch (a seen term, no copy). This is the same two-branch arena design as tantivy's `mutate_or_create`.

READ the shipped measurements. `lucene/lucene/benchmark-jmh/src/java/org/apache/lucene/benchmark/jmh/LowerCaseBenchmark.java` (lines 35 to 53, 110 to 149) is a JMH throughput benchmark whose class comment says it "compares the generic Unicode codepoint path against an optimized ASCII fast path", over 1,000 tokens of 3 to 10 chars drawn from five distributions, `english` (98% ASCII) down to `allNonAscii`; the `asciiFastPath` method in the bench is the one now in `CharacterUtils.toLowerCase`. `CaseFoldBenchmark.java` in the same directory does the same for `simpleCaseFold` over nine language distributions. `lucene/lucene/benchmark/src/java/org/apache/lucene/benchmark/byTask/tasks/ReadTokensTask.java` lines 65 to 94 drives an analyzer over a document, calls `getBytesRef()` per token and reports "read N docs; M tokens", a token count, in the byTask framework. None of the three files carries a number; none was run here.

## 4. bm25s: `re.findall` over a lowered copy, a `str` per token, a dict to ids

READ `bm25s/bm25s/tokenization.py`. The module-level `tokenize` (lines 569 to 700) compiles `token_pattern`, default `r"(?u)\b\w\w+\b"` (line 572), to `re.compile(token_pattern).findall` (line 641); per text it does `text = text.lower()` when `lower` is set (line 653), `splitted = split_fn(text)` (line 655), and maps each token to an integer through a `token_to_index` dict (lines 664 to 670), appending the id to the document's list. The `Tokenizer` class has the same default `splitter` (line 153), compiles it the same way (line 159), and its `streaming_tokenize` (lines 274 to 366) lowers the text (lines 314 to 315), materializes `list(self.splitter(text))` (line 317) and looks each word up in `word_to_id` (lines 324 to 360).

INFERRED from those lines. A token is an owned Python `str` from the regex engine; the whole document is copied once by `lower()` before scanning; the two-character floor is the `\w\w+` in the pattern and there is no ceiling; character classes are Python `re`'s Unicode `\w`, which is the same `str.isalnum()`-or-underscore class our `WORD` table was generated from, so bm25s and vfs agree on what a word character is and disagree on the fold (`str.lower()` against our `casefold`); there is no identifier split; and the output is ids, not strings, with one dict probe per occurrence. The representation is what a Python library can do, and it is the design we had before the Rust port.

READ `bm25s/examples/tokenize_multiprocess.py` lines 12 to 14, the one tokenizer throughput figure in the clone: on the BEIR NQ corpus, "Single Process: 110.0863s (24357.87/s)" and "Multiprocess (4x): 61.4338s (43648.09/s)", documents per second through `bm25s.tokenize`. READ `bm25s/README.md` lines 42 to 47: the published comparison is queries per second against `rank-bm25` and Elasticsearch on BEIR, a retrieval figure, not a tokenizer one.

## 5. zoekt: bytes in, a `uint64` trigram out, case folded at query time

READ `zoekt/index/shard_builder.go` lines 163 to 245, `newSearchableString`. The indexer walks the UTF-8 bytes of a file once: `if data[0] < utf8.RuneSelf { c = rune(data[0]) } else { c, sz = utf8.DecodeRune(data) }` (lines 182 to 189, with the comment "For source code, 95-99% of bytes are ASCII"), shifts a three-rune window (line 194), and when all three runes are ASCII indexes a flat array of posting lists by `asciiNgramIndex(a, b, c) = a<<14 | b<<7 | c` (lines 76 to 78, 213 to 227, "no hash/probe"); otherwise it packs the runes into a `uint64` at 21 bits each (`runesToNGram`, `zoekt/index/bits.go` lines 125 to 127, used at line 228) and uses a map. The posting delta is appended as a varint with a single-byte fast path (lines 237 to 244). No string is ever built for a trigram, and no lowercasing happens at index time.

READ `zoekt/index/bits.go` lines 27 to 45 and 60 to 75. Case-insensitive search is served by generating the case variants of a query trigram with `unicode.SimpleFold` (`generateCaseNgrams`) and by `caseFoldingEqualsRunes`, which compares needle and haystack bytes with an ASCII fast path `mb |= 0x20` before any rune decoding. The byte-slice `toLower` at lines 50 to 57 allocates a new slice and decodes every rune; INFERRED from its callers' absence in `shard_builder.go`, it is not on the indexing path.

READ `zoekt/index/postings_bench_test.go` lines 15, 76 to 100 and 102 to 122. `BenchmarkPostings_NewSearchableString` runs the trigram scan over up to 50,000 files of a repository named by `ZOEKT_BENCH_REPO`, with `b.ReportAllocs()` and a custom `input-bytes/op` metric, at 1,000, 5,000 and all files; `BenchmarkPostings_Reuse` measures the same with a pooled builder that keeps its maps and slices. `zoekt/index/case_folding_bench_test.go` lines 44 to 76 benchmarks `caseFoldingEqualsRunes` on an ASCII and a non-ASCII sentence with allocations reported. ## 8. What our tokenizer does differently, and why each difference might cost time

INFERRED throughout, with the prior art cited where it avoids the cost. These are observations for study 02 to measure and for the memo to weigh; nothing here is decided, and every one of them keeps the emitted terms byte-identical.

The whole body is collected into a `Vec<char>` before scanning (`lexical.rs` line 167). That is a full pass over the body writing 4 bytes per character before the first class check, and a 28 KB allocation for the 7,167-byte reference body. tantivy scans `char_indices` over the `&str` and slices by byte offset (`simple_tokenizer.rs` lines 24, 45 to 50); zoekt scans bytes with an ASCII branch (`shard_builder.go` lines 182 to 189); Lucene keeps a 255-char window (`StandardTokenizerImpl.java` line 51). Only Postgres does what we do (`wparser_def.c` lines 294 to 295), and Postgres is the slowest design in the set by allocation count. Study 03 attributed about 17 µs of 64 to this collection together with the fold buffer. The brief's variant (a) is this change.

Every emitted term is `scratch.clone()` (`lexical.rs` line 129), a heap allocation and a copy per occurrence, about 1,092 times per reference body. tantivy fills one `Token.text` that is never reallocated after warm-up and hands a `&Token` to a sink closure (`tokenizer-api/src/lib.rs` lines 144 to 148); Lucene copies into a reused `char[]` and interns bytes once (`CharTermAttributeImpl.java` lines 45 to 47, `TermsHashPerField.java` line 195). Study 03 measured about 22 µs of 64 here, a third of the tokenizer's time. The brief's variant (b), a borrowed `&str` through a closure, is the consensus shape.

`emit` counts characters on every term with `scratch.chars().count()` (`lexical.rs` line 128), a second pass over the folded bytes to test a floor of 2. tantivy tests `text.len()` in bytes (`remove_long.rs` line 36), Lucene tests `yylength()` that the scanner already holds (`StandardTokenizer.java` line 163), Postgres carries `lenchartoken` as it scans (`wparser_def.c` line 235). A folded term of more than 4 bytes has at least two characters, since one `char` is at most 4 bytes of UTF-8, so the count is only needed for byte lengths 2 to 4; the brief's variant (d) is this.

The fold pushes character by character into the scratch even when the run is ASCII, and the ASCII test is per character (`lexical.rs` lines 114 to 115). tantivy tests `is_ascii()` once per token and then lowercases the buffer bytewise (`lower_caser.rs` lines 59 to 61); Lucene lowercases `char`s with `c | 32` and leaves the ASCII loop only at the first non-ASCII `char` (`CharacterUtils.java` lines 57 to 68), and ships a JMH benchmark whose whole purpose is that fast path (`LowerCaseBenchmark.java` lines 35 to 39). Our full casefold, which can map one code point to three, means the non-ASCII path needs an output buffer as it has today; the ASCII path does not. The brief's variant (c) covers this.

Non-ASCII class checks are a binary search over range tables of 651 to 749 entries (`lexical.rs` lines 74 to 106), about ten comparisons per check, and `identifier_parts` plus `case_boundary` can make up to four checks per character (`is_upper` on every character, then `is_lower`/`is_digit` on the previous and `is_lower` on the next). Lucene's generated scanner classifies any code point in two array reads (`StandardTokenizerImpl.java` lines 740 to 744), and its word-delimiter iterator uses a 256-entry byte table for Latin-1 (`WordDelimiterIterator.java` lines 84 to 104). The brief's variant (e), a 128-entry ASCII table, addresses the ASCII side; the non-ASCII side would want a two-level table if study 02 finds non-ASCII bodies pay for the search, and the corpus in study 03 was all ASCII, so that has not been measured.

The fold table lookup is a binary search over 1,530 `CASEFOLD` entries per non-ASCII character (`lexical.rs` line 119), about eleven comparisons. JDK `Character.toLowerCase` and `UnicodeUtil.foldCase`, which Lucene calls per code point (`CharacterUtils.java` lines 62 to 63 and 87 to 88), are table lookups. The same two-level-table remark applies, and the same caveat that it is unmeasured on non-ASCII text.

The result is a `Vec<String>` (`lexical.rs` line 166) that the builder sorts (`add_doc`, line 442), run-length counts and looks up by `String` key, and that the Python binding turns into a list of 1,092 `str` objects per body (`python.rs` lines 324 to 325). tantivy and Lucene never produce a collection: the indexer consumes each token as it is produced and hashes its bytes into an arena that copies the key once per distinct term (`postings_writer.rs` lines 143 to 160, `TermsHashPerField.java` lines 190 to 200). Our sort is an extra O(n log n) of `String` compares per document that the arena designs do not have, and our allocation is per occurrence where theirs is per distinct term. Study 03 line 43 measured the Python-side materialization at about 23 µs per body on top of the 64. The brief's accumulator variant, looking a term up as a borrowed slice and cloning only on first sight, is the arena shape without the arena.

Every part of a split identifier is folded and cloned separately (`lexical.rs` lines 185 to 186), so `snake_case_name` costs four folds and four clones. Lucene's word-delimiter filter saves the term once and emits each part as a `copyBuffer` from the saved copy (`WordDelimiterGraphFilter.java` lines 417, 524 to 528); tantivy's compound splitter does clone a `Token` per part (`split_compound_words.rs` line 153), the one place in the compiled engines that allocates per part, and it is an optional filter that is not in the default analyzer (`tokenizer_manager.rs` lines 64 to 66). INFERRED: since a part's fold is a subsequence of the run's fold except across a Turkic-i or multi-character fold boundary, a part could be sliced from the folded run instead of refolded; whether that preserves output exactly in every case is a correctness question study 02 would have to assert over both corpora before timing it.

## 9. What this study does not settle, as experiments

INFERRED. This study read code and ran no clone's benchmark, so it cannot say how fast any of these designs is on this machine; the figures it can quote are bm25s's 24,357.87 documents a second on NQ, a Python figure on a different corpus, and our own 64 µs per 7,167-byte body from study 03. The experiment that settles the comparison is study 02's: variants (a) through (f) of the brief, byte-identical to `vfs_core::tokenize` on every body of both corpora, timed in the scratch crate with allocations counted.

INFERRED. Running tantivy's `cargo bench --bench analyzer` on `alice.txt` here, and feeding the same text to our tokenizer in the scratch crate, would put a mature Rust tokenizer with the same output shape (lowercased words, a byte-length cap) beside ours on one machine; it was out of this study's box and is a one-command experiment for study 02 or a follow-up, with the caveat that the two tokenizers' rules differ (tantivy has no identifier split and no underscore in its word class) so token counts will not match and only per-byte throughput is comparable.

INFERRED. Whether the non-ASCII paths (binary search over the class tables and over `CASEFOLD`) cost anything measurable is unmeasured, because study 03's corpus was all ASCII; the brief's second corpus, the repository's own `src/`, `crates/` and `context/` prose with non-ASCII characters, is the experiment, and a two-level table like Lucene's `cmap` is the candidate if it does.

INFERRED. Whether a split part's fold can be sliced from the run's fold without changing any emitted term (section 8, last paragraph) is a correctness experiment: assert equality against `vfs_core::tokenize` on both corpora plus a synthetic set of identifiers containing İ, ı, ß, ŉ and the other multi-character folds in `CASEFOLD`, before timing anything.
