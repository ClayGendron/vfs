## 2. Linux: the name is not the file

Three terms first. An *inode* is the record that is the file: its number, owner, mode, size and data. A *directory entry* is a row in a directory that maps one name to one inode number. The *link count* is how many directory entries point at an inode. In POSIX the identity of a file is its inode, and a path is only a way to find it.

**A rename keeps the inode.** ext4's rename writes the source's inode number into the destination entry and removes the source entry (`fs/ext4/namei.c:3937-3944`, `3962-3963`). Nothing about the file itself changes. A rename of a directory changes one entry and the directory's own `..` entry (`fs/ext4/namei.c:3972-3974`); no descendant is touched. INFERRED: the cost of moving a tree is constant because children name their parent by inode number, never by path.

**A rename onto an existing file takes one name away from the file that was there.** The destination entry is rewritten to point at the source inode. The replaced inode's link count is dropped (`fs/ext4/namei.c:3966-3969`). If the count reaches zero the inode goes onto the *orphan list*, a crash-safe list of inodes that have no name left and are waiting to be freed (`fs/ext4/namei.c:4023-4024`; the list is described at `Documentation/filesystems/ext4/orphan.rst:11-21`). The kernel frees the inode when the last open handle on it closes and its link count is zero (`fs/inode.c:1916-1928`, `include/linux/fs.h:2952-2955`). The whole swap is one step under the locks `vfs_rename` takes (`fs/namei.c:5992-6018`). A replaced directory must be empty, or the rename fails with `ENOTEMPTY` (`fs/ext4/namei.c:3897-3901`). A directory cannot replace a file and a file cannot replace a directory (`fs/namei.c:3674-3675`, `3711`, `3715`).

**The replaced file cannot be brought back.** There is no undo in the kernel. An inode whose link count has reached zero cannot be given a name again: `vfs_link` refuses it with `ENOENT` (`fs/namei.c:5764-5766`). The one exception is a file that was created nameless on purpose with `O_TMPFILE`, marked `I_LINKABLE` (`fs/namei.c:4763`). So POSIX gives the developer's ruling its first half, a move keeps identity, and gives nothing for the second half, a replaced file that can be undone. That half has to be designed.

**`renameat2` has three flags** (`include/uapi/linux/fs.h:59-61`). `RENAME_NOREPLACE` refuses when the destination exists (`fs/namei.c:4105-4106`). `RENAME_EXCHANGE` swaps two existing names in one step, so both files survive with both identities (`fs/namei.c:6067-6072`; ext4 writes each inode number into the other entry at `fs/ext4/namei.c:4146-4150`). `RENAME_WHITEOUT` leaves a marker at the source name (`fs/ext4/namei.c:3886-3888`, `3922-3928`). `NOREPLACE` and `WHITEOUT` cannot be combined with `EXCHANGE` (`fs/namei.c:6105-6110`).

**An unlink removes a name, and the path is free at once.** `unlink` drops the link count and, at zero, puts the inode on the orphan list (`fs/ext4/namei.c:3285-3287`). A process that still holds the file open keeps reading and writing it. A new file created at the same name gets a new inode and inherits nothing. ext4 also gives every new inode a fresh random *generation* number (`fs/ext4/ialloc.c:1290`). The generation exists because inode numbers are reused: a remote file handle carries the pair of inode number and generation, so a handle to a deleted file does not silently reach the next file that gets the same number.

**A whiteout is a tombstone that lives at the path.** A *whiteout* is a marker entry that says "the name below me is deleted". overlayfs, which stacks a writable layer on a read-only one, records a delete of a lower-layer file as a whiteout at the same name in the upper layer (`Documentation/filesystems/overlayfs.rst:143-153`). The whiteout hides the lower file and is itself hidden. INFERRED: a new file at that name simply replaces the whiteout; the marker holds no content and nothing is inherited from it.

**Cost.** `rmdir` refuses a directory that is not empty (`fs/ext4/namei.c:3170-3172`). INFERRED: the kernel therefore never deletes a tree in one call. Deleting a tree is a walk in user space, one bounded call per entry, and it can stop and resume anywhere.

## 3. pjdfstest: what a POSIX file system must do

pjdfstest is a test suite that states POSIX behaviour as executable expectations. It pins five things that matter here.

- A rename keeps the inode number, for regular files, fifos, devices and sockets (`tests/rename/00.t:20-26`) and for directories (`tests/rename/00.t:38-43`).
- A rename onto an existing file succeeds, and the destination name then shows the source's inode number (`tests/rename/10.t:31-40`).
- The replaced file is not destroyed by the rename itself. When it has a second name, that name still reaches it, with a link count one lower and a newer change time (`tests/rename/23.t:21-33`).
- The type rules: `ENOTDIR` for a directory onto a file (`tests/rename/13.t`), `EISDIR` for a file onto a directory (`tests/rename/14.t`), `EEXIST` or `ENOTEMPTY` for a directory onto a directory that is not empty (`tests/rename/20.t`).
- A file unlinked while open reports a link count of zero and still accepts reads and writes (`tests/unlink/14.t:19-30`).

Nothing in the suite tests an undo. POSIX has no such operation.

## 4. FreeBSD and Plan 9: two things they add

**FreeBSD has a system call named `undelete`, and it does not undelete a file.** It removes a whiteout: it refuses unless the name is a whiteout with nothing live at it (`sys/kern/vfs_syscalls.c:1963-1988`), then deletes the marker (`sys/kern/vfs_syscalls.c:2001`). The effect is to un-hide a lower-layer file in a stacked mount. It cannot bring back a removed inode. FreeBSD's rename takes the same no-replace and exchange flags as Linux (`sys/kern/vfs_syscalls.c:3839-3842`), and its UFS inodes carry a generation number that is changed on each allocation (`sys/ufs/ufs/inode.h:127`, `sys/ufs/ffs/ffs_alloc.c:1189-1191`).

**Plan 9 writes the identity rule down.** A file's *qid* is the server's unique identity for it. The qid's path field is an integer unique among all files, and the manual says that when a file is deleted and recreated with the same name in the same directory, the old and new path fields should differ (`sys/man/5/0intro:419-435`). So a new file at a deleted file's name is a different file, by rule. Plan 9 has no replacing rename at all: a name is changed with `wstat`, and changing it to the name of an existing file is an error (`sys/man/5/stat:189-193`).

## 5. JuiceFS: deleted files move into a trash directory and keep their inode

JuiceFS is a POSIX file system whose metadata lives in a database, SQL among the choices. It is the closest prior art to the developer's ruling, because it has both POSIX rename and an undoable delete.

**Identity.** A `node` row is keyed by inode number (`pkg/meta/sql.go:76-77`). A name is an `edge` row with a unique key over parent inode and name (`pkg/meta/sql.go:68-74`). The unique key has no deleted flag in it and needs none, as the next paragraphs show.

**Delete moves the name; it does not mark the row.** With the trash on, `unlink` leaves the inode row alone and inserts a new edge for the same inode under a trash directory (`pkg/meta/sql.go:2263-2270`). The trash is a reserved directory `.trash` with a fixed inode number (`pkg/meta/interface.go:122`, `144`). Under it is one directory per UTC hour of deletion (`pkg/meta/base.go:3138`, `3147-3150`). The entry's name there is the old parent's inode number, the file's inode number and the old name, joined by hyphens (`pkg/meta/base.go:3170-3171`). Three consequences follow. The old path is free at once. The deleted file keeps its inode, so its attributes and data are untouched. And two deleted files that once had the same path can never collide in the trash, because each trash name carries its own inode number.

**A replacing rename sends the replaced file to the trash.** This is the case the developer asked about. When a rename lands on an existing file and the trash is on, JuiceFS does not drop the replaced inode. It inserts a trash edge for it under the same naming rule and updates its parent (`pkg/meta/sql.go:2730-2741`). Only with the trash off does it fall back to the POSIX path of dropping the link count and freeing the inode (`pkg/meta/sql.go:2742-2760`). So the moved file keeps its inode, the replaced file keeps its inode, and the replaced file can be restored.

**A new file at the freed path inherits nothing.** INFERRED from the two paragraphs above: the path's edge is gone, so a create makes a new inode. The deleted one sits in the trash under its own number.

**Restore is a rename that refuses to replace.** The `restore` command parses the old parent inode and name out of the trash entry's name and renames the entry back with the no-replace flag (`cmd/restore.go:124-140`). When the path has been taken since, the rename returns `EEXIST`, the command counts a conflict, logs it, and leaves the entry in the trash (`cmd/restore.go:144-146`). Nothing is overwritten and nothing is renamed aside. Ordinary callers cannot rename into the trash; an internal flag marks the restore (`pkg/meta/interface.go:78`, `pkg/meta/sql.go:2533-2535`).

**Names.** The documentation says deleted files are "moved" to the trash (`docs/en/security/trash.md:10`), "recover" and `restore --put-back` for the undo (`docs/en/security/trash.md:29`, `103`), and "permanently delete" for the irreversible act (`docs/en/security/trash.md:106-116`). There is no separate verb for it: permanent deletion is an ordinary delete issued inside `.trash`, or expiry after `--trash-days`. A per-file flag skips the trash (`pkg/meta/interface.go:105`, `docs/en/security/trash.md:122`).

**Rights.** Only root may write, move or delete inside the trash (`pkg/meta/base.go:1874`, `docs/en/security/trash.md:174`). Trashed files keep their mode bits, so a user reads in the trash only what they could read before (`docs/en/security/trash.md:168`). But every user may list the trash and see the names of everything deleted (`docs/en/security/trash.md:168`). INFERRED: that listing is a leak by the standard in the brief, where a caller who could not see a file must not learn of it through a delete.

**Cost.** A delete is one edge insert and one edge delete per entry. `rmdir` refuses a directory that is not empty (`pkg/meta/sql.go:2404`), so a tree is deleted by a walk, and every entry of the tree becomes its own flat trash entry (`docs/en/security/trash.md:39`, `72-81`). The tree's shape is lost in the trash and is rebuilt from the parent inode numbers in the names (`docs/en/security/trash.md:84-100`). Expiry runs hourly in the background, one hour directory at a time (`docs/en/security/trash.md:108`, `pkg/meta/base.go:3264-3270`).

## 6. Object stores: a key holds a stack of versions, and a delete is one more version

**MinIO.** An object's identity is its key plus a version id. Every key has one metadata record holding a list of versions (`cmd/xl-storage-format-v2.go:901-902`). A version is an object or a *delete marker*, a version with an id and a time and no content (`cmd/xl-storage-format-v2.go:110-111`, `149-153`). On a versioned bucket a delete with no version id adds a delete marker with a new id (`cmd/erasure-object.go:2092-2124`). The marker becomes the current version and a plain read returns 404, while every older version stays (`docs/bucket/versioning/README.md:17-21`). A delete that names a version id is the permanent one, and no marker is added for it (`docs/bucket/versioning/README.md:29`). Repeated deletes do not stack markers (`docs/bucket/versioning/README.md:76`). INFERRED: the key is free at once, since a new write is one more version on top of the marker, and the new object shares the key's version history with the deleted one. There is no rename; the object API has copy and delete only.

**SeaweedFS's S3 layer** follows the same model on top of its filer. The delete marker is an entry stored in a `.versions` directory beside the object (`weed/s3api/s3api_object_versioning.go:204-220`), flagged by an extended attribute (`weed/s3api/s3api_object_versioning.go:35-36`).

**OpenDAL** is a library that puts one API over many stores, so its choices are a survey in themselves. Its `delete` is idempotent: deleting a missing path succeeds (`core/core/src/types/operator/operator.rs:1797`). Its `rename` overwrites the destination (`core/core/src/types/operator/operator.rs:1565-1566`), with a separate capability for a rename that refuses (`core/core/src/types/capability.rs:233`). It can list deleted entries (`core/core/src/types/capability.rs:246`) and delete one version (`core/core/src/types/capability.rs:161`). Its newest addition is a first-class `restore` (`core/core/src/types/capability.rs:222-227`), designed in `core/core/src/docs/rfcs/7182_restore_api.md`. Four choices in that document bear on vfs.

- **The name.** The authors considered `undelete` and chose `restore`, because `restore` names the outcome and not the store's mechanism (`7182_restore_api.md:216-220`).
- **Restore of a live path is a success, not an error** (`7182_restore_api.md:39`). A path with nothing to recover is `NotFound` (`7182_restore_api.md:41-42`).
- **A restore that must not overwrite is an option.** Restoring a named version replaces the current value by default. With `if_not_exists` it fails with `ConditionNotMatch` when the path is taken (`7182_restore_api.md:59-79`).
- **One call does one bounded thing.** On S3 a restore removes only the current delete marker. Removing every stacked marker was rejected because one call would make an unbounded number of irreversible changes (`7182_restore_api.md:177-182`, `222-226`).

## 7. SeaweedFS's filer: the path is the identity, so a move rewrites the tree

The filer's entry is keyed by its full path (`weed/filer/entry.go:36-37`). A rename builds a new entry at the new path and deletes the old one (`weed/server/filer_grpc_server_rename.go:423-432`, `534`). A directory rename lists the children in pages of 1,024 and moves each one, recursively (`weed/server/filer_grpc_server_rename.go:303-336`). An existing destination is deleted first (`weed/server/filer_grpc_server_rename.go:395-420`), unless the caller set the flag that refuses (`weed/server/filer_grpc_server_rename.go:66-70`). A recursive delete also pages by 1,024 (`weed/filer/filer_delete_entry.go:214`, `weed/filer/filer.go:40`). The filer has no trash; a search for the word found only admin interface templates. INFERRED: with a path as the key, a move costs one write per descendant and nothing stable names a file across it.

## 8. Jackrabbit Oak: the tombstone stays on the path's own record

Oak's document store is the nearest thing in the clones to what the brief says vfs does today. One document holds one node, and the document's id is the depth and the path (`oak-store-document/src/main/java/org/apache/jackrabbit/oak/plugins/document/Document.java:44-47`). A delete does not remove the document. It writes an entry into the document's `_deleted` map, keyed by revision, with the value true (`NodeDocument.java:163-166`, `CommitBuilder.java:183`, both under the same package path). Creating a node at that path again writes false into the same map on the same document (`DocumentNodeState.java:451`). A second flag, `_deletedOnce`, records that the document was ever deleted, and its comment warns that a true value does not mean deleted, because the node may have been "resurrected" (`NodeDocument.java:169-177`). The garbage collector reads the documents that were possibly deleted and removes one only after checking it was not revived inside the retention window (`VersionGarbageCollector.java:1107-1117`).

What this shows. The tombstone lives at the path's key. The path is free at once, and a new node there reuses the old document. The cost is that "deleted" stops being a simple fact about a record: every reader and the collector must ask whether the record was deleted and then revived. INFERRED: this is the same family of surprise the brief asks study 01 to probe under the name revive.

Oak's own identity and move rules, one layer up. A node's identifier is its `jcr:uuid` property when it has one, and otherwise its parent's identifier plus its name, which is a path (`oak-core/src/main/java/org/apache/jackrabbit/oak/plugins/identifier/IdentifierManager.java:101-110`). A move refuses an existing destination with `ItemExistsException` (`oak-jcr/src/main/java/org/apache/jackrabbit/oak/jcr/delegate/SessionDelegate.java:602-606`, and `oak-core/src/main/java/org/apache/jackrabbit/oak/core/MutableRoot.java:210`). There is no replacing move. INFERRED: because the document id is the path, a move in the document store writes every descendant at its new path and tombstones every one at its old path.

## 9. The file systems built for agents

These eight were read by the two helper agents. I re-read the lines marked with a dagger (†) myself; the others are READ by a helper only. None of the eight has a verb that undoes a delete.

**agentfs** (a file system in SQLite). Identity is an inode: `fs_inode.ino` is an autoincrement primary key (`SPEC.md:165`†), and a name is an `fs_dentry` row unique over parent inode and name (`SPEC.md:234`†). A rename is one update of one dentry row (`sdk/rust/src/filesystem/agentfs.rs:3683-3689`†), so a directory move touches no descendant. A rename onto an existing file deletes that name and drops the link count, and at zero deletes the inode and its data in the same call (`agentfs.rs:3647-3679`). Delete cannot be undone and leaves nothing behind (`agentfs.rs:3371-3418`). The overlay mode has whiteouts in a table keyed by path (`sdk/rust/src/filesystem/overlayfs.rs:97-100`†), written only when a base-layer entry would otherwise show through (`overlayfs.rs:1141-1143`†) and removed when a new entry is created at the path (`overlayfs.rs:992`, `1028`). `rmdir` refuses a directory that is not empty (`agentfs.rs:3471-3473`).

**computer** (Cloudflare's `dofs`, an inode tree in SQLite). Identity is an inode: `vfs_nodes.inode` is an autoincrement primary key and `vfs_dirents` has a primary key over parent inode and name (`packages/dofs/src/schema/core.ts:32`†, `50-55`†). A rename deletes one name row and inserts one for the same inode (`packages/dofs/src/fs/rename.ts:131-137`†). It refuses to move a directory into itself (`rename.ts:98-107`†). A rename onto an existing name unlinks that name and removes the inode when its last link goes (`rename.ts:126`†); a directory that is not empty is refused (`rename.ts:112-118`†). Delete cannot be undone. There is a tombstone table, `vfs_changes`, but it is a log of deleted paths for a sync protocol, keyed by its own autoincrement id and not by path (`packages/dofs/src/schema/sync.ts:16-22`†). One cost is worth noting: a directory rename, though it moves one name row, also runs two statements over the whole subtree, one to restamp a revision on every descendant and one to log every old path as deleted (`rename.ts:219-231`†). INFERRED: a design that keeps identity through a move can still pay per descendant if anything else, here the sync log, is keyed by path.

**libsqlfs** (a POSIX file system in SQLite, 2019). Identity is the path string: `meta_data` has its primary key on the path (`sqlfs.c:3235-3240`†). A rename rewrites the key in two tables (`sqlfs.c:793-794`†), and a directory rename loops over every descendant row (`sqlfs.c:2287-2328`). An existing destination is deleted (`sqlfs.c:2389-2399`†). Delete is a hard delete with no undo (`sqlfs.c:549-550`†). Hard links are refused (`sqlfs.c:2417-2420`†), which is what a path-as-identity design forces. INFERRED by the helper and confirmed by my reading of `sqlfs.c:2382`: the empty-directory test compares with "at least zero", so a directory can never replace an existing directory, empty or not.

**branchfs** (copy-on-write branches over a real directory). Identity is the relative path; inode numbers are an in-memory map and a rename gives the destination a fresh number (`src/fs.rs:1302-1304`†). A delete appends the path to a per-branch tombstone file (`src/branch.rs:287-295`†) and reads check the tombstones first (`src/branch.rs:694`†). The only undo is `abort`, which throws away the whole branch (`src/branch.rs:975-979`†). A rename onto an existing destination deletes the destination's copy, a whole directory included, with no emptiness check (`src/fs.rs:1258-1271`†). The helper found that a plain create never clears a tombstone; only rename does (`src/fs.rs:1285`†). INFERRED by the helper: a new file at a deleted path stays hidden until the branch commits. That is a tombstone-at-the-path design failing in the simplest way it can.

**mirage** (the direct competitor; paths below are under `python/mirage/`). It has three shapes in one product. Its SQL backend is an inode design: `fs_inode.ino` is an autoincrement key and `fs_dentry` is unique over parent inode and name (`core/sql/constants.py:70-76`†). A rename is one update of one dentry (`core/sql/constants.py:165-167`†, `core/sql/rename.py:78-83`†) and follows the POSIX type rules, refusing a directory that is not empty and a move into its own subtree (`core/sql/rename.py:54-64`†). The replaced entry is removed and its inode dropped (`core/sql/rename.py:66-85`). Delete there is a hard delete (`core/sql/unlink.py:32-40`). A recursive delete lists the subtree and deletes in chunks of 500 ids inside one transaction (`core/sql/rm.py:43-78`). Its RAM backend keys by path and re-keys every descendant on a move (`core/ram/rename.py:51-65`, `93-102`). Its GridFS backend is the interesting one. Every operation that takes a name away, a delete and the replaced destination of a rename alike, goes through one function that retags all of the file's revisions to a name under the prefix `/trash/` and then prunes the trash past a retention count (`core/gridfs/constants.py:21`†, `core/gridfs/driver.py:189-207`†, `264-272`†). The revisions keep their ids. A rename retags every revision, so the history moves with the file (`core/gridfs/driver.py:265-266`†). The helper found no restore verb for that trash. INFERRED: mirage reached the same two decisions as JuiceFS, one door for deleted and replaced files and a trash name outside the live namespace, but stopped before the undo. Because the trash name is the old path with a prefix, two files deleted from one path share a trash name and are told apart only as revisions.

**afs** (typed verbs over providers). Identity is the path. `delete` and `rename` are optional provider methods (`packages/core/src/type.ts:565-567`). A rename takes an `overwrite` flag that defaults to false (`packages/core/src/type.ts:272-274`†); without it the file and git providers refuse an existing destination (`providers/fs/src/index.ts:838-844`). A rename across mounts is refused (`packages/core/src/afs.ts:1917-1933`). Delete of a directory needs a `recursive` flag (`providers/fs/src/index.ts:791-795`) and is then one unbounded recursive removal (`providers/fs/src/index.ts:800`†). There is no trash. The git provider can commit each delete, so the content survives in history, but no verb brings it back (`providers/git/src/index.ts:899-918`).

**deepagents**. Identity is the path; a file record has content and two timestamps and no id (`libs/deepagents/deepagents/backends/protocol.py:187-200`). There is no move or rename in the backend protocol at all. `delete` is optional, always recursive, and raises by default (`libs/deepagents/deepagents/backends/protocol.py:722-748`†). A new file at a deleted path inherits nothing. INFERRED by the helper: earlier graph checkpoints still hold deleted content, which is an undo of the whole state and not of one file.

**letta** (read at `56ba9c255`, the parent of the commit that archived the server off `main`). It is the one clone with a deleted flag on the row. Every table has an `is_deleted` column (`letta/orm/base.py:18`†), and `delete_async` sets it (`letta/orm/sqlalchemy_base.py:674-682`†). But files, sources and memory blocks do not use it: they call `hard_delete_async`, whose docstring says it permanently removes the record (`letta/orm/sqlalchemy_base.py:685-686`†, `letta/services/file_manager.py:487`†, `letta/services/block_manager.py:286`). INFERRED: the project built a soft delete and then chose not to rely on it for files. Its name pair is worth noting: the soft one is plain "delete" and the irreversible one is "hard delete". In its git-backed memory a block's identity is its label, so a renamed file becomes a new block with a new id and the old block is detached (`letta/server/rest_api/routers/v1/git_http.py:179-191`).

## 11. What the prior art says about the redesign options

All of this section is INFERRED from the sections above. The three options are the ones the brief gives study 01.

**Every system that keeps identity through a rename separates the name from the file.** Linux, FreeBSD, JuiceFS, agentfs, dofs and mirage's SQL backend all have a file record keyed by a number and a separate name record keyed by parent and name. A rename is one name record. Every system that keys the file by its path, SeaweedFS's filer, Oak's document store, libsqlfs, branchfs, afs, deepagents and mirage's RAM backend, either loses identity on a move or rewrites every descendant, and usually both. The developer's ruling that a move keeps the id puts vfs with the first group. The cost of a tree move is then decided by what else in vfs is keyed by path, as dofs's sync log shows.

**Option: the tombstone moves to a path under the trash.** This is JuiceFS, and it is the only system read here that satisfies the ruling whole: the moved file keeps its id, and the replaced file survives and can be restored. Its lessons are concrete. The trash name must carry the deleted file's own id, or two deleted files from one path collide. The path's unique key needs no deleted flag, so it works the same on every SQL engine. The replaced file of a rename goes through the same door as a deleted file, so there is one mechanism and not two. A restore onto a taken path refuses and leaves the item in the trash. The price is that the tree's shape is gone from the trash, and restoring a tree is one rename per entry. mirage's GridFS backend makes the same move with a weaker name, the old path under a prefix, and so has to tell two deleted files from one path apart by revision.

**Option: the tombstone leaves the path's unique key.** The object stores are the precedent: a key is not unique among versions, only among live ones, because a delete marker is a version. dofs's delete log does the same in SQL by keying tombstones on their own id. The precedent's warning is OpenDAL's: once a path can hold several dead things, a restore must say which, and one call must touch a bounded number of them.

**Option: the unique key gains a generation.** The generation in ext4 and UFS and the rule in Plan 9 exist for one purpose: to make a new file at an old address provably a different file. S3's version id is the same idea applied to a key. So the precedent supports a generation as a way to tell successive files at one path apart. It does not by itself say where the dead ones are listed; the object stores answer that with a version listing.

**Today's shape, a tombstone on the path's own row, has one precedent here and it is a caution.** Oak keeps the deleted mark on the path's document and reuses the document when the path is created again. It needs a second flag, a revive-aware reader and a collector that re-checks every candidate. branchfs keeps tombstones by path and hides new files behind them. No system read here keeps a tombstone at the path and also lets a new, different file live there cleanly.

**On the name of the irreversible verb.** None of the passages read uses "sweep". POSIX has no word for it because its delete is already irreversible. JuiceFS and MinIO both say "permanently delete". letta says "hard delete" and documents it as permanent. OpenDAL pairs `delete` with `restore` and rejected `undelete`. FreeBSD shows the risk of a loose name: its `undelete` does something narrower than the word promises. I did not search the clones for the word "destroy", so this study neither supports nor weakens the developer's choice of it beyond this: the prior art names the irreversible act by saying outright that it is permanent.

**On rights.** JuiceFS lets every user list the names of all deleted files. The brief's standard is stricter. A trash that is a directory needs the same row-level rule as any other directory, applied to the deleted file's own grants, not to the trash's.

## One line

Every system that keeps a file's identity through a rename stores the name apart from the file, and the only one that also makes a replaced file undoable, JuiceFS, does it by moving the deleted or replaced file's name into a trash directory under a name that carries its own id, leaving the path free and the unique key plain.
