# How products with a trash name it and shape it

This is study 03 of three, written on 2026-11-15 to [the brief](00-brief.md). The brief asks what well-known products with a trash or a soft delete do, read in their official documentation: what identity a file has and whether a rename keeps it, what a rename onto an existing file does to the file that was there, whether a delete can be undone and where the deleted thing lives, what a new file at a deleted file's path inherits, what a restore does when the path is taken, what the irreversible operation is called, and how the cost of a large delete is bounded. It asks for particular attention to three things: the names of the undoable and the irreversible operation, the identity of a restored item, and what happens to shares, links and permissions in the trash and after. The vfs tree stood at commit `08c372affd1730739c27aec84b8e94e0d6ef1e87` (`git rev-parse HEAD`); this study reads no vfs code and its findings do not depend on the commit. What was done: 50 page fetches and 7 web searches, all on 2026-11-15, against the official documentation of eleven products and two specifications. Nothing about this project was put in any request.

EXECUTED means a command ran and the claim reports its output. READ means read on a page cited by URL, on the read date 2026-11-15. INFERRED means this study's reasoning, or the researcher's background knowledge where the text says so.

One caution on every READ quote. Pages were fetched through a tool that converts a page to text and answers a question about it. For the Amazon and Microsoft Learn pages the tool returned the page text whole, and the quotes below are taken from that text. For the other pages the tool returned selected sentences as quotations, and they are reproduced as returned. No quote was compared by eye against the rendered page. A quote is evidence of what the page says, not a certified transcription.

## 2. Google Drive

A Drive file is identified by an id, not a path. READ at https://developers.google.com/workspace/drive/api/guides/about-files: the id is "A unique, opaque ID for each file" and "File IDs are stable throughout the life of the file, even if the file name changes." A rename and a move change the `name` and `parents` attributes of the same file.

Trash is a flag on the file. READ at https://developers.google.com/workspace/drive/api/reference/rest/v3/files: `trashed` is "Whether the file has been trashed, either explicitly or from a trashed parent folder." and `explicitlyTrashed` is "Whether the file has been explicitly trashed, as opposed to recursively trashed from a parent folder." READ at https://developers.google.com/workspace/drive/api/guides/delete: a file is trashed by `files.update` with `trashed` set to true and restored by the same call with it set to false. INFERRED: because trashing and restoring are updates to one field of one file, the restored file is the same file with the same id, revisions and permissions. No page read says so in one sentence.

The irreversible verb is the one called delete. READ on the reference page: `files.delete` "Permanently deletes a file owned by the user without moving it to the trash." and `files.emptyTrash` "Permanently deletes all of the user's trashed files." READ on the delete guide: "Files in the trash are automatically deleted after 30 days." The product's own pages call the same act "Delete forever" (READ at https://support.google.com/a/users/answer/9310154). So in the API `delete` cannot be undone and the undoable act has no verb of its own, only a field. This is the naming hazard the brief asks about, in a shipped product.

Sharing survives the trash. READ on the delete guide: "Only the file owner can trash a file", and "other users can still access the file in the owner's trash until it's permanently deleted." READ at https://support.google.com/drive/answer/2375102: "Anyone you shared your file with can continue to access it until the file is permanently deleted." Access ends at the irreversible step: "After you delete a file, anyone you've shared the file with loses access to it." (delete guide).

Each of the three acts has its own right. READ on the reference page: the capabilities `canTrash`, `canUntrash` and `canDelete` are three separate fields. READ at https://support.google.com/a/users/answer/9310154, for shared drives: moving a file to the trash "Requires at least Content manager access", restoring "Requires at least Contributor access", and permanent deletion "Requires Manager access".

INFERRED from background knowledge, not read today: Drive does not require names to be unique within a folder, so a restore can never find its path taken. READ at https://support.google.com/drive/answer/1716222: the recovery page does not say where a restored file goes when its folder is gone.

The two trash fields bound the cost of a tree. INFERRED from the two field descriptions above: trashing a folder marks the folder explicitly, and each descendant is trashed "from a trashed parent folder". The design keeps "this was deleted on its own earlier" apart from "this is deleted because its parent is", so a restore of the folder need not bring back what was trashed separately.

## 3. Dropbox

Dropbox has both a path and an id, and it keeps their histories apart. READ in Dropbox's published API specification at https://raw.githubusercontent.com/dropbox/dropbox-api-spec/main/files.stone: a file's `id` is "A unique identifier for the file." and its `rev` is "A unique identifier for the current revision of a file." Listing revisions has two modes: `path` "Returns revisions with the same file path as identified by the latest file entry at the given file path or id." and `id` "Returns revisions with the same file id as identified by the latest file entry at the given file path or id." INFERRED: a path is a slot that successive files may occupy, and a file is a thing that may occupy successive paths. The API names both histories because they differ.

Delete leaves an entry at the path. READ in the same file: route `delete:2` is "Delete the file or folder at a given path." and `DeletedMetadata` "Indicates that there used to be a file or folder at this path, but it no longer exists." Restore is by revision: `RestoreArg.path` is "The path to save the restored file." and `RestoreArg.rev` is "The revision to restore." READ at https://help.dropbox.com/delete-restore/recover-deleted-files-folders: "Dropbox restores files to the folder they were deleted from." The recovery window is 30, 180 or 365 days by plan.

The irreversible verb carries the word permanent, and it is two steps. READ in the API specification: route `permanently_delete` is "Permanently delete the file or folder at a given path", and "It is possible for this route to successfully delete, then fail to permanently delete." READ at https://help.dropbox.com/delete-restore/deleted-files: "When you permanently delete a file or folder, it's no longer visible in any of your folders and you can't recover it."

A move does not replace. READ in the API specification: the move argument `autorename` is "If there's a conflict, have the Dropbox server try to autorename the file to avoid the conflict." and a write conflict is "There's a file in the way." INFERRED: a move onto an occupied path is refused unless the caller asks for a new name, so the question of what happens to the replaced file is avoided, not answered.

Links and membership come back with the file. READ at https://help.dropbox.com/share/shared-link-stopped-working: "Your shared link won't work if the file or folder was deleted." and "If you restore the deleted file or folder, the shared link will work again." READ on the recovery page: "Restoring the deleted file makes it available in the shared folder again for members who have access." and a member with "Can view" access cannot restore. READ on the deleted-files page: an owner who permanently deletes a shared folder removes it for all members "and their access is permanently removed."

## 4. OneDrive and SharePoint

Delete goes to a recycle bin, and the permanent verb is a separate call. READ at https://learn.microsoft.com/en-us/graph/api/driveitem-delete: "Deleting items using this method moves the items to the recycle bin instead of permanently deleting the item." READ at https://learn.microsoft.com/en-us/graph/api/driveitem-permanentdelete: "If you delete items using this method, they're permanently removed and aren't sent to the recycle bin ... Therefore, permanently deleted drive items can't be restored afterward."

A deleted item is still addressed by its id, and the caller may choose where it comes back. READ at https://learn.microsoft.com/en-us/graph/api/driveitem-restore: the call is `POST /me/drive/items/{item-id}/restore`; `parentReference` is "Optional. Reference to the parent item the deleted item will be restored to." and `name` is "Optional. The new name for the restored item. If this isn't provided, the same name will be used as the original." The page also says "This functionality is currently only available for OneDrive Personal." INFERRED: the item keeps its id while in the bin, because the restore call names it by that id.

SharePoint states its collision rule. READ at https://learn.microsoft.com/training/modules/explore-archiving-records-management/7-restore-deleted-data-sharepoint-online: "When someone restores an item, the system restores it to the same location that contained the item at the time of deletion." and "If a file or folder already exists at the original path, the system restores the item with a number appended at the end of the file name." When the item's folder was deleted too, "The system recreates the folder in its original location" and restores the one item into it; "the system doesn't restore the entire contents of the folder."

A restored item brings its history. READ on the same page: "If you restore a file or other item that has multiple versions, the restored file or item includes all the versions it contained at the time of deletion." and a restored list, library or folder "contains all the documents and other items that it contained at the time of deletion."

There are two stages and a clock. READ on the same page and at https://support.microsoft.com/en-us/office/restore-items-in-the-recycle-bin-that-were-deleted-from-sharepoint-or-teams-6df466b6-55f2-4898-8d6e-c0dff851a0be: items stay 93 days from deletion; deleting an item from the site recycle bin sends it to the site collection recycle bin, the second stage, which needs "administrator or owner permissions"; anyone with edit permissions can restore from the first stage, including "items other people deleted". The second stage is capped at 200% of the site quota and "starts purging the oldest items" when it is exceeded. READ at https://support.microsoft.com/en-us/office/restore-deleted-files-or-folders-in-onedrive-949ada80-0026-4db3-a953-c99083e6a84f: OneDrive keeps deleted items 30 days for personal accounts and 93 for work accounts, and "You can only restore files or folders that were located in your own OneDrive, not files that someone else shared with you."

## 5. The freedesktop.org trash specification

The specification is the plainest statement of trash as a place. READ at https://specifications.freedesktop.org/trash/latest/ (version 1.0, published 2014-01-02): trashing is "a “delete” operation in which files are transferred into the Trash can." Erasing is "an operation in which files (possibly already in the Trash can) are removed (unlinked) from the file system." and "An erased file is generally considered to be non-recoverable; the space used by this file is freed." The address https://specifications.freedesktop.org/trash-spec/latest/ returned 404.

The trashed file leaves its path and gets a new name. READ: "The $trash/files directory contains the files and directories that were trashed." and names there are "to be determined by the implementation", where "the only limitation is that they must be unique within the directory." Many deletions from one path coexist: "Even if a file with the same name and location gets trashed many times", each later trashing "must not overwrite a previous copy."

The old path is a record beside the file, not the file's name. READ: "The $trash/info directory contains an “information file” for every file and directory in $trash/files." Its key `Path` "contains the original location of the file/directory" and `DeletionDate` "contains the date and time when the file/directory was trashed." And "A filename in the $trash/files directory MUST NEVER be used to recover the original filename". The record is written first and atomically: "the implementation MUST create the corresponding file in $trash/info first."

A directory is one move and one record. READ: "when a subdirectory gets trashed, it must be moved to $trash/files with its entire contents" and "The names of the files and directories within the directory MUST NOT be altered". The specification advises that "it is easiest to undelete it or remove it from the trash only in its entirety as well". A cache file, `$trash/directorysizes`, holds each trashed directory's size so a listing of the trash need not walk it.

Rights are meant to be unchanged. READ: "The access rights, access time, modification time and extended attributes (if any)" of a trashed file "SHOULD be the same as the file/directory had before getting trashed." The specification does not say what a restore does when the original path is taken.

## 6. The macOS Trash and the Windows Recycle Bin

macOS. READ at https://support.apple.com/guide/mac-help/delete-files-and-folders-on-mac-mchlp1093/mac: "the items aren't deleted until you empty the Trash." and "WARNING: Any items emptied from the Trash are permanently deleted and are no longer available." The undo is "choose File > Put Back". A second irreversible act is named for what it skips: "Delete Immediately". An option removes items after 30 days. READ at https://developer.apple.com/tutorials/data/documentation/foundation/filemanager/trashitem%28at:resultingitemurl:%29.json: the system call "Moves an item to the trash." and returns the item's new location because "The actual name of the item may be changed when moving it to the trash, so use this URL to access it." The HTML page for the same call returned only its title.

Windows. READ at https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shfileopstructa: the flag `FOF_ALLOWUNDO` is "Preserve undo information, if possible." and `FOF_WANTNUKEWARNING` is "Send a warning if a file is being permanently destroyed during a delete operation rather than recycled." READ at https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags: `FOFX_RECYCLEONDELETE` is "When a file is deleted, send it to the Recycle Bin rather than permanently deleting it." The vocabulary is a pair: a file is either recycled or destroyed.

One Windows detail is a warning about silent fallbacks. READ on the first page: "If pFrom is set to a file name without a full path, deleting the file with FO_DELETE does not move it to the Recycle Bin, even if the FOF_ALLOWUNDO flag is set." An undoable delete that quietly becomes a permanent one is the failure the warning flag exists for.

## 7. Amazon S3 versioning and delete markers

In a versioned bucket a delete adds a version. READ at https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeleteMarker.html: "A *delete marker* in Amazon S3 is a placeholder (or marker) for a versioned object that was specified in a simple `DELETE` request." "The object specified in the `DELETE` request is not actually deleted. Instead, the delete marker becomes the current version of the object." A marker "has a *key name* (or *key*) and version ID like any other object", but "doesn't have data associated with it" and "isn't associated with an access control list (ACL) value."

Readers see a missing object. READ on the same page: a GET without a version id returns "A 404 (Not Found) error" and the header `x-amz-delete-marker: true`, and a plain listing "doesn't return objects whose current version is a delete marker." The older versions can still be fetched by version id (READ at https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html).

Identity is the key plus a version id. READ on the versioning page: "Only Amazon S3 generates version IDs, and they cannot be edited." A write to an existing key "adds this newer version of the object to the bucket" and "The original object ... remains in the bucket." INFERRED: the key is free the moment the marker lands, and a new object written there sits on top of the marker and the old versions, which stay ("Even if overwritten, delete markers remain in your object versions", READ on the marker page). The path is the identity, so the new object deliberately joins the old one's version stack.

Undo and the irreversible act are the same verb with a different argument. READ at https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html: "To undelete the object, you must delete this delete marker." and "To delete a delete marker permanently, you must include its version ID in a `DeleteObject versionId` request." READ at https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html: "To delete versioned objects permanently, you must use `DELETE Object versionId`." The console makes the caller type the words: "In **Permanently delete objects?**, enter **permanently delete**." and warns "When you permanently delete an object version, the action cannot be undone." A plain delete of a key whose current version is already a marker "does not delete the delete marker, but instead `PUTs` another delete marker."

The permanent act is held to a higher right. READ on the versioning page: "Only the owner of an Amazon S3 bucket or an authorized IAM user can permanently delete a version." and a bucket can require multi-factor authentication "to delete a version".

The stack has a cost. READ on the versioning page: a rise in 503 responses can mean "one or more objects in the bucket for which there are millions of versions." READ on the marker pages: lifecycle rules remove an "expired object delete marker", one whose every other version is gone. INFERRED from background knowledge, not read today: general purpose S3 buckets have no rename, so a move is a copy and a delete and makes a new object.

## 8. Azure Blob soft delete

All of this section is READ at https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-blob-overview unless another page is named. Soft delete keeps "the deleted data in the system for a specified period of time", between 1 and 365 days, and "you can restore a soft-deleted object to its state at the time it was deleted" with the Undelete Blob operation.

The deleted thing is hidden and unreadable. "Soft-deleted objects are invisible unless you explicitly display or list them." "You can't read data in a soft-deleted blob or snapshot until the object is restored." A listing asks for them with `include=deleted`.

This is the one product read that documents a replacing rename. In accounts with a hierarchical namespace, for a rename: "The existing destination blob or empty directory is soft-deleted and the source replaces it. The soft-deleted object is deleted after the retention period." So a replaced file is undoable there, by the same means as a deleted one.

A restore never displaces a live file. "You also can't restore a directory or a blob to a filepath that already has a directory or blob of that name. For example, if you delete `a.txt` (1) and upload a new file also named `a.txt` (2), you can't restore the soft-deleted `a.txt` (1) until the active `a.txt` (2) is either deleted or renamed." INFERRED: the path was free at once, the new file inherited nothing, and the deleted file kept its own identity beside it. READ at https://learn.microsoft.com/en-us/azure/storage/blobs/soft-delete-blob-manage: the restore command takes `--deleted-path-name` and `--deletion-id`. INFERRED: the deletion id is what tells apart several deleted items that had one path.

Soft-deleted children are tied to their directory's name. "If you rename a directory that contains soft-deleted blobs, those soft-deleted blobs become disconnected from the directory. To restore those blobs, you need to revert the directory name to its original name or create a separate directory that uses the original directory name." This is a documented defect of recording the deleted item by its old path alone.

A deleted directory is one unit. "If you delete a directory ... the directory and all its contents are marked as soft-deleted. You can only access the soft-deleted directory. To access the contents of the soft-deleted directory, you need to undelete the soft-deleted directory."

Rights come back with the item, and seeing the trash is its own right. "In accounts that have a hierarchical namespace, the access control list of a blob is restored along with the blob." READ on the manage page: "Soft-deleted blobs and directories won't appear if your security principal relies only on access control list (ACL) entries for authorization."; a role on the whole account is needed.

There is no early irreversible verb for a soft-deleted blob. READ on the manage page: "You cannot permanently delete a blob that has been soft deleted before the retention period expires." The overview's advice for a retention period set too long is to "undelete the soft deleted blobs, turn off the blob soft delete feature, and redelete the blobs." The overview also warns of "increased latency when listing blobs" where soft-deleted data accumulates.

In a flat namespace the name is the identity and a write to a soft-deleted name stacks. A write "called on a soft-deleted blob ... generates a snapshot of the blob's prior state only if it's being replaced by a blob of the same type. If the blob is of a different type, the operation permanently deletes all existing soft-deleted data."

## 9. Google Cloud Storage soft delete

READ at https://docs.cloud.google.com/storage/docs/soft-delete (https://cloud.google.com/storage/docs/soft-delete redirects there): soft delete "preserves objects and buckets that get deleted or overwritten by retaining them in a soft-deleted state". "The default retention duration is 7 days and you can customize the retention duration between 7 days and 90 days." "During this time, the object or bucket can't be permanently deleted and can be restored." "Soft-deleted resources are hidden from list operations by default."

A restore makes a copy, not the same object. READ on the same page: "Cloud Storage creates a new, live copy of that object within the same bucket." READ at https://docs.cloud.google.com/storage/docs/json_api/v1/objects/restore: "A new generation is assigned and the metageneration is reset to 1." The caller names the deleted object by its generation number, and in hierarchical buckets by a `restoreToken`, "a universally unique identifier (UUID) associated with each soft-deleted object", needed when name and generation do not identify it alone.

A restore onto a taken name overwrites, and the overwritten object is itself recoverable. READ on the soft-delete page: "the restored object will overwrite the existing live version." and "The overwritten object that was formerly live is then automatically soft-deleted." The caller can refuse that: READ on the restore reference, "Setting `ifGenerationMatch` to 0 makes the operation succeed only if there is no such live object." Bulk restore runs asynchronously and carries an `allow_overwrite` flag (READ at https://docs.cloud.google.com/storage/docs/use-soft-deleted-objects).

Rights on the restored copy are a choice the caller makes. READ on the restore reference: `copySourceAcl` is "If `true`, copies the soft-deleted object's ACL and applies it to the restored object."; the page's account of the default is that the copy takes the bucket's default object ACL. READ on the soft-delete page: "Soft delete cannot restore the IAM policies on managed folders."

Restore is its own permission, and it needs the delete permission when it would replace. READ on the restore reference and the use page: the caller needs `storage.objects.restore` and `storage.objects.create`, and `storage.objects.delete` "is only required for restoring objects in a way that causes existing objects to be overwritten."

## 10. HashiCorp Vault KV version 2

Vault has three verbs with three plain names. READ at https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2: delete "issues a soft delete of the secret's latest version at the specified location."; undelete "Undeletes the data for the provided version and path in the key-value store."; destroy "Permanently removes the specified version data for the provided key and version numbers from the key-value store." A fourth call, a DELETE on the metadata path, "permanently deletes the key metadata and all version data for the specified key."

Delete is a mark on a version. READ at https://developer.hashicorp.com/vault/docs/v1.15.x/secrets/kv/kv-v2: "Soft deletes do not remove the underlying version data from storage, which allows the version to be undeleted." READ at https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2/cookbook/delete-data: "You can revert soft deletes as long as the destroyed field is false in the metadata." READ at https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2: "When an entry is permanently deleted, Vault purges the underlying version data and marks the key metadata as destroyed." INFERRED: destroy leaves its own small record, a version number marked destroyed, so a destroyed version's number is not handed out again and a reader can tell destroyed from never written.

Identity is the path plus a version number, and a write after a delete continues the same history. READ on the 1.15 page: "In order to write to a soft deleted key, the cas parameter must match the key's current version." INFERRED: the path is free at once, and what is written there is the next version of the same secret, with the same metadata and the deleted versions beneath it. The inheritance is total and deliberate, because the path is the identity.

Each verb is a separate grant. READ on the 1.15 page, under its access rules: deleting the latest version is the `delete` capability on the `data/` path; deleting any version is `update` on the `delete/` path; "To allow a policy to undelete data" is `update` on `undelete/`; "To allow a policy to destroy versions" is `update` on `destroy/`; and "To allow a policy to permanently remove all versions and metadata for a key" is `delete` on `metadata/`. A caller can be given delete without undelete, and either without destroy. Retention is bounded by two settings, `max_versions` ("The number of versions to keep per key.") and `delete_version_after` (READ on the API page).

## 11. IMAP

IMAP is deletion by a flag on a message that stays in place. READ at https://www.rfc-editor.org/rfc/rfc9051.html, section 2.3.2: `\Deleted` means "Message is "deleted" for removal by later EXPUNGE". Section 6.4.3: "The EXPUNGE command permanently removes all messages that have the \Deleted flag set from the currently selected mailbox." Section 6.4.1: CLOSE does the same without reporting each removal. Section 6.4.9: UID EXPUNGE limits the removal to named messages. INFERRED from background knowledge: the flag is cleared the way any flag is, so the undo has no verb of its own, and a flagged message is still listed and still readable until the expunge.

A message's identity is never reused. READ in section 2.3.1.1: "The unique identifier of a message MUST NOT change during the session and SHOULD NOT change between sessions." and "When a message is expunged, its UID MUST NOT be reused under the same UIDVALIDITY value."

A move does not keep identity, and the protocol says so and hands back a map. READ in section 6.4.8: on a MOVE "a new message is created in the target mailbox with a new UID, the original message is removed from the source mailbox." The server must send a COPYUID response, which pairs each old UID with its new one. INFERRED: IMAP is the read example of a move that changes the id, and it treats the mapping from old to new as a required part of the answer.

## 12. Git, as the contrast

Git has no file identity at all. READ at https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository: "Unlike many other VCSs, Git doesn’t explicitly track file movement. If you rename a file in Git, no metadata is stored in Git that tells it you renamed the file." `git mv` "is equivalent to" a move, a `git rm` and a `git add`. A rename is guessed afterwards from content: READ at https://git-scm.com/docs/git-diff, `-M` makes Git "consider a delete/add pair to be a rename" above a similarity threshold, and "The default similarity index is 50%."

A replacing move is refused unless forced. READ at https://git-scm.com/docs/git-mv: `--force` is "Force renaming or moving of a file even if the <destination> exists."

Delete is undoable because history is never rewritten, and the irreversible act is a timed collection. READ on the Pro Git page: `git rm` of a changed file needs `-f`, "a safety feature to prevent accidental removal of data that hasn’t yet been recorded in a snapshot and that can’t be recovered from Git." READ at https://git-scm.com/docs/git-gc: gc will "Prune loose objects older than date (default is 2 weeks ago", reflog entries expire after "90 days", or "30 days" when unreachable, and gc keeps "objects referenced by ... reflogs". INFERRED: Git undoes a delete with no trash by keeping every past state, and pays for it by having no way to say "this is the same file" across a rename. It is the far end from the property the developer ruled for.

## 13. The three things the brief asked to watch

This section is INFERRED from the READ claims above.

The names. No product read calls its irreversible operation sweep, and none uses a housekeeping word for it. The irreversible name is one of three kinds: the word permanent attached to delete (Dropbox `permanently_delete`, Microsoft Graph `permanentDelete`, S3's typed "permanently delete", Drive's "Delete forever"); a word of its own for destruction (Vault's destroy, freedesktop's erasing, IMAP's EXPUNGE, Windows's "destroyed" against "recycled"); or the emptying of a container (Empty Trash, `emptyTrash`). Vault is the closest match to the developer's proposal: delete, undelete, destroy, each a separate grant. The one counter-example is the Drive API, where the undoable act is a field and `delete` is the permanent call. Two stores go further and have no early irreversible verb at all: Azure and Google Cloud Storage refuse to destroy a soft-deleted object before its retention period ends.

The identity of a restored item. The products fall into four shapes. In the first, the file has an id and the path is an attribute; trash is a flag or a bin addressed by that id, and a restore returns the same item (Drive, OneDrive and SharePoint). In the second, the path is the identity and deleted states are versions stacked under it; the path is free at once and a new write joins the stack (S3, Vault, Azure in a flat namespace). In the third, the deleted item leaves the namespace for a trash, under a new handle, with its old path kept as a record beside it; the path is free at once, several deleted items from one path coexist, and a new file there inherits nothing (freedesktop, macOS, Windows, Azure with a hierarchical namespace, the SharePoint bins). In the fourth, the deleted item stays in place and visible with a flag (IMAP), which works only because a mailbox has no unique names. Only Google Cloud Storage restores a copy with a new identity, and it says so. No product read combines a stable file id, a unique path, and a deleted item that goes on holding the path. Where a product has both an id and a unique path, the deleted item gives the path up.

Shares, links and permissions. No product read widens access through its trash. They differ on whether the trash narrows it. Drive leaves a trashed file readable by everyone it was shared with until it is permanently deleted. Dropbox stops a shared link at delete and revives it at restore. Azure, S3 and Google Cloud Storage make deleted data unreadable or hidden until restored. Where the same item comes back, its rights come back with it (Drive, Dropbox links and membership, Azure access lists, SharePoint versions). Where a copy comes back, the old rights are an explicit choice (`copySourceAcl`), and one kind of right is documented as lost (managed folder policies). The acts themselves are separately granted nearly everywhere: three capabilities in Drive, three access levels in shared drives, separate policy paths in Vault, a separate restore permission in Google Cloud Storage, the bucket owner for a version delete in S3, a site collection administrator for SharePoint's second stage.

## 14. What the prior art says about the three redesign options

This section is INFERRED. The brief names three places a deleted or replaced row could live. Each has a read precedent, and each precedent shows a cost.

Tombstones leave the path's unique key. This is Azure with a hierarchical namespace, and Drive and OneDrive by another route. The precedents show three things it needs. It needs a second handle for the deleted item, because its path no longer identifies it: a deletion id, a restore token, an item id. It needs a rule for a restore onto a taken path. And it should not record a deleted item's place by its parent's path alone, or a rename of the parent orphans it, as Azure documents.

Tombstones move under a trash path. This is the freedesktop specification, macOS and Windows. The precedents show what the move must carry: a name unique within the trash, the original path and the deletion time as a side record written first, and one record for a whole directory with the names inside it untouched. It makes a directory delete one move, not one write per descendant.

The unique key gains a generation. This is S3's version id, Google Cloud Storage's generation and Vault's version number. It fits stores where the path is the identity. The precedents show its two costs. A new file at the path joins the deleted one's stack, so "what does it inherit" is answered "the whole history" unless more is done. And the stack under one key grows without a bound unless something expires it, which S3 documents as a cause of failed requests.

A replacing move that leaves the replaced file undoable has one read precedent, Azure's rename, and it is built on the first option: the replaced item is soft-deleted beside the path and the mover takes the path. Google Cloud Storage does the same for an overwrite. Neither needed the replaced item to keep holding the path.

The restore collision has five read answers, and a design picks one on purpose: refuse until the occupant is gone (Azure); append a number to the restored name (SharePoint); overwrite, and soft-delete the occupant in turn, with a precondition that can refuse (Google Cloud Storage); let the caller name a new parent and name (Microsoft Graph); or have no collision because states stack (S3, Vault).

Every hosted product puts a clock on its trash: 30 days in Drive, 30 to 365 in Dropbox, 30 or 93 in OneDrive, 93 in SharePoint, 1 to 365 in Azure, 7 to 90 in Google Cloud Storage, a version count and an age in Vault. The irreversible step is mostly a timer and rarely a verb a person runs. A trash with no clock is the unusual design, and the two listing-cost warnings read (Azure's listing latency, S3's millions of versions) are what an unbounded trash costs.

The Graph restore page does not say what happens on a name conflict, and its sample response is too short to show whether the id is unchanged.

No dedicated Microsoft page on the Windows Recycle Bin's restore behaviour was found; the Windows section rests on two API reference pages. ## One line

Products that give a file both a stable id and a unique path never let a deleted file keep the path: the deleted item steps aside under a second handle, the path is free at once, a replaced file is soft-deleted the same way, a restore onto a taken path follows a chosen rule, and the irreversible act is named permanent or destroy and granted separately.
