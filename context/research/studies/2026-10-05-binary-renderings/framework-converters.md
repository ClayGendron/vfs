# Study: how haystack, llama_index and langchain turn binary files into text

Status: study. Date: 2026-10-05. Owner: Clay Gendron.

Sources (refreshed 2026-10-05, licences read after the refresh):

| clone | ref | commit | licence | note |
|---|---|---|---|---|
| haystack | origin/main | ff13437 | Apache-2.0 | shallow clone; converter removal history is not reachable |
| llama_index | origin/main | 81f0e06 | MIT | |
| langchain | origin/master | 7ca02f333a | MIT | monorepo; holds only the seam, not the loaders |
| langchain-community | main (new, shallow, scratch) | f425a3e | MIT | cloned into the job scratchpad because the monorepo's loaders are shims pointing here |

Method: read the converter, reader and parser modules of each framework
end to end, plus the splitter that carries page provenance into chunks,
plus each package's `pyproject.toml`. Every claim below is cited as
`repo:path:line` and labelled **observed** (read in the code) or
**inferred** (my conclusion from the code). No code was copied.

The vfs question this feeds: a binary file is an entry whose body is
bytes; a derived text rendering is stored as the entry's text content so
the existing line-range chunker, grep, glean and link extraction run
unchanged. The sub-questions: which libraries per format, what metadata,
one-or-many documents per file, chunk-to-page provenance, extras
packaging, failures and limits, and bulk/parallel loading.

---

## 1. Where the converters live (observed)

- **haystack** keeps its converters in core:
  `haystack/components/converters/` holds pypdf, pdfminer, docx, xlsx,
  pptx, csv, html, json, markdown, msg, txt, a `MultiFileConverter`
  router and an `image/` subpackage; the vision-LLM step is in
  `haystack/components/extractors/image/`. Tika and Azure are **not in
  core**: the 2026-09-30 docs sync (commit 0499239) documents
  `TikaDocumentConverter` under
  `haystack_integrations.components.converters.tika` with an
  `XHTMLParser` "to extract pages from Tika XHTML content", and the
  Azure Document Intelligence / Form Recognizer, Docling, Docling Serve,
  MarkItDown, Unstructured and OpenDataLoader PDF converters likewise
  under `integrations-api/`. The in-core `MultiFileConverter` describes
  its PDF leg as "PDF (no OCR)"
  (`haystack:haystack/components/converters/multi_file_converter.py:49`).
- **llama_index** splits core from readers. `SimpleDirectoryReader`
  lives in core
  (`llama_index:llama-index-core/llama_index/core/readers/file/base.py`)
  and imports the per-format readers from the separate
  `llama-index-readers-file` package; if that package is missing it
  warns and serves an empty extension map
  (`base.py:68-90`). Docling is a further package
  (`llama-index-readers-docling`) with its own node parser.
- **langchain**: the monorepo holds only the seam. `langchain_core`
  defines `Blob`, `BlobLoader`, `BaseLoader` and `BaseBlobParser`;
  `langchain_classic.document_loaders.pdf` and friends are deprecation
  shims generated by `create_importer` whose `DEPRECATED_LOOKUP` points
  every loader and parser at `langchain_community`
  (`langchain:libs/langchain/langchain_classic/document_loaders/pdf.py:1-40`,
  `langchain:libs/langchain/langchain_classic/document_loaders/parsers/pdf.py:1-30`).
  `langchain_v1` has no document loaders at all (its package holds
  agents, chat_models, embeddings, mcp, messages, tools). The loaders
  therefore come from the `langchain-community` repo, studied from a
  scratch clone.

## 3. The image-to-text seams, read closely (observed)

**haystack** separates "which page" from "what does it say". Converters
produce text documents; `ImageFileToDocument` produces empty documents;
`DocumentToImageContent` turns documents back into page images: it
requires `file_path` in metadata and, for PDFs, `page_number`
(`image/image_utils.py:229-298`), groups requests by file so each PDF is
opened once (`:307-347`), rasterizes with pypdfium2 and caps the pixel
count at 90% of `PIL.Image.MAX_IMAGE_PIXELS` (`:189-191`). Then
`LLMDocumentContentExtractor` sends each image with a fixed prompt to a
chat generator: markdown output, reading order kept, visual elements
replaced by `[img-caption]…[/img-caption]`, tables as markdown with a
`[table-caption]`, forms as markdown checkboxes, returned as a JSON
object with `document_content`
(`extractors/image/llm_document_content_extractor.py:32-61`). One LLM
call per document; `ThreadPoolExecutor(max_workers=3)` in sync,
`asyncio.Semaphore(max_workers)` in async (`:146,395,440`). Failures do
not raise by default: the document comes back in `failed_documents`
with `extraction_error` in its metadata (`:145,278-280,403-410`).

**langchain-community** nests the seam inside the PDF parser. Any
`BaseImageBlobParser` can be the `images_parser`; the PDF parser wraps
every extracted image as a `Blob.from_data(png, mime_type="image/png")`
and takes `next(images_parser.lazy_parse(blob)).page_content`
(`parsers/pdf.py:464-465`). The text goes back into the page via
`_merge_text_and_extras`, which looks for the last `\n\n\n` or `\n\n`
in the page text and splices the extras before it, falling back to
appending (`:189-239`); `images_inner_format` can wrap it as
`![text](source)` or `<img alt="text" src="source"/>` (`:105-124`).
Unknown PDF image filters are skipped with a warning (`:456`); zero-byte
images are skipped (`:461-462`).

**llama_index** captions with a local vision model inside the PPTX
reader only (`vit-gpt2`), and keeps image handling in the image readers
otherwise. Nothing OCRs images inside a PDF in the default `PDFReader`.

## 4. Provenance from chunk back to page (observed)

- **haystack**: the only place page numbers exist is the splitter. The
  converter output is one text with `\f` between pages (PDF, PPTX
  slides, DOCX rendered page breaks). `DocumentSplitter` maps
  `split_by="page"` to `"\f"` (`document_splitter.py:24`) and, for
  every split mode, writes `page_number` = the page the chunk's first
  non-page-break character lies on, computed by counting `\f` in the
  source before the chunk start (`:203-204,436-441,455`). The shared
  convention is spelled out in `_page_numbers.py:5-11`: a chunk that
  spans a page break belongs to the page it starts on; page breaks a
  chunk opens with belong to that chunk's own page; an all-`\f` chunk is
  an empty page. Each split also carries `source_id` (the parent
  document id), `split_id`, `split_idx_start` (character offset) and an
  optional `_split_overlap` list (`:333,455-472`).
- **llama_index**: provenance is per Document, set by the reader
  (`page_label`, `file_name`, `total_pages`). Nodes inherit it: the node
  parser merges `parent_doc.metadata` into each node's metadata when
  `include_metadata` is on
  (`llama-index-core/llama_index/core/node_parser/interface.py:121-123`)
  and `build_nodes_from_splits` sets the `SOURCE` relationship to the
  ref document (`node_utils.py:29-42`). `SimpleDirectoryReader` adds
  `file_path`, `file_name`, `file_type` (mimetypes guess), `file_size`,
  `creation_date`, `last_modified_date`, `last_accessed_date`
  (`readers/file/base.py:148-183`), and with `filename_as_id` gives
  per-page ids `"{path}_part_{i}"` (`:629-631`).
- **langchain-community**: per Document, set by the parser: `page`
  (0-based), `page_label` (PDF label), `source`, `total_pages`, PDF info
  keys normalized to lower case with `/` stripped and dates parsed to
  ISO (`parsers/pdf.py:143-181`). Single mode keeps `\n\f` between
  pages and no page keys (`:414-417`). Text splitters downstream copy
  metadata; there is no page recomputation in single mode.

## 5. Failures and limits (observed)

| framework | default on a bad file | opt-in raising | failure as data | limits found |
|---|---|---|---|---|
| haystack | every converter wraps read and parse in `try/except Exception`, logs a warning and **skips the source** (`pypdf.py:259-271`, `docx.py:206-221`, `xlsx.py:120-134`, `pptx.py:139-150`); empty text still yields a document, with a warning (`pypdf.py:273-277`); `PDFMinerToDocument` warns on the share of undecoded `(cid:n)` glyphs (`pdfminer.py:233-257,312-320`) | `FileTypeRouter(raise_on_failure=False)` (`routers/file_type_router.py:64,79-81`); `LLMDocumentContentExtractor(raise_on_failure=False)` | router returns `unclassified` (no MIME match) and `failed` (unreadable) buckets (`file_type_router.py:166-167,183,218`); extractor returns `failed_documents` with `extraction_error` | rasterization capped at 90% of PIL's pixel ceiling; none on text size |
| llama_index | `SimpleDirectoryReader.load_file` re-raises `ImportError` always, prints and skips other exceptions unless `raise_on_error=True` (`readers/file/base.py:609-626`); `PDFReader.load_data` is wrapped in `tenacity.retry(stop_after_attempt(3))`, so a deterministic parse failure is retried three times (`docs/base.py:25,37-39`) | `raise_on_error` on the directory reader and on `PptxReader` (`slides/base.py:108-116`) | `PptxReader` returns per-slide error dicts with `partial_extraction=True` and keeps `extraction_errors`/`extraction_warnings` in slide metadata (`slides/base.py:218-227,326-334,126-127`) | `num_files_limit` (`readers/file/base.py:235,370`); HWP decompressed section capped at 100 MB (`docs/base.py:141,250-259`) — the only hard byte cap seen; a warning above 1,000 slides (`slides/base.py:376-377`); `num_workers` clamped to CPU count |
| langchain-community | parsers **raise** (`ImportError` with a pip hint; `ValueError` for an unsupported MIME in `MimeTypeBasedParser` and `MsWordParser`; `ValueError` from `_validate_metadata` if a parser omits the standard keys) | `PyPDFDirectoryLoader(silent_errors=False)` warns instead of raising when true (`pdf.py:479,555-558`) | none at the parser level | none; the memory story is `lazy_parse` generators and `pages_delimiter` single mode |

Inferred: haystack is the only one of the three whose failure channel is
already the vfs `Result` shape — the failure is returned, classified
(`unclassified` vs `failed`), and carries the reason as data.

## 6. Bulk and parallel loading (observed)

- **haystack**: converters iterate `sources` sequentially; `meta` is
  either one dict deep-copied per source or a list whose length must
  equal `len(sources)` (`converters/utils.py:59-82`). Parallelism exists
  only in the LLM extractor (`max_workers=3`, thread pool or semaphore)
  and the once-per-file PDF rasterization batch.
- **llama_index**: `SimpleDirectoryReader.load_data(num_workers=N)`
  uses a `multiprocessing` **spawn** pool with `pool.imap`, clamped to
  `cpu_count()` with a warning (`readers/file/base.py:750-770`);
  `PptxReader` threads over slide batches (`batch_size=10`,
  `num_workers=4`) and calls `gc.collect()` after each batch
  (`slides/base.py:46-47,193-243`). `show_progress` uses tqdm.
- **langchain-community**: no parallelism; `GenericLoader` streams one
  blob at a time from a `FileSystemBlobLoader` (`glob`, `suffixes`,
  `exclude`, `show_progress`) into `blob_parser.lazy_parse`
  (`generic.py:111-116,129-181`).

Inferred: none of the three treats a 10,000-file batch as a contract;
they are per-file loaders with an optional process pool. The bulk story
is vfs's own to design.

## 7. Abandoned or demoted choices (observed)

- haystack moved Tika and Azure OCR out of core into
  `haystack-core-integrations`, keeping pypdf and pdfminer.six as the
  only in-core PDF engines; Docling, MarkItDown and Unstructured joined
  the integrations rather than core.
- langchain moved every loader out of the monorepo into
  `langchain-community`, leaving only `Blob`/`BaseBlobParser` in
  `langchain_core`; `PDFMinerParser` still accepts the deprecated
  `concatenate_pages` and maps it onto `mode` with a warning
  (`parsers/pdf.py:579-585`); `mode="paged"` on the unstructured loaders
  is deprecated in favour of `chunking_strategy="by_page"`
  (`unstructured.py:121-147`).
- llama_index replaced its simple `PptxReader` with the "Enhanced"
  per-slide reader that captions with `vit-gpt2`; the directory reader
  keeps `.ppt`/`.pptm` pointing at it. `PandasExcelReader` dropped the
  sheet name from metadata (it was never there in the current code).

## 8. What this says for vfs

**Library per format** (observed consensus, inferred recommendation):

| format | evidence | vfs pick |
|---|---|---|
| PDF | pypdf is the in-core default in haystack and llama_index and the named `PyPDFLoader` in langchain; pdfminer.six is the second engine in haystack and langchain; PyMuPDF is faster and has tables but is AGPL-licensed (inferred from its licence, not from the code) and is an extra in llama_index and the registry default in langchain-community | pypdf, `extraction_mode="plain"`, one page at a time; pdfminer.six is not needed |
| DOCX | python-docx is the only library of the three that walks body order (paragraphs interleaved with tables), renders tables, keeps hyperlinks and emits rendered page breaks; docx2txt (llama_index, langchain) flattens; unstructured is a heavy dependency | python-docx |
| XLSX | haystack and llama_index both read through pandas with the openpyxl engine; haystack needs a second openpyxl pass for hyperlinks anyway; langchain has no native reader | openpyxl directly, no pandas (pandas adds nothing vfs needs and is a large dependency — inferred) |
| PPTX | python-pptx in haystack and llama_index; langchain has no native reader | python-pptx: shape text per slide, tables as rows, notes appended |
| images | all three default to **no text** for a bare image and bolt OCR or a vision model on as a separate, optional step | no text in the base rendering; OCR/caption as an optional second renderer (§ seam) |

**The provenance convention.** vfs stores one rendering per entry, so
haystack's convention is the direct fit and llama_index/langchain's
one-document-per-page is not: put a form feed `\f` between units (PDF
pages, slides, sheets, DOCX rendered page breaks) and let the chunker
derive `page = 1 + text.count("\f", 0, chunk_start)`, with haystack's
three rules (`_page_numbers.py:5-11`): a chunk spanning a break belongs
to the page it starts on; leading breaks belong to the chunk; an
all-break chunk is an empty page. Keep per-unit labels (PDF page labels,
sheet names, slide titles) as a small unit table on the rendering, not
in the text, because llama_index shows the cost of losing them
(`PandasExcelReader` drops the sheet name) and langchain shows the value
of keeping both the ordinal (`page`) and the label (`page_label`)
(inferred). The line-range chunker needs no change if `\f` is on its
own line; the chunk-to-page map is then a count of `\f` lines before the
chunk's first line (inferred).

**Table rendering.** Markdown pipe tables, with haystack's two escaping
rules (collapse in-cell line breaks to a space; escape `|` while
doubling any backslash run in front of it,
`docx.py:22-25,314-328`, `xlsx.py:237-244`), NaN/None as an empty cell,
and for XLSX Excel column letters as the header row and the 1-based
Excel row number as the first column so a grep hit reads as a cell
address (`xlsx.py:150-158,200-204`). CSV is haystack's default only
because `to_csv` has no escaping surprises; markdown is what the vision
prompts ask for and what Docling exports (inferred preference: markdown
is line-oriented, so one table row is one grep line and one chunk line).

**Embedded images.** Drop by default, exactly as all three do. When an
image pass is enabled, place its text inline at the image's position
with a visible marker — langchain splices at the last paragraph break
(`_merge_text_and_extras`), llama_index writes `Image: {caption}` lines,
haystack's prompt asks for `[img-caption]…[/img-caption]` — and let the
image pass be a second renderer that rewrites the rendering, not a flag
on the first one (inferred from haystack's two-stage design: text
converter, then `DocumentToImageContent` + LLM extractor keyed by
`file_path` + `page_number`).

**Extras packaging.** None of the three ships pip extras for parsers:
haystack uses `LazyImport` with a `pip install …` hint and checks it in
the component constructor; `llama-index-readers-file` makes pypdf a
hard dependency and declares only `pymupdf` as an extra; langchain-
community imports at call time with a hint. For vfs as a uv project
(inferred): declare real extras per format — `vfs[pdf]` (pypdf),
`vfs[docx]` (python-docx), `vfs[xlsx]` (openpyxl), `vfs[pptx]`
(python-pptx), `vfs[ocr]` (an OCR engine) — plus an umbrella
`vfs[documents]`; probe them once at renderer-registry construction
(haystack's constructor-time `check()`), and report a missing extra as
a classified outcome on the entry (the renderer is *unavailable*), never
as an exception at render time.

**The bytes-first parser seam.** langchain's `Blob` → `BaseBlobParser`
→ `MimeTypeBasedParser` is the closest analogue to vfs's blob table plus
extractor: `Blob` carries `data: bytes | str | None`, `mimetype`,
`encoding`, `path`, `metadata`, and a `source` property that prefers
`metadata["source"]`
(`langchain:libs/core/langchain_core/documents/base.py:59-148`);
`BaseBlobParser.lazy_parse(blob) -> Iterator[Document]` is the only
abstract method (`libs/core/langchain_core/document_loaders/base.py:117-155`);
`MimeTypeBasedParser` dispatches on exact MIME with an optional
fallback and raises on a missing MIME
(`langchain-community:libs/community/langchain_community/document_loaders/parsers/generic.py:14-71`).
haystack's `ByteStream(data, meta, mime_type)` + `FileTypeRouter`
(exact match first, then regex, with `unclassified` and `failed`
buckets) is the same shape with the better failure channel. llama_index
is path-first (readers take a `Path` plus an fsspec filesystem) and is
the weaker fit. For vfs (inferred): `render(data: bytes, mime: str,
label: str) -> Result[Rendering]`, a registry keyed by exact MIME then
pattern, with three distinct classified outcomes — *no renderer for
this type*, *renderer unavailable* (extra not installed), *renderer
failed* (reason as data) — mirroring haystack's `unclassified` /
`failed` and its `extraction_error` metadata. MIME comes from the entry
(declared or sniffed), never from a filename alone; haystack registers
the OOXML MIME types explicitly because `mimetypes` misses them on some
platforms (`multi_file_converter.py:75-80`).

**Size and failure.** No framework bounds the size of a text rendering;
the only hard cap seen is llama_index's 100 MB HWP section guard, and
haystack caps rasterization pixels. vfs must declare its own rendering
byte budget, truncate at a unit boundary with a visible marker, and
record `truncated` on the rendering (inferred, and required by the
no-unbounded-growth rule). Default to warn-and-skip at the batch level
with the failure returned as data per entry, as haystack does; do not
retry a deterministic parse failure (llama_index's `@retry(3)` on
`PDFReader` is a smell to avoid).

One line: use pypdf, python-docx, openpyxl and python-pptx behind
per-format extras; render one text per entry with `\f` between pages,
slides and sheets so page provenance is a count the chunker can do;
markdown tables with haystack's escaping; images dropped unless a second
renderer runs; a MIME-keyed `bytes -> Result[Rendering]` seam with
unclassified / unavailable / failed as distinct classified outcomes.
