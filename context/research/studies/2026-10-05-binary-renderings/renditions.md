# Renditions: how three systems store a derived text of a binary

- **Status:** study
- **Date:** 2026-10-05
- **Owner:** Clay Gendron
- **Sources** (clones refreshed 2026-10-05, see `sources.md`):
  - `git` — `origin/master` @ `5a7d1e8045`, GPL-2.0
  - `jackrabbit-oak` — `origin/trunk` @ `f80bf24`, Apache-2.0
  - `nuxeo` — branch `2025` @ `00b5bed6` (shallow), Apache-2.0
- **Method:** read-only code study. Each finding is cited as `repo:path:line`
  against the commits above. No code was copied. The vfs side was read from
  `src/vfs/models/rows.py` (the entry row's `chunk_*`/`link_*` stamps and the
  `vfs_content` table) and `src/vfs/storage/backends/database/indexing.py`
  (the fingerprint-skip law), plus §6 Q1 of
  `context/research/2026-07-25-multimodal-result-content.md`.

The question vfs is deciding: a binary file's bytes go to a new `vfs_blobs`
table, and a derived **rendering** (text) of those bytes goes into the
existing `vfs_content` row for the same entry, so chunking, grep, glean and
link extraction run unchanged. The three systems below each keep a derived
text of a binary; this study records what keys it, when it is rebuilt, how
staleness is decided, what is stored on failure, and whether the derivation
is in-line or asynchronous.

## 1. git — `textconv` and the notes cache

**What it is.** A diff driver may declare a `textconv` program; git runs it
on a blob and diffs the program's stdout instead of the bytes
(`git:Documentation/gitattributes.adoc:942-955`). The conversion is declared
one-way: "diffs generated by textconv are _not_ suitable for applying", so
only `git diff` and the `git log` family perform it; `format-patch` never
does (`git:Documentation/gitattributes.adoc:967-978`,
`git:Documentation/diff-options.adoc:838-846`,
`git:builtin/log.c:590-592`).

**Which operations get the text view.** The text view is opt-in per verb,
not a property of the blob:

| verb | textconv | where |
|---|---|---|
| `diff`, `log -p` | on by default | `git:builtin/diff.c:512`, `git:builtin/log.c:211` |
| `blame` | on by default | `git:builtin/blame.c:1026`; applied at `git:blame.c:257-258`, `:1040-1041`, `:2871-2872` |
| `log -S` / `-G` (pickaxe) | follows the diff flag | `git:diffcore-pickaxe.c:148-170` |
| `grep` | **off by default**, `--textconv` to enable | `git:Documentation/git-grep.adoc:83-87`, `git:builtin/grep.c:1064-1065` |
| `cat-file --textconv` | explicit | `git:builtin/cat-file.c:206-210`, `:461` |
| `format-patch`, diff plumbing | never (unless passed on the command line) | `git:builtin/log.c:590-592` |

Once a textconv is in play the result is "known to be text", so grep skips
its binary-file handling entirely (`git:grep.c:1619-1636`).

**What keys the cache.** `diff.<driver>.cachetextconv = true` turns on a
cache (`git:Documentation/gitattributes.adoc:980-990`,
`git:userdiff.c:506-507`). The cache is a notes tree at
`refs/notes/textconv/<driver>` (`git:userdiff.c:564-572`). Its key is the
**blob object id**; its value is the converted text stored as another blob
in the object database (`git:notes-cache.c:79-105`). So one cache entry
serves every path and every commit that holds that blob, and a blob rewritten
with different bytes is simply a different key. Entries are only written for
objects with a valid oid; a worktree file (no oid) is converted every time
and never cached (`git:diff.c:7794-7800`, `:7806-7816`; grep's worktree
sources carry a null oid, `git:grep.c:1515-1525`).

**Extractor generation.** The cache's "validity" string is the textconv
command itself (`git:userdiff.c:570`). It is written as the commit message of
the notes ref (`git:notes-cache.c:57-77`); on open, git compares the stored
message to the current command and starts the notes tree empty on mismatch
(`git:notes-cache.c:13-39`, `:41-55`). Changing the program's *name or
arguments* therefore invalidates the whole namespace; upgrading the program
binary in place does not, and the documented remedy is manual
(`git update-ref -d refs/notes/textconv/<driver>`,
`git:Documentation/gitattributes.adoc:991-998`).

**Staleness.** There is none to handle: the key is content identity, and the
only non-content input (the command string) is the validity gate above.
Entries are cached "indefinitely" (`git:Documentation/gitattributes.adoc:992`).

**Lazy vs eager.** Strictly lazy. `fill_textconv` checks the cache, runs the
program on a temp file on miss, and writes the cache immediately after
("generating a cache entry is the slow path anyway", `git:diff.c:7802-7816`).
Cache-write failures are ignored so a read-only repository still works
(`git:diff.c:7807`).

**Size and time limits.** None on the conversion itself. `big_file_threshold`
only short-circuits the *binary sniff* (a file above the threshold is declared
binary without being read, `git:diff.c:4546-4556`); a driver with
`binary = true` plus `textconv` bypasses the sniff for conversion
(`git:Documentation/gitattributes.adoc:1053-1060`). The conversion runs
single-threaded under the object-read lock even in multithreaded grep
(`git:grep.c:1527-1542`; documented at
`git:Documentation/git-grep.adoc:349-352`).

**Missing or failing driver.** If the `diff=<name>` attribute names a driver
with no `[diff "<name>"]` section, lookup yields no driver and no textconv
(`git:userdiff.c:538-556`, `git:diff.c:3741-3749`); the blob is then treated
as an ordinary binary (`Binary files differ`; grep's binary rules apply,
`git:grep.c:1623-1636`). If the program *exists but fails* (non-zero exit or
unreadable stdout), `run_textconv` returns NULL and the command dies with
"unable to read files to diff" (`git:diff.c:7738-7771`, `:7803-7804`) — a
hard error, nothing cached.

## 2. jackrabbit-oak — Tika extraction for the Lucene/Elastic index

**Where the binary lives.** A binary is a `Blob` value on a `jcr:data`
property; the node also carries `jcr:mimeType` (mandatory for indexing) and
optional `jcr:encoding` (`jackrabbit-oak:oak-search/.../spi/binary/FulltextBinaryTextExtractor.java:102-122`).
The blob's identity is `Blob.getContentIdentity()`: stable for a value,
"if two values have the same identifier, the content of the value is
guaranteed to be the same", but not the converse, and it may be null
(`jackrabbit-oak:oak-api/src/main/java/org/apache/jackrabbit/oak/api/Blob.java:77-89`).

**Where the extracted text lives.** Three places, none of them the node:

1. **In the index, as tokens only.** The extracted string is added to the
   Lucene `:fulltext` field with `Store.NO` by default
   (`jackrabbit-oak:oak-lucene/.../FieldFactory.java:149-155`;
   fed from `FulltextDocumentMaker.java:298-301`). The text is not
   retrievable from the index afterwards.
2. **An in-memory cache keyed by content identity**, `ExtractedTextCache`,
   whose stated purpose is to avoid re-extracting a binary "already
   processed (in a different node that references the same binary)"
   (`jackrabbit-oak:oak-search/.../ExtractedTextCache.java:58-62`,
   key/value at `:85-86`). Defaults: 20 MB, 300 s expire-after-access
   (`jackrabbit-oak:oak-lucene/.../LuceneIndexProviderService.java:119-121`;
   builder at `ExtractedTextCache.java:107-113`).
3. **An optional pre-extracted store on disk**, written by `oak-run tika`
   and read back through `PreExtractedTextProvider`
   (`jackrabbit-oak:oak-core/.../fulltext/PreExtractedTextProvider.java:29-41`).
   The store lays one text file per blob id out in the `FileDataStore`
   directory shape, plus two sidecar lists, `blobs_error.txt` and
   `blobs_empty.txt`
   (`jackrabbit-oak:oak-core/.../datastore/DataStoreTextWriter.java:54-57`,
   `:90-123`, `:191-197`;
   `jackrabbit-oak:oak-doc/src/site/markdown/query/pre-extract-text.md:103-110`).
   The provider is consulted only during **reindex** (or when
   `alwaysUsePreExtractedCache` is set), never in incremental indexing
   (`ExtractedTextCache.java:133-161`).

**What keys it.** Content identity (the blob id), nothing else — no
extractor version in the key. The lookup order is pre-extracted store (reindex
only) → in-memory cache → persisted timeout map (`ExtractedTextCache.java:142-160`).

**How the index knows a blob changed.** The index editor is diff-driven:
`propertyChanged(before, after)` marks the property and re-makes the Lucene
document for the node (`jackrabbit-oak:oak-search/.../spi/editor/FulltextIndexEditor.java:264-285`).
The new blob has a new content identity, so the cache misses and Tika runs.

**Limits.**

| knob | default | where |
|---|---|---|
| `maxExtractLength` (chars) | `-10` → 10 × `maxFieldLength` (10,000) = **100,000 chars** | `jackrabbit-oak:oak-search/.../IndexDefinition.java:147`, `:164`, `:1770-1777`; `oak-doc/.../query/lucene.md:1161-1165` |
| extraction timeout | 60 s (`oak.extraction.timeoutSeconds`) | `ExtractedTextCache.java:65-66`, `:307-331` |
| timeout pool | 1 thread; only binaries > 16 KiB go through it | `ExtractedTextCache.java:67-68`; `FulltextBinaryTextExtractor.java:70`, `:163-173` |
| cache size / expiry | 20 MB / 300 s | `LuceneIndexProviderService.java:119-120` |

Hitting `maxExtractLength` is normal termination: the write-limit exception
is swallowed and the truncated text is kept
(`FulltextBinaryTextExtractor.java:196-209`).

**What is stored on failure — the sentinel.** Every failure path stores the
literal string `"TextExtractionError"` (`FulltextIndexEditor.TEXT_EXTRACTION_ERROR`,
`jackrabbit-oak:oak-search/.../spi/editor/FulltextIndexEditor.java:54`) as
the extracted text, so the token itself is indexed and the blob is not
retried while cached:

- parser libraries missing (`LinkageError`, "equivalent to disabling
  selected media types") → sentinel, cached (`FulltextBinaryTextExtractor.java:178-189`);
- any other throwable → sentinel, cached (`:196-206`);
- timeout → sentinel, cached, **and** written to a persistent
  `textExtractionTimeout.properties` in the index directory whose header
  reads "will not be retried" (`:190-195`;
  `ExtractedTextCache.java:173-183`, `:389-402`); `close()` deliberately
  keeps that file "so we don't re-try after restarting" (`:300-305`).
- `ExtractedText` has three results — `SUCCESS`, `EMPTY`, `ERROR` — and the
  cache maps them to text / `""` / sentinel (`jackrabbit-oak:oak-core/.../fulltext/ExtractedText.java:28-49`;
  `ExtractedTextCache.java:185-195`). A flag `oak.extracted.cacheOnlySuccess`
  can stop errors from being cached (`:63-64`, `:166-168`).
- The oak-run pre-extractor applies the same split to disk: `markError` on
  the sentinel, `markEmpty` on blank output, `write` otherwise, and skips
  any blob id already processed
  (`jackrabbit-oak:oak-run/.../tika/TextExtractor.java:181-205`).

**Unsupported mime.** A null or unsupported `jcr:mimeType` is silently
skipped — no text, no sentinel (`FulltextBinaryTextExtractor.java:106-114`,
`:243-255`).

**In-line or asynchronous.** Asynchronous only. The binary text extractor is
created only when the editor context is on an async indexing lane
(`jackrabbit-oak:oak-search/.../spi/editor/FulltextIndexEditorContext.java:242-247`);
the document maker explicitly skips extraction for sync indexing
(`FulltextDocumentMaker.java:483-490`). The lane is the index definition's
`async` property (`jackrabbit-oak:oak-doc/src/site/markdown/query/indexing.md:112-119`).
Bulk pre-extraction exists precisely because async single-threaded
extraction "slows down the indexing rate considerably" on reindex
(`pre-extract-text.md:32-40`); it is incremental and can run on another
machine against only the blob store (`:109-110`, `:130-136`).

## 3. nuxeo — the Rendition service and fulltext extraction

Nuxeo has two distinct derived-content mechanisms. **Renditions** are
user-facing derived blobs (PDF, thumbnail) that are themselves documents.
**Fulltext extraction** is the search-only text of a document's blobs, kept
in a dedicated SQL table. They answer the sub-questions differently, so both
are reported.

### 3.1 Renditions

**Model.** A stored rendition is a *separate document* that copies the
source's content, carries the `Rendition` facet and the `rendition` schema:
`sourceId` (the version document), `sourceVersionableId` (the live
document), `sourceModificationDate`, `renditionName`, `renditionVariant`
(`nuxeo:modules/platform/nuxeo-platform-rendition/nuxeo-platform-rendition-core/src/main/resources/schemas/rendition.xsd`;
`nuxeo:.../nuxeo-platform-rendition-api/.../rendition/Constants.java:35-60`;
creation at `nuxeo:.../rendition/service/RenditionCreator.java:197-212`).

**Versioned with the document — yes, deliberately.** Stored renditions are
only looked up for a non-versionable document or a versionable one that is
*checked in*; a checked-out document always gets a live (recomputed)
rendition (`nuxeo:.../rendition/service/RenditionServiceImpl.java:318-335`).
Storing a rendition of a checked-out versionable document first **checks it
in** (a MINOR version) so the rendition can point at an immutable version
(`RenditionServiceImpl.java:256-283`); the rendition document itself is then
checked in with the same version numbers (`RenditionCreator.java:118-130`,
`:246-247`). Definitions default to `storeByDefault = false`
(`nuxeo:.../rendition/service/RenditionDefinition.java:254-262`).

**Staleness.** Two rules, chosen by versionability
(`nuxeo:.../rendition/service/RenditionFinder.java:73-123`):

| source | lookup predicate | staleness |
|---|---|---|
| versionable | `ecm:isVersion = 1 AND rend:sourceId = <last version id>` | impossible — the version is immutable; a new version is a new key |
| non-versionable | `rend:sourceModificationDate >= <source's modification date>` | by comparing the recorded source modification date with the current one |

The modification property defaults to a configured name per definition
(`RenditionDefinition.java:233-242`). On re-store, an existing rendition whose
recorded date is not older than the source is reused outright; otherwise it
is re-rendered into the same rendition document (`RenditionCreator.java:170-186`).

**Lazy renditions.** `AbstractLazyCachableRenditionProvider` renders in a
background `Work` and parks the result in a transient store keyed by a
rendition key plus the source modification date
(`nuxeo:.../rendition/lazy/AbstractLazyCachableRenditionProvider.java:60-80`).
The states are signalled **in the blob's MIME type**:

- first request: schedule the Work, return an empty `text/plain;empty=true`
  blob named `inprogress` (`:163-178`; markers at
  `nuxeo:.../rendition/impl/LazyRendition.java`, `EMPTY_MARKER`,
  `ERROR_MARKER`, `STALE_MARKER`, `IN_PROGRESS_MARKER`);
- completed but the source's modification date moved: reschedule and return
  the **old** blob with `;stale=true` appended (`:220-232`);
- completed in error: `error=true`; if the source moved, reschedule and tag
  stale too (`:195-213`).

`storeRendition` refuses to persist a blob whose MIME carries `error=true` or
`stale=true` (`RenditionServiceImpl.java:247-253`), and a `LazyRendition`
is "completed" only once the `empty=true` marker is gone
(`LazyRendition.java`, `isCompleted`).

### 3.2 Fulltext extraction

**Where the text lives in SQL.** A dedicated `fulltext` table, one row per
document, with columns `jobid`, `fulltext` (the indexed synthetic column —
`tsvector` on PostgreSQL), `simpletext` and `binarytext`, suffixed per
configured index (`nuxeo:modules/core/nuxeo-core-storage-sql/nuxeo-core-storage-sql/src/main/java/org/nuxeo/ecm/core/storage/sql/Model.java:299-318`,
`:1390-1413`; PostgreSQL types at
`nuxeo:.../sql/jdbc/dialect/DialectPostgreSQL.java:287-295`). When
`fulltextStoredInBlob` is on, `binarytext` becomes a blob id instead of a
stored column (`Model.java:1402-1411`). The extracted binary text is also
readable through the API, `CoreSession.getBinaryFulltext(ref)` with main key
`"binarytext"` (`nuxeo:modules/core/nuxeo-core-api/.../CoreSession.java:1607-1615`).

**Computed asynchronously as a Work after commit — yes.** At `save()` the
session computes which documents have dirty strings and dirty binaries,
stamps each with `ecm:fulltextJobId = <its own id>` (`markIndexingInProgress`),
flushes, and then schedules one `FulltextExtractorWork` per document
"post-commit" with `Scheduling.IF_NOT_SCHEDULED`
(`nuxeo:.../storage/sql/SessionImpl.java:243-268`, `:298-341`). The DBS
(MongoDB) backend does the same (`nuxeo:modules/core/nuxeo-core-storage-dbs/.../DBSTransactionState.java:1364-1410`).
The job id serves two purposes: it marks "indexing in progress", and when the
Work runs it queries `WHERE ecm:fulltextJobId = '<id>'` so copies or versions
made between save and the Work also receive the text, then clears the stamp
(`nuxeo:modules/core/nuxeo-core-storage/src/main/java/org/nuxeo/ecm/core/storage/FulltextExtractorWork.java:165-180`,
`:182-194`). Retry count is 1 (`:117-120`).

**Extraction.** Each blob goes through the `any2text` converter — a
wildcard `*` → `text/plain` converter (`nuxeo:modules/core/nuxeo-core-convert-plugins/src/main/resources/OSGI-INF/convert-service-contrib.xml:102-105`)
that looks up a *specific* source-mime → `text/plain` converter and
delegates (`nuxeo:.../convert/plugins/text/extractors/FullTextConverter.java:50-75`).
Results are joined with a leading and trailing space (for `LIKE '% foo %'`
phrase emulation) and truncated to `fulltextFieldSizeLimit`
(`FulltextExtractorWork.java:222-243`, `:304-321`), default **128 KiB**
(`nuxeo:.../storage/FulltextDescriptor.java:91`).

**No extractor / failure.** Both yield the **empty string**: no converter
for the mime → `""` at debug level (`FullTextConverter.java:71-74`);
`ConversionException`/`IOException` → `""` with a warning log
(`FulltextExtractorWork.java:274-302`). Nothing distinguishes "no text in
file" from "could not extract" in the stored row. A bulk re-extraction action
exists for repair (`nuxeo:.../storage/action/ExtractBinaryFulltextAction.java:54-57`).

## 4. Side by side

| question | git textconv | oak | nuxeo fulltext | nuxeo rendition |
|---|---|---|---|---|
| key | blob oid | blob content identity | document id (+ job id while pending) | source id (version) or source id + modification date |
| extractor generation | command string → whole-cache invalidation | none | none | none |
| rebuilt when | on demand, cache miss | async index lane, on property diff | post-commit Work when a binary is dirty | checked-in: never; non-versionable: date moved; lazy: date moved |
| versioned with file | implicitly (per-blob) | no (index only) | no (one row per live doc) | yes — pinned to a checked-in version |
| read-only | yes, one-way by contract | yes (tokens only) | yes | separate document |
| where stored | object db via notes ref | Lucene tokens + mem cache + optional disk store | `fulltext` table | its own document |
| size cap | none | 100,000 chars (truncate, keep) | 128 KiB (truncate, keep) | n/a |
| time cap | none | 60 s, 1-thread pool, >16 KiB only | Work retry 1 | Work |
| no extractor | treat as binary | skip silently (unsupported mime); sentinel on missing libs | `""` | n/a |
| failure | hard error, not cached | `"TextExtractionError"` cached; timeouts persisted as never-retry | `""` + warn | `error=true` in MIME, never stored |
| in-flight marker | none | none | `ecm:fulltextJobId` | `empty=true` / `inprogress` |
| stale marker | none needed | none | none | `stale=true`, old blob served |

## 5. What this says for vfs

Labels: **observed** = the repo does it, cited above; **inferred** = my
reading of what the vfs design should take from it.

**5.1 What keys the rendering.**
- *observed:* all three key the derived text by content identity (git blob
  oid; Oak content identity; Nuxeo by document + modification date, the
  weakest). Only git carries an extractor identity, and it does so as a
  single validity string that invalidates the whole namespace.
- *inferred:* stamp the entry row exactly like chunks and links already are —
  a `render_source_hash` (the **bytes** hash) and a `render_generation` (the
  extractor's name + version, e.g. `pdftotext/24.02` or `docx-xml/1`). The
  fingerprint-skip law then applies unchanged: same hash under the same
  generation → do nothing. This is strictly better than git's validity string
  because a generation bump is per-row and recoverable, not a whole-cache
  drop. Oak's lesson is the cost of *not* carrying a generation: nothing can
  retire a stale `"TextExtractionError"` except manual cache reset.

**5.2 When it is rebuilt.**
- *observed:* Oak rebuilds in the async index pass when the property diff
  shows a new blob; Nuxeo schedules a post-commit Work the moment a binary is
  dirty; git on first text operation.
- *inferred:* rebuild in the existing reindex pass as a stage that runs
  **before** chunk-split, keyed by the stamp pair: dirty binaries with a
  mismatched (`render_source_hash`, `render_generation`) render, their
  rendering is written to `vfs_content`, and the same pass then chunks it.
  That keeps one dirty loop (vfs has `chunked` already) and one offload hop.
  The generation bump should re-dirty via the same lock-free existence probe
  the chunk generation uses.

**5.3 Versioned with the file.**
- *observed:* Nuxeo pins stored renditions to an immutable checked-in
  version precisely so they can never be stale; git's per-blob keying has
  the same effect for free; Oak and Nuxeo fulltext keep only the current
  text.
- *inferred:* do not version the rendering. `vfs_versions` should record the
  **bytes** hash (and a blob reference) for a binary version; the rendering
  is regenerable from (bytes, generation) at any time, which is what the
  stamp pair promises. If a later verb needs "text of version N", it renders
  the version's blob on demand — git's lazy path — rather than storing a
  rendering per version.

**5.4 Read-only.**
- *observed:* git declares textconv output one-way and refuses to apply it;
  Oak stores only tokens; Nuxeo keeps renditions as separate documents that
  never write back.
- *inferred:* the rendering is read-only. A `write` to a binary path replaces
  bytes in `vfs_blobs` and re-dirties the stamp; a text edit of a binary
  entry (edit/replace on the rendering) must be refused with a classified
  result, never silently written to `vfs_content`, because the next reindex
  would overwrite it.

**5.5 What `content_hash` / `size_bytes` on the entry row describe.**
- *observed:* every system keeps the bytes' identity on the owner (Nuxeo's
  `file:content` digest and length, Oak's blob and `jcr:data`, git's blob
  oid) and the derived text's metadata elsewhere (the `fulltext` row, the
  cache entry, the notes value blob).
- *inferred:* the entry row describes the **bytes**: `content_hash` = bytes
  hash, `size_bytes` = bytes length, `mime_type` = the binary's type. That is
  what a caller wrote and what `write`/`move` compare. The rendering's own
  facts — its hash, its line count (what grep reports line numbers against),
  whether it was truncated — belong with the stamp: `render_source_hash`
  plus a small `render_*` set, or on the `vfs_content` row. The `lines`
  column needs an explicit decision: today it describes `vfs_content`, which
  for a binary is the rendering; either keep it as "lines of the text the
  verbs see" and document that, or move it next to the render stamp.

**5.6 Lazy vs eager.**
- *observed:* git is lazy and cached; Oak is eager on the async lane and
  adds bulk pre-extraction because single-threaded eager extraction is the
  reindex bottleneck; Nuxeo fulltext is eager-async post-commit, and Nuxeo's
  lazy renditions return an explicit `empty=true` / `inprogress` placeholder
  rather than nothing.
- *inferred:* eager-async in the reindex pass (5.2), with two borrowings:
  (a) a read or grep that reaches a binary whose rendering is not yet stamped
  returns a classified "not rendered yet" row — Nuxeo's in-progress marker —
  not an empty body; (b) at the 10,000-file batch contract, rendering must
  be chunked and offloaded like chunk-split already is, and the pass must
  write renderings per sub-batch so a long extractor cannot hold the whole
  batch's state. Oak's 16 KiB small-binary fast path and 60 s timeout are
  reasonable defaults to carry as config, not as design caps.

**5.7 No extractor available, or extraction fails.**
- *observed:* git treats the file as plain binary; Oak skips unsupported
  mimes silently but stores a `"TextExtractionError"` sentinel (and a
  persisted never-retry list for timeouts) when a parser is missing or
  fails; Nuxeo stores `""` and a warn log, making "empty file" and "could not
  extract" indistinguishable.
- *inferred:* record the outcome as a **state, not a body**. Keep no
  `vfs_content` row for an unrenderable binary and stamp the entry with the
  generation it was judged under plus a small status (`rendered`,
  `unsupported`, `failed`, `timeout`, `truncated`). The skip law then does
  not retry under the same generation (Oak's point), a generation bump does
  retry (git's point), and grep/glean can report "binary, no text rendering"
  rather than matching a sentinel token or returning silence (the Oak and
  Nuxeo failure modes). Never put a sentinel string into `vfs_content`: it
  would be chunked, embedded and grep-matchable.

**5.8 Size budget.**
- *observed:* Oak truncates at 100,000 chars and keeps the prefix; Nuxeo at
  128 KiB and keeps the prefix; git has no limit.
- *inferred:* a configurable per-rendering character budget with the
  `truncated` state above, so the fact of truncation is visible on the row.
  This is a per-file extractor budget, not a corpus cap.

**5.9 Dedup across entries.**
- *observed:* Oak's cache exists mainly so the same blob referenced from two
  nodes is extracted once; git's blob keying gives the same property.
- *inferred:* when two entries share `render_source_hash` under the current
