# R2 — How graphs-on-SQL compile multi-hop traversal, and what semantics they choose

- **Date:** 2026-10-14
- **Researcher:** R2 (vfs graph-traversal study)
- **Sources:** read-only clones under `~/Git/Repos`, refreshed 2026-10-13 (`age` d7e2e74 Apache-2.0; `gel` 8519106 Apache-2.0; `cayley` 81dcd7d Apache-2.0; `duckpgq` 91433a8 MIT; `jackrabbit-oak` 9c7d6d0 Apache-2.0; `terminusdb` 79cbbcff Apache-2.0; `GraphLite` a370a1c Apache-2.0; `helix-db` 16b7a837 AGPL — study only). Engine facts from vendor docs (URLs inline). One executed SQLite experiment (`scratchpad/experiments/r2_recursive_vs_frontier.py`).
- Every claim is tagged **READ** (from source), **EXECUTED** (we ran it), or **INFERRED** (our reasoning).

## Summary

Nobody in this set compiles a multi-hop traversal into a recursive SQL statement. The two serious "graph on a SQL engine" systems — Apache AGE and DuckPGQ — both load the whole edge set into an in-memory adjacency structure inside the engine process (AGE: per-backend hash tables; DuckPGQ: a CSR built by a CTE per query) and run a hand-written DFS or multi-source BFS over it as a set-returning / scalar function called from the SQL plan. Cayley runs its `FollowRecursive` as a client-side frontier loop, one morphism application per depth, with a visited map in Go. Gel has backlinks but no transitive closure at all. Oak answers only direct children from SQL (a key-range scan on a depth-prefixed id); descendants are a client-side tree walk or an external index. TerminusDB and GraphLite and helix-db are not on SQL and walk their own stores in-process. The recursive CTE is, in this field, something only vfs's own archived spec reached for. Semantics split cleanly by purpose: **path-returning** queries use edge-unique (trail) semantics (AGE, TerminusDB, GraphLite's default is WALK but it supports all four PGQ modes); **reachability** queries use a plain visited set (AGE's shortest-path BFS, DuckPGQ's `iterativelength`, cayley, helix-db, Oak). Depth is a caller bound everywhere, with a default only in cayley (50) and GraphLite (`AtLeast` capped at 10). Direction words are Cypher arrows (AGE), `->`/`<-`/`-` and `*` (DuckPGQ), `.<` backlinks (gel), `Out`/`In`/`Both` (cayley, helix-db), `p`/`n` (TerminusDB). Rights inside the walk exist in exactly one system: AGE loads the adjacency through SPI so Postgres row-level security filters vertices and edges at load, and drops every edge whose endpoint is hidden — the "nothing is reached through a hidden node" rule vfs wants, implemented at the adjacency layer, not per hop.

Our executed SQLite experiment confirms the shape vfs should expect from a recursive CTE: `UNION` on a node-only column converges unbounded on a cyclic graph; `UNION` on `(node, depth)` does **not** converge (rows grow 24 → 84 → 204 as the bound grows 8 → 16 → 32 on a 4-cycle), and `UNION ALL` on a 6-clique produced 19,531 rows for 6 nodes at depth 6. Per-hop visibility as a join on the entries table hid both the invisible and the tombstoned node and everything only reachable through them. Multi-seed reachability is a union of per-seed reachability with the same minimum depths, so seeds can be chunked to the IN-list budget and merged.

## Evidence per source

### Apache AGE (Cypher on Postgres)

**Execution shape — READ.** The parser turns `(a)-[*lo..hi]->(b)` into a call to the SRF `vle(...)` and appends it to the FROM clause as a LATERAL item (`age:src/backend/parser/cypher_clause.c:4501-4535`, `append_VLE_Func_to_FromClause`; the "vle" FuncCall is named at `:148-174`). The SRF `age_vle` (`age:src/backend/utils/adt/age_vle.c:1960-2110`) runs an iterative DFS (`dfs_find_a_path_from` `:1210`, `dfs_find_a_path_between` `:1065`) and returns one row per path, a composite `(edges, start_id, end_id)` (`:1986-1998`). The DFS walks a **per-backend in-memory copy of the whole graph**: `GRAPH_global_context` holds a vertex hash table with flat `edges_in` / `edges_out` / `edges_self` arrays per vertex and a Robin-Hood edge table (`age:src/backend/utils/adt/age_global_graph.c:135-193`). The cache is invalidated by a per-graph version counter in shared memory, bumped by every Cypher mutation (`:59-75`). A VLE in one query is re-invoked per outer row (per seed) and its local context is cached per grammar node, five deep (`age_vle.c:84`, `MAXIMUM_NUMBER_OF_CACHED_LOCAL_CONTEXTS`; `:231-370`). This is a **custom executor node in all but name**: SQL supplies the seeds and consumes the rows; the hops never touch SQL.

**Depth — READ.** Lower bound defaults to 1, upper omitted means infinite (`age_vle.c:912-933`). The DFS stops expanding at `uidx` (`:1310-1316`). There is no engine-side cap; the header comment states the cost model plainly: paths enumerated are bounded by `sum_{k=lo..hi} P(E,k)`, "factorial in the depth bound", and unbounded patterns "have no termination guarantee other than edge-uniqueness depletion" (`:20-62`).

**Cycle policy — READ.** The file's header is explicit: edge-isomorphism, "a path is valid iff no edge appears in it more than once. Vertices MAY recur", and it names tracking visited vertices "incorrect, not merely faster" because openCypher requires the triangle path A→B→C→A for `[*3]` (`age_vle.c:27-45`). Enforced by `edge_state_entry.used_in_path` set/cleared on the DFS stack (`:1261-1300`) and `is_edge_in_path` (`:1335`). Multiple relationship patterns in one MATCH get `_ag_enforce_edge_uniqueness` applied across them (`cypher_clause.c:4749-4762`). For the **reachability-flavoured** verbs AGE added separately — `age_shortest_path` / `age_all_shortest_paths` — the policy flips to a plain visited hash keyed by vertex with a depth, a FIFO queue, and the comment "Because BFS depth strictly increases, every emitted path is simple" (`age_vle.c:2807-2880`, `sp_run_bfs` `:3013-3120`). So: trail semantics for path enumeration, visited-set BFS for shortest/reachability.

**Direction — READ.** `cypher_rel_dir { NONE=0, LEFT=-1, RIGHT=1 }` (`age:src/include/nodes/cypher_nodes.h:159-162`). The DFS reads `edges_out` for RIGHT, `edges_in` for LEFT, both for NONE; self-loops are always traversed (`age_vle.c:1423-1440`). The BFS does two passes, outgoing then incoming, gated by the same enum (`:3028-3029`, `:3100`).

**Return shape / multi-seed — READ + INFERRED.** One row per path; the outer Postgres plan joins the rows back to the node tables. A multi-seed query is simply a MATCH whose start pattern binds many rows; the LATERAL SRF runs once per row. Results are not deduplicated (paths are the unit), so two seeds reaching the same node yield two rows — vfs would have to `DISTINCT` on the end id itself.

**Filtering inside the walk — READ.** Two mechanisms. (1) Edge label and property constraints from the pattern are matched per edge during the DFS (`is_an_edge_match` `:408`; fields `edge_label_name_oid`, `edge_property_constraint` `:118-123`). (2) **Row-level security.** With `age.enforce_rls_in_traversal` (default on, `age:src/backend/utils/ag_guc.c:26,46`), vertex and edge label tables under RLS are loaded through SPI so "the planner applies row-level security" (`age_global_graph.c:880-895`, `load_vertex_label_rls`, `load_edge_label_rls` `:1009`), and any edge whose start or end vertex was filtered is dropped: "This mirrors MATCH's inner-join behavior and avoids leaving a dangling edge in the cache" (`:1104-1112`). The cache is keyed by role and rebuilt whenever RLS was involved, because policies can depend on session state (`:314-360`). The regression test `age:regress/sql/rls_vle.sql` pins the exact contract vfs wants: hiding the intermediate vertex n2 makes `n1-[*1..3]->(b)` return nothing ("the traversal cannot pass through it", `:94-105`), hiding only the leaf n4 still reaches n2 and n3 (`:107-117`), and a hidden edge property stops the walk at the edge (`:60-77`). A caveat they hit: RLS loads are refused in parallel workers because policies may read session state a worker lacks (`age_global_graph.c:1202-1217`).

**Performance notes — READ.** No CTE-vs-loop comparison exists because AGE never used a CTE. What the code records: the adjacency was moved from linked lists to flat arrays "significantly better for cache and branch-predictor behaviour on the DFS hot path" (`age_vle.c:1374-1381`), and edge lookups are batched 8 at a time to overlap cache misses (`:1361-1368`, `:1393-1405`). The edge entry omits its own id to save 8 bytes/edge because "on SF10 (~175M edges) is over a gigabyte" (`age_global_graph.c:143-150`) — i.e. the whole-graph-in-memory model is what they scale, not the SQL.

### gel (EdgeDB on Postgres)

**READ.** Backlinks are the `.<link[is Type]` syntax (`gel:docs/reference/edgeql/paths.rst:110-195`). In the SQL compiler a backlink whose link is stored inline "outputs the source path" — a join to the source table's column — else it goes through the link table (`gel:edb/pgsql/compiler/relctx.py:575-600`); when a backlink revisits a type, a semi-join is produced (`:1682-1687`). The Postgres AST supports `recursive` on a CTE and codegen writes `RECURSIVE` (`gel:edb/pgsql/ast.py:288-289`, `codegen.py:219-220`), but the only place that sets it is the SQL-adapter resolver passing a user's own SQL through (`gel:edb/pgsql/resolver/range_var.py:247,284`). No `recursive=True` exists anywhere under `edb/pgsql/compiler`. **INFERRED:** EdgeQL has no transitive closure; the grammar has no path quantifier. gel is evidence that a typed-link system over Postgres can ship without any k-hop primitive at all — every hop is a named step the caller writes.

### cayley (graph over SQL, KV, Mongo)

**Execution shape — READ.** `FollowRecursive(via, maxDepth, depthTags)` "will repeatedly follow the given string predicate or Path … ignoring loops. For example, this turns 'parent' into 'all ancestors'" and warns "This is a very expensive operation in practice" (`cayley:query/path/path.go:369-387`). It builds a `Recursive` iterator (`cayley:graph/iterator/recursive.go:29-37`). `recursiveNext.Next` (`:140-192`) is a client-side level loop: when the current level's iterator is exhausted it bumps `depth`, wraps the values discovered at this level in a `Fixed` iterator, and applies the morphism to it (`it.morphism(Tag(it.baseIt, recursiveBaseTag)).Iterate()`, `:166`). A `seen` map keyed by value records the first depth (`:176-187`). The SQL backend's `OptimizeShape` has no `Recursive` case (`cayley:graph/sql/optimizer.go:80-103`), and when a `Fixed` set has more than one value the optimizer gives up with `// TODO: support IN, or generate SELECT equivalent` (`:319-323`). **INFERRED:** on the SQL backend each depth is therefore not even one `IN`-list query; the generic iterators evaluate the morphism value-by-value with `Contains` lookups, i.e. many small SQL point queries per hop.

**Depth — READ.** `DefaultMaxRecursiveSteps = 50`; 0 means default, -1 unlimited (`recursive.go:18,30-32`; `path.go:375-380`).

**Cycle policy — READ.** Visited set over values; a value is emitted once, at its first depth (`recursive.go:176-187`). Reachability semantics only; path recovery is by walking the `seen` chain (`getBaseValue` `:200-213`).

**Direction / return — READ.** `Out`, `In`, `Both` morphisms; result is a node set with an optional depth tag (`TagResults` `:121-137`).

### duckpgq (SQL/PGQ on DuckDB)

**Execution shape — READ.** `MATCH` with a quantified edge is rewritten at bind time (`duckpgq:src/core/functions/table/match.cpp`): a CTE `cte1` builds a CSR over the **entire** edge table with `CREATE_CSR_VERTEX` / `CREATE_CSR_EDGE` (`:726-745`, `CreateDirectedCSRCTE` / `CreateUndirectedCSRCTE`), the FROM gets a cross join to `(SELECT count(cte1.temp) * 0 AS temp FROM cte1) __x` purely to force the CSR to be built first (`:415-417`, `:748-751`), and the quantifier becomes a WHERE predicate `__x.temp + iterativelength(csr, n, a.rowid, b.rowid) BETWEEN lower AND upper` (`AddPathQuantifierCondition` `:710-724`). `ANY SHORTEST` adds a `MATERIALIZED` CTE calling `shortestpath(...)` (`GenerateShortestPathCTE` `:520-549`). The test `duckpgq:test/sql/path_finding/path-finding-cte.test:38-70` shows the generated SQL verbatim. `iterativelength` is a frontier BFS over the CSR with `seen`/`visit`/`next` bitsets of `LANE_LIMIT = 512` lanes (`duckpgq:src/core/functions/scalar/iterativelength.cpp:12-33`; `duckpgq_utils.hpp:10`) — a **multi-source BFS**, 512 sources per pass, which is the batch primitive for "many seeds at once". No recursive CTE anywhere.

**Depth — READ.** `SubPath` defaults `lower = 1, upper = 1`, `path_mode = NONE` (`duckpgq:src/include/duckpgq/parser/subpath_element.hpp:17-30`). Unbounded `*` with ALL and WALK is refused: "ALL unbounded with path mode WALK is not possible as this could lead to infinite results. Consider specifying an upper bound or path mode other than WALK" (`match.cpp:118-121`). Unbounded `ANY SHORTEST` is allowed because BFS terminates.

**Cycle policy / PGQ path modes — READ.** `enum PGQPathMode { NONE, WALK, SIMPLE, TRAIL, ACYCLIC }` (`subpath_element.hpp:9`); anything but WALK throws "Path modes other than WALK have not been implemented yet" (`match.cpp:115-116`; test `pattern_matching/path_modes.test:84-125`); `ALL SHORTEST` likewise unimplemented. The BFS's `seen` bitset gives shortest-hop-count reachability, which is what `iterativelength` returns. Meaning of the modes (READ from GraphLite's implementation, which is the clearest statement in the set, `GraphLite:graphlite/src/ast/ast.rs:276-287` and `exec/executor.rs:6620-6640`): **WALK** — repeats allowed; **TRAIL** — no repeated edge; **SIMPLE** — no repeated vertex on the path; **ACYCLIC** — no repeated vertex at all (visited set). Cypher's default (AGE, Neo4j) is TRAIL.

**Direction — READ.** `MATCH_EDGE_RIGHT` (`->`), `MATCH_EDGE_LEFT`, `MATCH_EDGE_ANY` (`-`), `LEFT_RIGHT` (`path_element.hpp:8`); path finding supports only RIGHT and ANY (`match.cpp:733-741`).

**Return / per-hop filter — READ.** Path functions return lists of rowids (`CreatePathFindingFunction` `:551-560`); vertex WHERE clauses on the endpoints are pushed into the shortest-path CTE (`:583-589`), but there is no hook to filter the intermediate vertices of the repeated step: the CSR is built from the whole edge table.

**Performance — READ.** No CTE comparison in the repo; the design itself is the statement (CSR + bitset MS-BFS inside the engine). `test/sql/path_finding/non-unique-vertices.test` documents that duplicate vertex keys produce duplicate rows "as expected".

### jackrabbit-oak (hierarchical content over RDB/Mongo)

**READ.** Node documents are keyed `depth + ":" + path` (`oak:oak-store-document/src/main/java/org/apache/jackrabbit/oak/plugins/document/util/Utils.java:352-371`), so the direct children of `/a` are exactly one key range: `getKeyLowerLimit` = id of `/a/a` minus its last char, `getKeyUpperLimit` = id of `/a/z` with the tail replaced by `0` (`:568-585`). `DocumentNodeStore.readChildDocs` issues `store.query(NODES, from, to, limit)` (`DocumentNodeStore.java:1532-1542`), which on RDB becomes `... where ID > ? and ID < ?` (`rdb/RDBDocumentStoreJDBC.java:989-1000`). Those helpers are used only for children (`DocumentNodeStore.java:1535-1538, 3474-3475`; `DocumentNodeStoreMBeanImpl.java:210-211`). **INFERRED:** because the depth prefix sorts all depth-2 nodes before all depth-3 nodes, one range cannot cover a subtree; descendants need one range per depth or a walk. That walk is the query engine's `TraversingIndex`, whose cost estimate assumes "worst case 100 million descendant nodes" and ~10 children per node (`oak:oak-core/src/main/java/org/apache/jackrabbit/oak/query/index/TraversingIndex.java:127-140`). **Incoming references** are a write-time index: `ReferenceEditor` accumulates `<UUID, Set<paths-pointing-to-the-uuid>>` during the commit and updates the `reference` / `weakreference` index stores in `leave()` (`oak-core/.../reference/ReferenceEditor.java:80-180`). Oak's lesson for vfs: the hierarchy's single-parent property makes "children" an index range, and reverse edges are a maintained table, not a query-time join — which vfs already has in `ix_vfs_edges_rev`.

### terminusdb (WOQL `path`)

**READ.** Patterns: `p | n | p(P) | n(P) | P,Q | P;Q | plus(P) | star(P) | times(P,N,M)` (`terminusdb:src/core/query/path.pl:300-310`). `p` follows a predicate forward, `n` inverse (`invert_path` `:115-126`); if only the object is bound, the whole pattern is inverted and run from the other end (`run_pattern` `:128-133`). `star`/`plus` call `run_pattern_n_m_(P,1,-1,…)` — unbounded (`:188-193`); `times` is bounded (`:194-195`, `:205-218`). Cycle policy is **trail**: an edge already in the open set makes the branch fail (`in_open_set(Edge,Open_Set), !, fail` `:150-158`, `:170-178`). Returns X/Y bindings and, with the 4-arity form, the `Path` as a list of edge objects (`woql_compile.pl:2539-2560`). Execution is Prolog backtracking over the triple store — in-process, never SQL.

### GraphLite (embedded ISO GQL) — READ

In-process over a `GraphCache`. Quantifiers `?`, `{n}`, `{n,m}`, `{n,}` (capped: "max_cap = 10; // Reasonable limit to prevent infinite expansion"), `{,m}` (`GraphLite:graphlite/src/exec/executor.rs:6434-6530`). Each hop filters by `PathType` — WALK: none; TRAIL: `!visited_edges.contains`; SIMPLE: `!path.contains(next)`; ACYCLIC: `!visited_nodes.contains` (`:6620-6640`). Logical plan also exposes `FindNeighbors{max_hops}`, `ShortestPath{max_length}`, `IsReachable{max_hops}` (`plan/operators/physical.rs:40-66`).

### helix-db — READ (AGPL, study only)

`TraversalOptions { strategy: BFS|DFS, seeds: Vec<NodeId>, max_depth, direction: Out|In|Both, allowed_labels, hub_policy }`, "Maximum emitted depth. Zero emits only seeds" (`helix-db:crates/graph-algorithms/src/algorithms/traversal.rs:9-57`). Seeds are deduplicated before the walk (`:191-201`); BFS uses a `visited` bitmap and emits `Visit{node_id, depth, discovery_order}` plus one `discovery_edge` per non-seed (`:208-252`). The planner's `RepeatPlan` carries a hard `max_depth: NonZeroUsize` "as a hard guardrail" even when a stop condition is given (`crates/planner/src/ir/control_flow.rs:52-72`). `ExpandDirection { Out, In, Both }` (`crates/planner/src/ir/stream.rs:20-26`). Notable idea: `HubExpansionPolicy::StopNonSeedAtOrAbove{degree}` — include but do not expand high-degree nodes.

### vfs's own prior work (archived, pre-refactor) — READ

`context/research/2026-04-22-mssql-native-meeting-subgraph.md`: the SQL Server port rejected `SHORTEST_PATH`/`MATCH` graph tables ("no Steiner-tree or multi-source-BFS-with-component-merging primitive"), rewrote the PL/pgSQL per-neighbour cursor loop as **set-based BFS steps** over `#visited` / `#queue` temp tables inside a stored procedure (one `INSERT … LEFT JOIN #visited … WHERE v.node IS NULL` per level), needed TVPs for seed lists, `SET NOCOUNT ON`, and an empty-but-valid result set. `context/specs/archive/011-mssql-native-multi-hop-traversal/spec.md` recorded that the then-current MSSQL path was "a Python BFS loop that calls `_one_hop` once per layer" costing N round trips, and proposed a single recursive CTE with a `NVARCHAR(4000)` breadcrumb trail and `CHARINDEX` cycle check plus `OPTION (MAXRECURSION 0, RECOMPILE)` for ancestors/descendants, and a stored-proc BFS for `neighborhood`. It flagged parameter sniffing as the real hazard: "a proc compiled against a 3-seed call … can produce a plan that is catastrophically wrong for a 300-seed call" — hence `OPTION (RECOMPILE)` on every seed-dependent statement. Acceptance criteria counted statements per depth, not time.

## Engine facts that bound a recursive-CTE design (READ, vendor docs)

| engine | dedupe inside the recursion | cycle guard | depth cap |
|---|---|---|---|
| PostgreSQL | `UNION` "discard[s] duplicate rows and rows that duplicate any previous result row" at each step; `UNION ALL` keeps all | `CYCLE col SET is_cycle USING path` (14+) adds a path array; docs note `UNION` alone does not stop a loop when a depth column is present | none; `SEARCH BREADTH FIRST BY … SET ordercol` gives BFS order. https://www.postgresql.org/docs/current/queries-with.html |
| SQLite | `UNION`: "only add rows to the queue if no identical row has been previously added"; `UNION ALL` queues everything | none built in | none; FIFO queue = breadth-first when the recursive select has no ORDER BY. https://sqlite.org/lang_with.html |
| SQL Server | `UNION ALL` only inside the recursive member | none; breadcrumb columns by hand | `OPTION (MAXRECURSION n)`, default **100**, max 32,767, 0 = unlimited; exceeding it is an error that rolls the statement back. https://learn.microsoft.com/en-us/sql/t-sql/queries/with-common-table-expression-transact-sql |
| MariaDB | `UNION` / `UNION DISTINCT` dedupes | `CYCLE … RESTRICT` (10.5.2+) | `max_recursive_iterations`, default **1000** since 10.6, and when reached the CTE **stops silently** with no error (MDEV-31214). https://mariadb.com/kb/en/with/ , https://jira.mariadb.org/browse/MDEV-31214 |
| Oracle | recursive subquery factoring; `UNION ALL` | without a `CYCLE` clause Oracle raises **ORA-32044** when a row repeats an ancestor's values for the columns referenced in the recursive WHERE; `CYCLE col SET flag TO '1' DEFAULT '0'` marks instead | none documented. https://docs.oracle.com/en/error-help/db/ora-32044 |

**INFERRED consequences.** A recursive CTE that is correct on all five engines must (a) carry its own cycle guard (a visited-node dedupe or a breadcrumb), because SQL Server has no dedupe, Oracle errors on a repeat, MariaDB caps silently; (b) carry an explicit depth bound as a column predicate, so SQL Server's 100 and MariaDB's 1000 are never the thing that stops it; (c) accept that "min depth per node" needs a post-aggregation, because `UNION` dedupes on the whole row and `(node, depth)` never converges on a cycle (we executed this below).

## Open questions

1. **Breadcrumb vs node-dedupe on SQL Server and Oracle.** Neither engine dedupes inside the recursion. `UNION (node, depth) … WHERE depth < k` is bounded (k × nodes rows) without any dedupe at all, so it is portable; whether Oracle's default cycle check fires on it needs an engine leg run (`[NOT VERIFIED: no Oracle instance in this session]`). Oracle's rule fires when a row repeats an ancestor's values for the columns referenced in the recursive WHERE; the WHERE references `node` and `depth`, and `depth` always increases, so by the documented rule it should not fire — INFERRED only.
2. **Per-hop rights pushdown cost.** vfs's `Visibility` is a three-seek `UNION ALL` join or an OR of path terms. Repeating that join inside the recursive member is one extra join per hop; AGE's alternative is to filter the adjacency once at load. A middle form — compute the visible node set once as a non-recursive CTE and join the recursive member to it — is what an engine without the AGE cache can do. Not measured here.
3. **Multi-source BFS as a Rust kernel.** DuckPGQ's 512-lane bitset BFS is the only batch-native primitive in the set. If vfs ever pulls the edge table into memory per call it should look like that, not a per-seed loop; but that is the whole-corpus profile CLAUDE.md says to acknowledge, not design to.
4. **Does vfs want paths at all?** Every path-returning system chose TRAIL semantics and paid factorial cost; every reachability system chose a visited set. The brief's verb is reachability. If a later `paths` verb is wanted it is a different algorithm, not a flag.

## Implications for vfs

The field uses three shapes for reachability over a SQL table:

1. **Whole-graph in-memory + in-engine kernel** (AGE, DuckPGQ). Fastest, batch-friendly (MS-BFS), rights filtered once at load. Requires an extension in the engine process; vfs cannot ship C into Postgres/SQL Server/Oracle, so this shape is off the table for the SQL-native goal.
2. **Client-side frontier loop, one statement per hop** (cayley; vfs's own pre-2026-04 MSSQL path). Simple, every hop is an ordinary `IN`-list query that chunks naturally, rights predicate is the ordinary per-row filter. Cost is `depth × ceil(frontier / budget)` round trips and a snapshot that may drift between hops (spec 011 named this).
3. **One recursive statement per seed chunk** (only vfs's archived spec 011 proposed it; no studied system ships it). One round trip per chunk of ≤ `in_list_budget` seeds, one snapshot, the rights predicate joined in the recursive member, depth as a column bound, dedupe on node. Needs per-dialect guards: `MAXRECURSION 0` on SQL Server, a `CYCLE` clause or depth-only guard on Oracle, `max_recursive_iterations` irrelevant once depth is bounded in the WHERE.

For the brief's three requirements — **bounded depth, a rights predicate per hop, 10,000 seeds per call** — the field's own choices point at shape 3 with shape 2 as the fallback, for these reasons: a depth bound in the WHERE removes the only thing that makes recursive CTEs dangerous (the experiment shows `(node, depth)` with `depth < k` is bounded by `k × nodes` rows, and node-only `UNION` converges even unbounded); the rights term is a join inside the recursive member, so a hidden node is never a frontier row and nothing is reached through it (executed: `hidden`/`dead` and their children absent); and 10,000 seeds become `ceil(10,000 / membership_budget)` statements whose results union exactly (executed: union of per-seed runs equals the joint run, including minimum depths), which is the same chunking discipline `rows_by_path` already uses. Shape 2 remains the correct answer for `GENERIC`-floor dialects where vfs cannot vouch for the recursive-CTE dialect (the brief says every dialect must serve `graph`): it is the shape cayley and the old vfs used, it needs nothing beyond `IN` lists, and its cost is `depth` round trips, which a `depth` argument bounds. Direction vocabulary in the field is consistently a three-valued enum (`Out`/`In`/`Both`, `RIGHT`/`LEFT`/`NONE`, `p`/`n`); the one-hop and k-hop verbs collapse into "direction + depth" everywhere a reachability API exists (helix-db `max_depth` with "zero emits only seeds"; cayley `FollowRecursive(maxDepth)`; GraphLite `FindNeighbors{max_hops}`), which is exactly Clay's direction (3). Return shape for reachability in every system is a node set with depth (and in helix-db the discovery edge); none return a subgraph for a reachability verb.

One-line version: nobody compiles hops to recursive SQL today, but for a bounded, rights-filtered, chunked-seed reachability the recursive CTE is the one-round-trip shape that works on every vfs dialect with a dedupe-on-node and a depth-in-WHERE guard, and the per-hop frontier loop is the universal fallback.
