# Engines check a deadline at loop bottoms, not per item, and the counter test costs more than the clock

This is study 02 of the folder whose brief is [00-brief.md](00-brief.md), on how database and search engines bound a long statement in time, how often they look, where the look sits in the code, and how a partial result is reported. The time box was 45 minutes, started 22:41 EST on 2026-11-07 by `date`; the four clones were refreshed and read, both experiments had run (their output files are stamped 22:44 and 22:45), and this file was complete with every section at 22:47 by `date`, well inside the box; the remaining time was not used. The finding, stated up front: all four engines store an absolute deadline (or a flag set by a timer at that deadline) in one place, check it at the bottom of a loop over a unit of work rather than inside the innermost step, and report an early stop as a classified result the caller already expects (an error code, an exception caught one frame up and turned into a flag, or a counter on the stats record). None of them lets each hot loop invent its own cadence constant; SQLite and Lucene each own the cadence in one helper, Postgres owns the check in one macro but places it by hand at 327 sites, and zoekt relies on Go's context and polls once per document. On this machine, in CPython, the per-item `i & 63 == 0` test costs more than the clock read it guards, and a chunked loop that reads the clock once per chunk with no per-item test is within noise of the bare loop.

## 1. SQLite: one `isInterrupted` flag plus one opcode counter, checked at the bottom of every loop opcode, not on every opcode

READ `src/main.c:1929-1939`: `sqlite3_interrupt()` does one thing, `AtomicStore(&db->u1.isInterrupted, 1)`. There is no deadline inside SQLite; the caller owns time and sets the flag from another thread, or returns non-zero from the progress callback. `sqlite3_progress_handler()` at `src/main.c:1842-1864` stores three fields on the connection: `xProgress`, `nProgressOps` (the cadence, in virtual-machine instructions), `pProgressArg`. So the bound is a relative budget expressed in operations, owned by the connection, and the only time-keeping is whatever the callback does.

READ `src/vdbe.c:993`: `nVmStep++` once per executed opcode. READ `src/vdbe.c:938-944`: at entry to `sqlite3VdbeExec` the next firing point is computed as `nProgressLimit = nProgressOps - (iPrior % nProgressOps)`, so the cadence survives across `sqlite3_step()` calls rather than restarting at each row returned. READ `src/vdbe.c:1134-1166`, quoted because the placement rule is stated in the source: "Opcodes that are used as the bottom of a loop (OP_Next, OP_Prev, OP_VNext, or OP_SorterNext) all jump here upon completion. Check to see if sqlite3_interrupt() has been called or if the progress callback needs to be invoked. This code uses unstructured goto statements and does not look clean. But that is not due to sloppy coding habits. The code is written this way for performance, to avoid having to run the interrupt and progress checks on every opcode. This helps sqlite3_step() to run about 1.5% faster according to valgrind --tool=cachegrind." The label `check_for_interrupt` reads the flag with `AtomicLoad`, then a `while (nVmStep>=nProgressLimit && db->xProgress!=0)` loop advances `nProgressLimit += nProgressOps` and calls the callback. EXECUTED `grep -n 'check_for_interrupt' src/vdbe.c`: the label is reached by `goto` from eleven opcode sites (`OP_Goto`, `OP_Yield`, `OP_SeekScan`, `OP_Rewind`, `OP_SorterNext`, `OP_Prev`, `OP_Next`, `OP_IfPos`, `OP_DecrJumpZero`, `OP_VNext`, and the exit path at `src/vdbe.c:9446`), and the loop at `9446-9453` fires the callback once more on the way out so a statement that ends between firings still reports.

READ `src/vdbesort.c`: EXECUTED `grep -n -i 'interrupt\|progress' src/vdbesort.c` returns nothing. The sorter does not read the flag itself; `OP_SorterNext` jumps to `check_for_interrupt` (`src/vdbe.c:6553-6605`), so the sorter's cadence is the VM's. The btree reads the flag in two places, both outside the VM loop: `src/btree.c:10549` the `sqlite3BtreeCount` page walk tests `!AtomicLoad(&db->u1.isInterrupted)` in its `while` condition once per page, and `src/btree.c:10623-10642` `checkProgress()` for `PRAGMA integrity_check` reads the flag and fires the callback when `(pCheck->nStep % db->nProgressOps)==0`, counting its own steps because no opcode runs there. The parser side has the same shape in `src/util.c:218-237` `sqlite3ProgressCheck(Parse*)`, called from four planner loops (`select.c:2350`, `vdbeaux.c:639`, `where.c:3058`, `where.c:3594`), with its own `nProgressSteps` counter against the same `nProgressOps`; the docs page records that this was added in 3.41.0 so the callback "might also be invoked directly from sqlite3_prepare()". Two more one-off reads sit in the tokenizer loop (`src/tokenize.c:665`) and the WAL checkpoint frame loop (`src/wal.c:2308`). EXECUTED `grep -rc isInterrupted src/*.c`: 17 mentions across nine files, of which seven are reads in loops and the rest are set and clear sites.

READ, reporting: every read site turns the stop into `SQLITE_INTERRUPT` on the statement (`src/vdbe.c:9484-9486 abort_due_to_interrupt`), the integrity check records it as an error row with `mxErr = 0`, and the parser sets `pParse->rc`. There is no partial row set: `sqlite3_step()` returns the error and the rows already returned stand. READ <https://sqlite.org/c3ref/progress_handler.html>: "The parameter N is the approximate number of virtual machine instructions that are evaluated between successive invocations of the callback X", "If the progress callback returns non-zero, the operation is interrupted", "This feature can be used to implement a Cancel button on a GUI progress dialog box", and "The progress handler callback must not do anything that will modify the database connection". The cost was measured once and recorded in the source comment: 1.5% under cachegrind for moving the check from every opcode to loop bottoms. Summary for the table: relative budget in ops on the connection; cadence a constant the caller chooses; one label in the VM owns the check, three counter-owning helpers outside it; stop is an error code; cost measured.

## 2. Postgres: a timer sets a flag at the deadline, and `CHECK_FOR_INTERRUPTS()` is one macro placed by hand at 327 sites

READ `src/backend/tcop/postgres.c:5384-5399` `enable_statement_timeout()` calls `enable_timeout_after(STATEMENT_TIMEOUT, StatementTimeout)` once per statement at `postgres.c:2901`, and `disable_statement_timeout()` at `2916`. READ `src/backend/utils/misc/timeout.c:560-575`: `enable_timeout_after` reads `GetCurrentTimestamp()` once, computes an absolute `fin_time = now + delay_ms`, stores it in `all_timeouts[id].fin_time` (`timeout.c:37-38,192-193`), and `schedule_alarm` arms one `setitimer(ITIMER_REAL)` for the nearest `fin_time` of all active timeouts (`timeout.c:239,339`). So the deadline is absolute and lives in a table owned by the timeout module, one entry per timeout kind, never passed through the executor. READ `timeout.c:303-309`: the module deliberately avoids a `setitimer` per statement, "roughly once a second, rather than thousands of setitimer() calls per second", which is the only cost discussion in the file.

READ the chain on expiry: `timeout.c:364-435` `handle_sig_alarm` runs the handler of every timeout whose `fin_time <= now`; `src/backend/utils/init/postinit.c:1415-1431` `StatementTimeoutHandler` sends `SIGINT` to its own process; `postgres.c:3155-3168` `StatementCancelHandler` sets `InterruptPending = true; QueryCancelPending = true` and `SetLatch`. The worker never reads a clock in its hot loops; it reads one global boolean.

READ `src/include/miscadmin.h:113-129`: `INTERRUPTS_PENDING_CONDITION()` is `unlikely(InterruptPending)` and `CHECK_FOR_INTERRUPTS()` is `if (INTERRUPTS_PENDING_CONDITION()) ProcessInterrupts();`. One macro owns the check; its fast path is one load and one predicted branch. READ `postgres.c:3575-3615` `ProcessInterrupts`: when `QueryCancelPending` it reads both timeout indicators, reports whichever finished first, and raises `ereport(ERROR, ERRCODE_QUERY_CANCELED, "canceling statement due to statement timeout")`. The report is an error that unwinds the statement; the rows already sent to the client stand, nothing marks them partial.

READ placement. `src/backend/executor/execProcnode.c:494`: `ExecProcNodeFirst` calls `CHECK_FOR_INTERRUPTS()` once per tuple pulled through a plan node (the brief named `execMain.c ExecutePlan`; EXECUTED `grep CHECK_FOR_INTERRUPTS src/backend/executor/execMain.c` finds no site there in this tree, the per-tuple check lives in the node dispatch). `src/backend/access/heap/heapam.c:722-727`, quoted: "Be sure to check for interrupts at least once per page. Checks at higher code levels won't be able to stop a seqscan that encounters many pages' worth of consecutive dead tuples." That comment is the placement rule: a check at the per-tuple layer is not enough when a lower loop can spin without producing a tuple, so the lower loop carries its own. `src/backend/commands/vacuum.c:2484-2500` `vacuum_delay_point()` wraps the macro with the cost-based sleep and is itself called from 25 sites (EXECUTED count). EXECUTED counts: `CHECK_FOR_INTERRUPTS()` appears 327 times in 148 files under `src/backend`, 64 in `executor/`, 66 in `access/`, 426 across `src` and `contrib`. Summary for the table: absolute deadline in the timeout table, converted to a flag by a signal; cadence is "every unit of work at every layer that can loop", a per-site judgement with no constant; one macro owns the test, hundreds of hand placements; stop is an error; the only measured cost is the setitimer rate, the check itself is a predicted branch and never discussed as a cost in the files read.

## 3. zoekt: Go's context carries the absolute deadline, polled once per shard and once per document, and the stop is a counter on Stats

READ `api.go:1050-1055`: `SearchOptions.MaxWallTime` and `FlushWallTime` are `time.Duration` values, relative budgets on the request. READ `search/shards.go:1014-1021` `withMaxWallTime` turns the budget into an absolute deadline once, `context.WithTimeout(ctx, opts.MaxWallTime)`, at the two request entry points (`shards.go:897,950`), with the comment that it is applied "when the request arrives so time spent waiting for the scheduler counts against it". From there the deadline travels as `ctx`, never as a number, and nothing below reads a clock to compare against it.

READ `index/eval.go:150-155` and `204-211,263-271`, the only two `ctx.Done()` polls in the whole `index/` package (EXECUTED `grep -rn 'ctx.Done()\|ctx.Err()' index/*.go` excluding tests returns exactly these two). The first, before any work, bumps `res.ShardsSkipped++` and returns an empty result with no error. The second sits at the top of the `nextFileMatch:` document loop as a non-blocking `select`, sets a local `canceled`, and the loop body then checks `if canceled || shardMaxMatchCountReached` and breaks, adding `docCount - nextDoc` to `res.FilesSkipped` and, when the cause was cancellation, to `res.FilesSkippedDueToCancellation`. The cadence is therefore once per candidate document, never per match or per line within a document, and the per-shard poll before the match tree is built is the coarse one. A document whose regexp verification is slow finishes before the next poll; nothing inside the content provider reads the context.

READ reporting: `Search` returns `(&res, nil)`, a result with counters, not an error. `api.go:409-412` `ShardsSkipped` is "Shards that we did not process because a query was canceled", and `FilesSkipped`/`FilesSkippedDueToCancellation` carry the per-document count. `FlushReason` (`api.go:350-360,441-442`) is a separate signal about the streaming aggregator: READ `search/aggregate.go:137-146`, a goroutine waits `FlushWallTime` on a `time.Timer` and calls `stopCollectingAndFlush(FlushReasonTimerExpired)`, so `FlushReason` says why the first batch was sent (timer, final flush, max size), not that the search was cut short. `Stats.Add` at `api.go:473-476` keeps the first non-zero `FlushReason` sticky across shards. No comment in the files read discusses the cost of the poll; a non-blocking `select` on a done channel is the idiom and is not treated as a cost. Summary for the table: relative budget on the request, absolute deadline inside `ctx`; cadence per shard then per document, a fixed unit, no constant; the language owns the check, each loop writes the two-line `select`; stop is counters on the result, no error; cost not discussed.

## 4. Lucene: `QueryTimeout` holds an absolute `nanoTime` deadline, the bulk scorer checks it per chunk with a chunk that grows by half, and the searcher turns the exception into a `timedOut()` flag

READ `lucene/core/src/java/org/apache/lucene/index/QueryTimeoutImpl.java:29-60`: the deadline is `timeoutAt = nanoTime() + timeAllowed`, absolute, stored once in a small object; `shouldExit()` is `timeoutAt != null && nanoTime() - timeoutAt > 0`. `QueryTimeout.java:25-33` is the one-method interface `boolean shouldExit()`, so a caller can substitute a flag, a counter or a test double. `IndexSearcher.java:89,613` holds one `QueryTimeout` per searcher.

READ `lucene/core/src/java/org/apache/lucene/search/TimeLimitingBulkScorer.java`, quoted: "We score chunks of documents at a time so as to avoid the cost of checking the timeout for every document we score. static final int INTERVAL = 100;" and in `score()`: `newMax = min(min + interval, max)`, `newInterval = interval + (interval >> 1); // increase the interval by 50% on each iteration`, with an overflow guard, then `if (queryTimeout.shouldExit()) throw new TimeExceededException();` before delegating `in.score(collector, acceptDocs, min, newMax)`. So the cadence is adaptive by document count: 100, 150, 225, 337, and so on, within one leaf, restarting at 100 for each leaf. The wrapper is the only place in the scoring path that reads the clock; the inner `BulkScorer` loop carries no test at all. The check sits above the inner loop, between chunks, which is the shape the experiment in section 5 finds cheapest. EXECUTED `git log --follow -p` on the file: the comment about avoiding the per-document cost and the 50% growth rule were both in the file's first revision in this history; no measurement is recorded in the source, the comment states the intent.

READ `IndexSearcher.java:846-861`: when a timeout is set, `scorer = new TimeLimitingBulkScorer(scorer, queryTimeout)`; the `catch (TimeExceededException) { partialResult = true; }` sits one frame up and the leaf collector's `finish()` still runs, so the hits already collected on that leaf are kept and the search continues to the next leaf (which will throw on its first chunk and also be marked). `timedOut()` at `648-650` returns the volatile `partialResult`, and the comment at `90-93` explains the volatile is for visibility across executor threads. `TimeExceededException` overrides `fillInStackTrace()` to return `this`, "never re-thrown so we can save the expensive stacktrace", the one explicit cost note on the stop path. READ the second placement, `lucene/core/src/java/org/apache/lucene/index/ExitableDirectoryReader.java:73,127-259`: `DOCS_BETWEEN_TIMEOUT_CHECK = 1000`, a fixed cadence on the postings and points iterators (EXECUTED: 20 mentions in that file, each a `docToCheck = target + 1000` carry), throwing `ExitingReaderException` with the timeout's `toString()`. READ `TimeLimitingKnnCollectorManager.java:57-67` and `util/hnsw/HnswGraphSearcher.java:241,263,288,292`: the kNN path checks `shouldExit()` per visited graph node and marks `KnnResults` as partial. Summary for the table: absolute `nanoTime` deadline in one object; cadence 100 documents growing by half per chunk in the scorer, 1,000 fixed in the reader, per node in HNSW; one wrapper owns the scorer check; stop is an exception caught one frame up and turned into a flag with the partial hits kept; cost named as the motive, not measured in source.

## 5. Experiment on this machine: the clock costs about 16 ns, a per-item mask test costs more than the clock it guards, and a chunked loop is free

EXECUTED [experiments/02-engine-interrupt-cadence/clock_cadence.py](experiments/02-engine-interrupt-cadence/clock_cadence.py), output in [clock_cadence.out.json](experiments/02-engine-interrupt-cadence/clock_cadence.out.json), Apple M1 Pro, CPython 3.13.11, 1,000,000 iterations, medians of 7 runs, repeated three times. `time.monotonic()` alone, with the empty loop subtracted: 17.0, 15.4, 16.6 ns per call across the three runs; `time.get_clock_info("monotonic").resolution` is 41.7 ns. The bare loop (`acc += i`) runs at 27.0 ns per iteration. Ratios over the bare loop, three runs each: every item 3.06, 3.01, 2.94; every 64th item (`i & 63 == 0 and monotonic() >= deadline`) 1.73, 1.66, 1.67; every 1,024th item 2.09, 1.73, 1.76. The 64th and 1,024th cadences cost the same within noise, and the first run's 2.09 for the sparser cadence shows the noise band is wider than the sixteen-fold difference in clock reads. INFERRED: once the clock is read less than once per 64 items, the cost that remains is the per-item counter test itself, about 0.65 of a bare iteration in CPython bytecode, and no sparser constant buys anything.

EXECUTED [clock_cadence_chunked.py](experiments/02-engine-interrupt-cadence/clock_cadence_chunked.py), output in [clock_cadence_chunked.out.json](experiments/02-engine-interrupt-cadence/clock_cadence_chunked.out.json): same work shaped as Lucene shapes it, an outer loop over chunks that reads the clock once per chunk and an inner loop with no test. Ratios over bare: masked every 64th 1.58, masked every 1,024th 1.67, chunked by 64 1.07, chunked by 1,024 0.98. The chunked loop pays nothing measurable; the mask pays about 0.6 of the loop. The clock read itself at 16 ns per 64 items is a quarter of a nanosecond per item and is not where the money goes. Wall-clock numbers here are facts about this machine and are reported to compare shapes, not to set a budget.

## 6. The table and the agreement

| Engine | Where the bound lives | Cadence rule | Who owns the check, where it sits | How the stop is reported | Cost discussed |
|---|---|---|---|---|---|
| SQLite | `db->u1.isInterrupted` flag set by caller; `nProgressOps` op budget on the connection | constant N ops, caller-chosen, carried across `step()` calls | one VM label, reached by `goto` from loop-bottom opcodes; three counter helpers outside the VM | `SQLITE_INTERRUPT` error code, returned rows stand | measured: 1.5% cachegrind for loop-bottom placement |
| Postgres | absolute `fin_time` in the timeout table; `setitimer` sets `InterruptPending` | every unit of work at every layer that can loop, no constant | one macro, hand-placed at 327 backend sites | `ereport(ERROR)` query canceled, sent rows stand | setitimer rate discussed; the branch is `unlikely()` and not discussed |
| zoekt | relative `MaxWallTime` turned into `ctx` deadline once at request entry | per shard before work, then per document | the language's `ctx.Done()`, two `select` sites in `index/` | counters on Stats (`ShardsSkipped`, `FilesSkippedDueToCancellation`), no error | not discussed |
| Lucene | absolute `nanoTime` in `QueryTimeout`, one object per searcher | 100 docs growing by half per chunk; 1,000 fixed in reader; per node in HNSW | one wrapper `BulkScorer` above the inner loop | exception caught one frame up, `partialResult` flag, collected hits kept | named as the motive; stack trace elided |

INFERRED, what the four agree on. One: the bound is stored once, as an absolute instant or a flag that a timer flips at that instant, and no engine threads a number through its call tree; the hot loop sees a handle (`db`, a global, `ctx`, `QueryTimeout`) and asks it one yes-or-no question. Two: the check sits at the bottom of a loop over a unit of work (an opcode that closes a loop, a tuple, a page, a document, a chunk of documents), never inside the innermost step, and the engines that wrote down why (SQLite's 1.5%, Lucene's "avoid the cost of checking the timeout for every document") did so because the test was measurable there. Three: the layer below the obvious one also checks when it can loop without producing a unit (Postgres's dead-page comment, SQLite's btree count and integrity walk, Lucene's reader at 1,000 docs), so cadence is per unit per layer rather than one global count. Four: the stop is a result the caller already handles, not a new kind of thing; the rows or hits produced before the stop are kept and the caller learns "stopped early" from an error code, a caught exception turned into a flag, or a counter on the stats record, and in every case that record is minted in one place (one label, one `ereport`, one `catch`, one `break`). Five: the cadence constant is owned by whoever owns the check (SQLite's `nProgressOps`, Lucene's `INTERVAL` and `DOCS_BETWEEN_TIMEOUT_CHECK`), not by each loop. For vfs, where the brief reports 43 `monotonic()` reads and four names for "every 64th", a single `Deadline` helper would need to offer, in Python: construction from a budget that captures the absolute instant once; a `remaining()` for handing the rest to a Rust kernel; an `expired()` that is one comparison; and above all a chunking iterator (`for chunk in deadline.chunks(items, size)` or equivalent) so the hot loop is an inner loop with no test, because the experiment shows the per-item mask is the cost and the chunked shape is free. In Rust the same type would hold an `Instant`, offer `past()` and a `check_every(n)` counter, and the two existing helpers (`past` in `glob.rs:317`, the inline `is_some_and` in `verify.rs:207,232`) would collapse into it; Lucene's growing interval is worth copying as an idea only where a unit's cost is unknown, and a fixed chunk serves where it is known. The truncation record belongs beside the helper, minted once, as the four engines mint theirs once.

## What this study does not settle

It does not settle which chunk size vfs should use; the experiment shows 64 and 1,024 are indistinguishable in Python once the shape is chunked, and the right size is a per-stage question about how long one item can take, which is the Postgres dead-page argument applied to glob arms and grep bodies. It does not measure the Rust side; an `Instant::now()` on macOS is a vDSO-style read whose cost relative to a glob step was not timed here. It does not settle whether vfs should report a stop as an exception caught at the stage boundary (Lucene) or as a counter in the result (zoekt); both keep the partial rows, and the choice is about who the caller is. It did not study SQL Server, Oracle or MariaDB, whose query-timeout mechanisms sit in the client driver and were outside the box. It did not time Lucene's growing interval against a fixed one.

## One line

Store the deadline once as an instant behind a handle, check it between chunks of work in one helper rather than per item in every loop, keep what was produced, and mint the "stopped early" record in that same helper; on this machine the per-item counter test costs more than the clock read it guards, and a chunked loop costs nothing.
