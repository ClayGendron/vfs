## 2. trio: `CancelScope` holds an absolute float on the run's clock, the run loop expires deadlines once per tick, and a thread can only poll

READ, absolute or relative: `CancelScope` stores `_deadline: float` defaulting to `inf` (`src/trio/_core/_run.py:596`). A `relative_deadline` is accepted only as a constructor convenience and is converted on `__enter__`: `self._deadline = current_time() + self._relative_deadline` (`_run.py:620-623`). Reading `.deadline` on an unentered relative scope raises `RuntimeError("Unentered relative cancel scope does not have an absolute deadline.")` (`_run.py:808-812`), so the type refuses to let a relative value be mistaken for an absolute one. `move_on_at(deadline)` builds `CancelScope(deadline=deadline)`; `move_on_after(seconds)` builds `CancelScope(relative_deadline=seconds)`, and its docstring says "The deadline of the cancel scope is calculated upon entering" (`src/trio/_timeouts.py:14-57`). The clock is `trio.current_time()`, the runner's monotonic clock (`_run.py:204`). `current_effective_deadline()` returns the minimum over the active scopes, `-inf` when already cancelled and `inf` when no deadline is set, and its docstring names gRPC-style propagation as the reason it exists (`_run.py:2990-3014`).

READ, the thread hop: `trio.to_thread.run_sync` does not carry the deadline into the thread. It checks cancellation once on entry, then with `abandon_on_cancel=False` (the default) "ignores the cancellation and keeps going, just like if we had called sync_fn synchronously", and with `abandon_on_cancel=True` "immediately raises Cancelled. In this case the thread keeps running in background" with its result discarded, and "the limiter is only released after the thread has actually finished" (`src/trio/_threads.py:305-328`). The abort hook returns `Abort.SUCCEEDED` only when abandoning, else `Abort.FAILED` (`_threads.py:431-441`). The only cooperative channel into the thread is `trio.from_thread.check_cancelled()`, which the thread code must call itself, "to raise Cancelled at a suitable place" (`_threads.py:461-473`). The default thread limiter is `CapacityLimiter(DEFAULT_LIMIT)` with `DEFAULT_LIMIT = 40` (`_threads.py:56,137`).

READ, cadence: the run loop reads the clock once per iteration, after the I/O wait, and expires every scope whose deadline has passed from a heap: `now = runner.clock.current_time(); if runner.deadlines.expire(now)` (`_run.py:2771-2773`; `Deadlines.expire` at `_run.py:305-313`). Cost is one clock read per loop tick however many scopes exist. The `.deadline` docstring states the consequence: "the core run loop only checks for expired deadlines every once in a while. This means that in certain cases there may be a short delay between when the clock says the deadline should have expired, and when checkpoints start raising Cancelled" (`_run.py:785-803`). Delivery then happens at the task's next checkpoint, so the check cadence is the scheduler's tick plus the task's checkpoint density, not a per-item clock read.

READ, reporting: an early stop is the `Cancelled` exception with a `CancelReason(source="deadline")` recorded (`_run.py:626`), the scope's `cancelled_caught: bool` is set when the scope swallowed it (`_run.py:586,686-691`), and `fail_at`/`fail_after` convert the swallowed cancel into `TooSlowError` (`_timeouts.py:122-152`). There is no partial-result type; whatever the with-block accumulated in locals survives, and the caller reads `cancelled_caught` to know it stopped short.

READ, one value type: `trio.CancelScope`, accepted by `move_on_at`, `fail_at` and read by `current_effective_deadline()`. Code that needs the number gets a `float` on the run clock, never a `timedelta` or a relative seconds value.

## 3. anyio: the same `CancelScope` with the deadline as an absolute float, a `call_at` timer that sets the flag, and a worker thread that polls `check_cancelled()`

READ, absolute or relative: `CancelScope(deadline: float = math.inf)` where the parameter is "The time (clock value) when this scope is cancelled automatically" (`src/anyio/_core/_tasks.py:40-55`). `move_on_after(delay)` and `fail_after(delay)` compute `current_time() + delay` once at creation (`_tasks.py:173-175,213-216`); `move_on_at` and `fail_at` take the absolute value. `fail_at` raises `TimeoutError` only when `cancelled_caught and current_time() >= cancel_scope.deadline`, so a scope cancelled for another reason is not reported as a timeout (`_tasks.py:151`). `current_effective_deadline()` mirrors trio (`_tasks.py:219-232`).

READ, cadence: the asyncio backend does not poll the clock at all. On enter it arms `self._timeout_handle = loop.call_at(self._deadline, self._timeout)`, and `_timeout` calls `self.cancel("deadline exceeded")` once `loop.time() >= self._deadline` (`src/anyio/_backends/_asyncio.py:404-410`). A timer sets the flag; checkpoints read the flag.

READ, the thread hop: `run_sync_in_worker_thread` runs the thread under `CancelScope(shield=not abandon_on_cancel)` (`_asyncio.py:2623-2632`), so by default the host task is shielded from cancellation while the thread runs, and with `abandon_on_cancel=True` the host task leaves and the thread finishes alone. The thread may call `anyio.from_thread.check_cancelled()`, which walks the host task's scope chain and raises the backend's cancellation error if any unshielded scope has `cancel_called` (`src/anyio/from_thread.py:668-676`; backend `check_cancelled` at `_asyncio.py:2635-2644`). The default limiter is `CapacityLimiter(40)` (`_asyncio.py:3110`). The pool is anyio's own `WorkerThreadPool(max_idle_time=10)` of non-daemon threads; `shutdown()` enqueues a `None` sentinel behind any queued job "so submitted work can finish before the worker exits" and joins every worker, and `drain()` is registered through `threading._register_atexit` because "Regular atexit callbacks run after Python joins non-daemon threads" (`_asyncio.py:879-940,1034-1040`).

READ, reporting: `CancelledError` carrying the scope id, `TimeoutError` from `fail_after`, `cancelled_caught`, and the cancel reason string `"deadline exceeded"`.

READ, one value type: `anyio.CancelScope`; the deadline inside is a `float` on `get_async_backend().current_time()`.

## 4. tokio: `timeout` converts a `Duration` to an `Instant` at construction, the deadline is a timer, and the 128-operation budget is a fairness device that counts operations rather than reading a clock

READ, absolute or relative: `timeout(duration, future)` computes `Instant::now().checked_add(duration)` once and builds a `Sleep` for that instant (`tokio/src/time/timeout.rs:86-95`); `timeout_at(deadline: Instant, future)` takes the absolute value directly (`timeout.rs:165-171`). The stored form is always the absolute `Instant` inside `Sleep`.

READ, cadence of the deadline: there is none in the future's own loop; the `Sleep` is a timer-wheel entry and `Timeout::poll` polls the inner future first, then the delay (`timeout.rs:210-227`). `poll` also reads the cooperative budget before and after polling the inner future, and if the budget ran out during that poll it polls the delay with `coop::with_unconstrained` so that a future which exhausts the budget on every poll can still see its deadline fire; the comment calls the alternative "pathological" (`timeout.rs:213-249`).

READ, cadence of work: the cooperative budget is `Budget(Some(128))` per poll of a task, and the comment on `Budget::initial` says "The value itself is chosen somewhat arbitrarily. It needs to be high enough to amortize wakeup and scheduling costs, but low enough that we do not starve other tasks for too long. The value also needs to be high enough that particularly deep tasks are able to do at least some useful work at all. Note that as more yield points are added in the ecosystem, this value will probably also have to be raised." (`tokio/src/task/coop/mod.rs:104-117`). The module doc explains why it exists: Rust has no runtime that can preempt, so "this module provides an opt-in mechanism for futures to collaborate with the executor to avoid starvation" (`coop/mod.rs:3-30`). A long computation that touches no tokio resource opts in by calling `tokio::task::consume_budget().await` per unit of work; "The task will only yield if its entire coop budget has been exhausted" (`tokio/src/task/coop/consume_budget.rs:1-25`). The budget counts operations and never reads a clock; the deadline is a separate timer. One owner holds the counter, every loop calls the one tick function, and the budget, not the loop, decides when to stop.

READ, the thread hop: `spawn_blocking` runs on a separate pool whose default size is 512 threads (`tokio/src/runtime/builder.rs:324,607`) with a `KEEP_ALIVE` idle timeout of 10 seconds (`tokio/src/runtime/blocking/pool.rs:231`). Nothing crosses into the closure: "tasks spawned using spawn_blocking cannot be aborted because they are not async", abort can only prevent one from starting, and "runtime shutdown will wait indefinitely for all started spawn_blocking to finish running" unless `shutdown_timeout` is used (`tokio/src/task/blocking.rs:108-118`). `Runtime`'s `Drop` "waits forever" for blocking work; `shutdown_timeout(duration)` waits that long and `shutdown_background()` waits not at all and "may result in a resource leak" (`tokio/src/runtime/runtime.rs:39-46,457-494`). At shutdown a queued task is either run or dropped by its `Mandatory` mark (`pool.rs:187-226`). A closure that must respect a deadline takes an `Instant` or a `CancellationToken` by hand as an ordinary argument.

READ, reporting: `Result<T, Elapsed>`; `Elapsed` converts to `std::io::ErrorKind::TimedOut` (`tokio/src/time/error.rs:47,119-121`). On elapse the inner future is dropped, so partial results exist only if the future wrote them somewhere the caller holds.

READ, one value type: `std::time::Instant` is the absolute value every time API takes (`timeout_at`, `sleep_until`, `Sleep::deadline`); `Duration` is the relative form accepted only at the entry that converts it.

## 5. Go `context`: `WithDeadline` stores an absolute `time.Time`, a timer closes `Done`, the callee selects on `Done` where it chooses, and the Context travels as the explicit first argument

READ, absolute or relative: `WithDeadline(parent Context, d time.Time)` stores the absolute `time.Time` in a `timerCtx` and `WithTimeout(parent, timeout)` is one line, `WithDeadline(parent, time.Now().Add(timeout))` (`src/context/context.go:630-660,667-680,708-710`). A child deadline later than its parent's is ignored in favour of the parent's (`context.go:641`). `Deadline() (deadline time.Time, ok bool)` is readable and "Successive calls to Deadline return the same results" (`context.go:73-76`). If the deadline has already passed at creation the context is cancelled on the spot (`context.go:649-651`).

READ, cadence: a timer. `c.timer = time.AfterFunc(dur, func() { c.cancel(true, DeadlineExceeded, cause) })` (`context.go:657-659`) closes the `Done()` channel. The callee reads the channel wherever it chooses, the documented idiom being a `select` on `ctx.Done()` inside the loop (`context.go:86-100`). Reading a closed channel is not a clock read.

READ, the hop: the package doc rules that a Context is never hidden in state: "Do not store Contexts inside a struct type; instead, pass a Context explicitly to each function that needs it... The Context should be the first parameter, typically named ctx" (`context.go:38-44`). Goroutines share the same value; "Context's methods may be called by multiple goroutines simultaneously" (`context.go:70-71`). Across a process boundary nothing in the package crosses; gRPC does that below.

READ, reporting: `ctx.Err()` is `DeadlineExceeded` when the deadline passed and `Canceled` when cancelled by hand (`context.go:111-116,170-172`), and `Cause(ctx)` carries an optional reason. The two causes are distinct values so a caller can tell them apart.

READ, one value type: the `context.Context` interface, with `Deadline()`, `Done()`, `Err()` and `Value()`.

## 6. gRPC: the deadline is absolute at both ends and only the wire carries a relative timeout, re-derived from the absolute at each hop and rebuilt as an absolute on arrival

READ, the guide: a deadline is "a point in time past which a client is unwilling to wait for a response from a server"; a timeout "becomes a deadline when the application starts the call"; propagation is "supported by some gRPC implementations", on by default in Java and Go and explicitly enabled in C++; the deadline is converted to a timeout with the elapsed time subtracted before it is sent, which "shields your system from any clock skew issues"; a client failing on its deadline sees `DEADLINE_EXCEEDED`, a server sees the call cancelled and "is responsible for stopping any activity it has spawned"; for long work it says to "periodically check if the RPC that initiated it has been cancelled" and gives no number for how often.

READ, grpc-go's client hop: when the call's context has a deadline, `timeout := time.Until(dl)`; if `timeout <= 0` the call fails locally with `codes.DeadlineExceeded` before any header is sent; otherwise the `grpc-timeout` header is `grpcutil.EncodeDuration(timeout)` (`internal/transport/http2_client.go:633-641`). `EncodeDuration` rounds up to the coarsest unit that fits ("div does integer division and round-up the result", `internal/grpcutil/encode_duration.go:28-32`), so a hop never shortens the budget by rounding. The header is relative with a one-letter unit suffix (`H M S m u n`, `internal/transport/http_util.go:157-165`).

READ, grpc-go's server side: a received `grpc-timeout` is decoded to a `time.Duration` and the stream's context is immediately `context.WithTimeout(ctx, timeout)`, an absolute deadline on the server's own clock (`internal/transport/http2_server.go:452-456,535-537`), and a timer `TimeAfterFunc(timeout, ... t.closeStream(...))` closes the stream when it passes (`http2_server.go:600-608`). Any further outbound call from the handler re-derives a fresh `grpc-timeout` from that absolute deadline with the same `time.Until`, so each hop subtracts its own elapsed time and no clock is compared across machines.

READ, reporting: `ContextErr` maps `context.DeadlineExceeded` and `context.Canceled` to their status codes (`internal/transport/transport.go:872-876`), and the client reclassifies a received `Canceled` to `DeadlineExceeded` when its own deadline has already passed, with the comment "Our deadline was already exceeded, and that was likely the cause of this cancellation" (`http2_client.go:1326-1331`).

READ, one value type: in Go it is `context.Context`; on the wire it is the `grpc-timeout` header, and the two are never the same object: the absolute lives in memory, the relative lives only in flight.

## 8. An operation-counting experiment on cadence

EXECUTED: [cadence_overrun.py](experiments/01-runtime-deadline-primitives/cadence_overrun.py) runs a fake clock where every item costs a fixed number of ticks and the deadline is tick 1000, and counts clock reads and items run past the deadline for three patterns: a clock read before every item (trio's checkpoint shape, and `verify.rs:207` per body), a clock read before every 64th or 128th item (the vfs cadence, and tokio's budget shape), and a timer that sets a flag read per item (anyio and Go). Output is in [cadence_overrun.out](experiments/01-runtime-deadline-primitives/cadence_overrun.out). With items costing 1 tick, every-64 makes 17 clock reads against 1002 and overruns by 23 items; with items costing 7 ticks, every-64 overruns by 49 items and every-128 by 113; with items costing 50 ticks, every-64 overruns by 43 items and every-128 by 107, while the timer-flag pattern makes zero clock reads and overruns by zero items at every cost. No wall-clock number was produced and none is a budget.

INFERRED from the output: a count cadence bounds the overrun in items (at most N−1), never in time, because the time overrun is N−1 times the cost of one item and the item cost is whatever the data makes it (a 4 MB body, a 64-program glob row). Trio's docstring accepts exactly this kind of slack and names it. The timer-flag pattern is exact and free of clock reads but needs a second channel (a flag the timer can reach) to cross the hop, which is why anyio and Go, whose hop is in-process, use it, and why tokio's blocking pool and trio's threads, which cannot reach into the worker, do not.

## 9. INFERRED: what the five agree on for a Python-plus-Rust library, and where they part

INFERRED. They agree on four things. First, the stored deadline is absolute on one monotonic clock, and a relative timeout exists only at an entry point that converts it once: trio on `__enter__`, anyio and tokio at construction, Go in the one-line `WithTimeout`, gRPC "when the application starts the call". vfs already follows this rule in prose at `offload.py:28-30` and in code at `deadline_after`; the rule has no type to live in, so it is restated twenty times. Second, the relative form is re-derived from the absolute at each hop and never carried forward: gRPC's `time.Until(dl)` at send, grpc-go's `WithTimeout` on receipt, vfs's `deadline - monotonic()` at worker start. A type with `remaining()` on it is that derivation written once. Third, there is one explicit value that every API accepts and that is passed, never stored: `CancelScope`, `Instant`, `Context`, and Go writes the rule down ("first parameter, typically named ctx"). Fourth, stopping at the deadline is a distinct, classifiable outcome, told apart from a plain cancel wherever the system can: `source="deadline"`, `"deadline exceeded"`, `DeadlineExceeded` versus `Canceled`, and grpc-go's reclassification. None of the five returns partial results from the primitive itself; the caller keeps what it accumulated and reads a flag (`cancelled_caught`, `Err()`), which matches vfs's `(results, completed)` pairs.

INFERRED. They part on cadence, and the split follows where the clock can be read. The two in-process async runtimes with a timer (anyio, Go) let the timer set a flag and let the loop read the flag at a density the callee picks; the one with a tick (trio) reads the clock once per scheduler iteration and admits the slack; tokio reads no clock in the loop at all and uses a count, 128 operations, which it labels "somewhat arbitrarily" chosen and which bounds fairness, not time. Not one of them fixes a shared per-item clock cadence for a CPU loop, because none of them runs CPU loops under the runtime: every one of them gives up at the thread hop, where trio and anyio offer only a poll (`check_cancelled`) and tokio offers nothing. The pattern closest to the vfs question is tokio's `consume_budget()`: one owner holds the counter and the policy, every loop calls one tick function per unit of work, and the loop never names the number. For vfs, where the hot loops run on worker threads and in Rust kernels that already take an `Instant`, the systems agree on a single absolute-deadline value, converted once at the pyo3 boundary to an `Instant`, and the honest choice between the two cadence shapes is: a count-every-N tick owned by the deadline type (tokio's shape, slack bounded in items), or a flag set by a timer on the Python side and read by an atomic in the kernel (anyio's and Go's shape, exact, one more thread and one more field across the seam). The five systems do not pick between these for a worker thread; they are agreed only that the loop should not own the number.

## What this study does not settle

It does not settle which cadence shape vfs should take, nor a value of N; the experiment shows the two shapes' costs in operations and the sources show both in use, and the spec must choose. It does not settle who owns the thread pool, its width, or its shutdown rule; the reads record that trio and anyio run one default limiter of 40 tokens per run, that tokio runs one blocking pool of up to 512 threads per runtime that shutdown waits for by default, and that anyio joins its non-daemon workers after the queued work, but the pool question belongs to another researcher in this folder. It does not settle how a Rust kernel should receive a timer-set flag across pyo3, which no studied system does. It did not study Python's own `asyncio.timeout()`, Java's `Deadline` in grpc-java, or .NET's `CancellationToken`, which would be the next three sources for the same questions.

## One line

Every system studied keeps the deadline absolute in one explicit value that is passed and never stored, derives the remaining time from it at each hop, and classifies the stop as a deadline distinctly from a cancel; they split only on whether a loop reads a clock, counts operations or reads a flag set by a timer, and none of them fixes that cadence inside the loop.
