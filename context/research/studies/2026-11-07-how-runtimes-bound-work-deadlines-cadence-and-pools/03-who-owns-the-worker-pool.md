# The studied runtimes own one lazily made worker pool per process or per loop, size it by core count plus slack or by a flat token count, never by the caller, and a native engine that already parallelizes inside a call wants that Python pool narrow

This is researcher 03's study for [the brief](00-brief.md), on who owns the worker pool that carries CPU-bound work off the event loop, how wide it is, what its close does to work in flight, and whether a Python pool layered over a natively parallel runtime oversubscribes it. The time box was 45 minutes from 22:41 EST on 2026-11-07; the reading, the experiment and this write-up finished inside it, with every system in the brief covered and nothing cut. Every claim below is labelled EXECUTED, READ or INFERRED. The experiment's script and raw outputs are under [experiments/03-who-owns-the-worker-pool/](experiments/03-who-owns-the-worker-pool/).

## 1. CPython asyncio: the loop owns one lazy default executor, cores plus four capped at 32, closed without waiting, refused afterwards

READ. `Lib/asyncio/base_events.py:895-908`: `run_in_executor(None, ...)` reads `self._default_executor`, and when it is `None` constructs `concurrent.futures.ThreadPoolExecutor(thread_name_prefix='asyncio')` and stores it on the loop. The owner is the event loop object; the lifetime is from first use to `close()`. `asyncio.to_thread` (`Lib/asyncio/threads.py`) is a thin wrapper: copy the `contextvars` context and call `run_in_executor(None, ...)`, so it shares that one loop-owned pool.

READ. Width: `Lib/concurrent/futures/thread.py:174-182`, `max_workers = min(32, (os.process_cpu_count() or 1) + 4)` when the caller passes none. The comment gives the reason in two parts: the executor serves both "CPU bound task which releases GIL" and "I/O bound task", so it uses cores plus 4 for both, and it caps at 32 "to avoid consuming surprisingly large resource on many core machine". Threads are spawned lazily, one per submit while `len(self._threads) < self._max_workers` (`_adjust_thread_count`, lines 225-240), so an idle executor holds no thread until work arrives.

READ. Close versus shutdown are two different paths. `BaseEventLoop.close()` (`base_events.py:757-761`) sets `_executor_shutdown_called = True`, drops the reference and calls `executor.shutdown(wait=False)`: queued items still run (the worker loop at `thread.py:118-124` drains the queue before it sees the shutdown flag), running items finish, and nobody waits. `shutdown_default_executor(timeout=None)` (`base_events.py:606-633`) is the graceful path: it sets the same flag, runs `executor.shutdown(wait=True)` on a helper thread so the loop keeps ticking, awaits that with `asyncio.timeout(timeout)`, and on expiry warns "The executor did not finishing joining its threads within N seconds" and falls back to `shutdown(wait=False)`. `asyncio.run` calls it with `THREAD_JOIN_TIMEOUT = 300` seconds (`runners.py:76-77`, `constants.py:35`). `ThreadPoolExecutor.shutdown(cancel_futures=True)` (`thread.py:255-271`) is the only way to drop queued work; nothing cancels a running thread.

READ. After shutdown: `run_in_executor(None, ...)` calls `_check_default_executor()` (`base_events.py:563-565`), which raises `RuntimeError('Executor shutdown has been called')` once the flag is set, so a call after shutdown is refused and the loop never re-mints a default pool; the executor itself also refuses with `RuntimeError('cannot schedule new futures after shutdown')` (`thread.py:205-206`). An explicit `executor=` argument bypasses the flag and is the caller's own to manage. There is no discussion in asyncio of a native pool beneath; the cores-plus-four comment is the whole statement of the oversubscription posture: it assumes the GIL-releasing work is one thread deep.

## 2. anyio: one process-wide worker pool with 10-second idle retirement, one 40-token limiter per event loop, per-call override, work on cancellation is shielded or abandoned, never killed

READ. `src/anyio/_backends/_asyncio.py:879-1044`: `_threadpool = WorkerThreadPool()` is a module global, so the pool of threads is owned by the process, not the loop. `docs/threads.rst:170-178` states it: "worker threads are shared across event loops in a process. Closing an event loop does not stop its workers: they can be reused by another loop and exit automatically after being idle for 10 seconds." Each `WorkerThread` waits on its own two-slot queue with `timeout=self.pool.max_idle_time` (10 s) and retires itself when nothing arrived (`run`, lines 999-1030). A fork hook replaces the global with a fresh empty pool (`_reset_threadpool_after_fork`).

READ. Width: the pool has no width of its own; it grows one thread per concurrent submit and shrinks by idling. The bound is the `CapacityLimiter`, and `current_default_thread_limiter()` (lines 3106-3112) mints `CapacityLimiter(40)` lazily into a `RunVar`, so the limiter is per event loop (one run of `anyio.run`), and `docs/threads.rst:187-189` says so: "a maximum of 40 calls to run concurrently in each event loop". `run_sync(limiter=...)` (`src/anyio/to_thread.py`) takes a per-call limiter, and the docs note the default limiter "does not affect the default thread pool executor on asyncio", a plain statement that two bounded pools can coexist unknowingly.

READ. Cancellation and close. `run_sync_in_worker_thread` (lines 2614-2631) wraps the submit in `CancelScope(shield=not abandon_on_cancel)`: by default a cancelled host task waits for the thread to finish; with `abandon_on_cancel=True` the task returns at once and the thread keeps running, result discarded. The thread can only stop early by polling `from_thread.check_cancelled()` (`docs/threads.rst:200-204`). Loop close does nothing to the pool. At interpreter exit a `threading._register_atexit` hook calls `_threadpool.drain()`: idle workers are told to exit, busy workers "finish their submitted work before exiting", which the docs say "also applies to calls abandoned on cancellation" (`threads.rst:176-178`). `WorkerThreadPool.shutdown()` (lines 909-926) refuses to be called from a worker, queues a stop behind any queued job "so submitted work can finish before the worker exits", and joins every worker: wait, never cancel. A submit after `stopping` raises `RuntimeError("The worker thread pool is shutting down")` (line 896): refused, not re-minted. Since the pool is process-wide, "a call after loop close" is simply served by the same threads under the next loop's limiter.

READ. Trio backend difference: `threads.rst:180-182`, on Trio the workers are daemon threads and "interpreter shutdown can terminate its work before it finishes", so the abandon-versus-wait choice at process exit is the backend's, not the caller's.

## 3. trio: an unbounded process-wide thread cache, a per-run limiter of 40 chosen "out of the air", daemon threads, and a warning not to use it for CPU-bound work

READ. `src/trio/_core/_thread_cache.py:232-253`: `THREAD_CACHE = ThreadCache()` is a module global holding only `_idle_workers`, a LIFO dict; `start_thread_soon` pops an idle worker or starts a new one, and a worker that waits `IDLE_TIMEOUT = 10` seconds (line 128, "This value is pretty arbitrary") exits. Workers are `daemon=True` (lines 159-164); the docstring at lines 271-274 says "if your main thread exits, worker threads will automatically be killed", and the `fn`/`deliver` split exists to avoid spawning a thread too many in a submit-wait-submit loop (lines 290-300). The cache has no width: the width lives in the limiter.

READ. `src/trio/_threads.py:53-57`: `DEFAULT_LIMIT = 40` under the comment "I pulled this number out of the air; it isn't based on anything. Probably we should make some kind of measurements to pick a good value." `current_default_thread_limiter()` (lines 126-139) mints `CapacityLimiter(DEFAULT_LIMIT)` lazily into a `RunVar`, so it is per `trio.run`, and `to_thread_run_sync(limiter=...)` overrides it per call. anyio's 40 is this number carried across.

READ. The `to_thread_run_sync` docstring (lines 300-335) gives the cancellation contract: with `abandon_on_cancel=False` (the default) "the function ignores the cancellation and keeps going"; with `True` the call raises `Cancelled` at once and "the thread keeps running in background", its result discarded, with the limiter token "only released after the thread has actually finished", and "If trio.run finishes before the thread does, then the limiter release method will never be called at all." The same docstring warns: "You should not use this function to call long-running CPU-bound functions!", citing GIL convoy effects where CPU-bound threads starve IO-bound ones. Trio has no close for the pool at all: `trio.run` returning leaves the daemon threads to idle out or die with the process. No native parallel runtime beneath is discussed.

## 4. SQLAlchemy asyncio: no worker pool at all, because the blocking work is IO that the driver already awaits; the connection pool is bounded 5 plus 10 overflow

READ. `lib/sqlalchemy/util/concurrency.py:173-220`: `greenlet_spawn(fn, ...)` runs the synchronous SQLAlchemy core inside a greenlet on the loop thread; when that code reaches the driver, `await_()` switches back to the loop with a coroutine, the coroutine is awaited, and the greenlet resumes with the value. There is no thread and no pool because nothing in the path is CPU-bound enough to leave the loop: the slow part is the socket, and the async driver already yields there. The docs call the mechanism "controversial" against asyncio's every-IO-has-an-await philosophy but keep it (`doc/build/orm/extensions/asyncio.rst:556-566`). `AwaitRequired` is raised when a sync DBAPI is used and no switch ever happened (lines 213-219), which is the only guard against silently blocking the loop.

READ. `lib/sqlalchemy/pool/impl.py:258-276`: `AsyncAdaptedQueuePool` is `QueuePool` with an asyncio-adapted queue and no `threading.Lock`; it inherits `pool_size=5`, `max_overflow=10`, `timeout=30.0` (lines 75-77). The bounded resource is the connection, owned by the `Engine`; dispose drains and recreates it, as the 2026-08-25 memo already recorded. For this study the lesson is the null case: a library that does not run CPU work owns no thread pool, and its only width knob bounds the resource the engine beneath actually limits.

## 5. polars: one global rayon pool per process, `available_parallelism` wide, fixed before first use, and the guide tells callers that adding their own parallelism on top rarely helps

READ. `crates/polars-core/src/runtime.rs:213-220`: `pub static THREAD_POOL: LazyLock<ThreadPool>` built once with `ThreadPoolBuilder::new().num_threads(polars_config::config().max_threads())`. `crates/polars-config/src/lib.rs:30-35`: the width is `POLARS_MAX_THREADS` if set, else `std::thread::available_parallelism()` with a fallback of 4. The Python side (`py-polars/src/polars/meta/thread_pool.py`) exposes `thread_pool_size()` and documents the rule: the override must be set "before process start", "The thread pool is not behind a lock, so it cannot be modified once set", and "it is strongly recommended not to override this value as it will be set automatically by the engine." The owner is the process; the lifetime is the process; there is no close.

READ. `docs/source/user-guide/misc/multiprocessing.md:8-22`, section "When not to use multiprocessing": "Polars has been built from the start to use all your CPU cores... It is very unlikely that the multiprocessing module can improve your code performance in these cases", and when combined with another engine "they can compete for system memory and processing power, leading to reduced performance." The page's main teaching is that `fork` is unsafe once the rayon pool exists and `spawn` must be used. The guide does not mention Python `ThreadPoolExecutor` by name; the same page frames the only legitimate second layer as one around a single-threaded dependency, not around polars itself (lines 25-28).

READ. The pyo3 boundary in polars releases the GIL around rayon work with `py.detach` (formerly `allow_threads`): 9 call sites across `crates/polars-python/src` by count. Python threads that call polars concurrently therefore all land on the same process-wide rayon pool, which is exactly the shape vfs has.

## 6. pyo3's guidance: release the GIL around any rayon work, and expect Python-thread parallelism over a sequential kernel to roughly match a single Rust parallel call, not add to it

READ. <https://pyo3.rs/latest/parallelism> (read 2026-11-07): the page's example uses `ThreadPoolExecutor(max_workers=2)` to drive a sequential Rust kernel from two Python threads, and its benchmark table (mid-2020 machine) reads: rust_parallel 1.73 ms, rust_sequential 7.33 ms, rust_sequential_twice_with_threads 7.98 ms for twice the work, python_sequential 27.4 ms. The prose: "the Python threaded version is not much slower than the Rust sequential version" and "compared to an execution on a single CPU core the speed has doubled". On rayon: "You should always call detach in situations that spawn worker threads, but especially so in cases where worker threads need to acquire the GIL, to prevent deadlocks", with the deadlock sketched as "a rayon worker thread would block on acquiring the GIL while a thread that owns the GIL spins forever". The page takes no position on how wide a Python pool over a rayon kernel should be; its implicit model is that either layer, not both, supplies the parallelism.

READ. rayon's own default (`rayon-core-1.13.0/src/lib.rs:460-470`): the global pool is `available_parallelism()` wide unless `RAYON_NUM_THREADS` says otherwise, built lazily on first use and never shut down. vfs-core builds no pool of its own outside two tests (`glob.rs:729`, `verify.rs:562`), so `count_batch` (`verify.rs:196-210`, `par_iter` over the bodies) runs on rayon's global pool, 10 threads on this machine.

## 7. Executed experiment: Python threads over the rayon kernel add no throughput; past the core count aggregate throughput held within noise while per-call latency grew linearly

EXECUTED. Script [experiments/03-who-owns-the-worker-pool/oversubscription.py](experiments/03-who-owns-the-worker-pool/oversubscription.py), run twice with `uv run python` from the vfs checkout against the installed engine, read-only. Machine: Apple M1 Pro, `os.cpu_count() == 10` (8 performance, 2 efficiency cores), Python 3.13.11, rayon-core 1.13.0, rayon global pool 10 wide. Each width `N` in {1, 2, 4, 10, 20} starts a `ThreadPoolExecutor(max_workers=N)`; `N` Python threads release a barrier together and each calls `ContentMatcher.count_lines` on the same batch of 256 bodies of 1 MiB seeded random ASCII (256 MiB per call; 2 in 97 bytes a newline); the round's wall time is from release to the last result; three rounds per width, median reported; aggregate throughput is `N × 256 MiB / median`. Raw outputs: [output-literal.txt](experiments/03-who-owns-the-worker-pool/output-literal.txt) and [output-automaton.txt](experiments/03-who-owns-the-worker-pool/output-automaton.txt).

Rounds: N=1 [0.0948, 0.0881, 0.1034], N=2 [0.2244, 0.1956, 0.1787], N=4 [0.3499, 0.3654, 0.5339], N=10 [1.1252, 1.2283, 1.2184], N=20 [2.2597, 1.8792, 1.8829].

INFERRED. Reading: one Python thread already saturates the machine, because the kernel fans the 256 bodies over rayon's 10 threads inside that one call. Adding Python threads up to the core count held aggregate throughput flat on the CPU-bound pattern (2.64 to 2.74 GiB/s, with one 2.05 GiB/s dip at N=10 that N=20 did not repeat, so it is noise or scheduler jitter, not a trend) and gave a 17 percent rise on the bandwidth-bound literal (86 to 101 GiB/s), which is the efficiency cores and the between-body gaps being filled, not new parallelism. Past the core count (N=20, which is 20 Python threads queued on 10 rayon threads, 200 OS-thread-slots of demand on 10 cores) throughput held on the automaton (2.66 GiB/s) and dropped 16 percent on the literal (84.7 GiB/s); neither collapsed. The verdict for this machine is "held, did not degrade materially past the core count", which matches the measured note already written at `offload.py:103-108`. The cost of width shows up as latency, not throughput: median time for one call grew from 0.095 s alone to 1.22 s with ten co-submitters and 1.88 s with twenty, in step with fair sharing of one saturated pool. A wall-time deadline measured inside such a call therefore fires for reasons of queueing, not of the call's own work. These are machine facts about an M1 Pro, named as such, and not budgets.

## 9. What the systems agree on, and what that says for a library whose kernels already parallelize inside one call

INFERRED. Four points of agreement across the studied systems. First, the pool is minted lazily and owned by a long-lived scope, the process (anyio, trio, polars, rayon) or the loop (asyncio); no studied system mints a pool per client object or per call, and the per-call knob is a limiter token count, not a pool. Second, the width is a function of the machine or a flat small constant, never of the caller's batch: cores plus four capped at 32, available parallelism, or 40 tokens. Third, close never kills running work; the choices are wait with a timeout (asyncio's graceful path, anyio's drain and shutdown), do not wait but let it finish unobserved (asyncio `close()`, trio's abandon), or have no close at all (polars, trio's cache); refusing new submits after shutdown is the stdlib and anyio answer, re-use of a process pool is anyio's answer to loop close, and vfs's inline service is its own, already settled by the 2026-08-25 memo. Fourth, where a natively parallel engine sits beneath, the engine's own guidance (polars, pyo3's benchmark) is that one layer supplies the parallelism; a Python pool over it is for concurrency between callers, not for throughput, and the experiment here reproduced that: throughput at N=1 equalled throughput at N=10 within noise.

INFERRED. For vfs, whose `count_batch`, `judge_batch` and `chunk` kernels already `par_iter` over rayon's process-global pool, the Python pool's job is therefore only to keep the loop ticking and to let a few verbs' native calls interleave, and its width should express that: a small number of slots, not `cpu_count`, because every slot is a whole-machine rayon fan-out and the twentieth slot buys queueing latency, not work. Ownership follows the same logic: rayon's pool is per process and every Python slot lands on it, so a router pool and an engine-host pool of the same width are two gates over one resource, and the systems studied would own that gate once, at the longest-lived scope that can also own its shutdown, which for a library imported into an unknown host is the package (a lazily made module-level pool, like anyio's `_threadpool` and polars's `THREAD_POOL`), with the width a package constant and a per-call limiter token, not a per-router or per-host pool. The per-storage-host and per-router owners survive only if a spec wants their close to mean "my work is done", and the studied systems get that from a limiter whose tokens are released when the thread finishes (trio, anyio), not from owning threads. The spec decides; this study's reading is one process-wide lazily made pool, a few slots wide, with close semantics of "stop accepting, let running work finish" and a refused-or-inline rule chosen once.

## What this study does not settle

What width "a few slots" is on a machine other than this one, and whether efficiency cores change it; the experiment ran one kernel on one laptop and the 17 percent rise on the literal pattern suggests small gains up to the core count that a different kernel may not show. Whether rayon's `RAYON_NUM_THREADS` should be read or set by vfs, or whether vfs should build its own named rayon pool as polars does, so the Rust width is a declared fact rather than rayon's default. Whether the free-threaded CPython build changes the per-call thread tax or the queueing shape. How a package-level pool should behave under `fork` (anyio and polars both install a fork hook; vfs has none). Whether the ten-second idle retirement of anyio and trio matters for a library that may hold a pool for the host's lifetime. Whether the 10 s wall-time budget should be measured from submit or from the moment the kernel starts, given that ten co-submitters raised one call's latency thirteenfold with no change in work done.

## One line

Every studied runtime owns one lazily made pool at process or loop scope, sizes it by the machine or a flat token count and never by the caller, lets running work finish at close, and, where a rayon engine sits beneath, treats the Python pool as a concurrency gate rather than a source of throughput, which this machine confirmed: one call saturates ten cores and twenty Python threads over it buy latency, not work.
