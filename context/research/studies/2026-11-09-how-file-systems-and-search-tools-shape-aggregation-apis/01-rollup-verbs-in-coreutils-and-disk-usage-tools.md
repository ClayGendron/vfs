## 1. uutils `du`: one walk, one `Stat` per directory, and the measure, the depth, the threshold and the summary are all decided in the printer

READ. The verb's per-node record is `Stat` at `src/uu/du/src/du.rs:127-135`: `path`, `size` (apparent bytes, zero for a directory, line 33 of `Stat::new`), `blocks` (512-byte allocated blocks), `inodes` (starts at 1), `inode` (an optional `FileInfo` of device id and file id), the `Metadata`, and `latest_time`. The walk is `safe_du` at lines 385-640: it recurses into each child directory, receives the child's finished `Stat`, and adds `size`, `blocks` and `inodes` into its own while taking the maximum of `latest_time` (lines 603-611); a plain file adds its `size` and `blocks` and one inode (lines 616-619). `-S`/`--separate-dirs` skips the add for subdirectories (line 602), so the same walk yields "this directory's own files" instead of the subtree. Hard links are counted once through the `seen_inodes` set unless `-l`/`--count-links` (lines 572-576), and `-x` stops at a different `dev_id` (lines 581-586).

READ. Every finished `Stat` is sent with its depth over a channel to a printing thread (`print_tx.send(StatPrintInfo { stat, depth })`, lines 612-615 and 1240). `StatPrinter::print_stats` at lines 924-955 is where the grain lives: it adds depth-0 items into `grand_total`, then prints a row only if the threshold does not exclude it, `depth <= max_depth`, and `!summarize || depth == 0`. The walk is never shortened by `--max-depth`, `--summarize` or `--threshold`; those filter rows, so the number printed for a depth-1 directory is the full subtree. `--summarize` with `--max-depth` is refused outright (`DuError::SummarizeDepthConflict`, lines 821 and 1392). `--total`/`-c` prints the grand total as a final row whose path column is the word `total` (lines 950-953). Output is `size\t[time\t]path` per row (lines 991-1013); there is no structured output.

READ. The measure is a parameter of the printer, not of the walk: `choose_size` at lines 912-921 returns `inodes` under `--inodes`, `size` under `--apparent-size` or `-b`, otherwise `blocks * 512`. So `du --inodes` is a count rollup and `du --apparent-size` a byte rollup over the identical walk and the identical `Stat`, and `--time` turns the max of mtimes into a second column. `--threshold` is signed (lines 1656-1679): `-1M` excludes rows larger than the value (`Threshold::Upper`), `1M` or `+1M` excludes rows smaller (`Threshold::Lower`), and `-0` is rejected as GNU does. `--files0-from` reads the operand list from a file, the batch-input shape.

INFERRED. The design the printer embodies is the one the brief's rollup columns need: one walk carries several measures (bytes apparent, bytes allocated, inode count, newest time) at once, and depth is a display cut, so a depth-1 row is exact for the whole subtree. The grand total is a row, not a footer, labelled by a reserved path value; a program consuming it must know the word `total`.

## 2. uutils `wc`: a five-field count record with a sum that is not a sum, and a `--total` mode that chooses whether the total row, the per-file rows or both appear

READ. `WordCount` at `src/uu/wc/src/word_count.rs:10-16` is `bytes`, `chars`, `lines`, `words`, `max_line_length`; its `Add` sums the first four and takes the maximum of the fifth (lines 18-29), which is exactly the rollup rule a total line needs and the reason a total record is a type and not a loop over integers. `--total={auto,always,only,never}` is the `TotalWhen` enum at `wc.rs:318-347`: `auto` shows the total row only when there is more than one input, `only` shows the total and hides every per-file row (the number width collapses to one and `are_stats_visible` is false, lines 972-975), `never` hides the total. The total row is the per-file formatter run on the summed record with the title `total` (lines 1065-1071). Column width is computed before any row is printed by summing file sizes from metadata (`compute_number_width`, lines 794-830), so the layout itself needs the aggregate first. `--files0-from` takes the batch of paths from a file or stdin (lines 131-187).

EXECUTED (`experiments/01-rollup-verbs-in-coreutils-and-disk-usage-tools/wc.txt`). On this Mac, `find src/ -type f -name "*.py" | xargs wc -l | tail -5` ends in `39158 total` after 94 per-file rows; `find context/ -type f -name "*.md" | xargs wc -lwc | tail -3` ends in `138537 2389171 17130383 total`; the BSD `wc` rejects `--files0-from` (`wc: illegal option -- -`), so that batch shape is GNU and uutils only; and `cat src/vfs/*.py | wc -l` prints `8478` alone, the shape a caller gets when it concatenates first and loses every per-file row.

INFERRED. `wc` is the one coreutil whose aggregation has an explicit "total only" mode, and that mode is what an agent that only wants the number asks for; the per-file rows and the total row are the same record type, which is the shape the brief's `total_lines` column would take on a directory observation.

## 3. GNU `tree`: `--du` is an option on the listing, the report is a typed trailing element in text, JSON and XML, and the total is a rollup of exactly what was listed, so `-L` and `-P` silently shrink it

READ. `struct totals { size_t files, dirs; off_t size; }` is at `tree.h:173-176`; each output mode installs a `report` callback (`unix_report`, `json_report`, `xml_report`, `html_report`, `tree.c:145-296`). The text footer is `unix.c:135-148`: `<size> used in N directories, M files` when `--du`, otherwise `N directories, M files`, and `-d` drops the file count. JSON emits a last array element `{"type":"report","size":…,"directories":…,"files":…}` (`json.c:189-194`), XML a `<report><size/><directories/><files/></report>` element (`xml.c:172-184`), and `--noreport` suppresses all three (`tree.c:375-377`). The sizes are apparent: each entry's `size` is `lst.st_size` (`tree.c:895`), and the per-entry `-s` column prints it (`tree.c:1560`).

READ. When `--du` is on, the whole tree is built first by `unix_getfulltree` (`list.c:88-89`), and a directory's size is the sum of its children's sizes (`if (flag.du) *size += (*dir)->size;`, `tree.c:1146`). The depth cut is inside that builder: `if (Level >= 0 && lev > (u_long)Level) return NULL;` at `tree.c:1053`, so `-L` stops the walk, not just the display. The pattern filter and `--prune` also act inside the builder (`tree.c:1127-1140` and the `patinclude` calls above it), so a filtered-out file is not in its parent's size. `--filelimit N` refuses to open any directory with more than N entries: the builder returns an error string `"%ld entries exceeds filelimit, not opening dir"` (`tree.c:1082-1083`), the lister marks it (`list.c:106-110`, `246-250`), and JSON writes the error inline as `{"error": "…"}` inside that directory's `contents` (`json.c:168-170`). In `list.c:101-105` a root that cannot be opened is counted as one file (`subtotal.files++`).

EXECUTED (`experiments/01-rollup-verbs-in-coreutils-and-disk-usage-tools/tree-du-json.txt`). The clone built with `make -j4 CC=cc` in 0.95 s wall in a scratch copy (`tree-build.log`). `tree --du -J -L 1 src/vfs` reports `{"type":"report","size":84822740,"directories":8,"files":16}` while its subdirectory entries show `"size":640` for `models` and `"size":288` for `embedding`, their own inode sizes; `tree --du -J -L 2 src/vfs` reports `"size":86096277,"directories":15,"files":87`. The sum of the 23 listed entries at `-L 1` plus the root's own 800 bytes is 84822740, so the root's `--du` size is the rollup of the visible set, 1.27 MB short of the depth-2 figure, and nothing in the report says the walk was cut. `-P "*.py"` at `-L 1` shrinks the report to `"size":354398,"files":13` and `--prune` to `"size":351454,"directories":1`: filtered entries leave the total. `--filelimit 10 -L 2` on `src/vfs` (23 entries) printed `[ 800]  src/vfs  [error opening dir]` and `800 used in 0 directories, 1 file`, and the JSON carried `"contents":[{"error": "error opening dir"}]` with `"files":1`: a refused root is reported as one file of 800 bytes. `tree -s -L 1` without `--du` prints every directory at its inode size (`[ 800]`, `[ 640]`), and `--noreport` drops the footer.

INFERRED. `tree` is the clearest precedent for the brief's typed stats block: a `report` record of the same output type as the rows, carried as the last element, with counts by kind and a byte total. It is also the clearest warning: because its rollup is of the listed set, `tree -L 1 --du` answers "how big is what you can see", not "how big is this directory", and the two differ by whatever the depth cut hid. A caller cannot tell them apart from the output. The brief's `tree(max_depth=1, columns={"total_bytes"})` must mean the whole subtree, which is `du -d 1`'s semantics, not `tree -L 1 --du`'s.

## 4. dust: a tree of `Node { size, children, depth }` built once, then the N biggest nodes anywhere under the depth ceiling, with the parent's exact total standing in for an "other" bucket

READ. `Node` at `src/node.rs:11-17` is `name`, `size`, `children`, `inode_device`, `depth`. The measure is fixed when the node is built (`node_from_tuple`, lines 70-108): `-F`/`--filecount` makes a file's size 1 and a directory's 0, `-m`/`--filetime` makes it a timestamp, otherwise it is the byte size (apparent under `-s`); a node that fails the regex or time filters gets size 0 but stays in the tree. The rollup is `clean_inodes` at `src/dir_walker.rs:152-188`: it drops any node whose `(inode, device)` was already seen unless apparent size is on, then sets a directory's size to its own plus the sum of its surviving children, or to the maximum when the measure is a time. So one tree serves bytes, counts and newest-time rollups, and the aggregation rule (sum or max) follows the measure.

READ. What is shown is chosen by `get_biggest` and `fill_remaining_lines` at `src/filter.rs:22-98`: a `BinaryHeap` ordered by size pops the largest node, admits it, and pushes its children only if `display_data.depth > node.depth` (`add_children`, lines 100-108); it stops when `number_of_lines` nodes are admitted. `-n`/`--number-of-lines` is therefore the budget and `-d`/`--depth` a ceiling, and the N biggest can come from different depths. The defaults are at `src/main.rs:155-170`: `number_of_lines` is the terminal height unless `-d` is given or `-j` JSON is on, when it becomes unlimited. `-z`/`--min-size` filters children, `-D`/`-F` restrict to directories or files, `--skip-total` drops the synthetic `(total)` root dust makes when given several arguments (`total_node_builder`, lines 56-64), and `--collapse` keeps a directory closed. The CLI is `src/cli.rs:13-193`.

READ. `-j` serialises `DisplayNode { size, name, children }` (`src/display_node.rs:10-14`) with `size` passed through `human_readable_number` for the `-o` output format (lines 46-58), so the JSON `size` is a formatted string such as `"81M"`, not a number; the file's own comment explains the thread-local `OUTPUT_TYPE` that makes this possible. The percent bars are each node's share of the root (`display.rs:75-80`). Nothing is cached between runs.

INFERRED. dust's grain is the brief's top-N, applied to a tree rather than to buckets: the budget is "N rows", and a directory whose children were not admitted still shows its exact total, so the difference between a parent and its shown children is an implicit "other" that the reader must compute. dust's JSON shows why the stats block must carry numbers: a human string in the structured output forces every consumer to parse units.

## 5. ncdu: cumulative size, shared size and item count on every `Dir`, an error bit that propagates up, a JSON export without totals and a binary export with them

READ. `Entry` at `src/model.zig:65-77` is a packed type with `etype`, `blocks` (512-byte) and `size`; `Dir` at lines 193-220 adds `shared_blocks`, `shared_size`, `items: u32` and the packed bits `dev`, `err`, `suberr`. The comment at lines 198-203 defines the two totals: `entry.{blocks,size}` is the space of all unique files and directories below (a hard link counted once), `shared_*` is the part of that which is also linked from outside this directory, and the space deleting the directory would reclaim is the difference. `err` means this directory could not be read, `suberr` means something below it could not; `updateSubErr` (lines 240-250) sets `suberr` from the children and the scan's `done` walks the parent chain so the bit reaches the root (`src/mem_sink.zig:203-205`).

READ. The totals are built bottom-up during the scan, not after: `mem_sink.Dir.addStat` adds one item and the file's blocks and size into the directory (`src/mem_sink.zig:115-121`), `final` adds the directory's accumulated counts into itself and then into its parent, minus its own entry so nothing is counted twice (lines 140-168). The progress counter divides a hard-linked file's bytes by `nlink` (`src/sink.zig:100`), and the browser can show an item-count column (`--show-itemcount`, `src/main.zig:225`). Refresh (`r` in the browser, `--enable-refresh`) rescans one directory: `createRoot` zeroes that directory's stats and rescans it (`src/mem_sink.zig:177-195`), then `done` adds the new totals back up every ancestor (lines 197-212). The man page says a shell command's completion refreshes only the selected item (`ncdu.1:376-380`), that hard-link counts drift between refreshes and need a full rescan (`ncdu.1:603-607`), and that sizes are clipped at 8 EiB and item counts are 32-bit (`ncdu.1:609-616`). Refresh and delete are disabled on an imported tree (`ncdu.1:82-84`, `277-280`).

READ. `-o file` writes JSON: one object per entry with `name`, `asize` (apparent), `dsize` (allocated, blocks converted to bytes), `dev` only when it differs from the parent, `ino`/`hlnkc`/`nlink` for hard links, `notreg`, and under `-e` `uid`/`gid`/`mode`/`mtime`; a directory is an array whose first element is that object and whose remaining elements are its children (`src/json_export.zig:179-222`). No cumulative field is written; the importer recomputes every total. The newer binary export (`src/bin_export.zig`, signature `\xbfncduEX1`, CBOR items in zstd blocks with a block index) stores per directory `cumasize`, `cumdsize`, `shrasize`, `shrdsize` and `items` (`ItemKey` 7-11 at lines 23-45) so a browser can open a directory without reading its subtree; `--export-block-size` and `-c`/`--compress` tune it (`src/main.zig:296-308`).

INFERRED. ncdu is the only project in this question that carries an explicit incompleteness signal, and it does so per directory with propagation: a total whose subtree had an unreadable directory is marked, and the mark reaches every ancestor. Its two export formats are the cleanest statement of when to store a rollup: a stream that will be fully re-read can leave totals out, a snapshot that will be browsed by random access must carry them. Its `shared_size` is a second rollup over the same walk that answers a different question (what deletion reclaims), a reminder that "total bytes" is one of several totals a directory can own.

## 6. macdirstat: `file_count` and `dir_count` cached on every node at scan, decremented when the app itself deletes, and the per-extension histogram rebuilt from scratch

READ. `FileNode` at `src/model/tree.rs:23-35` is `name`, `size`, `is_dir`, `children`, a treemap `rect`, `file_count` ("1 for files, sum of children for dirs") and `dir_count` ("0 for files, 1 + sum of children for dirs"). `build_node_fd` (lines 236-300) reads a directory in bulk through `getattrlistbulk` (one syscall stream per directory, `ATTR_FILE_TOTALSIZE` at `src/scan/getattrlistbulk.rs:28`), recurses into subdirectories in parallel with rayon when there are two or more, and sets the directory's `size`, `file_count` and `dir_count` from its files plus its children; children are sorted by size descending at build. `FileTree.extensions` (lines 69-76 and 85-125) is a histogram of extension to total bytes, accumulated in thread-local maps during the scan and merged once, with `(no ext)` as the bucket for extensionless files (lines 190-197).

READ. Invalidation is by the app's own actions only. `remove_child` subtracts the removed node's `size`, `file_count` and `dir_count` from the parent (lines 56-66), `subtract_from_ancestors` continues up to the root (lines 155-183), and after a delete `rebuild_extensions` recomputes the whole extension histogram (lines 186-193, called from `src/app.rs:387`). There is no file-system watcher and no persistent cache; the `cached_layout_rect` in `src/ui/treemap_view.rs` caches the drawing, not the counts.

INFERRED. The "cache" is a set of rollup columns stored on the node at build time and kept consistent by the one writer that exists, the app's delete. That is the in-memory shape of the brief's per-directory counters, including the asymmetry that the tree counters are adjusted incrementally while the group-by histogram is recomputed, because a histogram has no parent chain to walk.

## 7. The small `du`s: the verb's irreducible shape is a recursive sum returned to the parent, a depth that filters printing, `-s` as depth zero, `-c` as a row named `total`, and hard links deduplicated by device and inode

READ, plan9port `src/cmd/du.c` (194 lines). Options `-a`, `-s` (top level only), `-f`, `-n` (bytes, not blocks), `-t` (mtime), `-u` (atime), `-q` (qid), `-b blocksize`. `du()` (lines 66-139) reads the directory, adds `k(d->length)` for each file, recurses into each subdirectory and adds its return, prints `fmt` (`%llud\t%s\n`) per directory unless `-s`, and returns the total; a directory's own length is not counted. `-t`, `-u` and `-q` reuse the number column for a time or a qid, the oldest instance of "the measure is a flag over the same walk". `seen()` (lines 141-171) deduplicates by qid path, type and device through a small hash of `Dir`s. There is no depth, no threshold and no grand total.

READ, sbase `du.c` (116 lines). Options `-a`, `-s`, `-d depth`, `-h`, `-k`, `-H`/`-L`/`-P`, `-x`. The `recursor` callback (lines 36-50) computes `subtotal` from `st_blocks`, recurses into a directory, adds into the caller's total, and prints the root when `depth == 0`, otherwise prints a directory (or a file under `-a`) when `depth <= maxdepth`. `-a` with `-s` and `-d` with `-s` are usage errors (line 100). No `-c`.

READ, toybox `toys/posix/du.c` (165 lines). Options `-d N` ("Only depth < N"), `-a`, `-c`, `-s`, `-x`, `-H`/`-L`, `-l`, `-b`, `-h`/`-k`/`-K`/`-m`. The dirtree callback `do_du` (lines 93-146) returns `DIRTREE_COMEAGAIN` so a directory is visited after its children; it then adds its blocks into its own `extra` and its parent's `extra` (lines 132-137), adds the root into `TT.total`, and `print` (lines 50-67) returns early when `TT.depth > TT.d`, so depth filters printing after the full walk. `-c` prints `TT.total` with the name `total` (line 154). `seen_inode` (lines 71-91) deduplicates non-directories with `st_nlink > 1`.

READ, busybox `coreutils/du.c` (311 lines). Options `-a`, `-H`, `-L`, `-d N`, `-c`, `-l`, `-s`, `-x`, `-h`, `-m`, `-k`, `-b`. `du()` (lines 144-220) is the recursive sum; `-s` is implemented as `max_print_depth = 0` (line 287), rows print when `du_depth <= max_print_depth` (line 216), `-c` prints the summed operands as `total` (line 308), and an `ino_dev` hashtable deduplicates `st_nlink > 1` (lines 180-188). The header comment records that the 2003 rewrite exists so that "calculated sizes should now match gnu du output".

EXECUTED (`experiments/01-rollup-verbs-in-coreutils-and-disk-usage-tools/du-d1.txt`). The `src/vfs` figure is dominated by the 81 MB `_native.abi3.so`, which `tree --du` later confirmed at 84465520 bytes.

INFERRED. Across four codebases of 116 to 311 lines and two licences, the verb never varies in shape: the subtree measure is computed bottom-up and returned to the caller, the depth and `-s` decide which rows print and never how far the walk goes, `-c` is one more row named `total`, the apparent-versus-allocated switch changes the unit of the same number, and identity (device and inode) is deduplicated so a hard link counts once. None of them caches anything between runs.

## 8. nushell: `du` returns a table whose columns are the rollup, `--long` nests the children, and `histogram`, `group-by` and `uniq -c` are separate verbs that produce tables with no footer, no cap and no "other"

READ. `du`'s signature is `crates/nu-command/src/filesystem/du.rs:38-80`: rest `path` globs, `--deref`, `--long`, `--exclude`, `--max-depth`, `--min-size`, `--all`; the input type is `Nothing` and the output a table. Each directory row is the record `{ path, apparent, physical, directories, files }` (`crates/nu-command/src/platform/dir_info.rs:292-306`), where `apparent` and `physical` are `filesize` values and `directories` and `files` are nested lists present only under `--long`; a file row is `{ path, apparent, physical }` (lines 321-326). `max_depth` bounds how deep the nested `--long` listing goes, while the walk that fills `apparent` and `physical` is the whole subtree (`DirInfo::new` carries `max_depth` only to shape the children). Hard links are counted once per invocation across all operands (`du.rs:120-123`), and a path that errors becomes an error value in the stream rather than a stderr line (`du.rs:261`). `ls --du` replaces a directory's metadata size with its apparent disk usage (`crates/nu-command/src/filesystem/ls.rs:177`).

READ. `histogram` (`crates/nu-command/src/charting/histogram.rs:21-44`) takes an optional column name and frequency column name and `--percentage-type normalize|relative`; `histogram_impl` (lines 245-290) counts every distinct value in a `HashMap`, sorts by count descending, and emits one row per value with `count`, `quantile` (a float share of the total or of the maximum), `percentage` (a string such as `66.67%`) and `frequency` (a string of up to 100 asterisks). There is no size cap, no "other" bucket and no total row; the total is the sum of `count`. `group-by` (`crates/nu-command/src/filters/group_by.rs:20-35`) returns a record keyed by group, or with `--to-table` a table with one column per grouper plus `items`; `uniq --count` returns `{ value, count }` rows (`crates/nu-command/src/filters/uniq.rs:137-146`).

INFERRED. nushell removes the footer entirely: the listing verb returns typed rows, the aggregation verbs return typed rows, and `math sum` or `length` is the total. The cost is that nothing bounds the group-by: `histogram` materialises every distinct value, and top-N and "other" are the caller's `first 10` and arithmetic. The gain is that `apparent` and `physical` are columns of the same row as `path`, which is the brief's rollup-column shape with the walk unbounded by `--max-depth`.

## 9. PowerShell: `Measure-Object` streams one `MeasureInfo` per measured property with `Count` always filled and the rest null unless asked; `Group-Object` returns `GroupInfo { Name, Count, Group, Values }` and `-NoElement` drops the members

READ. `Measure-Object` (`src/Microsoft.PowerShell.Commands.Utility/commands/utility/Measure-Object.cs`) has two parameter sets: generic with `-Sum`, `-Average`, `-Maximum`, `-Minimum`, `-StandardDeviation`, `-AllStats` (lines 254-355), and text with `-Line`, `-Word`, `-Character`, `-IgnoreWhiteSpace` (lines 374-432); `-Property` takes property expressions with wildcards (lines 246-247). `ProcessRecord` (lines 480-493) folds each input into a `Statistics` accumulator per property (count, sum, running variance, min, max, characters, words, lines, lines 200-215), so memory is constant in the input. `EndProcessing` (lines 805-853) emits one `GenericMeasureInfo { Count, Average, Sum, Maximum, Minimum, StandardDeviation, Property }` or `TextMeasureInfo { Lines, Words, Characters }` per property; the numeric fields are nullable doubles (lines 40-60) and stay null unless their switch was given, while `Count` is a plain int that is always set. With no input and no property it emits zeros "to emulate wc behavior" (lines 809-813).

READ. `Group-Object` (`Group-Object.cs`) emits `GroupInfo` with `Name`, `Count`, `Group` (a `Collection<PSObject>` of the members) and `Values` (the grouping key values, lines 125-205); `-NoElement` substitutes `GroupInfoNoElement`, whose `Add` only increments `Count` (lines 107-118), so the members are never retained; `-AsHashTable`/`-AsString` return a hashtable instead (lines 237-249, 515-544); `-CaseSensitive` and `-Culture` govern key equality. There is no cap, no "other" bucket and no ordering guarantee beyond the input order; `Sort-Object Count -Descending | Select-Object -First N` is how a caller gets a top-N, and nothing then reports the remainder.

INFERRED. `Measure-Object` is the closest precedent for the brief's typed stats block: a record whose count is always present and whose heavier measures are present only when requested, computed in one streaming pass. `Group-Object -NoElement` is the count-only histogram, a verb over records rather than over a file tree. Both leave truncation and "other" to the pipeline, which is why a PowerShell top-10 of extensions does not know how many extensions it dropped.

## 10. Comparison: where the aggregation lives, what it measures, how it is cut, how it is shaped, how it says it is incomplete, what it caches, and whose rights it respects

Where it lives. Three placements recur. The rollup is the verb's own rows in every `du` (uutils, BSD, plan9port, toybox, busybox, sbase), in dust and in ncdu: a row is a directory and its number. It is an option on the listing plus a trailing report in GNU `tree` (`--du`, `-s`, the `report` element). It is a separate verb over records in nushell (`histogram`, `group-by`, `uniq -c`, `math sum`) and PowerShell (`Measure-Object`, `Group-Object`), with the listing verb returning typed rows that carry per-entry measures (`ls` size, nushell `du`'s `apparent` and `physical`). The brief's three layers map onto all three: the stats block is `tree`'s report and `Measure-Object`'s record, the rollup columns are nushell `du`'s columns and `du --inodes`'s number, and the histogram verb is `Group-Object -NoElement` and nushell `histogram` with the cap those two lack.

What it measures, over what unit. Bytes apparent and bytes allocated are universal and always a unit switch over one number (`--apparent-size`, `-A`, `-b`, dust `-s`, ncdu `asize`/`dsize`, nushell `apparent`/`physical`). Counts appear as a second measure over the same walk: `du --inodes`, dust `-F`, ncdu `items`, macdirstat `file_count`/`dir_count`, `tree`'s `directories`/`files`. Lines appear only in `wc` and `Measure-Object -Line`, never on a directory. Newest time is a max-rollup in `du --time` and dust `-m`. Distinct values are only in the shells (`histogram`, `uniq -c`, `Group-Object`). The unit is a subtree for the `du` family, the result set for `wc` and the shells, a bucket for the shells' group-bys, and ncdu adds a second subtree total, `shared_size`, for a different question.

How the grain is chosen. Depth, in two incompatible senses: a display cut after a full walk (every `du`, nushell `du`) or a walk cut (`tree -L`, dust `-d` as a ceiling on where the heap may look). A threshold on the row's value (`du -t`, signed in uutils and GNU; dust `-z`; nushell `--min-size`). A top-N (dust `-n`, the only tool that owns one; the shells leave it to `first`/`Select -First`). A summary flag that is depth zero (`-s` everywhere, `wc --total=only`). A group-by key (nushell column name, PowerShell property). No tool in this question offers a bucket width; numeric histograms are the shells' per-distinct-value tables.

Output shape and structured output. Text rows of `number\tpath` in every `du`, with the grand total a row whose path is the word `total` (`-c`), and `wc`'s `total` row likewise. A trailing typed element in `tree -J`/`-X`. A nested tree in dust `-j` and ncdu's JSON, with dust's size a human string and ncdu's a number. Typed records in nushell (`filesize` values, nested lists) and PowerShell (nullable fields). Only `tree`, dust, ncdu, nushell and PowerShell have structured output at all; the `du`s and `wc` have none.

Truncation. `tree --filelimit` is the only hard cap on reading, and it reports itself as an inline error element while leaving the unread directory out of the totals. dust's top-N leaves the remainder implicit in the parent's exact total. `wc --total=only` and `du -s` collapse rows but keep the exact total. The shells do not truncate. No tool reports exact versus lower-bound totals as such; the nearest is ncdu's `err`/`suberr` bit on every directory, and `tree`'s depth-cut total is a lower bound presented as a total.

On demand or maintained. Every coreutil, every small `du`, dust and nushell recompute on each call and cache nothing. ncdu and macdirstat build the totals bottom-up once into memory and adjust them for the one writer they know about (ncdu's refresh and delete, macdirstat's delete), with ncdu's binary export the only persisted rollup and its man page the only honest account of what drifts (hard-link counts) and what overflows (8 EiB, 32-bit items). Nothing watches the file system.

Rights and visibility. None of these tools has a rights model; what they have is "could not open". `du` warns on stderr and continues, so the total is of what it could read; `tree` writes an inline error and excludes the directory; ncdu sets `err` and propagates `suberr`; nushell emits an error value as a row. In every case the unreadable directory's existence is visible and its contents are absent from the number. The brief's posture, that a count must not reveal an entry the caller may not list, is stricter than anything here: these tools reveal the refused directory by name and leave its size out.

## 11. What vfs should adopt and what it should not

Adopt, from the `du` family and nushell `du` (READ, EXECUTED): compute the rollup columns over the whole subtree in one walk and let depth cut only the rows returned, so `tree(max_depth=1, columns={"total_bytes"})` is `du -d 1` and a depth-1 row is exact; carry several measures off that one walk (bytes, file count, directory count, newest time, and for vfs lines) the way `du --inodes` and `--time` and dust `-F` do, so the measure is the column the caller asks for and never a second traversal.

Adopt, from ncdu and PowerShell (READ): a per-row and per-result incompleteness signal shaped like ncdu's `err`/`suberr`, a bit that is set where a subtree could not be fully counted and propagates to every ancestor and to the result's stats block, so `exact` on the block is the root of that propagation rather than a guess; and a stats block shaped like `Measure-Object`'s record, counts always present, heavier measures present only when asked, filled in one streaming pass, and carried as a typed sibling of the rows the way `tree -J`'s `report` element is, never as a text footer.

Do not adopt, from GNU `tree` (EXECUTED): a directory size that is the rollup of the entries the listing happened to show. `tree --du -L 1` reported 84822740 bytes for `src/vfs` and `-L 2` reported 86096277 for the same directory, and `-P "*.py"` cut it to 354398, with no field saying the walk was cut; a number labelled as a directory's total that changes with the display depth or the filter is a lower bound wearing a total's name, and vfs's `total_bytes` must not be one.

## What this study does not settle

GNU coreutils' own `du` and `wc` were not cloned; uutils reimplements them and busybox's header says it matches GNU output, but the GNU source was not read. nushell and PowerShell were read, not executed: neither `nu` nor `pwsh` is installed here, so the record shapes are from source and tests, not from a run. dust and ncdu were not built: a Rust or Zig build with dependency fetch was not a safe bet inside the three-minute limit, so their outputs are READ from the serialisers rather than EXECUTED; macdirstat is a GUI and was not run. The cost of `getattrlistbulk` against `readdir` plus `stat` for a 10,000-entry directory was not measured. No tool in this question has a rights model, so how a rights-filtered count should behave when a subtree is partly hidden has no precedent here and is for the facet and database researchers.

## One line

Roll every measure up one whole-subtree walk and let depth, threshold and top-N trim only the rows; give every directory and every result an incompleteness bit that propagates upward; and never let a total shrink with the view the way `tree -L --du` does.
