# File-system libraries aggregate by summing a walk on demand, the filesystem-over-database peers that aggregate at all keep non-recursive per-directory counters and fold a top-N's tail into one named bucket, and the oldest aggregate a file system offers is already computed under the caller's rights

This is the study of Researcher 04 in the prior-art study described in [the brief](00-brief.md). The box opened at 08:32:34 EST on 2026-11-09 and the study was finished inside it; the closing time is in the last section. Every claim below is labelled EXECUTED (a command run here, output recorded under [experiments/04-aggregation-in-file-system-libraries-and-database-peers/](experiments/04-aggregation-in-file-system-libraries-and-database-peers/)), READ (a file cited by clone path and line) or INFERRED (reasoning from the two). No clone was modified and no code was copied; every description below is in my words.

The finding in one paragraph. The Python file-system libraries (fsspec, pyfilesystem2) offer one aggregate each, bytes summed over a walk, computed on demand with nothing cached, returned as a bare `int` or a three-field named tuple, with no truncation signal and no notion of rights (READ, EXECUTED). opendal offers none: it hands the caller a recursive lister and per-entry `content_length`, and the caller sums (READ). Of the filesystem-over-database peers, JuiceFS is the one that aggregates seriously: a non-recursive `(length, space, inodes)` counter per directory, updated by every metadata mutation in memory and flushed on a one-second ticker, read back with the pending deltas added, exposed as a `fast` default that the CLI itself labels possibly inaccurate and a `--strict` mode that re-walks; its `summary` verb takes `depth`, `entries` (top N) and `sort-by`, and folds everything past the top N into one child literally named `...` whose counts are the sum of what was folded, so the tree always reconciles (READ). MinIO's `ListObjectsV2` rolls up by prefix but measures nothing per prefix, caps the page at 1,000 keys the caller cannot raise, and reports `KeyCount` as rows returned, not rows existing; its real aggregate is a background scanner's cache, admin-only, stamped with `LastUpdate`, with a fixed-interval size histogram (READ). SeaweedFS's `fs.du` is a shell walk printing text, and its `Statistics` RPC is a volume-level number from the master, not a directory one (READ). The agent-facing peers (agentfs, mirage, afs, computer, eve) aggregate almost nothing: agentfs runs two whole-table SQL aggregates for `statfs` and fabricates the totals FUSE needs; mirage is the exception worth studying, since it implements GNU `du` and `df` over mounts as typed records and refuses to print a capacity it does not have (READ). POSIX `statvfs`, the smallest aggregate a file system has always offered, already splits `free` from `available to unprivileged processes`, and Linux ext4 clamps every one of its totals to the caller's project quota (READ).

## 1. fsspec: `du` is a sum over a walk, `int` or `dict`, depth is a filter that drops bytes, nothing cached

Where it lives. `du(path, total=True, maxdepth=None, withdirs=False, **kwargs)` is a method on `AbstractFileSystem` (READ, `fsspec/spec.py` lines 618-648); `disk_usage` is a one-line alias (READ, lines 1947-1949); `sizes(paths)` is a list comprehension over `size`, itself `info(path)["size"]` (READ, lines 822-828). The async mixin reimplements the same shape as `_du` (READ, `fsspec/asyn.py` lines 1062-1071) and the only backend override in the clone is `dirfs`, which prefixes paths and delegates (READ, `fsspec/implementations/dirfs.py` lines 395-403). There is no stats block on `ls` or `find`; aggregation is this one verb.

What it measures and how. `du` calls `find(path, maxdepth=..., withdirs=...)` without `detail`, so it gets names, then calls `info()` once per name and stores `info["size"]` in a dict; with `total=True` it returns `sum(dict.values())` as an `int`, else the dict `{path: bytes}` (READ, lines 638-648). INFERRED: this is one `walk` plus one `info` per entry, an N-plus-walk shape, because `find` already had the detail records and threw them away. `withdirs=True` adds the directories' own `st_size` (their inode size, not their contents): the docstring says a directory's size does not include its contents (READ, line 621). On the local backend `info` is one `os.stat` or `DirEntry.stat` per entry (READ, `fsspec/implementations/local.py` lines 79-125); the `ls` record has `name`, `size`, `type`, `created`, `islink`, `mode`, `uid`, `gid`, `mtime`, `ino`, `nlink` (EXECUTED, `fsspec_du.out`).

Grain. The only grain is `maxdepth`, and it is passed through to `find` as a walk cut-off, not a rollup depth. EXECUTED (`experiments/.../fsspec_du.py`, fsspec 2026.7.0, `uv run --with fsspec python -I`): over `src/`, `du(total=True)` returned `90199312`; `du(total=False)` returned a dict of 284 entries; `du(total=False, maxdepth=1)` returned an empty dict and `du(total=True, maxdepth=1)` returned `0`, because `src/` holds only the `vfs/` directory and no files at depth 1; `du(total=False, maxdepth=1, withdirs=True)` returned `{src: 96, src/vfs: 800}`, the two directories' inode sizes. INFERRED: fsspec's `maxdepth` is therefore not `du -d 1`; `du -d 1` would print `src/vfs` with 90 MB rolled up, and fsspec prints 0. A caller asking for a shallow total gets a smaller number with no signal that anything was cut.

Output and truncation. An `int` or a plain dict; no record type, no footer, no truncated flag, no exact-versus-estimate marker. Maintenance: none. `DirCache` caches directory listings with an optional expiry and `invalidate_cache(path)` clears listings at or under a path (READ, `fsspec/dircache.py` lines 6-60, `fsspec/spec.py` lines 364-376); it caches the inputs to `du`, never its result. Rights: none at this layer; the local backend reports whatever `stat` returns.

## 2. pyfilesystem2: `count()` is a terminal on a lazy glob query returning `Counts(files, directories, data)`

Where it lives. `fs.glob(pattern)` returns a `Globber`, a lazy query object; `count()` and `count_lines()` are terminal methods on it (READ, `fs/glob.py` lines 275, 345-388). The aggregate is a method on the query, not on the file system and not on the listing. `Counts = namedtuple("Counts", ["files", "directories", "data"])` and `LineCounts = namedtuple("LineCounts", ["lines", "non_blank"])` are module-level types (READ, lines 18-19).

What it measures. `count()` iterates the matches with the `details` namespace, increments `directories` or `files` by `is_dir`, and adds `info.size` to `data` for every match, directories included (READ, lines 357-366). `count_lines()` opens every matched file in binary mode and counts lines and non-blank lines (READ, lines 368-388), so it is a content read, not a metadata walk. `getsize` documents that a directory's size is the overhead bytes of its entry (READ, `fs/base.py` lines 781-799). The `Walker` yields `Step(path, dirs, files)` and takes `max_depth` (READ, `fs/walk.py` lines 41, 62, 251); `Info` wraps a raw dict of namespaces and exposes `size`, `is_dir` and `get(namespace, key)` (READ, `fs/info.py` lines 30-54, 87-108, 261, 378).

Grain. The glob pattern is the grain; there is no depth parameter on `count()` beyond what the pattern expresses (`**/*.py` versus `*/*.py`). EXECUTED (`experiments/.../pyfs_count.py`, fs 2.4.16, `uv run --no-project --python 3.12 --with fs --with "setuptools<80" python -I`, since the package imports `pkg_resources`, which the setuptools shipped for 3.13 no longer provides): over `src/`, `glob("**/*.py").count()` returned `Counts(files=94, directories=0, data=1657004)`; `glob("**").count()` returned `Counts(files=284, directories=18, data=90210096)`; `glob("**/").count()` returned `Counts(files=0, directories=18, data=10784)`; `getinfo("vfs", namespaces=["details"]).size` was `800`; `walk(max_depth=1)`'s first `Step` had 1 dir and 0 files. INFERRED cross-check: fsspec's `du(total=True, withdirs=True)` was `90210192` and pyfilesystem2's `**` data was `90210096`; the difference is 96 bytes, the inode size fsspec reported for the root `src/` itself, which fsspec's `withdirs` adds and a `**` glob relative to the root does not match. The two libraries agree on the 284 files and 90,199,312 content bytes.

Output, truncation, maintenance, rights. A named tuple, structured and consumable; no truncation concept, because the query runs to exhaustion; nothing cached; no rights. One shape worth noting: `count()` is the same traversal as iterating the glob, so a caller who wants both the rows and the counts walks twice.

## 3. opendal: no aggregate at all; a recursive lister, `content_length` per entry, and the caller sums

Surface. `Operator::list_with` and `lister_with` take `limit`, `start_after`, `recursive`, `versions` and `deleted` (READ, `core/core/src/types/operator/operator_futures.rs` lines 1407-1480; `core/core/src/raw/ops.rs` lines 265-275). `Metadata` exposes `mode`, `is_file`, `is_dir`, `content_length`, `last_modified`, `version`, `is_current`, `is_deleted` (READ, `core/core/src/types/metadata.rs` lines 209-319). A grep of `core/core/src` for `usage`, `stats`, `capacity`, `total_bytes`, `object_count`, `disk_usage` and `du` finds nothing (EXECUTED); there is no aggregate verb, option, column or side channel.

Semantics that bear on summing. `content_length` is documented as the complete object size for files and zero for directories and unknown entries (READ, `metadata.rs` lines 248-253), so a sum over a recursive listing is a content-bytes sum with directories contributing nothing. `Capability` declares `list_with_limit`, `list_with_start_after` and `list_with_recursive` per service (READ, `core/core/src/types/capability.rs` lines 238-242); for a service without native recursion, `FlatLister` walks bottom-up (READ, `core/core/src/raw/oio/list/flat_list.rs` lines 18-58), and for a service that only lists flat, `HierarchyLister` filters to one level after fetching and documents that an empty page does not mean the end (READ, `core/core/src/raw/oio/list/hierarchy_list.rs` lines 18-32). Truncation is paging to exhaustion, with no total and no flag. Maintenance and rights: none.

## 4. JuiceFS: a non-recursive counter per directory, batched deltas flushed every second, a fast mode the CLI calls inaccurate, a strict mode that re-walks, and a `...` bucket that carries the folded sums

Where it lives. Three places. In the metadata engine, `GetDirStat(ctx, inode)` returns the per-directory `dirStat{length, space, inodes}` (READ, `pkg/meta/interface.go` lines 513-514; `pkg/meta/quota.go` lines 33-37); `GetSummary(ctx, inode, summary, recursive, strict)` fills `Summary{Length, Size, Files, Dirs}`; and `GetTreeSummary(ctx, root, depth, topN, strict, sortBy, updateProgress)` fills a `TreeSummary{Inode, Path, Type, Size, Files, Dirs, Duration, Children}` (READ, `interface.go` lines 348-372, 547-549). In the CLI, `juicefs info` prints `files`, `dirs`, `length`, `size` and takes `--recursive` and `--strict` (READ, `cmd/info.go` lines 55-70, 151-154); `juicefs summary` takes `--depth` (zero means only the root), `--entries` (top N), `--sort-by size|inodes|cost`, `--strict` and `--csv` (READ, `cmd/summary.go` lines 64-86). In the format, `DirStats bool` enables the feature and `DirStatFlushPeriod` defaults to one second (READ, `pkg/meta/config.go` lines 53, 62, 108; `cmd/config.go` lines 92, 311-314).

What is maintained and what a write does. `updateDirStat(ctx, ino, length, space, inodes)` returns immediately when `DirStats` is off; otherwise it adds the deltas into an in-memory map keyed by directory inode under a lock, deleting the entry when it nets to zero (READ, `quota.go` lines 181-196). `flushDirStat` runs a ticker at `DirStatFlushPeriod` and calls the engine's flush (READ, lines 219-235). Call sites: 13 in `pkg/meta/base.go`, 7 each in `redis.go`, `sql.go` and `tkv.go`, 2 in `changelog_replay.go` and 2 in `quota.go` (EXECUTED, grep count), so every mutation that changes a directory's direct contents adjusts the counter in all three engine families. The counter is non-recursive: it covers a directory's direct children only, and the guide says so, pointing a caller who wants a cheap recursive total at setting an empty quota on the directory, because a `Quota{MaxSpace, MaxInodes, UsedSpace, UsedInodes}` is maintained recursively for the quota root (READ, `docs/en/guide/dir-stats.md` line 97; `quota.go` lines 46-50). `checkQuota` runs before a write that would add space or inodes (READ, `pkg/meta/base.go` lines 1699, 3504).

How a read assembles the number. `GetDirStat` asks the engine for the stored stat; if none was ever stored it falls back to `calcDirStat`, a readdir that sums `inodes`, `length` and `space = align4K(length)` over direct children; otherwise it adds the in-memory pending deltas to the stored value before returning (READ, `quota.go` lines 141-180). `getDirSummary` is the recursive walk behind `info -r` and `summary`: in strict mode, or when `DirStats` is off, it readdirs every directory and sums attributes; in fast mode it takes `GetDirStat` for the directory's own files and still recurses into subdirectories, 50 at a time, because the counter is non-recursive (READ, `pkg/meta/utils.go`, `GetSummary` lines 408-426 and the body of `getDirSummary`). INFERRED: fast mode is therefore a directory-only walk, one counter read per directory instead of one readdir per directory, which is why the guide calls it an acceleration of `quota`, `info` and `summary` rather than an O(1) answer.

Grain and the `...` bucket. `getTreeSummary` recurses to `depth`, sums children into the parent, sorts children by the chosen key descending, and when there are more than `topN` folds the rest into a single child whose `Path` is the parent joined with `...`, whose `Size`, `Files` and `Dirs` are the sums of the folded children, and whose `Duration` is the slowest of them (READ, `utils.go`, the tail of `getTreeSummary`). INFERRED: this is an "other" bucket done so the parent's totals always equal the sum of its displayed children, and it is named in the tree rather than flagged beside it.

Exactness. The `info --recursive` help text says the result may be inaccurate and to use `--strict` for an accurate one; the guide says directory statistics are calculated asynchronously, can be wrong when clients run into problems, that all three commands take `--strict` to bypass them, and that `fsck` diagnoses a disagreement (READ, `cmd/info.go` lines 60-63; `dir-stats.md` lines 104-109). The default for new volumes since v1.1 is on; the guide notes a minor performance cost (READ, `dir-stats.md` line 7). Output: text in the CLI, `--csv` for programs, and the Go structs for the library; `TreeSummary.Children` carries `json:",omitempty"` (READ, `interface.go` line 363). Rights: none in the aggregate; the meta layer is below permission checks, and `GetDirStat` only maps the inode through `checkRoot` for subdirectory mounts (READ, `quota.go` line 164).

## 5. SeaweedFS: `fs.du` is a text-printing shell walk, and `Statistics` is a volume total from the master

`weed shell`'s `fs.du` takes a directory, a file or a file prefix (READ, `weed/shell/command_fs_du.go` lines 24-31). `duTraverseDirectory` reads all entries of the directory from the filer, recurses into subdirectories, and for each file adds its chunk count as `block` and `filer.FileSize(entry)` as `logical size`; it prints one line per file only when a name or prefix was given, otherwise one total line for the directory, in a fixed `block:%4d\tlogical size:%10d\t%s` text format (READ, lines 37-95). The filer's `Statistics` RPC forwards to the master and returns `total_size`, `used_size`, `file_count`, `logical_total_size` and `logical_used_size` for a `(replication, collection, ttl)` triple (READ, `weed/server/filer_grpc_server_admin.go` lines 20-48; `weed/pb/filer.proto` lines 640-652; `weed/pb/master.proto` lines 351-359), a volume-server aggregate with no directory grain. The filer `Entry` and `FuseAttributes` carry `file_size`, times and mode and no per-directory counters, and a grep of `weed/filer/*.go` for directory size or file-count fields finds none (READ, `filer.proto` lines 163-177, 229-237; EXECUTED, grep). `ListEntries` takes a `limit` and the server pages at `PaginationSize = 1024` (READ, `filer.proto` lines 135-141; `weed/filer/filer.go` line 40; `weed/server/filer_grpc_server.go` lines 72-87). Rights: the shell runs as an operator against the filer; nothing in the aggregate consults a caller.

## 6. MinIO and S3: `CommonPrefixes` rolls up by delimiter without measuring, `KeyCount` counts the page, `MaxKeys` is clamped to 1,000, and the real aggregate is a stale-by-design scanner cache behind an admin endpoint

The S3 shape. `ListObjectsV2Response` carries `Prefix`, `Delimiter`, `MaxKeys`, `KeyCount`, `IsTruncated`, `NextContinuationToken`, `Contents []Object` and `CommonPrefixes []CommonPrefix` (READ, `cmd/api-response.go` lines 130-160). `KeyCount` is set to `len(Contents) + len(CommonPrefixes)`, the number of rows in this page (READ, line 760), so it is a count of what was returned, not of what exists under the prefix. A `CommonPrefix` is a name only; no byte count or object count accompanies it. `maxObjectList = 1000` is the hard page cap, and a caller's `max-keys` above it is silently reduced to it in three request parsers and again in the object layer (READ, `cmd/api-response.go` line 43; `cmd/api-resources.go` lines 37, 57, 87; `cmd/erasure-server-pool.go` lines 1477-1478). INFERRED: the S3 rollup is purely navigational; a program that wants bytes per prefix must list every key and sum, 1,000 at a time.

Rights. The handler checks `ListBucketAction` at bucket level with the request's prefix and delimiter available to `s3:prefix` and `s3:delimiter` policy conditions, and optionally checks each object when metadata is requested (READ, `cmd/bucket-listobjects-handlers.go` lines 172-181; `cmd/bucket-handlers.go` lines 359-363; `cmd/bucket-policy.go` line 78). So the count is rights-aware only in that a denied prefix returns an error rather than a smaller number.

The scanner. `DataUsageInfo` holds `LastUpdate`, `ObjectsTotalCount`, `VersionsTotalCount`, `DeleteMarkersTotalCount`, `ObjectsTotalSize`, `BucketsCount`, `BucketsUsage map[bucket]BucketUsageInfo`, `BucketSizes` and `TierStats`; `BucketUsageInfo` holds `Size`, `ObjectsCount`, `VersionsCount`, `DeleteMarkersCount`, `ObjectSizesHistogram map[string]uint64` and `ObjectVersionsHistogram` (READ, `cmd/data-usage-utils.go` lines 49-107). The histogram's buckets are fixed intervals from `LESS_THAN_1024_B` to `GREATER_THAN_512_MB` (READ, `cmd/object-api-datatypes.go` lines 81-93). It is built by the data scanner, which keeps a `dataUsageEntry` per folder with `Children`, `Size`, `Objects`, `Versions`, `DeleteMarkers`, two histograms and a `Compacted` flag, where the fields exclude children until a branch is compacted; compaction happens at fewer than 500 objects, 10,000 children or 2,500 subfolders, and is forced at 250,000 subfolders; a leaf is rescanned once every 16 cycles and otherwise carries its totals forward; the cycle delay is one minute (READ, `cmd/data-usage-cache.go` lines 60-71; `cmd/data-scanner.go` lines 51-56, 270-292). The result is persisted as `.usage.json` in the metadata bucket and served by an admin-only handler that loads it and adds live capacity figures (READ, `cmd/data-usage.go` lines 34, 45, 113; `cmd/admin-handlers.go` lines 853-870). INFERRED: MinIO separates the two audiences cleanly, exact-but-paged for the S3 caller and approximate-but-whole for the operator, and exposes the approximation's age as `LastUpdate` rather than pretending it is current.

## 7. agentfs: two whole-table SQL aggregates for `statfs`, fabricated FUSE totals, and real GROUP BY only on the tool-call log

agentfs stores a file system in SQLite as `fs_inode` (with `size` and `nlink`), `fs_dentry` and chunked `fs_data` (READ, `SPEC.md` lines 159-285). The only file aggregate is `statfs()`, which runs `COUNT(*) FROM fs_inode` and `COALESCE(SUM(size), 0) FROM fs_inode` and returns `FilesystemStats{inodes, bytes_used}` (READ, `sdk/rust/src/filesystem/agentfs.rs` lines 2455-2486; `sdk/rust/src/filesystem/mod.rs` lines 125-130). The FUSE layer turns that into a `statfs` reply by subtracting from constants, `TOTAL_BLOCKS` of about 4 TB virtual and `TOTAL_INODES` of 1,000,000 (READ, `cli/src/fuse.rs` lines 1012-1040). `COUNT(*) FROM fs_dentry WHERE parent_ino = ?` appears only as an emptiness check before `rmdir` (READ, `agentfs.rs` lines 2125, 2329). The Go SDK's filesystem interface has `Stat`, `Readdir`, `ReaddirPlus` and the usual verbs and no aggregate (READ, `sdk/go/interfaces.go` lines 14-73). Aggregation proper exists only on the tool-call log: `GetStats` runs a `GROUP BY name` with `COUNT(*)`, two conditional `SUM`s and `AVG(duration_ms)`, returning `ToolCallStats{Name, TotalCalls, Successful, Failed, AvgDurationMs}` (READ, `SPEC.md` lines 79-92; `sdk/go/types.go` lines 186-192). No per-directory counters, no caching, no rights.

## 8. mirage: GNU `du` and `df` over mounts as typed records, and a capacity it refuses to fabricate

mirage is a virtual terminal for agents with a Python VFS of mount drivers. It implements `du` as a builtin with GNU's flag set, `-s`, `-a`, `-d/--max-depth`, `-c`, `-S`, `-x`, `--apparent-size`, `--inodes`, `-t/--threshold`, `--time`, `--exclude`, `-X` and more (READ, `python/mirage/commands/spec/builtin_specs/listing.py` lines 217-245; `python/mirage/commands/builtin/generic/du.py` lines 58-94). The cross-mount layer runs each mount's own `du` over the start points inside it and renders their `PathRecord`s as one tree, where a `PathRecord` is `(path, run, size | None, values, modified)` with `size` the bytes of a counted file and `None` for a directory the walk met; the docstring states that no mount's output text is read back, that `-c` totals the line, and that a mount whose `du` fails contributes its diagnostic and the mounts below it count only where the walk could still reach them (READ, `python/mirage/commands/builtin/generic/crossmount/du.py` lines 55-125; `python/mirage/io/types.py` lines 139-155). INFERRED: the aggregate crosses the seam as records and is assembled by the renderer, which is the shape vfs's own `Result` rows already have.

`df` rests on `capacity()`, a driver method returning `CapacityResult(state, total, used, available, inodes, inodes_used, inodes_free)` where `state` is `QUOTA` (real numbers), `ELASTIC` (no fixed size, an object store), `NA` (no capacity concept, a table or message surface) or `UNKNOWN` (bounded but not cheaply measurable); every byte count is `None` unless the state is `QUOTA`, the base class returns `UNKNOWN`, and both docstrings say never to fabricate a number, `df` rendering a literal `-` instead (READ, `python/mirage/types.py` lines 377-420; `python/mirage/vfs/base.py` lines 858-867). Ten drivers override it (EXECUTED, grep). A listing result also carries `partial` (filtered or truncated, so not cached as the directory's listing) and `window` (capped to the newest N, so proving nothing absent) flags (READ, `types.py` lines 280-300). Writes are charged against a `StorageUsage` with a pending hold that counts until the write lands (READ, `python/tests/vfs/test_capacity.py` lines 21-58). Rights: `available` is documented as bytes available to the workspace user, the `statvfs` distinction carried through.

## 9. afs: `explain` delivers a row count as Markdown prose, and `list` carries `total` only if known

The AFS protocol adds `exec` and `explain` to `list`, `read`, `write`, `stat` and `search`; `explain(path, format)` returns `AFSExplainResult{format: "markdown" | "text", content: string}`, self-description for humans and agents (READ, `spec/afs-protocol.md` lines 16-29, 317-340; `packages/core/src/meta/type.ts` lines 102-107). The SQLite provider's table-level `explain` runs `SELECT COUNT(*)` on the table and writes `**Rows:** N` into the Markdown along with the columns and indexes (READ, `providers/sqlite/src/sqlite-afs.ts` lines 961-1000); it is the one aggregate in the clone and it is delivered as prose for a model to read, not as a typed field a program can use. `list` takes `limit` (default 1,000), `maxDepth`, `offset`, `orderBy`, `pattern` and an `onOverflow: "truncate"` option, and returns `{data: AFSEntry[], total?: number}` with `total` described as the total count if known, for pagination (READ, `afs-protocol.md` lines 111-135, 829-830, 1314). No counters, no caching; the licence is BUSL 1.1, studied only.

## 10. computer (`dofs`): paged `readdir`, `find` and `grep` with a `limit` and no total, `COUNT(*)` only for link counts and emptiness

`dofs` is a SQLite file system inside a Durable Object with `vfs_nodes` (`size`, `rev`), `vfs_dirents` and `vfs_chunks` (READ, `packages/dofs/src/schema/migrations.ts` lines 112-129). `readdir` returns size and modification time with stable `limit` and `offset` pages; `find` and `grep` take a `limit` and stop at it; none returns a total or a truncated flag (READ, `packages/dofs/README.md` lines 51-55; `src/fs/readdir.ts` lines 48-82; `src/fs/find.ts` lines 53-68; `src/fs/grep.ts` lines 29-91). `stat` reads the cached `size` off `vfs_nodes`, or the dirty buffer's size for a pending write (READ, `src/fs/stat.ts` lines 66-82). `COUNT(*)` appears for `nlink` and for emptiness before `rename`, `rm` and `unlink` (READ, `src/provider.ts` line 769; `src/fs/rename.ts` line 113; `src/fs/rm.ts` line 125; `src/fs/unlink.ts` line 24). No aggregate verb, column or side channel.

## 11. eve: a filesystem-first agent framework with no file aggregation

eve is a framework whose agents are authored as files on disk (READ, `README.md` lines 14-40). A grep of `packages/eve/src` finds `readdir` only in discovery and trace-reading code, and the only byte sum is a `totalBytes` reduction in trace retention used to decide what to prune (READ, `packages/eve/src/tracing/local/trace-retention.ts` lines 121-145; EXECUTED, grep). It aggregates nothing over a file tree for a caller.

## 12. `statvfs` and `statfs`: the oldest aggregate is whole-filesystem block and inode counts, and it already distinguishes what the caller may use

FreeBSD's `struct statvfs` holds `f_bavail`, `f_bfree`, `f_blocks`, `f_favail`, `f_ffree`, `f_files`, `f_bsize`, `f_flag`, `f_frsize`, `f_fsid` and `f_namemax`; the header comment above it explains that `avail` is space available to unprivileged processes while `free` includes space reserved for privileged ones, and adds that by the letter of the standard the interface is unspecified (READ, `sys/sys/statvfs.h` lines 48-68). The native `struct statfs` adds `f_iosize`, four I/O counters since mount (`f_syncwrites`, `f_asyncwrites`, `f_syncreads`, `f_asyncreads`), `f_owner`, `f_fstypename` and `f_mntonname`; its man page glosses `f_bavail` as free blocks available to non-superuser and `f_ffree` likewise (READ, `sys/sys/mount.h` lines 91-111; `lib/libsys/statfs.2` lines 75-79 via `git show`). Linux's uapi `statfs` carries the same seven counts plus `f_type`, `f_namelen`, `f_frsize` and `f_flags` (READ, `include/uapi/asm-generic/statfs.h` lines 24-34). The rights point is sharpest in ext4: `ext4_statfs_project` takes the project quota's block and inode limits and clamps `f_blocks`, `f_bfree`, `f_bavail`, `f_files` and `f_ffree` to the project's limit and remaining, so a caller inside a project-quota'd directory sees its own ceiling, not the disk's (READ, `fs/ext4/super.c` lines 6902-6942). INFERRED: the smallest aggregate file systems offer is whole-filesystem, O(1) because superblock counters are maintained on every allocation, and from its first design it reported a rights-adjusted number beside the raw one.

Three patterns recur. First, every library-level aggregate is a sum over the same walk the listing does, so the caller who wants rows and totals walks twice (fsspec, pyfilesystem2, SeaweedFS `fs.du`); none attaches the totals to the listing it just produced (READ throughout). Second, the systems that maintain anything maintain it non-recursively per directory (JuiceFS) or per folder with explicit compaction (MinIO), and both treat the recursive answer as a walk over those counters rather than a stored field, and both label the maintained number as possibly stale or inaccurate rather than hiding it (READ, sections 4 and 6). Third, the `int`-returning APIs give no way to say "I could not measure this": fsspec returns 0 for a depth with no files, agentfs invents a 4 TB disk, while mirage's `CapacityState` and JuiceFS's `--strict` make the gap explicit (READ, EXECUTED, sections 1, 7, 8). INFERRED: vfs's typed stats block sits where none of the libraries put one and where only mirage's records and JuiceFS's `TreeSummary` come close.

## 14. What vfs should adopt and what it should not

Adopt, from JuiceFS (READ, section 4): the pair of a non-recursive per-directory counter maintained by every mutation and flushed in batches, and a caller-visible choice between the fast answer and a strict re-walk, with the fast answer labelled as such. For vfs's rollup columns this is the shape that keeps `tree(max_depth=1, columns={"total_bytes"})` cheap on Postgres at 10,000-file batches without a declared corpus ceiling: the counter row per directory is bounded by the number of directories, a write touches one row per ancestor it changes, and the rollup is a bounded walk over counter rows. The second JuiceFS move to adopt is the `...` child in `GetTreeSummary`: a top-N whose tail is folded into one named bucket carrying the folded `Size`, `Files` and `Dirs`, so the parent's totals always equal the sum of what is shown. That is the histogram verb's "other" bucket, already proven in a file-system tree.

Adopt, from mirage and `statvfs` (READ, sections 8 and 12): a stats block states what it could not measure instead of printing a number. mirage's `CapacityState` (`QUOTA`, `ELASTIC`, `NA`, `UNKNOWN`) with every count `None` outside `QUOTA`, and `statvfs`'s `avail` beside `free` with ext4's quota clamp, are two independent designs that reached the same rule: the aggregate is computed under the caller's rights and says when it is partial. vfs's exact-versus-lower-bound flag and rights-judged counts are the same rule.

Do not adopt, from fsspec (EXECUTED, section 1): a depth parameter that cuts the walk rather than rolling up to the depth. `du(total=True, maxdepth=1)` over `src/` returned 0 for a 90 MB tree with no signal, because depth was a filter on which files to count. vfs's `max_depth` on a rollup column must mean "show me these directories with everything below them summed", which is what `du -d 1` and `tree(max_depth=1, columns={"total_bytes"})` promise. Alongside it, do not adopt S3's `KeyCount` (READ, section 6): a count of rows in the page labelled as if it were a count of matches. vfs's stats block names both numbers, entries matched and entries returned, and the two must never share a field.

## 15. What this study does not settle

I did not run JuiceFS, SeaweedFS or MinIO; every claim about them is READ from source and documentation, and the one-second flush cost, the fast-versus-strict disagreement rate and the scanner's staleness in practice were not measured here. The opendal Python binding's stub file was not at the path I tried, so section 3 rests on the Rust core and the capability table alone. I did not exhaust every SeaweedFS filer store for a store-specific directory counter; the grep covered `weed/filer/*.go` and the protos. The FreeBSD man page was read from the git object because the clone is sparse, and the linux clone was dirty in 13 netfilter headers unrelated to what I read. The box closed with this study written at the time recorded in that file, inside the 45 minutes.

## One line

Libraries sum a walk and return a bare number, JuiceFS keeps a non-recursive counter per directory with a fast answer it labels inaccurate and a `...` bucket that carries what the top-N folded, MinIO and S3 roll up by prefix without measuring and cap the page at 1,000, and `statvfs` has reported a rights-adjusted total beside the raw one since the beginning: vfs should keep the counter, the labelled exactness and the named other-bucket, and refuse fsspec's depth-as-filter and S3's page-count-as-match-count.
