# Query engines put the group-by in a request of its own, cap it with a size plus one probe row, and report what fell off the end as a flag, an "other" count or an error bound, never silently

Researcher 03 opened the 45-minute box at 08:32:34 EST on 2026-11-09 and finished the reading, the experiment and this file inside it, with the writing complete at the time recorded in the last section. The question was how five query engines (datasette, sqlite-utils, Lucene's facet module, tantivy's aggregation module and qdrant's facet endpoint) shape a group-by aggregation: where it lives in the API, what it measures and over what unit, how the caller picks the grain, how the output is shaped, how truncation is reported, whether totals are maintained or computed on demand, and whether the count respects the caller's visibility. The finding in one sentence is that every one of the five makes the group-by a separately named request (a facet, an aggregation, a facet request) that takes a key, a cap and an optional filter, fetches the cap plus one row or an oversampled set to learn whether it was cut, and reports the cut in the result itself; none of them maintains counts, and only datasette and qdrant evaluate the count under the caller's filter at request time.

## 1. datasette: a facet is a URL option on the table listing, capped by size plus one, timed out per facet, and reported as a JSON record with a `truncated` flag

Where it lives (READ `datasette/facets.py` lines 85-160, `datasette/views/table.py` lines 2620-2633). A facet is an option on the table view, not a verb: the caller adds `?_facet=<column>` to the same URL that lists rows, and the JSON response grows a `facet_results` object beside `rows`. Facets are plugins: `Facet` is a base class with `suggest()` and `facet_results()`, and three subclasses ship (`ColumnFacet`, `ArrayFacet` for JSON arrays via `json_each`, `DateFacet` which groups on `date(column)`). The `allow_facet` setting can refuse `_facet=` outright with a 400, and `_nofacet=1` turns the computation off for a request.

What it measures and over what unit (READ `facets.py` lines 243-250). One SQL statement per facet: `select <col> as value, count(*) as count from (<the filtered listing SQL>) where <col> is not null group by <col> order by count desc, value limit <facet_size + 1>`. The unit is the current filtered result set, so a facet count is always "rows matching the caller's filters that also have this value", and nulls are left out rather than bucketed.

How the caller chooses the grain (READ `facets.py` lines 122-150, `app.py` lines 233-245). The key is the column; the grain for dates is fixed to the day by `DateFacet`; the top-N is `facet_size`, resolved as `default_facet_size` (30) overridden by table config and by `?_facet_size=N` or `?_facet_size=max`, and finally clamped to `max_returned_rows`. There is no bucket width for numbers; a numeric column is faceted on distinct values or not at all.

Output shape (READ `facets.py` lines 259-275 and 296-313; EXECUTED, `datasette_facets.json`). Each facet is a record `{name, type, hideable, toggle_url, results: [{value, label, count, toggle_url, selected}], truncated}`. The experiment returned, for `?_facet=ext&_facet=dir` with facet size 5 over the 97 files of vfs `src/`: `dir` with five buckets (`vfs/storage/backends/database` 33, `vfs/models` 17, `vfs` 16, `vfs/rendering` 8, `vfs/embedding` 6) and `"truncated": true`, and `ext` with four buckets (`py` 94, `pyi` 1, `so` 1, `typed` 1) and `"truncated": false`. Filtering to `ext=py` and asking `_facet=dir&_facet_size=3` returned three `dir` buckets, `truncated: true`, and `filtered_table_rows_count: 94`. Every bucket carries a `toggle_url` that is the same listing with that value added as a filter, so the facet result is also the drill-down menu.

Truncation (READ `facets.py` line 271; `table_extras.py` lines 110-156; `database.py` lines 85 and 856-870). Truncation of a facet is detected by fetching `facet_size + 1` rows and comparing: the flag is `len(rows) > facet_size`, and the extra row is dropped, so there is no "other" bucket and no total of what fell off. The row count has the same shape at a coarser cap: `CountExtra` runs `select count(*) from (select * <from and where> limit count_limit + 1)` with `count_limit = 10000`, and `count_is_truncated` is true exactly when the count equals 10001, so a displayed count of "10,001" means "more than ten thousand". A facet that exceeds `facet_time_limit_ms` (200 ms; `facet_suggest_time_limit_ms` 50 ms for suggestions) raises `QueryInterrupted` through SQLite's progress handler and lands in `facets_timed_out`, a list of column names returned beside `facet_results`, so a missing facet is named rather than silent.

On demand or maintained (READ `database.py` lines 147-156 and 856-870; `table_extras.py` lines 118-127). Every facet and every filtered count is computed on demand by a fresh `group by`. The one cache is for immutable databases: `datasette inspect` writes per-table counts into `inspect-data.json`, `cached_table_counts` serves them, and `CountExtra` uses the cached count only when the count SQL is exactly the unfiltered `select count(*) from <table>`; a mutable database never caches. Nothing is invalidated because nothing is cached while writes are possible.

Rights and visibility (READ `facets.py` lines 229-250; INFERRED). Facet SQL wraps the view's own filtered SQL, and datasette's table-level permission check runs before the view builds that SQL, so a facet is computed only over a table the actor may see; within a table there is no row-level visibility, so the count respects the table gate and nothing finer. Suggestion (`ColumnFacet.suggest`, lines 173-220) is itself bounded: it looks at the first `suggest_consider = 1000` rows, keeps a column only if `1 < distinct <= facet_size`, distinct is below the row count and some value repeats, and gives up on a column after 50 ms.

## 2. sqlite-utils: aggregation is a verb of its own (`analyze-tables`) that computes a fixed per-column profile with a `--common-limit` top and bottom N, and saves it as a table

Where it lives (READ `sqlite_utils/cli.py` lines 3029-3071, `sqlite_utils/db.py` lines 5299-5385). `analyze-tables` is a CLI command and `Table.analyze_column` a method; neither is an option on a listing. It takes table names, `-c` column names, `--common-limit N` (default 10), `--no-most`, `--no-least` and `--save`, which upserts each `ColumnDetails` record into a `_analyze_tables_` table keyed by `(table, column)`.

What it measures and over what unit (READ `db.py` lines 5322-5385). Per column over the whole table: `total_rows`, `num_null`, `num_blank` (empty string), `num_distinct`, `most_common` and `least_common` as lists of `(value, count)`. The unit is one column of one table; there is no filter, no subtree and no result set.

How the caller chooses the grain (READ `db.py` lines 5302-5306). Only the top-N (`common_limit`) and which columns; the group-by key is every column asked for, the value is the raw column value with `value_truncate=80` characters applied to the label only.

Output shape (EXECUTED, `analyze_tables.txt` and `analyze_tables.json`). Text is a block per column ("Total rows: 97 / Null rows: 0 / Blank rows: 0 / Distinct values: 9 / Most common: 33: vfs/storage/backends/database ..."). The structured form is the saved table: the `ext` row came back as `{"table": "files", "column": "ext", "total_rows": 97, "num_null": 0, "num_blank": 0, "num_distinct": 4, "most_common": [["py", 94], ["typed", 1], ["so", 1], ["pyi", 1]], "least_common": null}`.

Truncation (READ `db.py` lines 5347-5380; EXECUTED). There is no truncated flag and no other bucket; the caller reads `num_distinct` against `len(most_common)` to know whether the list is complete. Two shortcuts encode that arithmetic: when `num_distinct == 1` the single value is reported with `total_rows` and no `group by` runs; when `num_distinct <= common_limit` the least-common query is skipped and `least_common` is `None`, which is why `ext` (4 distinct, limit 5) has `least_common: null` while `dir` (9 distinct) has both lists. When all rows are null, `most_common` is `[(None, total_rows)]` without a query.

On demand or maintained (READ `db.py` lines 5322-5380, `cli.py` lines 3074-3110; INFERRED). Everything is computed on demand by four to six statements per column: a `count(*)` once per table (passed in as `total_rows` so columns share it), `count(*) where is null`, `count(*) where = ''`, `count(distinct)`, and up to two `group by ... order by count(*) ... limit N`. Each `group by` scans the whole table; the bound is the output (`limit N`), not the work. `--save` is a materialization that nothing invalidates: the `_analyze_tables_` table is a snapshot the caller rewrites by running the command again.

Rights and visibility. None; sqlite-utils is a single-user library over a file (INFERRED from the absence of any actor or permission concept in `db.py`).

## 3. Lucene facets: a separate `Facets` object built from the hit set, with counts computed at search time from ordinals stored at index time, reporting `value`, `childCount` and the top-N children

Where it lives (READ `lucene/facet/src/java/org/apache/lucene/facet/Facets.java` lines 27-70, `FacetsCollector.java`, `FacetsConfig.java` lines 171-260). Faceting is a second pass over the hits of a search, not an option on the query: the caller collects matches with a `FacetsCollector`, then constructs a `Facets` implementation over those matches (`FastTaxonomyFacetCounts`, `SortedSetDocValuesFacetCounts`, `LongValueFacetCounts`, range and association variants) and asks it `getTopChildren(topN, dim, path...)`, `getAllChildren(dim, path...)`, `getSpecificValue(dim, path...)`, `getAllDims(topN)` or `getTopDims(topNDims, topNChildren)`. Index-time configuration lives in `FacetsConfig`: per dimension `setHierarchical`, `setMultiValued`, `setRequireDimCount`, `setIndexFieldName`, and `build(doc)` rewrites the document's `FacetField`s into the stored shape.

What it measures and over what unit (READ `FacetResult.java` lines 22-45, `package-info.java` lines 24-36). The default measure is a document count per label under a path, over the hit set of the query; association variants aggregate a stored int or float per document instead of counting, and `LongValueFacetCounts` counts numeric values. The unit is the result set of a search, never a stored collection total, except that the no-hits constructors (`countAll`) count every live document.

How the caller chooses the grain (READ `Facets.java` lines 43-70, `FacetsConfig.java` line 171, `taxonomy/TaxonomyFacets.java` lines 261-280). Grain is the dimension plus a path into a hierarchy, with `topN` on the children; a hierarchical single-valued dimension rolls child counts up into parents through the taxonomy's `parents` array (`rollup()`), so `getTopChildren(10, "Path", "src", "vfs")` is a `du -d 1`-shaped question answered from the same ordinals. There is no bucket width in the core module; range facets (`facet/range`) take explicit `LongRange`/`DoubleRange` lists from the caller.

Output shape (READ `FacetResult.java`, `LabelAndValue.java`). `FacetResult` is `{dim, path[], value, childCount, labelValues[]}` where `value` is documented as "total number of documents containing a value for this path, even those not included in the topN" (each document counted once however many values it has), `childCount` is "how many child labels were encountered", and `labelValues` is the top-N `LabelAndValue(label, value, count)`. Structured by construction; there is no text form.

Truncation (READ `FacetResult.java` lines 29-41, `Facets.java` lines 32-37 and 60-67, `FacetsConfig.java` lines 191-200; INFERRED). Truncation is reported by arithmetic rather than a flag: `childCount` minus `labelValues.length` is how many labels fell off, and `value` minus the sum of the returned counts is the "other" mass for a single-valued dimension. The `value` field is accurate only when the dimension was indexed with `setRequireDimCount(true)` (the docs for `getTopDims` say so explicitly); otherwise it is derived from the children and may undercount a multi-valued dimension. `getSpecificValue` returns -1 for a path that does not exist, and `getTopChildren` returns null for a dimension never seen.

On demand or maintained (READ `package-info.java` lines 24-36, `sortedset/SortedSetDocValuesFacetCounts.java` lines 173-230 and 305-325, `taxonomy/FastTaxonomyFacetCounts.java` lines 69, 117-120, `RandomSamplingFacetsCollector.java` lines 30-40). No count is stored. What the index stores is, per document, the ordinal of each facet label (sorted-set doc values, or packed ordinals in a binary doc-values field for the taxonomy path), plus a mapping from label to ordinal (the segment's sorted set, or the separate taxonomy index). Counting is a search-time scan of the hit set incrementing `counts[ord]`; the sorted-set variant chooses per segment between iterating hits (when `hits < numSegOrds / 10`) and iterating the ordinals (line 216), and `countAll` walks every live document when there is no query. Invalidation is therefore free: a new segment brings its own ordinals, and the taxonomy index only ever grows. `RandomSamplingFacetsCollector` samples the hit set and offers `amortizeFacetCounts` to scale the sampled counts back up, the module's one approximate mode.

Drill-down and drill-sideways (READ `DrillDownQuery.java`, `DrillSideways.java` lines 50-69). `DrillDownQuery` adds a facet value as a filter clause. `DrillSideways` runs the drill-down and, for each drilled dimension, also counts the hits that match every other drill-down but not that one, "so that a dimension does not disappear after the user drills down into it"; the cost is one `FacetsCollector` per drilled dimension plus one, and the docs warn that memory multiplies with the label count. This is the engine-side version of datasette's `toggle_url` on a selected facet value.

Rights and visibility (INFERRED from the API). The hit set is whatever query the caller ran, so visibility is whatever the caller folded into the query; the facet module has no notion of an actor and `countAll` counts every live document in the reader.

## 4. tantivy aggregations: an Elasticsearch-shaped request tree with `size`, `sum_other_doc_count`, `doc_count_error_upper_bound` and a hard memory and bucket budget

Where it lives (READ `src/aggregation/README.md` lines 8-24, `agg_req.rs` lines 48-96 and 185-245). Aggregation is a request object passed to an `AggregationCollector` beside the query, not an option on the search verb and not a separate verb: `Aggregations` is a map from caller-chosen name to `Aggregation {variant, sub_aggregation}`, deserialized from JSON that is "compatible with elasticsearch aggregation requests". Bucket variants: `range`, `histogram`, `date_histogram`, `terms`, `filter`, `composite` (paginable), `multi_terms`. Metric variants: `average`, `count`, `max`, `min`, `stats`, `extended_stats`, `sum`, `percentiles`, `top_hits`, `cardinality`. Bucket aggregations nest sub-aggregations; metrics do not.

What it measures and over what unit (READ `agg_result.rs` lines 22-175 and 265-310). Per bucket, `doc_count` plus whatever metric sub-aggregations the caller nested (a `stats` of a size field inside a `terms` on an extension field yields count, min, max, sum and average of bytes per extension). The unit is the query's result set, scoped per bucket by the parent's key.

How the caller chooses the grain (READ `bucket/term_agg/mod.rs` lines 199-260, `bucket/histogram/histogram.rs` lines 139-170). `terms` takes `field`, `size` (default 10), `segment_size` ("defaults to 10 * size", the per-segment oversample), `min_doc_count` (default 1; 0 returns every term and is marked expensive), `order` by `_count`, `_key` or a named metric, `missing` to bucket documents without a value under a caller-chosen key, and `show_term_doc_count_error`. `histogram` takes `field`, `interval` (the bucket width, a positive float), `offset` to shift the grid, `min_doc_count` (default 0, so empty buckets between first and last are emitted), `hard_bounds` and `extended_bounds`. `range` takes explicit ranges; `date_histogram` takes a fixed interval.

Output shape (READ `agg_result.rs` lines 51-175, 265-310, 353-360). `AggregationResults` is a map by the request's names; a `Terms` result is `{buckets: [{key, key_as_string, doc_count, sub_aggregation}], sum_other_doc_count, doc_count_error_upper_bound}`; a `Histogram` result is the same bucket list with gaps filled when `min_doc_count` is 0; a `Range` bucket adds `from` and `to`. All of it serializes to JSON in the Elasticsearch shape, so programs consume it directly.

Truncation (READ `agg_result.rs` lines 150-160, `term_agg/mod.rs` lines 207-224). Two numbers, both in the result: `sum_other_doc_count`, "the number of documents that didn't make it into to TOP N due to shard_size or size", which is the "other" bucket as a total rather than a label; and `doc_count_error_upper_bound`, "the sum of the size of the largest bucket on each segment that didn't fit into shard_size", which bounds how wrong any returned count can be because the top-N was chosen per segment before merging. The error bound defaults to on when ordering by count descending and is omitted from the JSON otherwise.

Bounded work (READ `agg_limits.rs` lines 30-110, `collector.rs` line 7, `error.rs`). `AggregationLimitsGuard` carries a `memory_limit` (default `DEFAULT_MEMORY_LIMIT`, 500 MB) and a `bucket_limit` (default `DEFAULT_BUCKET_LIMIT`, 65,000); `add_memory_consumed` is called as buckets accumulate and fails the request with an `AggregationError` when the budget is exceeded. The bound is a declared budget that refuses, not a silent cap; `min_doc_count: 0` on `terms` and a tiny histogram `interval` are the documented ways to hit it.

On demand or maintained (READ `agg_req.rs` lines 100-106, `README.md` lines 20-24; INFERRED). Everything is computed at query time from fast fields (tantivy's columnar doc values), which the request enumerates through `get_fast_field_names` so the collector can open them once. No count is stored; per-segment intermediate results are merged, and that merge is what produces `sum_other_doc_count` and the error bound.

Rights and visibility (INFERRED). The collector runs over the query's matching documents; there is no actor concept, so visibility is whatever the caller put into the query.

## 5. qdrant facets: a dedicated endpoint taking `key`, `limit`, `filter` and `exact`, where inexact means per-segment index counts, sampled and oversampled, merged and cut to the limit

Where it lives (READ `lib/api/src/rest/schema.rs` lines 1463-1506). `POST /collections/{name}/points/facet` is a verb of its own. `FacetRequestInternal` is `{key: JsonPath, limit: Option<usize> (default 10), filter: Option<Filter>, exact: Option<bool> (default false)}`, wrapped with an optional `shard_key`. `FacetResponse` is `{hits: [{value: FacetValue, count: usize}]}`, where `FacetValue` is a keyword, integer, UUID or boolean.

What it measures and over what unit (READ `schema.rs` lines 1464-1476, `lib/collection/src/shards/local_shard/facet.rs` lines 23-110). The count of points, under the filter if one is given, per distinct value of one payload key, across the whole collection (every shard, every segment). No bytes, no sums, no sub-aggregation; a facet needs a payload index on the key.

How the caller chooses the grain (READ `schema.rs` lines 1467-1476). Only the key, the top-N (`limit`) and the filter; there is no bucket width, no path, no nesting.

Output shape (READ `schema.rs` lines 1497-1506). A flat list of `{value, count}` sorted by count; no total, no other bucket, no truncated flag, no error bound.

Truncation and the meaning of inexact (READ `lib/collection/src/collection/facet.rs` lines 20-24 and 80-106, `local_shard/facet.rs` lines 23-110, `lib/segment/src/segment/read_view/facet.rs` lines 22-40 and 102-165, `segment/entry.rs` lines 283-289). With `exact: false` the coordinator multiplies the caller's `limit` by `FACET_OVERSAMPLE_FACTOR` (4) with a floor of `FACET_MIN_OVERSAMPLE` (128), sends that to every shard, and only the final merge on the entry node truncates back to the caller's limit. Within a shard the full per-segment value maps are merged before any cut, because, as the comment at lines 55-59 says, per-segment top-k is unsafe since the same value can rank differently across segments. Within a segment `approximate_facet` chooses between walking the facet index, walking the filter's matching points when the filter's estimated selectivity is under `ITER_FILTER_INDEX_SELECTIVITY` (0.1), and random sampling when the number of distinct values exceeds `MIN_SAMPLE_TARGET.max(limit * OVERSAMPLE_FACTOR)` with `OVERSAMPLE_FACTOR = 10` and the filter is broad enough for random draws to be cheap. Two things make the result inexact: a sampled segment reports counts for the values its sample found, and the same point can live in more than one segment with different versions and be counted twice. With `exact: true`, `exact_facet` first collects the set of unique values under the filter and then runs one filtered count per value through `read_filtered`, which deduplicates points across segments; the cost is a count per distinct value rather than one pass, and that is what "a more expensive exact count" in the field's doc comment means.

On demand or maintained (READ `read_view/facet.rs` lines 142-165). Counts are computed at request time from the payload index's postings (the "facet index"); nothing stores a count per value, and the cardinality estimator (`estimate_cardinality`) is consulted only to pick the walk. Invalidation is therefore the index's own.

Rights and visibility (INFERRED from `schema.rs` and the shard code). qdrant has API keys with collection-level and read-only scopes but no per-point actor model in this path; the filter is the only per-request visibility, and the inexact path can count a point twice, so an inexact count is not a safe statement about what a caller may see.

## 6. Comparison: five answers to the seven questions

Where the aggregation lives. Two put it in a dedicated verb or endpoint (sqlite-utils `analyze-tables`, qdrant `/points/facet`); two put it in a request object that rides beside the search (Lucene `Facets` over a `FacetsCollector`, tantivy `Aggregations` on a collector); one puts it in a URL option on the listing verb itself (datasette `?_facet=`). None of the five puts a group-by on a column the caller asks for, and none emits buckets as a side channel on every result; the cheapest thing any of them attaches to every result is datasette's bounded row count. For vfs this says the three proposed layers are three different things in prior art too: a stats block is datasette's `filtered_table_rows_count` plus `count_truncated`, a rollup column is Lucene's hierarchical taxonomy rollup read by path, and a histogram verb is qdrant's endpoint or tantivy's `terms` request.

What it measures. Four count documents or rows; only tantivy aggregates a measure (bytes, lines) per bucket through metric sub-aggregations, and only Lucene's association facets do the same in the search world. sqlite-utils adds the column profile (null, blank, distinct) that none of the search engines has. The unit is the filtered result set everywhere except sqlite-utils, where it is the whole table.

How the caller chooses the grain. Every one takes a key and a top-N; the names are `_facet_size`, `--common-limit`, `topN`, `size`, `limit`. Only tantivy has a bucket width (`interval` and `offset`) and explicit ranges; only Lucene has a path into a hierarchy; datasette's `DateFacet` fixes the grain to a day; qdrant has neither width nor path.

Output shape. All five are structured records, and all but sqlite-utils are structured first (sqlite-utils renders text and saves a table). The bucket is `{value, count}` everywhere, with Lucene calling it `LabelAndValue` and tantivy `BucketEntry {key, doc_count}`. datasette alone attaches a navigation affordance (`toggle_url`) to each bucket; Lucene's `DrillSideways` is the same idea pushed into the engine.

How truncation is reported. The spread is the most useful finding of the study. datasette fetches size plus one and sets a boolean `truncated`, with the row count capped at 10,001 meaning "more than 10,000". sqlite-utils reports `num_distinct` and lets the caller subtract. Lucene reports `childCount` (labels seen) and `value` (documents under the path), so both the number of missing labels and the missing mass are recoverable by subtraction, with the caveat that `value` is exact only when `requireDimCount` was set at index time. tantivy reports the missing mass directly as `sum_other_doc_count` and adds `doc_count_error_upper_bound` for the error a per-segment cut can introduce. qdrant reports nothing in the response and moves the guarantee into the request (`exact`), compensating with a 4x oversample and a 128 floor. Only datasette and tantivy refuse work past a budget (a 200 ms facet time limit landing the column in `facets_timed_out`; a 500 MB and 65,000-bucket guard failing the request); the other three bound output and let the scan run.

On demand or maintained. None of the five maintains a count. Lucene and tantivy store the per-document ordinal or fast-field value at index time and count by scanning the hit set; qdrant counts from the payload index's postings; datasette and sqlite-utils issue a `group by` per request. The only caches are datasette's `inspect-data.json` for databases declared immutable, and sqlite-utils' `--save` snapshot, neither of which is invalidated by anything but a rerun. The lesson for vfs's rollup columns is that no studied engine keeps per-directory counters; the engines that are fast at counting are fast because the attribute is columnar and the scan is over ordinals, not because a total was kept.

Rights and visibility. Only datasette evaluates the aggregate under the same gate as the listing it rides on, because the facet SQL wraps the listing's SQL. qdrant's filter plays the same role per request, but its inexact mode can double count. Lucene and tantivy count whatever the caller's query admitted. None has a per-row actor model in the aggregation path, so vfs's requirement that a count never leaks an entry the caller may not list is stricter than any studied engine, and datasette's "wrap the already-gated query" is the only prior-art shape that satisfies it by construction.

The experiment in one paragraph (EXECUTED). The corpus is 97 files, 86,125,346 bytes and 436,412 lines by a newline count that includes the compiled `vfs/_native` extension; the top three directories by file count are `vfs/storage/backends/database` (33 files, 819,799 bytes), `vfs/models` (17, 176,164) and `vfs` (16, 84,818,996, almost all of it the extension's shared object). datasette at facet size 5 returned `dir` truncated and `ext` complete, and under the filter `ext=py` returned `filtered_table_rows_count: 94` with `dir` truncated at size 3; sqlite-utils reported `num_distinct: 9` for `dir` with both common lists and `num_distinct: 4` for `ext` with `least_common: null`. The `count` extra came back `null` in both datasette responses while `filtered_table_rows_count` carried the number, which shows that datasette's JSON currently exposes the bounded count under the older key.

Design moves for vfs. ADOPT: report truncation as data in the result, the way tantivy and Lucene do, with the total under the scope (`value`), the number of distinct labels seen (`childCount`), the top-N buckets and the mass that fell off (`sum_other_doc_count`); a boolean `truncated` alone, datasette's shape, tells an agent that something is missing but not how much, and the "other" bucket in the proposed histogram verb is the right place for that mass. ADOPT: bound the aggregation by a declared budget that refuses, the way tantivy's `AggregationLimitsGuard` and datasette's `facet_time_limit_ms` do, and compute the count under the same gated query the listing runs, datasette's shape, so a bucket count can never include an entry the listing would have withheld; fetching cap plus one to detect the cut costs one row and is the uniform trick across datasette, sqlite-utils' shortcut arithmetic and tantivy's oversample. DO NOT ADOPT: an `exact: false` default in the style of qdrant, where the response carries no marker of its own inexactness and a point can be counted twice; an agent reading a count needs the result to say whether the number is exact, and the proposed stats block's "whether it is exact" field is the right carrier, with inexact counts allowed only when the result says so.

## 7. What this study does not settle

Lucene's `facet/facetset` and `rangeonrange` subpackages, which match documents against caller-supplied sets and ranges, were not read inside the box; they are the closest thing in the module to a caller-defined bucket list and would inform a size-bucket histogram. tantivy's `composite` aggregation, which pages through buckets by an `after` key, was not read beyond its one-line doc; it is the only paginated group-by among the five and would inform how a histogram verb with more buckets than the top-N hands the rest back. qdrant's `FacetValue` ordering and tie-breaking at the merge, and whether a `read_only` segment path differs, were not traced. No real-engine measurement was made: the experiment ran on SQLite over 97 rows, which exercises the shapes and flags but not the statement budgets vfs must respect on Oracle or SQL Server, and no clock from this machine is a fact about those engines.

## One line

The box closed with the writing complete at 08:44 EST, eleven minutes in and well inside 45; every engine studied makes the group-by a request that names a key and a cap, learns whether it was cut by fetching one more than the cap or oversampling, and the engines worth copying put the cut's size in the result (`sum_other_doc_count`, `childCount`, `value`) rather than a bare flag, while none of them keeps a count and only datasette computes it under the listing's own gate.
