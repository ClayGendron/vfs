## 1. ripgrep: counting is one of six printer kinds that replaces the match rows, and `--stats` is an additive seven-field struct that measures the search that ran

Where it lives. ripgrep has two printers. The standard printer prints match lines; the summary printer prints one line per file and is selected by an output-mode flag. The summary printer's `SummaryKind` enum has six variants, `Count`, `CountMatches`, `PathWithMatch`, `PathWithoutMatch`, `QuietWithMatch` and `QuietWithoutMatch` (READ, `crates/printer/src/summary.rs:57-95`), reached from the flags `-c/--count`, `--count-matches`, `-l/--files-with-matches`, `--files-without-match` and `-q` (READ, `crates/core/flags/defs.rs:1249-1299` for `--count`, `1324-1362` for `--count-matches`). Each flag sets `args.mode` to one `SearchMode`, so the modes are mutually exclusive and the last one wins; `--count` combined with `--count-matches` resolves to `Count` (READ, `defs.rs:1288-1290` and the test at `1313-1317`). The aggregation is therefore an output mode of the search verb, not a separate verb and not a column: the row set changes from matches to one count per file. `--stats` is a different thing: a logging-category switch (READ, `defs.rs:6518-6555`) that leaves the rows alone and appends a block at the end, "always and implicitly enabled when `--json` is used" and with "no effect if `--files`, `--files-with-matches` or `--files-without-match` is passed" (READ, `defs.rs:6544-6547`).

What it measures and over what unit. The `Stats` struct holds exactly seven fields: `elapsed`, `searches`, `searches_with_match`, `bytes_searched`, `bytes_printed`, `matched_lines`, `matches` (READ, `crates/printer/src/stats.rs:13-21`). The unit is the search (one file is one search), so `searches` is files searched and `searches_with_match` is files with a hit; `matched_lines` and `matches` differ because a line may hold several matches and a multiline match may span several lines (READ, `stats.rs:56-69`). Per file, `-c` counts matching lines and `--count-matches` counts individual matches; `--count-matches` forces stats tracking on because the match count only exists in the stats (READ, `summary.rs:112-122`, `requires_stats`, and `summary.rs:764-773` where `CountMatches` prints `stats.matches()`). The struct implements `Add`, `AddAssign` and `Default`, and the parallel driver folds each worker's `Stats` into one behind a `Mutex` (READ, `stats.rs:107-148`; `crates/core/main.rs:136-138` for the serial fold and `main.rs:166` for the mutex). Additivity is the whole design for parallelism: every field is a sum, including elapsed time, so the "seconds spent searching" line exceeds wall-clock when threads overlap (EXECUTED: `0.027395 seconds spent searching` against `0.009385 seconds total` in `rg-transcript.txt`).

How the caller chooses the grain. There is no grain parameter: the count is always per file, the stats always per run. The only knobs are `--include-zero` (print `path:0` for files with no match, off by default "to make ripgrep behave more like grep" when on) (READ, `defs.rs:3332-3361`; EXECUTED, `rg -c --include-zero` printed `src/vfs/native.py:0`) and `-m/--max-count NUM`, which caps matching lines per file (READ, `defs.rs:3876-3916`).

How the output is shaped. Text: `path:count` lines for `-c`, and for `--stats` an eight-line footer (`N matches`, `N matched lines`, `N files contained matches`, `N files searched`, `N bytes printed`, `N bytes searched`, two timings) (READ, `main.rs:461-481`; EXECUTED in `rg-transcript.txt`). JSON: the printer emits JSON Lines with four message types, `begin`, `end`, `match`, `context` (READ, `crates/printer/src/json.rs:130-152`); every `end` message carries a `stats` object for that one file with `searches` always 1 (READ, `json.rs:231-244` and `338-341`), and the binary adds a fifth message type, `summary`, whose `data.stats` is the same seven-field object summed over the run plus an `elapsed_total` (READ, `main.rs:441-459`; EXECUTED: the last line of `rg --json` was `{"type":"summary","data":{"stats":{"searches":96,"searches_with_match":10,"matches":13,...}}}`). The structured and text forms are the same struct serialized two ways (READ, `stats.rs:150-171`, the serde impl).

How truncation is reported. It is not reported as a flag; it shows up in the numbers. With `-m 1` the searcher stops a file after its first matching line (READ, `crates/searcher/src/searcher/core.rs:422-424`, `has_exceeded_match_limit` returns `Stop`), and the stats then describe that shortened search: `matches` fell from 13 to 10 and `bytes searched` from 1,659,826 to 1,285,267 (EXECUTED, the two `--stats` blocks in `rg-transcript.txt`). So ripgrep's stats are a record of work done, not of the corpus; nothing in the output says a cap was hit. The flag docs name a second truncation hazard: `-c` and `-l` can disagree, because `-l` quits at the first match while `-c` must read the whole file and may then hit binary data and drop the file (READ, `defs.rs:1280-1286`; `summary.rs:725-752`, where the match count is squashed to zero but "the statistics reported will still contain the match count").

On demand or maintained. Entirely on demand: ripgrep has no index and no cache; each run walks and counts (INFERRED from the absence of any persistence in `crates/core/main.rs` and the `Stats::new()` zero start at `stats.rs:27-29`).

Rights and visibility. Not modelled; ripgrep runs as the user. The one visibility rule is the ignore and hidden-file filter, which decides which files are searched and so which are counted in `searches` (EXECUTED: `96 files searched` equals `rg --files src/ | wc -l` and `git ls-files src | wc -l`, both 96).

## 2. zoekt: a 20-field `Stats` embedded in every `SearchResult`, additive across shards, that reports truncation as `FilesSkipped`, `ShardsSkipped` and a sticky `FlushReason`, while tenant-filtered documents are skipped before any counter sees them

Where it lives. `SearchResult` embeds `Stats` by value, beside `Files []FileMatch` (READ, `api.go:527-541`), so every search answer carries the block whether or not the caller wants it; there is no flag to request or suppress it. The CLI exposes it only as a debug log line, `log.Printf("stats: %#v", sres.Stats)` under `-v` (READ, `cmd/zoekt/main.go:173` and `:248`). Two further surfaces aggregate: `SearchOptions.EstimateDocCount` turns a search into a pure count, returning early with `ShardFilesConsidered = len(d.fileBranchMasks)` and no files (READ, `api.go:1024-1026`, `index/eval.go:162-165`); and the `List` verb returns a `RepoList` whose `Stats RepoStats` is the sum of each entry's `RepoStats` plus `Repos` set to the number of entries (READ, `api.go:806-852` and `900-904`; `index/eval.go:589` and `:612`). The `zoekt -l` flag is a files-with-matches mode that prints names only (READ, `cmd/zoekt/main.go:175`).

What it measures and over what unit. The search `Stats` struct has 20 fields in four families: I/O (`ContentBytesLoaded`, `IndexBytesLoaded`), funnel counts over documents (`ShardFilesConsidered`, `FilesConsidered`, `FilesLoaded`, `FilesSkipped`, `FilesSkippedDueToCancellation`, `FileCount`), funnel counts over shards (`ShardsScanned`, `ShardsSkipped`, `ShardsSkippedFilter`, `Crashes`), match counts (`MatchCount`, `NgramMatches`, `NgramLookups`, `RegexpsConsidered`) and timings (`Duration`, `Wait`, `MatchTreeConstruction`, `MatchTreeSearch`) plus the `FlushReason` enum (READ, `api.go:372-443`). The documented meaning of each funnel field is precise: `FilesConsidered` is "files for which all atom matches (including negations) evaluated to true", `FilesSkipped` is "candidate files whose contents weren't examined because a search limit was reached or the search context was canceled" (READ, `api.go:392-401`). `MatchCount` is non-overlapping matches, incremented by the number of line matches or chunk ranges per file, and `FileCount` by one per file with a match (READ, `index/eval.go:349-361`). `RepoStats` for `List` measures the corpus, not a search: `Documents`, `Shards`, `IndexBytes`, `ContentBytes`, `FileContentBytes` and three newline counts, the last noted as about 10% slower to compute at shard load but kept because "computing them outside of load time introduces a lot of complexity" (READ, `api.go:830-852`).

How the caller chooses the grain. Through limits on `SearchOptions`, not a grain: `ShardMaxMatchCount` (stop a shard after this many matches, default 100,000), `TotalMaxMatchCount` (stop across shards, default ten times the shard cap), `ShardRepoMaxMatchCount` (per repository within a compound shard, "most often set to 1 to find all repositories containing a result"), `MaxWallTime`, `FlushWallTime`, and two display truncators applied after collation and sort, `MaxDocDisplayCount` and `MaxMatchDisplayCount` (READ, `api.go:1023-1112`). The repo-level cap is a group-by-with-top-1 in disguise: with `ShardRepoMaxMatchCount = 1` the result is the set of repositories that match, one file each (INFERRED from the comment at `api.go:1039-1043` and the skip at `index/eval.go:240-246`).

How the output is shaped. A Go struct, mirrored field for field into protobuf for gRPC (READ, `api_proto.go:297-327`, the `Stats` conversions) and JSON-encoded on the web path; `Progress` is excluded from JSON because it can hold `-Inf` (READ, `api.go:530-531`). `Stats.Add` sums every field and keeps the first non-zero `FlushReason` sticky "when aggregating stats from several Zoekts" (READ, `api.go:452-478`). `RepoStats.Add` sums everything except `Repos`, "since one repo may have multiple shards" (READ, `api.go:885-898`): the one count that is not additive is set once at the top from the length of the merged list (READ, `index/eval.go:610-612`).

How truncation is reported. By counting what was not done, in three places. In the shard loop, once `MatchCount >= ShardMaxMatchCount` or the context is cancelled, the remaining `docCount - nextDoc` documents are added to `FilesSkipped` in one step, and to `FilesSkippedDueToCancellation` when the cause was cancellation rather than the cap (READ, `index/eval.go:263-271`). A shard never opened because the query was cancelled increments `ShardsSkipped`; one pruned by the ngram filter increments `ShardsSkippedFilter` (READ, `index/eval.go:150-153` and `:182-184`). Across shards, the aggregator stops dispatching once `totalMatchCount > TotalMaxMatchCount` but still drains results already in flight (READ, `search/shards.go:1130-1171`). The display truncators cut the sorted `[]FileMatch` to the doc and match caps and return `hasMore` (READ, `index/limit.go:19-67`); they do not touch `Stats`, so `FileCount` and `MatchCount` keep describing what was found before display truncation while `len(Files)` describes what was shown (INFERRED from `limit.go` mutating only the slice). `FlushReason` names why a streamed batch was emitted: `timer_expired`, `final_flush` or `max_size_reached` (READ, `api.go:350-361`). There is no exact total: `EstimateDocCount` is documented as "an upper-bound estimate of eligible documents" (READ, `api.go:1024-1026`).

On demand or maintained. Search stats are computed per request. `RepoStats` are computed once at shard load from the index and carried in the shard's `repoListEntry`, so `List` is a sum of precomputed per-shard records with no scan (READ, `api.go:830-833` and `index/eval.go:584-589`); they are invalidated by reindexing the shard (INFERRED, since the entry lives in the shard file).

Rights and visibility. Multi-tenancy is enforced inside the document loop: a document whose repository fails `tenant.HasAccess` is `continue`d before `FilesConsidered`, `FilesSkipped` or any other counter is touched, under a comment marked as a security check (READ, `index/eval.go:227-231`), and `List` does the same per repository before `l.Stats.Add` (READ, `index/eval.go:579-583`). So a caller's stats never count another tenant's documents, not even as skipped. One exception stands out: the `EstimateDocCount` early return reports `len(d.fileBranchMasks)`, the whole shard's document count, before the loop that applies the tenant check (READ, `index/eval.go:162-165` sits above the loop at `:204`), so that estimate is not rights-filtered (INFERRED).

## 3. codesearch: a `-c` printer flag on the grep and a five-line index-size report, nothing more

Where it lives. `csearch` takes the grep flags `-c`, `-h`, `-i`, `-l`, `-n` "as in grep" (READ, `cmd/csearch/csearch.go:21-26`), implemented as four booleans on the `Grep` struct: `L` (file names only), `C` (count of matches), `N`, `H` (READ, `regexp/match.go:355-363`). `cindex -stats` prints index size statistics after indexing (READ, `cmd/cindex/cindex.go:67` and `:190-192`).

What it measures and over what unit. `-c` counts matching lines per file, incremented once per line, and prints `name: count` only when the count is positive (READ, `regexp/match.go:499` and `:541-545`). `PrintStats` prints five byte sizes with a count in parentheses: the path list and number of paths, the name list and number of names, the posting lists and number of trigrams, the name index, the posting index (READ, `index/read.go:188-194`). In `-verbose` mode the search logs its funnel as it goes: "post query identified %d possible files" and "filename regexp matched %d files" (READ, `cmd/csearch/csearch.go:120-121` and `:135-137`).

Grain, shape, truncation, maintenance, rights. There is no grain choice, no structured output (text only, stats to stdout via `fmt.Printf` and funnel counts to the log), no cap and so no truncation report, and no rights model (INFERRED from the files cited). The index is rebuilt by `cindex`; the only "maintained" aggregates are the sizes the index file records about itself, read at open time (READ, `index/read.go:196-215`). codesearch is the smallest shape in this question: one count flag and one size report.

## 4. git: aggregation as flags on verbs that otherwise list, with a text footer and a tab-separated twin, binary files counted in files but excluded from line sums, and a `-s` that turns a grouped list into a counter

`grep -c` and `-l`. `git grep` has `-l/--files-with-matches`, `-L/--files-without-match`, `-c/--count` and `-m/--max-count` (READ, `builtin/grep.c:1090-1102` and `:1160`). The count loop increments `count` only while `max_count < 0 || count < max_count`, and `-c` then prints `name:count` once per file, skipping files whose count is zero under a comment that GNU grep's `bar.c:0` lines "feel mostly useless but sometimes useful" (READ, `grep.c:1696-1705` and `:1785-1800`). So `-c -m 1` prints `1` for every matching file (EXECUTED, `git grep -c -m 1 "def read" -- src` in `git-transcript.txt`), the same cap-then-count shape as ripgrep. `--max-count 0` short-circuits the whole command "to keep results consistent with GNU grep(1)" (READ, `builtin/grep.c:1308-1315`).

`diff --stat`, `--shortstat`, `--numstat`. All three read the same `diffstat_t` of per-file `added` and `deleted` counts with `is_binary`, `is_unmerged` and `is_interesting` flags (READ, `diff.c:2802-2825`). `--shortstat` sums adds and deletes over the files, drops unmerged and uninteresting zero-change files from the file count, and excludes binary files from the line sums while keeping them in the file count ("don't count bytes") (READ, `diff.c:3221-3241`), then prints the one-line footer through `print_stat_summary_inserts_deletes`, which pluralises and omits a zero side unless both are zero (READ, `diff.c:2880-2915`). `--numstat` is the structured twin: one `added\tdeleted\tpath` line per file, with `-\t-` for binary files (READ, `diff.c:3243-3270`). `--stat` prints the per-file histogram bars and ends with the same footer (EXECUTED: `git diff --stat HEAD~5 | tail -3` ends ` 105 files changed, 8049 insertions(+), 305 deletions(-)`, identical to the `--shortstat` output). The footer is therefore a rollup that the listing carries at its tail, and the machine shape is a separate flag that emits rows and no footer (INFERRED).

`shortlog -sn`. `shortlog` groups commits by author (or committer, trailer or format via `--group`) into a `string_list` keyed by identity; with `-s/--summary` the item's `util` becomes an integer counter incremented per commit, and without it a list of subjects (READ, `builtin/shortlog.c:57-95`). `-n` sorts by that counter (READ, `shortlog.c:396` and `:499-501`). Output is `%6d\t%s` per group (READ, `shortlog.c:505`). This is a group-by with count and sort, as a flag on a listing verb (INFERRED). One executed surprise: a bare `git shortlog -sn` printed nothing here because stdin was not a terminal and no revision was given, so shortlog read commits from stdin (READ, `shortlog.c:119-143`, `read_from_stdin`; EXECUTED, the empty block in `git-transcript.txt`); `git shortlog -sn HEAD` printed `867 Clay Gendron` and `44 Claude` (EXECUTED).

`rev-list --count`, `count-objects`, `ls-files | wc`. `rev-list --count` prints one integer, or `left\tright` and `left\tright\tsame` under `--left-right` and `--cherry-mark` (READ, `builtin/rev-list.c:1121-1128`; EXECUTED, `911`). `count-objects -v` prints eight `key: value` lines (`count`, `size`, `in-pack`, `packs`, `size-pack`, `prune-packable`, `garbage`, `size-garbage`) (READ, `builtin/count-objects.c:155-162`; EXECUTED in `git-transcript.txt`); its sizes are in KiB unless `-H` (READ, `count-objects.c:93`). `ls-files` has no count of its own; the count is `wc -l` on its rows (EXECUTED, `96`).

Maintenance and rights. Every git aggregate here is computed on demand from the object store or the index, none is cached, and none is rights-aware beyond the pathspec the caller gives (INFERRED from the cited builtins).

## 5. tokei: a three-level additive rollup (file `Report` to `Language` to `Languages::total`) with an `inaccurate` flag that ORs upward, a JSON shape that is the map with no total row, and per-file rows only on `--files`

Where it lives. tokei is a library with a CLI. `Languages` is a newtype over `BTreeMap<LanguageType, Language>` (READ, `src/language/languages.rs:16-23`); `get_statistics(paths, ignored, config)` walks, fills it, then calls `total()` on every language in parallel (READ, `languages.rs:79-87`). The CLI's `--files` prints per-file rows, `--output json|yaml|cbor` selects the structured form, `--sort` orders languages by `files`, `lines`, `blanks`, `code` or `comments`, `--exclude` removes paths (READ, `src/cli.rs:38-53`; `README.md:244-267`).

What it measures and over what unit. The leaf is `CodeStats`: `blanks`, `code`, `comments`, plus `blobs: BTreeMap<LanguageType, CodeStats>` for embedded languages (a Rust block inside Markdown) (READ, `src/stats.rs:7-19`); `lines()` is derived as the sum of the three (READ, `stats.rs:28-32`). A `Report` is a `CodeStats` with a file `name` (READ, `stats.rs:70-78`). A `Language` holds the three totals, `reports: Vec<Report>`, `children: BTreeMap<LanguageType, Vec<Report>>` and `inaccurate: bool` (READ, `src/language/mod.rs:12-27`). Files and bytes are not measured; the file count printed in the table is `reports.len()` (INFERRED from the struct and the `Files` column in `README.md:20-35`).

How the rollup works. `Language::add_report` pushes the report and copies each embedded blob into `children` keyed by the embedded language (READ, `mod.rs:50-59`). `Language::total` recomputes the three totals by summing `reports` (READ, `mod.rs:103-117`). `Language::summarise` folds `children` back into the parent's counts (READ, `mod.rs:72-84`), and `CodeStats::summarise` does the same recursively over `blobs` (READ, `stats.rs:37-49`). `Languages::total` builds a synthetic `Language` by summing each language's `summarise()` and ORing `inaccurate` (READ, `languages.rs:103-114`). Every level implements `AddAssign` and the `Language` impl also ORs `inaccurate` (READ, `stats.rs:52-68`, `mod.rs:167-176`), so the rollup is addition at every step and the quality flag propagates by OR to the total; the CLI prints a marker beside flagged rows and a footnote "results can be inaccurate for languages marked with" it (READ, `src/cli_utils.rs:173-182` and `:202`).

How the output is shaped. Text: a table with one row per language, nested `|-` rows for embedded languages with a `(Total)` subtotal, and a final `Total` row (READ, `README.md:20-35`; `cli_utils.rs:486-491`, `print_total`). JSON: `Languages` serializes as its inner map, so the document is `{ "<LanguageType>": { blanks, code, comments, reports: [ { name, stats: { blanks, code, comments, blobs } } ], children, inaccurate } }` (READ, `languages.rs:25-32` and the derives at `mod.rs:13` and `stats.rs:8` and `:71`); the total row is not in the JSON, it is computed by `Languages::total` at print time (INFERRED from `cli_utils.rs:487`). JSON can also be read back with `--input` and merged by `AddAssign` into a new run (READ, `languages.rs:34-61`, `from_previous`; `README.md:230-236`).

Truncation, maintenance, rights. There is no cap and no truncation report; `inaccurate` is the only quality signal, and it marks parsing trouble, not incompleteness (READ, `mod.rs:25-26`, `:61-65`). Nothing is maintained between runs except through `--input` (READ, above). No rights model (INFERRED).

## 6. scc: a per-file `FileJob` folded into per-language `LanguageSummary` and run-wide sums in a `summaryTotals` that merges by addition, with `--by-file` deciding whether leaves are retained, and a footer of COCOMO cost, ULOC and bytes processed

Where it lives. scc is a CLI with package-level option variables: `Files` (`--by-file`), `Format` (`-f`), `FormatMulti`, `SortBy` (`-s`), `Cocomo`, `UlocMode`, `Percent`, `Dryness`, `Complexity` (READ, `processor/processor.go:74-154`; `README.md:316-402` for the flags, `:346` listing the formats `tabular, wide, json, json2, csv, csv-stream, cloc-yaml, html, html-table, sql, sql-insert, openmetrics`). `fileSummarize` dispatches on `Format` to one formatter per shape (READ, `processor/formatters.go:139-170`).

What it measures and over what unit. The leaf `FileJob` carries `Bytes`, `Lines`, `Code`, `Comment`, `Blank`, `Complexity`, `Cognitive`, `WeightedComplexity`, `Uloc` and the booleans `Binary`, `Minified`, `Generated` (READ, `processor/structs.go:181-211`). `LanguageSummary` adds `Count` (files), `Bytes`, `CodeBytes`, `ULOC`, optional percentage pointers (`CodePercent` and six more, `omitempty`) and `Files []*FileJob` (READ, `structs.go:258-280`). `summaryTotals` holds the per-language map and eight run-wide sums, `sumFiles` through `sumBytes` (READ, `processor/summary_totals.go:15-36`).

How the rollup works and what it costs. `summaryTotals.add` folds one file into the eight sums and into its language's summary, appending the `FileJob` to `Files` only when `keepFiles` is set, "which only the --by-file output needs. Leaving it off is what stops a whole tree of jobs staying alive until the run ends" (READ, `summary_totals.go:16-19` and `:48-86`). `merge` folds another worker's totals in, and the comment states the invariant: "Addition is the only operation, so the result does not depend on the order the workers finish in" (READ, `summary_totals.go:88-117`). The tabular formatter passes the `Files` flag as `keepFiles` (READ, `processor/formatters_tabular.go:75` and `:288`). The percentages are computed once at the end from the sums (READ, `processor/formatters_json.go:9-36`).

How the output is shaped. Tabular: one row per language, a `Total` row, then footer lines `Estimated Cost to Develop (organic) $N`, `Estimated Schedule Effort`, `Estimated People Required`, and `Processed N bytes, N megabytes (SI)` (READ, `README.md:445-451`; `processor/formatters_cost.go:86-97`), with `Unique Lines of Code (ULOC)` and `DRYness %` under `-u` and `-a` (READ, `formatters_tabular.go:24-27`). JSON (`--format json`): an array of `LanguageSummary` objects (READ, `formatters_json.go:40-50`). `json2`: an envelope with `languageSummary`, `estimatedCost`, schedule and people fields, and an optional `estimatedLLMCost` (READ, `formatters_json.go:56-111`). The `Cognitive` field is emitted only when the metric is enabled, through a custom `MarshalJSON` (READ, `structs.go:212-233` and `:282-293`). The COCOMO figures are a function of the single `sumCode` number (READ, `formatters_cost.go:57-71`), so the "estimate" footer is a derived view of one total, not a separate measurement (INFERRED).

Truncation, maintenance, rights. No cap and no truncation report; `Binary`, `Minified` and `Generated` are per-file exclusion flags, not incompleteness markers (READ, `structs.go:200-202`). Nothing is maintained between runs. No rights model (INFERRED).

## 7. Comparing the six

Where aggregation lives. Four of six put counting in the printer: ripgrep's `SummaryKind`, git grep's `count`/`name_only`, codesearch's `Grep.C`/`Grep.L`, and zoekt's `-l`. In every case the count mode replaces the match rows with one row per file, and the modes are mutually exclusive (READ, section 1 for the enum, section 4 for `goto next_line` under `opt->count`). The stats block is a different channel in every tool that has one: a footer (ripgrep text, git `--shortstat`, scc), a distinct message type (ripgrep JSON `summary`), or a struct embedded by value in every result (zoekt). No tool in this question exposes an aggregate as a column the caller asks for; the closest is tokei's and scc's per-file rows, which exist only under `--files` or `--by-file` and are leaves of the rollup rather than rollups themselves (READ, sections 5 and 6).

What is measured. Two families. Search tools measure the work: searches, files considered, bytes loaded, matches, skipped files, time (ripgrep's seven fields, zoekt's twenty). Code counters measure the corpus: files, lines by class, bytes, and quality flags (tokei, scc). git has one of each: `diff --shortstat` measures a change set, `count-objects` the store. Every one of them keeps the total additive, with the single exception of zoekt's `RepoStats.Repos`, which is set from a list length because one repository spans shards (READ, `api.go:885-898`); that is the one place in six projects where a count is not a sum, and the code says why.

How truncation is reported. Nobody reports an exact total before truncation. ripgrep and git grep shrink the counts silently when `-m` is set (EXECUTED, both transcripts). zoekt is the strongest: it reports the number skipped and partitions it by cause (`FilesSkipped`, `FilesSkippedDueToCancellation`, `ShardsSkipped`, `ShardsSkippedFilter`, `FlushReason`), while its only "total" is documented as an upper bound (READ, section 2). tokei's `inaccurate` is a quality flag ORed up the rollup, which is the one example here of a result-level truth flag on an aggregate (READ, section 5). vfs's planned "total before truncation and whether it is exact" is therefore stronger than any of these; the evidence supports carrying the skipped count and its reason beside the flag (INFERRED).

On demand versus maintained. Five of six compute on demand every run. The only maintained aggregate is zoekt's per-shard `RepoStats`, computed at shard load, summed at `List`, and refreshed by reindexing, with the newline counts kept there despite a measured 10% load cost because computing them anywhere else "introduces a lot of complexity" (READ, `api.go:830-833`).

Rights. Only zoekt has a rights model, and its rule is the useful one: a document the caller may not see is skipped before any counter increments, so it appears in no statistic, not even as skipped (READ, `index/eval.go:227-231`). The one count that bypasses the loop, `EstimateDocCount`, reports the whole shard (READ, `index/eval.go:162-165`), which is exactly the leak shape vfs's posture forbids (INFERRED).

Design moves vfs should adopt. ADOPT: the additive stats struct as a side channel on every result (ripgrep's `Stats` with `Add`/`AddAssign`, zoekt's `Stats.Add`, scc's `summaryTotals.merge`), with `entries considered`, `entries returned`, `bytes` and a `skipped` count partitioned by reason as zoekt does, so that chunked SQL statements and parallel legs merge by addition and a cap shows up as a named skipped quantity rather than a silently smaller number. ADOPT: zoekt's rule that rights filtering happens before any counter is touched, so a hidden row is absent from every statistic rather than counted as skipped, and the corollary that any fast-path count (an `EstimateDocCount`) must run through the same gate. DO NOT ADOPT: the printer-mode design in which `-c`, `-l` and the match listing are mutually exclusive modes that stop at different points and so can disagree with each other, documented as an accepted bug in ripgrep (READ, `summary.rs:735-743`); vfs's column model should let a count and the rows it summarises come from one pass so they cannot diverge.

## What this study does not settle

The tokei and scc build experiment was skipped by the coordinator's instruction, so their JSON shapes are described from source and README, not from an executed run over `src/`. ripgrep's searcher-level `max_count` documentation was not read beyond the flag definition and the `has_exceeded_match_limit` stop; the exact interaction of `--max-count` with `--after-context` is taken from the flag doc (READ, `defs.rs:3903-3905`) rather than traced. zoekt's web UI and `zoekt-webserver` JSON endpoints were not read, so whether the web path exposes `Stats` to end users beyond the `-v` log line is not established here. codesearch's `csweb` was not read. The study did not measure the memory of retaining leaves under `--by-file`; it reports scc's own stated reason for the toggle. No clock figures beyond the two ripgrep runs are reported, and those are facts about this machine, not benchmarks.

## One line

Six tools agree that a count is an output mode that replaces rows and a stats block is an additive side channel that measures the work done; only zoekt reports what a cap skipped and why, and only zoekt filters rights before counting, and both of those are the moves vfs should take.
