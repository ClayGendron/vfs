# livegrep / roaring / caching (raw agent findings)

## Topic A — livegrep / suffix arrays
- Build: concatenate whole corpus into one flat buffer, suffix array via libdivsufsort (earlier hand-rolled radix sort "often went quadratic"); no inverted index — SA indexes every substring. (blog.nelhage.com/2015/02/regular-expression-search-with-suffix-arrays/)
- Dedup is a build-time input step, not an index structure: index.bytes vs index.bytes.dedup, index.lines(.dedup), index.content.chunks, timer.index.divsufsort (livegrep issue #25).
- Regex→query: tree of character-range narrowings — locate SA range for first char class, subdivide within each range for next char, recursively; each narrowing = binary search. Positions sorted, coalesced into ranges, RE2 run once per range. Filename restriction does NOT prune the walk (`. file:zzzz` among slowest — post-filter only).
- Memory: README — "index file... usually 3-5x the size of the indexed text"; mmap works out-of-RAM but degraded ("perform better if the file can be loaded entirely into memory... fast SSDs recommended"). 32-bit SA = 4 B/corpus byte + compressed corpus.
- Access pattern: each binary-search probe = two random accesses (SA[mid] + corpus dereference at arbitrary offset); O(log n) probes per range boundary, many boundaries per regex. Cursor writeup: binary search vs trigram "direct hash lookups"; SA monolithic, non-incrementally-updatable (cursor.com/blog/fast-regex-search).
- VERDICT: DOA as SQL rows. (1) Probe amplification: one row fetch per probe, ~30 probes/binary search on 2^30 corpus, random corpus dereference per probe, unbatchable. (2) Epoch mismatch: monolithic sorted permutation over concatenated corpus — any change re-permutes globally; epoch rebuild would rewrite 4-8 B/corpus-byte of rows; no row-granular unit. Viable only RAM-resident, the design vfs avoids.

## Topic B — Roaring bitmaps
- Structure: 2^16-value chunks by high 16 bits. ≤4096 values → array container (sorted uint16); >4096 → bitmap container (8 kB fixed); run containers (RLE) added in follow-up paper for long-run data (arXiv:1402.6407 §2; arXiv:1603.06549). 4096 threshold ⇒ never >16 bits/int. First-level key array cache-resident; per-container cardinality cached.
- Compression boundary (load-bearing for vfs): Roaring floor 16 bits/value in sparse chunk; delta-varint ~8 bits/value on dense-in-value-space docids. Papers assume density >0.1%: "When applications encounter integer sets with lower density (less than 0.1%), a bitmap is unlikely to be the proper data structure" (1402.6407 §2). Rare-trigram postings are exactly sub-0.1% — Roaring a wash or loss there. Dense postings: Roaring wins decisively (2^16 bits fixed regardless of cardinality). vs Concise/WAH: 50%/25% space on sparse, but 30% worse where long runs of ones (pre-run-container).
- Intersection: merge over key arrays O(n1+n2), then per-container ops. bitmap×bitmap = 1024 word ANDs + popcnt; bitmap×array = bit tests, no decode; array×array = merge, or GALLOPING (exponential probe + binary search) when cardinalities differ >64× (1402.6407 §4). Measured ×4–×5 vs Concise/WAH; "up to 900× faster for intersections" vs RLE formats (abstracts). NOTE: no published Roaring-vs-delta-varint intersection benchmark — unproven for vfs's specific case.
- Adoption: Lucene RoaringDocIdSet (cached filter sets <1% density; FixedBitSet above — LRUQueryCache javadoc), Elasticsearch, Druid (roaring bitmap indexes in immutable segments), ClickHouse (groupBitmap; Set<32 elems, roaring above), Spark, Pinot, Hive, Doris, InfluxDB, StarRocks, Sourcegraph, Procella (roaringbitmap.org). Postgres: pg_roaringbitmap — real `roaringbitmap` column type, &,|,#,- operators, rb_and_agg etc., CRoaring-compatible portable format (github.com/ChenHuajun/pg_roaringbitmap).
- Serialization: RoaringFormatSpec — cookie header, descriptive header (key, cardinality−1)/container, OFFSET HEADER of 32-bit byte offsets per container "enabling random access without full materialization", payloads. Cross-language (CRoaring/Java/Go interop). CRoaring frozen format for mmap (roaring_bitmap_frozen_view, little-endian, COW).
- VERDICT: adaptable, selectively, keyed on density. Portable format drops into BLOB/BYTEA/VARBINARY unchanged; offset header allows seeking to one container without decoding all — beats delta-varint's decode-from-byte-0. pg_roaringbitmap can push intersection server-side (Postgres only). But wrong encoding for sparse tail (16 vs 8 bits/docid). Defensible design: per-blob encoding tag — roaring for dense/high-cardinality grams, delta-varint for sparse tail. Caveat vs cost model: shrinking posting blobs moves a small denominator; real win = intersect speed + server-side intersect, not index size.

## Topic C — query/result caching
- Lucene node query cache (LRUQueryCache): filter clause results as docid bitsets PER SEGMENT; default 10% heap, 10k queries LRU; only segments ≥10k docs and ≥3% of shard ("at most 33 leaves... limiting linear-time operations"). Value: RoaringDocIdSet <1% density else FixedBitSet. (elastic node-query-cache-settings; Lucene LRUQueryCache javadoc)
- Shard request cache: whole per-shard result objects (hits.total, aggs; size=0 only by default). Key: "A hash of the whole JSON body... if keys are output in a different order then the cache key will not be recognized." Invalidation: "invalidated automatically whenever the shard refreshes... or when you update the mapping." (elastic shard-request-cache doc)
- Philosophy: segments immutable → (query, segment) cache entries never go stale; never invalidated, just die when segment merged away ("Frame of Reference and Roaring Bitmaps" — elastic blog; "Dynamic Indices" guide). Request cache = coarse unit, frequent invalidation (dashboards); filter cache = fine unit, survives refresh, dies with segment.
- VERDICT: direct mapping; epoch id is a strictly better key than segment id (whole-corpus granularity, one bulk drop on reclaim). Cache granularities, all keyed (epoch, …):
  1. (epoch, gram) → posting blob — highest reuse, Lucene's biggest investment.
  2. (epoch, normalized_query) → candidate docid set — canonicalize query before hashing (ES JSON-order sharp edge).
  3. (epoch, normalized_query) → final result — cheapest hit, narrowest key.
  4. (epoch, docid) → content — LRU byte-budgeted content cache; attacks the DOMINANT cost; Lucene gets this free from OS page cache over immutable segment files, vfs must build it explicitly.
- Operational notes: budget caches in BYTES not entries; Lucene's don't-bother heuristic (skip caching tiny leaves/postings where re-execution is cheaper than cache overhead).
