# Chunk-level verification + CDC/dedup (raw agent findings)

## 1. Search-side sub-document granularity
- Zoekt: postings ARE corpus-global rune offsets (shard_builder.go:166, :215); doc recovered after the fact via fileEndRunes (write.go:169) — candidate unit is a byte position; existence proof for sub-document granularity in this exact domain.
- FTS5 detail=full: doclist = varint rowid + poslist (size varint + per-column collist, delta varints) — sqlite ext/fts5/fts5_index.c:144-169; detail modes FTS5_DETAIL_FULL/NONE/COLUMNS at fts5Int.h:285-287. Granularity ladder full→columns→none is a document-region dial. BUT positions are token ordinals, not byte offsets — can't drive a fetch range without a forward map; FTS5 still fetches the whole row for snippet/highlight.
- Lucene highlighters: offsets from postings (DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS), term vectors with offsets, or re-analysis — the stated trade is "significantly larger index" vs re-analysis at query time (UnifiedHighlighter / TokenSources docs). Same trade vfs faces.
- Lucene stored fields = closest structural analogue to a chunks table: bodies compressed in ~16KB LZ4 blocks within chunks; per-chunk metadata stores original lengths so the decompressor "can stop decoding as soon as enough data has been decompressed" — bounded fetch by design (Lucene50StoredFieldsFormat docs; jpountz blog on stored-fields compression).
- Block-max WAND (Lucene 8): per-block impact metadata lets scorers skip whole posting blocks; 3-7x term queries, up to 15x disjunctions (Grand et al. ECIR 2020; LUCENE-8135; Elastic blog). Transferable SHAPE: cheap per-block summary between posting list and payload → vfs analog: per-chunk trigram summary (Bloom/bitmap) to reject a chunk without fetching bytes.
- BitFunnel (SIGIR 2017): bit-sliced Bloom signatures per doc, sharded by doc term count; document-granularity, no positions, false positives resolved downstream — the design point MOST like vfs today (coarser, not finer). Its length-sharding concedes doc-size heterogeneity is what wrecks doc-granularity signatures.
- Elasticsearch semantic_text: chunks long fields (~250 words, 100-word OVERLAP), each chunk a nested Lucene doc; "chunks are stored as start and end character offsets... pointing to the exact location of each chunk within the original input text"; per-passage scoring (elastic semantic_text reference; search-labs chunking posts). DIRECT production precedent for "postings point at chunks; chunk = (start,end) offset range; overlap handles straddle."

## 2. borg / restic CDC
- borg (borgbackup docs, data-structures; discussion #6639): buzhash rolling hash, cut when low HASH_MASK_BITS bits zero; defaults min 512 KiB (2^19), max 8 MiB (2^23), target ~2 MiB (2^21), window 4095 B. "Buzhash is only used for cutting... NOT used as the deduplication criteria" — dedup key = separate strong id_hash of chunk contents; repo index maps 32-byte key → (segment, offset). Min/max clamps also bound hashing work.
- restic (doc/design.rst): Rabin fingerprints, 64-byte window; per-repo random irreducible polynomial (watermark-attack hardening); files <512 KiB unchunked; blobs 512 KiB–8 MiB targeting ~1 MiB; identity = SHA-256; content-addressed throughout. Payoff: only modified blobs re-saved even with arbitrary insertions.
- Both converge min 512 KiB / max 8 MiB / target 1-2 MiB — tuned for dedup-ratio vs index overhead in backup stores, NOT for verification-fetch amplification. Do not import uncritically.

## 3. seaweedfs / juicefs — both offset-based, neither CDC
- juicefs: file → 64 MiB chunks, purely positional ("chunk division remains fixed" — docs/en/introduction/architecture.md:36; const chunkSize = 1<<26 at pkg/chunk/cached_store.go:40, boundary guard :268-269); chunk → slices (one contiguous write, may overlap; latest wins per position; architecture.md:40, 61-65); slice → 4 MiB blocks, physical object unit; reads use S3 Range so only overlapping blocks fetched (architecture.md:44; io_processing.md). Fragmentation → async compaction (architecture.md:67). Explicitly NO dedup — "too expensive on large-scale data" (juicefs_vs_s3ql.md:21, :40). Keying = (inode, chunk index, slice id).
- seaweedfs: FileChunk carries offset + size + FileId (volume/key/cookie) — weed/pb/filer.proto:183-197; identity = physical needle address, not content hash. Default split 4MB (-maxMB; weed/command/filer.go:105, filer_copy.go:58); copy path slices arithmetically (filer_copy.go:456,467). Chunk MANIFEST: batches of ≤10,000 chunks collapsed into a manifest chunk (filechunk_manifest.go:23 ManifestBatch=10000, :214 MaybeManifestize, :277; proto :194,199-201) — two-level index so entry rows don't carry unbounded chunk lists.
- seaweedfs read path IS "fetch only overlapping chunks": ViewFromChunks(ctx, lookup, chunks, offset, size) resolves visible intervals over [offset, offset+size) and clips (filechunks.go:188,196; clip at :210 chunkStart,chunkStop = max/min; OffsetInChunk :215/:154; readResolvedChunks filechunks_read.go:10).
- Summary: filesystems needing O(1) offset→chunk use fixed arithmetic boundaries; CDC lives in backup/dedup world; CDC destroys arithmetic "which chunk holds byte N".

## 4. Synthesis
- Keying: entry+ordinal, NOT content hash. Content-hash keying serves dedup only and costs the positional lookup (needs an offset table anyway). Every positional-retrieval system keys by entity+position (juicefs, seaweedfs, ES semantic_text (start,end)). Recommended: PK (entry_id, ordinal) + indexed start_offset/end_offset columns → range predicate WHERE entry_id=? AND end_offset>lo AND start_offset<hi (mirrors filechunks.go:210). Dedup, if wanted, = secondary content_hash column (borg's cut-vs-identity split).
- Fixed-size boundaries, not CDC: vfs re-chunks whole entries on write, so CDC's stability is unused; CDC costs rolling hash over every byte + loss of arithmetic mapping. Revisit only for cross-version chunk-body dedup (then borg is the template).
- Size: dedup numbers (512 KiB floor) are WRONG for this use — median source file smaller than one borg minimum chunk → chunk-level verification degenerates to whole-file. Retrieval-side precedents: Lucene 16 KB blocks (bounded decompression), juicefs 4 MiB blocks, seaweedfs 4 MB. For grep over source: anchor 16-64 KiB; sanity-check vfs's body-size distribution first — if p50 body < chunk size, only the tail pays.
- Boundary straddle, three answers: (1) overlap chunks (ES: 100-word overlap; for trigram attribution 2 bytes suffices; for regex verification, ~max-line-length); (2) fetch chunk+neighbors: expand candidate pos ± max_match_len, fetch all overlapping chunks (seaweedfs clip pattern) — zero storage cost, ≤2x fetch at boundaries; (3) LOAD-BEARING CORRECTNESS: the straddle fix must land at INDEX time for postings — a straddling trigram dropped at index time is a false negative, unrecoverable at query time (a chunk containing no indexed trigram of the pattern is never fetched). Fetch-time expansion alone fixes only the fetch, not candidate generation.
- Also steal: per-chunk trigram Bloom/bitmap beside the chunk row → reject chunk without reading body (block-max WAND shape; Lucene stored-field length metadata shape).

## Draft verdict (agent's)
ADAPTABLE, leaning direct, one hard constraint. Mainstream design point approached from two directions (zoekt positions; ES semantic_text chunk postings with overlap; Lucene bounded stored-field decompression; seaweedfs range-clipped chunk fetch). Costs: index format change (postings become (doc, chunk-ordinal) or (doc, position)) — the Lucene term-vectors trade. Straddle fix at index time or silent false negatives. Don't import CDC or borg/restic sizes; key (entry_id, ordinal) + offsets; 16-64 KiB; payoff concentrated in the tail — measure body-size distribution before committing.
