# Study 02: what vfs could check and what each check costs

The brief asked for every invariant the store holds across rows, where each can break, what each verb does once it is broken, what the tests already audit, what a check of each would cost at the reference deployment in [AGENTS.md](../../../../AGENTS.md), what `scrub`, `rebuild` and `refresh` are, what the rows already know about references between files, and who may run each check. It was answered against vfs commit `08c372affd1730739c27aec84b8e94e0d6ef1e87` (`git rev-parse HEAD`, branch `main`, with uncommitted context files and no change under `src/` or `tests/`). The code under `src/vfs` and the audits under `tests/` were read, and eight probes were run on the in-memory store (`InMemoryStorage`, an in-process SQLite) as `uv run --no-sync python <script>`. Every probe and its output is in [experiments/](experiments/lint_common.py). No pytest, no Docker and no database server ran. The work took about 20 minutes of the 45-minute box by the wall clock, and it stopped because the brief's list was covered, not because the box ran out.

EXECUTED means a command ran here and the claim reports its output. READ means read in a file cited by path and line. INFERRED means the researcher's reasoning from the two.

## 1. The answer in one paragraph

vfs holds its integrity in application code, not in the database: the schema has no foreign key at all, so every cross-row rule is kept by the verbs and by nothing else (READ, [rows.py](../../../../src/vfs/models/rows.py), every table). When a rule is broken underneath the verbs, almost nothing notices (EXECUTED, sections 4 to 6). Eighteen kinds of damage were planted, and only these were noticed: `rebuild` repaired segment postings and the parent-child edge mirror and deleted edges to a missing row, each with a warning; an `edit` of a file with no body row was refused, under the wrong kind; an index lease left behind was refused and then healed by its own timeout; a version number reset by SQL made every later overwrite fail; and a relabel mark with no posture row made the calls of named and anonymous callers raise an unclassified `KeyError`. Everything else was served as success. Four findings matter most. A wrong label lets an anonymous caller `glob` and `grep` a file that `read` refuses. A row stamped as indexed that the index does not hold is invisible to `grep` for good, across `refresh` and `rebuild`. A grant on a purged path applies to the next file written at that path. And an entry whose `version` sits below its own version rows refuses every overwrite with the database's raw constraint text, so the file is locked against writing. Every one of these is found by a plain SQL read that seeks an index, one statement per page of rows, with no lock (EXECUTED, section 9). The structure checks cost one visit per entry row, about 11 million a day if run once over the whole mount. The bytes check costs every stored byte and cannot ride any pass that exists. The content layer already has typed link rows, and rows alone answer three wiki questions: a link to a deleted file, a file nothing links to, and two files with one hash. Rows alone cannot answer the fourth, a link to a path that never existed, because the extractor counts such references and stores none of them.

## 2. The store, and what is truth in it

READ. One mount is 24 tables built in [rows.py](../../../../src/vfs/models/rows.py) (`build_vfs_tables`, line 385). The identity of a file is `entry_id`, a ULID (a 128-bit, time-ordered identifier). Every dependent table keys on it: bodies (`vfs_content`, `vfs_blobs`), history (`vfs_versions`, `vfs_version_subjects`), index rows (`vfs_chunks`, `vfs_lex_docs`), path-segment postings (`vfs_segments`), edges (`vfs_edges`) and ranking signals (`vfs_signals`). The module docstring calls `path` "a regenerable cache (unique, binary-collated) that nothing references" and `parent_id` "the one structural pointer" (lines 10 to 18). The rights tables key on other things: `vfs_grants` on a path prefix as text (line 841), `vfs_memberships` on principal names.

READ. The database itself enforces only these: `UNIQUE(path)` (line 432), `UNIQUE(entry_id)` (line 429), `UNIQUE(parent_id, name)` (line 486), the primary keys of the dependent tables, `UNIQUE(source_id, target_id, edge_type)` on edges (line 632), a partial unique index giving each entry at most one `fs` in-edge, emitted only on SQLite, Postgres and SQL Server (lines 638 to 646), and a `CHECK (id = 1)` on the three single-row tables (lines 669, 684, 694). There is no `FOREIGN KEY` anywhere. The sweep's own docstring says so: "The schema carries no foreign keys" ([trash.py](../../../../src/vfs/storage/backends/database/trash.py), line 622).

INFERRED. So there are two kinds of column. Some are truth: the body, `parent_id`, `name`, the grant and posture rows. The rest are derived from the truth and stored for speed: `content_hash`, `size_bytes`, `lines`, `path`, the segment postings, the `fs` edges, `everyone_level`, the index flags, the chunk and posting rows, the extracted link edges. A lint is a comparison of a derived column against its truth, plus a search for dependent rows whose owner is gone.

Two things the brief listed are not invariants today. First, a grant on a path that no longer exists: a grant is a prefix, not a reference to a row, and nothing removes it when its row is purged (READ, `rows.py:831` to `849`; the one `delete` on the grants table a grep of `src/vfs` finds is in the revoke path, `rights.py:1016`; EXECUTED, p03 D2). The brief also named "closure rows". There is no closure table; the nearest thing is `vfs_segments`, row 7 above (READ, `rows.py:734` to `745`).

## 4. The audits the tests already run

READ. `_audit` in [test_races.py](../../../../tests/storage/database/test_races.py) (lines 79 to 97) is the only whole-store integrity audit in the tree. It issues two statements: `SELECT entry_id, parent_id, path, name FROM vfs_entries` with no filter, and `SELECT entry_id FROM vfs_content`. It loads both whole tables into Python and asserts four things: a row with no parent has path `/` ("rootless row"); every `parent_id` names a loaded row ("dangling parent_id"); `path` equals the parent's path plus `/` plus `name` ("torn path cache"); and no content row names an entry that is not loaded ("orphan content rows"). That is invariants 4 and 5 in part, and the body half of 10. It is called at 30 sites across the race tests, on the server engine legs only, so it never runs in the default local suite (lines 14 and 15 of the module docstring).

READ. It does not check: any hash (1 to 3), the parent's kind or a cycle (5), tombstones (6), segments (7), `fs` edges (8), edge endpoints (9), blobs, versions or chunks without an entry (10), labels (12), index cover (14) or links (15).

READ. The other audits are narrower. `_content_bytes_audit` in `tests/storage/test_conformance.py:835` compares each engine's cast of a text body to bytes against the UTF-8 vfs wrote. `assert_lexical_fidelity` in `tests/support/lexical_fidelity.py:158` referees the stored BM25 index against a pure-Python scorer. `tests/support/storage_contract.py:1583` asserts a cascade delete "leaves no orphans", and line 2296 that a limited walk returns "no dangling edge". None of these walks a whole store.

EXECUTED. The four `_audit` checks, written as SQL self-joins instead of Python over loaded tables, are the first four statements of the prototype in [p02_structure.py](experiments/p02_structure.py). On a clean store all nine of its statements return nothing (p02 S0).

## 5. The bytes layer: what each verb does on a damaged body

EXECUTED, [p01_bytes.out](experiments/p01_bytes.out). Spec 175 ran the first three of these at commit `ba77449`; they were re-run here at HEAD and still hold.

| Damage planted by SQL | What happened |
|---|---|
| A text body rewritten (hash now wrong) | `read` succeeds and serves the rewritten text. `stat` succeeds. `copy` succeeds and the copy reads back the rewritten text. `edit` succeeds: version 3 is the edited damage, and the version row minted for the damaged body carries a hash that matches the damage, so history holds it looking healthy. `refresh`, `rebuild` and `sweep` report nothing. `grep` for a word of the new text returned no row, before any index pass had run again. |
| A text body row deleted | `read` succeeds with no content and `size_bytes=11`. `copy` succeeds and makes a second file with a size and no body. `edit` refuses with `vfs.wrong_kind`, "no editable content". An overwrite succeeds and heals the file. `refresh`, `rebuild` and `sweep` report nothing. |
| A bytes body row deleted | `read` with `data` projected succeeds with no data. `stat` and `copy` succeed. `rebuild` reports nothing. |
| `content_hash` set to NULL, or to a wrong value; `size_bytes` and `lines` set wrong | `read` and `stat` succeed and report the wrong size. Writing the same body again succeeds, raises the version and restores the hash, size and lines. `rebuild` changes none of them. |
| A version row's body rewritten | Nothing reads it. The row's hash no longer matches its body, and nothing says so. |

EXECUTED. A prototype of the check is one statement: a keyset page (a page that starts after the last key of the page before, here `id > :after ORDER BY id LIMIT :n`) of file rows left-joined to both body tables, hashed in the caller's process. On a store with the three faults above it returned exactly `/docs/a.md` mismatch, `/docs/b.md` missing body, `/docs/c.bin` missing body (p01 B6).

INFERRED. The damage is not only served; three verbs spread it. `copy` duplicates it, `edit` rewrites it under a fresh matching hash, and the version mint files it as history. After an `edit`, no check of the current row can tell the file was ever damaged. A lint that runs after the fact finds less than a lint that runs before the next edit, which is the argument for the read-time check spec 175 plans beside its walk.

A `write` at the true path is refused `vfs.conflict`, "the address is held by a row this write may not adopt". A `move` of the parent carries the tear along. | torn path | nothing |

INFERRED. Two rules of thumb fall out. Point reads, `tree`, `glob` and `grep` trust `path`; `ls` trusts `parent_id`. When the two disagree the same file is present to one verb and absent to another, and no verb says the store is inconsistent.

EXECUTED. A dangling parent never settles under `rebuild`. The edge pass treats `parent_id` as the truth, so it mints the `fs` edge the bad pointer asks for; the next pass sees that edge names a missing endpoint and deletes it, then mints it again. Three rebuilds in a row each returned the same two warnings ([p03](experiments/p03_dependents_rights_index.out) D8). READ: the cause is in `collect_edge_drift`, which checks an edge's endpoints against the entry ids but never checks that a row's own `parent_id` is one of them (`edges.py:298` to `307`).

## 7. Dependent rows, versions, rights and the index

EXECUTED, [p03_dependents_rights_index.out](experiments/p03_dependents_rights_index.out).

**Rows left behind.** Two entry rows were deleted by SQL. Left behind: 2 bodies, 2 version rows, 2 chunk rows, 2 lexical-index rows, 2 segment postings, 3 edges and 1 grant. `refresh` removed none. The retention `sweep` removed none, because its orphan fence is an age of 24 hours. `rebuild` removed the segment postings and the edges, with three warnings, and left the bodies, the version rows, the chunk rows and the grant. A purge done properly through `sweep` leaves two rows behind: one lexical-index row of the published epoch, which the next rebuild replaces, and the grant row, which nothing removes (D2).

**A grant outlives its file.** With `/private` set to posture `none`, alice was granted `read` on `/private/secret.md`. The file was purged with `sweep`. The grant row stayed. The system actor then wrote a different file at the same path, and alice read it ([p04](experiments/p04_content_references.out) C6). INFERRED: this is the grant model working as written, a prefix and not a row reference, but it is the one finding here that hands a person access nobody chose to give to that file.

**A wrong label.** `/q` was set to posture `none`. Then one row's `everyone_level` was raised to 5 by SQL. An anonymous `read` of it was still refused, `vfs.unauthenticated`. An anonymous `glob` listed it, and an anonymous `grep` for a word of its body returned it. A second row under a `read_write` posture had its label lowered to 0: an anonymous `read` answered `not_found` and `glob` dropped it. `rebuild` and `refresh` changed neither label. Calling `posture` again on `/q` put that region right and left the other row wrong. READ: a function that recomputes every label from the posture rows exists, `rebuild_labels` (`labels.py:388`), and no code under `src/` calls it (`grep -rn rebuild_labels src/vfs` returns its definition and one docstring mention).

**A mark left behind.** A row was inserted into `vfs_relabels` for `/p` with no posture row at `/p`. Both calls then tried, an anonymous `read` and a `write` by a named caller, raised `KeyError: '/p'` as a raw exception and not a classified `Result`. `rebuild` left the mark. An unrelated `posture` call on another path cleared it. INFERRED: the verbs cannot make this state, because the mark and its posture row are written in one transaction; it is reachable by out-of-band SQL only.

**Index cover.** A file was written and then stamped `chunked`, `encoded` and `indexable` by SQL before any index pass. `grep` for its only word returned nothing, and still returned nothing after `refresh` and after `rebuild`. READ: the schema comment says `grep` probes the rows flagged not encoded as its pending set (`rows.py:488` to `490`). INFERRED: a row flagged encoded is left to the index, and the passes select only rows flagged dirty, so nothing ever looks at this row again. Deleting the chunk rows of an indexed file instead left `grep` and `search` answering on this three-file store, and left the file with no chunk rows across `refresh` and `rebuild`.

**Versions.** Deleting one version row from a chain changed nothing any verb reported. An entry with version rows 1 and 2 then had its `version` reset to 1 by SQL. Each overwrite after that failed with `vfs.unavailable`, "write failed: UNIQUE constraint failed: vfs_versions.entry_id, vfs_versions.version_number": the mint tries to file the replaced body under a number that is taken. Two overwrites in a row failed the same way, `read` still served the file, and the driver's own text reached the caller ([p08](experiments/p08_what_rebuild_reads.out) R6). INFERRED: this is the bytes-layer worry in another column. The developer's ruling was that a wrong hash must not lock a file; a wrong version number locks one against writing today.

**The lease.** A foreign lease with a fresh heartbeat made `rebuild` and `refresh` refuse with a retryable `vfs.conflict`. With the heartbeat six minutes old, `rebuild` claimed it and ran. This one heals itself.

## 8. What `scrub` is planned to be, and what `rebuild` and `refresh` do today

READ, [spec 175](../../../specifications/active/175-integrity-verify-on-read-and-scrub/spec.md), status draft, not started. `scrub(path="/", *, after=None, limit=1000, authority=None)` is a paged, read-only walk in path order over every row at or beneath `path`, live and tombstoned. It has two phases: current bodies, then version rows. It hashes each body with `hashlib` and compares it with the recorded hash. It reports each fault as a `vfs.unavailable.integrity` error at warning severity with a reason of `mismatch`, `missing` or `unhashed`, both hashes, the body table and the version, and never a byte of the body. It returns a resumption key when it stops at `limit`. It writes nothing: "no repair, no flag, no mark". It believes a fault only when a second read in a fresh transaction agrees. It is a developer-plane verb at the `read` rung, and it refuses outright unless the caller may read every row beneath `path`. Section 6 of the spec puts orphan bodies out of scope and gives them to `sweep`. The spec covers the bytes layer only: it checks invariants 1 and 3 of section 3 and none of the others. The spec's text still carries five undecided points that it marks itself, and [the kernel rulings spec](../../../specifications/active/2026-11-15-the-kernels-public-names-and-argument-families-are-ruled.md), decision 9, has since ruled that a failed check must never leave a file that can be neither read, rewritten nor removed.

READ, [maintenance.py](../../../../src/vfs/storage/backends/database/maintenance.py). `rebuild` (line 141) is the full pass. Under the index lease it renders dirty binaries, re-chunks stale rows, builds the whole index into a new epoch and publishes it, then runs three re-convergence passes and the ranking signals (`_rebuild_phases`, lines 322 to 411). The three passes are the nearest thing vfs has to a lint today, and they also repair. Each has the same shape (`_reconverge`, line 667): a plain read collects drift, and only found drift opens a writer transaction that re-reads each row under a lock and applies the fix if the row has not changed since. The segment pass streams every segment row and every entry row and holds the postings in memory (`segments.py:168` to `190`). The edge pass streams every entry's `(entry_id, parent_id)` and every edge row, and its docstring says it "holds the corpus's ids in memory", "acknowledged rather than capped" (`edges.py:31` to `33`). The flag pass is one index seek that normally returns nothing (`flags.py:38` to `50`). Each repair is reported as a `vfs.internal` warning on the verb's `Result`, with the entry id and the delta in `data`.

EXECUTED, [p08_what_rebuild_reads.out](experiments/p08_what_rebuild_reads.out), on a store of 2,000 files. A rebuild with nothing changed still issues `SELECT entry_id, path FROM vfs_entries` and `SELECT entry_id, parent_id FROM vfs_entries` with no filter, and one unfiltered read each of `vfs_segments` and `vfs_edges`: the re-convergence passes walk the whole tree on every rebuild, dirty or not. It reads no body. A rebuild after one file changed reads `vfs_content` in one statement, for the rows flagged dirty, and then reads every chunk row's text in keyset pages (`SELECT id, entry_id, content FROM vfs_chunks WHERE id > ? ORDER BY id LIMIT ?`). So the daily rebuild already visits every entry row twice and every chunk's text once, and visits a body only when a write flagged it.

READ. `refresh` (line 152) is the incremental pass, "O(dirty)". Its docstring is exact about what it leaves out: "No segment, edge, flag or signal pass runs." It does nothing for integrity beyond indexing what writes flagged.

READ. Neither is a routed verb. They are methods on the storage object with no `authority` parameter (`backend.py:1117` to `1123`), they are not in the `Op` vocabulary ([ops.py](../../../../src/vfs/ops.py), lines 36 to 62), and no method of the router in `base.py` is named for them. Whoever holds the storage object may run them. `sweep` is a routed developer-plane verb at the `read_write` rung (`ops.py:97,165`).

INFERRED. So vfs already has a finder with a repairer for three invariants (7, 8, 9), a reclaimer for one half of one (bodies in 10), a planned finder with no repairer for two (1, 3), a repairer nobody calls for one (12), and nothing for the rest. The three finders that exist report in one shape: an error record at warning severity, a kind, a path where there is one, and a `data` dictionary.

## 9. What each check costs at the reference deployment

The reference deployment has 10,000,000 files in about 1,000,000 directories, so about 11,000,000 entry rows, and about 100,000,000 chunk rows (READ, AGENTS.md). Every check below is a plain read. None takes a lock a caller waits on. The counts in the first columns are EXECUTED on a 20,806-row store ([p05_cost.out](experiments/p05_cost.out), [p06](experiments/p06_label_plan_and_session_statement.out)), where each statement's plan was read with SQLite's `EXPLAIN QUERY PLAN`; "SEARCH" in a plan means an index seek and "SCAN" a walk of the whole table. The last column multiplies and is INFERRED.

| Check | Statement and plan measured | Whole mount | One directory or one subtree | At the reference deployment |
|---|---|---|---|---|

EXECUTED, clocks as facts about this machine only (arm64 macOS, Python 3.13.11, in-process SQLite, no network): the structure pass over 20,805 rows took 119 ms; the bytes pass over 20,000 small bodies took 103 ms, of which 33 ms was hashing; `hashlib.sha256` over 64 MB in one call took 31 ms, about 2 GB a second. Each session also issued one `BEGIN`, which is why the counters read 22 and not 21.

INFERRED, the multipliers from AGENTS.md applied.

- **Per corpus, once a day.** The structure, dependent-row, index-cover and label checks are all whole-table reads bounded per statement and resumable by a key. That is the one place AGENTS.md allows a whole-table operation. At the measured 6 microseconds a row, 11 million rows is about a minute of database work in-process; a server adds 11,000 round trips.
- **Per index visit.** Nothing here should be added per file to the rebuild's index path. A hash per index visit is the whole bytes check every day, which spec 175 section 5.7 already rejects.
- **Riding the rebuild.** The rebuild's segment and edge passes already read every entry row twice, every segment row and every edge row, every day (EXECUTED, p08 R2). The structure checks need only three more columns on the edge pass's entry stream (`path`, `name`, `deleted_at`) and no further statement. The price is memory: that pass holds its rows in a dictionary, and paths for 11 million rows are far heavier than ids. The SQL-join form of section 6 visits the same rows with no memory at all, because the database does the join. The orphan checks ride less well: they walk the dependent tables, which the rebuild's passes do not all visit.
- **The bytes check rides nothing.** The rebuild reads a body only when a write flagged it (EXECUTED, p08 R3), so a hash of every body is a read the rebuild does not make. What the rebuild does read whole is the chunk text, and each chunk row carries its own `content_hash` (READ, `rows.py:589`), so a check of chunk text against chunk hash could share that stream; it would prove the index's copy, not the file's body. 40 GB of text is about 20 seconds of hashing on one core and about five minutes on a 1 gigabit link. 5 TB of bodies is about 40 minutes of hashing and about 11 hours on the same link. It is a paged job with a resumption key and an off-peak schedule, as spec 175 plans it.
- **Per directory and per subtree.** Every structure and content check has a form scoped by `parent_id` or by a range of `path`, and its cost is the rows in scope. At a median of 2 files a directory, a directory lint is one statement. This is the form an agent can afford on a verb call: it costs what it returns.
- **Per lock.** No check needs one. Two cautions follow from the rules in AGENTS.md. Each page should be its own short transaction, so no snapshot is held open across a walk. And because pages are separate transactions, a rival's commit between two statements can look like damage, so a finding is believed only when a second read agrees, the law spec 175 section 3.3 already states and the shape `rebuild`'s guarded repair already has.

## 10. The content layer: what the rows already know about references

READ. vfs stores references between files as rows of `vfs_edges`: a source id, a target id, a type, a weight, a provenance and, for an extracted edge, the referring line folded to 256 characters (`rows.py:619` to `649`). Three kinds exist. `fs` edges mirror the tree. Authored edges are minted by `mkedge`. Extracted edges of type `links` are minted during the index pass from Markdown bodies: [models/links.py](../../../../src/vfs/models/links.py) parses inline links, images, reference definitions and code spans shaped like a path, drops URLs and anchors, and turns each destination into candidate paths, the document's own directory first and the mount root second; [links.py](../../../../src/vfs/storage/backends/database/links.py) probes the candidates among live rows and rewrites the source's extracted out-edges. A reference that resolves to nothing mints no row. It is counted, and the count rides one info record on the pass's `Result` (`links.py:106` to `114`). [Spec 147](../../../specifications/active/147-import-edge-extractor/spec.md), a seed and not scheduled, would add `imports` edges from Python import statements through the same publisher, with the same count of unresolved references and the same stamp law.

EXECUTED, [p04_content_references.out](experiments/p04_content_references.out), on a seven-page wiki.

- **A link to a path that does not exist.** The rebuild reported `vfs.not_found` at info severity: "2 markdown references across 7 documents name no live entry", with `data` of `{'leg': 'links', 'sources': 7, 'edges': 4, 'unresolved': 2}`. It names no document and no destination. No row records either reference. Rows alone cannot answer this check.
- **A target created later.** The missing page was then written, and `refresh` and `rebuild` both ran. No edge to it appeared. The source's stamp pair still matched its unchanged body, so it was skipped. The stored links are a snapshot of the tree at the time each source was last changed.
- **A link to a deleted file.** After a `delete` the edge stays and its target is tombstoned. One join over edges finds it: two rows here.
- **A link to a moved file.** After a `move` the edge follows the file's identity to its new path, while the text of the source still names the old path. The rows look healthy; a reader following the text meets a miss.
- **Re-extraction finds all of these.** Parsing the seven bodies again with the same extractor and probing the nine candidate paths took two statements, one for the bodies and one for the paths, and reported every broken reference, the moved one included. It reads every Markdown body, so it costs what the bytes check costs for those files.
- **A file nothing links to.** One anti-join on the reverse edge index. It listed five pages here, the index page among them: a page with no inbound link is not always a fault.
- **Two files with one hash.** One `GROUP BY` on the hash index found the planted pair.

INFERRED. Three wiki checks run from rows alone today: link to a tombstoned row, file with no inbound link, twin content. One needs the extractor to keep what it now only counts, or needs the bodies read again: link to a path that never existed. One is invisible to rows by design: link text that names a file's old path.

## 11. Who may run each check today, and what a finding reveals

READ. The ladder is in `ops.py:142` to `168`. `stat`, `ls`, `tree` and `glob` need `list`. `read`, `grep`, `search` and `grants` need `read`. `traverse` needs `read` and passes a node at `list`. `sweep`, `posture`, `grant` and `revoke` need `read_write`. `rebuild` and `refresh` take no authority at all (section 8). Spec 175 plans `scrub` at `read`, on the developer plane, all or nothing: "a recorded hash is an oracle for a body (it confirms a guess), so the scrub reports only to someone who may read everything it covers" (section 5.2).

EXECUTED, p04 C5: what a caller learns today about a row she cannot see. With `/private` at posture `none`, alice's `read` of a file that exists there and of a file that does not both answer `vfs.not_found` at `/private`. Her `glob` of `/private/**` is empty. Her `traverse` outbound from a page that links into `/private` returns the page alone, where the system actor's returns the hidden target too. Today's rule is that a hidden row and no row look the same.

INFERRED, each check against that rule.

| Check | Rung it fits under today's rules | What a finding could reveal |
|---|---|---|
| Body against hash | `read` on every row covered, as spec 175 rules | the recorded and actual hash confirm a guess at a body |
| Structure of rows the caller can see | `list` on each row named | a path, a kind, and that a neighbour row exists; a finding about a parent the caller cannot list names a hidden row |
| Rows with no entry (bodies, versions, chunks, edges) | none fits: such a row has no path, so no grant can be judged against it | an entry id and a table; the system actor or the developer plane only |
| Label against posture | `read`, the rung `grants` lists at, on the region | where postures sit and which rows are mislabelled; a wrong label is itself a leak, so the finding is for an operator |
| Grant on a path with no row | `read` or `read_write` on the prefix | who holds a grant on a path that is free to be written |
| Index cover | `read` on the row | that a row exists and is unindexed |
| Link to a missing or deleted target | `read` on the source; the target judged at `list` | whether a path the caller cannot list exists, unless a hidden target is reported exactly as a missing one |
| File nothing links to | `read` on the file; sources judged at `list` | nothing new if hidden sources are left out, as `traverse` inbound leaves them out today |
| Two files with one hash | `read` on both twins | a body oracle if a hidden twin is counted: write a guess, lint, and learn that a hidden file holds it |

INFERRED. Two rules fall out. A check that names a row the caller cannot see must report it as absent, or the lint becomes the existence oracle that today's reads avoid. And the checks that have no path to judge, plus those whose finding is itself a rights fact, belong to the system actor.

## 12. How finding relates to repairing, as the code stands

READ and EXECUTED, gathered from the sections above. The repairs that exist are of four kinds. `rebuild` recomputes a derived row from its truth and rewrites it under a guard: segments, the `fs` mirror, the directory flag. `rebuild` and `sweep` delete a row whose owner is gone: edges at once, bodies after 24 hours. A `write` over a file heals its hash, size, lines and body. A `posture` call finishes any standing relabel and clears every mark. Spec 175 rules that `scrub` never repairs, because a damaged body has no second copy to repair from.

INFERRED. The invariants split by whether a repair can be computed. Where the damaged column is derived and its truth is intact, the fix is a recomputation and is safe to automate: `path` from parent and name, segments, the `fs` mirror, labels, sizes, index flags, extracted links. Where the truth itself is damaged, there is nothing to recompute from and a person must choose: a body that fails its hash, a `parent_id` that names nothing, a version row with no entry. The dangling-parent loop of section 6 is what happens when a recomputing repair is run against damaged truth without checking it first.

## What this study did not reach

- **Server engines.** Every probe ran on in-process SQLite. The plans, the absence of reader waits and the page costs on Postgres, SQL Server and Oracle were not measured. The experiment is the nine statements of `p02_structure.py` and the plans of `p05_cost.py` on the four engine legs, under the `db_test` cycle.
- **The reference scale.** The largest store probed held 20,806 rows. The 11-million-row figures are multiplication. The experiment is `p05_cost.py` with `FILES` raised to 10,000,000 on a file-backed Postgres.
- **A chunk's text against its own hash.** Section 9 infers that this check could share the rebuild's read of every chunk row. Whether `vfs_chunks.content_hash` is the sha256 of `vfs_chunks.content`, and what a damaged chunk does to `grep` and `search`, was not run. The experiment is one more case in `p03_dependents_rights_index.py`.
- **What unlocks a file whose version is wrong.** Section 7 shows every overwrite failing. Whether a `delete` and a fresh `write`, or a `move`, frees the path was not run.
- **The posting tables.** The gram and lexical posting rows have stated internal rules, such as `doc_count == len(decode(postings))` (`rows.py:715` to `719`). None was broken or costed here.
- **Renderings, embeddings, signals, memberships.** A bytes row's rendering has no hash of its own (READ, spec 175 section 3.2). Stale embeddings, signal rows of a dead generation, membership cycles and `vfs_principal_revisions` were not probed.
- **`search` on damaged index rows at a useful scale.** On three files `search` returns every file, so the effect of missing chunk rows on `search` was not observable.
- **Concurrency.** No check was run beside a writer. Whether a page can report a tear that a rival's commit explains was reasoned, not executed.

## One line

vfs keeps every cross-row rule in its verbs and none in the database, the verbs notice almost no damage planted beneath them, and every kind of damage found here is visible to an index-seeking SQL read that costs one visit per row in scope, except a damaged body, which costs its bytes.
