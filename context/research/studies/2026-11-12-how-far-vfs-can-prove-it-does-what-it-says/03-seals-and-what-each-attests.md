## 1. Three kinds of seal, and which kind each one is

A seal is any mark a stranger can check without reading the code: a badge, a signature, a certificate, a report. They answer three different questions, and most confusion about trust comes from reading an answer to one as an answer to another. INFERRED from every source below.

| Kind | The question it answers | Seals of this kind |
|---|---|---|
| Built and delivered | Did these bytes come from that source, through that pipeline, untouched? | PyPI Trusted Publishing, PEP 740 attestations, Sigstore signatures, GitHub artifact attestations, SLSA build levels, reproducible builds, SBOMs (an inventory, not a guarantee) |
| How the project is run | Does the project follow the practices that make good software more likely? | OpenSSF Best Practices Badge, OSPS Baseline, OpenSSF Scorecard, cargo-vet and cargo-crev (applied to dependencies), OSS-Fuzz membership (a practice: continuous fuzzing) |
| What the code does | Does the code behave as it claims? | None of the badges. The nearest things are a security audit report (a time-boxed expert search for defects, not a certificate of their absence) and FIPS 140-3 (which certifies a cryptographic module's algorithms and boundary, and which vfs is not) |

The organisation frames a buyer asks about, SOC 2 and ISO/IEC 27001, sit outside all three: they attest an organisation's controls over a service it runs, and a library is neither an organisation nor a service. The EU Cyber Resilience Act is not a seal but a law, and it places its duties on whoever sells a product, which for vfs is the enterprise that embeds it. Sections 9 and 10 give the detail. READ (AICPA, EUR-Lex) and INFERRED.

## 2. Built and delivered: Trusted Publishing, PEP 740, Sigstore, GitHub attestations and SLSA

### 2.1 PyPI Trusted Publishing

What it is: PyPI accepts an upload authenticated by a short-lived OIDC token from a named CI workflow (GitHub Actions, GitLab CI/CD, Google Cloud are documented) instead of a long-lived API token. READ (docs.pypi.org/attestations/producing-attestations). What a passing result proves: the upload came from a run of the workflow file registered on PyPI for that project; no stored secret could have leaked. What it does not prove: anything about the workflow's inputs or the code; a compromised workflow or a malicious commit on the trusted branch publishes as easily as an honest one. INFERRED. vfs already uses it: the `publish` job in [`publish.yml`](../../../../.github/workflows/publish.yml) runs in the `pypi` environment with `id-token: write` and calls `uv publish --trusted-publishing always`. READ. Cost to vfs: none further; it is done. Whether the `pypi` environment has required reviewers or a branch rule is a GitHub repository setting this study cannot see from the tree. INFERRED.

### 2.2 PEP 740 digital attestations on PyPI

What it is: a Sigstore-signed statement, uploaded with each distribution file, that binds the file's SHA-256 digest to the Trusted Publisher identity (repository, workflow file, ref) that uploaded it; PyPI serves it from an integrity API and shows it on the file's page. PyPI rejects attestations not signed by a Trusted Publisher. READ (docs.pypi.org; PyPI blog 2024-11-14). The official `pypa/gh-action-pypi-publish` (v1.14.3, released 2026-10-20) generates and uploads them by default; `uv publish` uploads attestations it finds beside the files but does not generate them, and Astral's `astral-sh/attest-action` (v0.0.7 in its README, described there as pre-stable) generates them for `uv publish` (uv 0.9.12 or newer). READ (docs.astral.sh/uv/guides/package; github.com/astral-sh/attest-action) and EXECUTED (release dates from the GitHub API).

What a passing verification proves, run here: `pypi-attestations verify pypi --repository https://github.com/sigstore/sigstore-python pypi:sigstore-4.5.1-py3-none-any.whl` printed `OK: sigstore-4.5.1-py3-none-any.whl`; the same file checked against a wrong repository printed `Verification failed: provenance was signed by repository "sigstore/sigstore-python", expected "pypa/pip"`. EXECUTED ([pep740-verify.txt](experiments/03/pep740-verify.txt)). So the check is real and specific: it proves these exact bytes were uploaded by that repository's workflow. It does not prove the workflow built them from clean inputs, that the commit was reviewed, or that the code is correct. INFERRED.

Who carries it, checked on the first file of each project's newest release through PyPI's integrity API: urllib3 2.8.0, cryptography 50.0.2, pydantic 2.14.3, requests 2.34.2, SQLAlchemy 2.1.8, polars 2.1.0, orjson 3.13.0, maturin 1.16.0, rpds-py 2026.9.1 and sigstore 4.5.1 carry provenance; pydantic-core 2.50.4, ruff 0.17.5 and uv 0.13.8 do not. EXECUTED ([pypi-provenance.txt](experiments/03/pypi-provenance.txt)). Three of those are maturin-built Rust-extension wheels like vfs's (polars, orjson, rpds-py), so the pattern is proven for the shape of package vfs ships. INFERRED.

vfs today: the one release on PyPI, `vfs-py` 0.0.22 uploaded 2026-04-23, has no provenance (the integrity API answers 404), and it is a `py3-none-any` wheel, so it predates the Rust engine and the current five-wheel workflow. EXECUTED. The current workflow would also publish without attestations, because `uv publish` creates none. READ and INFERRED. Cost to make every future release carry them: one step, `astral-sh/attest-action` pinned by SHA, placed just before `uv publish` in the `publish` job, which already has `id-token: write`; or swap `uv publish` for `pypa/gh-action-pypi-publish`. Nothing is paid and nothing runs except at release. INFERRED.

### 2.3 Sigstore

What it is: keyless signing. The signer proves an identity to an OIDC provider, Fulcio issues a short-lived certificate for that identity, and the signature goes into Rekor, an append-only transparency log; verifiers trust a root distributed through TUF. READ (docs.sigstore.dev/about/security). What a signature proves: that an identity which passed an OIDC login signed this artifact while its certificate was valid. What it must trust: the OIDC provider (Sigstore's page says Fulcio "assumes that a valid OIDC token from a trusted provider is sufficient proof of ownership"), Fulcio, Rekor and the trust root; and it warns that "If no third parties monitor the logs, then any misbehavior by Rekor and Fulcio might go undetected." READ. Maturity: sigstore-python 4.5.1 released 2026-10-20. EXECUTED (GitHub API). For vfs, Sigstore is not a separate seal to adopt: PEP 740 attestations and GitHub artifact attestations for public repositories are both Sigstore bundles. READ (GitHub concepts page: public repositories use the Sigstore Public Good Instance and a public transparency log).

### 2.4 GitHub artifact attestations and SLSA build levels

SLSA is a graded framework for build integrity; v1.2 is current and adds a Source track beside the Build track. READ (slsa.dev/spec/v1.2). The Build levels, in SLSA's words: L1 "provenance exists" and "is trivial to bypass or forge"; L2 a hosted platform signs the provenance, which "deters unsophisticated adversaries"; L3 a hardened platform isolates runs and keeps signing keys away from user build steps, so forging needs "exploiting a vulnerability that is beyond the capabilities of most adversaries". READ (slsa.dev/spec/v1.1/levels). SLSA speaks to how the artifact was built and nothing else; the levels page never mentions source review, dependencies or correctness. READ and INFERRED.

GitHub artifact attestations (`actions/attest`, latest v4.2.2 released 2026-08-04) sign build provenance naming the workflow, repository, commit SHA and trigger, verified with `gh attestation verify <file> -R <owner>/<repo>`. READ and EXECUTED (release date). GitHub states that attestations alone give "SLSA v1.0 Build Level 2", that Build Level 3 needs the build in a shared reusable workflow for isolation, and that attestations are not "a guarantee that an artifact is secure"; they bring no benefit unless someone verifies them. READ (docs.github.com concepts page). Who uses it: of the projects checked in 2.2, PEP 740 is the seal that shows on PyPI; this study did not survey which of them also publish GitHub attestations. Cost to vfs: add `attestations: write` to the `wheels` and `sdist` jobs and one `actions/attest` step with `subject-path: dist/*` after the maturin step, for SLSA Build L2; moving the build matrix into a reusable workflow called from `publish.yml` for L3. INFERRED.

The two attestations attest different moments, and vfs's split pipeline makes the difference visible. The PEP 740 attestation would be signed by the `publish` job, which only downloads the artifacts the `wheels` and `sdist` jobs built; it proves who uploaded, and ties the build only through being the same workflow run. A GitHub build attestation signed inside the `wheels` job ties each wheel to the job that compiled it. Carrying both is what lets a stranger walk from the PyPI file to the commit that built it. INFERRED from READ.

## 3. Reproducible builds

What it is: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts", checked by comparing hashes. READ (reproducible-builds.org). It is the one built-and-delivered seal that needs no trust in the builder at all: anyone can rebuild and compare. It still says nothing about whether the source is correct. INFERRED.

Run here: the vfs wheel was built twice with maturin 1.16.0 from two copies of HEAD at different paths (`.../repro/a` and `.../repro/b`), with `SOURCE_DATE_EPOCH` set to the HEAD commit time, on one macOS arm64 machine. EXECUTED ([reproducible-build.txt](experiments/03/reproducible-build.txt)). The compiled engine `vfs/_native.abi3.so` came out byte-identical. The wheels' hashes differed (`ffa6b164…` against `848b3f0b…`), and the only differing files were the embedded SBOM and the `RECORD` that hashes it: maturin writes the build's absolute path into the CycloneDX SBOM's `bom-ref` (`path+file:///private/tmp/claude-501/verif-03/repro/a/crates/vfs-core#0.1.0`). EXECUTED. So the Rust compile is already reproducible across paths on this machine, and the one break is a path in the SBOM. On GitHub's hosted runners the checkout path is fixed per repository, so two CI builds would likely match; a stranger rebuilding on a laptop would not, unless the SBOM's path is normalised or the comparison excludes it. INFERRED. Not tested: a build without `SOURCE_DATE_EPOCH`, a build on another machine or toolchain, the Linux and Windows wheels, and the sdist. The OpenSSF badge requires a reproducible build only at gold (`build_reproducible`). READ.

## 4. Software bills of materials: CycloneDX, SPDX and PEP 770

What it is: a machine-readable inventory of the components in an artifact. CycloneDX and SPDX are the two formats; PEP 770 puts SBOMs inside a wheel under `.dist-info/sboms/`. READ (maturin.rs/sbom summary). An SBOM attests nothing about quality; it is an inventory that lets a buyer match components against vulnerability feeds, and it is what the CRA asks a manufacturer to draw up (section 10). INFERRED and READ.

vfs already ships one without having asked for it: the wheel built here contains `vfs_py-0.0.22.dist-info/sboms/vfs-core.cyclonedx.json`, CycloneDX 1.5, listing 97 Rust components (`aho-corasick`, `memchr`, the tree-sitter grammars and the rest). EXECUTED. It covers the Rust crates compiled into `_native` and not the Python dependencies, which is right for a library: pydantic and SQLAlchemy are resolved at install time and are not in the wheel. INFERRED. A March 2026 survey of 15,021 PyPI packages found 238 (about 1.6%) shipping SBOMs and traced every invalid one to a single cargo-cyclonedx bug, which is the generator maturin uses. READ (search summary of the sbomify analysis); vfs's file was not schema-validated here. GitHub's `actions/attest` can also sign an SBOM as an attestation predicate (SPDX or CycloneDX). READ.

## 5. Dependency review seals: cargo-vet and cargo-crev

cargo-vet (Mozilla, v0.10.3 released 2026-10-22) checks that every third-party crate in the lockfile is covered by an audit recorded by the project or by an organisation it imports audits from, with a ratcheting exemptions list. READ and EXECUTED (GitHub API). Its built-in criteria: `safe-to-run` ("can be compiled, run, and tested … without surprising consequences" such as touching unrelated files or the network) and `safe-to-deploy` ("will not introduce a serious security vulnerability to production software exposed to untrusted input", which requires reasoning about "all unsafe blocks and usage of powerful imports"). READ (built-in-criteria page). The public import registry names actix, ariel-os, bytecode-alliance, embark-studios, fermyon, google, isrg, mozilla and zcash. EXECUTED (registry.toml). A pass proves a named human looked at each dependency version against a stated criterion; it does not prove the dependency is correct, and an imported audit is only as good as the importing project's trust in that organisation. INFERRED. Cost to vfs: `cargo vet init` over `Cargo.lock` with the public imports, then an exemption or an audit for each of the 97 crates not already covered, and a diff audit on every dependency bump; the tree-sitter grammar crates are the likely uncovered tail. INFERRED; not run inside the box.

cargo-crev is a web-of-trust variant: reviewers publish signed review proofs and users choose whom to trust. Latest release v0.27.1, 2026-04-12; its README calls it "a work in progress". READ and EXECUTED. Its value depends on reviewers having covered the crates in question, which this study did not measure. INFERRED. Both tools attest how dependencies were vetted, which is a practice of the project, and neither has a Python counterpart of the same maturity that this study found. INFERRED.

## 6. The OpenSSF Best Practices Badge

What it is: a self-certification questionnaire at bestpractices.dev; projects "voluntarily self-certify, at no cost", and "Automated analysis will determine many of the criteria answers for you (and prevent obviously incorrect answers)". READ. No human review of the answers is described. READ (helper's reading of the home page; the FAQ was not read). It attests practices, not code. Levels and counts as read: passing 67 criteria (43 MUST), silver 55 (44 MUST), gold 23 (21 MUST), each requiring the one before. READ (criteria/0, /1, /2). bestpractices.dev also now serves OSPS Baseline levels 1 to 3 (24, 19 and 21 criteria). READ.

What a solo maintainer can and cannot meet. Passing has no criterion that needs a second person; its hardest items for vfs are a 14-day response to vulnerability reports (`vulnerability_report_response`), a documented reporting process, and a static analysis tool beyond the compiler (ruff and ty qualify). READ and INFERRED. Silver adds criteria that are hard solo but can be met with paperwork: `governance`, `roles_responsibilities`, a `dco`, `signed_releases` (PEP 740 attestations would plausibly satisfy it), an `assurance_case`, `test_statement_coverage80` (vfs's 100% gate exceeds it). One silver MUST is structurally hostile to a solo project: `access_continuity`, "MUST be able to continue with minimal interruption if any one person dies, is incapacitated…", which needs a second person holding the keys. READ and INFERRED. Gold is out of reach solo by construction: `bus_factor` (MUST, 2 or more), `contributors_unassociated` ("at least two unassociated significant contributors") and `two_person_review` ("at least 50% of all proposed modifications reviewed before release by a person other than the author"). READ. Gold's other demands (`build_reproducible`, `test_branch_coverage80`, `security_review` within five years, `require_2FA`, a licence and copyright line per file) are reachable. READ and INFERRED. vfs's own process has reviews by a fresh agent ([AGENTS.md](../../../../AGENTS.md), "Development process and project knowledge"); whether an agent's review counts as "a person other than the author" is the badge's call, and the criterion's wording says person. INFERRED.

Who carries it, from the public project search: curl and the Linux kernel are gold; urllib3, rustls, Kubernetes and OpenSSL are passing; SQLite is in progress; pydantic, pyca/cryptography, SQLAlchemy, requests, ruff, tokio and sigstore-python have no entry. READ (bestpractices.dev projects.json). Several of the most trusted Python packages do not carry it at all, which says the badge is a signal a stranger may look for rather than a norm of the ecosystem. INFERRED.

## 7. OpenSSF Scorecard

What it is: an automated scan of a repository's practices, 20 checks weighted Critical 10, High 7.5, Medium 5, Low 2.5 into a 0 to 10 aggregate; its README says the checks "are heuristics; there are false positives and false negatives". Latest release v5.6.0, 2026-10-12. READ (Scorecard README, checks.md, release page). It attests practices visible in the repository, not code behaviour.

Run on vfs here, in local mode over an archive of HEAD (local mode runs 11 of the checks; the ones that need GitHub's API, such as Branch-Protection, Code-Review, Maintained, Signed-Releases and CI-Tests, do not run): aggregate 3.2 of 10. EXECUTED ([scorecard-local.txt](experiments/03/scorecard-local.txt)). The rows: Binary-Artifacts 10, Dangerous-Workflow 10, License 9, Packaging inconclusive, and 0 for Dependency-Update-Tool (no Dependabot or Renovate), Fuzzing (none detected), Pinned-Dependencies (actions pinned by tag, not by SHA), SAST (no CodeQL or similar), Security-Policy (no `SECURITY.md`), Token-Permissions (no top-level `permissions:` block in `test.yml`, `test-dialects.yml` or `publish.yml`) and Vulnerabilities ("126 existing vulnerabilities detected"). EXECUTED, and READ for the workflow facts.

The Vulnerabilities zero needed reading closely. Rerun on `uv.lock` and `Cargo.lock` alone, it reported 124, so the context spikes' lockfiles add two. EXECUTED. Splitting `uv.lock` by audience with `uv export` and pip-audit: the core runtime dependencies are clean; the advisories fall on versions pinned for the optional extras (pillow, pypdf, cryptography, urllib3, langchain-core) and the dev group (pillow, tornado, virtualenv). EXECUTED ([lockfile-audit-by-audience.txt](experiments/03/lockfile-audit-by-audience.txt)). A library's lockfile does not ship to its users, who resolve `pydantic>=2.0` and the rest afresh, so the score overstates what a vfs user installs; it does correctly say that vfs's own CI and developers run on stale pins. INFERRED. The fix that moves the score is the one that fixes the exposure: a dependency-update tool and a lock refresh. INFERRED.

The Fuzzing check is narrower than its documentation. Its source accepts Python files containing `import atheris` and Rust files containing `libfuzzer_sys` (cargo-fuzz), plus OSS-Fuzz or ClusterFuzzLite membership, and searches a language only if it is "prominent" by lines of code; Hypothesis and proptest do not count. READ (checks/raw/fuzzing.go, against checks.md which names neither). So vfs's choice of fuzzing tool decides the score: an Atheris harness or a cargo-fuzz target scores, a Hypothesis suite does not. INFERRED. Public scores for comparison: urllib3 8.6 (2026-11-11), pyca/cryptography 8.5 (2026-11-02), tokio 6.7 (2026-10-26), SQLAlchemy 5.2 (2026-11-02); pydantic, pydantic-core, ruff and rustls are not in the public dataset. READ (api.securityscorecards.dev). Two checks a solo maintainer who commits to `main`, as [AGENTS.md](../../../../AGENTS.md) "Git workflow" directs, will score low by construction: Code-Review (human review before merge) and Branch-Protection; Contributors (several organisations) as well. INFERRED. Cost to vfs to raise the local score from 3.2: a top-level `permissions: contents: read` in each workflow, SHA-pinned actions, a `dependabot.yml` for the `github-actions`, `cargo` and `uv` ecosystems, a `SECURITY.md`, CodeQL, and the `ossf/scorecard-action` on a weekly schedule to publish a score and badge. Each is a small file; none runs more than weekly or per push. INFERRED.

## 8. OSS-Fuzz membership

What it is: Google's free continuous fuzzing service; a member project's fuzz targets run on Google's infrastructure and crashes are filed privately to the maintainers. Admission requires that a project "must have a significant user base and/or be critical to the global IT infrastructure", and the contact email must belong to an established committer and be tied to a Google account. READ (oss-fuzz accepting-new-projects). Python and Rust both have integration guides. READ. Members among the projects in this study: urllib3, SQLAlchemy, pyca/cryptography, rustls, tokio and orjson have `projects/<name>` directories in the OSS-Fuzz repository; pydantic-core does not. EXECUTED (GitHub API). That SQLAlchemy membership explains its Scorecard Fuzzing 10. INFERRED. What membership proves: the project's own harnesses are fuzzed continuously; the guarantee is only as deep as the harnesses, which the project writes. INFERRED. For vfs today: a pre-release package with no user base would not meet the admission bar. INFERRED from READ. The same harnesses run in ClusterFuzzLite on GitHub Actions need no admission and count for Scorecard. READ (fuzzing.go names ClusterFuzzLite).

## 9. Independent security audits

What it is: a time-boxed engagement in which a firm searches the code for vulnerabilities and publishes a report. It is the only seal-like artefact that looks at what the code does, and its promise is explicitly limited; Trail of Bits' PyPI report says "Security assessment projects are time-boxed … the findings documented in this report should not be considered a comprehensive list of security issues, flaws, or defects in the target system or codebase." READ (Trail of Bits 2023 PyPI Warehouse review). The rustls maintainer said of Cure53's 2020 audit that it can show defects are present, "not that they are absent". READ (search summary of jbp.io).

Costs and scale, from public figures only: OSTIF, which brokers audits for open-source projects and helps raise the money, says "initial audits could range anywhere from $30k to $200k"; its 2026 audit of Requests, CacheControl and urllib3 was done by 7ASecurity, five senior auditors over 34.2 working days, funded by Alpha-Omega, and found 9 security issues and 2 hardening items. READ (ostif.org/get-an-audit; ostif.org audit announcement). Trail of Bits' PyPI audit took 10 engineer-weeks and produced 29 advisories, funded by the Open Technology Fund. READ (search summaries of the ToB and PyPI posts). Cure53 audited rustls, ring and webpki in 2020 with four testers over about 30 days, sponsored by the CNCF. READ (search summary). No firm publishes a per-week rate that this study found. Funders that pay for open-source audits: Alpha-Omega (budget "over $7M" a year, no open application on its page) and the Sovereign Tech Agency's resilience programme, which delivers audits through OSTIF. READ. OSTIF's audit list carries Python and Rust projects (sigstore, python-tuf, rust-vmm, urllib3 and Requests, Paramiko, vLLM). READ. For vfs, an audit is worth most after the authorization and SQL-building paths have stopped moving, because a report is a snapshot of one commit. INFERRED. The OpenSSF gold criterion `security_review` asks for one within five years. READ.

## 10. Regulatory and enterprise frames

### 10.1 The EU Cyber Resilience Act

Regulation (EU) 2024/2847 applies from 11 December 2027; its reporting duty for actively exploited vulnerabilities (Article 14: early warning within 24 hours, notification within 72 hours, final report within 14 days of a fix) applies from 11 September 2026. READ (EUR-Lex). The Commission's single reporting platform has been "operational as of 11 September 2026". READ (digital-strategy.ec.europa.eu CRA reporting page). As of 30 July 2026 no harmonised standard had been cited in the Official Journal; this study could not confirm a citation since. READ (cyberresilienceact.eu).

Where vfs stands. A manufacturer can be "a natural or legal person" (Article 3(13)); recital 18 says free and open-source software "not monetised by their manufacturers should not be considered to be a commercial activity"; and an open-source software steward must be "a legal person" (Article 3(14)). READ (EUR-Lex). The Commission's July 2026 guidance, as summarised by a law firm, makes the commercial test product-specific and says consulting or support does not by itself make the software commercial unless access is "effectively tied to purchasing the service"; the guidance is not binding. READ (hlc.com summary; the Commission page itself was not opened). So, as vfs is published today (free, by one natural person, no monetisation), the owner is neither a manufacturer nor a steward and carries no CRA duty. INFERRED from READ. The duty falls on the enterprise that puts vfs inside a product it sells: Article 13(5) requires that manufacturer to "exercise due diligence when integrating components sourced from third parties", free components included; Article 13(6) to report vulnerabilities it finds to the component's maintainer; and Annex I Part II(1) to draw up "a software bill of materials in a commonly used and machine-readable format", supplied to an authority on reasoned request (Annex VII). READ. That is why the built-and-delivered seals matter commercially: an SBOM in the wheel, provenance a buyer can verify, a `SECURITY.md` with a response time, and a record of fixes are exactly the evidence a manufacturer's due diligence needs. INFERRED. A vendor blog reads paid support as commercial activity, against the Commission guidance summaries; the guidance is the better source. READ (search summary) and INFERRED. If the owner later sells vfs, support tied to access, or a hosted service, the analysis changes and the manufacturer duties attach. INFERRED.

### 10.2 SOC 2 and ISO/IEC 27001

SOC 2 is a CPA's examination of "Controls at a Service Organization Relevant to Security, Availability, Processing Integrity, Confidentiality, or Privacy", read by that service's users. READ (AICPA). ISO/IEC 27001 certifies an organisation's information security management system within a defined scope. READ (Drata; iso.org returned 403). Both attach to an organisation operating something, so a library cannot hold either; what a buyer's SOC 2 auditor asks of a library is how the buyer chose and patches it, which the seals in sections 2 to 7 answer. INFERRED. Cost figures, all from vendors that sell compliance platforms: SOC 2 Type 1 audit $7,500 to $15,000 over 1 to 3 months, Type 2 $12,000 to $20,000 over 6 to 12 months; ISO 27001 about $15,000 for the certification audits and $10,000 to $75,000 and more over a three-year cycle; other vendors quote far higher. READ (Drata, Vanta). They become relevant only if vfs is offered as a hosted service by a company. INFERRED.

### 10.3 FIPS 140-3

FIPS 140-3 validates a cryptographic module, a specific version in named operating environments, tested by an accredited laboratory and reviewed by NIST's CMVP; NIST's own fee for a full submission is $16,000 to $19,000, laboratory fees are separate, and totals of $200,000 and more and timelines from about one year to 30 months are quoted by analysts and vendors. READ (csrc.nist.gov; helper's search summaries for the totals). vfs implements no cryptography, so it is not a module and FIPS 140-3 does not apply to it; in a FIPS deployment the validated modules are the ones vfs runs over, such as OpenSSL's FIPS provider under Python and the database drivers, or aws-lc-rs, which rustls' `fips` feature uses and which is "covered by FIPS 140-3 certificate #4816". READ (docs.rs rustls fips manual) and INFERRED. The honest statement for a buyer is that vfs performs no cryptographic operations of its own and does not bypass the platform's TLS. INFERRED; a grep for vfs's own use of `hashlib` or TLS settings was not done inside the box.

## 11. What vfs's publish pipeline does today, and what is one change away

Today, from the tree. EXECUTED and READ. [`publish.yml`](../../../../.github/workflows/publish.yml) runs on a published GitHub release or a manual dispatch; builds five abi3 wheels (Linux x86_64 and aarch64 manylinux 2_28, macOS arm64 and x86_64, Windows x64) and an sdist with `PyO3/maturin-action@v1`; checks the tag against the project version with `scripts/check_release_tag.py`; gates every wheel at 50 MB; and uploads from a separate `publish` job in the `pypi` environment with Trusted Publishing. Every action is pinned by a major tag (`actions/checkout@v6`, `PyO3/maturin-action@v1`), none by SHA; in `publish.yml` only the `publish` job declares `permissions`, and `test.yml` and `test-dialects.yml` declare none, while `lint.yml` and `deploy-docs.yml` do. maturin embeds a CycloneDX SBOM of the Rust crates in every wheel. There is no `SECURITY.md`, no Dependabot or Renovate configuration, no CodeQL, and no fuzz target. `test.yml` uploads coverage to Codecov with a repository secret. The only release on PyPI carries no attestation.

## 13. Ranked recommendations for this dimension

1. PEP 740 attestations on every release, through `astral-sh/attest-action` before `uv publish`: one step, no running cost, the seal PyPI itself displays, already carried by the projects a buyer compares vfs to.
2. GitHub build provenance in the `wheels` and `sdist` jobs, and later the reusable-workflow move to SLSA Build L3: ties each PyPI file to the job and commit that compiled it, which PEP 740 alone does not.
3. A `SECURITY.md` with a stated response time and a private reporting channel: the prerequisite for the passing badge, a Scorecard check, and the first thing an enterprise's CRA due diligence will look for.
4. The Scorecard hygiene changes (workflow `permissions` blocks, SHA-pinned actions, Dependabot for actions, cargo and uv, CodeQL) and the `scorecard-action` publishing a score: each change closes a real supply-chain gap, and the lock refresh also clears the stale pins the Vulnerabilities check found.
5. A reproducible-wheel check, after normalising the absolute path maturin writes into the embedded SBOM: the engine already rebuilds byte-identical here, so this is close, and it is the one seal that needs no trust in the builder.
6. The OpenSSF Best Practices Badge at passing, with silver's documents (governance, roles, assurance case) written when there is a second person to name for `access_continuity`: say plainly that gold needs a second, unassociated reviewing maintainer and cannot be reached solo.
7. Fuzz harnesses in Atheris or cargo-fuzz, run in ClusterFuzzLite, when study 02's fuzzing work is adopted: the choice of tool, not the depth of the testing, decides whether Scorecard sees it.
8. cargo-vet with the public imports, once the dependency set settles: it gives an honest account of the 97 compiled crates, at a cost that grows with every bump.
9. An independent audit, funded through OSTIF, Alpha-Omega or the Sovereign Tech Agency, once the authorization and SQL-building paths stop moving: the only seal that looks at behaviour, and a snapshot of one commit.
10. Not SOC 2, ISO 27001 or FIPS 140-3: they attach to organisations, services and cryptographic modules, and vfs is none of these.

The thing in this dimension that "100% certainty" most misleads about: a signed, attested, reproducible build gives cryptographic certainty about origin and none about behaviour. A wheel can carry SLSA Build L3 provenance, a PEP 740 attestation, a byte-identical rebuild and a gold badge, and still let an agent read a row its grant forbids. The certainty a seal gives is certainty about where the bytes came from, conditional on GitHub's identity service and Sigstore's logs; the certainty that the bytes do what they say has to come from proofs and tests, and the best a seal can do is point a stranger at them.

## What this study does not settle

This study did not run Scorecard's API-backed checks against vfs's GitHub repository (Branch-Protection, Code-Review, Maintained, Signed-Releases, CI-Tests, CII-Best-Practices, Contributors, SBOM, Webhooks), because that would query GitHub about the project; the 3.2 is the local subset only. It did not see vfs's GitHub settings: whether the `pypi` environment has required reviewers, branch protection, or enforced two-factor authentication. It did not build the Linux or Windows wheels, build without `SOURCE_DATE_EPOCH`, or rebuild on a second machine, so the reproducibility result is one machine and one platform. It did not validate the embedded SBOM against the CycloneDX schema. It did not run `cargo vet init`, so the count of uncovered crates is unmeasured. It did not open the Commission's CRA guidance document itself, only a law firm's summary, nor confirm any harmonised-standard citation after July 2026. It did not read bestpractices.dev's FAQ on whether answers are ever spot-checked, nor the Best Practices criteria in full beyond the ids quoted. It did not check which of the projects in section 2.2 also publish GitHub artifact attestations, and it checked PEP 740 provenance on the first file of each release only. It found no public per-week price from any audit firm.

## One line

The seals vfs can carry say who built the wheel, how, and how the project is run, never what the code does; PEP 740 and GitHub build provenance are one step each in `publish.yml`, a `SECURITY.md` and workflow hygiene lift a 3.2 Scorecard and earn the passing badge, gold needs a second maintainer, and the certainty about behaviour has to come from proofs and tests that a seal can only point at.
