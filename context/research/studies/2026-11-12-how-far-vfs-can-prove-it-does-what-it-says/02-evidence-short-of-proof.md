# Evidence short of proof measures how hard a project tried to break itself, and the 100% vfs shows today is line coverage, the weakest of those measures

The box opened at 17:02 PST on 2026-11-12 and the study was finished inside it, at 17:27. This is Researcher 02's answer to the question "how the most trusted software earns its trust without a full proof". The short answer: the most trusted projects (SQLite, FoundationDB, TigerBeetle, Turso) do not claim correctness. They publish how hard they tried to break the code, in units a stranger can check: how many generated inputs, how many injected faults, how many planted bugs the suite caught. Every technique in this study ends in the same honest sentence: "no counterexample was found in what we tried". What differs between techniques is how large and how varied "what we tried" is, and whether the project counts it. Each claim below is labelled EXECUTED (a command run here, with its output), READ (a page or file cited) or INFERRED (reasoning from the two).

## 1. SQLite: the reference for evidence without proof

What it is. SQLite's testing page describes four harnesses and a family of fault and fuzz campaigns (READ, sqlite.org/testing.html). The public TCL suite has 51,445 distinct cases and runs millions of parameterized instances. TH3 is a separate harness of about 1,055 KSLOC of C and 50,362 cases; the page states that "the TH3 test harness is a set of proprietary tests". SQL Logic Test runs 7.2 million queries and compares SQLite's answers with PostgreSQL, MySQL, SQL Server and Oracle. dbsqlfuzz mutates both the SQL and the database file, about a billion mutations a day on about 16 cores. The page puts the test code at about 590 times the library code (92,053 KSLOC against 155.8 KSLOC).

What it measures beyond line coverage. Four things (READ). First, TH3 reaches 100% branch coverage of the core and the page says the core is held at 100% MC/DC. MC/DC (modified condition/decision coverage) means every sub-condition of every decision has been shown, by some test, to flip the decision on its own; it is the avionics standard. SQLite marks the conditions with a `testcase(X)` macro, which in a coverage build becomes a branch the coverage tool must see taken. Second, anomaly tests: simulated out-of-memory at every allocation, simulated I/O errors at every I/O call, simulated power loss with a VFS that reorders and damages writes, and compound failures during recovery, each followed by `PRAGMA integrity_check`. Third, assertions: 6,754 `assert()` calls in the core, plus `ALWAYS()` and `NEVER()` macros that assert in a debug build, pass through in release, and become constants in a coverage build so that a branch believed unreachable does not count against coverage; the suite runs under all three definitions. Fourth, a mutation check: a script compiles to assembly, turns each branch into an unconditional jump or a no-op, and confirms the tests notice.

What I counted in the clone (EXECUTED, commit above): 219,860 lines in `src/*.c` and `src/*.h`; 1,288 files and 1,020,800 lines under `test/`; 6,607 `assert(` occurrences, 913 `testcase(` and 333 `ALWAYS(`/`NEVER(` in `src/*.c`; 138 test files whose names mention fuzz, malloc, ioerr, crash or fault. The macro definitions are in `src/sqliteInt.h` lines 476 to 542. The counts differ from the page's (6,754 asserts, 1,184 testcase uses) because the page counts a different version and probably the headers and extensions as well; the order of magnitude agrees.

What a passing result proves, and what it does not. It proves that every branch and every condition of the core was driven both ways by some test, that every allocation and I/O failure point was exercised, and that the suite notices when a branch is broken. It does not prove the answers are right where no test states the right answer; SQL Logic Test supplies that for queries by comparing against four other engines (READ). It does not cover the build a stranger compiles: the page notes compiler bugs in GCC, Clang and MSVC and tests the as-delivered build for that reason (READ). And a stranger cannot rerun the strongest part, because TH3 is proprietary (READ). SQLite's trust is therefore partly earned in public (the TCL suite, the published method, the bug history) and partly a reputation for an audit nobody outside can repeat (INFERRED).

Who says what they got. SQLite says OSS-Fuzz "no longer finds historical bugs" and only occasionally finds issues in new check-ins, and that static analysis has "not been helpful in finding bugs" (READ). That is the signature of a mature regime: the cheap tools have run dry, so the evidence is in the expensive ones.

Fit for vfs (INFERRED). Three SQLite ideas transfer directly. The anomaly test is the one vfs lacks most: vfs's equivalent of an I/O error is a database error in the middle of a chunked batch (a dropped connection, a deadlock victim, a serialization failure, a statement timeout), and the claim to pin is that a 10,000-file write either lands whole or fails classified, never half. That can be done without mocking the database, which `context/standards/testing.md` forbids: a real SQLite or Postgres session with an engine event hook that raises on the Nth statement, swept over every N. The `testcase()` idea transfers as a cheap way to get condition coverage where it matters (a marker the gate must see taken both ways). The "590 times" ratio does not transfer as a target; vfs's Python tests are about 54,300 lines against about 39,700 lines of `src/` Python and 9,600 lines of Rust (EXECUTED, `wc -l`), and the ratio says nothing about strength on its own.

## 2. Deterministic simulation testing: FoundationDB, TigerBeetle's VOPR, Turso, Antithesis

What it is. The whole system runs inside one process under one seeded random number generator, with time, the network, the disk and the scheduler replaced by simulated ones that inject faults. A failing run is replayed exactly from its seed. FoundationDB built its simulator before the database; it runs a whole cluster single-threaded, injects network, disk, machine and datacenter faults, and runs tens of thousands of simulations nightly (READ, apple.github.io/foundationdb/testing.html). The page's figure of "roughly one trillion CPU-hours of simulation" is an estimate with no published accounting, and it is the kind of number that outruns its evidence (READ, INFERRED). TigerBeetle's VOPR runs a cluster of real code under network, storage and process faults "at 1000x speed", "24/7 on 1024 cores" (READ, docs.tigerbeetle.com/concepts/safety/).

Turso, the closest relative to vfs, layers several simulators (READ, the clone). `testing/simulator/` generates random interaction plans from a workload profile, checks properties (for example, two equivalent SELECTs must return the same rows), injects I/O faults through profiles, shrinks failures (`testing/simulator/shrink`), can run in `--differential` mode against SQLite, and can run under Miri for undefined behaviour. `testing/concurrent-simulator/` ("Whopper") adds swarm testing: each seed also switches whole workloads off and reweights the rest, because "a run with all workloads and fixed fault probabilities cannot get to some states"; CI runs it on every pull request with seed N for iteration N, and with fresh seeds on `main` (READ, `testing/concurrent-simulator/README.md`). Turso also writes `testing/antithesis/` templates and a local runner, `thesis`, that replays an Antithesis-style run from a seed (READ, `testing/antithesis/README.md`), and the workflows `build-sim.yml`, `antithesis.yml`, `antithesis-schedule.yml`, `elle.yml` and `fuzz.yml` run them (EXECUTED, `ls .github/workflows`).

Antithesis sells the same idea as a service: a deterministic hypervisor runs any x86 container system on one core, injects clock, scheduling, network and storage faults, and replays any bug exactly; SDKs exist for Python and Rust among others (READ, antithesis.com). It has no free or open-source tier and publishes no prices; purchases often go through AWS Marketplace. Its claim that a system which survives "will stay up in production" is marketing, not a stated guarantee (READ).

What a passing result proves, and what it does not. It proves that no property assertion failed across the explored seeds, under the faults the simulator models. It does not reach what the simulator does not model: the real kernel, the real network stack, the real database engine when that engine runs outside the simulated process, and bugs in the simulator itself (INFERRED; neither the FoundationDB page nor the Antithesis post names its limits, READ). Its trusted base is the simulator plus the property assertions. Its distinctive catch is the timing bug: an interleaving of events nobody wrote a test for, made reproducible.

Fit for vfs (INFERRED). vfs's nondeterminism lives in two places it does not own: the asyncio scheduler and the database engine, which on Postgres, SQL Server and Oracle is another process. Full deterministic simulation of vfs over Postgres is therefore only reachable through a hypervisor (Antithesis), at commercial cost. What is reachable now is the half that matters for correctness of the namespace: a seeded, shrinkable, generated sequence of verb calls against a model, on in-process SQLite, which is the stateful property test of section 7. Turso's swarm idea (each seed also switches workloads off) transfers to that machine at no cost.

## 3. Jepsen and Elle: checking what concurrent histories allow

What it is. Jepsen runs a real distributed or transactional system under faults, records the history of every operation's invocation and completion, and checks the history. Elle is its transactional checker: it infers dependency graphs from list-append or read-write-register histories and searches them for the cycles Adya's isolation definitions forbid (G0, G1a, G1b, G1c, G-single, G2), naming which consistency models the history violates (READ, github.com/jepsen-io/elle; EPL-2.0 or GPL-2.0 with classpath exception).

What a passing result proves. Elle is sound in the direction that matters for a bug report: a reported anomaly is real for every abstract history compatible with the observation. It "is not complete: it may fail to identify anomalies which were present", because outcomes go unobserved, timing is imprecise, and checking serializability exactly is NP-complete (READ). A clean Elle run is "no anomaly found in this history", not "serializable".

A real project and what it got. Jepsen's PostgreSQL 12.3 analysis found that "serializable" allowed G2-item anomalies in normal operation; a two-minute run caught six; the faulty code had barely changed since serializable snapshot isolation arrived in 9.1 in 2011, and the bug was present in every version tested. PostgreSQL's own isolation tests, Hermitage and Jepsen's bank test had not found it, because they used a few hand-built transactions (READ). The analysis also states its limits: list-append covers a few operations on a simple schema; Elle cannot model predicates, so it cannot tell repeatable read from serializable (READ). Turso integrates Elle in Rust (`testing/concurrent-simulator/elle.rs`, exporting EDN histories for `elle-cli`) and runs it in CI (READ, EXECUTED `ls`).

Fit for vfs (INFERRED). vfs inherits isolation from the engine, but it adds its own concurrency claims on top: two agents editing one path, a delete racing a write, version rows, directory aggregates maintained with the write. Those are exactly the claims a hand-built test samples thinly. A vfs-level Jepsen test would record histories of concurrent verb calls on real Postgres and SQL Server and check them, either with Elle (an append-only body maps onto list-append) or with a model of vfs's own promises. The cost is real: a history recorder, a workload generator, a Clojure or `elle-cli` dependency in a CI job, and a written statement of which isolation vfs promises per verb. It is worth it once vfs states those promises; until a docstring says what concurrent edits guarantee, there is nothing for a checker to check.

## 4. Differential testing: Cedar, Csmith, SQLancer, SQLsmith, Turso's oracle

What it is. Run two implementations of the same contract on the same generated inputs and fail on any disagreement. It needs no statement of the right answer, only a second implementation trusted for a different reason.

Cedar, the case closest to vfs's central claim. Cedar's authorizer is modelled in Lean and implemented in Rust; `cedar-drt` in `cedar-spec` runs cargo-fuzz targets that generate schemas, entities, policies and requests with the `arbitrary` crate and compare the Rust answers with the Lean model's; the README's `cedar-lean-ffi` directory and Lean library build indicate the Rust harness calls the compiled Lean model directly (READ, github.com/cedar-policy/cedar-spec, Apache-2.0). Amazon reports that proofs found 4 bugs in the validator and that differential random testing and property-based testing together found 21 more (READ, amazon.science). The split matters: the proof caught a handful of deep bugs; generated differential testing caught five times as many, because it checks the shipped code against the model rather than the model against itself (INFERRED). A passing DRT run is agreement on the inputs generated, not equivalence (READ).

Csmith generated random C programs free of undefined behaviour and compared compilers; over three years it found more than 325 unknown bugs, every compiler tested could be made to crash and to emit wrong code silently, and it found bugs in the unproved parts of the verified compiler CompCert (READ, PLDI 2011 via DOI and Regehr's blog). That last result is the clearest single lesson for this study: a proof covers what it covers, and a generator finds the seams around it.

SQLancer tests database engines with oracles that need no second engine: Ternary Logic Partitioning (a query's rows must equal the union of the same query filtered by p, by NOT p and by p IS NULL), NoREC (an optimized query must agree with a rewrite the optimizer cannot touch), Pivoted Query Synthesis, Differential Query Plans, and others; it reports "hundreds of bugs" in mature engines, is MIT licensed, and supports PostgreSQL, MariaDB, MySQL and SQLite among about twenty engines, but not SQL Server or Oracle (READ, github.com/sqlancer/sqlancer). SQLsmith generates random queries for PostgreSQL, SQLite and MonetDB and reports 118 bugs since 2015, mostly crashes; it is GPL-3.0 (READ). Turso's `testing/differential-oracle/` compares Turso against SQLite statement by statement, and `testing/sqlancer/` runs SQLancer against it (READ).

Fit for vfs (INFERRED, with EXECUTED counts). vfs already does differential testing: the readable oracles in `tests/support/oracles/` (glob, grams, grants, graph walk, lexical, links, matcher, postings, signals, vectors and more) are compared with the Rust engine and the SQL resolver on random inputs. The grant oracle's docstring says "a parity test runs both on random worlds; they must agree on every path" (READ, `tests/support/oracles/grants.py`). Those random inputs come from 35 `random.Random(<fixed seed>)` generators across 13 test files, for example 400 worlds per test in `tests/storage/test_grants.py` (EXECUTED, grep). A fixed seed is reproducible, which is good, but it means the same 400 worlds every run forever, no new exploration, and no shrinking of a failure to its smallest form. Two differential legs are missing. The first is cross-engine: the same generated verb sequence on SQLite, Postgres, MariaDB, SQL Server and Oracle must give identical results, which pins "every supported engine serves the same namespace" for generated inputs rather than for the conformance suite's chosen examples. The second borrows SQLancer's oracle shapes rather than SQLancer itself (vfs is a client of the engines, not an engine): a `glob` or `grep` with a filter must equal the unfiltered result filtered in Python; a search with rights must equal the search without rights intersected with the grant oracle's readable set. The second shape is the authorization claim stated as a differential, which is how Cedar states its own.

## 5. Mutation testing: mutmut, cosmic-ray, mutatest, cargo-mutants

What it is. The tool makes many small edits to the code (a `<` becomes `<=`, a condition becomes `True`, a function body returns a default) and runs the tests against each. A mutant the tests fail on is killed; one they pass on survived and marks a place where a bug could live unnoticed. The score is killed over generated, after removing equivalent mutants, the edits that change no behaviour.

What it says that coverage does not. Coverage counts lines that ran; mutation counts lines whose behaviour some assertion checks. Just et al. studied 357 real faults and 230,000 mutants in five Java programs and found that mutant detection correlates with real-fault detection independently of coverage, and more strongly than statement coverage does (READ, FSE 2014 abstract; the 73% coupling figure circulates only in secondary slides and was not checked). Google's study of almost 15 million mutants over six years found that developers shown surviving mutants in code review wrote more and better tests, and that mutants were coupled with real faults that later had to be fixed (READ, ICSE 2021 abstract and preprint).

The tools today (EXECUTED, PyPI and crates.io metadata). mutmut 3.8.1, released 2026-10-28, BSD-3-Clause; it mutates only functions the tests call, runs each mutant in a forked child, keeps results in a `mutants/` directory and retests only changed functions on later runs; it does not run natively on Windows (READ, README). cosmic-ray 8.9.0, released 2026-11-10, MIT. mutatest 3.1.0, last released 2022-02-20, which makes it unmaintained for this purpose. cargo-mutants 27.1.0, released 2026-06-02; it copies the tree to a temporary directory by default (`--in-place` is opt-in), and offers `--shard`, `--baseline`, `--test-tool` and `--test-workspace` (EXECUTED, `--help`).

What it looks like on a toy (EXECUTED, `experiments/02/results.txt`). The toy has three functions and five example tests, the kind of test that asserts something true but weak: a budget is `<= 1000`, chunk lengths sum to the total, a grant on `/a` opens `/a` and `/a/b`. coverage.py reports 100% with branch measurement on. mutmut generated 26 mutants: 17 killed, 3 timed out (counted as caught; the mutant looped forever), 6 survived. The survivors include `return 1 if (b == 0) or True else b` (the budget always returns 1, and "is at most 1000" still holds) and `while left > 1:` (the chunker drops a final one-item chunk, which no example reaches). cargo-mutants on the same logic in Rust generated 21 mutants: 12 caught, 3 timeouts, 6 missed, in 1 minute 46 seconds. Its most important miss was `replace may_read -> bool with true`: the permission check replaced with "always allow" passed every test, because every test asked only for an allow. Then three Hypothesis properties were added (the budget equals `max(1, min(a, b))`; every chunk is between 1 and the size, they sum to the total and there are `ceil(n/size)` of them; no grant on `/x` opens the sibling `/x<suffix>`). mutmut's survivors fell from 6 to 2, and both remaining ones are equivalent mutants (`<` to `<=` inside a minimum, `>` to `>=` where both arms then give the same value).

Three lessons from the toy (INFERRED from the EXECUTED runs). First, 100% line and branch coverage coexisted with a permission check that could be replaced by "always allow": applied by hand to a copy of the Python toy, `return True` passed all five example tests (`5 passed in 0.14s`) and failed the sibling-prefix property (`1 failed, 2 passed`) (EXECUTED). Coverage could not see it; a mutation tool or a property could. Second, the two tools disagree about the same logic: mutmut killed all six of its `may_read` mutants because it never generated the "return true" body, which cargo-mutants did. A mutation score is relative to the tool's operator set, so a published score is a claim about that tool, not about the code. Third, equivalent mutants are real and need a human to dismiss; a score of 100% is only reachable by marking them.

Fit for vfs (INFERRED). vfs already practises the idea by hand: `context/standards/testing.md`, "Pins land with their mutant", and `context/standards/mutant-ledger.md` with 84 recorded rows, each a one-line bug that once survived the suite (EXECUTED, grep). That is the right discipline and an unusual one. What a tool adds is the denominator: the ledger lists the mutants someone thought of, and a tool lists every mutant of a given shape, including the ones nobody thought of, which is exactly where the toy's "always allow" lived. Running mutants in a copy (mutmut's `mutants/` directory, cargo-mutants' temporary tree) also fits the AGENTS.md rules better than mutating the live tree. The costs are concrete. mutmut ran 1.7 mutants a second on the toy; with a suite of about a minute, a full run over 39,700 lines of Python would take many hours, so the practical shape is mutants on the functions a change touches, in CI on each pull request, plus a periodic full run. The forked-child model must be tried against vfs's async tests and xdist before relying on it. cargo-mutants runs `cargo test`, so a Rust mutant caught only by a Python parity test would be reported as missed unless the run is wired to rebuild the extension and run pytest; this study did not try that wiring.

## 6. Fuzzing: cargo-fuzz and libFuzzer, Atheris, OSS-Fuzz, ClusterFuzzLite

What it is. A coverage-guided fuzzer mutates byte inputs, keeps the ones that reach new code, and reports any input that crashes, panics, trips a sanitizer, or fails an assertion in the harness. cargo-fuzz 0.13.2 (2026-06-09) drives libFuzzer through `libfuzzer-sys` 0.4.13 on nightly Rust; `arbitrary` 1.5.0 turns bytes into typed values (EXECUTED, crates.io). Atheris 3.1.0 (2026-06-17, Apache-2.0) is libFuzzer for Python, supports Python 3.11 to 3.14 in source, and can fuzz native extensions with AddressSanitizer or UBSan if they are instrumented; on macOS it needs a non-Apple LLVM (READ, github.com/google/atheris; EXECUTED, PyPI).

What it finds that others miss. Inputs no person would write: malformed UTF-8, boundary sizes, deep nesting, the byte sequence that walks a tokenizer off a character boundary. In safe Rust the catch is panics (out-of-bounds indexing, slicing inside a UTF-8 character, arithmetic overflow in debug builds) and, with a differential assertion in the harness, wrong answers (INFERRED).

What it looks like (EXECUTED, `experiments/02/rtoy/fuzz/`). A differential fuzz target compared the Rust grant check with a model that walks the path's ancestors. Against a planted bug (a grant on `/a` also opens `/ab`) it failed after about 780 executions, under a second, with `assertion left == right failed, left: true, right: false`. Against the correct function it ran 6,896,515 inputs in 31 seconds with no failure. That second number is what a fuzz pass is worth: 6.9 million tries found nothing, on this harness, from this corpus. It is not absence.

OSS-Fuzz admits projects that "have a significant user base and/or be critical to the global IT infrastructure" (READ). A pre-release vfs does not qualify today; that is a fact about adoption, not quality. ClusterFuzzLite runs the same machinery inside GitHub Actions, with pull-request fuzzing, batch fuzzing and coverage reports, for Python and Rust among others, and needs no admission (READ, google.github.io/clusterfuzzlite).

Fit for vfs (INFERRED). The Rust kernels in `crates/vfs-core/src/` that parse or decode input are the natural targets: `glob.rs`, `lexical.rs` and `grams.rs` (tokenizing arbitrary text), `chunk.rs`, `postings.rs` (decoding stored postings, which a corrupted row could feed), `links.rs`. Each needs a ten-to-thirty line target, ideally differential against an invariant the oracle states. The Python ingress (path normalization, the verb argument gates) is reachable with Atheris or, more cheaply, with Hypothesis, which shares the shrinking and the pytest integration vfs already has. Cost: one nightly toolchain job, a corpus kept in the repository or a cache, minutes per pull request through ClusterFuzzLite.

## 7. Property-based and stateful testing: Hypothesis and proptest

What it is. Instead of writing the input, write the law and a generator; the tool generates hundreds of inputs, and on failure shrinks the input to a small one. A stateful test generates whole sequences of operations against a model and checks after every step that the system and the model agree. Hypothesis 6.170.15 (2026-11-06) provides `RuleBasedStateMachine` with rules, bundles, preconditions and invariants run after every step, and reports a failure as a short replayable program (READ, hypothesis.readthedocs.io; EXECUTED, PyPI). HypoFuzz 25.11.1 runs Hypothesis tests as a long-running coverage-guided fuzzer (EXECUTED, PyPI). proptest 1.12.0 with `proptest-state-machine` does the same for Rust against a `ReferenceStateMachine`, shrinking by dropping transitions, then shrinking them, then the initial state; it supports only sequential runs (READ, proptest book; EXECUTED, crates.io).

What it looks like (EXECUTED, `experiments/02/ptoy/tests/test_stateful_toy.py`). A toy governed store with rules `write`, `grant` and `read`, compared against a model that walks a path's ancestors, with the same planted sibling-prefix bug. Hypothesis found it in 0.37 seconds and shrank it to four steps: `grant(path='/a')`, `grant(path='/a')`, `read(path='/ab')`, then `assert 'missing' == 'denied'` failed. The repeated grant shows shrinking is good, not perfect. The same law as an example test needed someone to think of `/ab`; as a property it needed someone to think of "a grant opens only its subtree", which is what the docstring already says.

What it finds that others miss. Bugs in the interaction of operations: a state reachable only by grant, write, move, then read; an ordering the author never tried. And it turns a docstring's law into a check of every generated case rather than of the cases the author picked (INFERRED). What a pass proves: no counterexample in the generated cases, bounded by the strategy. A strategy that never generates a move cannot find a move bug; Turso's swarm testing exists to fight exactly that blind spot (READ, section 2).

Fit for vfs (EXECUTED, then INFERRED). No test file under `tests/` imports Hypothesis today (EXECUTED, grep: 0 files), and Hypothesis is not a dependency in `pyproject.toml`. The fixed-seed random worlds of section 4 are the nearest thing, without shrinking or a failure database. The highest-value single test this study can name is a stateful machine over vfs's verbs: rules for `write`, `edit`, `delete`, `move`, `grant` and `revoke` across two or three identities, rules for `read`, `ls`, `glob`, `grep` and `stat` that compare each answer with a model (a dictionary of files plus the grant oracle already in `tests/support/oracles/grants.py`), and invariants that no identity ever sees a row the oracle denies. Run on in-memory SQLite in the inner loop and on each real engine in the engine legs, that one machine pins the central authorization claim, the cross-engine claim and the result-classification claim on generated sequences. vfs's verbs are async; rules can drive them through one `asyncio.Runner` held by the machine, which this study did not try against vfs.

## 8. Coverage stronger than lines: branch, MC/DC, and what the tools can measure

What the tools measure. coverage.py's branch mode records transitions between lines and flags a transition never taken (READ, coverage.readthedocs.io/en/latest/branch.html). It does not see decisions inside one line: in the toy, deselecting the only test that took the `1 if b == 0` arm left coverage at 100% with branch measurement on, because a conditional expression is one line (EXECUTED, `results.txt`). Short-circuit `and`/`or` operands are invisible to it for the same reason (INFERRED from the line-transition model). For Rust, `cargo-llvm-cov` 0.9.1 (2026-09-06) measures line and region coverage on stable, branch coverage on nightly only (READ, README; EXECUTED, crates.io). MC/DC is where the sources disagree: cargo-llvm-cov's README still lists `--mcdc`, but rustc removed all unstable MC/DC instrumentation in PR #144999 in 2025, and a 2026 Rust project goal led by AdaCore aims only to bring it back as an unstable flag (READ). Python has no mainstream MC/DC tool; pymcdc 0.2.6 (2026-08-13) is a small analyser and Qt's commercial Coco reports MC/DC through a coverage.py integration (READ, EXECUTED PyPI; neither was tried).

vfs's gate (EXECUTED). `[tool.coverage.run]` in `pyproject.toml` does not set `branch = true`, so the 100% gate is line coverage. Its `exclude_lines` also lists `\.\.\.`, a pattern a sibling memo in this tree examines for excluding more than intended. A first branch measurement of the whole suite on the working tree as it stood (with uncommitted changes from other sessions) printed `Can't use core=sysmon: sys.monitoring can't measure branches in this version` on Python 3.13 and fell back to the C tracer, which does not follow SQLAlchemy's greenlet switches; it reported 4,296 branches with 177 partial and also showed missed lines that the CI gate does not miss. A second run with `concurrency = greenlet,thread` and the same exclusions followed. So turning branch coverage on in vfs is not a one-line change on 3.13: the `sysmon` core that the project chose for speed cannot measure branches before Python 3.14, and the fallback needs greenlet concurrency configured.

The second run (EXECUTED, config and report in `experiments/02/vfs-branch/`, coverage data written to scratch, 5 minutes 44 seconds, `4892 passed`, and two failures unrelated to coverage, one of them the brief's own link to the memo not yet written) measured every line covered, 4,296 branches, and 40 partial branches across 24 files: `TOTAL 13215 0 4296 40 99%`. So vfs's branch coverage is about 99%, not 100%, and the gap sits in places a stranger would care about: three partial branches in `src/vfs/storage/backends/database/rights.py`, three in `search.py`, four in `engine.py`, one in `writes.py`. One example shows what a partial branch means. In `rights.py` the arc `1530->1540` is the group-membership walk leaving its `while frontier and depth <= MAX_GROUP_DEPTH:` loop through the loop condition rather than the `break`; because the frontier is never empty at that check, the arc is the case where group nesting reaches the depth cap, and no test drives it (INFERRED from the EXECUTED report and the source). Line coverage counts that loop as fully covered.

What a passing result is worth. Line coverage at 100% proves every line ran at least once under some test; it proves nothing was checked. Branch coverage proves every line-to-line decision went both ways. MC/DC proves each condition was shown to matter on its own. None says an assertion looked at the result; that is mutation testing's job (section 5). To a stranger, a coverage badge is the weakest claim in this study and the easiest to misread (INFERRED).

## 9. Comparison

| Technique | Finds what the others miss | A pass proves | Trusted base and blind spot | Cost for vfs |
|---|---|---|---|---|
| Line coverage (today) | dead or untested lines | every line ran once | assertions are not inspected | in place |
| Branch / MC/DC | a decision only ever taken one way | each decision (or condition) went both ways | intra-line decisions in Python; MC/DC unavailable for Rust today | 40 partial branches to close; greenlet concurrency on 3.13; MC/DC not reachable |
| Mutation (mutmut, cargo-mutants) | weak or missing assertions | the suite notices the tool's edits | operator set; equivalent mutants; cost | per-PR on changed functions; hours for a full run |
| Property-based / stateful (Hypothesis, proptest) | interactions of operations; laws no example exercised | no counterexample among generated cases, with shrinking | the strategy's reach | one machine and its model; seconds to minutes per run |
| Differential (oracles, cross-engine) | divergence between two implementations | agreement on generated inputs | both sides wrong the same way | oracles exist; generators and engine legs to add |
| Fuzzing (cargo-fuzz, Atheris) | malformed inputs, panics, boundary sizes | no failure in N executions from this corpus | harness assertions; corpus reach | a target per kernel; a nightly CI job |
| Anomaly / fault injection (SQLite) | behaviour under failure mid-operation | every injection point was survived | the fault model | an engine hook and a sweep per batch verb |
| Deterministic simulation (FDB, VOPR, Turso, Antithesis) | timing and interleaving bugs, reproducibly | no property broke across explored seeds and faults | the simulator; anything outside it (for vfs, the engine) | in-process half via stateful tests; full half only via Antithesis, paid |
| Jepsen / Elle | isolation anomalies in concurrent histories | no anomaly found in this history (sound, not complete) | unobserved outcomes; no predicates | recorder, workload, CI job; needs stated concurrency promises first |

## 10. Ranked recommendations for vfs

1. A Hypothesis stateful machine over the verbs with the existing grant oracle as the rights model, run on SQLite in the inner loop and on every real engine in the engine legs: it pins the central authorization claim, the cross-engine claim and result classification on generated, shrinkable sequences, and reuses an oracle vfs already trusts.
2. Mutation testing in CI on the functions each change touches (mutmut for Python, cargo-mutants for `vfs-core`), with the hand ledger kept as the curated set: it supplies the denominator the ledger lacks and finds the "always allow" mutant nobody thought to record.
3. Move the 35 fixed-seed random generators to Hypothesis strategies, keeping a pinned seed where reproducibility matters: same parity tests, plus shrinking, a failure database and fresh exploration on every run.
4. Anomaly tests for batch verbs: a real engine with an event hook that raises on statement N, swept over every N of a chunked 10,000-file write, asserting whole-or-classified: it is the SQLite practice vfs most lacks, and it pins the batch contract the reference deployment rides on.
5. A cross-engine differential leg: the same generated verb sequence on SQLite and each real engine must return identical results: it raises "every supported engine serves the same namespace" from chosen examples to generated inputs.
6. Branch coverage gated at 100%: the measured gap is 40 partial branches, including the group-depth cap in `rights.py`, each one either a missing test or an arc to justify, and the gate needs the C tracer with greenlet concurrency on 3.13, because the `sysmon` core cannot measure branches there.
7. cargo-fuzz targets for the input-parsing kernels (`glob.rs`, `lexical.rs`, `grams.rs`, `chunk.rs`, `postings.rs`) through ClusterFuzzLite: minutes per pull request for the class of panic no example reaches, and OSS-Fuzz later, once there is a user base.
8. An Elle-style history check of concurrent writes on Postgres and SQL Server, after vfs writes down what each verb promises under concurrency: high value for the claims it covers, but nothing to check until those claims are stated.
9. Antithesis, not now: it is the only route to deterministic simulation over a real Postgres, and it is paid and unpriced; revisit when vfs runs at a customer.

What "100% certainty" most misleads about in this dimension is the number 100 itself. Every figure in this study that reads 100% (SQLite's branch coverage, vfs's line gate, a mutation score after equivalents are dismissed) is 100% of a denominator someone chose: the lines, the branches, the operators, the seeds. The toy here sat at 100% line and branch coverage while its permission check could be replaced by "always allow". Evidence short of proof never reaches certainty; what it can reach is a published, counted, repeatable account of how hard the project tried to break itself, and a stranger can check that account where they cannot check a percentage.

## What this study does not settle

It did not run mutmut or cargo-mutants on vfs itself, so the real survivor count, the run time, and whether mutmut's forked children work with vfs's async tests and xdist are unmeasured. It did not try wiring cargo-mutants to rebuild the extension and run pytest. It did not run Atheris (it needs a non-Apple LLVM on this machine), HypoFuzz, SQLancer, Elle or Antithesis. It did not read the full texts of the Just et al. and Petrović et al. papers, only their abstracts and preprint introductions. It did not verify whether the 2026 Rust MC/DC goal has landed on a current nightly. It did not measure condition-level coverage in vfs, because no maintained Python tool for it was tried. TigerBeetle's VOPR page gave no limits and no simulated-years figure; those were not pursued further.

## One line

The most trusted software publishes how hard it tried to break itself, and for vfs the cheapest large step is to replace "every line ran" with "every generated sequence of verbs agreed with the oracle and every planted bug was caught", because the toy here kept 100% coverage while its permission check was replaced with "always allow".
