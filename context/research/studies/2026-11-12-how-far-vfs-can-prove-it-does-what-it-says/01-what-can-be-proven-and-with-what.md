# vfs can prove its permission algebra and the safety of its Rust kernels, but no tool can prove that its SQL does what the algebra says: Cedar's proved model plus differential testing is the strongest honest claim, and vfs already has the testing half

The box opened at 17:02 PST on 2026-11-12 and this study was finished inside it. I read `AGENTS.md` and `context/standards/testing.md` first, then the vfs permission and grant code, the Cedar and cedar-spec clones, and the public pages listed below; I installed Kani, CrossHair and deal in `/private/tmp/claude-501/verif-01/` and ran each on a toy shaped like a vfs function. The kept toys and their outputs are in [experiments/01/](experiments/01/). The short version: a proof is a machine-checked argument that code (or a model of it) satisfies a written statement, and three things always stay trusted: the statement itself, the tool that checked it, and whatever lies between the thing proved and the thing shipped. For vfs the third gap is the largest, because the central claim (every call is judged against row-level rights before dispatch) is realized partly in Python and partly as SQL that Postgres, SQL Server, Oracle and SQLite evaluate, and no verifier in this study reaches across either boundary.

## 1. What a proof can and cannot be about, stated once

A proof answers "does this artifact satisfy this statement for every input in this domain". Every tool below differs in three dimensions: the artifact (a design model, a reference model, or the shipped code), the statement (no panic or overflow, functional correctness against a specification, an invariant of a protocol), and the domain (all inputs, or all inputs up to a bound). Every tool also carries a trusted base: the solver or proof kernel, the compiler or interpreter that turns the proved code into what runs, the model of anything the code calls but the tool cannot see (libpython, the SQL engine, the operating system), and the specification. INFERRED.

vfs has three layers that a proof could target, and they have very different reach (READ, from the vfs tree): the Rust kernels in `crates/vfs-core/src/` (about 5,200 hand-written lines once the 4,415-line generated `lexical_tables.rs` is set aside, two `unsafe` blocks, both `align_to` views in `python.rs`), the Python control plane in `src/vfs/` (39,716 lines, async, SQLAlchemy), and the SQL each backend emits, which the engine evaluates. The permission claim lives in the second and third layers: `src/vfs/permissions.py` (mount-level longest-prefix resolution, 363 lines) and `src/vfs/storage/grants.py` plus `src/vfs/storage/backends/database/rights.py` (row-level grants compiled into visibility clauses, 714 and 1,540 lines). The test suite already pins the grant layer the Cedar way: `tests/support/oracles/grants.py` is a 93-line pointwise oracle, and `tests/storage/database/test_rights.py` replays 30 seeded random worlds (`WORLDS = 30`, fixed `random.Random(58)` and similar) through the public verbs on SQLite, over two layouts that include prefix traps such as `/a-b` and `/a0` next to `/a`, and asserts exact agreement. READ.

## 2. Rust: bounded model checking and deductive verifiers

**Kani** (model-checking/kani, Apache-2.0, release `kani-0.68.0` of 2026-09-16, active daily; READ via GitHub API). A bit-precise bounded model checker that compiles Rust MIR to CBMC's goto programs. A harness declares symbolic inputs with `kani::any()` and the checker proves that, for every value of those inputs and every loop unwound up to the bound, no assertion fails, no arithmetic overflows, and no checked undefined behaviour occurs. What it does not prove: anything past the unwinding bound (unless loop contracts are written), anything concurrent (Kani compiles concurrent code as sequential and marks data races unsupported), inline assembly (unsupported), unwinding panics (abort strategy only), and some undefined behaviour classes (aliasing rules, invalid values are marked "No"; uninitialized memory is partial and opt-in); an unsupported construct becomes `assert(false); assume(false)`, which fails only if reachable. READ (Kani feature-support page). It trusts CBMC, its SAT backend, the Kani MIR translation and rustc. It cannot follow a call into libpython, so a `#[pyfunction]` is out of reach; the harness must target the pure Rust function behind the binding. INFERRED. Used by AWS on Firecracker and s2n-quic and as one of five approved tools in the standard-library challenge (below). INFERRED from prior knowledge for Firecracker and s2n-quic, not re-read in this box.

EXECUTED (Kani 0.68.0, CBMC 6.11.0, macOS arm64; toy in [experiments/01/kani_toy/](experiments/01/kani_toy/), output in [experiments/01/kani_results.txt](experiments/01/kani_results.txt)). Install was `cargo install --locked kani-verifier` then `cargo kani setup`, which downloaded a 352 MB bundle and a 1.3 GB pinned nightly toolchain into `~/.rustup` (I uninstalled that toolchain afterwards; the setup also self-updated rustup from 1.29.0 to 1.29.3, which I could not undo). A classic `(lo + hi) / 2` midpoint was refuted in 0.02 s with "attempt to add with overflow"; the fixed `lo + (hi - lo) / 2` was proved in 0.02 s for all 2^64 input pairs. A ten-line sorted posting-list intersection that pushes into a `Vec` was proved sound for two-element inputs in 152.5 s at 13.5 GB resident memory, and the same harness over four-element inputs was still running after about five minutes at 6 GB when I stopped it. What using it is like: arithmetic and indexing properties over scalars are instant; anything that allocates grows the formula fast, so harnesses must be kept to tiny bounds or rewritten over fixed-size arrays and stubs.

**Verus** (verus-lang/verus, MIT, rolling release `0.2026.11.02` of 2026-11-02, active). A deductive verifier: you write `requires`/`ensures` and loop invariants in a Rust-embedded specification language and Z3 discharges the verification conditions for all inputs, no bound. It aims at "full functional correctness of low-level systems code" and explicitly does not verify itself or the Rust/LLVM compilers, and does not intend to support all of Rust. READ (Verus guide). It trusts Z3, the Verus encoding, rustc and any function marked trusted with an external specification. INFERRED. Code must be written in Verus's dialect inside `verus!` macros, which is a rewrite of the kernel rather than an annotation of it. INFERRED.

**Creusot** (creusot-rs/creusot, LGPL-2.1, `v0.14.0` of 2026-10-12, active). Deductive verification of safe Rust through Why3, with Pearlite contracts as attributes on ordinary Rust; known for CreuSAT, a verified SAT solver. READ (release metadata); the rest INFERRED from prior knowledge. Same trusted base shape as Verus: the SMT solvers Why3 drives, the translation, rustc.

**Prusti** (viperproject/prusti-dev, last release `v-2023-08-22` per the GitHub API, repository still receiving commits). Deductive verification through the Viper infrastructure (the same base as Nagini, below). READ (metadata). The absence of a release in over three years makes it the weakest choice for a project that wants its gate to keep working. INFERRED.

**Aeneas** (AeneasVerif/aeneas, Apache-2.0, no tagged releases, active). Translates safe Rust, through the Charon front end and its borrow-aware intermediate form, into a pure functional model in Lean (or F*, Coq, HOL4), where properties are proved by hand. INFERRED from prior knowledge; the repository page failed to load in this box. Its appeal for vfs would be that the proofs land in the same language as a Cedar-style specification; its cost is that every property is an interactive Lean proof.

**Flux** (flux-rs/flux, MIT, no tagged releases, active). A refinement type checker: types carry logical predicates (an index is less than the length, a value is non-negative) checked by an SMT solver, which gives absence of out-of-bounds and overflow with lighter annotation than Verus. READ (repository, which names no production users) and INFERRED.

**VeriFast** (verifast/verifast, release `26.10` of 2026-10-05) is a separation-logic verifier aimed at unsafe code. READ (metadata).

**The standard-library effort** (model-checking/verify-rust-std). A community contest, started by AWS, to prove memory safety and the absence of a subset of undefined behaviour in the Rust standard library: 29 challenges, 10 resolved, financial awards up to 25,000 USD, five approved tools (Flux, ESBMC through the GOTO transcoder, Kani, KMIR, VeriFast). READ. What it gives vfs: the `std` functions vfs's kernels call (`align_to`, slice indexing, `Vec`) are being proved safe by others, which shrinks what a Kani harness on vfs has to assume; what it does not give: anything about vfs's own logic. INFERRED.

## 3. Python: symbolic execution and contract provers

**CrossHair** (pschanely/CrossHair, licence file not recognised by GitHub's classifier, `v0.0.113` of 2026-11-05, active). It runs your Python function on symbolic inputs, asks Z3 which branches are feasible, and reports concrete counterexamples to contracts (PEP 316 docstrings, `icontract`, `deal`, or plain asserts). READ (CrossHair docs). The docs do not claim that a clean run proves anything, and they list "interpreting logic that's implemented in C" among undocumented topics; when Z3 cannot decide a branch CrossHair picks one at random. READ.

EXECUTED (CrossHair 0.0.113 on Python 3.14.10; toy in [experiments/01/prefix_rule.py](experiments/01/prefix_rule.py), output in [experiments/01/crosshair_results.txt](experiments/01/crosshair_results.txt)). I modelled vfs's `PermissionMap._resolve` boundary test (`path == prefix or path.startswith(prefix + "/")`) and a buggy variant that drops the `/`. CrossHair refuted the buggy one in about 36 s with `resolve_buggy('/\x00', '/\x00\x00')`, the same sibling-prefix bug class vfs's `TRAPS` layouts guard against. On the correct one, `--report_all` printed "Not confirmed": no counterexample within the time limit, and no proof either. And the correct one's contract is worth a second look: its postcondition restates the implementation, so even a confirmation would have proved a tautology. That is the specification problem in miniature.

**hypothesis-crosshair** (pschanely/hypothesis-crosshair, `0.0.x`, 29 stars). A Hypothesis backend (`@settings(backend="crosshair")`) that drives property tests with symbolic execution instead of random draws; its changelog records fixes for false "verified" claims and path aborts. READ. For vfs it is the cheapest route from property tests to solver-driven search, but it is a bug finder, not a seal. INFERRED.

**deal** (life4/deal, MIT, `4.24.6` of 2025-11-30, no release in a year) with **deal-solver** (`0.1.2`). Contracts as decorators, plus `python -m deal prove`, which translates a restricted subset of Python into Z3 formulas. READ (metadata). EXECUTED ([experiments/01/deal_toy.py](experiments/01/deal_toy.py), [experiments/01/deal_results.txt](experiments/01/deal_results.txt)): on the buggy prefix function it returned "failed post-condition. Example: path='A', rule=''" instantly, a real counterexample (with no precondition the empty rule matches everything). Its subset covers pure functions over builtins; it cannot see SQLAlchemy, async code or the Rust extension. INFERRED.

**Nagini** (marcoeilers/nagini, MPL-2.0, `v1.3.1` of 2026-07-06, ETH Zurich research tool, Python 3.12 to 3.14). A deductive verifier for statically typed Python on Viper, with contracts, optional information-flow (noninterference) checking, and a case study verifying the SCION router; floats are abstract by default, bitwise integers bounded, counterexamples experimental, and it pins Z3 4.8.7 and Java 11. READ. It is the only Python tool here that proves rather than searches, and its subset excludes most of what vfs's control plane is made of (async, SQLAlchemy, pydantic, the native extension). INFERRED.

**Newer.** I found nothing newer for Python in this box that proves properties of real-world async, ORM-backed code. Dafny compiles to Python, so a Dafny-verified model could ship as a Python oracle; I did not check its current Python backend in this box. INFERRED.

## 4. Design-level model checkers and specification languages

These check a model of the design, never the code. Their worth is finding a wrong design before it is built; the link back to code is a separate step (traces, conformance tests, or runtime monitoring). INFERRED.

**TLA+ with TLC** (tlaplus/tlaplus, MIT, `v1.7.4` of 2024-08-05, nightly builds active). TLC exhaustively explores every reachable state of a finite instance of the specification; a pass proves the invariants for that instance only. AWS reported TLA+ finding deep design bugs in S3, DynamoDB and other services in 2014 to 2015, and the 2025 CACM article by Brooker and Desai describes TLA+ as central but abstract and mathematical for most developers. READ for the 2025 summary; the earlier history INFERRED from prior knowledge.

**Apalache** (apalache-mc/apalache, Apache-2.0, `v0.63.0` of 2026-11-10). A symbolic model checker for TLA+ and Quint using Z3: it checks invariants up to a bounded number of steps, and can check that a candidate inductive invariant holds for all states, which is an unbounded proof of that invariant for the model. READ (metadata); the rest INFERRED.

**Quint** (informalsystems/quint, Apache-2.0, `v0.33.1` of 2026-10-28). A programmer-friendly syntax over TLA+'s logic, with a random simulator, Apalache and TLC as back ends, and model-based testing that drives an implementation with traces from the model. READ (Quint docs, which describe it as "pen and paper" for protocol designers).

**P** (p-org/P, MIT, active). Communicating state machines with a checker that systematically explores message and failure interleavings and produces reproducible traces; used across AWS in S3, EBS, DynamoDB, MemoryDB, Aurora, EC2 and IoT teams; PObserve checks production logs against P specifications, which is the strongest model-to-code link in this family. READ (P site).

**Alloy** (AlloyTools, `v6.2.0` of 2025-01-09). A relational modelling language checked by SAT within a bounded scope; Alloy 6 adds linear temporal logic. A pass means no counterexample exists within the scope; the small-scope hypothesis (most bugs have small counterexamples) is the argument for trusting that. READ (about page) and INFERRED.

**Lean for specifications** (leanprover/lean4, Apache-2.0, `v4.35.0` of 2026-10-12). A proof assistant and a programming language: the same Lean file is an executable reference model and the object of the proofs, and the trusted base is a small proof-checking kernel. READ (AWS Lean post). This dual nature is why Cedar chose it (section 5).

## 5. Case studies: what proof costs and what it buys

**seL4.** A full code-level functional correctness proof that the C implementation meets its specification, extended to the binary on ARM and RISC-V so the compiler is not trusted there, plus integrity and confidentiality proofs; it still assumes the in-kernel assembly, the boot code, the hardware, TLB and cache management, and DMA being off or trusted, and makes no claim about timing channels. READ (seL4 FAQ). The cost: about 8,700 lines of C and 600 of assembly, 200,000 lines of Isabelle proof, about 25 person-years for the whole project of which about 12 were kernel verification. READ (L4.verified numbers, via search summary). Lesson for vfs: end-to-end proof of functional correctness runs at roughly 23 lines of proof per line of code and person-decades for ten thousand lines; vfs's Python alone is four times seL4's C. INFERRED.

**CompCert.** A Coq proof of semantic preservation from C to assembly (observable behaviour of the output is a behaviour of the source), covering about 90% of the compiler; elaboration, presimplification, assembling and linking are unverified. READ (CompCert page). Csmith (Yang et al., PLDI 2011) found over 325 bugs in other compilers and none of the middle-end wrong-code bugs in CompCert after about six CPU-years of testing. READ (as quoted on the CompCert page). The same paper reported bugs in CompCert's then-unverified front end. INFERRED from prior knowledge, not re-read in this box. Lesson: proof eliminated a bug class in exactly the proved part; the bugs moved to the unproved edges, which is where vfs's SQL would sit.

**ShardStore (Amazon S3).** Over 40,000 lines of Rust validated with executable reference models written in Rust (about 1% of the implementation's size; a hash map stands in for the LSM tree), property-based conformance checking of random API sequences, crash-consistency checking against the model, and stateless model checking for linearizability; the checkers are about 12% of the code base, 18% of them now written by the engineering team rather than formal-methods experts, and they prevented 16 issues from reaching production. The authors say plainly: "We do not aim to achieve full formal verification." READ (SOSP 2021 paper, pages 1 to 2). Lesson: the reference model is the specification and lives in the same language as the code; vfs's `tests/support/oracles/` are already this pattern. INFERRED.

**Cedar.** The case that matters most, because Cedar's central claim is an authorization claim, as vfs's is.

What is proved. The cedar-spec clone holds the Lean formalization: a definitional evaluator and authorizer (`Cedar/Spec/`, 2,239 lines), a validator, a symbolic compiler, and theorems (`Cedar/Thm/` and the symbolic compiler proofs, about 97,000 lines, 1,693 `theorem` declarations, no `sorry` placeholder in `cedar-lean/`). READ and EXECUTED (line counts, `grep -rlw sorry` returned nothing). The authorization theorems in `Cedar/Thm/Authorization.lean` are exactly the shape vfs needs: `forbid_trumps_permit`, `allowed_only_if_explicitly_permitted`, `default_deny`, and `order_and_dup_independent`. READ. Beyond those: sound policy slicing, sound type checking (a well-typed expression can fail only with three named error kinds), sound level-based entity slicing, and a symbolic compiler to SMT proved sound and complete, which the Rust crate `cedar-policy-symcc` ships so users can check their own policy sets for always-allows, always-denies, equivalence and disjointness against cvc5 1.3.1. READ (cedar-lean README, cedar `cedar-policy-symcc/README.md`).

What links the proof to Rust. Nothing proves the Rust. The bridge is differential random testing (DRT): `cedar-drt` compiles the Lean model, generates policies, entities and requests with type-directed generators, runs both, and fails on disagreement. The DRT README lists 18 differential targets (authorizer on RBAC and ABAC policies, evaluator, validator, entity and request validation, partial evaluation) and about 30 property-based targets for parts the Lean model does not cover (parser round trips, formatter, protobuf decoding, incremental entity updates). READ (`cedar-drt/README.md`). CI builds every target and runs a smoke pass on each pull request. READ (`.github/workflows/build_and_test_drt_reusable.yml`). The 2023 blog post reported DRT running six hours nightly at on the order of 100 million tests. READ.

What it found and what it cost. Proofs found 4 bugs in the validator; DRT and property-based testing found 21 more across the system. READ (arXiv 2407.01688). The April 2024 numbers were a 1,673-line Lean model, 5,714 lines of proof, 24,915 lines of production Rust, the largest proof (validator soundness, 4,686 lines) taking 18 person-days, Lean checking everything in 185 s, and the Lean model running DRT inputs at about 5 µs against Rust's 7 µs. READ (AWS Lean post). Comparing that with today's clone: the model grew by about a third and the proofs about seventeen-fold in two and a half years, mostly from the symbolic compiler. EXECUTED (line counts) and INFERRED (the ratio). The proofs and DRT still leave room for bugs in unmodelled code: the `entities-upsert-equivalence` property target exists because incremental entity updates kept a dropped parent's ancestors (cedar#2628), a bug in code the Lean model does not describe. READ (`cedar-drt/README.md`).

What it trusts. The Lean kernel (the only trusted component the AWS post names), the Lean-to-C compiler for the DRT build, rustc, the generators' reach, and above all that the Lean specification says what users mean by "authorized". READ and INFERRED.

The fit to vfs. vfs's grant semantics are smaller than Cedar's language: the 93-line oracle states them in five bullet points (everyone holds the deepest `*` row's level; a subject holds the maximum over its rows, its groups' rows and ownership; a subject set holds the minimum; trash is judged at its origin). That is a Lean model of perhaps a few hundred lines with theorems such as "deny by default", "a set never holds more than its weakest member", "a rule on `/a` never governs `/a-b`", and "a subtree-reaching verb is refused when any `read` rule lies beneath". vfs's `test_rights.py` already plays the DRT role, against a Python oracle, on SQLite. INFERRED.

## 6. What reaches pyo3 and what reaches SQL

No tool in this study proves anything about code on the other side of the pyo3 boundary or inside a SQL engine. INFERRED from sections 2 to 4. Concretely for vfs:

The Rust side of the seam can be reached. `crates/vfs-core/src/python.rs` is a 641-line binding layer whose `#[pyfunction]`s call pure kernels (`chunk_spans`, `glob_set`, `tokenize`, `overlay_postings`, `vector_topk`, `candidate_ids` and others). READ. Kani, Flux, Verus or Creusot can target those kernels directly; none can target the binding functions themselves, because they call into libpython. INFERRED. The two `unsafe { raw.align_to::<i64>() }` and `<f64>` views are the most proof-shaped code in the crate: a Kani harness over a small symbolic byte slice can prove the borrowed and copied paths return the same values. INFERRED.

The Python side of the seam can be reached only for pure helpers. CrossHair, deal and Nagini handle functions like path normalization, longest-prefix resolution, `membership_budget` and `chunked`; none handles async SQLAlchemy sessions. INFERRED, and EXECUTED for the prefix toy.

SQL cannot be proved, only checked. A proof about the clauses `rights.py` compiles would need a formal semantics of each engine's SQL dialect, NULL handling, collation and `LIKE` escaping, trusted as a model of Postgres, SQL Server, Oracle and SQLite. Research formalizations of SQL semantics exist but none is a tool a library could gate on. INFERRED. The honest instrument is the one Cedar uses for its Rust: differential testing of the real engines against a proved model. vfs's random-world parity runs that on SQLite today; the engine legs exist for the four real engines, so carrying the same random worlds to every leg is a test change, not a research one. INFERRED.

The structural half of the claim is not a property any of these tools states. "Every mutating verb funnels through the gate before dispatch" (the chokepoint in `src/vfs/base.py` that `permissions.py` describes) is a claim about the call graph. A model checker can prove that a modelled dispatcher only dispatches after a gate step, but the link to `base.py` would again be a test or a lint, not a proof. INFERRED.

| Lean (Cedar pattern) | Executable reference model | Any theorem you can state | All inputs | Lean kernel, the spec | Neither; bridged by DRT | 4.35.0, Oct 2026 | A model, theorems, a DRT harness; Cedar's largest proof took 18 person-days |

## 8. Ranked recommendations for vfs

1. Adopt the Cedar pattern for the rights algebra: an executable Lean model of mount permissions and row grants, with theorems for default deny, weakest-member subject sets, prefix boundaries, subtree refusal and trash-at-origin, and the existing random-world parity extended so the SQL path on every engine leg is compared against that model on every CI run. This is the only route to a sentence like "the authorization rules are proved, and the shipped implementation is tested against the proved rules on four engines", and it targets the claim a stranger relies on most.
2. Add Kani harnesses to the Rust kernels for absence of panics and overflow, starting with the two `align_to` views and the arithmetic in `postings.rs`, `chunk.rs` and `vectors.rs`, over fixed-size symbolic inputs, run in a scheduled CI job. Proofs of scalar arithmetic are instant and the result ("no panic for any input up to N bytes") is a true, checkable statement; heap-heavy harnesses must stay tiny.
3. Model the concurrent and incremental protocols (the write gate under concurrent writers, the partial index pass and the daily fold of delta posting tables) in Quint or TLA+ checked by Apalache, before or alongside their specs. These are the designs where ShardStore and AWS found bugs that testing missed, and neither Kani nor the oracles see interleavings.
4. Use CrossHair through hypothesis-crosshair, or deal, on pure Python helpers (path normalization, prefix resolution, `chunked`, `membership_budget`) as a solver-driven bug finder in the slow tier. It finds sibling-prefix bugs in seconds (EXECUTED) but reports "Not confirmed" on correct code, so it never belongs in a seal.
5. Hold Verus, Creusot and Aeneas for one kernel whose functional correctness carries the search claim (posting intersection or scoring), and only after items 1 to 3; the oracles and parity tests already pin those functions, and deductive proof means rewriting or hand-proving each one.
6. Do not adopt Nagini, Prusti or an seL4-scale end-to-end proof: Nagini's subset excludes async SQLAlchemy code, Prusti has not released since 2023, and end-to-end proof costs about 25 person-years per ten thousand lines of C.

What the phrase "100% certainty" most misleads about in this dimension is the specification. A proof never says the code is right; it says the code matches a statement, and the statement is trusted. My own CrossHair toy shows the trap: the correct function's postcondition restated its implementation, so a proof of it would have been true and worthless. Cedar shows the scale of the gap honestly: its proofs found 4 bugs and its testing against the proved model found 21, because most of what can go wrong lives outside the theorems. For vfs the statement that would need to be right is "what a grant means", and the code that would need to match it includes SQL that four engines evaluate, which no proof reaches.

## What this study does not settle

I did not install Lean or build cedar-spec, so the effort estimate for a vfs rights model rests on Cedar's published numbers, not a trial. I did not run Verus, Creusot, Aeneas, Flux, Nagini, TLC, Apalache, Quint, P or Alloy. I could not read the full CACM 2025 article (403) or the ShardStore paper past page 2, so the per-technique bug split there is not reported. I did not measure how many of vfs's Rust kernels Kani can handle within a CI budget beyond the toy, nor whether the random-world generators reach the states a Lean model's theorems would be about. I did not look at Dafny's Python backend or at research tools for SQL semantics beyond naming them.

## One line

vfs can honestly prove its rights algebra in Lean and its Rust kernels' safety with Kani, and then test its SQL against that proof on every engine, the way Cedar does, but no tool proves the SQL itself, and every proof is only as good as the statement it proves.
