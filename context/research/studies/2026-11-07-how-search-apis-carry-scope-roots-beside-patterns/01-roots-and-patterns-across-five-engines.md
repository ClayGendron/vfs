# Five engines carry roots as structured clauses applied during candidate generation, never as text composed into the pattern, and the one place that composes text (git's prefix) records the root's length beside it

Study 01 for [the brief](00-brief.md), written 2026-11-07 under a 45-minute box that opened at 22:42 EST and in which the clone refreshes, every source read, the ripgrep experiment and this write-up finished with the box open; nothing below was cut short, but the Sourcegraph client itself (the monorepo, not cloned) and the OpenSearch security plugin were studied only through what zoekt's own code and the OpenSearch documentation say about them, as the sections mark. The question is how mature engines that take both where to look (roots) and what to match (patterns) carry the two across their API, where they apply the root, how they authorize per root, and whether any client composes root text into pattern text. The vfs context is the two-shape seam the brief describes: composed pattern text below two hundred arms, `ScopeChannel(roots, arms, arms_not)` above it ([protocol.py](../../../../src/vfs/storage/protocol.py) `SupportsPatternSearch`, [glob.py](../../../../src/vfs/pattern_matching/glob.py) `ScopeChannel`, [the spec](../../../specifications/active/2026-11-07-storage-takes-scope-roots-and-arms-as-two-channels.md) decisions 3, 6 and 7). This study decides nothing.

## 1. zoekt: roots and patterns are different AST node types, the repository set prunes shards before any index is opened, and a tenant check runs per document in the match loop

READ. The query AST in `query/query.go` has two families of leaf. Patterns are `Substring` (line 407: `Pattern`, `CaseSensitive`, `FileName`, `Content`) and `Regexp` (line 75: a parsed `syntax.Regexp` with the same `FileName` and `Content` flags). Scope is a separate set of leaves: `Repo` (line 175, a regexp over repository names), `RepoRegexp` (line 195), `RepoSet` (line 295, `map[string]bool`), `RepoIDs` (line 289, a roaring bitmap), `BranchesRepos` (line 219, a list of branch name plus bitmap of repository IDs), `Branch` (line 514), and `FileNameSet` (line 328, an exact set of file names). The comments on `RepoSet`, `BranchesRepos` and `FileNameSet` say the same thing three times: a "Sourcegraph addition and only used in the RPC interface for efficient checking of large repo lists" (lines 219 to 221, 293 to 294, 325 to 327). `RepoSet.String()` truncates past five members with the comment "Large sets being output are not useful" (lines 299 to 303). The two families combine only through `And`, `Or` and `Not` (lines 469 to 514).

READ. The parser keeps the families apart from the first token. In `query/parse.go`, a `repo:` atom becomes `&Repo{r}` (the `tokRepo` arm, around line 184), `branch:` becomes `&Branch{Pattern: text}` (line 213), and `file:` or `f:` calls `RegexpQuery(text, false, true)` (line 221), the file-name variant of the same pattern constructor that bare text calls with `(text, false, false)` (line 215) and `content:` calls with `(text, true, false)` (line 227). A repository root is therefore never parsed into a file-name regexp: `repo:` and `file:` are different fields, and the parser has no path through which a repository name reaches `RegexpQuery`.

READ. The root is applied three times, each before content matching. First, before any shard is opened: `search/shards.go` `selectRepoSet` (lines 692 to 705) and `doSelectRepoSet` (707 to 880) walk the top-level `And`, find the first `RepoSet`, `RepoIDs`, `Repo` or `BranchesRepos` child, keep only the shards holding a repository the predicate admits, and, when every repository in a kept shard is admitted, replace the clause with `Const{true}` so no per-shard work remains (lines 855 to 858; for `BranchesRepos` with one branch the clause becomes an exact `Branch` query, 860 to 870). The comment at 850 to 854 states the aim: "This work can be done now once, rather than per shard." `shardedSearcher.Search` calls it at line 1058 and traces `shards=%d->%d`. Second, per shard: `index/eval.go` `simplify` (lines 56 to 136) folds each repository clause against the shard's repository metadata through `simplifyMultiRepo` (34 to 54): `Const{true}` when every live repository matches, `Const{false}` when none does, the clause itself otherwise; `Search` returns at once on a folded `false` (157 to 160). Third, inside the shard: a surviving `RepoSet` or `RepoIDs` becomes a `docMatchTree` whose predicate is a per-document lookup into a `reposWant []bool` indexed by `d.repos[docID]` (`index/matchtree.go` 1247 to 1275), and `BranchesRepos` a `branchQueryMatchTree` over per-document branch masks (1230 to 1245). These trees drive candidate generation, not a post-filter: `docMatchTree.nextDoc` advances to the next document its predicate admits (476 to 486), and `andMatchTree.nextDoc` returns the maximum over its children (496 to 505), so a repository clause under an `And` moves the cursor past every foreign document before the content tree is consulted. `pruneMatchTree` (1365 onward) then drops `And` branches proven impossible by the n-gram index and collapses `Or` branches.

READ. The search loop in `index/eval.go` (lines 200 to 235) is where per-root authorization lives in zoekt itself. After `mt.nextDoc()` yields a candidate and before `matches` runs, the loop reads the candidate's repository metadata and skips it when the repository is tombstoned, and then, under a comment that begins with a security marker, "Skip documents that don't belong to the tenant. This check is necessary to prevent leaking data across tenants", skips it when `tenant.HasAccess(ctx, repoMetadata.TenantID)` is false. `internal/tenant/query.go` lines 11 to 23 define `HasAccess`: true when enforcement is off or the context is the system tenant, otherwise the context's tenant ID must equal the document's repository's tenant ID. The authority therefore rides in the request context, the root (repository) carries the fact it is judged against, and the judgement is per candidate document during iteration, independent of which clause admitted it.

INFERRED from the READ comments above. Sourcegraph's own client is not in this clone, but zoekt's code says what shape the client sends: a repository set as `RepoIDs` or `BranchesRepos` over the RPC, built for "efficient checking of large repo lists". The repository-level permission decision (which repositories this user may search) is thus resolved on the client into a set of IDs and carried as one structured clause `And`-ed with the user's pattern; zoekt then applies that set at the shard list, the shard, and the document, and adds its own tenant check per document. No repository name is ever spliced into a file-name regexp to express scope.

READ. The only text composition in the clone is `web/server.go` lines 620 to 625: the web UI's file-view handler wraps a literal file name and a literal repository name in `^` + `QuoteMeta` + `$` to build two anchored regexps. That composes one exact value into an exact-match regexp for a single-document lookup; it does not compose a root into a pattern, and the repository value still becomes a `Repo` clause, not part of the file regexp. The other `QuoteMeta` (`index/eval.go` 96) builds an extension alternation for a legacy `lang:` fallback. Verdict for zoekt: two shapes across the API (repository-scope leaves beside pattern leaves, both structured); root applied before and during candidate generation; per-root authorization as a set clause from the client plus a per-document tenant check in the engine; client-side composition of root into pattern: no.

## 2. ripgrep: positional roots start the walk, globs are a per-entry override matched against the path as walked and anchored at the invocation directory, and the two never meet as text

READ. `crates/ignore/src/walk.rs` keeps the roots as `paths: Vec<PathBuf>` (line 489): `WalkBuilder::new(path)` takes the first (552) and `add(path)` pushes more (722 to 724). The globs are a separate object: `crates/core/flags/hiargs.rs` lines 1208 to 1232 build the `-g` and `--iglob` patterns into an `ignore::overrides::OverrideBuilder::new(&state.cwd)`, and the doc comment on `OverrideBuilder::new` (`crates/ignore/src/overrides.rs` 119 to 123) says "Matching is done relative to the directory path provided", that directory being the process's current directory, not any positional root. The builder is a thin wrapper over `GitignoreBuilder` (124 to 126), so override globs have gitignore semantics: a glob without a slash matches any path component, a glob with a slash is anchored at the matcher's root.

READ. The root is applied first and structurally: the walk begins at each positional path, so candidate generation is the directory traversal itself. The glob is applied per entry during that traversal: `crates/ignore/src/dir.rs` lines 540 to 553 consult the override matcher before any ignore file ("Overrides have the highest precedence") and return its verdict at once when it is not `None`; `overrides.rs` `matched` (97 to 110) inverts the gitignore verdict so a matching glob is a whitelist and, when any whitelist glob exists and the entry is a file that matched nothing, answers `Ignore(Glob::unmatched())`, which is the `UnmatchedIgnore` the debug log prints. Before matching, `crates/ignore/src/gitignore.rs` `strip` (286 to 315) removes a leading `./` and then the matcher's own root from the candidate path "to make sure we get relative matching right"; the matcher's root is the cwd, so a relative path like `rootA/src/a.py` is matched whole, root text included.

EXECUTED. A scratch tree `rootA/src/a.py`, `rootA/src/c.txt`, `rootA/src/deep/b.py`, `rootB/e.py`, `rootB/src/d.py`, `rootC/src/f.py` was built under the session scratchpad and `rg --files` run with two positional roots and one glob; the transcript is in the experiments folder. `-g '*.py'` listed the four `.py` files under `rootA` and `rootB` and none under `rootC` (roots bound the walk). `-g 'src/*.py'` and `-g '/src/*.py'` listed nothing (exit 1): the slash anchors the glob at the cwd, where no `src` directory exists, so it was not applied relative to each root. `-g '**/src/*.py'` listed `rootA/src/a.py` and `rootB/src/d.py`. `-g 'rootA/src/*.py'`, a glob the user composed from root text and pattern, listed `rootA/src/a.py`: it works only because the matcher sees the full walked path, and it silently excludes everything under `rootB`. Run from inside `rootA` as `rg --files . ../rootB -g 'src/*.py'`, only `./src/a.py` was listed: the glob matched the first root's entries because their walked paths begin at the cwd, and none of `../rootB`'s because theirs begin with `../rootB`. The `--debug` lines for the anchored glob show the override verdict per entry: `ignoring rootA/src/a.py: Ignore(IgnoreMatch(Override(Glob(UnmatchedIgnore))))` and the same for every other file, confirming the glob was evaluated per entry during the walk and rejected each as unmatched rather than being rewritten into a path pattern per root.

INFERRED. The brief asked whether ripgrep applies the glob "relative to each root": it does not, and it does not compose either. It carries roots and globs as two objects, applies the roots as the walk's start points and the globs as a per-entry filter against the walked path string anchored at the cwd. The consequence for a multi-root caller is visible in the experiment: an anchored glob cannot mean "under each root" in ripgrep at all, only "from the cwd" or, with `**/`, "anywhere". No per-root authorization exists beyond the operating system's.

## 3. git: a pathspec is one shape for roots and patterns, OR-ed per entry during the walk, and the one text composition, the cwd prefix, records the composed root's length as structured magic beside the text

READ. `pathspec.h` lines 30 to 50 define `struct pathspec` as a count plus an array of `pathspec_item`, each carrying `match` (the text matched against), `original`, `magic`, `len`, `prefix` and `nowildcard_len`. A root (`src`) and a pattern (`:(glob)src/**/*.py`) are the same item type; the magic bits `PATHSPEC_FROMTOP`, `PATHSPEC_GLOB`, `PATHSPEC_ICASE`, `PATHSPEC_EXCLUDE` (pathspec.h 7 to 19) qualify an item rather than typing it. Across the API, roots and patterns are therefore one shape.

READ. `init_pathspec_item` (`pathspec.c` 447 to 520) is the composition point. Unless the element carries `:(top)` (`PATHSPEC_FROMTOP`, prefix length 0, line 485) or an explicit `:(prefix:N)`, the command's working-directory prefix is joined with the element by `prefix_path_gently` (489) and the result stored as `item->match`, with `item->prefix = prefixlen` (507) recording how many leading bytes are the literal root. When a pathspec is re-serialized for another command (`PATHSPEC_PREFIX_ORIGIN`, 513 to 520), `prefix_magic` (114 onward) emits `:(prefix:%d)` so the receiving command recovers the same split. This is the single client-side composition the study found, and git pairs the composed text with a structured record of the root's extent.

READ. Matching is per entry and OR-ed: `do_match_pathspec` (`dir.c` 518 to 580) loops over every item, calls `match_pathspec_item` (392 onward; its leading comment at 400 to 428 explains that the common prefix may already have been cut by the caller's `common_prefix_len` pruning), and keeps the strongest verdict, so any item admits the entry. Exclude items run as a second pass and veto (`match_pathspec_with_flags`, 582 to 595). `match_pathspec_item` reads `item->prefix` to compare the literal root exactly even under `:(icase)` (429 to 431), which is why the prefix length is recorded rather than only the composed text. `git grep` applies it inside the index walk (`builtin/grep.c` 574) and, for tree walks, through `tree_entry_interesting` (634), whose `do_match` in `tree-walk.c` (1021 onward) can answer `all_entries_interesting` or `all_entries_not_interesting` for a whole subtree, so a directory root prunes descent before entries are generated. `git ls-files` applies the same `match_pathspec` per cache entry (`builtin/ls-files.c` 329, 371) and notes at 457 to 459 that "match_pathspec() is linear in pathspec.nr, so prefilter only the single-pathspec case". Root applied: during the walk, per entry, with subtree pruning from the literal prefix. Per-root authorization: none.

## 4. Lucene and OpenSearch: the root is a FILTER clause, scored clauses are MUST, both are required and conjoined with the cheapest leading, and the filter is cached by a usage policy

READ. `BooleanClause.Occur` (`lucene/core/src/java/org/apache/lucene/search/BooleanClause.java` 28 to 62) has four values; `FILTER` is documented at 35 to 36 as "Like MUST except that these clauses do not participate in scoring", `isRequired` is true for both `MUST` and `FILTER` (81), and `isScoring` for `MUST` and `SHOULD` (85). A path root is a `PrefixQuery` (`PrefixQuery.java` 29 to 44: an `AutomatonQuery` built from the prefix bytes with `CONSTANT_SCORE_BLENDED_REWRITE`) on the path field as a `FILTER`; a file-name wildcard is a `WildcardQuery` as `MUST` or `FILTER`; content text is a `MUST`. Two shapes across the API, in one request, by occurrence rather than by field.

READ. The filter is applied during candidate generation, not after. `BooleanWeight`'s constructor (`BooleanWeight.java` 55 to 60) creates every non-scoring clause's weight with `ScoreMode.COMPLETE_NO_SCORES`; `IndexSearcher.createWeight` (`IndexSearcher.java` 976 to 983) wraps any weight created without scores in the query cache. `BooleanScorerSupplier.getInternal` (141 to 150) builds a pure conjunction as `req(FILTER, MUST, leadCost)`, and `computeCost` (82 to 96) takes the lead cost as the minimum over the `MUST` and `FILTER` suppliers, so whichever required clause is cheapest, often the prefix filter, leads and the others are advanced to its documents. Caching is a policy: `UsageTrackingQueryCachingPolicy` caches a filter after it has been seen twice when it is "costly" (`MultiTermQuery`, its constant-score wrappers, `TermInSetQuery`, point ranges; lines 45 to 52 and 115 to 130) and after five uses otherwise; `LRUQueryCache` refuses to materialize a cache entry when `cost / skipCacheFactor > leadCost` (838 to 850), that is, when the filter is far broader than the clause it is being intersected with. A path prefix filter is thus a first-class cached DocIdSet, never a string spliced into the content query.

READ (documentation, 2026-11-07). OpenSearch's Boolean query page says `must` and `should` clauses "run in a query context and contribute to the `_score`" while `filter` and `must_not` "run in a filter context and only include or exclude documents", that "The results of a filter query are generally cached to allow for a faster return", and its example pairs a `must` `match` with a `filter` `term` on `play_name`. The query and filter context page says "With a filter context, OpenSearch returns matching documents without calculating a relevance score", that "OpenSearch caches frequently used filters", and shows a `match` in `must` beside `term` and `range` filters returning the same documents as the filters alone with their scores unchanged. The request carries the scope as its own JSON key beside the scored clause: two shapes, one call. Neither page composes a path into the match text.

INFERRED. Lucene core has no per-root authorization; OpenSearch's document-level security is, by its design, a further filter clause added server-side to the request, which fits the same pattern (a structured clause, not pattern text), but this study did not read that plugin and records it as inference only.

## 5. tantivy: roots are a range or regex query on the path field under Occur::Must beside the term query, intersected cheapest-first, with no FILTER occurrence

READ. `query-grammar/src/occur.rs` lines 9 to 19 define `Occur` as `Should`, `Must` and `MustNot` only; there is no non-scoring `Filter` occurrence, and `src/query/boolean_query/boolean_weight.rs` reads exactly those three (`per_occur_weights.get(Occur::Must)` at 321, `Should` at 335, `MustNot` at 341). A path root is a `RangeQuery` over the path field (`src/query/range_query/range_query.rs` 72 to 115: fast-field weight when the field is a fast field of a supported type, otherwise an `InvertedIndexRangeWeight` that walks the term dictionary between the bounds, 150 to 175), or a `RegexQuery` or `PhrasePrefixQuery` from the parser (`src/query/query_parser/query_parser.rs` 958 to 967), placed under `Must` beside a `TermQuery`. Two shapes across the API by occurrence and by field, in one `BooleanQuery`.

READ. Application is during candidate generation: `complex_scorer` (boolean_weight.rs 313 to 395) builds every `Must` scorer, returns empty at once if any is already terminated or empty, and intersects them; `intersect_scorers` (`src/query/intersection.rs` 20 to 35, 90) sorts the scorers by `cost()` and leads with the cheapest, which for a narrow path range is the range scorer. Scoring is a property of the combiner (`DoNothingCombiner` is imported at line 9 for the no-score case), not of the clause, so a root under `Must` contributes a constant unless wrapped in a `ConstScoreQuery`. No composition of a path into the term; no per-root authorization.

## 6. The table and what the five agree on

| Engine | API shape of roots | API shape of patterns | Where the root is applied | Per-root authorization | Client-side composition |
|---|---|---|---|---|---|
| zoekt | Structured leaves: `RepoSet`, `RepoIDs`, `BranchesRepos`, `Repo`, `Branch`, `FileNameSet` (READ) | Structured leaves: `Substring`, `Regexp` with `FileName`/`Content` flags (READ) | Before shard open (`selectRepoSet`), per shard (`simplify`), and during candidate generation (`docMatchTree.nextDoc`); never a post-filter (READ) | Client resolves permitted repositories to a set clause (INFERRED from READ comments); engine skips each candidate whose repository's tenant fails `tenant.HasAccess` (READ) | No; only `^QuoteMeta$` of a single exact value in the web UI (READ) |
| ripgrep | Positional paths, `WalkBuilder::add` (READ) | `-g`/`--iglob` globs in an `Override` rooted at the cwd (READ) | Roots start the walk; globs are a per-entry override against the walked path, anchored at the cwd, not per root (READ, EXECUTED) | None | No; a user may compose `rootA/src/*.py` and it works only because the full path is matched, excluding other roots (EXECUTED) |
| git | `pathspec_item` (READ) | The same `pathspec_item`, with `:(glob)` and other magic (READ) | Per entry during the walk, OR over items; literal prefix prunes subtrees via `tree_entry_interesting` (READ) | None | Yes, once: the cwd prefix is joined into `match`, and `item->prefix` plus `:(prefix:N)` magic carry the root's length beside the text (READ) |
| Lucene / OpenSearch | `FILTER` clause (`PrefixQuery`, `term`, `range`) in filter context (READ) | `MUST`/`SHOULD` clauses in query context (READ) | During candidate generation: required conjunction led by the cheapest clause; filter DocIdSets cached by usage policy (READ) | None in core; document-level security is a further server-added filter (INFERRED) | No (READ) |
| tantivy | `RangeQuery`, `RegexQuery` or `PhrasePrefixQuery` on the path field under `Must` (READ) | `TermQuery` and friends under `Must`/`Should` (READ) | During candidate generation: `Must` scorers intersected cheapest-first (READ) | None | No (READ) |

INFERRED. The five agree on three things. First, the root is a structured clause with its own type, field or occurrence, and the pattern is another; the two meet only in the engine's conjunction, never as one string. Even git, the one engine whose API gives roots and patterns a single item type, keeps the root's extent as a number beside the composed text and re-emits it as magic when the text is handed on, because matching needs to know where the literal root ends. Second, the root is applied as early as the engine's structure allows and always during candidate generation, never as a post-filter over matched rows: zoekt prunes shards and then drives the document cursor with it, git prunes subtrees with it, ripgrep starts the walk at it, Lucene and tantivy lead the conjunction with whichever required clause is cheapest. Third, where authorization exists it is judged per root and per candidate against a fact the root carries, in the engine, after the structured clause has admitted the candidate, and the permitted set itself crosses the wire as a set of IDs, not as pattern text. Read against a storage seam that takes `roots` and `arms` as two fields of one call: that is the shape every engine here already has, and none of them offers a second, text-composed shape beside it. The ripgrep experiment shows what composition costs when a tool lacks a per-root channel: an anchored glob cannot be made to mean "under each root", and a user who composes `rootA/src/*.py` silently drops the other root. git shows the minimum a composed text must carry to be judged correctly: the length of the root inside it. The rights question the brief raises, where an anonymous caller's gate is judged, maps in zoekt to a per-candidate check against the root's own fact after admission, not to a re-derivation of the admitting text; whether vfs can judge at the root the same way, or must keep the composed-path judgement for the posture inheritance decision 6 describes, is a vfs question this prior art informs but does not answer.

## What this study does not settle

It did not read Sourcegraph's zoekt client (the `sourcegraph/sourcegraph` monorepo is not cloned), so the claim that repository permissions are resolved to `RepoIDs` or `BranchesRepos` client-side rests on zoekt's own comments and the shapes it accepts, not on the sender's code. It did not read OpenSearch's security plugin, so document-level security as an added filter is inference from the documented filter model. It did not measure anything but ripgrep: zoekt's `docMatchTree.nextDoc` scans document IDs linearly against its predicate, and whether that costs more than a bitmap at ten thousand repositories per shard was not timed. It did not examine how Lucene or tantivy handle ten thousand roots in one request (ten thousand `PrefixQuery` filters under one `BooleanQuery`, or a `TermInSetQuery` of directory IDs), which is the scale the brief's spec designs for; the engines' clause-count limits and the cost of a wide filter union are a separate study. It did not study how any of the five judges a nested or overlapping root set, the case vfs's `ScopeChannel` reads every covering root for.

## One line

Every mature engine studied carries where-to-look and what-to-match as two structured channels, applies the root during candidate generation rather than after, judges authorization per root against a fact the root carries, and never composes root text into the pattern; the one that composes a cwd prefix (git) records the root's length beside the text so matching can still tell the two apart.
