## 1. import-linter is a contract checker over grimp's import graph, and its `protected` contract is exactly "nothing outside P imports P except these modules"

READ. import-linter has five contract types, one module each under `src/importlinter/contracts/`: `layers`, `forbidden`, `independence`, `protected` and `acyclic_siblings`. Each is a class with declared fields and a `check(graph, verbose)` method that queries a `grimp.ImportGraph`; the graph is built once per run by grimp and every contract reads it.

READ. The `forbidden` contract takes `source_modules` and `forbidden_modules`; by default both are treated as packages (descendants included) and indirect imports are checked too, so a chain through a third module breaks it (`docs/contract_types/forbidden.md` lines 5 to 10). `ignore_imports` is a set of `a -> b` expressions, with wildcards, that are removed from the graph before the check; `unmatched_ignore_imports_alerting` (`none`, `warn`, `error`, default `error`) makes a stale ignore fail the run, which is how an ignore list behaves as a shrinking baseline.

READ. The `layers` contract takes an ordered list, highest first, and fails on any import, direct or indirect, from a lower layer to a higher one (`docs/contract_types/layers.md` lines 5 to 40). Several modules can share one line: joined by `:` they share a layer and may import each other; joined by `|` they are independent siblings that must not. `containers` lets the layer names be relative to a parent package, and `exhaustive = true` (containers only) fails when a module appears in the container that no layer names, with `exhaustive_ignores` for the exceptions. Layers in parentheses are optional and skipped when absent.

READ. The `protected` contract (`src/importlinter/contracts/protected.py` lines 10 to 46) takes `protected_modules` and `allowed_importers`, both module expressions with wildcards, treats both as packages by default (`as_packages`), accepts `ignore_imports`, and checks direct imports only: "no module other than `green` (and its descendants) will be allowed to import `blue` (and its descendants) directly" (`docs/contract_types/protected.md` lines 5 to 9). That is the brief's sentence, "nothing outside package P imports from P except these two modules", as a six-line contract; the experiment in section 6 writes it for vfs and runs it.

READ. `independence` takes a list of modules none of which may import another, directly or indirectly; `acyclic_siblings` takes `ancestors` and fails on any import cycle among the children of each ancestor. import-linter's own `.importlinter` declares an exhaustive eight-layer contract over its own package (`cli`, `ui`, `api`, `contracts`, `configuration`, `adapters`, `application`, `domain`) plus `acyclic_siblings` over everything; grimp's own `.importlinter` declares a five-layer exhaustive contract and ignores four `grimp.<x> -> grimp` edges with the comment that grimp "doesn't understand extension modules", a quirk that bit the vfs run too (section 6).

READ. `TYPE_CHECKING` handling lives in grimp, not import-linter. grimp's Rust parser (`rust/src/import_parsing.rs` lines 125 to 153) marks an import `typechecking_only` when it sits in the body of an `if` whose test is the name `TYPE_CHECKING` or any attribute `.TYPE_CHECKING`, propagating the flag into nested bodies and treating `elif`/`else` branches as runtime; the top-level option `exclude_type_checking_imports = True` (`docs/get_started/configure.md` lines 74 to 77) then leaves those edges out of the graph entirely. Default is `False`: guarded imports count unless the project opts out.

READ. It runs as the console script `lint-imports` (alias `import-linter lint`), reading `.importlinter` (INI), `setup.cfg`, or `[tool.importlinter]` in `pyproject.toml`; it caches the graph under `.import_linter_cache` and has `--no-cache`. import-linter runs itself in CI as a plain step, `uv run lint-imports` (`.github/workflows/main.yml` line 62), and documents a pre-commit hook. Its dependencies are `click`, `grimp` and `rich` (`pyproject.toml` lines 10 to 14); grimp is a maturin-built Rust extension (`grimp/pyproject.toml` lines 2 to 3), so adopting import-linter adds one compiled wheel and two pure ones to the dev group.

## 2. tach declares per-module `depends_on` lists and an optional layer ladder in `tach.toml`, skips `TYPE_CHECKING` imports by default, and is a Rust binary

READ. tach's configuration is one `tach.toml`: a top-level `layers` list (highest first), `exclude` globs, `source_roots`, flags `exact` (fail when a declared dependency is unused), `forbid_circular_dependencies`, `ignore_type_checking_imports` (default `true`, the opposite default from grimp), and a `[[modules]]` table per boundary with `path`, `depends_on`, optional `layer`, `utility = true` (anyone may import it undeclared), `unchecked = true`, and `depends_on_external` (`docs/usage/configuration.md`; `docs/usage/faq.md` lines 61 to 63 for the type-checking default). A module in a layer may import any lower layer without declaring it, must declare same-layer dependencies, and may never import a higher layer; `layers_explicit_depends_on = true` demands declarations across layers too, and a "closed" layer forbids higher layers from reaching past it (`docs/usage/layers.md` lines 19 to 70).

READ. The vfs sentence "nothing outside P imports P except A and B" has no single tach construct: tach is declared from the importer's side, so every module's `depends_on` would simply omit P, and only A and B would list it. With `exact = true` the lists also fail when they over-declare. tach's own `tach.toml` uses three layers (`ui`, `commands`, `core`) and a `[[modules]]` entry per module with `exact = true` and `forbid_circular_dependencies = true`.

READ. It runs as `tach check`, recommended "like a linter or test runner, e.g. in pre-commit hooks, on-save hooks, and in CI pipelines" (`docs/usage/commands.md` line 80), with a pre-commit hook repo `gauge-sh/tach-pre-commit`. The wheel is maturin-built Rust with a Python shell (`pyproject.toml` lines 143 to 147), depending on `pyyaml`, `tomli-w` and `rich`. INFERRED: a PyPI listing for a fork named `dtach` calls tach "unmaintained", but the clone's last commit is dated 2026-10-30, so the upstream is alive as of this study.

## 3. pytest-archon is the only one of the three that is a pytest test by construction, and it is small, pure Python and quiet since 2025

READ. pytest-archon exposes one fluent builder, `archrule(name).match(glob).exclude(glob).should_not_import(glob).may_import(glob).check("package")`, used inside an ordinary test function (`README.md` lines 20 to 70; `src/pytest_archon/rule.py`). The whole package is 672 lines across six files.

READ. INFERRED: the `should_not_import` plus `may_import` pair expresses the vfs protection rule from the importer's side (`archrule("adapter").match("vfs*").exclude("vfs.storage.backends*").should_not_import("vfs.storage.backends.database*")`), about four lines, but it needs the dependency and gives a less exact report than either alternative. The last commit is 2025-09-19 and the dependency list is `importlib_metadata` for old Pythons only.

## 5. Module size: pylint caps a module at 1,000 physical lines, ruff declines to, and the ratchet shape exists only in two small tools

READ. pylint's `too-many-lines` (C0302), in `pylint/checkers/format.py`: message "Too many lines in module (%s/%s)", option `max-module-lines` default 1000, help "Maximum number of lines in a module." The checker walks the token stream, tracks the row of each token, subtracts one "to be ok with `wc -l`", and reports when the total exceeds the option; blank lines, comments and docstrings all count, since every one produces tokens with a row. The message can be disabled per file with the usual pragma, and the checker looks up `_pragma_lineno` to decide which line to report it on. INFERRED: it is a hard cap with a per-file escape hatch, and nothing in it reads a trend.

READ. ruff has no equivalent. `uv run ruff rule --all` lists thirteen `too-many-*` rules and every one is function- or class-scoped (`PLR0904` public methods, `PLR0911` return statements, `PLR0912` branches, `PLR0913` arguments, `PLR0914` locals, `PLR0915` statements, `PLR0916` boolean expressions, `PLR0917` positional arguments, `PLR1702` nested blocks, `PLW0717` statements in a try). Issue astral-sh/ruff 25001, "Pylint C0302", opened 2026-05-05 and still open, records that the umbrella issue 970 marks C0302 "not compatible with the formatter"; a maintainer answered that "the alternative is to use a complexity metric other than line numbers, for example mccabe" and later suggested that a file-length rule for agents belongs in a skills document rather than the linter. A third-party plugin, `ruffian`, ships `PLC0302 too-many-module-lines` at a 1,000-line default.

READ. Every project the search surfaced treats the ceiling as a hard cap at or above pylint's default: AI-SDC/ACRO 1000 under `[tool.pylint.format]`, andreoliwa/nitpick 1000, Eclipse Aidge 1000, a coronavirus-tracker-api config 800, and the tinybirdco fork of ClickHouse 2000 "because of SQL content". I found no project that lowers the cap below 800, and none that ratchets it.

READ. The ratchet shape exists outside the linters. `ratchet-size` 0.2.3 (PyPI, released 2026-10-11) writes a committed `.ratchet.json` after `ratchet init` holding line budgets for a `source` group and a `tests` group; the budget only shrinks as code is removed, a change that would push a group over it is refused with a message telling agents to stop and ask a human, and growth needs a human-issued `ratchet grant` recorded in `.ratchet-grants.jsonl`; it runs as an optional pre-commit hook and a CI step. `riskratchet` blends function length and file length into a "sprawl" score whose bar "can only move down, never up". INFERRED: both are young single-author tools; what vfs would take from them is the shape, a committed baseline that the check compares against and that may only move one way, not the dependency.

READ. dify's `.importlinter` shows the same shape applied to imports: the `ignore_imports` list is the baseline, `unmatched_ignore_imports_alerting = error` is the ratchet, and the comment names it as such. INFERRED: this is the strongest prior-art for a vfs size check, because it is a mature project treating a debt list as a one-way gate inside the very tool that holds its import direction.

## 7. Weighing the two for vfs, I would take the stdlib test now and name the condition under which import-linter replaces it

INFERRED. The case for the stdlib test. `tests/lint/` is already a package of pytest tests that read the tree with `pathlib` and regular expressions (`test_code_shape.py` lines 35 to 42 walk `SRC.rglob("*.py")` and assert on a list of `path:line` hits), so an `ast` walk in the same file shape is the pattern the project already runs, in the same `uv run pytest` and in `scripts/ci.sh` with nothing added; it needs no new dependency where import-linter brings a compiled `grimp` wheel plus `click` and `rich` into the dev group and tach brings a Rust binary; its failure message is the project's own `file:line: importer imports imported` list, which is what a reviewer and an agent act on; it ran in 0.38 seconds against 94 modules and the whole walk is a few hundred microseconds a file, so it will not move the one-minute budget; the layer table is a Python tuple in the test, read by the same people who read the lint; and the size baseline comes out of the same walk for free, where no linter offers one. The brief's first finding stands on its own: the test found today's five adapter imports and three upward imports that no tool in the gate refuses, and it found them before import-linter was installed.

INFERRED. What the stdlib test gives up, and when that matters. It checks direct edges only; import-linter follows chains, which catches a lower layer reaching a higher one through an unlisted helper module. In vfs every module is in some layer or is a leaf, and the brief's rule is already "every import at the top, absolute", so a chain is a sequence of direct edges each of which the test sees; a chain only escapes when its middle module is outside every declared layer, which the `exhaustive` idea closes: the test can assert that every module under `src/vfs` belongs to a declared layer, two lines, and then direct-edge checking is complete. import-linter also has `ignore_imports` with `unmatched` alerting, which is the ratchet for a boundary under repair; the stdlib test can hold the same as a frozenset of `(importer, imported)` pairs with a second assertion that every pair still occurs, about ten lines. It has caching, a rich report, wildcards, optional layers and a published semantics people know; none of those is load-bearing at five contracts.

INFERRED. The condition for switching: when the contract set grows past a handful (a layer ladder, a protected adapter, an independence pair, an acyclic check), or when someone wants `acyclic_siblings` over the whole tree, the stdlib test is reimplementing import-linter and the dependency is "clearly better" in the sense the brief uses; at that point the `importlinter.ini` in the experiments folder is the starting configuration, run as one more line in `scripts/ci.sh`, and the stdlib test's graph builder is deleted. kedro, dify and kopf show that shape works at scale with four to seven contracts. tach fits a project that wants every module's dependency list written out (scipy) and sits less well with a layer-and-exception style and with pytest-as-lint; pytest-archon fits the test shape best of the three but is dormant and adds a dependency for four lines.

INFERRED. For module size, no tool is the answer. pylint's cap is a dependency vfs does not carry for one number, ruff will not add the rule, and the ratchet tools are too young to pin a gate on. The shape the prior art agrees on (dify's exact ignore list, ratchet-size's committed budget, the fitness-function phrasing "do not add a violation") is a committed baseline that the test compares against and that may only move one way: a small mapping of module name to line count for every module over a threshold (say 1,000 lines, pylint's default, which five vfs modules exceed today), held in the lint package, with the test failing when a listed module grows past its entry or an unlisted module crosses the threshold, and shrinking the entry being the only edit a landing may make to it. The five-row baseline in this section is that file's first content. A hard cap would fail today on five modules, and a review prompt alone is what let `base.py` grow 450 lines in a week with nobody reading the trend.

## What this study does not settle

It does not settle whether the declared layer order in the brief is the order the spec wants, because the live tree contradicts it in three places the test exposes (`base` imports `session` at runtime; `results` imports `pattern_matching.grep`) and only the spec can say which side moves. It does not measure import-linter's or the stdlib test's running time on a tree ten times this size, nor the stdlib walk's cost once a transitive closure is added. It did not read PostHog's `hogli lint:tach` wrapper or kopf's custom conditional contract, so it cannot say what those add beyond the stock contract types. It did not find a mature project that ratchets file length, so the size baseline design in section 7 rests on two young tools and dify's import baseline, not on a precedent for size itself. It did not execute tach or pytest-archon against vfs; both are described from source and documentation. It did not confirm pylint's per-file disable pragma for C0302 beyond the checker's own lookup of the pragma line.

## One line

A stdlib `ast` test in `tests/lint/` already holds vfs's layer map and today names five adapter imports and three upward edges that import-linter's `protected` and `layers` contracts also name; keep the test, add a one-way size baseline from the same walk, and move to import-linter only when the contracts outgrow a handful.
