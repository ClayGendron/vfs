## The scenario (from Clay)
An enterprise runs its agents on vfs. The store holds ~1,000,000 files. Employees and agents edit 1–5% of files per day (10k–50k entries/day, concentrated in an 8h workday => roughly 20–100 edits/minute, so a 5-minute window dirties ~100–500 entries, a 60-minute window ~1,250–6,250). The devs can afford a FULL re-index three times a day (8AM, 12PM, 4PM). Question: what incremental refreshes could run every 5 / 15 / 30 / 60 minutes between full rebuilds, WITHOUT increasing the latency of `write`? Production is Postgres/SQL Server/Oracle, not SQLite (SQLite is the dev default). No statement may grow unboundedly with batch size (Oracle 1,000-element IN list, SQL Server ~2,100 binds). Never design a hard scale cap.

## How indexing works today (verified in the code, 2026-10-31)
Files to read: src/vfs/storage/backends/database/indexing.py (module docstring + build_epoch/publish_epoch/reclaim_epochs), lexical.py, grep.py (module docstring, _index_doc_ids, _posting_meta, _posting_blobs), glean.py (module docstring, _overlay, OVERLAY_BUDGET), embed.py, writes.py (_material_values), models/rows.py (entry, chunks, meta, gram_epochs, posting_list, lex_* tables), backend.py (reindex, _reindex_phases, _gram_phases, the embed step ~L1420-1483), crates/vfs-core/src/postings.rs (candidate_ids).

- The write path does NOT touch the index. A content write resets three flags on the entry row: chunked=False, encoded=False, indexable=False (writes.py `_material_values`). That is the whole write-side cost. The "dirty set" is `WHERE NOT encoded` (index `ix_vfs_entries_encoded_kind`). Deletes demote `encoded` too and stamp `deleted_at`.
- `reindex()` is a batch admin verb, one runner at a time via a heartbeat lease on the meta row. Phases: render binaries -> chunk the dirty (`chunk_dirty`: assess eligibility, split into semantic chunk rows, stamp `chunked`/`indexable`) -> `build_epoch` (gram trigram postings for EVERY `chunked ∧ indexable ∧ live` entry, keyed by entry surrogate `entry.id`, under a fresh epoch number; then BM25 lexical index `build_lexical_epoch` over every chunk row of the same entries, under the same epoch) -> `publish_epoch` (flip `encoded=True` for covered entries AND compare-and-set the pointer `meta.current_gram_epoch`, one transaction) -> `reclaim_epochs` (delete every epoch-scoped row strictly below the pointer) -> segment/edge re-convergence -> embed step (`select_unembedded` keyset pages; this step IS already incremental: only chunks with no vector are embedded, and a chunk's vector is carried forward by content hash).
- So the gram+lexical build is WHOLE-CORPUS whenever anything is dirty: `_work_pending` is true if any live entry awaits encoding; the rebuild re-posts all 1M entries. Peak memory is the whole posting set (disclosed in the build_epoch docstring; "gram-range partitioned passes" named as the future direction).
- Invariant (indexing.py docstring): `encoded=True` implies the entry's grams/terms are in the CURRENT epoch. Every coverage exit demotes the flag. Readers partition on it: index tier (encoded) ∪ scan tier (NOT encoded, live bodies read and matched/scored at query time). So staleness never loses a match — it costs scan work.
- grep: intersects posting blobs of the rarest grams via the Rust kernel `candidate_ids(groups, allow, cap)` (each group = AND over blobs, groups OR), then VERIFIES every candidate by fetching its content and running the matcher. So a stale posting that nominates an entry whose content changed is harmless: verification rejects it. Ghost doc ids (deleted entries) are likewise filtered at the content fetch. Then the scan tier reads EVERY admitted NOT-encoded row's body. Epoch coherence is checked by re-reading the pointer; movement raises StaleSnapshot and the call redrives.
- glean lexical leg: BM25 over `lex_df` (term stats per epoch) + `lex_postings` blocks; the `NOT encoded` rows are the "overlay": their live bodies are tokenized at query time and scored with the epoch's statistics. OVERLAY_BUDGET = 500: the overlay scores at most 500 unindexed entries per call, in path order, then a loud record. => with 10k dirty entries the lexical leg of glean silently serves only 500 of them. The vector leg reads chunk vectors directly, no epoch; new chunks have no vector until the embed step runs.
- Posting PK is (epoch, gram_key). Lexical tables are epoch-scoped too. `tables.epoch_scoped()` lists them. `gram_epochs` holds (epoch, format_version, options_hash).

## What "incremental" must respect
1. No extra write-path latency (an extra insert per write is NOT free; the flags already mark the dirty set).
2. Bounded statements on Oracle/SQL Server: chunk by `membership_budget`.
3. Readers must stay coherent (one consistent view per call) and never lose a match (the scan tier is the safety net; a refresh may only shrink it).
4. Concurrency with the 4-hourly full rebuild and with each other: the lease, the epoch CAS, reclaim.
5. BM25 statistics (df, N, avgdl) semantics under partial refresh.
6. Memory and CPU bounded by the dirty set, not the corpus.
