# Data engineers expect a plain blocking API with chunked iterables and a context manager, and every library they use gives them one, with async either absent or bolted on behind a background loop thread they never see

This study asks what the pandas population, data engineers who never write `await`, expects from a file-system library that reads and writes 10,000 entries at a time, and how each API shape in the brief's catalog feels in a Jupyter notebook. The box was 45 minutes. When it ran out, the pandas, fsspec, polars, DuckDB, pyarrow and Dask code reads were done, one notebook experiment had run in a real ipykernel with eleven cells, one statement-count experiment had run for `to_sql`, and, added mid-study at the owner's request, SQLAlchemy 2 had been read and one experiment run on its sync core and async front (section 4); to make room, the pyarrow and DuckDB reads stayed at the level of their public signatures, and no web pages were read, so every claim below rests on code or on an executed run.

## The answer

A data engineer expects to call `fs.read(...)` and `fs.write(...)` and get the answer back, in a script, a notebook cell, an Airflow task or a thread pool, with no event loop in sight. Every library in that population's toolbox does exactly this. pandas has no async path at all and refuses an async SQLAlchemy engine. DuckDB's Python package has no `async def` outside its tests. pyarrow's only asyncio surface is the Flight RPC client. fsspec and Dask are async inside, and both hide that behind one background loop thread, so the sync call is the default and the async form is the opt-in. polars marks its `collect_async` unstable, and its sync `read_database` over an async engine patches the notebook's running loop with a vendored `nest_asyncio`, which I watched change `asyncio.run`'s behaviour for the rest of the kernel session. SQLAlchemy 2, this population's other daily library, chose the same direction from the other end: a sync `Engine`/`Connection`/`Session` is the primary API, and `AsyncEngine`/`AsyncConnection`/`AsyncSession` are separate classes with the same method names, built over the sync core through a greenlet bridge, with `run_sync` as the hatch back. Big batches are served by two knobs everywhere: a `chunksize` or `batch_size` on the call, and an iterator of chunks on the way out. So, from this population's view, the best shape is the one vfs already has in `vfs.sync`: a separate blocking class with the same verb names, driven by its own loop thread, that works in a notebook because it never touches the notebook's loop. A one-class dual-mode API ranks lower here, because the notebook is exactly where such a class has to guess, and a wrong guess is either a coroutine where a result was expected or a blocked kernel. Said once more, plainly: blocking calls, same names, a hidden loop thread, chunked iterables in and out.

## 1. pandas offers sync only, chunks by caller-chosen size, and refuses an async engine

READ: `read_sql`, `read_sql_query` and `read_sql_table` return `DataFrame | Iterator[DataFrame]`, overloaded on `chunksize` (`pandas/io/sql.py:557`, `:572`, `:587`, `:598`). With a chunk size, pandas returns a generator that calls `result.fetchmany(chunksize)` in a loop and closes the connection when the generator ends (`pandas/io/sql.py:1859`, `self.returns_generator = True` at `:1833`). EXECUTED: `pd.read_sql('select * from t', eng, chunksize=2500)` over a 10,000-row table returned a `generator` yielding four frames of 2,500 rows (notebook cell 8).

READ: the user guide says plainly that `chunksize` alone usually does not cut peak memory, because most drivers fetch the whole result first; real streaming needs `execution_options(stream_results=True)` on the connection (`doc/source/user_guide/io.rst:6128`-`:6145`). INFERRED: the population has learned that "chunked" on the outside does not promise "bounded" on the inside, and the docs carry that caveat rather than the API.

READ: `to_sql` takes `chunksize` and `method` (`None` for executemany, `'multi'` for one multi-row `INSERT`, or a callable `(table, conn, keys, data_iter)`) (`pandas/io/sql.py:803`, `:1150`-`:1163`; the COPY recipe at `io.rst:5970`). With no `chunksize`, the whole frame is one chunk (`sql.py:1173`), and every chunk runs inside one transaction (`sql.py:1179`). EXECUTED: 10,000 rows, two columns, SQLite: `chunksize=None` sent one executemany INSERT; `chunksize=1000` sent ten; `method='multi'` with no chunk size sent one INSERT holding 20,000 bind parameters, and SQLite accepted it ([to_sql_statements.out](experiments/03-notebook-and-batch/to_sql_statements.out)). INFERRED: the same call against SQL Server's roughly 2,100-parameter cap would fail, so pandas leaves the parameter budget to the caller. vfs's rule that every statement chunks by a declared budget is stricter than what this population is used to, and they will not miss having to pick `chunksize` themselves.

READ: `pandasSQL_builder` accepts a `str` or a `sqlalchemy.engine.Connectable` and otherwise warns and falls back to treating the object as a DBAPI connection (`sql.py:968`, `:976`). EXECUTED: `pd.read_sql('select 1 as x', create_async_engine('sqlite+aiosqlite://'))` warned "pandas only supports SQLAlchemy connectable" and then raised `AttributeError: 'AsyncEngine' object has no attribute 'cursor'` (cell 9). INFERRED: pandas has no async story at all, and an async object handed to it fails late and confusingly. A data engineer will hand vfs objects to pandas, so a vfs object that is secretly a coroutine will meet the same kind of late failure.

READ: remote readers go through `fsspec.open(...).open()` inside `_get_filepath_or_buffer` (`pandas/io/common.py:500`, `:512`), and handles are closed through `IOHandles`, a context manager (`common.py:113`-`:157`). pandas never sees a coroutine; fsspec's loop thread does the async work.

## 2. fsspec and Dask are async inside and sync by default, through one hidden loop thread

READ: fsspec keeps one module-global loop and one daemon thread named `fsspecIO` (`fsspec/asyn.py:25`-`:26`, `get_loop` at `:243`-`:258`). `AsyncFileSystem.__init__` takes `asynchronous=False`; a sync instance attaches to that global loop (`asyn.py:490`-`:497`). `mirror_sync_methods` generates `cat` from `_cat`, `ls` from `_ls`, and so on, by wrapping each coroutine in `sync()` (`asyn.py:1150`-`:1179`); async generators are wrapped one `__anext__` at a time (`:227`). `sync()` submits with `run_coroutine_threadsafe` and waits on an `Event` in one-second slices so Ctrl-C can interrupt (`:86`-`:93`). It refuses only when the caller's running loop is the very loop it would wait on (`:78`-`:80`). The instance refuses use after `fork` (`:503`). Bulk calls fan out with `_run_coros_in_chunks`, whose default batch is 128 for file work, 1,280 for metadata work, or the open-file soft limit over eight (`:324`-`:351`, `:362`).

EXECUTED: from a notebook cell, while the kernel's loop was running on the main thread, `fsspec.asyn.sync(fsspec.asyn.get_loop(), answer)` returned the name `fsspecIO`: the coroutine ran on fsspec's own thread and the cell got a plain value (cell 7).

READ: Dask's `Client(asynchronous=False)` is the documented default; the docstring says to set it only "if using this client within async/await functions" (`distributed/client.py:1003`-`:1006`). `SyncMethodMixin.asynchronous` is context detection: true only when the running loop is the client's own loop (`distributed/utils.py:358`-`:365`, `in_async_call` at `:384`). `Future.result()` is annotated `-> _T` but its docstring says it returns "a coroutine if the client is asynchronous" (`client.py:409`-`:431`), and `Future.__await__` calls `self.result().__await__()` (`client.py:651`). `sync()` refuses a call from the loop's own thread (`utils.py:422`-`:423`). INFERRED: Dask is the catalog's mode flag and dual-use handle at once, and its type annotations already state one return type while the code returns another depending on the flag; a type checker cannot see the async branch.

READ against vfs: `SyncVirtualFileSystem` takes the same design, one loop per facade on a daemon thread named `vfs-sync-loop`, forwarding with `run_coroutine_threadsafe`, and refusing a call from its own loop thread (`src/vfs/sync.py:625`-`:631`, `:657`-`:663`, `:676`-`:683`). INFERRED: vfs is in good company; this is the shape fsspec and Dask converged on for the same population, with one difference worth keeping: a loop per facade rather than one global loop, which keeps an asyncpg engine bound to one loop.

## 3. polars, DuckDB and pyarrow are sync first, and polars shows the cost of guessing in a notebook

READ: polars' `LazyFrame.collect_async` is a name twin of `collect`, carries an "unstable" warning, runs the query in a thread pool, and returns an `Awaitable` or, with `gevent=True`, a handle with a blocking `.get()` (`lazyframe/frame.py:2228`-`:2300`). Batches go out as iterators: `DataFrame.iter_slices(n_rows=10_000)` (`dataframe/frame.py:12388`) and `LazyFrame.collect_batches` (`lazyframe/frame.py:4180`). `write_database(table_name, connection, if_table_exists=..., engine=...)` is plain blocking (`dataframe/frame.py:4485`-`:4492`).

READ: when `read_database` is handed an async SQLAlchemy connection, the sync call runs the coroutine itself through `_run_async`: `asyncio.run` with no running loop, and otherwise a vendored `nest_asyncio.apply()` followed by `run_until_complete` on the running loop (`io/database/_utils.py:18`-`:32`, called at `_executor.py:302`-`:303`). EXECUTED: in the kernel, `pl.read_database('select 1 as x', aeng)` returned `[{'x': 1}]`; afterwards `asyncio._nest_patched` was set, and `asyncio.run(asyncio.sleep(0, result='now allowed'))`, which had raised "cannot be called from a running event loop" in cell 2, now returned `now allowed` (cell 10). INFERRED: polars chose context detection plus a global monkeypatch to keep a sync signature over an async driver, and the patch outlives the call: every later cell in that kernel runs on a re-entrant loop. That is the brittle end of the "one API that detects context" shape, observed in a library this population uses daily.

READ: duckdb-python ships no `async def` outside its tests (searched the package and stubs). Its connection is a context manager (`_duckdb-stubs/__init__.pyi:154`), reads come back with `fetchmany(size)`, `fetch_df_chunk` and `to_arrow_reader(batch_size=131072)` (`:224`-`:229`, `:502`), and it accepts an fsspec filesystem through `register_filesystem` (`:491`), so a remote store reaches DuckDB through fsspec's sync face.

READ: pyarrow's only asyncio surface is the Flight RPC client, `FlightClient.as_async()` returning an asyncio-based client (`_flight.pyx:1348`, `:1489`). Datasets scan in batches of `2**17` rows by default (`_dataset.pyx:48`, `to_batches` at `:428`), and `write_dataset` accepts "iterable of RecordBatch" or a `RecordBatchReader` (`dataset.py:846`, `:858`-`:859`). It adapts fsspec through `FSSpecHandler` (`fs.py:265`). INFERRED: across these three, a bulk write takes an iterable or a reader, a bulk read yields batches, and nothing asks for a loop.

## 4. SQLAlchemy 2 keeps a sync core and wraps it in async class twins, the mirror image of vfs

READ: in SQLAlchemy the sync objects are the primary API and the async ones proxy them. `AsyncConnection` holds `self.sync_engine = async_engine.sync_engine` and `AsyncEngine.__init__(self, sync_engine: Engine)` keeps the sync engine it wraps (installed `ext/asyncio/engine.py:229`, `:1033`-`:1039`); each async method runs the sync method under `await greenlet_spawn(...)` (`engine.py:304`, `:351`, `:1098`). EXECUTED: the twins share names: `Session`/`AsyncSession` share 38 public names, 16 of which are coroutines on the async side (`execute`, `commit`, `close`, `delete`); `Connection`/`AsyncConnection` share 21, ten of them coroutines; `Engine`/`AsyncEngine` share 12 ([sqlalchemy_twins.out](experiments/03-notebook-and-batch/sqlalchemy_twins.out)). This is the catalog's class-twin shape, same method names on two classes.

READ: the bridge is two functions. `greenlet_spawn(fn, ...)` is a coroutine that runs a plain sync function in a new greenlet; whenever that function, deep in the sync core, reaches the async driver, `await_` (named `await_only` in 2.0, kept as a deprecated alias on main) switches to the parent greenlet with the awaitable, `greenlet_spawn` awaits it on the real loop and switches the result back (repository `lib/sqlalchemy/util/concurrency.py:143`-`:167`, `:173`-`:220`; installed `util/_concurrency_py3k.py:109`, `:167`). Called outside that context, `await_` cancels the awaitable and raises `MissingGreenlet` (`concurrency.py:155`-`:160`). EXECUTED: `aeng.sync_engine.connect()` from plain code raised `MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here. Was IO attempted in an unexpected place?`, and `await conn.run_sync(sync_work)` ran an ordinary sync function against the async connection and returned 42 (same output file). READ: `run_sync` exists on `AsyncConnection` and `AsyncSession` (installed `engine.py:820`, `session.py:335`) and the docs present it as the way to run sync-only code such as `metadata.create_all` or lazy loading under asyncio (`doc/build/orm/extensions/asyncio.rst:118`, `:554`-`:579`).

READ: on mixing, the docs say an `AsyncEngine` must not be shared across event loops with the default pool; moving it needs `dispose()` first, or else a "Future attached to a different loop" `RuntimeError`, and sharing needs `NullPool` (`asyncio.rst:973`-`:996`). They also say an `AsyncSession` is not safe for concurrent tasks (`asyncio.rst:162`, `:344`-`:350`), implicit IO such as lazy loading is not allowed under asyncio (`:396`-`:409`), and from 2.1 `greenlet` is no longer installed by default (`:43`). INFERRED: the loop-binding rule is the same hazard `SyncVirtualFileSystem.wrap` names for asyncpg, and the reason the vfs facade owns one loop per instance.

INFERRED: SQLAlchemy chose sync core, async wrapper, because its core sits on DBAPI, PEP 249, which is a blocking interface; nearly every driver is sync, the async drivers (asyncpg, aiosqlite) are the minority, and they are adapted to look like DBAPI so the one core can drive them. The greenlet lets that sync core suspend at the single point where IO happens without rewriting the compiler, the ORM and the event system as `async def`. vfs is the mirror image: its core is `async def` throughout (`src/vfs/base.py`), its storage is async SQLAlchemy, and its sync face is the wrapper. A thread-and-loop wrapper (fsspec's and Dask's choice, and vfs's) is the natural one for that direction, because no greenlet can make a coroutine callable from plain code; the greenlet trick only works when the core is sync. The lesson that carries over is the public shape, not the mechanism: SQLAlchemy shows a data engineer two classes with the same verbs, one per world, and that is the shape this population already knows from the library under `read_sql`.

## 5. What this population expects for 10,000 entries

INFERRED from sections 1 to 4: three habits are universal. First, a bulk call takes any iterable (a list, a generator, a reader) and a bulk read can come back as an iterator of chunks. Second, a size knob exists (`chunksize`, `batch_size`, `n_rows`), and the library has a sane default. Third, resources open with `with` and close at the end of the block or the end of the iterator. None of these needs `await`.

READ: vfs's `write` annotates `entries: Sequence[Entry] | None` (`src/vfs/base.py:958`-`:968`). EXECUTED: the sync facade accepted a generator of 10,000 entries anyway and wrote all of them, `success=True`, 10,000 rows (cell 5). INFERRED: the annotation is narrower than the behaviour, so `ty` or `mypy` will flag the generator a data engineer naturally writes; widening the annotation to `Iterable[Entry]` (or proving why it must stay `Sequence`) is the fix this population would notice first. vfs has no chunked-iterator read today; for this population that is the analogue of `read_sql(chunksize=...)` and its absence will be felt before any sync/async question.

## 6. How each shape feels in a notebook

EXECUTED: in ipykernel 7.2.0, cell code runs on `MainThread` while a `_UnixSelectorEventLoop` is running (cell 1). `asyncio.run(...)` raises `RuntimeError: asyncio.run() cannot be called from a running event loop`, and leaves a "coroutine was never awaited" warning in the cell output (cell 2). Top-level `await afs.write(...)` and `await afs.read(...)` on the async router work, because IPython's autoawait runs the cell as a coroutine (cell 3). A forgotten `await` gives a `coroutine`, and the next line fails with `AttributeError: 'coroutine' object has no attribute 'one'` (cell 4). The sync facade wrote 10,000 entries and read one back from a cell (cell 5), and served 200 reads from eight `ThreadPoolExecutor` threads (cell 11). While one sync facade call ran, the kernel's own loop advanced zero ticks; after one `await asyncio.sleep(0.01)` it advanced again (cell 6).

INFERRED, shape by shape, for a notebook user who never writes `await`. Class twins with the same names (`SyncVirtualFileSystem` beside `VirtualFileSystem`): works in every cell, script and thread, and the import line says which one you have; it blocks the kernel loop during the call, which matters only to widgets and comms, and pandas, DuckDB and fsspec block it the same way. Module twins (`vfs.sync.VirtualFileSystem`): the same behaviour, but a notebook that imports both under one name is confusing to read and to paste from. Name twins on one class (`read`/`aread`): works, and tab completion shows both, which doubles the list a data engineer scrolls. Mode flag (`VirtualFileSystem(asynchronous=False)`, fsspec and Dask): works, but the return type depends on a constructor argument, which Dask's own annotations get wrong. Context detection (Prefect, polars): in a notebook the loop is always running, so a detector sees "async" in a cell where the user wrote no `await` and hands back a coroutine (cell 4's failure), or, to avoid that, patches the loop as polars does (cell 10). Dual-use handles with `.result()`: works, but every call gains a `.result()` this population did not ask for. Async only with a documented bridge: top-level `await` works in Jupyter but not in a plain script or an Airflow task, and `asyncio.run` fails in the notebook (cell 2), so the user meets two different instructions for the same code. Sync only: works everywhere this population lives, and leaves the other two populations without an async path.

## 7. The three deliverables

(a) What a data engineer types without reading docs, as three snippets:

```python
from vfs import VirtualFileSystem
with VirtualFileSystem("postgresql://etl@db/warehouse") as fs:
    text = fs.read("/raw/2026/11/06/orders.csv").one().content
```

```python
entries = (Entry(path=f"/clean/{row.id}.json", content=row.to_json()) for row in df.itertuples())
result = fs.write(entries=entries, parents=True)          # 10,000 rows, one call, a generator
print(result.success, len(result))
```

```python
for chunk in fs.grep("/clean", "refund", chunksize=1000):   # or pd.DataFrame(fs.glean(...).rows)
    process(chunk)
```

(b) The ranked shortlist from this population's view. 1. Class twins with the same method names (`Client`/`AsyncClient`, today's `SyncVirtualFileSystem`): it is SQLAlchemy's `Session`/`AsyncSession` shape and fsspec's and Dask's mechanism, works in a notebook cell, a script and a thread pool with no loop, and the type checker always knows the return type. 2. Sync only: this population would never notice anything missing, but it abandons the other two populations, so it ranks below the twin that serves all three. 3. Module twins with identical class names: same mechanism as 1, and only the import line changes, which notebooks copy-pasted between async and sync code make easy to get wrong. 4. Name twins on one class (`read`/`aread`): it works, but every completion list doubles and a sync user must ignore half of it. 5. One class with a mode flag: fsspec and Dask ship it, yet Dask's annotations already lie about the return type, and a flag set in one cell changes what every later cell gets. 6. Dual-use handles with a blocking `.result()`: correct everywhere, but adds a call this population does not expect on every read. 7. Async only with a documented bridge: `asyncio.run` fails in a notebook, so the bridge differs between notebook and script. 8. One API that detects the caller's context: a notebook always has a running loop, so the detector guesses wrong for the sync user or patches the loop, as polars does.

(c) Brittleness of the top two. Class twins: the twin can drift from the router when a verb or parameter is added to one and not the other, which breaks a sync user with a `TypeError` or a missing method; a parity test over signatures finds it in CI before any user does. The per-facade daemon thread can leak if the user never closes it, which shows in `threading.enumerate()` under the name `vfs-sync-loop`; a facade constructed over an engine already bound to the notebook's loop (`wrap`) can fail on asyncpg, which shows as a traceback from the driver. A call made from a callback on the facade's own loop is refused with an `invalid` row rather than deadlocking, so the failure is visible, not a hang. Blocking the kernel loop during a call freezes widgets in that interval, which a notebook user sees as a stalled progress bar, the same as with pandas. Sync only: nothing breaks for this population; it breaks the FastAPI and LangChain populations, who must wrap every call in a thread pool and who find out in a load test, when the event loop stalls under blocking I/O.

## What this study does not settle

Whether a chunked-iterator read in vfs bounds memory the way pandas' docs say `chunksize` alone does not: an experiment would read 100,000 entries through a server-side cursor on Postgres and count rows held per yield with a tracing allocator. Whether ipywidgets progress bars stay live during a 10,000-entry sync write: an experiment would run a widget-driven notebook under nbclient and count comm messages sent during the call. Whether `Iterable[Entry]` can replace `Sequence[Entry]` on `write` without a second pass over the input: an experiment would pass a one-shot generator that records each `next` and count how many times the router walks it. Whether a mode-flag class could be typed honestly with overloads on a `Literal` flag: researcher 04 runs that under `ty` and `mypy`.

## One line

Data engineers want blocking calls, the same verb names, chunked iterables in and out, and a `with` block, which is what `vfs.sync` already gives them through its own loop thread; any shape that must guess from a notebook's always-running loop will guess wrong for them.
