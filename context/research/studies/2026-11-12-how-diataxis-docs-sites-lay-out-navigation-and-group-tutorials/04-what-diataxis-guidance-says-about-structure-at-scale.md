# Diátaxis's author says the four types are kinds of content, not four mandatory top-level boxes, and the teams that run large Diátaxis sites put the four types on one axis and the product's subjects on the other, keep tutorials to one marked path, and let how-to guides and reference grow by subject

I was asked on 2026-11-12 what the written guidance says about documentation structure at scale: the Diátaxis site's own pages, the published practice of documentation teams that adopted it, and practitioners who argue where it stops helping. The question names five points: whether the four types should be the top level of the navigation, how to handle a second dimension, where a getting-started page and a landing page belong, how each type scales, and what to do with content for advanced readers. The time box was 30 minutes and I used about 28. I read guidance and accounts, not site navigation, so for each source I report what it says on the five points instead of the brief's per-site list. One finding changes the ground: the Diátaxis page that held almost all of the author's guidance on structure at scale, "Diátaxis in complex hierarchies", is no longer on the live site; it was removed from the source on 2026-08-03 and I read it from the repository history.

## The framework's author: what Daniele Procida's pages say

The status of the pages first. EXECUTED: https://diataxis.fr/complex-hierarchies/ returned HTTP 404 on two tries. EXECUTED: the `source/` listing of the framework's repository on `main` has no `complex-hierarchies.rst`, and commit c9534824 of 2026-08-03, "Added translation machinery and content", lists the file as removed and drops it from the index toctree. Its last edit before then was 2023-12-22. READ: the live sidebar today is Start here, Applying Diátaxis (the four types, the compass, Workflow), Understanding Diátaxis (Foundations, the map, Quality, and the two comparison pages), then Colophon, translation and news. INFERRED: the commit message gives no reason. I cannot tell whether the author withdrew the page's argument or only left it out of the translated rebuild. Many recent secondary pages still cite the URL. Below, "the removed page" means that file at its last version.

Point 1, should the four types be the top level. READ, the removed page: "Diátaxis is not a scheme into which documentation must be placed - four boxes." It also says that positing four kinds of documentation "does not mean that there must be simply four divisions of documentation in the hierarchy", and that a clear four-way division is "a typical outcome of the good practice, not its end." READ, the live Workflow page: "Getting started with Diátaxis does not require you to think about dividing up your documentation into four sections." On creating empty sections for the four types first: "Don't do that. It's horrible." The top level comes last: the small changes are "how your top-level structure will form." READ, the 2021 Canonical post, which the same author wrote about Canonical's own plan: the aim is "a high-level division of the technical documentation into the four types, clearly signposted". INFERRED: so the author describes a four-way top level as the usual result, endorsed it for Canonical, and still refuses to make it a rule. The current live site says nothing about navigation at all. READ: the map page, the compass page, the quality page and the foundations page each have no sentence about site navigation; the compass works "at the level of sentences and words."

Point 2, the second dimension. READ, the removed page, section "Two-dimensional problems": Diátaxis collides with other structures, such as a product used on land, at sea and in the air, or users, developers and contributors. It draws two trees, one with the four types above the user type and one with the user type above the four types, and notes "There seems to be a lot of repetition in either cases." It picks neither. It sends the writer back to user needs, under "User-first thinking": "What we must document is the product as it is for the user, the product as it is in their hands and minds." It allows mixed shapes, for example developer content that follows on from user material while contributor how-to guides are kept apart. And: "Documentation should be as complex as it needs to be." READ, the live reference page: reference is "structured according to the structure of the machinery itself", and "the structure of the documentation should mirror the structure of the product." INFERRED: inside reference, at least, the author does want the product's own areas as the organizing axis.

Point 3, getting started and landing pages. READ, the removed page: the basic structure is a home page with one landing page per type, and "a landing page contains an overview of the contents within." A landing page is not a bare list: "The content of a landing page itself should read like an overview." READ: no live page and no removed page names a getting-started page as its own thing. The live tutorials page calls a tutorial "a lesson." INFERRED: in the author's scheme, a getting-started page is a tutorial, the first lesson, not a fifth type.

Point 4, how each type scales. READ, the removed page, section "The problem of lists": lists longer than a few items are hard to read "unless they have an inherent mechanical order", and "Seven items seems to be a comfortable general limit." When a set grows, the fix is "adding another layer of hierarchy", with the example of separate installation options. READ, the live tutorials page: tutorials "are genuinely difficult to do well", and "many products lack good tutorials, or lack tutorials completely." READ, the live how-to page: a problem domain can be "a vastly open-ended sphere of skill", and "practical usability is more helpful than completeness." READ, reference: it should be complete and consistent, and should mirror the product. INFERRED: no page counts anything. The text points to few tutorials (costly, complete end-to-end lessons), open-ended how-to guides, and reference as big as the product.

Point 5, content for advanced readers. READ, the live page on tutorials against how-to guides, section "The basic and the advanced": "How-to guides can, do and often should cover basic procedures", and "a tutorial can present something complex or advanced." The difference is the reader's state, at study or at work, not difficulty. Tutorials are "for learners", even expert ones. INFERRED: the author would not make "advanced" a category of tutorial, nor a sign that a page is a how-to guide. An advanced page is a tutorial if it teaches by doing, and a how-to guide if it serves a competent reader with a goal.

## Adopters: what documentation teams report

Canonical has three layers of evidence. READ, Bill Wear's 2021 MAAS post: the old menu had "organically become like that overgrown to-do list", and the plan was four top-level buckets, with tutorials "probably tiered with detail sections that let you skip the most basic topics." READ, the Ubuntu for developers structure page (updated 2026-07-26): the sidebar's top level is the four type folders plus a Toolchains section. The second dimension, the programming language, lives inside each type. Each language gets a hub page, "a navigation aid, not a content page", created "when a toolchain has ≥3 articles across the docs set". A named sub-group inside a type forms "only when a toolchain has ≥2 advanced articles in that quadrant." Depth is capped: "≤3 levels (quadrant → sub-group → article)." Advanced tutorials sit under `tutorials/`, flat or in sub-groups. The home page uses a different axis from the sidebar on purpose: "These two views are intentionally different and serve different reader needs." READ, Canonical's AI-resources prompts (the `canonical/AI-resources-for-docs` repository, created 2026-01-13): every type in the left navigation has an `index.md` landing page; groups on it follow "product concepts and lifecycle", never alphabetical order; each group is heading, then one to three sentences, then links. For tutorials: "Ideally, there must be just one tutorial", the mandatory one for a new user goes first, and optional ones follow. How-to groups follow product lifecycle stages; explanation may split "foundational vs. advanced". The home page prompt says its main section is "organized by subject, not by Diataxis type", rows "Cross Diataxis boundaries", and "The label "Tutorial" or "How-to" is never an appropriate row label." INFERRED: these prompts encode the team's standard, but they are tooling text, not a published style guide.

Cloudflare. READ: its content strategy names fourteen content types and does not mention Diátaxis. Get started and Tutorial are separate types: get started is "the shortest path from nothing to a first working result", a tutorial teaches by building a real project. "Every new product needs an overview and a get-started page." READ, its information architecture page: "Every product's documentation is built from the same core set of sections", in a fixed order: Overview, Get started, Concepts, Features, Guides, Tutorials, Examples, Configuration, Reference, API, and more. The Overview sits at the product root. INFERRED: Cloudflare puts the product first and the content type second, the reverse of Canonical's sidebar. It is a multi-product estate where each product is a site of its own.

GitLab. READ: four topic types, concept, task, reference and troubleshooting, apply to topics within a page, and a page "usually starts with a concept and then includes a task or reference topic." Pages that are only links are discouraged except "top-level pages that aid with navigation." READ, its global navigation guide: "At the highest level, our global nav is workflow-based", and the levels below are feature names. Each Use GitLab category holds a top-level page, a Get started page and feature pages, a "repeatable pattern". INFERRED: GitLab is the clearest case of types used for writing and not for navigation at all.

Python. READ, the devguide: "Python's documentation strives to follow the Diátaxis framework", which it reads as adapting the writing style to the type. "There is no section dedicated to explanations but these can be found throughout Python's documentation." READ, the 2022 adoption thread: Petr Viktorin wrote that adopting it "doesn't mean we need to restructure the existing docs now" and "we don't need exactly four top-level categories"; Guido van Rossum floated restructuring only the top-level table of contents; others warned that people "spend a lot of time discussing what fits into each category." INFERRED: Python adopted the types as a writing discipline and left its navigation as it was.

NumPy, NEP 44. READ: the accepted 2020 proposal reorganizes the user docs into the four types, with an absolute beginners tutorial first, then a main tutorials section, how-tos, the reference guide, explanations, the F2Py guide and a glossary; contributor and meta material sit outside the four. It notes "NumPy does not have many how-to's", asks for tutorials "addressing different levels of experience", and moves explanation out of the reference. It says almost nothing about navigation or landing pages. INFERRED: NumPy treats level as a property of tutorials, and audience (user against contributor) as the axis above the four types.

Gatsby. READ, its contribution guide: the structure "is based on the Diátaxis documentation system", with Tutorials, How-To Guides, Reference Guides and Conceptual Guides, and one tutorial, "a self-contained introduction", beside a separate Quick Start. READ, Megan Sullivan's account: the four types are listed "in the navigation menu at the top of the page and in the sidebar", and the docs home page tells readers what each type is for. The example URLs show topic folders inside each type. EXECUTED: the Gatsby announcement post returned 404, so I skipped it.

Sequin. READ, Anthony Accomazzo's 2024 account: after the change the sidebar is Get Started, Sink Setup Guides, How-to Guides, Reference, Sink Reference, Database Setup Guides, Webhook Destinations and Management API. Tutorials became "Quickstarts" under Get Started, one per sink, about three minutes each. "We actually have very little in the way of explanation now." He also wrote that "Diátaxis doesn't do a good job of describing itself", and that the product changed at the same time, so the gain is not Diátaxis's alone. INFERRED: a small product that adopted the types still named its top-level sections by product area and type together, and let one type, explanation, nearly vanish.

## Critics: where they argue Diátaxis stops helping

Hillel Wayne, 2023. READ: the model "was designed for documenting tools" and "doesn't fully address the needs of frameworks and programming languages." It is oriented to random access while languages are taught "in a sequence-of-lessons". He would add conceptual overviews before the tutorial, for readers "getting ready to learn the subject", and snippets. He objects that "People use the model even when it's not the right choice." INFERRED: this bears on point 3; a reader's first page may be an overview, which the four types do not name.

Tom Johnson's I'd Rather Be Writing, 2023. READ: the author was "concerned about the separation of content into distinct groups", found the model "overly opinionated and arbitrary as an information model", and notes it has no extensibility for new types. He reports that separating concepts out of API overviews "turned out to be a good move." He relays from a Slack channel that Procida said Diátaxis "isn't meant to impose four rigid buckets." INFERRED: that last line is the author's view as relayed by a third party, not his writing.

Spectrum OS, 2022. READ: the maintainer wrote "we weren't applying it very well." A contributor argued documentation should first be split "into user documentation and developer documentation", that "when there are more and more pages and people, the documentation will turn into a mixture", and proposed a structure by the developer's steps: installation, configuration, development, sending a patch. The maintainer agreed. INFERRED: a small project chose audience and journey over type as its top level, the second tree the removed Diátaxis page drew.

A friendlier field guide makes the same boundary from the other side. READ, Steve Arrants: Diátaxis is "a strong default, not a mandate that every documentation set must have exactly four folders", and it "says nothing about how tightly to write each page." He also argues navigation that "groups content by product feature rather than by content type" makes readers struggle. INFERRED: practitioners disagree on point 1 itself; Arrants wants type on top, Spectrum and GitLab do not.

## The pattern

INFERRED, from the evidence above. First, the author separates the framework from the navigation. The four types are a discipline for writing and placing each page. A four-way top level is the common result, not a rule. His only structural rules for scale are a landing page that reads as an overview, about seven items to a list, and another layer when a list grows. That guidance now lives only in the repository history.

Second, every large adopter handles the second dimension by giving it its own surface. Canonical puts the four types in the sidebar and the product's subjects on the home page, on purpose. Cloudflare and GitLab put the product or workflow on top and the types inside. Nobody repeats the full four-by-subject grid at the top level. The subject axis appears either inside each type (Canonical, Gatsby) or above it (Cloudflare, GitLab, Spectrum).

Third, the types scale differently, and the sources agree on the direction. Tutorials stay few: one marked first lesson, then optional ones (Canonical, Gatsby, Sequin's quickstarts, NumPy's beginners tutorial). How-to guides grow without bound and are grouped by product lifecycle or subject. Reference grows with the product and mirrors its structure. Explanation is often the smallest set, and two adopters (Python, Sequin) report having little or none.

Fourth, "advanced" is not a type and not a tutorial group in the author's view. Advanced material is a how-to guide if it serves someone at work, a tutorial if it teaches by doing, and an explanation if it deepens understanding. Canonical does keep advanced tutorials, grouped under the tutorials section per subject once there are two, and allows explanation to split into foundational and advanced.

## What the vfs site should do

The horizontal bar and the sidebar. INFERRED. The top bar should hold the four types as sections, in reader words, plus the site's front door: Home (the overview and getting started), Tutorials, How-to guides, Reference, Explanation. History and community sit outside the four, on the home page or in the footer, not in the bar. The reason: vfs is one product, not an estate of products, so the Cloudflare and GitLab case of product-first does not apply. The four types give a short, stable bar that will not grow as domains are added; Canonical's sidebar, Gatsby's top bar and NumPy's user docs stand on this. The sidebar should be scoped to the chosen type and grouped by the product's domains inside it: the file system and its calls, the command line, storage and databases, search, permissions and governance, AI agents and MCP, mounts, operations. This is the author's "reference mirrors the product" rule applied to reference, and Canonical's "groups by product concepts and lifecycle" rule applied to how-to guides and explanation. The home page should then carry the other axis: a short overview, the first tutorial, and a map of rows by domain where each row links across all four types; Canonical's home page rule ("organized by subject, not by Diataxis type") is the evidence. Every type's landing page reads as an overview with a sentence or three per group, not a bare list, which is the author's rule and Canonical's.

Tutorials now, at five. INFERRED. Keep one ordered list, numbered, with the first tutorial marked as the start. Five is under the author's seven-item limit, so no grouping is needed yet. Each tutorial should state the one it builds on. The evidence: the seven-item limit in the removed page, and Canonical's rule that the mandatory first tutorial comes first and optional ones follow.

Tutorials later, at thirty. INFERRED. Group by domain, not by level, and keep a short numbered starting path above the groups. Before adding the thirtieth, test each page against the author's line between study and work: a page that serves a competent reader with a goal is a how-to guide, however advanced, and belongs in How-to guides under its domain. Most growth should land there, because how-to guides are the open-ended type and tutorials the costly one. What remains in Tutorials is a starting path of one to three lessons, then domain groups of no more than about seven each, one layer deep, so depth stays at three (type, domain, page) as Canonical caps it. A group forms when a domain has two or more tutorials, which is Canonical's threshold for an advanced sub-group. Level, where it matters, is the order inside a group, not the name of a group. The reasons: the author says level does not separate tutorials from how-to guides; grouping by domain matches the sidebar's grouping in every other type, so a reader finds the same domains in the same place; and a level split such as "advanced topics" mixes domains and becomes an unordered list past seven, which the author's list rule warns against.

The one-line version: put the four types in the top bar, the domains in the sidebar under each type and on the home page, keep tutorials to one marked path, and send advanced material to how-to guides by domain rather than to an "advanced tutorials" group.

## What this study could not settle

Why the "complex hierarchies" page was removed on 2026-08-03 is not stated anywhere I found. A reader can settle it by reading the framework's news page and its issue tracker for that date, or by asking the author. If he withdrew the argument, the recommendation above loses its seven-item rule and its landing-page rule as author guidance, though Canonical's prompts carry the same rules. I did not read the full Gatsby announcement, which returned 404; the Internet Archive copy would settle how Gatsby placed the four types in its top bar. No source counts how many tutorials a site of a hundred pages should hold; counting the tutorials on a dozen mature Diátaxis sites would turn "few" into a number. The Canonical prompts are tooling text, created in 2026; a reading of Canonical's published starter-pack guidance would show whether they match the team's documented standard.
