# The brief: how documentation sites that follow Diátaxis lay out their navigation, and how they group tutorials as the set grows, so the vfs docs site can choose a horizontal bar, a sidebar and a tutorial order that will still hold at a hundred pages

Clay asked on 2026-11-12, after the new docs site was first built from `documentation/` with a left sidebar only and themed from the Pluto Systems design system: "Can you have some opus agents study prior art of how other docs sites that use diataxis layout the page? I probably want to have some horizontal nav buttons along with the vertial ones on the left, but so we grow more and more docs, will we want to organize tutorials by just starting out and advanced topics, or group files by domain?" Four researchers, fresh Opus agents with no knowledge of the author's reasoning, each received the brief below verbatim with their own question appended. The box is 30 minutes each. No reference clone is studied: every site is read through its public pages and the public source of its navigation, so this folder has no refresh log and no licence log. The memo this folder stands on is [how Diátaxis docs sites lay out navigation and group tutorials](../../2026-11-12-how-diataxis-docs-sites-lay-out-navigation-and-group-tutorials.md).

## The brief every researcher received

You are researching for the repository at `/Users/claygendron/Git/Repos/vfs`. vfs is a Python library, a virtual file system that gives AI agents governed access to an organization's data and tools. A developer installs it with pip, creates a file system in a few lines of Python, and hands an AI agent one command-line tool (`ls`, `cat`, `grep` and a few others) to work in it. Its readers are developers: people building AI agents, and enterprise teams deciding whether to adopt it.

The documentation is being rewritten from nothing under the Diátaxis framework (tutorials, how-to guides, reference, explanation). It is a static site built with Material for MkDocs 9.7.1. Today it has eight pages and one navigation surface, a left sidebar: Introduction, Overview, a Tutorials group of five (Build Your First File System, Use the CLI, Keep Your Files in a Database, Give an AI Agent the File System, Control Who Can Access Files), and History. The right side holds the table of contents of the current page. There is no horizontal navigation yet: the top bar holds the wordmark, search and a GitHub link. How-to guides, reference and explanation are not written yet. The product's domains, the areas a reader would recognise, are roughly: the file system and its calls, the command line, storage and databases, search, permissions and governance, AI agents and tool calling (including MCP), mounts for custom backends, and operations. The site will plausibly grow to a hundred pages or more.

The owner's two questions are these. First, the page layout: he expects to add horizontal navigation buttons in the top bar alongside the vertical list on the left, and wants to know what mature documentation sites put in each, and how the two relate. Second, growth: as tutorials multiply, should they be ordered by level (just starting out, then advanced topics) or grouped by domain, and what do sites that follow Diátaxis do in practice.

Your deliverable is one study that answers your own question below from evidence. For every site you study, report: what the horizontal bar holds and on what axis it splits the content (content type, product area, audience, version, something else); what the sidebar holds and whether it changes with the horizontal choice; where each of the four Diátaxis types lives and what the site calls it; how many pages each type holds, counted or estimated and said which; how the tutorials are grouped and ordered; what the landing page of the site and of each section does; and one thing the site does that looks like a mistake. Give a compact table across your sites, then the pattern you see. End with what the vfs site should do, in two parts: what the horizontal bar and the sidebar should each hold, and how tutorials should be grouped now at five and later at thirty, with the reason for each and the evidence it stands on.

## The four questions

Researcher 01, sites that name Diátaxis and put its types in the navigation. Study the sites that say they follow Diátaxis and see how literally they put the four types on the page: the Diátaxis site itself (diataxis.fr, both its own navigation and what it says a site should look like); Django (docs.djangoproject.com, the origin of the four-part split: first steps and tutorial, topic guides, reference, how-to); Canonical's product docs, which mandate Diátaxis (Ubuntu Server, Juju, LXD and MAAS under documentation.ubuntu.com or their own domains, and the Canonical Sphinx starter pack's default layout); pytest (docs.pytest.org); NumPy (numpy.org/doc, and NEP 44 which restructured it); LangChain and LangGraph (their docs as they stand today, which have moved more than once); Cloudflare Workers (developers.cloudflare.com/workers); Wagtail; and two more adopters you find by search that are Python libraries of about vfs's size. For each: are the four types top-level, are they horizontal or vertical, are they named with the Diátaxis words or renamed (and to what), what sits outside the four (getting started, release notes, community, API), and what a multi-component product does (type first then component, or component first then type). Write to `01-sites-that-put-the-four-types-in-the-navigation.md`, saved outlines under `experiments/01-sites-that-put-the-four-types-in-the-navigation/`.

Researcher 02, horizontal navigation beside a sidebar. Study how sites combine a top bar of sections with a left sidebar, whether or not they name Diátaxis. First the sites built on the same tool as vfs, Material for MkDocs with its `navigation.tabs` feature: FastAPI, Pydantic, uv and Ruff (docs.astral.sh), Polars, Textual, and Material for MkDocs's own documentation; read each `mkdocs.yml` for the exact top-level entries and what nests under each, and read Material's documentation for what `navigation.tabs`, `navigation.tabs.sticky`, `navigation.sections`, `navigation.indexes`, `navigation.path` and `navigation.prune` each do and how they combine. Then sites on other tools: Docker (docs.docker.com: Get started, Guides, Manuals, Reference), React (react.dev: Learn and Reference), Next.js, Svelte, Vue, Tailwind, Stripe, Supabase, Vercel, Kubernetes, HashiCorp Developer, and one site built with Mintlify and one with Astro Starlight. For each: how many top-bar entries, the axis they split on, whether the sidebar is scoped to the chosen entry, whether each entry has a landing page, what happens to the bar on a phone, and where search, version and the repository link sit. Say what the common count of top-bar entries is and what the outliers cost. Write to `02-horizontal-navigation-beside-a-sidebar.md`, saved outlines under `experiments/02-horizontal-navigation-beside-a-sidebar/`.

Researcher 03, how tutorial sets are grouped as they grow. Study sites with many tutorials and report how each groups and orders them, with a count: Django (the numbered first tutorial and the advanced tutorials), FastAPI (Tutorial - User Guide and Advanced User Guide), Svelte's interactive tutorial (its basic and advanced parts for each of two products), React's Learn section, Vue, Kubernetes (Tutorials against Tasks and Concepts), PyTorch tutorials, TensorFlow tutorials, Hugging Face's courses and task guides, LangChain and LangGraph tutorials, HashiCorp Developer tutorials (collections by product and use case), SQLAlchemy's unified tutorial, pandas (getting started tutorials against the user guide), scikit-learn, Supabase's quickstarts by framework, Stripe's quickstarts, and Canonical's Juju and LXD tutorials. For each: the grouping axis (level, domain or feature, use case, framework, a single linear path), the labels used for level if any, the number of tutorials, whether a first path is marked for a newcomer, whether prerequisites are stated between tutorials, and whether the pages called tutorials are tutorials in the Diátaxis sense (a lesson for a beginner, learning by doing) or how-to guides under another name. Find the size at which sites change from one ordered list to groups, and say what the groups become. Report what Diátaxis's own pages say about advanced tutorials. Write to `03-how-tutorial-sets-are-grouped-as-they-grow.md`, saved outlines under `experiments/03-how-tutorial-sets-are-grouped-as-they-grow/`.

Researcher 04, what Diátaxis guidance and documentation teams say about structure at scale. Read the guidance, not the sites: every page of diataxis.fr that bears on structure (the pages on complex hierarchies, on how to use Diátaxis, on the map and the compass, on tutorials against how-to guides, and on the difference between a framework for content and a scheme for navigation); Canonical's public documentation practice and what it says about landing pages and navigation; Cloudflare's documentation content strategy and its content types; GitLab's topic types (concept, task, reference, troubleshooting); the Python developer guide's adoption of Diátaxis; NumPy's NEP 44; Gatsby's and Sequin's accounts of adopting it; and three practitioner critiques you find by search that argue about where Diátaxis stops helping (for example that it is not a navigation scheme, or that a strict four-way top level hides the product's areas). Report what each says about: whether the four types should be the top level of the navigation; how to handle the second dimension (type against product area, or type against audience); where a getting-started page and a landing page belong; how each of the four types should scale (which stay few and which grow without bound); and what to do with content for advanced readers. Separate what the framework's author says from what adopters report from what critics argue. Write to `04-what-diataxis-guidance-says-about-structure-at-scale.md`, saved outlines under `experiments/04-what-diataxis-guidance-says-about-structure-at-scale/`.
