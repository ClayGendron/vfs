# A Svelte app built from design-system v0.11.0 renders the docs pages and an export of the public API as 35 static pages, highlights code at build time, and fails its build on a dead link or a dead anchor

On 2026-11-14 Clay decided to stop building the docs site with MkDocs and its successor, and gave four requirements: "1. I want to use the design system 2. I want vfs.dev to be a seperate repo not in this one that is private 3. I want to be able to preview the docs page locally in this repo 4. I want to be able to "deploy" the docs from this repo as part of a release or seperate deployment and have them reach production without having to deploy anything else". He confirmed the address `docs.vfs.dev` and that the docs app lives in this repository. The question this memo answers is whether a static Svelte app that installs the Pluto Systems design system can render the pages of `documentation/` and the public API read from the docstrings, with the checks the MkDocs build gave. One researcher, the session's author, ran one probe in about forty minutes, in a scratch folder outside this checkout and outside the design system's. Its scripts and every command's output are under [the studies folder](studies/2026-11-14-a-svelte-app-built-from-the-design-system-renders-the-docs-and-the-api-export-as-static-pages/). There is no intention; the memo serves [the docs site spec](../specifications/active/2026-11-14-the-docs-site-is-a-svelte-app-in-this-repository-built-from-the-design-system.md). Two things were not probed and are named in the last section: a deployment, and the design system's sidebar in a docs layout. This memo commits to nothing; the spec that stands on it decides.

Labels: EXECUTED means a command ran in this probe and the claim reports its output, saved in [results.txt](studies/2026-11-14-a-svelte-app-built-from-the-design-system-renders-the-docs-and-the-api-export-as-static-pages/experiments/results.txt). READ means read in a file cited by path. INFERRED means this memo's reasoning from the two.

## Sources

The vfs working tree over `7edd8901` on `main`: `documentation/`, `src/vfs/` and `mkdocs-documentation.yml`. The design system at tag `v0.11.0` in the local checkout `../design-system` (Apache-2.0): `README.md`, `registry.json`, `static/r`, `tests/smoke/fixtures/kit3`, and the items it installed. The installed `@sveltejs/kit` 3.1.0, read at `node_modules/@sveltejs/kit/types/index.d.ts` in the probe's app. The earlier memo of the same day, [where the API reference sits on a Diátaxis site and how its pages are shaped](2026-11-14-where-the-api-reference-sits-on-a-diataxis-site-and-how-its-pages-are-shaped.md).

## 1. The answer in one paragraph

INFERRED from the probe. Yes. A fresh SvelteKit app took six design-system items in one command, read the Markdown under `documentation/` and a JSON export of the 22 exported names, and built 35 static pages. Code was highlighted during the build by the design system's own highlighter, the dev server served the same pages for local preview, and the build stopped on a link to a missing page and on a link to a missing anchor without any check of ours. The export read the source without importing the package. What the app would still have to write itself is small and named: a Markdown-to-component renderer, the docs layout, and the list of pages.

## 2. The design system installs into a fresh app in one command (EXECUTED, READ)

EXECUTED: the design system's own minimal test app, SvelteKit 3.1.0 with Svelte 5.57.3, Vite 8.3.5, Tailwind 4.3.3 and the static adapter, was copied to a scratch folder, and one `shadcn-svelte@1.7.1 add` of `sidebar`, `code-block`, `table`, `alert`, `breadcrumb` and `theme` against the registry at `v0.11.0` exited 0. It landed 97 files under `src/lib`, added ten packages, among them Shiki, bits-ui and the three font packages, and wrote the theme's tokens into the app's stylesheet. READ in the design system's `README.md`: an app installs an item pinned to a release tag and owns the source it receives. READ in `registry.json`: of 75 items the registry has `app-shell`, `sidebar`, `breadcrumb`, `code-block`, `table`, `tabs`, `alert`, `collapsible`, `marketing-bar` and `marketing-footer`, and has no item for long-form prose, for an "on this page" list, for a docs page layout or for search.

## 3. The public API exports from the source to one JSON file (EXECUTED)

EXECUTED: a trial script of about 130 lines loaded `vfs` with Griffe from `src/` and wrote the 22 names of `vfs.__all__` with their kind, signature, docstring and public members in source order: 298 members and 125,489 bytes. The member counts match the pages mkdocstrings built earlier the same day: 39 for `AsyncVirtualFileSystem`, 22 for `Entry`, 33 for `Result`, 9 for `MountInfo`, 1 for `MountError`. Twenty-one names are classes and one, `permissions`, is a module. The script turned each `:term:` marker into a link to the glossary and found no unknown term. It counted 125 public functions and methods with no docstring. INFERRED: Griffe is the part of the earlier toolchain worth keeping. It is a library separate from MkDocs, it never imports the package, so no build of the Rust extension is needed, and it sits behind one script.

## 4. Markdown renders through design-system components, and code is highlighted during the build (EXECUTED, READ)

EXECUTED: the app parsed each page with the `marked` lexer into tokens and rendered a token through a component: a fenced block through `CodeBlock`, a table through `Table`, a heading with an anchor made from its text. `bunx --bun vite build` exited 0 and wrote 35 HTML files: 12 documentation pages, 22 API pages and an index. The tutorial page's HTML carries the highlighter's token classes, and the page for `AsyncVirtualFileSystem` is 187,351 bytes with 39 member headings. Each built page names 11 script files of about 155 KB in all; the build also holds about 2.7 MB of script in 56 files, most of it Shiki grammars in chunks no built page names. READ in the installed `highlighter.ts`: its `highlightCode` is "the one-shot form for a server `load`, so a prerendered page ships no Shiki", and `CodeBlock.Content` takes the pre-highlighted lines. EXECUTED: the pages of `documentation/` use fenced code in three languages (89 blocks), tables, two images and nothing else of Markdown's extensions; the only raw HTML is four lines of the landing page. INFERRED: the renderer the app needs covers a short list of token kinds, and the landing page is better written as a Svelte page than as Markdown that wraps HTML.

## 5. The build stops on a dead link and on a dead anchor with no check of ours (EXECUTED, READ)

EXECUTED: against a copy of `documentation/` with one link to a page that does not exist, the build failed with `Failed to prerender /no-such-page` and exit 1. Against a copy with one link to `reference/glossary.md#no-such-term`, it failed with a message naming the missing id and the page that links to it, and exit 1. READ in the installed framework's types: `handleHttpError` and `handleMissingId` both default to `"fail"`. EXECUTED: the unchanged pages built, so every existing link resolved, among them the glossary's links to API pages and the links the export wrote from docstring markers to glossary terms. INFERRED: a glossary anchor that the export computes and the site does not have is caught by the same build check, so the two sides cannot disagree about an anchor silently.

## 6. The same app previews locally (EXECUTED)

EXECUTED: `vite dev` on a loopback port answered 200 for a glossary page, an API page and a tutorial. INFERRED: local preview is the export followed by the dev server, both run from this repository, with nothing else deployed or checked out.

## What this memo does not settle

A deployment was not made: no host credential was used, and `wrangler` is not installed on the machine; the experiment is one deployment of the probe's `build/` folder as a static-assets Worker under a throwaway name, by someone who holds the account. The design system's `sidebar` was installed and not laid out as a docs navigation with a phone drawer; the experiment is to build the left navigation from it and view it at phone and desktop widths. How the pages look was not viewed in a browser, only read as HTML; the experiment is the same viewing. Whether `marked` is the right parser against the alternatives was not compared; the experiment is to run the 13 pages through two parsers and diff the token kinds. The probe's page weight includes the data SvelteKit repeats for the browser; the experiment is to build once with client rendering off for documentation pages and compare the bytes.

## One line

The design system installs into a static Svelte app that builds every docs page and every exported name from this repository alone, with code highlighted at build time and dead links refused by the framework.
