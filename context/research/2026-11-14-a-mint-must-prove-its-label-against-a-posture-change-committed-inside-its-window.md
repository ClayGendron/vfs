## The question

To be settled: which mechanism makes every row a mint stamps carry, once no relabel mark stands over it, the label the standing posture rows give it, on all five profiles and for the system actor too, at a constant number of statements per mint attempt, with no writer waiting on another writer and no new lock cycle; and what that mechanism costs per file write and through a 10,000-file batch at the reference deployment.

## What is known today

- A label is a copy. Each entry row stores `everyone_level`, the rank of the deepest everyone posture on its path, derived from the posture rows and never authoritative (READ, `labels.py:1-41`). A write, a mkdir and the parents a write creates take it from `labels_for`, one plain read of the posture rows on the batch's ancestor prefixes, at `writes.py:412`, the first statement of `_apply`, before the inserts at `:413` and the guarded parent bumps at `:444`. A copy and a move take it from `posture_beneath` (`labels.py:167-180`), read at the gate for a partial caller (`authorized.py:185`, held at `:186`) or at `topology.py:207` otherwise, and stamp it at `:334`, `:405` and `:502`.
- A posture write bumps the mount revision as its first statement (`backend.py:1317`), stamps the everyone principal `*` (`rights.py:1099`), writes the posture row and plants a relabel mark (`:1100-1101`). The relabel then runs one chunk per transaction, each under the admin lock (`labels.py:276`), reads the posture rows under that lock (`:298-310`), rewrites the labels of the rows its statements find, and clears the mark with a revision bump on the last chunk (`:293-294`); `_settled` drives it to the end in the posture call (`backend.py:1326-1353`). READ.
- Once no mark stands, a reader trusts the stored label: `Rights.admits` passes a row whose label reaches the rung unless the path lies in a hole, and holes come only from marks in flight (READ, `grants.py:485-498`, `labels.py:24-31`).
- Nothing orders the mint's label read against the posture write. The mint takes no lock the posture write or the relabel takes; the relabel's statements do not find a row an uncommitted mint has inserted, or a row a move has rewritten to a path its statements range over (INFERRED from each engine's documented visibility of uncommitted rows). So a mint whose posture read precedes the posture commit, and whose commit follows the mark's clearing, leaves a stored label no relabel will rewrite (INFERRED).
- Confirmed on 2026-11-14 by the session lead (EXECUTED, lane `6644c60f`, the node above, 24 legs: three shapes, two minters, four engines). Postgres and MariaDB fail `at-path` and `at-minted-parent` for both the system actor and a caller granted `read_write`: the minted rows hold label 5 where the standing posture gives 0, with no mark standing (`{'/p/new.txt': 5} != {'/p/new.txt': 0}`; `{'/p/n': 5, '/p/n/new.txt': 5}`). `at-existing-parent` passes there, because the relabel rewrote the parent and the write's guarded parent bump met the snapshot conflict and redrove. SQL Server and Oracle pass all six.
- Why the commit-point fence does not close it on Postgres and MariaDB: writes there run at `REPEATABLE READ` (READ, `dialects.py:512`, `:582`), so the fence's read of the stamps (`authorized.py:228-244`) comes from the snapshot that read the stale posture and agrees with it by construction. The system actor is never fenced (READ, `authorized.py:140`).
- Why the SQL Server and Oracle passes are partial. The node's rival commits at `write:before-apply` (`writes.py:364`), before the label read, so on an engine whose statements each read the latest commit the label read already sees the tightened posture (READ, `writes.py:364`, `:412`). For the granted caller the fence also sees `*` stamped and redrives (READ, `authorized.py:243`). No seam sits between the label read and the insert, so the system actor's window there was never entered; with one, a failure in every shape is predicted on those engines, since under `READ COMMITTED` the guarded parent bump still matches after the parent's label was rewritten (INFERRED, the test's author). A granted caller there keeps a narrower window: a posture committed after the fence's read and relabelled before the mint's commit (INFERRED).
- The transfer path stamps from a posture read taken at `READ COMMITTED` on every engine (READ, `dialects.py:513`, `:585`, `topology.py:207`), and the same ordering gap holds there (INFERRED; the audit's trace names it). Restore keeps the stored label and writes no `everyone_level` (READ, `trash.py:511-549`), and the relabel reaches tombstoned rows (READ, `labels.py:35-37`). `rebuild_labels` has no caller in `src/` (READ, a search of `src/`); a later posture write at the same path relabels its region from the posture rows and would repair it (INFERRED from `labels.py:298-310`).
- The reverse direction is the same gap: a mint across a posture loosening keeps the closed label it read, and the row stays hidden from callers the standing posture admits until a repair (INFERRED).
- The scale every candidate is filtered through: about 1,050,000 file writes a day, about 50 a second through the nightly batch, 100 batches of 10,000 files a night; one statement landing on one hot row is a serialization point at about 30 updates a second by day and 50 through the batch (READ, `AGENTS.md`, the reference deployment).
- Lock orders that stand today (READ). An admin write: the mount revision row first (`backend.py:1317`), then the `*` stamp row for a posture (`rights.py:1099`), then the grant row and the mark. A relabel chunk: the mount revision row (`labels.py:276`), then the marks, then entry rows. A topology verb: its serialize lock row first (`topology.py:148`), then entry rows. A write: entry rows in path order (`writes.py:407-409`), parent bumps last. The fence takes no lock (`authorized.py:233`).

## The candidate directions

Each is a direction to build and measure, not a choice. What each would cost and risk is INFERRED from the code read above and from the commit-point spec's rejected alternatives.

1. A locking or current read at the end of the mint's transaction. The mount revision read under a shared lock, `FOR SHARE` or the engine's form, after the last stamp. On a snapshot engine it raises the serialization error when an admin write committed after the snapshot, which redrives. Risks: the mount revision row is bumped by every admin write and held by every relabel chunk (`labels.py:276`), so every mint in flight redrives across any grant anywhere and waits behind each chunk; taken last, it inverts the relabel's order (admin row first, entry rows after), the cycle the index-publish fix removed; Oracle's compiler renders a shared locking read as `FOR UPDATE`, which would serialize every mint on one row (READ, the commit-point spec, decision 3). A narrower form locks the `*` stamp row instead, which only posture writes update (`rights.py:1099`), held from before the label read to commit: it leaves grants and relabel chunks out, and on the read-committed engines the label read follows the lock. Its own risks: Postgres locks no row that does not exist, so a store whose first posture write has not run needs the row seeded; Oracle needs a table-level share lock or another form; many concurrent sharers on one Postgres row create a multixact per locker and dirty the row's page each time.
2. Re-reading the posture rows for the minted paths with a statement that sees the latest commit, then restamping or redriving when they differ. Risks: on Postgres and MariaDB at `REPEATABLE READ` no plain statement in the transaction sees past the snapshot, and a locking read does not see a newly inserted posture row, a phantom; a re-read on a second connection sees the posture but leaves the ordering gap open between the re-read and the commit, because the relabel may still pass before the mint commits.
3. The admin side covering mints that began before its commit: the posture write, or the relabel's last chunk, waits out every writer that could hold an older posture read, or the mark outlives the pass until they finish. Risks: no engine-portable way to know which transactions are older is known here; the engine-specific forms (Postgres transaction-id horizons, SQL Server and Oracle session views) differ per engine and need privileges a host app may not grant; a mark that stands longer keys every reader's compile while it stands.
4. Readers not trusting a label that could be stale: each row records the revision its label was read under, and a reader judges from the posture rows any row stamped under a revision older than the newest posture change over it. Risks: it moves the cost from about a million writes a day to about 150,000 verb calls a day, each a read whose cost must follow what it returns; it widens the row and the `(everyone_level, path)` index the partial caller's read seeks; it changes `Rights.admits`, the one authority.

## The experiment that answers it

Make a scratch copy of the tree with `git archive`, never in the repository. Add two seams there: one between `labels_for` and the insert in `_apply` (`writes.py:412-413`), and one between the destination posture read and the stamp in the transfer path (`topology.py:207-208`). Extend the node above with the transfer shapes (a move and a copy into a folder tightened at the seam), the loosening shape, and both minters at both the existing seam and the new one. Run it on the unfixed copy on the four server legs and record per engine and per node which windows are open. Then build each candidate above on its own copy and run the same nodes. For each candidate, count, never time: the attempts per call (redrives) across a rival posture write per seam; statements per call by a `before_cursor_execute` listener for one new file by the system actor and by a named caller, and for a 10,000-file batch with parents; whether a sharer blocks another sharer and whether a posture write blocks behind a sharer, proven per engine with the engine's no-wait form of each lock; deadlocks and retryable conflicts across 16 concurrent writers of 50 files each with one posture write and its relabel chunks and one purge running beside them; and on Postgres the multixacts created over that run. A candidate is admitted only if it closes every window on all five profiles for both minters, adds a constant number of statements per attempt, makes no writer wait on another writer, and adds no cycle to the lock orders above; the completed memo states the measured counts and the spec takes its cost bound from them.

## One line

A write, mkdir, copy or move can stamp a label from a posture read that a concurrent posture change has already replaced, confirmed on Postgres and MariaDB; which of four mechanisms proves the label at a bounded cost waits on a three-hour run of the four server legs.
