## The question

Which permissions, and no more, must an API token carry so that a workflow in a public repository can deploy one static-assets Worker and keep its custom domain attached, and which setting of that Worker serves `404.html` for an address that matches no file?

## What is known today

READ in the design system at tag `v0.11.0`, `wrangler.jsonc`: an assets-only Worker is configured by three settings, a name, a compatibility date and an assets directory, and its README says nothing is deployed from it. READ in [the docs app memo](2026-11-14-a-svelte-app-built-from-the-design-system-renders-the-docs-and-the-api-export-as-static-pages.md), last section: no deployment was made in the probe, no host credential was used, and `wrangler` is not installed on the machine that ran it. READ in the review's finding H3: this repository's `publish.yml` runs its publishing job in a protected environment named `pypi`, which is the pattern a deploy job here can follow. READ, the owner on 2026-11-14: "I am actively moving the vfs.dev domain to cloudflare". INFERRED: a custom domain joins a hostname of a zone to a Worker, so the token must be able to write the Worker's script and assets in the account and to act on the one zone; which named permissions those are is the host's to say and a deployment's to prove. INFERRED: a token made from a broad template would also be able to change other Workers and other zones of the account, which is what the review's premortem warns of.

## The experiment that answers it

The account's holder builds the docs with `scripts/docs.sh build`, or uses the probe's built folder. They write a Worker configuration with a throwaway name and a throwaway hostname of the zone, and create a token limited to that account and that zone with the permissions the host's own documentation lists for deploying a Worker and for a custom domain. They deploy with the host's command-line tool at a recorded version. If it succeeds, they remove one permission at a time and deploy again, until removing any one more makes the deployment fail. They record: the tool and its version, the configuration file as deployed, the final list of permission names with the scope of each, the message of each failed deployment, and what the hostname answers for `/`, for one page and for an address that matches nothing, under each not-found setting the host offers. They then delete the Worker, the hostname and the token. The answer is the final list and the setting, and the deployment spec is completed from them.
