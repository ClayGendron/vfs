## The question

The line law says how a text becomes lines: it breaks on `\n` only and drops the final terminator. It is declared in the pattern layer, as grep's law. The result layer, which the layer-map spec declares beneath the pattern layer, imports it to render and to pick previews. Where does the line law belong, so that every part of the package that needs it imports it downward and spells it once?

## What is known today

1. READ, vfs at `4a6d3e0`. `split_lines(text)` is defined in `src/vfs/pattern_matching/grep.py` under the banner "The line law", and `vfs.pattern_matching` exports it. Its docstring gives the reason for the law: `str.splitlines` also breaks on the vertical tab, the form feed, the file, group and record separators, U+0085, U+2028 and U+2029, which grep and ripgrep keep in a line, so using it would skew matches and line numbers against those tools.
2. EXECUTED on 2026-11-12, the same commit. Outside the pattern layer, three modules import `split_lines` at runtime: `src/vfs/results/preview.py`, `src/vfs/results/render.py` and `src/vfs/storage/backends/database/search.py`. The first two are the only imports of the pattern layer by the result layer. The pattern layer imports nothing from the result layer, at runtime or for types.
3. EXECUTED, the same run. Under the ladder as the spec declares it, with `vfs.results` on the rung beneath `vfs.pattern_matching`, the two imports point up. With those two rungs exchanged they point down and nothing else changes: the ladder is left with its other two exceptions. So a redraw alone would remove both entries. The spec did not redraw, because the order it declares is the one the project stated when it commissioned [the research on import direction](2026-11-07-import-direction-and-module-size-fitness-functions.md): the result envelope at the bottom, the pattern layer above it.
4. READ and EXECUTED. The law has a second spelling. `src/vfs/storage/replace.py` holds `_split_dropping_trailing_blank(text)`, which splits on `\n` and drops the empty line a trailing newline leaves, and calls it twice in the edit matcher. On eleven sample strings (empty; with and without a final newline; with two final newlines; with `\r\n`; with a form feed, U+2028 and U+0085) it returns what `split_lines` returns. On four of the eleven both differ from `str.splitlines`. READ: the same module and `results/render.py` each also split on `"\n"` directly once, and `results/render.py` and `rendering/markdown.py` each call `str.splitlines` once, which is a different law.
5. READ. The Rust engine states the same law for its line counter: `crates/vfs-core/src/verify.rs` says it splits on `\n` only with no phantom line after a trailing terminator. `tests/pattern_matching/test_grep.py` pins the Python law, `tests/results/test_preview.py` counts calls to `split_lines` through a spy on the preview module's own name, and the matcher's reference implementation in `tests/support/oracles/matcher.py` imports it from `vfs.pattern_matching.grep`.
6. INFERRED. Three shapes would each end with no import against the ladder, and this memo chooses none. First, the law moves to a leaf module on one of the ladder's low rungs, which grep, the renderers, the search snippet and the edit matcher all import. Second, the ladder is redrawn with the pattern layer beneath the result layer, and the edit matcher's copy stays or imports grep's. Third, the renderers are handed lines and never text, so only the callers above them split.
