# The development process: seven studies, and the shape of each stage's document

This is a research memo; it commits us to nothing. Clay Gendron asked for it on 2026-10-29, it serves [the intention](../intentions/2026-10-29-the-development-process.md), and it feeds [the spec](../specifications/active/2026-10-29-the-development-process.md), drafted from it. The researcher was the orchestrating session (Claude Fable 5.1) with seven study agents, one per stage; the studies had 30 minutes each and the synthesis was not boxed. The question, in Clay's words: "We are going to be dropping ADRs, the process is intent → research → spec → review → code → review → commit. Study the patterns of the wasi-python project and update the workflow and documentation of this repo. Create a sub-agent for each of these phases to learn what format those documents should take. For intent, read about Anthropic's AI SDLC; for reviews, incorporate Cloudflare's security audit skill; for code, research reusable coding patterns this repo should follow." Rulings during the work: no numbers in document file names; the intention has no header lines and is about the experience, not the mechanism; the problem must be properly specified; the code stage is tests first, then code. The method was seven parallel studies under [the studies folder](studies/2026-10-29-the-development-process/00-brief.md), whose `00-brief.md` holds the brief and the file table, each reading wasi-python at `1431ba6f` (Apache-2.0, read-only), vfs's own `context/` and code, and online prior art with URLs and read dates; this memo synthesizes them, resolves the places where two studies chose differently, and names what only Clay can settle. Nothing was copied from any project. Every claim below that repeats a study is labelled with the study's own label; the synthesis is INFERRED. It supersedes nothing; it replaces the four-stage pipeline described in [the process page](../README.md) (research → decide → specify → code) once the spec lands.

Labels: EXECUTED means a command ran and the claim reports its output. READ means read in a file or page cited. INFERRED means reasoning from the two.

## 0. In one paragraph

INFERRED. Every stage produces one dated Markdown file in a known folder, named `YYYY-MM-DD-descriptive-slug.md`, never numbered, linked to earlier documents by relative path. The intention is a page about an experience, with the problem stated as facts. The research memo is a labelled, boxed, append-only answer standing on studies in a folder of the same name. The spec is one file with a fixed header, nine sections in order, a Mermaid diagram, numbered decisions with reasons, counted criteria that each name the test that will pin them, and landing notes. Each spec gets two reviews, both files, both by a reviewer who did not write the change: one before the build with the verdict "Fit to build", one before the landing with the verdict "Lands". The code stage writes the test first and records the red run. The landing is one commit to `main` whose trailers point at the spec and its two reviews. One lint package, `tests/lint/`, holds every shape so `scripts/ci.sh` fails when the process drifts. No new file is written to `context/decisions/`; the folder freezes as history.

## 1. What the seven studies agree on (INFERRED from S1 to S7)

Seven points came back the same from every study that touched them. They need no further decision.

1. **One document per stage, one file each, dated and descriptive.** No number anywhere in a file name. A studies folder's `NN-` prefix is reading order, not identity (S2).
2. **Links point backward, by relative path.** A spec cites its intention and its research; a review cites its spec; landing notes cite both reviews. Nothing is edited to point forward, so the earlier document can freeze (S1, S3, S4, S6).
3. **Every claim is labelled.** EXECUTED, READ or INFERRED, in memos, studies, specs' problem sections and reviews. Synthesis sits apart from evidence (S2, S4, S6).
4. **No open question in a spec or a memo.** What cannot be decided becomes a placeholder research memo naming the experiment and the spec that waits (S2, S3). The only place a question may stand is the intention, as the list of what the research must answer (S1).
5. **A fresh reviewer, two reviews, two words.** The reviewer did not write the change and gets the spec and the diff, never the author's summary. The spec review ends "Fit to build" or "Not yet"; the code review ends "Lands" or "Does not land yet". Findings are High, Medium or Low, each with a failure scenario; a Low carries its fix text and needs no round; the author answers in a Disposition section of the same file and the reviewer signs again (S4, S6).
6. **Tests first, recorded.** The test is written and seen failing before the code. The spec's criteria name the test before it exists. The landing notes carry a "Seen failing first" record per criterion. The tests commit precedes the first code commit. The reviewer reproduces at least one red (S3, S5, S6).
7. **Lint tests hold the shape, in `tests/lint/`, run by `scripts/ci.sh`.** They check names, header lines, sections, labels, resolving links, the absence of open questions, and that a landed spec cites two review files that exist and say the right word. They cannot check judgment, and they say so (S2, S3, S4, S6, S7).

## 2. The intention (S1)

READ (S1). Anthropic's AI-native SDLC playbook puts an `intent.md` before `spec.md`: the problem, the outcome, the affected users, the constraints, the open questions, in the originator's own words, version-controlled, read by plan mode "if one exists". The four user-story templates (Connextra, PR/FAQ, Shape Up, job story) agree on a person, the value wanted and a check that it arrived, and disagree only on how much solution to include; for vfs the right amount is none.

INFERRED. The format, as Clay shaped it today and S1 confirmed: file `context/intentions/YYYY-MM-DD-slug.md`; the title is line one; no header lines; sections in order: **The story** (one Connextra sentence naming the audience), **The problem today** (facts, labelled), **What we intend to achieve** (experiences, no paths, no code), **Part of the story** (optional, one paragraph of means), **What this is not**, **Done when** (numbered, person-verifiable, counts never clocks), and a closing list of **What the research must answer** (numbered, or "None."). That last section is S1's "Open questions" renamed, so the no-open-question lint does not read the intention as a violation and so the words match the rule: the questions are the research's to answer, not the spec's to carry.

When an intention is written: when research will be commissioned, when more than one spec will carry the work, or when an audience gains or loses an experience. Otherwise the work starts at the spec, whose `Intention` line says "none" with the reason. One line: research never starts without an intention; a spec may (S1).

READ (S2). wasi-python's one lint for memos is a floor: at least one label anywhere, or a placeholder status.

INFERRED. Add three header lines from wasi-python: **Researcher** (agent and box), **Intention** (path), **Supersedes** (path or "nothing"). A memo's last section is "What this memo does not settle", each item naming a placeholder or an experiment by path. ## 4. The specification (S3)

EXECUTED (S3). 31 active folders; 23 carry markers, 72 marker lines; only 4 hold a plan or task file beyond the spec, so the three-file shape is honoured mostly in the breach; ten ADRs are still "proposed". The architecture pages use five Mermaid kinds with a `planned` class (dash 6 on 4) and a `retiring` class (dash 2 on 3).

INFERRED. One file, `context/specifications/active/YYYY-MM-DD-slug.md`, moved to `archive/` under the same name on landing. Eight header lines in order: Status, Date, Owner, Kind, Depends on, Intention, Research it stands on, Reviews. Nine sections in order: **The problem** (today's behaviour at a commit, labelled), **Architecture** (one Mermaid block in the pages' dialect, solid for what exists, dashed for what the spec adds, dotted for what it removes, naming the page it will change), **Decisions** (`### N.` headings, each a sentence with its reason; a departure from a frozen record or a landed spec named), **Intent** ("After this spec, …"), **Design** (files, sizes, slices, the commits in order with the tests first), **Scope** (in and out), **Acceptance criteria** (numbered; each names the test node id or conformance row that will pin it, before the test exists; counts never clocks), **Landing notes** (empty until landing; then the seen-failing record per criterion, commits by sha, both reviews by path, the gate's counts, the engine legs, measurements, the disposition of findings, deviations, the changelog line), **One line**.

The Kind line is one primary word (feature, fix, refactor, spike, process, docs) plus flags that trigger gates (structural → the spec review scores structure; changes the public API; changes the schema format; needs the engine legs → `db_test`; touches rights → the security lens is mandatory; touches the engine → `cargo test` and the wheel reinstall; parallel-safe), then the modules touched. The Status line's first word drives the lifecycle: draft, reviewed, building, built, landed, parked, withdrawn.

What flows backward with `decisions/` frozen: a build-time decision is appended to the spec's own Decisions section; a measurement goes to `research/`; the architecture page and glossary are updated. Nothing is ever written to `decisions/` again; a one-paragraph note at the top of `decisions/README.md` says so, and each "proposed" record's pending pins are answered as Decisions in the spec that implements them (S3).

The 31 numbered folders keep their names and are not scanned by the shape lint. A ratchet allowlist of (path, marker count) admits today's 72 markers and may only shrink. A numbered spec picked up to build is converted in place: markers become Decisions or a placeholder memo; it gains Architecture and the Reviews line (S3). `plan.md` and `tasks.md` lose nothing durable: their slices, trade-offs and commit order live in Design and Decisions. `STATUS.md` and `open-questions.md` are frozen with a top note (S3).

## 5. The spec review (S4)

READ (S4). wasi-python reviews a spec before build only when it is structural or touches the guest's imports, the artifact set or the build recipe; vfs's intention reviews every spec. Spec 164's pre-build review was written in a session scratchpad and is gone; only its amendments list survived in the spec. Google starts implementation "once further reviews are unlikely to require major design changes"; Kubernetes has the author answer a scalability questionnaire inside the proposal and a separate team approve it; Klein's premortem asks the reviewer to assume the build failed and name why.

INFERRED. File `context/reviews/YYYY-MM-DD-<spec-slug>-spec-review.md`. Header: Date, Reviewer ("a fresh sub-agent of <session>; not the author"), Reviewed (the spec's path at a commit), Brief (what was given, and that no author summary was), Re-ran, Box (25 or 45 minutes). Sections: the author's questions answered first; Decisions one line each; Acceptance criteria countable as written; the diagram and the scope; scale and the production posture; constitution checks (the five primitives, `CLAUDE.md`'s posture); a three-line premortem; findings most severe first with fix text; "Checked and found clean"; Disposition; Verdict. Ranking: High is a wrong design the build would carry (a constitution breach, an unbounded statement, a choice left to the developer); Medium is a guarantee not evidenced (an uncountable criterion, a missing diagram, an unnamed dependency); Low is a write-in. A changed Decision after "Fit to build" means a new dated review file. The reviewer must not get the author's summary, transcript, reasoning, expected verdict, or write access to the spec or the code (S4).

## 6. The code stage: how we code, tests first (S5)

READ (S5). The live tree already follows 24 named patterns, each cited by `file:line`: gate then act, parse at the boundary and carry the proof in the `Path` type, failures as `Result` rows built by `classified`, one ingress table in `params.py`, capabilities declared not sniffed, `Supports*` protocols as ports with one adapter, profile fields only where SQLAlchemy is silent, bind cost measured not remembered, every membership list chunked by `membership_budget`, plan then execute, one batch one transaction, snapshot reads and guarded writes with redrive, explicit provisioning and first-touch verification, one Rust seam that imports nothing from vfs, oracle-pinned kernels, mirrored test files, one conformance contract with zero per-engine conditionals, count pins, named seams, fixtures that own what they make, named types over bare tuples, banner layout, pure models, a pure result fold. EXECUTED (S5). 68 test files name their mutant and 89 commits name a kill, but 0 of 842 commit messages say "seen failing": the repository has the referee (the mutant) and lacks the record (the red run). `contributing.md` says "do not treat the repo as greenfield" and names `VFSResult` and `DatabaseFileSystem`, zero hits in `src/`; `python-style.md`, `testing.md` and `tooling.md` each contradict `CLAUDE.md` or `scripts/ci.sh` in at least one line.

INFERRED. One page, `context/standards/how-we-code.md`: about thirty-five one-sentence rules in seven groups, test-first at the top, each rule naming the file that shows it, with `CLAUDE.md`'s rules as pointers not copies, closing with "When the rules do not say" and "In one line" (the shape wasi-python's principles page uses). The test-first rule: the test is written and run red before the code, at the layer the behaviour lives (the mirrored file, the conformance row, the oracle parity row, the count pin, the seam test); the commit's test plan and the spec's landing notes name each test and its red shape; the reviewer runs one on the base. Enforcement splits three ways (S5's table): ruff holds imports (`TID252`, `PLC0415`) and flags asserts; `tests/lint/` holds the banner layout, two-line comments, no document names in code, mirrored test files, every `_native` export has an oracle, no elapsed-time asserts, no per-engine conditionals in the contract; the reviewer holds gate-then-act, `Path` below the gate, `Result` not exception, profile-field justification, unbounded statements, plan-then-execute. `contributing.md` is retired; the other three standards are corrected in the same landing.

## 7. The code review (S6)

READ (S6). wasi-python's review file is committed last so its push re-uses the branch's green CI run; the lint reads `reviews/<name>.md` references under "## Landing notes" and fails when none exists. The Cloudflare skill has two modes: guidance (no artifacts, the relevant parts only) and full audit (six phases, a run folder, on explicit request). Its evidence bar needs a trust boundary: a lower-trust principal, an input, the control that should have stopped it, the boundary crossed, a concrete result; severity is given only to a `confirmed` record; `needs_validation` names the missing fact; `rejected` says why. Licence MIT, Cloudflare 2025-2026. The install is `npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit -a claude-code` (Node 22.20 or later), which writes `.claude/skills/security-audit/` beside vfs's seven review skills and a root `skills-lock.json` whose hash is the "unchanged" proof. vfs's `code_review` orchestrator already normalises its five lenses onto one scale with a coverage ledger per lens, which is what lets one file carry them.

INFERRED. File `context/reviews/YYYY-MM-DD-<spec-slug>-code-review.md`. Header: Date, Reviewer, Spec (path, with its spec review), Reviewed (`<base>..<tip>` of local unpushed commits), Re-ran (`scripts/ci.sh` with counts; engine legs when storage changed; probes by node id), Method, Box (30 or 60 minutes). Sections: Scope (the commits); acceptance criteria against evidence, each naming the test that pins it and the seen-failing evidence (the author's record and the reviewer's own red, by taking one clean source file back to the tests commit, running the test, restoring, confirming the tree clean); one ranked findings list with the lens named per finding; one subsection per lens (contract, scale, tests, ownership, adversarial) holding method notes and a close-out ledger; a Security section in guidance mode naming the boundaries the diff touches, the attack-class blocks read, and each record as confirmed, needs_validation or rejected; standards checks (tests first, constitution, production posture, patterns, tooling); Disposition; Verdict. The attack classes that apply to vfs: injection in the SQL builders and pattern compilers, path handling, permission compilation and bulk per-item checks, secrets in database URLs, tool-argument injection and confused deputy on the MCP surface, unbounded growth, data isolation; supply chain at release only. A release gets a full-audit review file plus its run folder, as wasi-python's 0.1.0 audit did.

## 8. The landing (S7)

EXECUTED (S7). Every one of the last sixty subjects is `type(scope): words`; many run 90 to 130 characters; 21 carry a `(spec NNN, ADR NNN)` suffix. Code landed in one commit and its record in a later one, ten days later for some specs. `test.yml` skips commits that touch only `context/`. `CHANGELOG.md`'s unreleased section is from the previous generation.

INFERRED. Keep `type(scope): words`, cap the subject at 72, drop every number and suffix. Body in order: the problem; the mechanism; what was decided at the build and flagged to Clay; "Also carried"; what did not run. Four trailers git can read by key: `Spec:` (the archive path), `Spec-review:`, `Code-review:`, `Co-Authored-By:` naming the model that wrote it. One landing commit by default, carrying the code, the tests, the docs, the review file, the landing notes, the `git mv` to `archive/` and the architecture page; slices allowed when each is green and the last carries the trailers. The review file never lands after the code. The landing checklist, eleven steps in order, is S7's; the changelog answer is a `**Changelog:**` line at the end of every landed spec's landing notes, assembled into `CHANGELOG.md` at release from the `Spec:` trailers since the last tag; no news files, no maintained unreleased section. `commits-and-prs.md` is replaced by `landing.md`; `release.md`'s steps 0 to 5 are rewritten; a small `lint.yml` runs `tests/lint` on `context/**` changes so a context-only commit is not unchecked.

## 9. Where two studies chose differently, and the resolution (INFERRED)

- **Review file names.** S4 and S6: `-spec-review.md` and `-code-review.md`. S7's example trailers used `-spec.md` and `-code.md`. Resolution: the longer names; the word "review" is what a listing of `context/reviews/` reads.
- **Spec as a file or a folder.** S3: one file. S7's example paths kept a folder with `spec.md`. Resolution: one file, as Clay decided.
- **Where the review file is committed.** S6: after the last code commit and before or with the landing commit. S7: inside the landing commit, never its own. Both agree it never comes after the code. Resolution: the tests commit, then the code commits, then one landing commit that carries the review file, the landing notes, the archive move and the architecture page. The review's Reviewed line names the final code tip.
- **Where the intention's questions go.** S1: an "Open questions" section. The rule everywhere else: no open questions. Resolution: the section is "What the research must answer", and the no-open-question lint does not scan intentions for that heading.
- **The Date header line.** Every study kept a Date line on memos, specs and reviews; Clay dropped it from the intention because the file name carries the date. Resolution: a lean, listed below.

## 10. What this memo does not settle

Each is a decision for the spec's Decisions section, with the lean the studies support.

1. **Header lines on memos, specs and reviews.** Keep Status and Owner; drop the Date line, since the file name carries it and the Status line dates every state change. Lean: drop it, for the same reason the intention has none.
2. **One-line paragraphs** (S2 §5 item 7). wasi-python forbids hard-wrapped prose under `context/` so a header line and a label always sit on one line and diffs stay small. Lean: adopt for new documents; a fixer joins wrapped lines; old documents are left alone.
3. **The `lint.yml` workflow** (S7). A context-only commit runs no CI today. Lean: add a one-job workflow on `context/**` that runs `uv run pytest tests/lint`.
4. **The commit-message red-run line** (S5). Whether the landing commit's body must name each new test and its red shape, held by a lint that reads `git log -1`. Lean: the landing notes carry the record and the lint reads the notes; the commit body says it in prose when it helps.

## One line

Seven stages, seven dated documents in seven known shapes, linked backward by path, labelled, boxed, reviewed twice by someone who did not write them, built tests first, landed in one commit whose trailers name the spec and both reviews, and held by one lint package so the process cannot drift from its description.
