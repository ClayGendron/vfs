# Two classes with the same verb names is what all three developer populations expect and the only shape that passes every setting; one object cannot serve `fs.read()` and `await fs.read()` under one name without guessing wrong in every notebook cell, and the one choice the evidence leaves open is which class carries the plain name

Clay asked on 2026-11-06, after the sync facade landed as `vfs.sync.SyncVirtualFileSystem` beside the async `vfs.VirtualFileSystem`: "Can we research how FastAPI does this? My dream is that `VirtualFileSystem` can be both, and if called like `await fs.read()` it runs async but if it is just `fs.read()` it is sync, but THE TOP PRIORITY is that the API follows what developers expect to see. Our developers are using langchain (AI Engineers), fastapi (Software Engineers), pandas (Data Engineers). We do not want to prioritize any of them. However, I do not want to create a brittle and fragile API or code, we need to be stable. I am open to anything, do not take the current design as something to uphold." While the studies ran, Clay added a ruling input: "if we think about vfs as a kernel, it needs to be an async kernel to be cloud native as well as agent native as most agent designs are going async, so we should consider that with our choice." Four fresh Opus researchers each took one question under a 45-minute box, the brief in [the studies folder](studies/2026-11-06-sync-and-async-api-shapes/00-brief.md): [FastAPI and the software engineers](studies/2026-11-06-sync-and-async-api-shapes/01-fastapi-and-software-engineers.md), [LangChain and the AI engineers](studies/2026-11-06-sync-and-async-api-shapes/02-langchain-and-ai-engineers.md), [pandas, SQLAlchemy and the data engineers](studies/2026-11-06-sync-and-async-api-shapes/03-pandas-and-data-engineers.md), and [the dual-mode mechanism itself](studies/2026-11-06-sync-and-async-api-shapes/04-the-dual-mode-mechanism.md), with thirteen executed prototypes. This memo serves roadmap story X1 and the landed [sync facade spec](../specifications/archive/2026-11-06-the-sync-facade.md); the spec that follows it decides, this memo does not. Every box was kept; what each study did not reach is named in its own last section and gathered below.

## The answer

All three populations rank the same shape first or second: two classes with identical verb names, one awaited and one not, the httpx `Client`/`AsyncClient` shape that psycopg, pymongo and SQLAlchemy also chose and that fsspec and Dask implement underneath with the very mechanism `vfs.sync` uses, one loop on a background thread (READ, studies 01, 03). FastAPI developers choose `def` or `async def` per function by the import a library gives them (READ, 01); data engineers want blocking calls, the same names, chunked iterables and a `with` block, and every library they use gives them that (READ and EXECUTED, 03); AI engineers want both spellings reachable from one engine-owning object because LangChain's tool API takes `func=` and `coroutine=` side by side (READ and EXECUTED, 02). The dream shape, one method name that returns a value when called and a coroutine when awaited, fails on evidence rather than taste: a function cannot see whether its caller will `await` it, so every mechanism guesses from "is a loop running on this thread", and a Jupyter cell always has one, so the data engineer's `fs.read()` hands back a coroutine and an `AttributeError` one line later; both `ty` and `mypy` reject the `Result | Coroutine` type in both spellings; and Prefect, the main precedent, is migrating its own code off the decorator (EXECUTED and READ, 04). What survives of the dream is its substance: one object can serve both populations as long as the two spellings differ by a name and not by the presence of `await`, and an async spelling that awaits the facade's own loop through a wrapped future keeps one engine on one loop while leaving the caller's loop free (EXECUTED, 02). With Clay's ruling that the kernel stays async, the mechanism is settled (the sync face is a front over the async kernel) and one decision remains for the spec: which class carries the plain name `VirtualFileSystem`, where the three populations' habits and the kernel's identity pull in different directions (section 4).

## 1. What the three populations expect, side by side

1.1 READ (01). FastAPI's own rule, from its `async.md`: use `async def` when the library tells you to `await` it, `def` when it does not, and "if you just don't know, use normal `def`"; a `def` endpoint or dependency runs on an anyio worker thread, at most 40 at once (EXECUTED, the limiter's token count). The SQL tutorial this population copies is fully synchronous. Starlette's own `TestClient` is a sync front over the async app through a blocking portal, the mechanism `vfs.sync` uses.

1.2 READ (01). Every library this population pairs with FastAPI answers with two classes of the same method names: httpx `Client`/`AsyncClient`, psycopg `Connection`/`AsyncConnection`, pymongo `MongoClient`/`AsyncMongoClient`, SQLAlchemy `Session`/`AsyncSession`, and redis-py's same name in two modules. Three of them generate the sync face from the async source so the two cannot drift (httpcore's `unasync.py`, psycopg's AST rewriter, pymongo's `synchro.py`); redis-py instead carries 704 `@overload`s to type one shared mixin (EXECUTED, the count). None of the six offers one object whose method is sometimes awaitable.

1.3 READ and EXECUTED (02). LangChain's whole surface is name twins on one object (`invoke`/`ainvoke`, `_run`/`_arun`, `similarity_search`/`asimilarity_search`); sync is the abstract floor and the async twin defaults to a thread hop through `run_in_executor` with the caller's context copied. There is no general reverse bridge: a tool with only an async body raises `NotImplementedError` from `.invoke`. `StructuredTool.from_function(func=..., coroutine=...)` takes both halves at once, which is why this population wants both spellings from one object.

1.4 READ and EXECUTED (03). pandas has no async path and fails late when handed an `AsyncEngine` (`AttributeError: 'AsyncEngine' object has no attribute 'cursor'`); DuckDB's package has no `async def`; pyarrow's only asyncio surface is Flight; fsspec and Dask are async inside and sync by default through one hidden loop thread; polars keeps a sync signature over an async driver by patching the notebook's loop with a vendored `nest_asyncio`, and the patch outlived the call for the rest of the kernel session. SQLAlchemy 2, added to the study at Clay's request, is the mirror image of vfs: a sync core over the blocking DBAPI, with `AsyncEngine`/`AsyncSession` as class twins built over it through the greenlet bridge and `run_sync` as the hatch back; `Session`/`AsyncSession` share 38 public names, 16 of them coroutines on the async side (EXECUTED).

1.5 INFERRED (this memo, from 1.1 to 1.4). The populations agree on more than they differ: the same verb names on both faces; a type the checker can tell apart; a sync face that works on a worker thread with no loop; an async face that never blocks the loop. They differ on where the two faces live: the FastAPI and pandas populations expect two classes and pick by import; the LangChain population expects two names on one object and picks by method.

## 2. The rankings, laid side by side

| Shape | 01 FastAPI | 02 LangChain | 03 pandas | 04 mechanism |
|---|---|---|---|---|
| Class twins, same method names | 1 | 2 | 1 | 1 |
| Module twins, identical class names | 2 | 4 | 3 | (a spelling of 1) |

| Awaitable handle with explicit `.result()` | 6 | 7 | 6 | 3 |

2.1 INFERRED (this memo). Class twins is the only shape in every study's top two. Name twins is first for one population and third or fourth for the others, because it doubles every completion list and puts the blocking verb one keystroke from async code (READ, 01, 03). Context detection is last or near last everywhere, for the same measured reason in three studies: the notebook (EXECUTED, 02, 03, 04).

2.2 EXECUTED (01). Inside a real FastAPI app with 100 concurrent requests per route over the real router and the real facade: the async router in `async def` served 100 reads in flight in 0.58 s; the facade in `def` served 40 in flight (the worker cap) in 0.63 s through its one loop thread; the facade called from `async def` serialised everything into 5.68 s with the server loop frozen for 5,683 ms; the router called without `await` returned HTTP 200 with a coroutine repr as the body; `asyncio.run(router.read())` from `def` endpoints under eight threads failed 38 of 40 calls with "bound to a different event loop" and hung one. Background tasks worked in both shapes.

2.3 EXECUTED (02). A sync `@tool` over the facade works through `.invoke` and `.ainvoke` and carries both the caller's `ContextVar` and LangChain's config through the executor hop and the facade's loop hop. Two hundred blocking facade reads on the agent's loop thread let a heartbeat tick zero times; through `asyncio.to_thread` about 680,000. Per-call cost at in-memory storage, microseconds, single run: `await router.read` 4,198; `facade.read` with no loop 4,399; `to_thread(facade.read)` 4,713; the owner-loop bridge (an async spelling that awaits `wrap_future(run_coroutine_threadsafe(..., facade_loop))`) 4,891 sequential and 4,807 amortised over 500 gathered calls, with the caller's loop free.

2.4 EXECUTED (03). In a real ipykernel: `asyncio.run` raises "cannot be called from a running event loop"; top-level `await` on the router works; a forgotten `await` fails one line later with `AttributeError: 'coroutine' object has no attribute 'one'`; the facade wrote 10,000 entries from a generator and served 200 reads from eight pool threads; one facade call froze the kernel's loop for its duration, as pandas and DuckDB do.

2.5 EXECUTED (04). Thirteen prototypes in four settings. Every mechanism that chooses by a running loop (plain detection, Prefect's `sync_compatible` and `async_dispatch`) returned a coroutine for the sync spelling inside a running loop and inside a real kernel cell, with the "never awaited" warning attached to the next cell's source line. greenback needs a portal per task, and ipykernel runs each cell as its own task, so a portal opened in one cell does not help the next. The lazy awaitable result, the only mechanism that gives the exact dream spelling, moves the I/O to the first attribute access, blocked the loop silently when returned from a worker thread, and erases every type to `Any`. Under `ty` and `mypy`, a dual method annotated `Result | Coroutine[Any, Any, Result]` is rejected in both spellings; Prefect's real decorator leaves a type variable unsolved and its docstring tells users to `# type: ignore`. Both checkers flag a discarded plain coroutine (`unused-coroutine`, `unused-awaitable`) and neither flags a dropped handle or a dropped union.

## 3. What the evidence settles

3.1 INFERRED (this memo, from 2.5 and 2.4). The dream spelling is not available at any acceptable brittleness: the mechanisms that produce it are wrong in the notebook, untypeable, or silently lazy, and their best-known user is retreating from them. The two spellings must differ by name.

3.2 INFERRED (this memo, from Clay's ruling and 1.4). The kernel stays async, so SQLAlchemy's direction (sync core, async wrapper) is closed, and the sync face is a front over the async kernel. The front's mechanism, one loop on one daemon thread per facade, is the one fsspec, Dask, Starlette's `TestClient` and LangChain's own callback bridge use; it is settled.

3.3 INFERRED (this memo, from 2.3 and 02's 4.9). One object can serve both populations without the two-loop hazard: the facade's loop owns the engine, the sync spelling blocks on it, and an async spelling awaits it through a wrapped future, so an asyncpg engine is only ever touched by the loop that created it while the agent's loop stays free. This is available under any naming: as `aread` beside `read` on the facade, or as the async class built over the facade's loop. It costs one cross-thread hand-off per async call, a few hundred microseconds against a four-millisecond read at in-memory storage, unmeasured against a network database.

3.4 INFERRED (this memo, from 01's section 5 and 04's section 4). The forgotten `await` is caught by a type checker only while the async face's verbs are typed as returning coroutines; any shape that types a verb as "value or awaitable" gives that up. This holds for class twins, module twins and name twins alike, and is lost by context detection and the handle.

3.5 READ and INFERRED (03, 04, 02). Three guards belong to whatever shape is chosen: the refusal of a call from the facade's own loop thread (fsspec's `sync()` has it; the landed facade has it; the prototypes without it hung); a warning or refusal when the sync spelling is called on a thread whose running loop is not the facade's, the FastAPI `async def` freeze and the LangChain loop-thread stall, which no checker catches today; and a drift check between the faces, which the paired libraries do by generation and vfs does by a signature parity test.

## 4. The decision the evidence leaves open: which class carries the plain name

4.1 READ (01). The FastAPI population's libraries put the plain name on the sync face and `Async` on the other (httpx, psycopg, pymongo, SQLAlchemy); vfs today does the reverse (`vfs.VirtualFileSystem` async, `vfs.sync.SyncVirtualFileSystem`), which study 01 names as the one departure from the population's habit. Module twins (`vfs.aio.VirtualFileSystem`, the redis-py shape) are equally familiar, and their cost is that a wrong import looks identical in review and in a traceback because both classes print one name (READ, 01; INFERRED, 03).

4.2 INFERRED (this memo). Three spellings are consistent with everything above. First, as landed: the kernel keeps the plain name, the front is `SyncVirtualFileSystem`; honest about the async kernel, unusual in its prefix. Second, module twins with identical class names under `vfs.sync` and `vfs.aio`, with the marked names as top-level aliases; the same code under two import lines, at the price of one `__name__` for two classes unless each class is defined under its marked name and the module provides the plain alias. Third, the httpx shape inverted onto the kernel: `VirtualFileSystem` sync and `AsyncVirtualFileSystem` the kernel; it matches the software engineers' habit and contradicts the ruling that the kernel is the thing. The populations split on this axis and the mechanism does not care; it is a naming decision for the spec, not a research question, and the evidence that bears on it is 4.1 and the ruling.

4.3 INFERRED (this memo). Whichever name is chosen, the LangChain population's one-object need (3.3) is met by giving the facade an async spelling that awaits the facade's loop, or by building the async class over the facade's loop; the spec that names the classes should decide whether that bridge is part of the facade or a separate adapter such as `as_retriever()`.

## 5. Side findings that are not about the shape

5.1 EXECUTED (01). `src/vfs` ships no `py.typed` marker, so `mypy` users see no vfs types at all (`module is installed, but missing library stubs or py.typed marker`); every argument above about the checker catching a forgotten `await` holds for `ty` and for `mypy` reading from source only until the marker ships.

5.2 EXECUTED (03). `write` is annotated `entries: Sequence[Entry] | None` and accepts a generator of 10,000 entries at run time; the annotation is narrower than the behaviour, so the generator a data engineer naturally writes is flagged by the checker. vfs has no chunked-iterator read, the analogue of `read_sql(chunksize=...)`, and that population will feel its absence before any sync-or-async question.

5.3 EXECUTED (04). On `InMemoryStorage`, writing on one loop and reading on another succeeded and left two aiosqlite connection threads alive with a `ResourceWarning`; the loop-affinity failure the studies reason about is asyncpg's, and no study ran it against Postgres.

## What this memo does not settle

The asyncpg loop-affinity behaviour under each shape: the experiment is `vfs_confirm.py` and `probe_errors.py` run against the Postgres leg with per-call `asyncio.run`, the facade's loop, an async write then a sync read on one storage and the reverse, recording which raise "attached to a different loop" (named by 01, 02 and 04). The cost of the owner-loop bridge under real concurrency: `owner_loop.py` against the Postgres and SQL Server legs with 8 and 64 gathered calls against `await router.read` on the caller's loop (02). Whether a foreign-running-loop warning from the sync spelling is noise in Jupyter, where every cell has a running loop: `kernel_cells.py` with the warning enabled, counting warnings per cell over a ten-cell notebook (04). Whether a reentrancy guard costs anything measurable: 10,000 guarded against unguarded calls under cProfile (04). Whether pyright, the checker behind most FastAPI editors, flags both lines of `forgot_await.py`: run it once `py.typed` ships (01). Whether `Iterable[Entry]` can replace `Sequence[Entry]` on `write` without a second pass: a one-shot generator that counts its `next` calls (03). The naming decision of section 4 is a spec decision and waits on Clay, not on an experiment.

## One line

Every population and every executed setting point at two faces with the same verb names, awaited or not, over one async kernel and one loop thread; the dream of one name that does both guesses wrong in every notebook cell and cannot be typed; what is left to decide is which face is called `VirtualFileSystem`.
