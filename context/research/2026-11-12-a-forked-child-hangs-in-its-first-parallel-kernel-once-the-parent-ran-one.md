# Placeholder: once a process has run one parallel kernel, a child it forks hangs in its own first parallel kernel call; what the engine's pool should do after a fork is not yet researched

This is a placeholder memo: it holds a question, what is known, and the experiment that answers it, and it decides nothing. The question was raised on 2026-11-12 by [the second spec review of bounded work has one home](../reviews/2026-11-12-bounded-work-has-one-home-spec-review.md), finding M1, and the session lead ruled the same day that [that spec](../specifications/active/2026-11-07-bounded-work-has-one-home.md) does not fix it: the spec guards the Python pool across a fork, names the engine's pool as a thread set it does not own, and lists this memo in its Out list. The answer will be used by a fix spec for the engine's pool after a fork, which is not yet written. No spec waits on this memo. The research will have two 45-minute boxes, one for the prior-art study and one for the prototypes and the Linux run. The probe scripts and their output are under [the studies folder](studies/2026-11-12-a-forked-child-hangs-in-its-first-parallel-kernel-once-the-parent-ran-one/). There is no intention: the hazard exists today, and the fix spec will say whether an audience gains an experience.

Labels: EXECUTED means a command ran here and the claim reports its output. READ means read in a file cited by path. INFERRED means this memo's reasoning from the two.

## The question

After a process that has already run a parallel kernel forks, what should a parallel kernel call in the child do: run on a pool the engine re-makes for the child, run without parallelism, or refuse with an error the caller can read? Today it does none of the three. It never returns.

## What is known today

1. EXECUTED on 2026-11-12, vfs at `280a983`, CPython 3.13.11, macOS on an Apple M1 Pro with 10 cores, rayon-core 1.13.0 (`Cargo.lock`), by the reviewer and again by the spec's author from unchanged copies of the reviewer's scripts ([q3_fork_head.py](studies/2026-11-12-a-forked-child-hangs-in-its-first-parallel-kernel-once-the-parent-ran-one/experiments/01-fork-probe/q3_fork_head.py), [q3_fork_write.py](studies/2026-11-12-a-forked-child-hangs-in-its-first-parallel-kernel-once-the-parent-ran-one/experiments/01-fork-probe/q3_fork_write.py), [output.txt](studies/2026-11-12-a-forked-child-hangs-in-its-first-parallel-kernel-once-the-parent-ran-one/experiments/01-fork-probe/output.txt)). A parent that ran one `ContentMatcher.count_lines` batch of 2,000 bodies and then called `os.fork()` has a child whose own batch did not return inside 8 seconds and was killed by its alarm; no thread pool of Python's, no event loop and no storage was involved. A parent that ran one `InMemoryStorage.grep` has a child that builds its own storage and hangs the same way in its grep. A child of a parent that ran no kernel answers both (100,000 lines counted; 50 rows found), exit code 0.
2. EXECUTED, the same run. A parent that only wrote one body past `MEASURE_OFFLOAD_BYTES`, which hops to a Python worker and enters no parallel kernel, forks children that write and then grep, exit code 0. So the hazard needs both halves: a parallel kernel in the parent before the fork, and a parallel kernel in the child.
3. READ. Every parallel loop in the crate runs on rayon's process-global pool, which the crate neither builds nor names: `verify.rs:205,230` (grep's count and hit batches), `glob.rs:300` (the row judge behind glob, grep's and search's gates and the router's chained calls), `chunk.rs:43` (reindex's chunk split), `links.rs:60` (reindex's reference extraction) and `vectors.rs:70` (the cosine kernel of search's vector leg). [The runtimes memo](2026-11-07-how-runtimes-bound-work-deadlines-cadence-and-pools.md), section 3.2, records that the global pool is as wide as the machine and that vfs-core builds no pool of its own, and leaves a named pool of the crate's own unsettled. The sequential kernels (the overlay counter, the lexical and posting builders) enter no pool.
4. INFERRED. The cause is that a fork copies the calling thread alone: the child holds rayon's global registry, which records workers, and none of the worker threads, so work the child injects is never taken. That is the same on Linux as on macOS, because it is how `fork` behaves on every POSIX system. It has not been executed on Linux.
5. READ, the standard library of the interpreters installed here. `multiprocessing`'s default start method is fork on every platform but macOS and Windows under Python 3.11, 3.12 and 3.13 (`lib/python3.13/multiprocessing/context.py:323-328`: spawn on macOS, fork otherwise), and forkserver on those platforms from Python 3.14 (`lib/python3.14/multiprocessing/context.py:339-344`). macOS has defaulted to spawn throughout, and Windows has no fork. A child started by spawn or forkserver is a new interpreter and inherits no pool. An explicit `os.fork()`, or a start method set to fork, forks on any of them.
6. READ and INFERRED. [AGENTS.md](../../AGENTS.md), "Production posture", makes ETL developers and data pipelines a first-class audience, with batches of 10,000 files and a nightly batch of 100 of them. INFERRED: a pipeline that spreads those batches across worker processes with `multiprocessing` or `concurrent.futures.ProcessPoolExecutor` on Linux under Python 3.11 to 3.13, without choosing a start method, forks its workers. A worker that only writes is safe (item 2). A worker that reindexes, greps, globs or searches hangs if its parent ran any of those before the fork. No measurement exists of how vfs hosts start their workers or of how often a parent runs a kernel first.
7. READ. After the bounded-work spec lands, its decision 11 makes the Python pool safe across a fork: a forked child forgets the inherited executor and mints its own. That changes nothing about this hazard, which is in the engine and is the same before that landing and after it.

## The experiment that answers it

The research is done when each item below has a labelled result.

1. The Linux run. The two probe scripts, unchanged, in a Linux container of the kind the wheels are built for (manylinux 2_28, x86_64 or aarch64), under Python 3.13 (fork by default) and Python 3.14 (forkserver by default), with `os.fork()` as written and again through `multiprocessing` with its default start method. The result is an exit code per case.
2. Three candidate behaviours, each prototyped in a scratch build of the crate and run through the same probes. First, a pool the crate builds and holds, re-made in a child, with every parallel loop run inside it. Second, kernels that run their loops without parallelism in a process that is not the one that started the pool. Third, a refusal: the binding raises a named error in place of entering a pool that has no threads. For each candidate the run records: whether the child's first parallel kernel call returns, as an exit code; whether its results equal the parent's; how many threads the child holds afterwards; what a child of that child gets; whether the parent's pool is unchanged; what the detection costs per kernel call, counted in system calls, with a clock reported only as a fact about the machine; and what happens when the fork lands while the parent's pool is in the middle of a batch.
3. The prior art, each from a clone refreshed and licence-checked as [AGENTS.md](../../AGENTS.md) requires, described and never copied: what rayon's own documentation and issue tracker say about a fork; how other Rust-backed Python packages that run rayon under pyo3 behave after a fork, starting with polars (already cloned beside this checkout), Hugging Face `tokenizers` and the `blake3` binding; what the pyo3 guide says about forking; and, as the nearest non-Rust precedent, how the thread pools under numpy (OpenBLAS and the OpenMP runtimes) are re-made or disabled in a forked child. For each: which of the three candidate behaviours it chose, what it tells the user, and what it costs.
4. What the fix spec then needs from this memo: the three candidates side by side on the counts of item 2, the prior art's choices, and the Linux result. The choice among them is the fix spec's.
