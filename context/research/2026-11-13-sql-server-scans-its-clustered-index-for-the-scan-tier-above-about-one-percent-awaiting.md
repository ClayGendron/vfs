It was raised on 2026-11-13 by the session lead's ruling on what the engine legs of [the scan-tier spec](../specifications/active/2026-11-12-the-scan-tier-reveals-nothing-about-rows-a-caller-cannot-read.md) found, after [its code review](../reviews/2026-11-13-the-scan-tier-reveals-nothing-about-rows-a-caller-cannot-read-code-review.md) (its finding H1) showed that criterion 7's first world held nine tenths of its rows awaiting the index; the spec records the plan as predating it and names it Out (its decision 18). The research will have one 45-minute box with the SQL Server leg up, plus the Postgres and MariaDB legs for the comparison. There is no studies folder yet; the measurements below were made by the scan-tier spec's builder with a probe script in that build's scratchpad, and are restated here as outcomes.

Labels: EXECUTED means a command ran and the claim reports its output, with who ran it. READ means read in a file cited by path. INFERRED means this memo's reasoning from the two.

## The question

The scan tier's statement, `SELECT … FROM vfs_entries WHERE <content kinds> AND NOT encoded AND <arms> [AND <the caller's packed rights group>] ORDER BY path LIMIT limit + 1`, is meant to start from the few rows awaiting the index through `ix_vfs_entries_encoded_kind`. On SQL Server, once those rows are about 1 % of the table, the planner reads the whole clustered index instead, for every caller, the whole caller included, on the code before the scan-tier spec as after it. The choice is between two answers, and it cannot be made until the experiment below has run: carry an index hint naming the `(encoded, kind)` index as a `DialectProfile` fact, so the statement always seeks, at a cost to callers the planner would have served from their own ranges and at a cost in key lookups when many rows await the index; or accept the scan above the threshold, whose rows read grow with the corpus but whose logical reads, at those ratios, are fewer than the seek's. The answer also depends on what share of the table awaits the index at the reference deployment, which the refresh spec's partial index passes change.

## What is known today

1. EXECUTED by the scan-tier builder on live SQL Server 2025, Postgres 17 and MariaDB from `docker/compose.test.yml`, 2026-11-13, on the tree as built. The world: roots `/a/dNNNNN` and `/b/dNNNNN` alternating, 100 files each, posture `none`, rows bulk-inserted already encoded except one file per root in the first 2,000 roots; three stages, 202,003 rows with 2,000 awaiting the index (1 %), 808,003 rows with the same 2,000 (0.25 %), and 808,003 rows with 8,000 awaiting (1 %); each engine's statistics command run after each stage. Callers: the system actor; one reading 5 roots (500 files, 5 dirty); one reading `/a` (about half); one reading 300 roots. The statements were the ones `entries_for_scan` issues, with no globs and a limit of 25,000, spelled with literal values. Work was counted from the actual plan, never a clock: on SQL Server rows read (`ActualRowsRead`) over the accesses to `vfs_entries` and logical reads summed over every operator, from `SET STATISTICS XML ON`.
2. EXECUTED, the same run, SQL Server. The whole caller read all 202,003 rows by a `Clustered Index Scan` (5,207 logical reads) at 1 %, sought `ix_vfs_entries_encoded_kind` with key lookups at 0.25 % (4,000 rows, 5,349 reads), and read all 808,003 rows by a `Clustered Index Scan` (21,891 reads) at 1 % again. The half caller did the same (202,003 rows and 5,475 reads; 4,000 and 5,755; 808,003 and 21,891). The five-root caller was served by seeks on its path ranges, `ix_vfs_entries_owner_id` and `ix_vfs_entries_everyone_path` with key lookups at every stage (1,010 rows, 1,554 reads). The 300-root caller, three packed groups, sought `ix_vfs_entries_encoded_kind` and `ix_vfs_entries_owner_id` (4,200 rows and 6,098 reads at the first two stages, 16,200 and 23,381 at the third).
3. EXECUTED, the same run, Postgres and MariaDB, for comparison. Their work never grew with the corpus: about the smaller of the rows awaiting the index and the caller's visible rows. Postgres's whole caller examined 2,000 rows for 2,003 buffers at both 2,000-awaiting stages and 8,001 for 221 at the third; MariaDB's 2,000 rows for 12,076 and 12,086 pages, and 8,000 for 48,192.
4. EXECUTED, the same run, the hint. SQLAlchemy's `with_hint` spelling `WITH (INDEX(ix_vfs_entries_encoded_kind))` on SQL Server held the seek for every caller: the whole caller at 808,003 rows with 8,000 awaiting read 16,000 rows for 22,962 logical reads against the scan's 808,003 rows for 21,891, so rows read followed the rows awaiting the index while logical reads stayed about equal at that ratio. The narrow callers paid: the five-root caller 4,000 rows and 5,761 reads against 1,010 and 1,554; the 300-root caller 48,000 and 69,114 against 16,200 and 23,381 at the third stage. On MariaDB `FORCE INDEX` did the same and the five-root caller paid 2,000 rows and 6,031 pages against 505 and 1,672. The hint changes no bind or depth budget. Oracle's index hint was not measured, nor any engine's cardinality hint.
5. READ, `src/vfs/storage/backends/database/dialects.py`: `rarity_hint` is declared on SQLite alone (`unlikely`), and holds SQLite's seek whatever its statistics say; no other profile declares a per-term selectivity hint, and none declares an index hint.
6. INFERRED from items 2 and 4. A seek with key lookups costs SQL Server about three logical reads a row awaiting the index (5,755 reads for 2,000 such rows; about 23,000 for 8,000), and a scan of the clustered index about one read per 37 rows of the table (21,891 for 808,003). The planner's switch near 1 % is that crossover: by logical reads the scan is the rational plan above it, and by rows read it grows with the corpus.
7. INFERRED at [the reference deployment](../../AGENTS.md), 10,000,000 files, linear in the measured ratios. Without partial passes (the scan-tier spec's landing, a daily rebuild): by day up to about 50,000 rows await the index (0.5 %, between the measured seek and scan points), and through the nightly batch up to about 1,000,000 (10 %), where every scan-tier statement on SQL Server reads all 10,000,000 rows for about 270,000 logical reads, and a hinted seek would read about 2,000,000 rows for about 3,000,000 logical reads. With the refresh spec's partial passes every 15 minutes: about 1,250 to 2,500 rows awaiting by day (0.0125 to 0.025 %) and about 45,000 between passes through the nightly batch (0.45 %), both under the measured 1 %, so the scan would rarely be planned. Every row whose body is oversized, gram-saturated or shorter than three bytes stays awaiting the index for good (READ, `indexing.py`, the module docstring) and raises the share permanently; that share at the reference deployment is not measured.
8. READ, the direction other documents name. [The overlay spec](../specifications/archive/2026-11-09-the-overlay-counts-in-the-engine-and-the-scan-tier-shares-one-budget.md) and the scan-tier spec name a partial index over the rows awaiting the index (on SQL Server a filtered index `WHERE encoded = 0`) as the way to make the dirty-row read independent of the table on every engine; it is a schema change and has not been measured.

## The experiment that settles it

The research is done when each item below has a labelled result.

1. On SQL Server at 808,003 rows, the share awaiting the index stepped through 0.25, 0.5, 0.75, 1 and 2 %: the plan, rows read and logical reads of the whole caller's, a half caller's and a five-root caller's scan statement, unhinted and hinted. The result is the threshold and the two cost curves.
2. The same with a filtered index on the rows awaiting the index, keyed by path, in place of the hint. The result is whether it removes the scan without costing the narrow callers, and its write cost per row demoted and per publish.
3. Oracle's plan and work on the same world, unhinted and with its index hint.
4. The share of content rows oversized, gram-saturated or shorter than three bytes in a real corpus of the reference deployment's shape, and the share awaiting the index at the refresh spec's cadence once it has landed.
5. What the following spec needs from this memo: the two curves, the filtered index's figures, and the shares of item 4. The choice is that spec's.

## One line

Above about 1 % of rows awaiting the index, SQL Server reads its whole clustered index for every caller's scan-tier statement because a seek's key lookups cost more reads; an index hint stops the scan but costs narrow callers, and the share the refresh passes leave and a filtered index over the rows awaiting the index decide which to carry.
