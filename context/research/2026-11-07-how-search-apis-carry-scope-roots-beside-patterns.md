# Five search engines carry roots as structured clauses beside the patterns, apply them during candidate generation and never compose them into pattern text; authorization is judged per root and per candidate against a fact the root carries, so a storage seam that takes roots and arms as two fields of one call is the shape every engine already has, and a second text-composed shape beside it is a shape none of them offers

On 2026-11-07 Clay asked, after a structural review of the day's eleven landings: "Please research prior art before writing these specs, ensure we are following good patterns and then write up the specs." The review had found that scope now crosses the vfs storage seam in two shapes chosen by a router constant, composed pattern text below two hundred arms and roots beside arms above it, that every backend must serve both and prove them equal, and that the anonymous rights gate in storage re-composes the text to judge where composition would have judged. This memo answers one question: in mature engines that take both where to look and what to match, how are the two carried through the API and applied, and is pattern text ever composed client-side. One researcher, a fresh agent with no knowledge of the author's reasoning, worked a 45-minute box and finished inside it. The study, the brief and the demonstration are under [the studies folder](studies/2026-11-07-how-search-apis-carry-scope-roots-beside-patterns/). There is no intention: the work decides the end state of a seam the tree already has. The in-flight spec this memo informs is [storage takes scope roots and arms as two channels](../specifications/active/2026-11-07-storage-takes-scope-roots-and-arms-as-two-channels.md).

## The answer

READ across the five: roots and patterns are different clause types in zoekt's query tree, a positional path beside a glob override in ripgrep, one `pathspec_item` type OR-ed per entry in git, a filter clause beside a must clause in Lucene and OpenSearch, and a range or regex query on the path field under `Must` beside the term query in tantivy. In every one the root meets the pattern only inside the engine's conjunction, and it is applied during candidate generation, never as a post-filter: zoekt prunes shards by repository set before any index is opened and then drives the document cursor; Lucene leads the required conjunction with the cheapest clause and caches the filter by a usage policy; tantivy intersects `Must` scorers cheapest first. READ: the one place that composes text, git's current-directory prefix, stores the composed root's length as structured magic beside the text so a later command can tell root from pattern again. EXECUTED: ripgrep neither composes nor re-roots a glob per root; a glob is matched against the walked path anchored at the invocation directory, so `src/*.py` under two roots matches nothing and only `**/src/*.py` matches both, which is the cost of a tool that has no per-root channel. READ: authorization, where it exists, is judged per root and per candidate against a fact the root carries; zoekt checks tenancy once per candidate document inside the match loop, and its client sends the permitted repositories as a set of identifiers, never as text. INFERRED: a seam that takes `roots` and `arms` as two fields of one call is the shape the five agree on; none offers a text-composed second shape beside it chosen by size, and the posture gate's question, where a scoped anonymous call is judged, is one the prior art frames as "per root, against the root's own fact" and does not answer for vfs's inherited postures.

## 1. zoekt

1.1 READ ([study](studies/2026-11-07-how-search-apis-carry-scope-roots-beside-patterns/01-roots-and-patterns-across-five-engines.md), section 1). Repository scope and patterns are different leaf types in `query/query.go`: `RepoSet`, `RepoIDs`, `BranchesRepos`, `Repo`, `Branch` and `FileNameSet` on one side, `Substring` and `Regexp` with `FileName` and `Content` flags on the other. `query/parse.go` routes a `repo:` atom to `Repo` and a `file:` atom to a file-name regexp, so a repository name never enters a file regexp.

1.2 READ (the same section). The root is applied three times, all before content matching: `search/shards.go`'s `selectRepoSet` prunes the shard list and folds the clause to a constant true, with the comment that this is done once rather than per shard; `index/eval.go`'s `simplify` folds per shard; a surviving `RepoSet` becomes a `docMatchTree` whose `nextDoc` drives the candidate cursor. The tenant check runs per candidate document in the search loop under a security comment, against the tenant the document's repository carries; zoekt's comments say the identifier forms exist for efficient checking of large permitted lists sent by the client. The only composition in the clone wraps one exact file or repository name in `^` and `$` with its metacharacters quoted, for a single-document lookup.

## 2. ripgrep

2.1 READ and EXECUTED (section 2, [the transcript](studies/2026-11-07-how-search-apis-carry-scope-roots-beside-patterns/experiments/01-roots-and-patterns-across-five-engines/rg-two-roots-one-glob.txt)). Positional roots seed the walk; `-g` globs build an `Override` rooted at the invocation directory, whose source says matching is done relative to the directory path provided. Over a scratch tree with roots A, B and C: `-g '*.py'` listed four files under A and B and none under C; `-g 'src/*.py'` and `-g '/src/*.py'` listed nothing, because the slash anchors at the invocation directory and not at each root; `-g '**/src/*.py'` matched both roots; `-g 'rootA/src/*.py'` matched only A, which works only because the full walked path is matched and silently drops B. INFERRED: ripgrep has no per-root channel, and a user who wants one composes the root into the glob by hand and loses the other roots; that is the failure a seam with a roots field exists to prevent.

## 3. git

3.1 READ (section 3). A pathspec is one item type for roots and patterns, OR-ed per entry in `dir.c`'s matching with exclusions as a second veto pass; a literal prefix prunes subtrees in the tree walk. The one client-side composition joins the current-directory prefix into the item's match text, stores the prefix length on the item, and re-emits it as `:(prefix:N)` magic when the pathspec is handed to another command, so the receiving command can compare the literal root exactly. INFERRED: even the one engine that composes text carries the root's boundary as a structured fact beside it, which is what vfs's composed shape lacks and what its storage side then reconstructs by parsing the pattern's literal prefix.

## 4. Lucene, OpenSearch and tantivy

4.1 READ (sections 4 and 5). In Lucene the root is a `PrefixQuery` under a `FILTER` clause, which is required like `MUST` but does not score; `BooleanWeight` builds filter clauses without scores, the searcher wraps them in the query cache, the caching policy caches a multi-term query after two uses, and the scorer conjoins filter and must clauses led by the cheapest. OpenSearch's documentation says filter clauses run in filter context, score nothing and are generally cached, with its own example of a match in `must` beside a term and a range in `filter`. tantivy has only `Should`, `Must` and `MustNot`; the root is a range, regex or phrase-prefix query on the path field under `Must` beside the term query, and the complex scorer intersects the `Must` scorers sorted by cost with the cheapest leading. None composes text and none authorizes in core; document-level security in OpenSearch is an added filter, which the study marks as inferred from the documented model.

## 5. What this means for the seam

5.1 INFERRED, the synthesis. The five agree on three things: the root is its own structured clause and meets the pattern only in the engine's conjunction; it is applied during candidate generation, never as a post-filter; and authorization is per root and per candidate against a fact the root carries, with permitted sets crossing the wire as identifiers rather than text. A storage call that takes `roots` beside `arms` and `arms_not` is therefore the ordinary shape, not a departure. What no engine does is offer two shapes for the same intent and pick one by size: that doubles what every backend must serve and prove, and the in-flight spec's own criterion 5 exists only to prove the two equal. The composed shape's one remaining virtue, a tighter SQL prefilter below the limit, is a plan choice storage can make for itself from the roots and arms it already holds, as Lucene chooses its leading clause from costs.

5.2 INFERRED, the rights gate. zoekt's answer, judge each candidate against the fact its root carries, is the per-candidate view vfs already has in its visibility join; the posture question is whether an anonymous caller is refused by name before any row is read. Today that refusal is judged at the deepest literal directory each composed pattern names, a set of root-and-arm-prefix paths; the study shows no engine with inherited postures to borrow from, so the place of that judgement stays a vfs decision. What the prior art does say is that the judged fact should be built from the structured root and the arm's literal prefix as paths, as git keeps the prefix length, and never by composing pattern text and parsing it back.

## What this memo does not settle

Where the anonymous posture gate judges a scoped call once the seam carries one shape: at each root alone, or at each root joined with each path arm's literal directory as composition judges today; the in-flight spec's reviewer showed the two answer differently under nested postures, and the spec that adopts one shape decides it with a test over both posture orders. The cost of a root set of ten thousand in Lucene or tantivy, whose clause limits and filter unions were not examined, and of zoekt's linear document scan at ten thousand repositories per shard: experiments in those clones if a future seam needs them. Sourcegraph's client code and OpenSearch's security plugin: unread, and named as inference in the study.

## One line

Every engine studied carries roots as structured clauses beside the patterns and applies them while generating candidates, none composes pattern text from a root, and the one that does keeps the root's length beside it; vfs's seam should carry one shape, roots beside arms, and let storage choose its prefilter from them.
