# The API reference belongs inside Reference as one group among the product's interfaces, its pages are short hand-written files that pull the docstrings in, and build-time hooks are the one part of the site that its tool's successor does not carry

On 2026-11-14 Clay asked, after five pages of API reference were first generated from docstrings into the Reference tab of the new docs site: "can we think about the structure of this site long term? How will wil manage the UI of the API docs? Should we keep the API docs as a seperate page from reference? Can we study prior art repos and then come back with a propsoal? How does diataxis really well and who do we need to clone locally to study?" The question this memo answers is where a documentation site that follows Diátaxis puts its API reference, how mature projects shape and maintain API pages, and what the tool under the vfs site will carry in the long term. Four researchers, fresh agents with no knowledge of the author's reasoning, each worked a 30-minute box over seventeen reference clones, thirteen cloned for this study and four refreshed, and all four finished inside it (about 11 minutes for researchers 01, 02 and 03 and about 12 for 04, by the harness's clock). Five deviations are recorded. Researcher 02 found that Pydantic's public site is built by a second repository that was not cloned, so that builder was not read. Researcher 04 could not reach two pages of Zensical's site and used the public release list in place of the changelog. The Polars and CPython clones are shallow, so the commit of Polars' move and CPython's history were not read. Researchers 03 and 04 went past reading: 03 ran a two-file Sphinx probe, and 04 built a scratch copy of the vfs site with Zensical six times, outside the checkout. One fetched page carried text addressed to automated readers, which researcher 02 ignored and reported. The brief, the four studies, the logs and the saved outputs are under [the studies folder](studies/2026-11-14-where-the-api-reference-sits-on-a-diataxis-site-and-how-its-pages-are-shaped/). There is no intention: the memo informs the layout of the Reference tab and the spec that will replace the published site; none exists yet. An earlier memo, [how Diátaxis docs sites lay out navigation and group tutorials](2026-11-12-how-diataxis-docs-sites-lay-out-navigation-and-group-tutorials.md), settled the top bar, the sidebar and the tutorial order, and this one does not repeat it. This memo commits to nothing; the spec that stands on it decides.

Labels: EXECUTED means a command or fetch ran in this study, by a researcher or the coordinator, and the claim reports its output. READ means read in a file or page cited by path or URL, or in one of the four studies, each of which cites its own sources by clone, commit and URL. INFERRED means this memo's reasoning from the two.

## 1. The answer in one paragraph

INFERRED from the four studies. The API reference stays inside the Reference tab, as a group named "Python API", beside a group for each other interface the product has: the command line, settings, error kinds, access levels and the glossary. No source studied puts the API beside a Reference entry, and the framework's own text defines reference by the API. An API page should be a short file a person wrote, holding a sentence or two and the lines that pull docstrings in, not a page a build hook creates. A large class gets a page of its own and small related names share one, with every exported name documented exactly once and the build checking that. The look is set once in the handler's options and no template is overridden, which is how four projects keep it for years. All of this stays in one build so links are checked. The tool under the site receives fixes only until 2027-05-05, its successor already builds the vfs site except for its two hooks, one template line and one guard, and so each hook is the cost of a later move.

## 2. No source puts the API reference beside Reference; it is a part of Reference or it is all of Reference under a narrower name (READ, INFERRED)

READ in study 01: in none of eight sources is the API a top-level entry beside an entry called Reference. In pytest, Toga, LXD and the framework's own outline the entry is called Reference and the API is one named part of it. In Django, Hypothesis and NumPy the entry is called "API Reference" and it is the only reference there is. READ in study 01: the framework's page on reference says reference guides describe "APIs, classes, functions and so on", names generation from the code as "a powerful way of ensuring that it remains faithfully accurate", and asks that the structure of the documentation "mirror the structure of the product". Its only published site outline listed three children under Reference: "Command-line tool", "Available endpoints" and "API". EXECUTED by researcher 01: that outline's page was deleted in commit c953482 of 2026-08-03 and its live address returns 404. READ in study 02: FastAPI, Pydantic and Textual do give the API its own top entry, but none of the three organises its top bar by Diátaxis type, and FastAPI and Pydantic have no other reference to put beside it. Griffe, the one site of that set with a command line and a parser reference, nests "Python API" inside Reference beside them. INFERRED: a separate tab for the API is what a site does when it has no Reference tab. The vfs site has one.

## 3. The name "API Reference" misfiles everything that is not a Python object, so Reference is grouped by kind of interface first (READ, INFERRED)

READ in study 01: Django's section titled "API Reference" holds 6,462 lines of command-line and settings reference. pytest files its command-line flags, configuration keys and environment variables as sections of a page called "API Reference". Hypothesis had to head one page "Features with a defined interface, but no code API". The sites whose entry is named Reference need no such sentence. READ in studies 01 and 04: where Reference holds more than the API it is grouped by the kind of thing the reader has in hand. LXD's Reference landing page has seven headed groups with one sentence each, pytest has five pages by kind, and uv orders Commands, Settings and Environment variables first and hand-written facts after. READ in study 01: release notes sit outside Reference in six of the seven sources that have them. READ in study 04: eleven of the twenty pages in uv's Reference are troubleshooting, contributing, benchmarks and policies, and its hand-written index of the section omits four of its own entries. INFERRED: for vfs the groups are Python API, Command line, Settings, Error kinds, Access levels and Glossary, with the storage protocol added when it has a page, and with history and release notes kept outside.

## 4. An API page is a short file a person wrote, and no site on these tools generates it (READ, INFERRED)

READ in study 02: FastAPI, Pydantic, Textual and Griffe each hand-write their API pages as stub files of a title, one to three sentences, sometimes an import line or group headings, and the `:::` lines that mkdocstrings replaces with rendered docstrings. FastAPI has 24 such files, Pydantic 36, Textual 50 and Griffe 22. None creates them with a script or a plugin that walks the package. READ in study 01: Toga, on the same tools with tabs, does the same over 56 pages. READ in study 02: Griffe keeps the list honest with two tests, one failing when a public object is missing from the built site and one failing when the site documents an object that is not public. READ in studies 02 and 04: the stub file is also what survives a change of tool. FastAPI moved builder on 2026-05-19 and Griffe has moved, both keeping their `:::` pages and their options unchanged, and Pydantic's own hook carries a comment that a piece registered by a hook did not travel to its second builder. INFERRED: the vfs hook that writes one-line pages at build time has the right rule, only exported names get a page, in the wrong place. As a file each page gains room for the sentence that says what the object is for, and as a check the rule can run in both directions.

## 5. A page holds one large class or a handful of small related names; a page per member multiplies the page count by fifteen to nineteen (READ, INFERRED)

READ in study 03: NumPy and Polars generate a page per object, methods included. NumPy's 113 hand-written source files become 2,148 generated pages and Polars' 101 become 1,541, and 53 and 81 percent of those pages hold a single member. A Polars method page is about 94 percent sidebar by bytes. CPython writes by hand and gives a module a page, about thirty objects each. READ in study 02: on the mkdocstrings sites a page is a topic or a module, never one small name. FastAPI puts 61 objects on 24 pages and Griffe 225 on 22, a class with many members has a page to itself, and no site has a page for an object with one member. READ in study 03: one page holds a large class well when it has topic groups. CPython's `pathlib` page carries 81 signatures in 271,233 bytes under hand-written headings, and Polars' DataFrame page, 136 signatures inline in 1.5 MB, is where a page stops being usable. The two studies disagree on one point. Study 02 recommends eight to ten pages grouped by topic. Study 03 recommends one page per exported name, with the six error classes sharing one, because the glossary's links and the export check both rest on a name having an address. INFERRED: the two meet. A name's address is its anchor, not its page, and study 01 found that every site links by object name, so a name can share a page and keep a stable link. The rule that satisfies both is that every exported name is documented exactly once, a class with many members has its own page, and small related names share a topic page. EXECUTED by researcher 03: the 22 exported names hold about 266 members, so a page per member would be about 290 pages today and about 790 at 60 names.

## 6. The look is set once in the handler's options, and nobody overrides a template (READ, EXECUTED)

READ in study 02: the four sites set between 7 and 22 handler options for the whole site, and a page overrides almost nothing but which members appear. `separate_signature`, `signature_crossrefs` and `merge_init_into_class` are set by all four, and all four filter to public names. EXECUTED by researcher 02: no handler template is overridden in any of five repositories, the handler's own documentation included, and the most stylesheet any site adds for handler classes is Textual's eight rules. READ in study 02: showing source is what makes a page heavy. FastAPI's and Griffe's largest pages are 1.22 MB and 0.77 MB with source shown, and Textual's 196-heading page is 0.52 MB without. READ in study 02: Textual locks the handler at 1.3.0 where the current release is 2.0.11, and the badges and parameter headings its options ask for do not appear on its live page, with no warning; the study infers the old handler ignores options it does not know. EXECUTED by the coordinator: the vfs site builds under `--strict` with `summary` and `signature_crossrefs` added. The largest page, `AsyncVirtualFileSystem`, grows from 171,078 to 200,815 bytes, gains two summary tables at its top and 66 links from signatures to the pages of the types they name, and keeps its 40 headings. INFERRED: the vfs option block already matches the common ground except for those two options. What maintains an API page's look over years is that there is nothing local to maintain, plus a deliberate handler upgrade followed by a look at one built page.

## 7. The index of an API is by topic and kept by hand, and only one project checks it for completeness (READ)

READ in study 03: all three large projects lead with a hand-kept index by topic: 26 topic pages at NumPy, a card grid and about 1,641 names typed into tables at Polars, and 34 topic pages at CPython. None leads with the alphabet or with modules. READ in studies 01 and 02: Toga orders 56 API pages in seven hand-named domain groups and renders its landing tables from one data file, Griffe's entry page is a topic-grouped list of names with one line each, and FastAPI's and Textual's entry pages are two sentences that leave the work to the sidebar. READ in study 03: neither NumPy nor Polars fails a build when a public name is missing from its index. NumPy's checker says its output must be read by a person, and Polars has one sentence in its contributing guide. READ in study 03: a class with dozens of methods is always given topic groups, on a second hand-written page at NumPy, as ten topic pages at Polars, and as headings on the one page at CPython. INFERRED: at 22 to 60 names the index is one short hand-written page grouped by what the reader is doing, and the completeness check that the large projects lack costs vfs one comparison against `vfs.__all__`.

## 8. One build keeps its links, and links are made by name, never by page (READ, EXECUTED)

READ in study 03: NumPy and CPython build guide and reference together and refuse a broken link, with 396 and 1,492 links from guide to reference resolved by the build. Polars builds its guide and its API reference with two tools and joins them through a hand-kept table of 505 lines. EXECUTED by researcher 03: of that table's 143 distinct addresses, 3 returned 404 on the day. READ in study 03: the link back is one top-bar entry and four links in docstrings. READ in study 01: every site studied links from its guides to the API by object name through a mechanism that finds the object wherever it is documented: 3,176 roles in Django's guides, 76 autorefs in Toga's with no link by file path, and 590 uses of a custom role at LXD. Toga's configuration holds 39 redirects for reference pages that moved. READ in study 02: Pydantic uses a fixed admonition in 34 docstrings to point at a guide page and a fixed one in 26 guide sections to point back, and the prose of Textual, Pydantic and Griffe carries 376, 331 and 151 links into the API where FastAPI's carries none. INFERRED: the API reference stays in the same build as the rest of the site, and both the hand-written pages and the glossary link to an object by its name so that a page can be regrouped without breaking a link.

## 9. A glossary is linked mostly from prose pages, and what stops a build on an unknown term is a general warning gate (READ, EXECUTED)

READ in study 01: three of eight Diátaxis sources have a glossary, all three keep it outside the reference section, and two barely link to it. Django's 12 terms receive 4 links and NumPy's glossary is not reachable from its front page. Hypothesis links 5 terms 23 times from pages and 34 times from docstrings. READ in study 03: CPython's 178 terms are linked 2,073 times from pages and never from a docstring, and NumPy's 50 terms 74 times from pages and 4 times from docstrings to its own glossary. EXECUTED by researcher 03: neither has a glossary check of its own. A two-file Sphinx probe with one unknown term printed a warning and exited 0, and exited 1 when warnings are errors, which is how all three Sphinx sites build. EXECUTED by the coordinator earlier the same day: a `:term:` marker naming a term the vfs glossary lacks aborted the Material for MkDocs build under `--strict`. EXECUTED by researcher 04: the same marker builds clean under Zensical's `--strict`, because the vfs extension reports through a logger that only MkDocs counts. INFERRED: marking terms from docstrings is the less common practice and the vfs check on them is stricter than any project's own, but it holds only on today's tool until it raises an error instead of logging one. Most term links will be written in tutorials, how-to guides and explanation, where they are ordinary links to a heading and the strict build already checks the anchor.

## 10. Fixes for the site's tool end on 2027-05-05, and its successor builds the vfs site except for its hooks (READ, EXECUTED)

READ in study 04: the authors of Material for MkDocs say feature development has ended and that critical and security fixes continue "through May 5, 2027", and they call MkDocs itself unmaintained since August 2024. Their successor, Zensical, is at 0.1.1 of 2026-11-10, classed beta, with about one release every four days, and reads an existing `mkdocs.yml` as it is. Its migration page lists `hooks` as the one setting "not yet supported", says unlisted plugins are "silently ignored", and its roadmap places a Python module interface "up next" with no date and with paid members first. READ in study 02: FastAPI and Griffe already publish with it and Polars' guide does too. EXECUTED by researcher 04, on a scratch copy of the vfs site built with Zensical 0.1.1: the unchanged configuration fails on one footer template line that calls a Python method on the build date. With that line replaced the build exits 0 and says nothing about hooks, while no API page exists and both diagrams stay images, because neither hook ran. With the five stub pages written as files, mkdocstrings and the Griffe extension render them with the same heading counts as today and the glossary links resolve. Checks for a missing page and a missing anchor fire; checks for an absolute link and for a page left out of the navigation do not. Zensical's own API generator writes 103 pages, one per module, and knows nothing of `vfs.__all__`. READ in study 04: Polars' one hook became a workflow step before the build, under a comment that reads "zensical has no hooks". INFERRED: the content of the site carries and its build-time code does not. A hook that only creates files can be files or a script today at no loss, and a hook that rewrites rendered pages is the expensive kind.

## 11. Reference that is not a Python API is one generated page per kind of interface, with an anchor per item, and is never stored (READ)

READ in study 04: uv generates three reference pages from its own code, one for commands by walking the real argument parser, one for settings from the comments on its settings types, and one for environment variables from a table of constants. The three are ignored by git, and every check job and publish job remakes them and then runs a strict build, so a stale page cannot exist. Each page has one heading per item whose anchor is the item's name, and uv's hand-written pages hold 61 links to those anchors. Its settings page works as one page at 432 KB, and its command-line page, 62 commands on one page of 1.18 MB, is the example of one page kept too long. READ in study 02: Griffe's command-line page is one sentence and a block that the build runs against the program's argument parser. READ in study 01: LXD generates its REST specification, its man pages and 986 configuration options from the source and hand-writes the overview pages around them, and its guides link to an option by name 590 times. INFERRED: the vfs command line, settings and error kinds each want one page generated from the code that defines them, sitting as plain siblings of the hand-written pages, with one heading per command, key or kind.

## 12. What this means for the vfs site as built today (INFERRED, EXECUTED)

INFERRED: five things on the site as it stood differ from what the evidence supports. First, the API pages are written by a hook, `overrides/api_pages.py`, where every site studied keeps them as files. Second, each exported name has a page, so `MountError`, with one member, is a page of one paragraph; the studies agree that the six error classes share a page. Third, the section is named "API", which stops being exact once a command-line reference sits beside it. Fourth, the glossary guard in `overrides/docstring_markup.py` logs a warning, which stops one tool and not the next. Fifth, the site has two hooks and one footer line that its tool's successor does not run, and the newer of the two hooks is the one that can become files today. EXECUTED by the coordinator earlier the same day: six public verbs of the file system class (`read`, `stat`, `ls`, `tree`, `move`, `copy`) have no docstring, so their entries are a signature alone. READ in study 02: on all four mkdocstrings sites the docstrings were written for the rendered page, with links, examples and a fixed pointer to the guide. INFERRED: once the options are set, the largest lever on how the API pages read is the public docstrings themselves, which today are written as notes for maintainers. INFERRED: which exported names share a page, and under which domain names, is the coordinator's reading of the product and the owner should set it before the pages are written.

## What this memo does not settle

Whether two full pages for the two faces of the file system read better than one page and a pointer rests on one precedent, FastAPI's two classes with the same verbs; the experiment is to build `VirtualFileSystem` both ways with summaries on and compare the page, its table of contents and the search results for one verb. How the site renders under Zensical was not looked at in a browser; the experiment is to open researcher 04's run C output beside the Material build, once with the classic variant and once without. Whether raising an error from the Griffe extension stops a build cleanly on both tools is not tested; the experiment is to change the guard and repeat the coordinator's unknown-term build and researcher 04's run D. When Zensical gains a public way to run build-time code is not stated anywhere read; the experiment is to repeat runs A to F at each Zensical minor release. Whether readers find an API page faster from a top-level tab than from a group inside Reference is measured by no source; the experiment is a first-click test on the built vfs site, or its own search log once it has traffic. How Pydantic's second builder renders a `:::` line was not read, because its repository was not cloned; the experiment is to read that repository's build script.

## One line

Keep the API inside Reference as "Python API" beside a group for each other interface, write its pages as short files with one large class or a few small names each, set the look once in the options, and stop adding hooks, because hooks are what the site cannot take to the tool that replaces Material.
