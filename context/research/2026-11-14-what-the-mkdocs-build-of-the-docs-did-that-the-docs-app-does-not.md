# The docs app keeps the pages, the navigation and the look of the MkDocs build and lacks five things a reader would notice and eight smaller ones, with search set aside as a decision already made

On 2026-11-14 Clay asked, after previewing the docs app that replaced the MkDocs build of `documentation/`: "for the python api, can we add in the meth attr and other labbeling as before? We changed a lot from using mkdocs, so please have a sub agent identify the feature and functionality gaps so we can close them from mkdocs". The question this memo answers is what the MkDocs build did, by configuration or by its tools' own defaults, that the docs app does not. One researcher, a fresh agent with no knowledge of the author's reasoning, worked a 40-minute box and used about 17 minutes of it. It rebuilt the old site in a scratch folder from the copy taken when its files were removed, built the new site from a scratch copy of `docs-app/`, and compared the two as configured and as built, in Chromium at four window widths, with scripts on and off, and in print. Three things were skipped and are named in the last section. The brief, the study and its saved outputs are under [the studies folder](studies/2026-11-14-what-the-mkdocs-build-of-the-docs-did-that-the-docs-app-does-not/). There is no intention; the memo serves [the docs site spec](../specifications/active/2026-11-14-the-docs-site-is-a-svelte-app-in-this-repository-built-from-the-design-system.md), which records each gap it closes as a decision. This memo commits to nothing; the spec decides.

Labels: EXECUTED means a command or a build ran in this study, by the researcher or the coordinator, and the claim reports its output. READ means read in a file cited by path, or in the study, which cites its own sources. INFERRED means this memo's reasoning from the two.

## 1. The answer in one paragraph

READ in the study: of 63 items, 36 are the same in the docs app, better, or different with no loss; 5 are High gaps, 8 Medium and 14 Low. The five a reader would notice are the labels before and after API names, the table of contents on any window narrower than 1280 pixels, the link mark beside a heading, and a link that leaves the site opening in a new tab. The eight smaller ones are a back-to-top control, a skip-to-content link, the description and canonical address in a page's head, a sitemap, an icon in the browser tab, print rules, the attributes of a module on its API page, and two behaviours with scripts turned off. Search is the largest loss to a reader and is ranked Low only because the spec set it aside as its own work.

## 2. The five High gaps (READ, EXECUTED)

READ in the study, each EXECUTED there on both built sites. First, the kind label: the old pages drew 340 of them in headings, 209 `meth`, 100 `attr`, 24 `class`, 6 `func` and 1 `mod`, and one on every row of the table of contents; the app's first build drew `class` on a class heading alone. Second, the declaration label: the old pages drew 242, 90 of them `async`, 32 `property` and 9 `classmethod`; the app drew none, so nothing on a method's entry told a reader to await it. Third, the table of contents: the old site showed it as a column from 960 pixels and inside the drawer on a phone; the app shows it at 1280 pixels and nowhere below, which is worst on the API pages, where the list is the only index of a class's members. Fourth, the link mark: every old heading and every API member linked to itself on hover, 14 on the Overview page; an app heading has its id and no link. Fifth, a link that leaves the site: the old build opened it in a new tab, told a screen reader so, and put an arrow on the header's repository link, by hand in three files; the app's 8 outside links and its header link open in the same tab, and the spec never says why, so this was not left out on purpose.

## 3. The eight Medium gaps (READ, EXECUTED)

READ in the study, each EXECUTED there. A "Back to top" button appeared on the old site when a reader scrolled up; the app has none. The old site's first Tab stop was "Skip to content"; the app's is the wordmark, with the article 12 presses away on Overview and 23 on the longest API page. Every old page carried a description, a canonical address and previous and next links in its head; 1 of the app's 26 pages has a description and none has the other two. The old build wrote `sitemap.xml` with 31 addresses; the app writes none. The old pages linked an icon, Material's own; the app links none and `/favicon.ico` answers 404. Printed, the old Overview is the article at the page's width; the app prints its header and left navigation and keeps that column empty on every page after. On the Permissions page the old build drew the module's attribute `Permission` and the three fields of `PermissionLayer`; the app draws neither, because the export lists only a module's functions and classes. With scripts off, a reader whose system is dark gets the light theme and a phone's drawer does not open; the text, the diagrams and the highlighted code still show.

## 4. What is Low, and what is deliberate (READ, INFERRED)

READ in the study: 14 items are ranked Low. Five are deliberate, each named by a decision of the spec: search, the Markdown extensions no page uses, the constructor-assigned value of an instance attribute, heading levels below the third in the table of contents, and the Introduction page. The other nine are small: a copy button on an API signature, the `n` and `p` keys, options on a code fence, the repository link in a phone's menu, one API page 5 pixels wider than a phone's window, the inventory file other projects' docs read, one anchor of 96 that differs by an apostrophe, a diagram also published as a file, and the dotted path in an API heading. INFERRED: one of the deliberate five hides a hole the spec did not intend. READ in the study: decision 6 says a page holding any kind of Markdown the renderer does not draw fails the build, and the parser returns a plain paragraph for a note, a footnote, a definition list and four more, so those would print as typed with no error. No page uses one today.

## 5. What the app does that the old build did not (READ)

READ in the study: a theme switch beside following the system; the header links and the left navigation at tablet widths, where the old build folded both into a drawer below 1220 pixels; moving between pages without a full reload; twenty-two exported names on twelve hand-written pages where the old build's final form generated five; a build that fails where the old one warned; a not-found page with a way home; both side panels held still by tests; and no script from another project in the build.

## 6. Where the first two gaps stood when the study ended (EXECUTED, READ)

READ in the study: the researcher's copy of the app was taken while the labels were being restored, so gaps 1 and 2 describe the app before that change, and the study saved the old counts to check a restoration against. EXECUTED by the coordinator the same day, after the study's copy was taken: the export gained a `labels` field and the app draws the kind before a name in the heading and in the table of contents and each label after it, pinned by `tests/scripts/test_docs_export.py::test_labels_say_how_a_name_is_declared` and by the API block case of `docs-app/tests/build.test.ts`; the spec records it as decision 33.

## What this memo does not settle

Whether any gap differs in Safari or Firefox is not known, since every run was Chromium; the experiment is the same comparison in Safari, the browser the inline diagrams exist for. What a screen reader says of an outside link and of the drawer is read from attributes and not heard; the experiment is VoiceOver on both. Whether the fine styling matches, a table's row hover and a name in code that never breaks inside a cell, was photographed and not compared rule by rule; the experiment is screenshots of the Access Levels page at 390, 800 and 1280 pixels on both sites. How the host answers an old-style address such as `/overview/` belongs to [the deployment spec](../specifications/active/2026-11-14-a-release-or-a-manual-run-deploys-the-docs-from-this-repository-to-docs-vfs-dev.md) and is settled by the first deployment. Which icon stands for VFS in a browser tab is a design choice no study can make; the experiment is the owner's.

## One line

The app draws the same pages with the same look and lost the reader's small tools: the labels on API names, a table of contents on narrow windows, link marks on headings, new tabs for outside links, and the page furniture a keyboard, a printer and a search engine rely on.
