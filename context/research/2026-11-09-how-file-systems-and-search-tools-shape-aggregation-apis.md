# Mature systems aggregate in three distinct shapes that match the three layers vfs is weighing, and prior art fixes each shape's semantics: a stats block is an additive side channel that names what was skipped and why; a rollup is one whole-subtree walk whose depth trims rows and never the walk; a histogram is a request of its own that takes a key, a cap and a filter, probes cap plus one, and reports the mass that fell off as data; no studied engine maintains a count, the file systems that do keep a non-recursive counter per directory and label the fast answer inexact, and the only rights rule worth copying filters before any counter is touched

On 2026-11-09 Clay asked, while writing the navigational-primitives section of the introduction and after placing aggregate beside drill, filter, match, connect, describe, sample and seek: "please clone down prior art to study and send of research agents to understand how those projects design apis and functions around aggregations for file systems." The question this memo answers is how mature file systems, search tools and query engines shape the API of an aggregation, so that vfs can add an aggregate primitive that fits beside its navigational verbs. The design under consideration before the research began had three layers: a typed stats block on every listing and search result, rollup columns on directory observations fetched through the existing `columns` parameter, and a histogram verb taking a scope root, a group-by key and a top-N. ## 1. The answer in one paragraph

READ, across the four studies. Every mature system studied aggregates in one of three shapes, and the three are the three layers vfs proposed before the research began. The first is a stats block: an additive record carried beside the rows of every search or listing result, measuring the work that ran and the set it returned (ripgrep's `Stats`, zoekt's `Stats` embedded in every `SearchResult`, GNU `tree -J`'s trailing `report` element, PowerShell's `Measure-Object`). The second is a rollup: one measure or several summed bottom-up over a whole subtree in one walk, with depth, threshold and summary flags choosing which rows print and never how far the walk goes (every `du` from plan9port to uutils, nushell's `du`, dust, ncdu). The third is a group-by: a request of its own that names a key, a cap and an optional filter, returns buckets of value and count, and reports what the cap cut (datasette's facets, sqlite-utils' `analyze-tables`, Lucene's `Facets`, tantivy's `Aggregations`, qdrant's facet endpoint, JuiceFS's `summary`). Prior art then fixes each shape's semantics. A stats block merges by addition, keeps "matched" and "returned" in separate fields, and reports a cap as a named skipped quantity with its reason rather than a silently smaller number. A rollup's depth trims rows, never the walk, so a depth-1 row is exact for its whole subtree; the two tools that cut the walk, GNU `tree -L --du` and fsspec's `du(maxdepth=)`, report a smaller total with nothing to say so. A group-by probes cap plus one to learn it was cut and returns the cut as data (tantivy's `sum_other_doc_count`, Lucene's `value` and `childCount`, JuiceFS's `...` child), not as a bare flag and not as an unmarked inexact count. On maintenance, no query engine keeps a count: Lucene, tantivy and qdrant are fast because the attribute is columnar at index time; the file systems that maintain anything keep a non-recursive counter per directory, batch the deltas, and label the fast answer as possibly inexact beside a strict re-walk (JuiceFS), or stamp the cached figure with its age (MinIO). On rights, only zoekt and datasette have a rule, and it is the same rule from two directions: filter before any counter is touched, so a hidden row appears in no statistic, and run every fast path through the same gate, because zoekt's one shortcut that skips the gate leaks the whole shard's count. `statvfs` has reported a rights-adjusted figure beside the raw one since it was designed. INFERRED: vfs's proposed posture, a total before truncation with an exactness marker and counts judged at the caller's `list` rung, is stricter than any studied system; the evidence says the pieces exist separately in prior art and nothing studied combines them.

## 2. The stats block is an additive side channel that measures the work and the result set, and the systems that have one differ only in whether it is optional

READ, study 02. ripgrep's `Stats` has seven fields (`elapsed`, `searches`, `searches_with_match`, `bytes_searched`, `bytes_printed`, `matched_lines`, `matches`), implements `Add` and `AddAssign`, and the parallel driver folds each worker's copy into one behind a mutex; the text footer and the JSON `summary` message are the same struct serialised two ways. zoekt embeds a 20-field `Stats` by value in every `SearchResult`, with no flag to request or suppress it, and `Stats.Add` sums every field while keeping the first non-zero `FlushReason` sticky. scc's `summaryTotals.merge` carries the invariant as a comment: addition is the only operation, so the result does not depend on the order the workers finish in. The one non-additive count in six projects, zoekt's `RepoStats.Repos`, is set from a list length because one repository spans several shards, with the reason beside it in a comment.

READ, study 01. GNU `tree` installs a `report` callback per output mode: the text footer `N directories, M files`, a last JSON array element `{"type":"report","size":…,"directories":…,"files":…}`, an XML `<report>` element, and `--noreport` to drop all three. PowerShell's `Measure-Object` streams one record per measured property in constant memory, with `Count` always set and the heavier measures (`Sum`, `Average`, `Maximum`, `Minimum`, `StandardDeviation`) null unless their switch was given. Every `du` and `wc` instead makes the total one more row whose path column is the word `total`, a reserved value a consuming program must know.

EXECUTED, study 02. `rg --stats` over `src/` reported 13 matches and 1,659,826 bytes searched; with `-m 1` the same command reported 10 matches and 1,285,267 bytes searched, and nothing in either output says a cap was hit. `rg --json` ended in a `summary` line whose `stats` object carried `searches: 96`, `searches_with_match: 10`, `matches: 13`. `git diff --stat HEAD~5` ended in the same one-line footer `--shortstat` prints alone, and `--numstat` is the structured twin that emits rows and no footer.

INFERRED. The stats block the brief proposed sits exactly where ripgrep's `Stats`, zoekt's `Stats`, `tree`'s `report` and `Measure-Object`'s record sit, and the prior art fixes four properties: it is typed and structured first, with numbers as numbers (dust's JSON `size` of `"81M"` is the counter-example study 01 flags); it merges by addition so chunked statements and fanned-out mounts fold into one; it is a sibling of the rows, never a text footer and never a reserved row; and its count is always present while heavier measures arrive only when asked, which is the `columns` dial vfs already has.

## 3. Truncation is reported as what was skipped and why, and the tools that shrink a number silently are the anti-pattern every study found independently

READ, study 02. zoekt partitions what it did not do: once a shard's `MatchCount` reaches `ShardMaxMatchCount` or the context is cancelled, the remaining documents are added to `FilesSkipped` in one step and to `FilesSkippedDueToCancellation` when cancellation was the cause; shards never opened increment `ShardsSkipped`, shards pruned by the ngram filter increment `ShardsSkippedFilter`, and `FlushReason` names why a streamed batch was emitted. The display truncators cut the sorted file list and return `hasMore` without touching `Stats`, so `FileCount` and `MatchCount` describe what was found while `len(Files)` describes what was shown. zoekt's only "total", `EstimateDocCount`, is documented as an upper bound. tokei's `inaccurate` flag is ORed up every level of its rollup to the total, the one example in that study of a truth flag on an aggregate.

READ, study 01. ncdu carries an `err` bit on a directory that could not be read and a `suberr` bit on every ancestor of one, set during the scan and propagated to the root, so a total whose subtree had an unreadable directory is marked at every level above it. `tree --filelimit N` refuses to open a directory with more than N entries, writes the refusal inline as `{"error": "…"}` inside that directory's JSON `contents`, and leaves it out of the totals.

EXECUTED, studies 01 and 04. `tree --du -J -L 1 src/vfs` reported `"size":84822740` and `-L 2` reported `"size":86096277` for the same directory, because the depth cut sits inside the tree builder and the root's size is the rollup of the entries that were listed; `-P "*.py"` cut it to 354398. No field says the walk was cut. fsspec's `du(total=True, maxdepth=1)` over `src/` returned `0` for a 90,199,312-byte tree, because `maxdepth` is passed to `find` as a walk cut-off and `src/` holds no files at depth 1. S3's `ListObjectsV2` sets `KeyCount` to the number of rows in the page, contents plus common prefixes, not the number of keys under the prefix, and clamps a caller's `max-keys` above 1,000 down to 1,000 in four places without saying so.

INFERRED. Three of the four researchers, working without sight of each other, named the same anti-pattern as the one thing not to adopt: a number that wears a total's name and shrinks with the view, the cap, or the page. The precedents to follow are zoekt's skipped-by-reason counters, ncdu's propagating incompleteness bit and tokei's ORed flag. For vfs the shape is one `exact` marker on the stats block that is the root of a per-row propagation, beside a skipped count partitioned by cause, and separate fields for entries matched and entries returned that never share a name.

## 4. A rollup is one whole-subtree walk carrying several measures, and depth, threshold and summary decide which rows print

READ, study 01. uutils `du` sends every finished per-directory `Stat` (apparent bytes, allocated blocks, inodes, newest time) to a printer, and the printer applies `--max-depth`, `--threshold` and `--summarize`; the walk is never shortened by any of them, `--summarize` with `--max-depth` is refused outright, and `choose_size` picks inodes, apparent bytes or blocks from the same record, so `du --inodes` is a count rollup and `du --apparent-size` a byte rollup over one identical walk. The four small `du`s (plan9port at 194 lines, sbase at 116, toybox at 165, busybox at 311) never vary this shape: the subtree measure is computed bottom-up and returned to the caller, `-s` is depth zero, `-c` is one more row named `total`, and hard links are deduplicated by device and inode. nushell's `du` returns each directory as the record `{path, apparent, physical, directories, files}` with `--max-depth` shaping only the nested `--long` listing while the walk that fills `apparent` and `physical` covers the whole subtree. dust builds one `Node` tree, fixes the measure at build time (bytes, a count of 1 per file under `-F`, or a timestamp), and lets the aggregation rule follow the measure: sum for bytes and counts, maximum for times. ncdu keeps `size`, `shared_size` and `items` per directory, where `shared_size` is a second rollup over the same walk answering a different question, what deletion would reclaim.

READ, study 03. Lucene's taxonomy facets reach the same shape from the index side: a hierarchical single-valued dimension rolls child counts into parents through the taxonomy's `parents` array, so `getTopChildren(10, "Path", "src", "vfs")` is a `du -d 1`-shaped question answered from per-document path ordinals stored at index time.

INFERRED. The rollup columns the brief proposed (`file_count`, `dir_count`, `total_bytes`, `total_lines` on a directory observation) are nushell `du`'s columns and uutils `du`'s printer measures, and the prior art fixes their contract: a directory's rollup is always its whole subtree, so `tree(max_depth=1, columns={"total_bytes"})` means `du -d 1` and never `tree -L 1 --du`; several measures come off one walk and the measure is the column the caller asks for, never a second traversal; and the rule that merges a measure upward is a property of the measure (sum for bytes, counts and lines; maximum for a newest time), which the stats block's additivity in section 2 already assumes.

## 5. No query engine maintains a count; the file systems that do keep a non-recursive counter per directory, batch the deltas, and label the fast answer

READ, study 03. None of datasette, sqlite-utils, Lucene, tantivy or qdrant stores a count. Lucene and tantivy store per-document ordinals or fast-field values at index time and count by scanning the hit set, choosing per segment between iterating hits and iterating ordinals; qdrant counts from the payload index's postings; datasette and sqlite-utils issue a `group by` per request. The only caches are datasette's `inspect-data.json` for databases declared immutable, used only when the count SQL is exactly the unfiltered table count, and sqlite-utils' `--save` snapshot, neither invalidated by anything but a rerun. The engines that are fast at counting are fast because the attribute is columnar and the scan is over ordinals, not because a total was kept.

READ, study 04. JuiceFS keeps a `dirStat{length, space, inodes}` per directory covering its direct children only, adjusts it in an in-memory map on every metadata mutation across all three engine families, flushes on a one-second ticker, and adds the pending deltas to the stored value on read. `info -r` and `summary` default to a fast mode that reads one counter per directory and still recurses into subdirectories because the counter is non-recursive; the CLI's own help text says the fast result may be inaccurate and offers `--strict` to re-walk; the guide points a caller who wants a cheap recursive total at a quota, which is maintained recursively for its root. MinIO's data scanner keeps a `dataUsageEntry` per folder whose fields exclude children until the branch is compacted, rescans a leaf once every 16 cycles, persists the result as `.usage.json`, and serves it from an admin endpoint stamped with `LastUpdate`. `statvfs` is O(1) because superblock block and inode counters are maintained on every allocation, the oldest maintained aggregate a file system offers.

READ, study 01. ncdu and macdirstat build their totals bottom-up once into memory and adjust them for the one writer they know about, ncdu's refresh and delete and macdirstat's delete, which subtracts the removed node's `size`, `file_count` and `dir_count` from every ancestor while the per-extension histogram is rebuilt from scratch because a histogram has no parent chain to walk. ncdu's binary export stores cumulative sizes and item counts per directory so a browser can open a directory without reading its subtree, while its JSON export stores none and the importer recomputes; its man page is the only honest account in the set of what drifts (hard-link counts between refreshes) and what overflows (8 EiB, 32-bit item counts).

INFERRED. Two futures for vfs's rollup columns have precedent and the studies rank them. The on-demand shape, one bounded `GROUP BY` over the subtree per call, is what every query engine and every coreutil does, and it is correct by construction because nothing is cached. The maintained shape has exactly one serious precedent in a file system over a database, JuiceFS, and its design has three parts that travel together: the counter is non-recursive, so a write touches one row and a recursive answer is a walk over counter rows bounded by the number of directories; the deltas are batched, so a 10,000-file write is not 10,000 counter updates; and the fast answer is labelled as such beside a strict re-walk the caller can choose. macdirstat's asymmetry adds a fourth: a tree rollup can be adjusted incrementally, a group-by histogram cannot, so the histogram verb stays on demand whatever the rollup columns do.

## 6. A group-by is a request of its own, capped by size plus one, and the engines worth copying put the cut's mass in the result

READ, study 03. All five engines make the group-by a separately named request that takes a key, a cap and an optional filter: datasette's `?_facet=<column>` on the listing URL (facets are plugins with `suggest` and `facet_results`), sqlite-utils' `analyze-tables` with `--common-limit`, Lucene's `Facets` over a `FacetsCollector` with `getTopChildren(topN, dim, path…)`, tantivy's `Aggregations` map on a collector with Elasticsearch-shaped `terms`, `histogram`, `date_histogram`, `range` and metric sub-aggregations, and qdrant's `POST /points/facet` with `key`, `limit`, `filter`, `exact`. Every one takes a key and a top-N; only tantivy has a bucket width (`interval` and `offset`) and explicit ranges; only Lucene has a path into a hierarchy; datasette's `DateFacet` fixes the grain to a day; qdrant has neither width nor path. The bucket is `{value, count}` everywhere, and datasette alone attaches a navigation affordance to each bucket, a `toggle_url` that is the same listing filtered to that value, which Lucene's `DrillSideways` pushes into the engine so a dimension does not disappear after drilling into it.

READ, study 03. Truncation is detected uniformly by fetching one more than the cap, and reported in five ways of rising usefulness. datasette fetches `facet_size + 1` and sets a boolean `truncated`, and caps its row count at 10,001 meaning "more than ten thousand". sqlite-utils reports `num_distinct` and leaves the subtraction to the caller. Lucene's `FacetResult` carries `value` (documents under the path, exact only when the dimension was indexed with `setRequireDimCount`) and `childCount` (labels seen) beside the top-N, so both the missing labels and the missing mass are recoverable by arithmetic. tantivy reports the missing mass directly as `sum_other_doc_count` and adds `doc_count_error_upper_bound` for the error a per-segment cut can introduce. qdrant reports nothing in the response and moves the guarantee into the request: `exact` defaults to false, the coordinator oversamples the limit fourfold with a floor of 128, and the inexact path can count a point that lives in two segments twice.

READ, study 04. JuiceFS's `GetTreeSummary` recurses to `depth`, sorts children by the chosen key, and when there are more than `topN` folds the rest into a single child whose path is the parent joined with `...` and whose `Size`, `Files` and `Dirs` are the sums of what was folded, so the parent's totals always equal the sum of its displayed children. dust's top-N leaves the remainder implicit: a directory whose children were not admitted still shows its exact total, and the reader subtracts.

EXECUTED, study 03. Over a 97-row corpus of `src/` at facet size 5, datasette returned `dir` with five buckets (`vfs/storage/backends/database` 33, `vfs/models` 17, `vfs` 16, `vfs/rendering` 8, `vfs/embedding` 6) and `"truncated": true`, and `ext` with four buckets (`py` 94, `pyi` 1, `so` 1, `typed` 1) and `"truncated": false`; sqlite-utils reported `num_distinct: 9` for `dir` and `num_distinct: 4` for `ext` with `least_common: null` because the distinct count was under the limit.

INFERRED. The histogram verb the brief proposed is qdrant's endpoint and tantivy's `terms` request with the cap-plus-one probe every engine uses, and the prior art fixes its result shape: the total under the scope, the number of distinct values seen, the top-N buckets, and the folded mass of the rest, which is tantivy's `sum_other_doc_count` and JuiceFS's `...` child and the "other" bucket in the brief. A boolean alone, datasette's shape, tells an agent something is missing but not how much; an unmarked inexact count, qdrant's default, tells it nothing. The one grain prior art offers that the brief did not name is tantivy's `interval` for a numeric or time bucket width, which a histogram over `size_bytes` or `updated_at` needs.

## 7. Work is bounded by a declared budget that refuses, and the count runs under the same gate as the listing

READ, study 03. Only datasette and tantivy refuse work past a budget. datasette's `facet_time_limit_ms` (200 ms; 50 ms for suggestions) interrupts the statement through SQLite's progress handler and lands the column's name in a `facets_timed_out` list beside `facet_results`, so a missing facet is named rather than silent; its suggestion pass looks at the first 1,000 rows and keeps a column only if its distinct count sits between 2 and the facet size. tantivy's `AggregationLimitsGuard` carries a memory limit (500 MB by default) and a bucket limit (65,000) and fails the request with an error when either is exceeded; `min_doc_count: 0` and a tiny histogram `interval` are the documented ways to hit it. The other three engines bound output and let the scan run.

READ, study 03. datasette's facet SQL wraps the view's own filtered listing SQL (`select <col>, count(*) from (<the listing SQL>) group by <col> … limit size + 1`), and the table-level permission check runs before the view builds that SQL, so a facet is computed only over rows the listing would have shown. It is the one engine in that study whose aggregate respects the caller's visibility by construction.

READ, study 02. zoekt's tenant check `continue`s a document before `FilesConsidered`, `FilesSkipped` or any other counter increments, under a comment marked as a security check, and `List` does the same per repository before `Stats.Add`, so a document the caller may not see appears in no statistic, not even as skipped. Its one shortcut, `EstimateDocCount`, returns the whole shard's document count from above the loop that applies the tenant check, so that fast count is not rights-filtered.

READ, study 04. `statvfs` has distinguished `f_bfree` from `f_bavail`, blocks available to unprivileged processes, since its design, and Linux ext4 clamps every `statfs` total to the caller's project quota so a caller inside a quota'd directory sees its own ceiling. mirage's `CapacityResult` carries a state enum (`QUOTA`, `ELASTIC`, `NA`, `UNKNOWN`) with every count `None` outside `QUOTA`, its `df` prints a literal `-` rather than a fabricated number, and its listings carry `partial` and `window` flags; agentfs, by contrast, answers FUSE's `statfs` by subtracting two whole-table SQL aggregates from a constant 4 TB virtual disk.

INFERRED. Three independent designs reached the rule vfs proposed: compute the aggregate under the caller's rights and say when it is partial. datasette's wrap-the-gated-query is the SQL shape that satisfies "a count never leaks an entry the caller may not list" by construction; zoekt's filter-before-any-counter is the loop shape; and zoekt's leaking shortcut is the warning that every fast path, a cached counter included, must run through the same gate. The budget that refuses, tantivy's guard and datasette's time limit, is the shape vfs's production posture already requires of statements, applied to the aggregate's output rather than only to its bind parameters.

## 8. Count modes on search verbs are printer modes that replace the rows, and the one documented bug in them is that two modes can disagree

READ, study 02. ripgrep's summary printer has six kinds (`Count`, `CountMatches`, `PathWithMatch`, `PathWithoutMatch`, and two quiet forms) reached from `-c`, `--count-matches`, `-l`, `--files-without-match` and `-q`; each sets one `SearchMode`, so the modes are mutually exclusive and the last wins. git grep's `-c`, `-l` and `-m`, codesearch's `-c` and `-l`, and zoekt's `-l` share the shape. The flag docs record the hazard: `-l` quits at the first match while `-c` must read the whole file and may then hit binary data and drop it, so the two can disagree about the same file, and ripgrep's summary printer documents this as accepted. With `-m 1`, both ripgrep and git grep print `1` for every matching file (EXECUTED, study 02), the cap-then-count shape.

READ, study 04. pyfilesystem2's `glob(pattern).count()` is a terminal on a lazy query returning `Counts(files, directories, data)`, the same traversal as iterating the glob, so a caller who wants both rows and counts walks twice; fsspec's `du` calls `find` for names and then `info` once per name, throwing away the detail records `find` already had.

INFERRED. Count modes are universal and agents reach for them, so the brief's `grep` count option has precedent in every tool studied; what prior art warns against is building them as modes that stop at different points. In vfs's column model, a per-file match count is one more field on the observation the same pass fills, and the stats block in section 2 carries the run total, so a count and the rows it summarises cannot diverge and the walk is not repeated.

## 9. What the four studies rank as the moves to adopt and the one to refuse

READ, the closing sections of all four studies. Adopt: an additive stats struct as a typed sibling of the rows on every result, counts always present and heavier measures on request, with entries considered, entries returned, bytes, and a skipped count partitioned by reason (studies 01 and 02). Adopt: rollup columns computed over the whole subtree in one walk with depth trimming only the rows, several measures off that walk, and an incompleteness bit per row that propagates to the result's `exact` marker (study 01). Adopt: truncation as data in the histogram result, the total under the scope, the distinct values seen, the buckets and the folded mass of the rest, with the cap-plus-one probe (studies 03 and 04). Adopt: a declared budget that refuses, the aggregate computed under the same gated query as the listing, and rights filtering before any counter, fast paths included (studies 02 and 03). Adopt, if the rollup columns are ever maintained: JuiceFS's non-recursive per-directory counter with batched deltas and a labelled fast mode beside a strict re-walk (study 04). Refuse: a total that shrinks with the view, the cap or the page with nothing to say so, which is `tree -L --du`, fsspec's `maxdepth`, ripgrep's and git grep's `-m` and S3's `KeyCount` (all four studies); mutually exclusive count modes that stop at different points (study 02); an inexact-by-default count with no marker in the response (study 03); a human-formatted number in structured output (study 01).

INFERRED. The three layers survive the research as three things rather than one, because prior art keeps them apart too: no engine puts a group-by on a column, no coreutil carries buckets as a side channel, and the cheapest thing any system attaches to every result is a bounded count. The one place the brief's design was weaker than prior art is the grain of the histogram verb, which needs a bucket width for numeric and time keys; the one place it was stronger than anything studied is the combination of an exactness marker, a rights-judged count and a total before truncation in a single result, which no studied system offers together.

## What this memo does not settle

The cost of a maintained per-directory counter on Postgres, SQL Server and Oracle at a 10,000-file write, in rows touched and statements issued, against the cost of an on-demand subtree `GROUP BY` at the same batch, is an experiment to run against the real engines before a spec chooses between the two shapes in section 5; no study measured it and JuiceFS's figures are READ, not EXECUTED. How the histogram verb hands back buckets past the top-N is for a reading of tantivy's `composite` aggregation, the one paginated group-by among the engines, which study 03 did not reach. A caller-defined bucket list for a size histogram is for a reading of Lucene's `facet/facetset` and `rangeonrange` subpackages, which study 03 did not reach. The `getattrlistbulk` against `readdir` plus `stat` cost for a 10,000-entry directory, which bears on a local file backend's rollup, is an experiment study 01 named and did not run. GNU coreutils' own `du` and `wc` were not cloned; uutils reimplements them and busybox's header says it matches GNU output, but the GNU source was not read.

## One line

Three shapes, three layers: a stats block that adds up and names what it skipped, a rollup whose depth trims rows and never the walk, and a group-by of its own that probes cap plus one and returns the mass it cut; no engine keeps a count, the one file system that does keeps it per directory and labels the fast answer, and the only rights rule worth having filters before the first counter moves.
